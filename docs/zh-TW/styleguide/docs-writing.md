# 文件與對外撰寫規則

本文頁規範 ErisPulse 的文件撰寫風格與對外（README/發布頁）撰寫。目標讀者為文件貢獻者與負責維護 README 的人。

## 一、文件行文

### 1. 價值先行

每篇文件的第一屏應回答一個問題："閱讀這篇我能得到什麼"。對於按需查閱類文件，使用統一的 `> [!TIP]` 觸發描述開頭——**"什麼時候需要閱讀這篇：……不需要則跳過"**；對於核心必讀類文件，使用 `> [!NOTE]` 標註其在閱讀路徑中的位置。

### 2. 實例優先於敘述

能用可運行的代碼塊說明的，不寫描述性段落。代碼示例必須可直接複製運行（包含 import 與最小上下文），不使用 `...` 省略關鍵步驟。

### 3. 觸發描述即檢索入口

文件開頭的一句"什麼時候閱讀"就是 AI 助手與搜索的匹配文本——應寫具體場景（"當你的適配器需要……"），不寫抽象歸類（"本文介紹……"）。

### 4. 結尾按意圖分組

文末"下一步"連結按讀者意圖分組（想深入了解 X → 鏈接 A；遇到問題 Y → 鏈接 B），不放無差別的目錄平鋪。

### 5. 變更記錄寫作

更新日誌記錄發布狀態之間的淨差異，不記錄開發過程：同一主題多次修改更新既有條目為最終形態；版本內引入又版本內修復的不單列；無用戶感知的內部調整不記。完整規範見 `CHANGELOG.md` 頭部「寫作規範」。

### 6. 版本標註規範

文件正文的版本標註只寫**行為差異**，不寫准入門檻：

- **正文標註行為差異**：僅在行為隨版本變化時標註，且必須說清"差異是什麼"——例如"X.Y.Z 起 `reload()` 預設全量重載（此前僅重載變更模組）"。讀者可據此判斷自己的程式碼在新舊版本下行為是否不同
- **"本特性需要 X+"類准入標註集中到版本速查表**：不散落在各篇正文；統一收斂在 `docs/zh-TW/README.md` 的版本速查表，正文需要時連結過去即可
- **示例中的版本號用佔位符**：文件示例代碼裡出現的版本號寫 `x.y.z` 等佔位形式，避免隨發布頻繁過時（正文標註真實版本號的行為差異除外）

## 二、對外頁面（README / 發佈頁）

### 1. 三段式骨架

1. **價值主張**：用一句話說清楚「用它能做什麼」，緊接 30 秒內可驗證的效果（最小範例 / 演示影片 / 截圖）
2. **證明**：功能卡片、真實運行截圖、生態規模——證據按說服力排序，不堆砌
3. **行動入口**：安裝命令一行可複製；每條主要路徑（快速上手 / 深入開發 / 生態瀏覽）提供明確的下一步連結

### 2. 场景化而非罗列

功能列表每條回答「解決什麼問題」，而非「我們有什麼」。生態展示每項附一句適用場景與最小範例，不只貼 logo 了事。

### 3. 語言與口徑

- **主版語言**：現狀——以中文（zh-CN）為文件主源，英文等其他語言由 CI 翻譯流程從 zh-CN 自动生成（只改 `docs/zh-CN`，其他語言隨 CI 同步）；目標——長期演進為英文主版。在目標達成前，對外頁面按「中文主源、多語言翻譯產物」維護，其他語言不標註「待同步」（CI 保證自動同步）
- 不在對外頁面使用內部行話（模組代號、里程碑名、內部流程詞）——讀者是第一次見到專案的人
- 數字與承諾（版本、效能、支援範圍）必須與文件正文一致，過期內容寧可刪除勿留

### 4. 快速上手頁的轉化結構

`quick-start` 類頁面：先給「60 秒效果」（安裝 → 三行程式碼 → 運行結果），再展開解釋；使用者先看到成功，才願意繼續閱讀。
