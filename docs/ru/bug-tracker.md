# Трекер ошибок

Документация отслеживает известные ошибки ErisPulse SDK и их исправления, отсортированные по времени исправления.

> **Для читателя**
> Никакое программное обеспечение не может быть идеальным, даже самые внимательные разработчики могут оставить небольшие ошибки. В этот трекер включены только проблемы, которые реально влияют на работу — те, что слишком незначительны, чтобы даже назвать их «легкими», здесь не представлены. Хотя в списке значится много пунктов «серьезного» уровня, цель публичной записи этих ошибок — сделать отслеживание и восстановление более плавным, а не вызывать беспокойство: возможность видеть, записывать и исправлять проблемы — это доказательство постоянного улучшения проекта. Не стоит беспокоиться, увидев этот список: это инструмент для диагностики, а не источник страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ корневой причины, диапазон версий, в которых она влияет, схему исправления и т.д. Рекомендуется перед обновлением проверить, охватывает ли «диапазон версий» используемую вами версию.
> - Если вы хотите добавить новую запись об ошибке, добавьте её в соответствующее место, следуя описанным ниже полям и классификации серьезности/типа.

## Описание полей

### Обязательные поля

| Поле | Описание |

| **Дата исправления** | Дата публикации соответствующей версии исправления, в формате `YYYY/MM/DD` |

| **Тип** | Отмечено в соответствии с «классификацией типов», может быть комбинированным (например, `адаптер / маршрутизация`) |

## Шкала серьезности

| Идентификатор | Уровень | Критерии | Типичные проявления |
|---------------|---------|---------|----------------------|
| 🔴 | Серьезный | Причина сбоя процесса, потеря или повреждение данных, полная недоступность основных функций, уязвимости безопасности | OOM Kill, невозможность отправки сообщения, невозможность загрузки модуля, неудачное горячее перезагрузка |
| 🟡 | Средний | Нарушение функциональности, но есть пути обхода, недоступность неосновных функций, случайные проблемы | Неверное определение состояния, повторное срабатывание, истечение кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на основную функциональность, проблемы качества кода или пользовательского опыта, потенциальные риски, не проявившиеся | Устаревший API, мертвый код, отсутствие предупреждения в журнале |

## Исправленные ошибки

### [BUG-001] Повторная регистрация обработчиков событий приводит к многократной обработке событий

**Проблема**: При регистрации обработчиков с помощью нескольких декораторов, таких как `@message` / `@notice`, одно и то же событие срабатывает многократно, что приводит к многократному выполнению команд и дублированию вывода журналов.

**Причина**: `BaseEventHandler` при регистрации обработчиков в шине событий адаптера не имел логики дедупликации; каждый декоратор монтируется в шину один раз, и при диспетчеризации событий вызывается многократно.

**Затронутые версии**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия исправления**: 2.2.1-dev.0

**Содержание исправления**: Оптимизирован `BaseEventHandler`, чтобы гарантировать регистрацию обработчика для каждого типа события в адаптере только один раз, предотвращая повторные срабатывания.

**Дата исправления**: 2025/08/18

**Критичность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера в команде Init

**Проблема**: При интерактивной инициализации с помощью команды `ep init` выбор настройки адаптера вызывает ошибку типа:

```
Интерактивная инициализация завершилась ошибкой: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: В версии 2.3.7 при изменении путей файлов конфигурации типы параметров методов оказались несогласованными. `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри использует оператор `/` объекта `Path` для конкатенации путей.

**Затронутые версии**: 2.3.7 - 2.3.9-dev.1

**Версия исправления**: 2.3.9-dev.1

**Содержание исправления**: Тип параметра метода `_configure_adapters_interactive_sync` изменён с `str` на `Path`; при вызове теперь передаётся объект `Path` напрямую.

**Дата исправления**: 2026/03/23

**Критичность**: 🟡 Средняя

**Тип**: CLI

### [BUG-003] Командные события перестают работать после перезапуска

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные через `@command`, перестают срабатывать: после отправки команды бот не отвечает.

**Причина**: После очистки шины событий в `adapter.shutdown()` состояние `_linked_to_adapter_bus` у `BaseEventHandler` не сбрасывается в `False`, из-за чего метод `_process_event` считает, что обработчик уже смонтирован в шину адаптера, и пропускает повторное монтирование.

**Затронутые версии**: 2.2.x - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Содержание исправления**: Введено отслеживание состояния `_linked_to_adapter_bus`; после отключения от шины в `_clear_handlers()` при следующем `register()` выполняется автоматическое повторное монтирование, что подходит для сценариев shutdown/restart.

**Дата исправления**: 2026/04/09

**Критичность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-004] Обработчики событий жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла продолжают существовать и срабатывать повторно, из-за чего одно и то же событие обрабатывается несколько раз.

**Причина**: Словарь `lifecycle._handlers` никогда не очищался при `uninit()`, поэтому после restart старые обработчики сосуществуют с новыми.

**Затронутые версии**: 2.3.0 - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Содержание исправления**: В конце процесса очистки `Uninitializer` (после отправки всех событий) словарь `lifecycle._handlers` очищается.

**Дата исправления**: 2026/04/09

**Критичность**: 🟡 Средняя

**Тип**: Среда выполнения

### [BUG-005] detail_type у Event.is_friend_add/is_friend_delete не соответствует стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, а `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, однако стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Это не совпадает со значениями, используемыми декораторами `on_friend_add`/`on_friend_remove` в `notice.py`, из-за чего при срабатывании обработчиков, зарегистрированных через декораторы, соответствующие методы проверки `is_friend_add()`/`is_friend_delete()` возвращают `False`.

**Причина**: В `wrapper.py` использовались нестандартные наименования, тогда как в `notice.py` использовались корректные наименования по стандарту OB12.

**Затронутые версии**: С момента внедрения по настоящее время

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Значение сопоставления `is_friend_add()` изменено с `"friend_add"` на `"friend_increase"`, а `is_friend_delete()` — с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Критичность**: 🟡 Средняя

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, что приводит к некорректному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает набор `_started_instances`. Если вызвать `clear()` во время работы адаптера, в `_started_instances` останутся висячие ссылки, что приводит к ошибочной оценке состояния после перезапуска.

**Причина**: При добавлении `_started_instances` в 2.4.0-dev.1 соответствующая очистка в `clear()` не была реализована.

**Затронутые версии**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: В метод `clear()` добавлен вызов `self._started_instances.clear()`.

**Дата исправления**: 2026/04/13

**Критичность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания future и получения временных меток; этот метод устарел в Python 3.10+, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Это не согласуется с `get_running_loop()`, используемым в методе `wait_for()` того же файла `wrapper.py`.

**Причина**: При разработке использовался устаревший API; впоследствии добавленный `wait_for()` использовал корректный API, но ретроспективное исправление старого кода не выполнялось.

**Затронутые версии**: 2.3.0-dev.0

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Два вызова `asyncio.get_event_loop()` в `command.py` заменены на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Критичность**: 🟢 Незначительная

**Тип**: Система событий

### [BUG-008] События отключения ботов дублируются в процессе shutdown

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров `_update_bot_status()` многократно отправляет события отключения ботов в процессе завершения работы, из-за чего одна и та же группа ботов несколько раз помечается как офлайн и несколько раз вызываются события жизненного цикла `adapter.bot.offline`.

**Причина**: Система отслеживания статуса ботов, добавленная в 2.4.0-dev.1, не устанавливала флаг «идёт завершение работы» во время `shutdown()`, поэтому `_update_bot_status()` не могла отличить обычное отключение от каскадного отключения в процессе завершения работы.

**Затронутые версии**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, который устанавливается в True в начале `shutdown()` и сбрасывается в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку событий в процессе завершения работы.

**Дата исправления**: 2026/04/21

**Критичность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-009] Синхронный доступ LazyModule к BaseModule приводит к незавершённой инициализации

**Проблема**: Когда пользователь обращается к атрибутам лениво загружаемого BaseModule в синхронном контексте, модуль инициализируется асинхронно через `loop.create_task()` без ожидания завершения, из-за чего при доступе к атрибуту инициализация может быть не завершена, что вызывает состояние гонки.

**Причина**: `_ensure_initialized()` для BaseModule вызывает `loop.create_task(self._initialize())` и немедленно возвращается, не гарантируя завершения инициализации.

**Затронутые версии**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule теперь выполняется через `asyncio.run(self._initialize())`, гарантируя завершение инициализации перед возвратом. Свойства прозрачного проксирования сохранены: пользователю не нужно ощущать различия между синхронным и асинхронным режимами.

**Дата исправления**: 2026/04/21

**Критичность**: 🟡 Средняя

**Тип**: Система загрузки

### [BUG-010] Многопоточная запись в системе конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция чтения-модификации-записи в `_flush_config()` не является атомарной, что может привести к потере части записей.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет файловой блокировки, а таймер в `_schedule_write` может срабатывать несколько раз, вызывая перезапись.

**Затронутые версии**: 2.3.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавлен механизм файловой блокировки (`_file_lock`) для обеспечения атомарности файловых операций
2. Запись во временный файл с последующим атомарным переименованием (`os.replace`/`os.rename`)
3. Улучшена логика отмены и перепланирования таймера в `_schedule_write`

**Дата исправления**: 2026/04/21

**Критичность**: 🔴 Критическая

**Тип**: Система конфигурации

### [BUG-011] CTRL+C не останавливает программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие CTRL+C не завершает программу. После нормального запуска программы и вывода информации о маршрутизирующем сервере CTRL+C полностью не реагирует, процесс можно завершить только принудительно через диспетчер задач. При запуске через `epsdk run` остановка работает нормально — но `epsdk run` работает через модель подпроцессов.

**Причина**: Функция `serve()` ASGI-сервера Hypercorn внутри регистрирует собственный обработчик SIGINT через `signal.signal(SIGINT, handler)`, переопределяя стандартный механизм обработки `KeyboardInterrupt` в Python. При запуске Hypercorn как фоновой задачи через `asyncio.create_task()` внутренний процесс shutdown Hypercorn не может корректно запуститься (поскольку он ожидает режим `worker_serve`), в результате сигнал CTRL+C поглощается Hypercorn без каких-либо действий по очистке.

**Затронутые версии**: 2.3.6 - 2.4.2

**Версия исправления**: 2.4.3-dev.0

**Содержание исправления**:
1. ASGI-сервер переключён с Hypercorn на Uvicorn (изменение зависимостей в `pyproject.toml`)

```
_load_accounts() удалена
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
```

- адаптеры, не объявляющие `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращает `(None, None)`

- адаптеры, переопределяющие `_load_accounts` или вручную устанавливающие `_accounts_data`: переопределяют после `super().__init__()`, имеют наивысший приоритет

```

    → convert_to_send_type("group_member_increase") отсутствует в таблице сопоставления → откат к "user"

      → target_id = event["user_id"]  ← личные сообщения нового участника (а не группа)
```

**Версия исправления**: 2.7.0-dev.3

**Содержание исправления**: В `infer_receive_type()` добавлена проверка — `detail_type` возвращается напрямую только если он является известным типом беседы (стандартным или пользовательским); в противном случае корректный тип беседы выводится по полю ID (`group_id` / `channel_id` / `user_id` и т.д.).

**Проблема**: Несколько пользователей сообщили, что после использования `config.setConfig(key, value)` (по умолчанию `immediate=False`) конфигурация их модулей не записывается в `config.toml`, тогда как конфигурация других модулей сохраняется нормально. 2. **Дефект потоков**: `_watch_loop` оперирует `_write_timer`/`_dirty_keys` без захвата `_lock`, существует состояние гонки данных с `setConfig` (пишет `_dirty_keys` под блокировкой) и `_schedule_write` (пишет `_write_timer` под блокировкой).

**Цепочка первопричины**:
```
Модуль A setConfig(immediate=True) → flush записывает на диск, mtime меняется

      → _dirty_keys.clear() → ключи, ожидающие записи пользовательского модуля, молча отбрасываются
        → после перезапуска конфигурация отсутствует
```

**Затронутые версии**: 2.6.0 - 2.7.0

**Версия исправления**: 2.7.1

**Содержание исправления**:

### [BUG-036] Эпизодические сбои записи конфигурации (ENOENT) при совместном использовании каталога конфигурации несколькими экземплярами

**Проблема**: в сценариях Docker-развёртывания (несколько контейнеров монтируют один и тот же каталог конфигурации хоста) в журнале эпизодически появляются подряд две записи `Failed to write configuration file ... [Errno 2] No such file or directory: '...config.toml.tmp' -> '...config.toml'`. Данная запись конфигурации отбрасывается (старая конфигурация полностью сохраняется, потери конфигурации не наблюдалось), функциональность не затронута, но повторяющиеся предупреждения мешают диагностике, а ожидающие записи элементы конфигурации попадают на диск только при следующей записи.

**Причина**: цепочка первопричин: `_flush_config` / `setConfigTemplate` используют временный файл с **фиксированным именем** `config.toml.tmp` для нового содержимого, после `write()` без `fsync` сразу выполняется `rename()`. Когда два экземпляра ErisPulse используют один каталог конфигурации, `open("w")` экземпляра B может **обрезать** (truncate) временный файл, который в этот момент пишет экземпляр A → при rename в A цель уже забрана B или содержимое обрезано, возникает ENOENT (те самые две подряд идущие ошибки в журнале пользователя). В reported случаях проявлялось лишь предупреждение о сбое записи (старая конфигурация сохранялась); при ещё более крайнем чередовании таймингов rename может вывести пустой/полуцелый `config.toml` (потенциальный риск, в реальной среде пока не проявился). В сценарии с одним экземпляром отложенное выделение ext4 также создаёт окно сбоя «метаданные rename попадают на диск раньше блоков данных» (SIGKILL / отключение питания). `_file_lock` — это `threading.RLock` внутри процесса, он никак не ограничивает записи между процессами/контейнерами.

**Затронутые версии**: 2.2.0-dev.0 - 2.8.0

**Версия исправления**: 2.8.1

**Содержание исправления**: запись конфигурации единообразно сведена к `_atomic_write_text()`: `mkstemp` в том же каталоге создаёт уникальный для процесса временный файл (устраняет борьбу за фиксированное имя, при нескольких экземплярах деградирует до last-writer-wins, ENOENT больше не возникает) → по завершении записи `flush + fsync` принудительно сбрасывает данные на диск (устраняет окно «rename уже вступил в силу, данные ещё не на диске») → `os.replace` атомарно заменяет целевой файл (атомарно и на POSIX, и на Windows; в любой момент на диске либо целое старое содержимое, либо целое новое); на POSIX дополнительно выполняется fsync каталога конфигурации. Все три точки записи — `_flush_config`, `setConfigTemplate` и миграция конфигурации из корневого каталога — переключены; логика очистки в путях исключений переработана под уникальное имя временного файла. Добавлено **обнаружение нескольких экземпляров**: при запуске advisory lock (POSIX `flock` / Windows `msvcrt.locking`) эксклюзивно захватывает lock-файл каталога конфигурации `.erispulse_config.lock`; если он занят — выводится i18n-предупреждение (не блокирует запуск), блокировка автоматически освобождается ОС при завершении процесса, фантомных блокировок нет.

**Дата исправления**: 2026/09/13

**Шаги воспроизведения**: ① два контейнера монтируют один и тот же каталог `config/` хоста и одновременно запускают ErisPulse; ② любой экземпляр инициирует запись конфигурации (например, модуль регистрирует конфигурацию по умолчанию); ③ в журнале наблюдается предупреждение о сбое записи ENOENT, данная запись отбрасывается (старая конфигурация сохраняется).

**Связано**: отчёт пользователя (контейнеры 1Panel ×2)

**Регрессионный тест**: `tests/unit/test_unit_config_atomic_write.py` (полная запись содержимого / отсутствие остатков временных файлов / при сбое записи исходный файл сохраняется / файл всегда валиден при параллельной записи двух экземпляров / создание lock-файла / предупреждение о нескольких экземплярах / атомарная запись при миграции)

### [BUG-038] Runtime-привязки с persist=False попадают на диск попутно с персистентными записями, «воскресают» с диска после выгрузки модуля

**Проблема**: runtime-привязки, записанные через `scope.set(path, value, persist=False)` (документация обещает: не записываются на диск, теряют силу при перезапуске процесса, очищаются при выгрузке модуля), при любой посторонней записи с `persist=True` (значение по умолчанию, например `set_module` модуля / сохранение конфигурации в WebUI) дифференциально записываются в пользовательский `config.toml`; после этого, даже если модуль выгружен и runtime-привязка разрегистрирована, при следующей перезагрузке конфигурации привязка «воскресает» с диска и продолжает действовать, сохраняется после перезапуска процесса — что противоречит семантическому контракту «runtime-привязки не записываются на диск» и крайне трудно поддаётся диагностике.

**Причина**: цепочка первопричин: `ScopeManager.set()` сначала записывает значение в дерево конфигурации в памяти `_data` (runtime-привязки тоже записываются прямо в `_data`) → ветка персистентности делает глубокую копию снимка **всего `_data`** и передаёт его в `update_erispulse_config` для дифференциальной записи на диск → в снимок примешиваются значения привязок с `persist=False`. `delete(persist=True)` имеет тот же источник: живая ссылка на `_data` (узел `parent`) передаётся в отложенную очередь грязных записей, и во время отложенной записи runtime-изменения соседних ключей под этим узлом записываются на диск вместе с ней; кроме того, пока живая ссылка задерживается в грязной очереди, существует окно перекрёстного загрязнения между записями.

**Затронутые версии**: 2.8.0-dev.2 - 2.9.0-dev.0

**Версия исправления**: 2.9.0-dev.2

**Проблема**: записи, возвращаемые всеми интерфейсами запросов к входящим (`get()` / `get_by_trace()` / `event.history()`), содержат только `role/text/ts/event_id` — существующий в слое хранения столбец `sender` отбрасывается уровнем запросов, при воспроизведении группового чата сообщения разных участников неразличимы на уровне API (AI принимает участника B за собеседника A из предыдущего раунда); входящие записи к тому же не архивируют метаданные момента события, такие как никнейм, и при последующем обратном запросе получается «нынешний никнейм», а не «никнейм на тот момент».
**Причина**: в комментарии при добавлении столбца `sender` в 2.8.0 прямо указывалось его назначение — «восстановление источника сообщения при воспроизведении», но ни Select, ни построение возвращаемых данных его не несли (упущение реализации); архивирование метаданных же вообще не проектировалось — у `append()` нет канала meta, в структуре таблицы нет соответствующего столбца.
**Затронутые версии**: 2.8.0 - 2.11.0 (столбец sender введён с 2.8.0)
**Версия исправления**: 2.11.1-dev.0
**Содержание исправления**: добавлен столбец `meta` (контракт белого списка: для входящих nickname/self_id/sub_type/message_id, для исходящих контекст отправки и module; старые таблицы мигрируют автоматически, при отсутствии поддержки ALTER в бэкенде — тихий откат к `{}`); `append()` получил параметр `meta`, проходящий через буфер в памяти и пакетную запись на диск; `get` / `recent` / `get_by_trace` / `event.history` единообразно возвращают `sender` + `meta` (при повреждении JSON — откат к `{}`).
**Связано**: #467 (в той же партии #468 / #469 / #470)
**Регрессионный тест**: tests/unit/test_unit_transcript_attribution.py::TestSenderMetaReadback / TestMetaMigration

**Серьёзность**: 🟡 средняя
**Тип**: входящие беседы (inbox) / система хранения

### [BUG-049] Эхо self-сообщений бота во входящих записывается как user, загрязняя атрибуцию входящих

**Проблема**: когда платформы/протоколы с включённым эхо сообщений (OneBot v11 `report-self-message`, Telegram outgoing и т.д.) сообщают о сообщениях, отправленных самим ботом, как о событиях message, во входящих всегда записывается `role="user"` — реплики самого бота неотличимы от реального ввода пользователя, нижестоящие модули обрабатывают реплики бота как пользовательский ввод (AI отвечает на «сказанное пользователем»), статистика по role искажается.
**Причина**: точка автоматической записи входящих (`Core/adapter.py`) безусловно записывает `role="user"` для всех `event_type == "message"`, не потребляя поле `self` для определения эха бота — при том, что логика автоматического обнаружения бота, следующая сразу за ней, уже потребляет то же самое поле (поле доступно в момент записи, но логика записи его упустила).
**Затронутые версии**: 2.8.0 - 2.11.0 (автоматическая запись во входящие введена с 2.8.0)
**Версия исправления**: 2.11.1-dev.0
**Содержание исправления**: перед записью эхо распознаётся по `self.user_id == user_id` и обрабатывается по новой настройке `ErisPulse.transcript.self_echo` в трёх режимах: `"bot"` (по умолчанию) — записывается `role="bot"` + `sender=self_id` + `meta.self_echo=true`; `"skip"` — не записывается; `"user"` — сохраняется старое поведение. Для платформ без эха (self отсутствует или не совпадает) поведение по каждому полю остаётся неизменным.
**Связано**: #470 (опирается на столбец meta из #467 для хранения маркера self_echo)
**Регрессионный тест**: tests/unit/test_unit_transcript_attribution.py::TestSelfEcho

**Серьёзность**: 🟡 средняя
**Тип**: адаптер / входящие беседы (inbox)

### [BUG-050] Выполнение epsdk restart внутри контейнера приводит к немедленному завершению контейнера

**Проблема**: когда фреймворк работает как главный процесс контейнера (PID 1) (официальный образ `CMD ["epsdk", "run"]` или скрипт прямого запуска), после установки компонента через `ep i <пакет>` и выполнения по подсказке `epsdk restart` контейнер сразу завершается и больше не поднимается — установленный новый компонент не вступил в силу, сервис прерван.
**Причина**: реализация `epsdk restart` — «завершить работающий экземпляр + перезапустить с исходными параметрами» — перезапуск выполняется под управлением процесса epsdk CLI. В сценарии контейнера целевой экземпляр — это PID 1 (главный процесс контейнера), SIGINT/SIGTERM приводит к его завершению, что означает уничтожение всего PID namespace, CLI сам и дочерний процесс, ожидающий перезапуска, убиваются вместе, и перезапуск так и не может произойти.
**Затронутые версии**: 2.11.0 - 2.11.2 (управление экземплярами через runtime.json введено с 2.11.0; в более ранних версиях команды restart не было)
**Версия исправления**: 2.12.0-dev.0
**Содержание исправления**: когда `epsdk restart` обнаруживает в файле состояния `pid == 1` (признак главного процесса контейнера), он больше не завершает процесс с перезапуском, а отправляет процессу фреймворка `SIGUSR1`, и фреймворк выполняет мягкий перезапуск на уровне компонентов внутри процесса (`sdk.restart()`: конвейер горячей перезагрузки модулей и адаптеров, entry-point недавно установленного адаптера вступает в силу немедленно во время работы); `sdk.run()` регистрирует обработчик `SIGUSR1`, обслуживающий этот канал. Сценарий перезапуска всего процесса передаётся перезапуску контейнера (`docker restart` / политика restart).
**Регрессионный тест**: tests/unit/test_unit_cli_runtime.py::TestRestartContainerHot

**Серьёзность**: 🔴 критическая (перезапуск при контейнерном развёртывании означает прерывание сервиса)
**Тип**: CLI / развёртывание
