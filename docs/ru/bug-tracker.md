# Отслеживание ошибок

Документация содержит известные ошибки ErisPulse SDK и информацию об их исправлении, отсортированных по времени исправления.

> **Для читателя**
> Никакой программный продукт не является идеальным с самого начала, даже самые внимательные разработчики могут допускать небольшие ошибки. В этом списке собраны только те проблемы, которые реально влияют на работу — те, что слишком мелкие, чтобы даже считаться «незначительными», здесь не представлены. Хотя в списке значительное количество пунктов «серьезных», первоначальная цель публикации этих ошибок — обеспечить более плавное выявление и отслеживание, а не создавать беспокойство: проблемы, которые можно увидеть, зафиксировать и исправить, сами по себе являются доказательством постепенного улучшения проекта. Видя этот список, не стоит волноваться — он служит инструментом для поиска и устранения проблем, а не источником страха.

> **Как читать и правила ведения**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ причины, диапазон версий, подверженных влиянию, и решение. Рекомендуется перед обновлением проверять, охватывает ли «диапазон версий» используемую вами версию.
> - Если вы хотите добавить новую запись об ошибке, дополните соответствующее место, следуя спецификации полей и классификации серьезности/типа, описанным ниже.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|----------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем аномальное поведение. Стремитесь предоставить сообщение об ошибке или типичную сцену |
| **Причина** | Анализ корневой причины, указывающий на конкретный дефект кода (включая «диаграмму корневой цепочки» для сложных сценариев) |
| **Влияющие версии** | Интервал версий, затронутых ошибкой, формат `Версия введения - Версия исправления` (включая бета-версии) |
| **Исправленная версия** | Конкретный номер версии, в которой была исправлена ошибка |
| **Содержание исправления** | Краткое описание решения, включая ключевые изменения кода |
| **Дата исправления** | Дата выпуска соответствующей версии с исправлением, в формате `YYYY/MM/DD` |
| **Серьезность** | Отметка по «Классификации серьезности» ниже |

| **Тесты обратного воспроизведения** | Расположение тестовых случаев для проверки исправления и предотвращения повторного появления ошибки | При наличии соответствующих тестов pytest рекомендуется дополнить |

## Уровни серьезности

| Идентификатор | Уровень | Критерии определения | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Критический | Приводит к сбою процесса, потере или повреждению данных, полной недоступности основных функций, уязвимостей безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Нарушение функций, но существуют пути обхода, неосновные функции не работают, случайные проблемы | Неправильное определение состояния, повторное срабатывание, истечение срока действия кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на основные функции, только проблемы качества кода или пользовательского опыта, потенциальные риски не проявляются | Устаревший API, мертвый код, отсутствие логов предупреждений |

## Исправленные ошибки

### [BUG-001] Дублированная регистрация обработчика событий приводит к многократной обработке события

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков, одно и то же событие будет многократно запускаться, что приводит к многократному выполнению команд, дублированию вывода логов.

**Причина**: `BaseEventHandler` при регистрации обработчика в событийную шину адаптера не содержит логики дедупликации, каждый декоратор будет добавлять обработчик один раз, и при отправке события будет вызываться несколько раз.

**Версии с ошибкой**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия с исправлением**: 2.2.1-dev.0

**Исправление**: Оптимизирован `BaseEventHandler`, чтобы убедиться, что обработчик для каждого типа события регистрируется в шине адаптера только один раз, предотвращая многократный запуск.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера при инициализации командой init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации при выборе конфигурации адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметры типа `str`, но внутри используется оператор `/` для объединения путей с `Path`.

**Версии с ошибкой**: 2.3.7 - 2.3.9-dev.1

**Версия с исправлением**: 2.3.9-dev.1

**Исправление**: Изменен тип параметра метода `_configure_adapters_interactive_sync` с `str` на `Path`, вызовы теперь передают объект `Path` напрямую.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средняя

**Тип**: CLI

---

### [BUG-003] Командные события не срабатывают после перезапуска

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные через `@command`, не будут срабатывать, что проявляется в том, что после отправки команды бот не отвечает.

**Причина**: `adapter.shutdown()` очищает событийную шину, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, из-за чего метод `_process_event` считает, что уже подключен к событийной шине адаптера, и пропускает повторную регистрацию.

**Версии с ошибкой**: 2.2.x - 2.4.0-dev.2

**Версия с исправлением**: 2.4.0-dev.3

**Исправление**: Введено отслеживание состояния `_linked_to_adapter_bus`, после `clear()` обработчиков при отключении шины, при следующем `register()` автоматически перерегистрируется, адаптируясь к сценариям перезапуска.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-004] Обработчики жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно срабатывают, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищался при `uninit()`, после перезапуска старые и новые обработчики существуют одновременно.

**Версии с ошибкой**: 2.3.0 - 2.4.0-dev.2

**Версия с исправлением**: 2.4.0-dev.3

**Исправление**: В процессе очистки `Uninitializer` (в конце, после всех событий), очищаем `lifecycle._handlers`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средняя

**Тип**: Рантайм

### [BUG-005] detail_type для Event.is_friend_add/is_friend_delete не соответствует стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Несоответствие с декораторами `on_friend_add`/`on_friend_remove` в `notice.py`, из-за чего обработчики, зарегистрированные через декораторы, при срабатывании, соответствующие методы `is_friend_add()`/`is_friend_delete()` возвращают `False`.

**Причина**: В `wrapper.py` использованы нестандартные имена, а в `notice.py` использованы правильные имена стандарта OB12.

**Версии с ошибкой**: С момента реализации

**Версия с исправлением**: 2.4.2-dev.1

**Исправление**: Значение проверки `is_friend_add()` изменено с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Система событий

---

### [BUG-006] adapter.clear() не очищает _started_instances, приводит к некорректному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает очистку `_started_instances`. Если адаптер запущен и вызывается `clear()`, `_started_instances` сохранит висячие ссылки, что приведет к ошибкам состояния после перезапуска.

**Причина**: При введении `_started_instances` в версии 2.4.0-dev.1 не было синхронной очистки в `clear()`.

**Версии с ошибкой**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия с исправлением**: 2.4.2-dev.1

**Исправление**: Добавлено `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущих объектов и получения временной метки, этот метод устарел в Python 3.10+, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с методом `wait_for()` в `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, а позже добавленный `wait_for()` использовал правильный API, но старый код не был обновлен.

**Версии с ошибкой**: 2.3.0-dev.0

**Версия с исправлением**: 2.4.2-dev.1

**Исправление**: Заменены два вызова `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкая

**Тип**: Система событий

### [BUG-008] Событие отключения бота при shutdown повторно отправляется

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` будет многократно отправлять событие отключения бота в процессе закрытия, что приводит к многократной маркировке одних и тех же ботов как отключенных и многократному срабатыванию события жизненного цикла `adapter.bot.offline`.

**Причина**: Система отслеживания состояния ботов, введенная в 2.4.0-dev.1, не установила флаг "в процессе закрытия" в `shutdown()`, из-за чего `_update_bot_status()` не может отличить нормальное отключение от каскадного отключения в процессе закрытия.

**Версии с ошибкой**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.1

**Исправление**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, который устанавливается в `True` в начале `shutdown()` и сбрасывается в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к LazyModule приводит к незавершенному инициализации

**Проблема**: При синхронном доступе к атрибуту лениво загружаемого BaseModule, модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает, что приводит к гонке за ресурсами, когда инициализация может быть незавершена.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и немедленно возвращает, не обеспечивая завершение инициализации.

**Версии с ошибкой**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.2

**Исправление**: В синхронном контексте инициализация BaseModule заменена на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем вернуться. Сохраняется прозрачность прокси, пользователь не должен осознавать различия между синхронным и асинхронным контекстом.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Система загрузки

### [BUG-010] Многопоточная запись в конфигурацию приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция `_flush_config()` (чтение-изменение-запись) не является атомарной, что может привести к потере части данных.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет атомарной защиты с помощью файлового блокировщика, и `Timer` `_schedule_write` может быть запущен несколько раз, вызывая перезапись.

**Версии с ошибкой**: 2.3.0 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.2

**Исправление**:
1. Добавлен механизм файловой блокировки (`_file_lock`), чтобы обеспечить атомарность операций с файлом.
2. Использование временного файла с атомарной заменой (`os.replace`/`os.rename`).
3. Улучшена логика отмены и перезапуска таймера `_schedule_write`.

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Критическая

**Тип**: Система конфигурации

---

### [BUG-011] CTRL+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows, нажатие CTRL+C не может остановить программу. Программа нормально запускается и выводит информацию о сервере маршрутизации, но CTRL+C не реагирует, и процесс можно остановить только через диспетчер задач. При запуске через `epsdk run` можно нормально остановить — но `epsdk run` работает через модель подпроцессов.

**Причина**: ASGI-сервер Hypercorn в функции `serve()` внутри зарегистрировал свой обработчик SIGINT, перекрыв механизм обработки KeyboardInterrupt Python. Когда Hypercorn запускается как фоновая задача через `asyncio.create_task()`, внутренний процесс остановки Hypercorn не может быть нормально запущен (так как ожидает режим `worker_serve`), из-за чего сигнал CTRL+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Версии с ошибкой**: 2.3.6 - 2.4.2

**Версия с исправлением**: 2.4.3-dev.0

**Исправление**:
1. ASGI-сервер заменен с Hypercorn на Uvicorn (`pyproject.toml` зависимость изменена).

### [BUG-022] Регрессия в _resolve_account() (отсутствие заполнения _accounts_data)

**Проблема**: После рефакторинга конфигурационной системы в 2.5.2, адаптеры с множеством аккаунтов, объявленные с `AccountConfigClass`, при вызове `wait_reply`, `reply` и других методов, требующих отправки сообщения, вызывают ошибку `ValueError("Не объявлен AccountConfigClass, невозможно разрешить аккаунт")`. Даже если адаптер правильно настроен с информацией о множестве аккаунтов, разрешение аккаунта по-прежнему не работает.

**Причина**: В 2.5.2-dev.5 `_load_accounts()` (ответственный за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторинг в `_ensure_accounts_exist()` (генерация шаблона конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда равно `None`, что приводит к тому, что `_resolve_account()` возвращает `(None, None)` и разрешение аккаунта полностью терпит неудачу.

**Корневая цепочка**:
```
_load_accounts() удалена
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        →下游 вызов _resolve_account() (например, call_api) получает None
          → вызывает ошибку
```

**Версии с ошибкой**: 2.5.2-dev.5 - 2.5.2

**Версия с исправлением**: 2.5.3

**Исправление**: В `BaseAdapter.__init__` после `_ensure_accounts_exist()` восстанавливается заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # восстановление заполнения, данные из текущего свойства accounts
```
Логика `_resolve_account()` остается без изменений, полностью обратная совместимость:
- Адаптеры без объявления `AccountConfigClass`: `_accounts_data` остается None → возвращает (None, None)
- Адаптеры с объявленным `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, перезаписывающие `_load_accounts` или вручную устанавливающие `_accounts_data`: в `super().__init__()` после перезаписи, приоритет высший

**Серьезность**: 🔴 Критическая

### [BUG-025] Callback on_config_update не вызывается ядром

**Проблема**: `on_config_update(old, new)` определён в базовых классах (`BaseModule` / `BaseAdapter`), но ядро не подписывается на события изменения конфигурации. ```
Ядро не подписывается на config.set / config.updated
  → События изменения конфигурации не пересылаются
    → on_config_update не вызывается
      → Ручное изменение файла / вызов setConfig не вызывает теплый перезагрузки

### [BUG-026] Ошибка вывода цели ответа для событий notice/request

**Проблема**: При вызове `event.reply()` в событии уведомления (например, добавление участника в группу `group_member_increase`), сообщение отправляется в личный чат пользователя, который вызвал событие, а не в группу, где произошло событие. Аналогично для событий уведомления о друзьях, цель ответа может быть неправильной.

**Причина**: `infer_receive_type()` возвращает `detail_type` как тип сессии. Для событий `message` это правильно (`detail_type` значения `private`/`group` — это тип сессии), но для событий `notice/request` `detail_type` — это семантический подтип (например, `group_member_increase`, `friend_increase`), а не тип сессии. Последующая `convert_to_send_type()` и `get_id_field()` в отображении не находят это значение, возвращая по умолчанию `"user"` / `"user_id"`, что приводит к неправильной цели ответа.

**Корневая цепочка**:
```
detail_type уведомления = "group_member_increase"
  → infer_receive_type() возвращает напрямую "group_member_increase"
    → convert_to_send_type("group_member_increase") не в отображении → возвращается "user"
    → get_id_field("group_member_increase") не в отображении → возвращается "user_id"
      → target_id = event["user_id"]  ← Личный чат нового участника (а не группа)
```

**Версии с ошибкой**: Все версии

**Версия с исправлением**: 2.7.0-dev.3

**Исправление**: `infer_receive_type()` добавляет проверку — `detail_type` возвращает напрямую только если это известный тип сессии (стандартный или пользовательский); в противном случае по полю ID (`group_id` / `channel_id` / `user_id` и т.д.) выводится правильный тип сессии.

### [BUG-027] Задача очистки маршрутизации с фиксированным окном приводит к сбою правила длительного окна

**Проблема**: При настройке маршрутизации с правилом длительного окна (например, `100/hour`, `{"requests": 100, "window": 3600}`), ограничение оказывается неэффективным — на практике поведение похоже на `100/minute` (в час можно пропустить до ~6000 запросов), что не обеспечивает ожидаемой защиты на уровне часа.

**Причина**: `_apply_rate_limit` получает фактическое `window` (максимум 3600 секунд) для маршрута; проверка на каждый запрос действительно использует это окно; но фоновая задача `_cleanup_expired_rate_limits` использует постоянную константу `DEFAULT_RATE_LIMIT_WINDOW_SECS` (60 секунд) в качестве общего порога очистки для всех маршрутов. Таким образом, записи старше 60 секунд удаляются из задачи очистки, и в окне в час никогда не накапливается почти 100 записей, ограничение сильно ослабляется.

**Корневая цепочка**:
```
_apply_rate_limit получает window=3600 (100/hour)
  → Проверка на каждый запрос по времени хранения 3600 секунд (правильно)
  → Но _cleanup_expired_rate_limits использует фиксированный max_window=60 секунд для очистки
    → Записи старше 60 секунд удаляются
      → В часовом окне остаются только последние 1 минуты записей
        → 100/hour фактически уменьшается до ~100/minute (охлаждение примерно в 60 раз)
```

**Версии с ошибкой**: 2.6.0-dev.0 - 2.7.0-dev.4

**Версия с исправлением**: 2.7.0-dev.5

**Исправление**: Добавлен `_rate_limit_windows: dict[str, int]` для хранения окна каждого маршрута; при первом создании записи в `_apply_rate_limit` записывается окно; `_cleanup_expired_rate_limits` теперь очищает по окну каждого ключа (в случае отсутствия — по значению по умолчанию); при удалении записей и `stop()` синхронно обслуживается два словаря.

**Дата исправления**: 2026/07/31

### [BUG-029] Задача наблюдения за конфигурацией транслирует незавершенный TOML и молча глотает исключения

**Проблема**: При ручном редактировании `config.toml` и сохранении в промежуточном состоянии (создание временного файла с синтаксической ошибкой), фоновый поток наблюдения обнаруживает изменение mtime, перезагружает конфигурацию, но при неудачной загрузке по-прежнему излучает событие `config.updated` с пустой конфигурацией `{}`, что приводит к тому, что адаптеры/модули `on_config_update` получают пустую конфигурацию и ошибочно считают, что все параметры конфигурации были очищены, возвращаясь к значениям по умолчанию. Кроме того, цикл наблюдения использует `except Exception: pass`, молча глотая все исключения, что затрудняет диагностику сбоев наблюдателя.

**Причина**: Два дефекта:
1. `_load_config` при синтаксической ошибке/ошибке прав доступа перезаписывает `self._cache` в `{}`, но фоновый цикл `_watch_loop` и путь сброса кэша `_check_cache_validity` безусловно вызывают `_emit_config_updated()` после `_load_config()`, излучая "загрузку неудачи, приведшую к пустому кэшу" как реальное изменение.
2. `_watch_loop` с `except Exception: pass` не записывает никаких логов.

**Корневая цепочка**:
```
Пользователь сохраняет в промежуточном состоянии → Синтаксическая ошибка TOML
  → _load_config() перезаписывает _cache = {}
    → _watch_loop безусловно _emit_config_updated(new_config={})
      → Адаптер/модуль on_config_update получает пустую конфигурацию
        → Ошибочно считает конфигурацию очищенной, возвращается к значениям по умолчанию
```

**Версии с ошибкой**: 2.6.2-dev.1 - 2.7.0-dev.4

**Версия с исправлением**: 2.7.0-dev.5

**Исправление**:
1. `_load_config` изменен на возвращение `bool`; при синтаксической ошибке/ошибках прав доступа и других ошибках `self._cache` не перезаписывается в `{}`, а сохраняется последняя действительная конфигурация (не перезаписывается), записываются только диагностические логи и возвращается `False`
2. `_watch_loop` и `_check_cache_validity` излучают `config.updated` только если `_load_config()` возвращает `True`
3. `except Exception` в `_watch_loop` заменен на запись предупреждения (новый ключ i18n `core.config.watcher_error`, синхронно пять языков)

**Дата исправления**: 2026/07/31

**Тесты**: `tests/unit/test_unit_config.py` → `test_malformed_toml_preserves_last_valid_cache`, `test_permission_denied_logs_clear_message` (обновлены для проверки сохранения кэша и возвращения False)

### [BUG-030] Гонка при наблюдении за конфигурацией приводит к потере данных при задержанной записи

**Проблема**: Несколько пользователей сообщили, что использование `config.setConfig(key, value)` (по умолчанию `immediate=False`) после этого конфигурация модуля не записывается в `config.toml`, в то время как конфигурация других модулей сохраняется. Установка `immediate=True` (принудительная запись) помогает избежать проблемы. Проявляется в том, что конфигурация, записанная в ходе выполнения, теряется после перезапуска, а конфигурация, сгенерированная при запуске, сохраняется.

**Причина**: Два накладывающихся дефекта:
1. **Логический дефект**: `_watch_loop` при `_check_file_change()` возвращает `True` безусловно `_dirty_keys.clear()` очищает все ключи для записи. Но `_check_file_change()` использует только `!=` для сравнения mtime, запись конфигурации фреймворка `_flush_config` также изменяет mtime — хотя `_flush_config` после записи обновляет `_config_mtime`, поток наблюдения может обнаружить разницу mtime между записью файла и присвоением `_config_mtime` (а также на грубых файловых системах) и ошибочно считать, что это внешнее изменение, очищая все ключи для записи.
2. **Потоковой дефект**: `_watch_loop` при операциях `_write_timer`/`_dirty_keys` не использует `_lock`, что создает гонку с `setConfig` (с блокировкой записи `_dirty_keys`), `_schedule_write` (с блокировкой записи `_write_timer`).

**Корневая цепочка**:
```
Модуль A setConfig(immediate=True) → flush запись, mtime изменяется
  → Пользовательский модуль setConfig(immediate=False) → входит в _dirty_keys, через 5s запись
    → Цикл наблюдения, _check_file_change замечает разницу mtime от предыдущей записи
      → _dirty_keys.clear() → ключи для записи пользователя теряются
        → При перезапуске конфигурация отсутствует
```

**Версии с ошибкой**: 2.6.0 - 2.7.0

**Версия с исправлением**: 2.7.1

**Исправление**:
1. Добавлено `_last_self_write_mtime` поле, `_flush_config` записывает его после записи; `_check_file_change` при изменении mtime сначала сравнивает это значение, если совпадает, считает, что это внутренняя запись, возвращает `False`
2. Весь блок `_watch_loop` захватывает `_lock`; при реальном внешнем изменении сохраняются `_dirty_keys` (слияние семантики), при следующей записи сливаются с внешними данными (ключи для записи имеют приоритет), `_dirty_keys` не очищаются
3. `getConfig`/`_check_cache_validity` не затрагиваются (перезагрузка не очищает ключи для записи)

**Дата исправления**: 2026/08/06

**Тесты**: `tests/unit/test_unit_config.py` → `test_self_write_not_detected_as_external`, `test_external_change_preserves_dirty_keys`, `test_flush_merges_dirty_with_external`

### [BUG-032] Чтение после записи в конфигурации с задержкой возвращает старое значение

**Проблема**: `config.setConfig()` (по умолчанию `immediate=False`, задержка около 5 секунд) после записи точки-разделенной ключа, немедленно читает его **родительский/родительский узел** (например, `set_erispulse_section("scope.actions.MyModule", {...})` и вызов `get_erispulse_config()`) возвращает старое значение, записанный подключенный ключ "исчезает", пока не произойдет запись. Затрагивает сценарии "запись-чтение-запись" с теплой перезагрузкой конфигурации (тестовый плагин `/t_section` в 2.8.0 выявил).

**Причина**: `setConfig` сохраняет точечно-разделенный ключ в виде **плоских** `_dirty_keys`, только точечный поиск `getConfig` попадает в `_dirty_keys`; дерево-разделенный поиск (например, `getConfig("ErisPulse.scope")`) идет только по кэшу, не добавляя `_dirty_keys` — до записи (когда `_flush_config` объединяет `_dirty_keys` в кэш и очищает очередь) возникает разрыв между чтением и записью.

**Версии с ошибкой**: 2.6.0 - 2.8.0-dev.1

**Версия с исправлением**: 2.8.0-dev.1

**Исправление**: `getConfig` вводит логику объединения `_dirty_keys` — ① точечное попадание в `_dirty_keys` возвращает напрямую (поведение без изменений); ② `_dirty_keys` является предком запроса — берется самый длинный предок в `_dirty_keys`, в его поддереве разрешается оставшийся путь; ③ `_dirty_keys` является потомком запроса — строится объединенное поддерево (`_dirty_overlay`) и глубокое слияние с поддеревом кэша (`_deep_merge`, приоритет override, не изменяя объект кэша). Без `_dirty_keys` идет быстрый путь, нулевые дополнительные накладные расходы.

**Дата исправления**: 2026/09/04

**Тесты**: `tests/unit/test_unit_config.py` → `test_get_config_overlays_dirty_descendant`, `test_get_config_overlay_merges_with_cache_siblings`, `test_get_config_overlay_new_branch`, `test_get_config_dirty_ancestor_query`, `test_get_config_dirty_exact_key_still_wins`
