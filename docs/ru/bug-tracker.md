# Трекер ошибок

Документация описывает известные ошибки и их исправления в ErisPulse SDK.

---

## Исправленные ошибки

### [BUG-001] Ошибка типа пути конфигурации адаптера в команде Init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации при выборе конфигурации адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Влияющие версии**: 2.3.7 - 2.3.9-dev.1

**Исправленная версия**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра метода `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

### [BUG-002] Отсутствие срабатывания команд после перезапуска

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные с помощью `@command`, не срабатывают, что проявляется в отсутствии ответа бота при отправке команды.

**Причина**: После очистки событийного буфера в `adapter.shutdown()` статус `_linked_to_adapter_bus` в классе `BaseEventHandler` не сбрасывается в `False`, из-за чего метод `_process_event` считает, что уже привязан к буферу адаптера, и пропускает повторную привязку.

**Влияющие версии**: 2.2.x - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания статуса `_linked_to_adapter_bus`, при разрыве соединения в `_clear_handlers()` следующий вызов `register()` автоматически переподключится, адаптировано для сценариев shutdown/restart.

**Дата исправления**: 2026/04/09

### [BUG-003] Неочищенные обработчики жизненного цикла

**Проблема**: После вызова `sdk.restart()` старые обработчики событий жизненного цикла остаются и срабатывают повторно, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищался при вызове `uninit()`, после перезапуска старые и новые обработчики существуют одновременно.

**Влияющие версии**: 2.3.0 - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в конце процесса очистки в `Uninitializer` (после всех событий).

**Дата исправления**: 2026/04/09

### [BUG-005] Перезапись определения метода at в MessageBuilder (мертвый код)

**Проблема**: В классе `MessageBuilder` метод `at` был определен трижды: как экземплярный метод, как статический метод, и в конце перезаписан значением `_DualMethod`. Первые два определения никогда не будут выполнены и являются мертвым кодом.

**Причина**: При рефакторинге в `_DualMethod` двойной режим дескриптора, забыли удалить старые ручные определения.

**Влияющие версии**: 2.4.0-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Удаление двух мертвых определений метода `at` в строках 159-181 файла `message_builder.py`, оставив только `_DualMethod`.

**Дата исправления**: 2026/04/13

### [BUG-006] Несоответствие detail_type в Event.is_friend_add/is_friend_delete и стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Это несоответствие с декораторами `notice.py` (`on_friend_add`/`on_friend_remove`), что приводит к тому, что обработчики, зарегистрированные через декораторы, не срабатывают при вызове соответствующих методов `is_friend_add()`/`is_friend_delete()`.

**Причина**: В `wrapper.py` использовались нестандартные имена, а в `notice.py` — правильные имена стандарта OB12.

**Влияющие версии**: С момента реализации rq

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения сопоставления `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

### [BUG-007] adapter.clear() не очищает _started_instances, что приводит к неправильному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если вызвать `clear()` во время работы адаптера, `_started_instances` сохранит неверные ссылки, что приведет к ошибочным состояниям после перезапуска.

**Причина**: При введении `_started_instances` в версии 2.4.0-dev.1 не было синхронного очищения в `clear()`.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

### [BUG-008] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущего и получения временной метки, этот метод устарел в Python 3.10+, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Это несоответствие с `wait_for()` в `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, впоследствии `wait_for()` использовал правильный API, но старый код не был исправлен.

**Влияющие версии**: 2.3.0-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Замена двух вызовов `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

### [BUG-009] Event.collect() игнорирует поля без ключа

**Проблема**: Метод `Event.collect()` при переборе списка полей игнорирует поле, если в словаре отсутствует ключ `key`, без вывода логов или предупреждений. Если разработчик допустил опечатку (например, `"Key"` вместо `"key"`), поле будет незаметно проигнорировано, что затруднит отладку.

**Причина**: Отсутствие проверки входных данных и обратной связи об ошибках.

**Влияющие версии**: 2.4.0-dev.4

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Добавление `logger.warning()` для записи информации о пропущенном поле без ключа перед пропуском.

**Дата исправления**: 2026/04/13

### [BUG-010] LazyModule синхронный доступ к BaseModule приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к свойству лениво загружаемого BaseModule модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает, что может привести к незавершённой инициализации при доступе к свойству и возникновению гонок.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и сразу возвращает, не обеспечивая завершение инициализации.

**Влияющие версии**: 2.4.0-dev.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule заменена на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена до возврата. Сохраняется прозрачность прокси, пользователь не должен осознавать различия между синхронным и асинхронным.

**Дата исправления**: 2026/04/21

### [BUG-011] Потеря данных при многопоточном записи в систему конфигурации

**Проблема**: В многопоточной среде, при одновременном вызове `config.setConfig()` несколькими потоками, операция `_flush_config()` (чтение-изменение-запись) не является атомарной, что может привести к потере части записей.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты файловым блокировщиком, и `_schedule_write` может быть запущен несколько раз, вызывая перезапись.

**Влияющие версии**: 2.3.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавление механизма файловой блокировки (`_file_lock`) для обеспечения атомарности операций с файлом
2. Использование временного файла для записи с атомарным переименованием (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Влияющие версии**: 2.0.0 - 2.4.2-dev.1

1. Зарегистрирован, но не включен: сообщение о том, что модуль/адаптер не включен
2. Полностью не существует: сообщение о проверке опечатки в имени
Оригинальная ошибка `AttributeError` также перебрасывается, чтобы верхние уровни могли перехватить.

### [BUG-013] Слишком сложная логика очистки Uninitializer для неинициализированных LazyModule

1. Пропуск неинициализированных LazyModule, без создания временных экземпляров
2. Вызов `on_unload` только для инициализированных модулей
3. Удаление сложной логики создания временных экземпляров

**Дата исправления**: 2026/04/21

### [BUG-014] CTRL+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие CTRL+C не останавливает программу. Программа запускается и выводит информацию о сервере маршрутизации, но CTRL+C не реагирует, процесс можно остановить только через диспетчер задач. При запуске через `epsdk run` остановка работает, но `epsdk run` использует модель подпроцессов.

**Причина**: Внутренний `serve()` функции сервера ASGI Hypercorn через `signal.signal(SIGINT, handler)` регистрирует свой обработчик SIGINT, перезаписывая стандартный механизм обработки KeyboardInterrupt Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()` внутренний процесс остановки Hypercorn не может быть нормально запущен (он ожидает режим `worker_serve`), из-за чего сигнал CTRL+C поглощается Hypercorn, но не вызывает никаких действий по очистке.

**Влияющие версии**: [2.3.6 - 2.4.2]

**Исправленная версия**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена сервера ASGI с Hypercorn на Uvicorn (`pyproject.toml` зависимость изменена)
2. Прямой запуск сервера с помощью `uvicorn.Server._serve()`, **обходя** контекстный менеджер обработки сигналов `capture_signals()`
3. Использование `server.should_exit = True` для обеспечения корректной остановки, по истечении времени фоновая задача отменяется
4. Синхронное удаление модели подпроцессов и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

### [BUG-015] Ошибка логики сортировки стратегии загрузки модуля

**Проблема**: `ModuleLoadStrategy` предоставляет поле `priority` для объявления приоритета инициализации модуля, но реализация стратегии загрузки содержит ошибку, из-за которой модули инициализируются не в соответствии с приоритетом, а в порядке `entry_points()` по умолчанию. При наличии зависимостей между модулями невозможно гарантировать правильный порядок инициализации через `priority`.

**Причина**: Ошибка в логике сортировки в реализации стратегии загрузки, `initialize_modules()` не использует `priority` для сортировки списка модулей.

**Влияющие версии**: 2.3.4 - 2.4.5-dev.2

**Исправленная версия**: 2.4.5-dev.3

**Содержание исправления**: Сортировка списка модулей по `priority` в порядке убывания до цикла `initialize_modules()`. Модули с одинаковым приоритетом сохраняют относительный порядок (стабильная сортировка).

**Дата исправления**: 2026/05/15

### [BUG-016] Возврат None промежуточным обработчиком адаптера приводит к потере данных события

**Проблема**: При выполнении промежуточной цепочки OneBot12 в `adapter.emit()` если какой-либо промежуточный обработчик возвращает `None` (например, забыл `return data`), последующие промежуточные обработчики и все обработчики событий получают `processed_data` в виде `None`, что приводит к полной потере обработки события.

**Причина**: Реализация цепочки промежуточных обработчиков `processed_data = await middleware(processed_data)` не проверяет возвращаемое значение на `None`, перезаписывая результат предыдущего шага.

**Влияющие версии**: unknown - 2.4.5-dev.3

**Исправленная версия**: 2.4.5-dev.4

**Содержание исправления**: При возврате `None` промежуточным обработчиком игнорировать это значение, сохранять исходные данные и выводить предупреждение.

**Дата исправления**: 2026/05/15

### [BUG-017] Зависимость пути конфигурационного файла от рабочей директории

**Проблема**: Путь конфигурационного файла `ConfigManager` по умолчанию — относительный путь `"config/config.toml"`, который в момент выполнения зависит от `os.getcwd()`. Если рабочая директория изменяется во время выполнения (например, через `os.chdir()`), операции чтения и записи конфигурационного файла будут указывать на неправильное место, что приведет к потере конфигурации или чтению старых данных.

**Причина**: В `__init__` хранится относительный путь, не преобразованный в абсолютный при инициализации.

**Влияющие версии**: 2.3.7 - 2.4.5-dev.3

**Исправленная версия**: 2.4.5-dev.4

**Содержание исправления**: При инициализации в `ConfigManager.__init__()` если путь относительный, автоматически преобразуется в абсолютный через `os.path.abspath()`.

**Дата исправления**: 2026/05/15

### [BUG-018] В режиме подпроцесса `ep run <script>` не находит подпакеты в директории скрипта

**Проблема**: При запуске скрипта с помощью `ep r .\main.py` в негорячем режиме, если скрипт имеет относительные импорты (например, `from qg import ...`), возникает ошибка `No module named 'qg'`. В режиме `--reload` скрипт работает нормально.

**Причина**: В негорячем режиме используется `runpy.run_path()` для выполнения скрипта, который не добавляет директорию скрипта в `sys.path`. В режиме `--reload` скрипт запускается через `subprocess.Popen`, подпроцесс наследует текущую рабочую директорию, `sys.path[0]` — это директория скрипта, поэтому импорты работают.

**Влияющие версии**: 2.5.0 - 2.5.2-dev.0

**Исправленная версия**: 2.5.2-dev.0

**Содержание исправления**: Перед вызовом `runpy.run_path()` вручную добавить директорию скрипта в `sys.path[0]`.

**Дата исправления**: 2026/06/27

### [BUG-019] Конструктор SQL-запросов отвергает допустимые выражения с подстановкой и списками

**Проблема**: `_build_select_sql()` в `SQLiteQueryBuilder` вызывает `_validate_identifier()` для всех столбцов SELECT, этот функция использует строгий белый список регулярного выражения `^[a-zA-Z_][a-zA-Z0-9_]*$`, что приводит к ошибочной классификации допустимых SQL-синтаксисов как небезопасных имен столбцов:
- `SELECT *` — стандартный SQL-шаблон
- `SELECT COUNT(*)` — агрегатная функция
- `SELECT users.name` — квалифицированное имя столбца
- `SELECT col AS alias` — псевдоним столбца

`Select("*")` используется модулями, такими как Cron, что приводит к сбою модуля при выполнении `on_load`, модуль не может загрузиться.

**Причина**: В версии 2.4.6 была усилена защита от SQL-инъекций, добавлено белый список `_validate_identifier()`. Эта проверка применяется ко всем именам столбцов, но не различает чтение (SELECT/ORDER BY) и запись (INSERT/UPDATE). SELECT-столбцы допускают сложные SQL-выражения, которые не должны ограничиваться простым белым списком идентификаторов.

**Влияющие версии**: 2.4.6 - 2.5.2-dev.1

**Исправленная версия**: 2.5.2-dev.2

**Содержание исправления**: Изменение проверки имен столбцов SELECT/ORDER BY с белого списка на черный список:
1. Добавлена функция `_validate_select_column()`, которая блокирует опасные символы SQL-инъекций (`;` `'` `"` `--` `/*` `*/` `\x00` символы новой строки)

### [BUG-020] Возврат значения при разрешении аккаунта _resolve_account() (_accounts_data не заполнен)

**Проблема**: После рефакторинга системы конфигурации в 2.5.2 при вызове методов, требующих отправки сообщений (например, `wait_reply`, `reply`), адаптеры с конфигурацией `AccountConfigClass` выдают ошибку `ValueError("Не объявлен AccountConfigClass, невозможно разрешить аккаунт")`. Даже при правильной конфигурации адаптера с информацией о нескольких аккаунтах разрешение аккаунта по-прежнему не удаляется.

**Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторинг в `_ensure_accounts_exist()` (генерирует только шаблон конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда равно `None`, что приводит к преждевременному возврату `(None, None)` и полной неудаче разрешения аккаунта.

**Корневая цепочка**:
```
_load_accounts() удалена
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        → Далее вызывающие _resolve_account() места (например, call_api) получают None
          → Вызывается ошибка
```

**Влияющие версии**: 2.5.2-dev.5 - 2.5.2

**Исправленная версия**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `_ensure_accounts_exist()` восстановлено заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # Восстановить заполнение, источник данных — актуальное свойство accounts
```
Логика `_resolve_account()` остается без изменений, полностью обратно совместима:
- Для адаптеров без объявления `AccountConfigClass`: `_accounts_data` остается `None` → возвращается `(None, None)`
- Для адаптеров с объявленным `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Для адаптеров с переопределением `_load_accounts` или ручным установлением `_accounts_data`: в `super().__init__()` после установки, приоритет высший

**Дата исправления**: 2026/07/07
