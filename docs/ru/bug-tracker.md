# Система отслеживания ошибок

Данная документация описывает известные ошибки ErisPulse SDK и их исправления, представленные в хронологическом порядке по времени исправления.

> **Обращение к читателю**  
> Никакое программное обеспечение не может быть идеальным, и даже самые внимательные разработчики могут допускать небольшие ошибки. В этом отслеживании перечислены только те проблемы, которые реально влияют на работу системы — мелкие недочеты, не достигающие даже уровня «незначительного», здесь не отражаются. Список с пометкой «серьезный» может показаться большим, но основная цель публикации таких ошибок — обеспечить более гладкое выявление и отслеживание проблем, а не вызывать беспокойство: возможность видеть, записывать и исправлять проблемы — это доказательство того, что проект постоянно улучшается. Не стоит беспокоиться, увидев этот список: он служит инструментом для диагностики, а не источником страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ корневой причины, диапазон версий, которые затронуты, решение, краткое описание изменений, дата публикации, уровень серьезности и тип ошибки. Рекомендуется перед обновлением проверять, попадает ли текущая версия в диапазон, указанный в записи.
> - При добавлении новой записи об ошибке следует следовать структуре и правилам категоризации, указанным ниже.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем. Следует максимально подробно описать сообщения об ошибках или типичные сценарии |
| **Причина** | Анализ корневой причины, указывающий на конкретные дефекты кода (включая "цепочку корневых причин" для сложных сценариев) |
| **Влияющие версии** | Диапазон затронутых версий, формат `Версия введения - Версия исправления` (включая версии dev) |
| **Исправлено в версии** | Конкретная версия, в которой была исправлена ошибка |
| **Содержание исправления** | Краткое описание решения, включая ключевые изменения в коде |
| **Дата исправления** | Дата публикации соответствующей версии, в формате `YYYY/MM/DD` |
| **Серьезность** | Уровень, указанный по нижеприведённой шкале |
| **Тип** | Тип ошибки, указанный по нижеприведённой классификации, может быть комбинированным (например, `Адаптер / Маршрутизация`) |

### Необязательные поля

| Поле | Описание | Сценарий применения |
|------|------|---------|
| **Шаги воспроизведения** | Минимальный путь для воспроизведения ошибки | Рекомендуется для сложных или случайных ошибок |
| **Связи** | Ссылки на связанные Issue / PR / Commit | Добавляется при наличии внешних обсуждений |
| **Тесты на повторное исправление** | Позиции тестовых случаев для проверки исправления | Добавляется при наличии соответствующих тестов pytest |

## Шкала серьезности

| Идентификатор | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Серьёзный | Причиняет сбой процесса, потерю или повреждение данных, полную недоступность основной функции, уязвимости безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, неудачный горячий перезапуск |
| 🟡 | Средний | Функциональные сбои, но есть пути обхода, недоступность неосновных функций, случайные проблемы | Ошибочное определение состояния, повторное срабатывание, просроченный кэш, неточная ошибка |
| 🟢 | Лёгкий | Не влияет на основную функциональность, только качество кода или проблемы с пользовательским опытом, потенциальные риски без проявления | Устаревший API, мёртвый код, отсутствие логов warning |

## Исправленные ошибки

### [BUG-001] Повторная регистрация обработчиков событий приводит к многократному срабатыванию события

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` для регистрации обработчиков одно и то же событие может быть обработано несколько раз, что приводит к многократному выполнению команды и дублированию логов.

**Причина**: `BaseEventHandler` не содержит логики удаления дубликатов при регистрации обработчиков в событийную шину адаптера. Каждый декоратор добавляет обработчик, и при распределении события он вызывается несколько раз.

**Влияющие версии**: 2.2.0-dev.0 - 2.2.1-dev.0

**Исправлено в версии**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался в шину адаптера только один раз, предотвращая многократное срабатывание.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Серьёзный

**Тип**: Система событий

---

### [BUG-002] Ошибка типа при выборе пути конфигурации адаптера в команде init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации возникает ошибка типа:

```
Ошибка интерактивной инициализации: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри использует оператор `/` для Path, что приводит к ошибке.

**Влияющие версии**: 2.3.7 - 2.3.9-dev.1

**Исправлено в версии**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра `_configure_adapters_interactive_sync` с `str` на `Path`, вызов метода с передачей объекта Path.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средний

**Тип**: CLI

---

### [BUG-003] После перезапуска команды события не активируются

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные с помощью `@command`, не срабатывают, что проявляется в том, что бот не реагирует на отправленные команды.

**Причина**: `adapter.shutdown()` очищает событийную шину, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, поэтому метод `_process_event` считает, что обработчик уже подключен к шине, и пропускает повторную регистрацию.

**Влияющие версии**: 2.2.x - 2.4.0-dev.2

**Исправлено в версии**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при `_clear_handlers()` обработка отключается, и при следующем `register()` автоматически переподключается, адаптируясь к сценариям shutdown/restart.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Серьёзный

**Тип**: Система событий

---

### [BUG-004] Неочищенные обработчики событий жизненного цикла

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно срабатывают, что приводит к многократному выполнению одного и того же события.

**Причина**: Словарь `lifecycle._handlers` не очищается при `uninit()`, поэтому после перезапуска старые и новые обработчики существуют одновременно.

**Влияющие версии**: 2.3.0 - 2.4.0-dev.2

**Исправлено в версии**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в процессе очистки `Uninitializer` (после всех событий), чтобы избежать повторного срабатывания.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средний

**Тип**: Рантайм

### [BUG-005] Несоответствие detail_type в Event.is_friend_add/is_friend_delete и стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Это несоответствие с `notice.py`, где используются правильные значения OB12, приводит к тому, что обработчики, зарегистрированные с помощью декораторов, не срабатывают, когда `is_friend_add()`/`is_friend_delete()` возвращают `False`.

**Причина**: В `wrapper.py` используется неправильное имя, в то время как `notice.py` использует правильные значения стандарта OB12.

**Влияющие версии**: С момента реализации

**Исправлено в версии**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения для `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Система событий

### [BUG-006] clear() адаптера не очищает _started_instances, приводя к ошибкам состояния при перезапуске

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен и вызывается `clear()`, `_started_instances` сохраняет висячие ссылки, что приводит к ошибкам состояния при перезапуске.

**Причина**: При введении `_started_instances` в версии 2.4.0-dev.1 не было очищено в `clear()`.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.0

**Исправлено в версии**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

---

### [BUG-007] wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущих объектов и получения временных меток, что в Python 3.10+ считается устаревшим. В то же время метод `wrapper.py` использует `asyncio.get_running_loop()`, что не соответствует.

**Причина**: Использование устаревшего API в старом коде, в то время как новый метод `wait_for()` использует правильный API, но не был обновлен.

**Влияющие версии**: 2.3.0-dev.0

**Исправлено в версии**: 2.4.2-dev.1

**Содержание исправления**: Замена двух вызовов `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Лёгкий

**Тип**: Система событий

### [BUG-008] События отключения бота повторно отправляются при shutdown()

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` повторно отправляет события отключения бота, что приводит к многократному отображению состояния "отключен" и повторному срабатыванию событий жизненного цикла `adapter.bot.offline`.

**Причина**: Система отслеживания состояния бота, введённая в 2.4.0-dev.1, не устанавливает флаг "в процессе закрытия" во время `shutdown()`, поэтому `_update_bot_status()` не может отличить нормальное отключение от каскадного отключения.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.1

**Исправлено в версии**: 2.4.2-dev.1

**Содержание исправления**: Добавление флага `_is_being_shutdown` в `AdapterManager`, который устанавливается в True в начале `shutdown()` и сбрасывается в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

---

### [BUG-009] Синхронный доступ к BaseModule без завершения инициализации

**Проблема**: При синхронном доступе к атрибуту лениво загружаемого BaseModule модуль инициализируется с помощью `loop.create_task()` без ожидания, что может привести к гонке состояний.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и немедленно возвращает, не обеспечив завершения инициализации.

**Влияющие версии**: 2.4.0-dev.0 - 2.4.2-dev.1

**Исправлено в версии**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule заменяется на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем вернуться. Сохраняется прозрачность для пользователя.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Загрузчик

---

### [BUG-010] Многопоточная запись конфигурации приводит к потере данных

**Проблема**: При одновременной записи конфигурации несколькими потоками `config.setConfig()` может произойти потеря данных из-за неатомарной операции чтения-изменения-записи.

**Причина**: Хотя `_flush_config()` использует `RLock`, отсутствует файловый блок, и `_schedule_write` может быть запущен несколько раз, перезаписывая данные.

**Влияющие версии**: 2.3.0 - 2.4.2-dev.1

**Исправлено в версии**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавление механизма файлового блока (`_file_lock`) для атомарной операции с файлом
2. Использование временного файла для записи, затем атомарное переименование (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Серьёзный

**Тип**: Система конфигурации

### [BUG-011] Невозможность остановки программы с помощью Ctrl+C в Windows

**Проблема**: При запуске `python main.py` в Windows нажатие Ctrl+C не останавливает программу. Процесс начинает работать и выводит информацию о сервере маршрутизации, но Ctrl+C не реагирует, приходится убивать процесс через диспетчер задач. При запуске через `epsdk run` остановка работает, но это происходит через подпроцесс.

**Причина**: ASGI-сервер Hypercorn в функции `serve()` регистрирует свой обработчик SIGINT, перекрывающий стандартный обработчик KeyboardInterrupt Python. При запуске Hypercorn как фоновая задача с помощью `asyncio.create_task()` внутренний процесс остановки Hypercorn не срабатывает, так как ожидает режим `worker_serve`.

**Влияющие версии**: 2.3.6 - 2.4.2

**Исправлено в версии**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена ASGI-сервера Hypercorn на Uvicorn (`pyproject.toml` зависимость)
2. Использование `uvicorn.Server._serve()` для запуска сервера, **исключая** контекстный менеджер `capture_signals()`
3. Использование `server.should_exit = True` для корректной остановки, с отменой задачи при таймауте
4. Синхронное удаление модели подпроцесса и модуля очистки `runtime/cleanup.py` (не требуется)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Серьёзный

**Тип**: CLI / Рантайм

### [BUG-012] После горячего перезапуска обновлённый код модуля не применяется

**Проблема**: После выполнения `sdk.restart()` модуль, обновлённый с помощью `epsdk install`, не применяет новые изменения кода (например, новые API-маршруты), продолжая работать по старой версии. Необходим полный перезапуск процесса для загрузки последней версии.

**Причина**: `_do_restart()` при повторной инициализации вызывает `entry_point.load()`, но эта функция возвращает закэшированный объект модуля из `sys.modules`, а не загружает его заново с диска.

**Влияющие версии**: Ранние версии - 2.4.3-dev.1

### [BUG-022] Решение учётных записей `_resolve_account()` не заполнено `_accounts_data`

**Проблема**: После рефакторинга системы конфигурации в 2.5.2, адаптеры с мультиаккаунтной конфигурацией не могут решить учётные записи при вызове методов, требующих отправки сообщений (например, `wait_reply`, `reply`). **Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечающий за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторинг в `_ensure_accounts_exist()` (генерация шаблона конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, этот атрибут остаётся `None`, что приводит к тому, что `_resolve_account()` возвращает `(None, None)`.

**Цепочка корневых причин**:
```
_load_accounts() удалён
  → __init__ не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → возвращает (None, None)
        → методы, использующие _resolve_account (например, call_api), получают None

**Влияющие версии**: 2.5.2-dev.5 - 2.5.2

**Исправлено в версии**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `self._ensure_accounts_exist()` восстанавливается заполнение `_accounts_data`:

if self.AccountConfigClass is not None:

    self._accounts_data = self.accounts  # восстановление заполнения, данные берутся из актуальных accounts
```
Логика `_resolve_account()` остаётся неизменной, полностью обратно совместимой:
- Если `AccountConfigClass` не объявлен: `_accounts_data` остаётся `None` → возвращает `(None, None)`
- Если `AccountConfigClass` объявлен: `_accounts_data` заполняется → нормальное решение
- Если адаптер переопределяет `_load_accounts` или вручную устанавливает `_accounts_data`: переопределяется после `super().__init__()` с наивысшим приоритетом

**Причина**: `ConfigManager` при изменении конфигурации издаёт события `config.set` / `config.updated`, но отсутствует логика пересылки этих событий на компоненты `on_config_update`.

**Цепочка корневых причин**:
```
Ядро не подписывается на события config.set / config.updated
  → События изменения конфигурации не пересылаются
    → on_config_update не вызывается
      → Ручное редактирование файла / код setConfig не вызывает горячего обновления
```

**Влияющие версии**: Все версии

**Исправлено в версии**: 2.6.2

**Содержание исправления**: `ModuleManager` / `AdapterManager` подписываются на события `config.set` (покрывает путь `setConfig()`) и `config.updated` (покрывает ручное редактирование файла), сопоставляя события с соответствующими компонентами `on_config_update` и передавая типобезопасные объекты конфигурации. ### [BUG-036] Ошибки записи конфигурации при совместном использовании каталога конфигурации несколькими экземплярами (ENOENT)

**Проблема**: При развертывании в Docker (несколько контейнеров монтируют один каталог хоста конфигурации), логи периодически показывают две последовательные ошибки `Failed to write configuration file ... [Errno 2] No such file or directory: '...config.toml.tmp' -> '...config.toml'`. Эта запись конфигурации теряется (старая конфигурация сохраняется, без потери данных), функциональность не нарушена, но предупреждения мешают отладке, и записываемые значения должны ждать следующей записи, чтобы сохраниться.

В одиночном экземпляре ext4 также существует окно сбоя "атомарного `rename` до записи данных на диск". `_file_lock` — это процессный `threading.RLock`, который не ограничивает перекрытие между процессами/контейнерами.

### [BUG-037] Команды с пробелами не могут быть вызваны

**Проблема**: При регистрации подкоманды с пробелом (например, `@command("admin add")`) команда может быть зарегистрирована и отображена в списке помощи, но при отправке `/admin add` бот не реагирует — ввод интерпретируется как команда `admin` с параметрами `["add"]`; если родительская команда не зарегистрирована, реакции нет. ### [BUG-038] persist=False привязки восстанавливаются из диска после отключения модуля

**Проблема**: Запись `scope.set(path, value, persist=False)` сохраняет привязки во время выполнения (документация обещает, что они не будут записаны на диск и исчезнут после перезапуска процесса, очистятся при отключении модуля), но при любом другом `persist=True` (по умолчанию, например, модуль `set_module` / сохранение конфигурации в веб-интерфейсе) они будут дифференциально записаны в `config.toml`; после отключения модуля и перезагрузки конфигурации эти привязки всё ещё будут восстанавливаться из диска и оставаться в процессе после перезапуска — в противоречие с семантикой "привязки во время выполнения не записываются на диск", и их трудно отследить.

**Исправлено в версии**: 2.9.0-dev.2

**Содержание исправления**: Введён базисная версия `_persisted_tree` (обновлённая из диска, проверенная версия дерева конфигурации) как зеркало диска: `set(persist=True)` применяет только изменения к базисной версии и отправляет дифференциальную запись, привязки persist=False никогда не попадают в постоянное содержимое; "чтение после записи" восстанавливается из окончательного состояния памяти, а не перестраивается через `_apply_tree`. `delete(persist=True)` аналогично: применяет удаление к базисной версии и передаёт поддерево базиса в постоянный слой; `set_action` заменяет старые ключи, старые ключи не остаются в постоянном содержимом.

**Проблема**: Внутри метода обработки команды, вызывающего `wait_reply` / регистрирующего ожидание взаимодействия, ожидание немедленно потребляется той же командой — первый шаг диалога пропускается, "ответ пользователя" на самом деле является самим текстом команды (ответ не соответствует вопросу/данные загрязнены).

**Причина**: `_handle_message` вызывает `interaction.resolve` дважды — в начале и в конце метода; второе завершение `resolve` потребляет ожидание, зарегистрированное во время выполнения; при отключении cmdpass отсутствие alt приводит к пустой строке, что позволяет пройти.

**Влияющие версии**: 2.8.0 (система сессий взаимодействия введена) - 2.10.0
**Исправлено в версии**: 2.10.1-dev.0
**Содержание исправления**: Диспетчеринг сведён к одному `interaction.resolve` (в начале метода), удалено второе завершение; ожидание должно потребляться следующим сообщением.

**Тесты на повторное исправление**: tests/unit/test_unit_command_multiseg.py::test_wait_reply_not_consumed_by_command_trigger

### [BUG-043] select() с одним ключом, но разными путями, последний тихо отменяет первый

**Проблема**: Когда `event.select()` несколько ожиданий приводят к одному ключу сессии (один пользователь, разные шаблоны, несколько ожиданий сессии и т.д.), последнее ожидание отменяет предыдущее, `select` немедленно выбрасывает `InteractionCancelled` вместо ожидания тайм-аута и возврата `(None, None)`.

**Причина**: Каждое ожидание вызывает `interaction.register` по отдельности, их взаимное исключение приводит к отмене `REASON_CONFLICT`, и комментарий утверждает, что "несколько путей для одного пользователя не конфликтуют из-за независимых копий события" — это неверно, так как копии меняют только `user_id`, а ключи для одного пользователя идентичны.

**Влияющие версии**: 2.9.0 (select введён) - 2.10.0
**Исправлено в версии**: 2.10.1-dev.0
**Содержание исправления**: select изменён на агрегацию ожиданий — все ожидания объединяются в одно предложение с пользовательским matcher (по ключу наборы регистрируются, разделяются одна общая будущая), при совпадении возвращается соответствующий индекс; ожидания с одним ключом естественно существуют вместе.

**Тесты на повторное исправление**: tests/unit/test_unit_command_multiseg.py::test_select_same_user_multi_branch

**Серьезность**: 🟡 Средний
**Тип**: Система событий

### [BUG-045] Без alt_message адаптера взаимодействие с оригинальными примитивами постоянно тайм-аут, команды не проникают

### [BUG-046] Вложенные заголовки подтаблицы в шаблоне конфигурации смещаются в верхний уровень

**Проблема**: Вложенные dataclass в декларативной конфигурации (ConfigClass с вложенным dataclass) при создании шаблона конфигурации помещают заголовок подтаблицы `[Nested]` в верхний уровень, а не в компонентный раздел — адаптер не может получить значение `cfg.嵌套字段`; `config.full.example` также смещается.

**Причина**: Генератор шаблона для вложенных dataclass рисует относительные заголовки таблицы (`[Nested]`), а семантика заголовков TOML — это абсолютные пути от корня; `setConfigTemplate` старая реализация переносит разобранный объект таблицы в компонентный раздел, `full.example` просто объединяет текст, обе траектории не переназначают относительные заголовки под компонентный путь.

**Влияющие версии**: 2.10.0 - 2.10.1 (введение декларативного шаблона вложенных dataclass с этой версией)
**Исправлено в версии**: 2.10.2-dev.0
**Содержание исправления**: `setConfigTemplate` точно переназначает заголовки таблицы (например, `[Nested]` → `[组件名.Nested]`) при анализе подтаблицы; `config.full.example` исправляет передачу `_prefix` для прямого вывода абсолютных заголовков.

**Тесты на повторное исправление**: tests/unit/test_unit_config.py::TestTomlclassEngineMigration::test_template_write_idempotent_and_nested_anchored

**Серьезность**: 🟡 Средний
**Тип**: Система конфигурации / Адаптер
