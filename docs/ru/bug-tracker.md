# Трекер ошибок

Данный документ фиксирует известные ошибки ErisPulse SDK и их исправления, отсортированные по времени исправления.

> **Для читателя**
> Никакое программное обеспечение не идеально, даже самые внимательные разработчики могут допустить небольшие ошибки. В этот трекер включены только проблемы, которые реально влияют на работу — те тонкие недостатки, которые даже не достигают уровня «легкий», здесь отсутствуют. Список с пометкой «серьезный» может показаться большим, но публичная запись этих ошибок призвана сделать отладку и отслеживание более плавными, а не вызывать беспокойство: видимые, записанные и исправленные проблемы — это доказательство того, что проект постоянно улучшается. Видя этот список, не стоит волноваться — это инструмент для отладки, а не источник страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ корневой причины, охватываемый диапазон версий, план исправления и т.д. Рекомендуется перед обновлением проверять, охватывает ли «диапазон версий» используемую вами версию.
> - Если необходимо добавить новую запись об ошибке, добавьте содержимое в соответствующее место, следуя формату полей и классификации серьезности/типа, описанным ниже.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем. Стремитесь указать сообщение об ошибке или типичную сцену |
| **Причина** | Анализ корневой причины, указывающий на конкретный дефект кода (с «цепочкой корневых причин» для сложных сценариев) |
| **Влияющие версии** | Охватываемый диапазон версий, формат `Версия введения - Версия исправления` (включая бета-версии) |
| **Исправленная версия** | Конкретный номер версии, содержащий исправление |
| **Содержание исправления** | Краткое описание плана исправления, включая ключевые изменения кода |
| **Дата исправления** | Дата выпуска соответствующей версии исправления, в формате `ГГГГ/ММ/ДД` |
| **Серьезность** | Отмечено в соответствии с «шкалой серьезности» |
| **Тип** | Отмечено в соответствии с «классификацией типов» ниже, можно комбинировать (например, `Адаптер / Маршрутизация`) |

### Необязательные поля

| Поле | Описание | Применение |
|------|------|---------|
| **Шаги воспроизведения** | Минимальный путь для воспроизведения ошибки | Рекомендуется для сложных, случайных ошибок |
| **Связанные** | Ссылки на связанные Issue / PR / Commit | Добавляется, если есть внешние обсуждения |
| **Тесты регрессии** | Пути к тест-кейсам для проверки исправления и предотвращения повторного появления | Добавляется, если соответствующие тесты pytest написаны |

## Шкала серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Серьезный | Приводит к сбою процесса, потере/повреждению данных, полной недоступности основных функций, уязвимости безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Функциональные сбои, но есть пути обхода, не основные функции не работают, случайные проблемы | Ошибочное определение состояния, повторный запуск, истечение кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на основную функциональность, только проблемы качества кода или пользовательского опыта, потенциальный риск не проявился | Устаревший API, мертвый код, отсутствие предупреждающих логов |

## Исправленные ошибки

### [BUG-001] Повторная регистрация обработчиков событий приводит к многократной обработке событий

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков, одно и то же событие будет многократно запускаться, что приведет к многократному выполнению команды и повторному выводу логов.

**Причина**: `BaseEventHandler` при регистрации обработчика в событийную шину адаптера не содержит логики удаления дубликатов, каждый декоратор будет присоединяться к шине один раз, что приводит к многократному вызову при диспетчеризации событий.

**Влияющие версии**: 2.2.0-dev.0 - 2.2.1-dev.0

**Исправленная версия**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался только один раз в шину адаптера, предотвращая многократный запуск.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Серьезный

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера в команде Init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7, параметр метода не соответствует типу. Метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Влияющие версии**: 2.3.7 - 2.3.9-dev.1

**Исправленная версия**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра метода `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средний

**Тип**: CLI

---

### [BUG-003] Команды не работают после перезапуска

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные с помощью `@command`, не могут быть запущены, что проявляется в том, что робот не отвечает после отправки команды.

**Причина**: `adapter.shutdown()` очищает событийную шину, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, поэтому метод `_process_event` считает, что уже подключен к шине адаптера, и пропускает повторную регистрацию.

**Влияющие версии**: 2.2.x - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, после отключения шины `_clear_handlers()` следующая `register()` автоматически перерегистрируется, адаптация к сценариям shutdown/restart.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Серьезный

**Тип**: Система событий

---

### [BUG-004] Обработчики событий жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла по-прежнему существуют и многократно запускаются, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищается при `uninit()`, после restart старые и новые обработчики существуют одновременно.

**Влияющие версии**: 2.3.0 - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в конце процесса очистки `Uninitializer` (после всех событий), после завершения всех событий.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средний

**Тип**: Время выполнения

### [BUG-005] Event.is_friend_add/is_friend_delete не соответствуют стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Несоответствие с использованными в `notice.py` декораторами `on_friend_add`/`on_friend_remove` приводит к тому, что при регистрации обработчика через декораторы, соответствующие методы `is_friend_add()`/`is_friend_delete()` возвращают `False`.

**Причина**: В `wrapper.py` используется нестандартное наименование, а в `notice.py` используется правильное наименование стандарта OB12.

**Влияющие версии**: С момента реализации

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения соответствия `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, приводя к неправильному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает очистку `_started_instances`. Если `clear()` вызывается, когда адаптер работает, `_started_instances` сохраняет висящие ссылки, что приводит к ошибочному определению состояния после перезапуска.

**Причина**: При введении `_started_instances` в 2.4.0-dev.1 не было синхронной очистки в `clear()`.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания future и получения временной метки, этот метод в Python 3.10+ устарел, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с методом `wait_for()` в том же файле `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, последующий `wait_for()` использовал правильный API, но старый код не был обновлен.

**Влияющие версии**: 2.3.0-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Замена двух вызовов `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкий

**Тип**: Система событий

### [BUG-008] Событие отключения Bot при shutdown повторно отправляется

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` в процессе закрытия повторно отправляет события отключения Bot, что приводит к многократной маркировке одной и той же группы Bot и многократному запуску событий жизненного цикла `adapter.bot.offline`.

**Причина**: Введённая в 2.4.0-dev.1 система отслеживания состояния Bot не установила флаг «в процессе закрытия» во время `shutdown()`, `_update_bot_status()` не может различить нормальное отключение и каскадное отключение в процессе закрытия.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, который устанавливается в True в начале `shutdown()` и сбрасывается в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторные отправки в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к BaseModule приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к свойствам лениво загружаемого BaseModule модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает завершения, что может привести к гонке данных при доступе к свойству.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и сразу возвращает, не обеспечив завершения инициализации.

**Влияющие версии**: 2.4.0-dev.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule изменяется на использование `asyncio.run(self._initialize())`, чтобы обеспечить завершение инициализации перед возвратом. Сохраняется прозрачность прокси, пользователь не должен осознавать различие между синхронным и асинхронным.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Загрузка системы

### [BUG-010] Многопоточный запись в конфигурацию приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция `_flush_config()` (чтение-изменение-запись) не является атомарной, что может привести к потере частичной записи.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты с помощью файла блокировки, и `Timer` `_schedule_write` может быть запущен несколько раз, что приводит к перезаписи.

**Влияющие версии**: 2.3.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавлена механизм блокировки файла (`_file_lock`), чтобы обеспечить атомарность операций с файлом
2. Использование временного файла для записи с атомарным переименованием (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Серьезный

**Тип**: Система конфигурации

### [BUG-011] CTRL+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие CTRL+C не может остановить программу. После нормального запуска и вывода информации о сервере маршрутизации, CTRL+C не реагирует, и программу можно остановить только через диспетчер задач. При запуске через `epsdk run` программа останавливается нормально, но `epsdk run` запускается через модель подпроцесса.

**Причина**: ASGI-сервер Hypercorn через `signal.signal(SIGINT, handler)` внутри функции `serve()` зарегистрировал свой обработчик SIGINT, заменив механизм обработки `KeyboardInterrupt` Python по умолчанию. При запуске Hypercorn через `asyncio.create_task()` в качестве фоновой задачи внутренний процесс остановки Hypercorn не может быть нормально запущен (так как он ожидает режима `worker_serve`), что приводит к тому, что сигнал CTRL+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Влияющие версии**: 2.3.6 - 2.4.2

**Исправленная версия**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена ASGI-сервера Hypercorn на Uvicorn (`pyproject.toml` зависимость)
2. Использование `uvicorn.Server._serve()` для прямого запуска сервера, **обход** контекстного менеджера `capture_signals()`
3. Использование `server.should_exit = True` для обеспечения элегантной остановки, с отменой фоновой задачи при превышении времени ожидания
4. Синхронное удаление модели подпроцесса и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Серьезный

**Тип**: CLI / Время выполнения

### [BUG-022] _resolve_account() возвращает ошибку при解析е аккаунта (_accounts_data не заполнен)

**Проблема**: После перестройки системы конфигурации в 2.5.2 при вызове `wait_reply`, `reply` и других методов, требующих отправки сообщений, возникает ошибка `ValueError("Не объявлен AccountConfigClass, невозможно разрешить аккаунт")`. **Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был перестроен в `_ensure_accounts_exist()` (генерирует только шаблон конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда равно `None`, что приводит к тому, что `_resolve_account()` рано возвращает `(None, None)`, разрешение аккаунта полностью не работает.

**Цепочка причин**:
```
_load_accounts() удалён
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        → Далее вызовы _resolve_account() (например, call_api) получают None
          → Вызывается ошибка
```

**Влияющие версии**: 2.5.2-dev.5 - 2.5.2

**Исправленная версия**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `self._ensure_accounts_exist()` восстанавливается заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # Восстановление заполнения, источник данных — актуальные accounts
```
Логика `_resolve_account()` остаётся без изменений, полностью обратная совместимость:
- Адаптеры, не объявившие `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращаются `(None, None)`
- Адаптеры, объявившие `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, переопределившие `_load_accounts` или вручную установившие `_accounts_data`: в `super().__init__()` после установки, приоритет выше

**Серьезность**: 🔴 Серьезный

### [BUG-025] on_config_update не вызывается для ядра маршрутизации

**Проблема**: `on_config_update(old, new)` объявлен в базовых классах (`BaseModule` / `BaseAdapter`), но ядро фреймворка не связывает эти события с изменениями конфигурации. На практике: при изменении конфигурации через панель управления это срабатывает, а при ручном редактировании `config.toml` или вызове `setConfig()` `on_config_update` не вызывается.

**Причина**: `ConfigManager` при изменении конфигурации излучает события жизненного цикла `config.set` / `config.updated`, но отсутствует логика подписки этих событий на методы `on_config_update` компонентов.

**Цепочка причин**:
```
Ядро не подписывается на config.set / config.updated
  → События изменения конфигурации не пересылаются
    → on_config_update не вызывается
      → Ручное редактирование файла / вызов setConfig не запускает теплый обновления
```

**Влияющие версии**: Все версии

**Исправленная версия**: 2.6.2

**Содержание исправления**: `ModuleManager` / `AdapterManager` регистрируют подписку на события `config.set` (перекрывает путь `setConfig()` кода) и `config.updated` (перекрывает путь ручного редактирования файла), после сопоставления по префиксу ключа конфигурации вызывают соответствующий метод `on_config_update` компонента, передавая типобезопасный объект конфигурации. Также исправлена проблема `_flush_config()` с записью файла без синхронизации `_config_mtime`, чтобы избежать повторного запуска `config.updated` задачей监听 файлов, ошибочно интерпретирующей запись фреймворка как внешнее изменение.

**Соответствие**: Теплый обновление теперь централизованно поддерживается ядром. Логика, ранее выполняемая панелью управления, удалена, после обновления фреймворка необходимо обновить и панель управления, иначе будет повторный вызов (ядро + панель по одному разу). Подпись и семантика метода `on_config_update` остаются без изменений, подклассы не нуждаются в изменении.

**Дата исправления**: 2026/07/23

**Серьезность**: 🟡 Средний

**Тип**: Система конфигурации

### [BUG-026] Неверная оценка цели ответа в событиях notice/request

**Проблема**: При вызове `event.reply()` в событии уведомления (например, добавление участника в группу `group_member_increase`), сообщение отправляется в личную переписку пользователя, который вызвал событие, а не в группу, где произошло событие. Аналогично, в событии уведомления о друге, цель ответа может быть неправильно определена.

**Причина**: `infer_receive_type()` возвращает `detail_type` как тип сессии. Для событий `message` это правильно (значения `detail_type` `private`/`group` — это типы сессии), но для событий `notice/request` `detail_type` — это семантический подтип (например, `group_member_increase`, `friend_increase`), а не тип сессии. Последующие `convert_to_send_type()` и `get_id_field()` в карте сопоставления не находят это значение, возвращаются к дефолтным `"user"` / `"user_id"`, что приводит к неправильной цели ответа.

**Цепочка причин**:
```
detail_type уведомления = "group_member_increase"
  → infer_receive_type() возвращает "group_member_increase"
    → convert_to_send_type("group_member_increase") не в карте сопоставления → возвращается "user"
    → get_id_field("group_member_increase") не в карте сопоставления → возвращается "user_id"
      → target_id = event["user_id"]  ← личная переписка нового участника (а не группы)
```

**Влияющие версии**: Все версии

**Исправленная версия**: 2.7.0-dev.3

**Содержание исправления**: `infer_receive_type()` добавляет проверку — `detail_type` возвращается напрямую только если это известный тип сессии (стандартный или пользовательский тип); в противном случае по полю идентификатора (`group_id` / `channel_id` / `user_id` и т.д.) выводится правильный тип сессии.

**Тесты регрессии**: `tests/unit/test_unit_session_type.py` → `TestNoticeRequestTypeInference` (10 тестов)

**Дата исправления**: 2026/07/29

**Серьезность**: 🟢 Легкий

**Тип**: Система событий
