# Баг-трекер

Данный документ содержит список известных багов ErisPulse SDK и информацию об их исправлении, отсортированную по времени исправления.

> **Для читателя**
> Ни одно программное обеспечение не бывает идеальным с самого начала, даже самые внимательные разработчики могут оставить небольшие ошибки. В этот трекер включены только проблемы, которые оказывают реальное влияние на работу приложения — те, что слишком мелкие или не достигают даже уровня "незначительного" бага, здесь не отображаются. Список содержит "серьезные" пункты, которых может показаться много, но публикация таких багов имеет цель сделать поиск и отслеживание проблем более гладким, а не вызывать беспокойство: проблемы, которые видны, записаны и исправлены, сами по себе являются свидетельством улучшения проекта. Не стоит беспокоиться, глядя на этот список — это инструмент для поиска проблем, а не источник страха.

> **Как читать и правила поддержки**
> - Каждая запись о баге содержит структурированные поля: описание проблемы, анализ причины, диапазон версий, в которых баг актуален, номер версии, в которой исправлен, краткое описание исправления, дата публикации, уровень серьезности и тип. Рекомендуется перед обновлением проверять, охватывает ли "диапазон версий" используемую вами версию.
> - Если требуется добавить новую запись о баге, дополните соответствующую позицию, следуя формату полей и классификации серьезности/типа, описанным ниже.

## Классификация серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Серьезный | Причиняет сбой процесса, потерю/повреждение данных, полную недоступность основных функций, уязвимости безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Нарушение функциональности, но есть пути обхода, неосновные функции не работают, случайные проблемы | Ошибочное определение состояния, повторный запуск, истечение кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на основную функциональность, только проблемы качества кода или пользовательского опыта, потенциальные риски не проявляются | Устаревший API, мертвый код, отсутствие предупреждающего лога |

## Исправленные ошибки

### [BUG-001] Дублированная регистрация обработчиков событий, приводящая к многократной обработке событий

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков, одно и то же событие будет триггериться несколько раз, что приводит к многократному выполнению команд, повторному выводу логов и т.д.

**Причина**: `BaseEventHandler` не имеет логики удаления дубликатов при регистрации обработчиков в событийном буфере адаптера — каждый декоратор добавляет обработчик отдельно, и при распределении событий он вызывается несколько раз.

**Версии, затронутые проблемой**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия с исправлением**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался в буфере адаптера только один раз, предотвращая повторные триггеры.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-002] Ошибка типа при указании пути конфигурации адаптера в команде инициализации

**Проблема**: При использовании `ep init` для интерактивной инициализации, выбор конфигурации адаптера приводит к ошибке:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для конкатенации путей.

**Версии, затронутые проблемой**: 2.3.7 - 2.3.9-dev.1

**Версия с исправлением**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра метода `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средняя

**Тип**: CLI

---

### [BUG-003] После перезапуска события команды не срабатывают

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные через `@command`, не срабатывают, что приводит к отсутствию ответа бота на отправленные команды.

**Причина**: `adapter.shutdown()` очищает событийный буфер, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, поэтому метод `_process_event` считает, что уже подключен к буферу адаптера, и пропускает повторную регистрацию.

**Версии, затронутые проблемой**: 2.2.x - 2.4.0-dev.2

**Версия с исправлением**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при `_clear_handlers()` отключение от буфера, при следующем `register()` автоматическая повторная регистрация, адаптация к сценариям `shutdown/restart`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

### [BUG-004] Неочищенные обработчики событий жизненного цикла

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно триггерятся, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищается в `uninit()`, после перезапуска старые и новые обработчики существуют одновременно.

**Версии, затронутые проблемой**: 2.3.0 - 2.4.0-dev.2

**Версия с исправлением**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в конце процесса очистки `Uninitializer` (после всех событий), чтобы избежать повторного триггера.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средняя

**Тип**: Рантайм

### [BUG-005] Несоответствие detail_type у Event.is_friend_add/is_friend_delete и стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Это несоответствие с декораторами `on_friend_add`/`on_friend_remove` в `notice.py` приводит к тому, что соответствующие методы `is_friend_add()`/`is_friend_delete()` возвращают `False` при триггере обработчиков, зарегистрированных через декораторы.

**Причина**: В `wrapper.py` используются нестандартные имена, а в `notice.py` — правильные значения стандарта OB12.

**Версии, затронутые проблемой**: С момента реализации

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения проверки `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, приводящее к некорректному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен при вызове `clear()`, `_started_instances` сохраняет неверные ссылки, что приводит к ошибочному состоянию после перезапуска.

**Причина**: В 2.4.0-dev.1 при введении `_started_instances` не было синхронного очищения в `clear()`.

**Версии, затронутые проблемой**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущих объектов и получения временных меток, этот метод устарел в Python 3.10+ и в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Это несоответствие с методом `wait_for()` в `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, а позже добавленный `wait_for()` использовал правильный API, но старый код не был обновлен.

**Версии, затронутые проблемой**: 2.3.0-dev.0

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: Замена двух вызовов `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкая

**Тип**: Система событий

### [BUG-008] События отключения бота при shutdown повторно отправляются

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` в процессе закрытия повторно отправляет события отключения бота, что приводит к многократной маркировке бота как отключенного и многократному триггеру события `adapter.bot.offline`.

**Причина**: Введённая в 2.4.0-dev.1 система отслеживания состояния бота не установила флаг "в процессе закрытия", поэтому `_update_bot_status()` не могла отличить нормальное отключение от отключения в процессе завершения.

**Версии, затронутые проблемой**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, который устанавливается при начале `shutdown()` и сбрасывается при завершении; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к BaseModule через LazyModule приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к атрибуту лениво загружаемого BaseModule, модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает завершения, что приводит к гонке состояний, когда атрибут может быть не инициализирован.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и немедленно возвращает, не ожидая завершения инициализации.

**Версии, затронутые проблемой**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule заменена на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем вернуться. Сохраняется прозрачность прокси, пользователь не должен знать о различии между синхронным и асинхронным.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Система загрузки

### [BUG-010] Многопоточная запись в конфигурацию приводит к потере данных

**Проблема**: При многопоточном доступе несколько потоков одновременно вызывают `config.setConfig()`, операция `_flush_config()` (чтение-модификация-запись) не является атомарной, что может привести к потере данных.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет файловой блокировки, и `Timer` `_schedule_write` может быть запущен несколько раз, что приводит к перезаписи.

**Версии, затронутые проблемой**: 2.3.0 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавлена файловая блокировка (`_file_lock`) для атомарности операций с файлом
2. Использование временного файла для записи, затем атомарное переименование (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Критическая

**Тип**: Система конфигурации

### [BUG-011] Ctrl+C не может остановить программу на Windows

**Проблема**: При прямом запуске `python main.py` на Windows, нажатие Ctrl+C не останавливает программу. Программа запускается и выводит информацию о сервере маршрутизации, но Ctrl+C не реагирует, программу можно остановить только через диспетчер задач. При запуске через `epsdk run` программа останавливается корректно, но `epsdk run` использует подпроцесс.

**Причина**: ASGI-сервер Hypercorn в функции `serve()` регистрирует свой обработчик сигнала `SIGINT`, заменяя стандартный механизм обработки `KeyboardInterrupt` Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()`, внутренний процесс остановки Hypercorn не запускается (так как ожидается режим `worker_serve`), сигнал Ctrl+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Версии, затронутые проблемой**: 2.3.6 - 2.4.2

**Версия с исправлением**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена ASGI-сервера Hypercorn на Uvicorn (изменение зависимости в `pyproject.toml`)
2. Использование `uvicorn.Server._serve()` для запуска сервера, **без** контекстного менеджера `capture_signals()`
3. Остановка через `server.should_exit = True`, с отменой фоновой задачи при таймауте
4. Удаление модели запуска через подпроцесс и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Критическая

**Тип**: CLI / Рантайм

### [BUG-022] Ошибка в `_resolve_account()` (отсутствие заполнения `_accounts_data`)

**Проблема**: После рефакторинга конфигурационной системы в 2.5.2, при вызове `wait_reply`, `reply` и других методов, требующих отправки сообщений, возникает ошибка `ValueError("Не объявлен AccountConfigClass, невозможно разрешить аккаунт")`. Даже если адаптер правильно настроен на несколько аккаунтов, разрешение аккаунта всё равно не работает.

**Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторингован в `_ensure_accounts_exist()` (только генерация шаблона конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда равно `None`, и `_resolve_account()` рано возвращает `(None, None)`, разрешение аккаунта полностью теряется.

**Корневая цепочка**:
```
_load_accounts() удалён
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        → методы, использующие _resolve_account (например, call_api), получают None
          → вызывает ошибку
```

**Версии, затронутые проблемой**: 2.5.2-dev.5 - 2.5.2

**Версия с исправлением**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `_ensure_accounts_exist()` восстанавливается заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # восстановление заполнения, данные берутся из актуального свойства accounts
```
Логика `_resolve_account()` остаётся неизменной, полностью обратная совместимость:
- Адаптеры, не объявляющие `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращается `(None, None)`
- Адаптеры, объявляющие `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, переопределяющие `_load_accounts` или вручную устанавливающие `_accounts_data`: перезаписываются после `super().__init__()`, с наивысшим приоритетом

**Дата исправления**: 2026/07/07

**Серьезность**: 🔴 Критическая

**Тип**: Адаптер / Система конфигурации

**Сценарий воспроизведения**: ① `scope.set_module("testplat", blocked=["TestB"], persist=False)` → возвращает False; ② любой модуль выполняет `config.setConfig("HelpModule", {...})` → вызывает перестройку scope; ③ `scope.is_allowed("testplat", None, "TestB")` возвращает True (ожидается False).

### [BUG-035] Веб-интерфейсе конфигурации select-опции и dict-поля отображаются как [object Object]

**Проблема**: В веб-интерфейсе панели конфигурации опции select отображаются как `[object Object]` (например, динамически генерируемые стили цвета); необъявленные поля типа dict (например, `stalker_mode`, `knowledge_base`) отображаются в текстовом поле как `[object Object]`, невозможно просматривать и редактировать.

**Причина**: Две независимые ошибки: ① парсер i18n `_resolve_i18n_text` восстанавливает только словари с ключом `i18n`, метки опций с `default` (без `i18n`) передаются как есть, фронтенд `esc(label)` приводит к `[object Object]`; ② рендеринг Dashboard только для массивов делает JSON textarea, dict-значения попадают в текстовое поле и приводятся к `String()`. Кроме того, если модуль объявляет `_schema_meta` как обычное поле dataclass (без `ClassVar`), оно попадает в схему, усугубляя путаницу.

**Версии, затронутые проблемой**: 2.7.0 - 2.8.0-dev.2
**Версия с исправлением**: 2.8.0-dev.2
**Содержание исправления**: ① `_resolve_i18n_text` поддерживает словари только с `default`; ② схема/шаблоны/значения по умолчанию/заполнение/валидация исключают поля с подчёркиванием в начале (ошибочная объявления безвредны); ③ рендеринг Dashboard для опций select label объекта с приоритетом `default`, dict/table поля рендерятся как JSON textarea (сохраняются как `tp=object` и восстанавливаются через `JSON.parse`).
**Дата исправления**: 2026/09/09

**Тесты**: `tests/unit/test_unit_config.py::TestResolveI18nDefaultOnlyDict`, `TestSchemaUnderscoreFieldExclusion`

**Серьезность**: 🟡 Средняя
**Тип**: Система конфигурации
