# Отслеживание ошибок

Данный документ содержит записи об известных ошибках ErisPulse SDK и их исправлениях, отсортированных по времени исправления.

> **Сообщение читателям**
> Ниже перечислены только те проблемы, которые реально влияют на работу. Мелкие недочеты, которые не достигают даже уровня "легкий", здесь не представлены. Хотя в списке может показаться много "серьезных" пунктов, основная цель публикации — обеспечить более плавное выявление и восстановление, а не вызывать беспокойство: проблемы, которые видны, записаны и исправлены, сами по себе являются доказательством улучшения проекта. Не стоит беспокоиться, увидев этот список — это инструмент для диагностики, а не источник страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ корневой причины, диапазон версий, влияющих на проблему, план исправления и т.д. Рекомендуется перед обновлением проверять, охватывает ли "диапазон версий" используемую вами версию.
> - Если вы хотите добавить новую запись об ошибке, добавьте содержимое в соответствующее место, следуя спецификациям полей и классификации серьезности/типа, описанным ниже.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем. Постарайтесь указать сообщение об ошибке или типичную сцену |
| **Причина** | Анализ корневой причины, указывающий на конкретные дефекты кода (с визуализацией "цепочки причин" для сложных сценариев) |
| **Влияющие версии** | Диапазон версий, затронутых проблемой, формат `введённая версия - исправленная версия` (включая версии dev) |
| **Исправленная версия** | Конкретный номер версии, в которой была исправлена ошибка |
| **Содержание исправления** | Краткое описание решения, включая ключевые изменения кода |
| **Дата исправления** | Дата выпуска соответствующей версии исправления, формат `YYYY/MM/DD` |
| **Серьезность** | Отмечено по классификации "уровней серьезности" |
| **Тип** | Отмечено по классификации "типов" и может комбинироваться (например, `адаптер / маршрутизация`) |

| Поле | Описание | Сценарий применения |

| **Тесты на регрессию** | Позиция тест-кейсов для проверки исправления и предотвращения повторного появления | Добавляется, если соответствующие тесты pytest написаны |

## Классификация серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Серьёзный | Причина краха процесса, потери/повреждения данных, полной недоступности ключевых функций, уязвимостей безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Нарушение функциональности, но с возможностью обхода, не ключевые функции недоступны, случайные проблемы | Неверное определение состояния, повторное срабатывание, истечение кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на ключевые функции, только проблемы качества кода или пользовательского опыта, потенциальная угроза не проявилась | Устаревший API, мёртвый код, отсутствие предупреждающего лога |

## Исправленные ошибки

### [BUG-001] Дублированная регистрация обработчиков событий приводит к многократной обработке событий

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков одно и то же событие будет многократно запускаться, что приводит к многократному выполнению команд и повторному выводу логов.

**Причина**: `BaseEventHandler` при регистрации обработчика на событийную шину адаптера отсутствует логика удаления дубликатов. Каждый декоратор добавляет обработчик на шину один раз, что приводит к многократному вызову при распределении событий.

**Влияющие версии**: 2.2.0-dev.0 - 2.2.1-dev.0

**Исправленная версия**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался только один раз на шину адаптера, предотвращая многократное срабатывание.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Серьёзный

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера в команде Init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации при выборе конфигурации адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Влияющие версии**: 2.3.7 - 2.3.9-dev.1

**Исправленная версия**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра `_configure_adapters_interactive_sync` с `str` на `Path`, вызов метода с передачей объекта `Path`.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средний

**Тип**: CLI

---

### [BUG-003] Командные события не работают после перезапуска

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные через `@command`, не срабатывают, что проявляется в отсутствии реакции бота на отправленные команды.

**Причина**: После очистки событийной шины в `adapter.shutdown()` состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, что приводит к тому, что метод `_process_event` считает, что уже зарегистрирован на шину адаптера, и пропускает повторную регистрацию.

**Влияющие версии**: 2.2.x - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при разрыве соединения в `_clear_handlers()` следующая `register()` автоматически перерегистрируется, адаптируясь к сценариям shutdown/restart.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Серьёзный

**Тип**: Система событий

---

### [BUG-004] Обработчики событий жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно срабатывают, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` при `uninit()` никогда не очищается, после перезапуска старые и новые обработчики существуют одновременно.

**Влияющие версии**: 2.3.0 - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в конце процесса очистки `Uninitializer` (после всех событий), чтобы удалить обработчики жизненного цикла.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средний

**Тип**: Рантайм

### [BUG-005] Event.is_friend_add/is_friend_delete detail_type не соответствует стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Это несоответствие с значениями, используемыми в декораторах `notice.py` `on_friend_add`/`on_friend_remove`, приводит к тому, что методы проверки `is_friend_add()`/`is_friend_delete()` возвращают `False` при регистрации обработчиков через декораторы.

**Причина**: В `wrapper.py` используется нестандартное наименование, в то время как `notice.py` использует правильные стандартные наименования OB12.

**Влияющие версии**: С момента реализации

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения проверки `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, приводя к некорректному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен, и вызывается `clear()`, `_started_instances` сохраняет висячие ссылки, что приводит к ошибкам состояния после перезапуска.

**Причина**: При введении `_started_instances` в 2.4.0-dev.1 не было синхронной очистки в `clear()`.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущего и получения временной метки, этот метод устарел в Python 3.10+, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с `wait_for()` в том же файле `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, последующий `wait_for()` использовал правильный API, но не было возврата к исправлению старого кода.

**Влияющие версии**: 2.3.0-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Замена `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкий

**Тип**: Система событий

### [BUG-008] Событие отключения Bot при shutdown повторно отправляется

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` повторно отправляет события отключения Bot в процессе закрытия, что приводит к многократной маркировке одной и той же группы Bot как отключенных и многократному срабатыванию события жизненного цикла `adapter.bot.offline`.

**Причина**: Система отслеживания состояния Bot, введенная в 2.4.0-dev.1, не установила флаг "в процессе закрытия" во время `shutdown()`, и `_update_bot_status()` не может отличить нормальное отключение от каскадного отключения в процессе закрытия.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, который устанавливается в `True` в начале `shutdown()` и сбрасывается в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к BaseModule из-за незавершённой инициализации

**Проблема**: При синхронном доступе к свойствам лениво загруженного BaseModule модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает завершения, что приводит к гонке за ресурсами при доступе к свойствам.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и немедленно возвращает, не обеспечив завершения инициализации.

**Влияющие версии**: 2.4.0-dev.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule изменена на использование `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем вернуться. Сохраняется прозрачность прокси-объекта, пользователь не должен осознавать различий между синхронным/асинхронным контекстом.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Загрузочная система

### [BUG-010] Многопоточный доступ к конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция `_flush_config()` (чтение-изменение-запись) не является атомарной, что может привести к потере части записей.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты с помощью файлового блокировщика, и `_schedule_write` может быть запущен несколько раз, что приводит к перезаписи.

**Влияющие версии**: 2.3.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавлена механизм файловой блокировки (`_file_lock`) для обеспечения атомарности операций с файлом
2. Использование временного файла для записи с последующей атомарной заменой (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Серьёзный

**Тип**: Система конфигурации

### [BUG-011] CTRL+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие CTRL+C не завершает программу. Программа нормально запускается и выводит информацию о сервере маршрутизации, но CTRL+C не вызывает никакого ответа, и можно только принудительно завершить процесс через диспетчер задач. При запуске через `epsdk run` остановка происходит нормально — но `epsdk run` запускается через модель подпроцесса.

**Причина**: ASGI-сервер Hypercorn через `signal.signal(SIGINT, handler)` внутри `serve()` зарегистрировал свой обработчик SIGINT, перезаписав механизм обработки KeyboardInterrupt Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()` внутренний процесс остановки Hypercorn не может быть нормально запущен (он ожидает режима `worker_serve`), что приводит к тому, что сигнал CTRL+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Влияющие версии**: 2.3.6 - 2.4.2

**Исправленная версия**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена ASGI-сервера Hypercorn на Uvicorn (`pyproject.toml` зависимость)
2. Прямой запуск сервера с помощью `uvicorn.Server._serve()`, **обход** контекстного менеджера `capture_signals()` для сигналов
3. Использование `server.should_exit = True` для обеспечения элегантного завершения, с отменой фоновой задачи при истечении таймера
4. Синхронное удаление модели подпроцесса и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцесса больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Серьёзный

**Тип**: CLI / Рантайм

```
_load_accounts() удалён
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → возвращает (None, None)
```

- Адаптеры, не объявляющие `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращаются `(None, None)`
- Адаптеры, объявляющие `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, перезаписывающие `_load_accounts` или вручную устанавливающие `_accounts_data`: в `super().__init__()` перезапись, с наивысшим приоритетом

### [BUG-025] on_config_update обратный вызов не был подключен к ядру

**Проблема**: `on_config_update(old, new)` был определён в базовых классах (`BaseModule` / `BaseAdapter`), но ядро фреймворка не связало этот обратный вызов с событием изменения конфигурации. Фактически: при изменении конфигурации через панель управления можно вызвать обратный вызов, а при ручном редактировании `config.toml` или вызове `setConfig()` через код — обратный вызов не срабатывает.

**Причина**: `ConfigManager` при изменении конфигурации излучает события жизненного цикла `config.set` / `config.updated`, но отсутствует логика подписки на эти события для передачи в методы `on_config_update` компонентов.

**Цепочка причин**:
```
Ядро не подписалось на config.set / config.updated
  → события изменения конфигурации не пересылаются
    → on_config_update не вызывается
      → ручное редактирование файла / вызов setConfig() не запускает горячий обратный вызов
```

**Влияющие версии**: Все версии

**Исправленная версия**: 2.6.2

**Содержание исправления**: `ModuleManager` / `AdapterManager` регистрируют подписки на события `config.set` (путь перекрытия вызова `setConfig()` кодом) и `config.updated` (путь ручного редактирования файла), по префиксу конфигурационного ключа сопоставляют и вызывают соответствующий компонент `on_config_update`, передавая типобезопасный объект конфигурации. Также исправлена проблема `_flush_config()` при записи файла, когда `_config_mtime` не синхронизируется, чтобы избежать повторного срабатывания `config.updated` из-за ошибочного восприятия изменения файлом как внешним.

**Совместимость**: Горячее обновление конфигурации теперь управляется ядром. Логика, ранее выполняемая панелью управления, удалена, после обновления фреймворка необходимо обновить и панель управления, иначе будет дублирование вызовов (ядро + панель по одному разу). Подпись и семантика метода `on_config_update` остаются без изменений, подклассам не нужно ничего менять.

**Дата исправления**: 2026/07/23
