# Трекер ошибок

Документация содержит список известных ошибок ErisPulse SDK и информацию о их исправлении, отсортированных по времени исправления.

> **Для читателя**
> Никакое программное обеспечение не бывает идеальным, даже самые внимательные разработчики могут оставлять небольшие ошибки. В этот трекер включены только те проблемы, которые реально влияют на работу. Те, которые слишком мелкие, чтобы даже считать их "незначительными", здесь не появятся. Список с пометкой "Критично" может показаться большим, но цель публикации — сделать отслеживание и откат более плавными, а не вызывать беспокойство: видимые, записанные и исправленные проблемы — это доказательство того, что проект становится лучше. Не стоит беспокоиться, увидев этот список, он служит инструментом для диагностики, а не источником страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ корневой причины, диапазон версий, в которых она возникла, номер версии, в которой была исправлена, краткое описание исправления, дата публикации, серьезность и тип. Рекомендуется перед обновлением проверять, охватывает ли "Версия, в которой возникла" текущую используемую версию.
> - Если нужно добавить новую запись об ошибке, вставьте её в соответствующее место, следуя формату полей и классификации серьезности/типа.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем. Старайтесь указать сообщения об ошибках или типичные сценарии |
| **Причина** | Анализ корневой причины, указывающий на конкретные дефекты кода (включая "цепочку корневых причин" для сложных сценариев) |
| **Версия, в которой возникла** | Влияющие версии, в формате `Версия, в которой возникла - Версия, в которой исправлена` (включая версии dev) |
| **Исправлено в версии** | Номер версии, в которой была исправлена ошибка |
| **Содержание исправления** | Краткое описание исправления, включая ключевые изменения кода |
| **Дата исправления** | Дата выпуска соответствующей версии, в формате `YYYY/MM/DD` |
| **Серьезность** | Определяется по классификации "Уровень серьезности" |
| **Тип** | Определяется по классификации "Тип ошибки", может быть комбинацией (например, `Адаптер / Маршрутизация`) |

| Поле | Описание | Сценарий применения |
|------|------|---------|

| **Тесты на повторное возникновение** | Пути к тестовым сценариям для проверки исправления | Добавляется, если написаны соответствующие тесты pytest |

## Классификация серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Критично | Приводит к краху процесса, потере/повреждению данных, полной недоступности основных функций, уязвимостей безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, неудачный горячий перезапуск |
| 🟡 | Средне | Функциональные сбои, но есть пути обхода, недоступность неосновных функций, случайные проблемы | Ошибки в определении состояния, повторное срабатывание, просроченный кэш, неточные сообщения об ошибках |
| 🟢 | Незначительно | Не влияет на основную функциональность, только проблемы качества кода или пользовательского опыта, потенциальные риски, не проявившиеся | Устаревшие API, мёртвый код, отсутствие предупреждающих логов |

## Исправленные ошибки

### [BUG-001] Дублированная регистрация обработчиков событий приводит к многократной обработке

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков одно и то же событие будет триггеряться несколько раз, что приведет к многократному выполнению команд и повторному выводу логов.

**Причина**: `BaseEventHandler` при регистрации обработчиков в событийной шине адаптера не содержит логики дедупликации, каждый декоратор вешает обработчик на шину, что приводит к многократному вызову при рассылке событий.

**Версии с ошибкой**: 2.2.0-dev.0 - 2.2.1-dev.0

**Исправленная версия**: 2.2.1-dev.0

**Содержание исправления**: Оптимизирован `BaseEventHandler`, чтобы убедиться, что каждый тип события регистрируется в шине адаптера только один раз, предотвращая многократный триггер.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера при инициализации с помощью `ep init`

**Проблема**: При использовании команды `ep init` для интерактивной инициализации при выборе конфигурации адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Версии с ошибкой**: 2.3.7 - 2.3.9-dev.1

**Исправленная версия**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средняя

**Тип**: CLI

---

### [BUG-003] После перезапуска события команды становятся неактивными

**Проблема**: Вызов `sdk.restart()` приводит к тому, что зарегистрированные с помощью `@command` команды не могут быть вызваны, что проявляется в том, что робот не отвечает после отправки команды.

**Причина**: `adapter.shutdown()` очищает событийную шину, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, из-за чего метод `_process_event` считает, что уже подключен к шине адаптера, и пропускает повторную регистрацию.

**Версии с ошибкой**: 2.2.x - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при `_clear_handlers()` отключение от шины, при следующем `register()` автоматическая повторная регистрация, адаптация для сценариев `shutdown/restart`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

### [BUG-004] Неочищенные обработчики событий жизненного цикла

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно триггерятся, что приводит к обработке одного и того же события несколько раз.

**Причина**: Словарь `lifecycle._handlers` никогда не очищался при `uninit()`, после перезапуска старые и новые обработчики существуют одновременно.

**Версии с ошибкой**: 2.3.0 - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в конце процесса очистки `Uninitializer` (после всех событий), синхронизация с `lifecycle._handlers`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средняя

**Тип**: Рантайм

### [BUG-005] `Event.is_friend_add/is_friend_delete` `detail_type` не соответствует стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Несоответствие с декораторами `on_friend_add`/`on_friend_remove` в `notice.py` приводит к тому, что соответствующие методы `is_friend_add()`/`is_friend_delete()` возвращают `False` при триггере обработчика.

**Причина**: В `wrapper.py` использованы нестандартные имена, а в `notice.py` — правильные имена стандарта OB12.

**Версии с ошибкой**: С момента реализации

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения проверки `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Система событий

### [BUG-006] `adapter.clear()` не очищает `_started_instances`, приводя к ошибке состояния после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен и вызывается `clear()`, `_started_instances` сохраняет висячие ссылки, что приводит к ошибкам состояния после перезапуска.

**Причина**: При введении `_started_instances` в 2.4.0-dev.1 не было очистки в `clear()`.

**Версии с ошибкой**: 2.4.0-dev.1 - 2.4.2-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-007] `command.wait_reply()` использует устаревший `asyncio.get_event_loop()`

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущих объектов и получения временной метки, этот метод устарел в Python 3.10+ и в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с методом `wait_for()` в `wrapper.py`, использующим `get_running_loop()`.

**Причина**: При разработке использовался старый API, а последующий `wait_for()` использовал правильный API, но не было возврата к исправлению старого кода.

**Версии с ошибкой**: 2.3.0-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Замена `asyncio.get_event_loop()` на `asyncio.get_running_loop()` в `command.py` в двух местах.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкая

**Тип**: Система событий

### [BUG-008] Событие отключения Bot при `adapter.shutdown()` триггерится повторно

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров `_update_bot_status()` при закрытии процесса повторно отправляет событие отключения Bot, что приводит к тому, что одни и те же Bot помечаются как отключенные несколько раз и триггерятся несколько раз события жизненного цикла `adapter.bot.offline`.

**Причина**: Введённая в 2.4.0-dev.1 система отслеживания состояния Bot не установила флаг "в процессе закрытия" во время `shutdown()`, поэтому `_update_bot_status()` не может отличить нормальное отключение от повторного отключения в процессе закрытия.

**Версии с ошибкой**: 2.4.0-dev.1 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.1

**Содержание исправления**: Добавление флага `_is_being_shutdown` в `AdapterManager`, установка в `True` в начале `shutdown()`, сброс в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторные отправки во время закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к `LazyModule` приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к лениво загружаемому `BaseModule` свойства модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает, что приводит к гонкам, когда свойство может быть не инициализировано.

**Причина**: `_ensure_initialized()` для `BaseModule` использует `loop.create_task(self._initialize())` и сразу возвращает, не обеспечивая завершение инициализации.

**Версии с ошибкой**: 2.4.0-dev.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация `BaseModule` заменена на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем вернуться. Сохраняется прозрачность прокси-объекта, пользователь не должен осознавать различия между синхронным и асинхронным.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Система загрузки

### [BUG-010] Многопоточная запись конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция чтения-изменения-записи `_flush_config()` не является атомарной, что может привести к потере части записей.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты с помощью файлового блокировщика, и `Timer` в `_schedule_write` может быть запущен несколько раз, вызывая перезапись.

**Версии с ошибкой**: 2.3.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавление механизма файловой блокировки (`_file_lock`), чтобы обеспечить атомарность операций с файлом
2. Использование временного файла для записи, затем атомарное переименование (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Критическая

**Тип**: Система конфигурации

### [BUG-011] На Windows Ctrl+C не может остановить программу

**Проблема**: При запуске `python main.py` на Windows, нажатие Ctrl+C не останавливает программу. Программа нормально запускается и выводит информацию о сервере маршрутизации, но Ctrl+C не реагирует, приходится убивать процесс через диспетчер задач. При запуске через `epsdk run` программа останавливается нормально, но `epsdk run` использует модель подпроцессов.

**Причина**: Внутри `serve()` сервера ASGI Hypercorn регистрирует свой обработчик сигнала `SIGINT`, перекрывающий стандартный механизм обработки `KeyboardInterrupt` Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()` внутренний процесс закрытия Hypercorn не срабатывает должным образом (он ожидает режима `worker_serve`), что приводит к тому, что сигнал Ctrl+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Версии с ошибкой**: 2.3.6 - 2.4.2

**Исправленная версия**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена сервера ASGI с Hypercorn на Uvicorn (`pyproject.toml` зависимость изменена)
2. Использование `uvicorn.Server._serve()` для запуска сервера, **обходя** контекст-менеджер `capture_signals()` для обработки сигналов
3. Использование `server.should_exit = True` для элегантной остановки, с отменой фоновой задачи при истечении таймера
4. Синхронное удаление модели запуска подпроцессов и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Критическая

**Тип**: CLI / Рантайм

### [BUG-022] Регрессия в `_resolve_account()` (отсутствие заполнения `_accounts_data`)

**Проблема**: После рефакторинга конфигурационной системы в 2.5.2, адаптеры с несколькими аккаунтами, объявленными с `AccountConfigClass`, при вызове методов отправки сообщения (например, `wait_reply`, `reply`) выдают ошибку `ValueError("Не объявлен AccountConfigClass, невозможно разрешить аккаунт")`. Даже если адаптер правильно настроен с информацией о нескольких аккаунтах, разрешение аккаунта по-прежнему не удаётся.

**Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторинг в `_ensure_accounts_exist()` (только генерация шаблона конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, этот атрибут всегда остаётся `None`, что приводит к тому, что `_resolve_account()` возвращает `(None, None)` заранее, и下游ные вызовы `_resolve_account()` (например, в `call_api`) получают `None`, что вызывает ошибку.

**Корневая цепочка**:
```
_load_accounts() удалён
  → __init__ больше не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        →下游ные вызовы _resolve_account() (например, call_api) получают None
          → вызывает ошибку
```

**Версии с ошибкой**: 2.5.2-dev.5 - 2.5.2

**Исправленная версия**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__`, после `self._ensure_accounts_exist()`, восстанавливается заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # восстановление заполнения, источник данных — актуальные accounts
```
Логика `_resolve_account()` остаётся без изменений, полностью обратная совместимость:
- Адаптеры, не объявляющие AccountConfigClass: _accounts_data остаётся None → возвращает (None, None)
- Адаптеры, объявляющие AccountConfigClass: _accounts_data заполняется → нормальное разрешение
- Адаптеры, переопределяющие _load_accounts или устанавливающие _accounts_data вручную: переопределяются после super().__init__(), с наивысшим приоритетом

**Дата исправления**: 2026/07/07

**Серьезность**: 🔴 Критическая

**Тип**: Адаптер / Конфигурационная система

### [BUG-030] Гонка в конфигурационном watcher приводит к тихой потере данных при отложенной записи

**Проблема**: Многие пользователи сообщают, что при использовании `config.setConfig(key, value)` (по умолчанию `immediate=False`) их конфигурация модуля не записывается в `config.toml`, в то время как конфигурация других модулей сохраняется. Проявляется так: конфигурация, записанная в процессе, теряется при следующем перезапуске, а конфигурация, сгенерированная в процессе запуска, сохраняется.

1. **Логическая ошибка**: `_watch_loop` при `_check_file_change()` возвращает `True` безусловно очищает `_dirty_keys`. 2. **Ошибки в потоках**: `_watch_loop` не использует `_lock` при операциях с `_write_timer`/`_dirty_keys`, что приводит к гонке с `setConfig` (захватывает `_dirty_keys`), `_schedule_write` (захватывает `_write_timer`).

**Корневая цепочка**:
```
Модуль A setConfig(immediate=True) → flush записывает файл, mtime изменяется
  → Пользовательский модуль setConfig(immediate=False) → входит в _dirty_keys, через 5 сек записывает
    → watcher цикл, _check_file_change обнаруживает разницу mtime, вызванную предыдущей записью
      → _dirty_keys.clear() → ключи пользователя теряются
        → при перезапуске конфигурация отсутствует
```

**Версии с ошибкой**: 2.6.0 - 2.7.0

**Исправленная версия**: 2.7.1

**Содержание исправления**:
1. Добавлено `_last_self_write_mtime` поле, `flush_config` после записи обновляет его; `check_file_change` при изменении mtime сначала сравнивает это значение, если совпадает — возвращает `False`
2. Весь `_watch_loop` захватывает `_lock`; при реальном внешнем изменении сохраняет `_dirty_keys` (логика слияния), при следующей flush объединяет с внешними данными (ключи с приоритетом), `_dirty_keys` не очищается
3. `getConfig`/`check_cache_validity` пути не затрагиваются (перезагрузка не очищает `_dirty_keys`)

**Версии с ошибкой**: 2.8.0-dev.1 - 2.8.0-dev.2
**Исправленная версия**: 2.8.0-dev.2

**Дата исправления**: 2026/09/09

**Сценарий воспроизведения**: ① `scope.set_module("testplat", blocked=["TestB"], persist=False)` → возвращается False; ② любой модуль выполняет `config.setConfig("HelpModule", {...})` → вызывает перестройку scope; ③ `scope.is_allowed("testplat", None, "TestB")` возвращает True (ожидается False).

### [BUG-036] При совместном использовании каталога конфигурации несколькими экземплярами запись конфигурации иногда терпит неудачу (ENOENT)

**Проблема**: В сценарии развертывания с Docker (несколько контейнеров монтируют один каталог конфигурации на хосте), логи периодически показывают две последовательные ошибки `Failed to write configuration file ... [Errno 2] No such file or directory: '...config.toml.tmp' -> '...config.toml'`. Эта запись конфигурации теряется (старая конфигурация сохраняется, без потери данных), функциональность не затронута, но предупреждения мешают диагностике, и записываемые параметры конфигурации должны ждать следующей записи, чтобы сохраниться.

**Причина**: Корневая цепочка: `_flush_config` / `setConfigTemplate` используют **фиксированное** имя временного файла `config.toml.tmp` для хранения новой информации, `write()` без `fsync` сразу переименовывает `rename()`; два экземпляра ErisPulse, совместно использующие один каталог конфигурации, могут B экземпляр `open("w")` **обрезать** временный файл, который A экземпляр записывает → A при переименовании получает уже украденный или обрезанный файл, вызывая `ENOENT` (как в логах). В отчётных случаях только предупреждение о неудачной записи (старая конфигурация сохраняется); если сценарий перекрёстного доступа более экстремальный, `rename` может выдать пустой или частично записанный `config.toml` (потенциально опасный сбой, в реальной среде не наблюдался). В одиночном экземпляре с ext4 также существует окно сбоя, когда `rename` выполняется до записи данных на диск (SIGKILL / отключение питания). `_file_lock` — это `threading.RLock` в пределах процесса, не ограничивает запись между процессами/контейнерами.

**Версии с ошибкой**: 2.2.0-dev.0 - 2.8.0

**Исправленная версия**: 2.8.1

**Содержание исправления**: Запись конфигурации объединяется в `_atomic_write_text()`: с помощью `mkstemp` в той же директории создаётся уникальный временный файл (устраняет конфликт фиксированных имён, в многоконтейнерном режиме превращается в last-writer-wins, не `ENOENT`); после записи `flush + fsync` гарантирует запись данных (устраняет окно "rename выполнен, данные не записаны"); `os.replace` атомарно заменяет цель (POSIX/Windows атомарны, в любой момент на диске либо полная старая, либо полная новая); дополнительно `fsync` каталога на POSIX. Три точки записи (`_flush_config`, `setConfigTemplate`, миграция корневого каталога) полностью переключены. Логика очистки исходных путей перестроена. Добавлено **обнаружение многоконтейнерного режима**: при запуске advisory lock (`flock` на POSIX / `msvcrt.locking` на Windows) на файл блокировки `.erispulse_config.lock`, если занят — выводится предупреждение на i18n (не блокирует запуск), блокировка автоматически освобождается ОС при завершении процесса, без "призрачных" блокировок.

**Дата исправления**: 2026/09/13

**Сценарий воспроизведения**: ① Два контейнера монтируют один каталог `config/` хоста и запускают ErisPulse; ② Любой экземпляр вызывает запись конфигурации (например, регистрация модуля с настройкой по умолчанию); ③ Наблюдайте, как в логах появляются ошибки `ENOENT`, эта запись теряется (старая конфигурация сохраняется).

**Связано**: Отчёт пользователей (1Panel ×2 контейнера)

**Тесты**: `tests/unit/test_unit_config_atomic_write.py` (полная запись содержимого/отсутствие временных файлов/сохранение файла при сбое/атомарная запись при одновременном доступе двух экземпляров/создание файла блокировки/предупреждение при многоконтейнерном режиме/атомарная запись при миграции)

**Серьезность**: 🟢 Легкая

**Тип**: Система конфигурации

### [BUG-037] Команды с пробелами в имени не могут быть запущены после регистрации

**Проблема**: При регистрации подкоманды с пробелами в имени (например, `@command("admin add")`) команда нормально регистрируется и появляется в списке помощи, но при отправке пользователем `/admin add` робот никогда не отвечает — ввод сопоставляется с командой `admin` + параметрами `["add"]`; если родительская команда не зарегистрирована, вообще нет ответа. Только при использовании точечного имени (например, `admin.reload`, как единый токен) можно избежать проблемы.

**Причина**: Корневая цепочка: `CommandHandler.__call__` сохраняет любое имя команды (с пробелами) в плоский словарь `self.commands` → при маршрутизации `_try_execute_command` сопоставляется только первый токен сообщения (`cmd_name = parts[0]`) → команды с несколькими токенами никогда не находятся в словаре. Логика регистрации и маршрутизации не согласована, и нет никаких предупреждений при регистрации (тихий сбой).

**Версии с ошибкой**: С момента появления системы команд - 2.8.0

**Исправленная версия**: 2.8.1

**Содержание исправления**: Маршрутизация изменена на **максимальное префиксное сопоставление**: начиная с самого длинного кандидата (`" ".join(parts[:n])`, где `n` ограничено максимальным числом токенов в зарегистрированных именах команд/别名, кэшируется `_max_name_tokens`), сопоставляется по убывающей, при совпадении выполняется с оставшимися токенами как параметрами, последующие области/ACL/перезапись/master/цепочка прав доступа автоматически применяются к полному имени команды. Сопутствующая семантика: при совместном существовании родительской и подкоманды не зарегистрированная подкоманда вводится как родительская команда (историческое поведение не меняется); если подкоманда не объявляет `permission`, наследует последнюю объявленную родительскую команду (защита родительской команды означает защиту всех её подкоманд); только при регистрации одиночного токена команды первый шаг совпадает, расходы на маршрутизацию остаются прежними. `unregister` / `unregister_by_owner` / полная очистка синхронно обновляют кэш числа токенов.

**Дата исправления**: 2026/09/13

**Сценарий воспроизведения**: ① Регистрация `@command("admin add")` в модуле; ② Отправка `/admin add x`; ③ До исправления нет ответа (или принимается как параметры для `/admin`), после исправления `admin add` срабатывает, `get_command_args()` возвращает `["x"]`.

**Тесты**: `tests/unit/test_unit_command_subcommand.py` (максимальное префиксное сопоставление/только подкоманда срабатывает/трехуровневая вложенность/регистрация с разным регистром/одиночные и множественные токены для别名/событие с полным именем/жизненный цикл с полным именем/наследование прав доступа/ACL glob с полным именем/master/отмена регистрации и пересчёт кэша)

**Серьезность**: 🟡 Средняя

**Тип**: Система событий
