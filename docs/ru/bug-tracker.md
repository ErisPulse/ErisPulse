# Трекер ошибок

Документация содержит список известных ошибок ErisPulse SDK и информацию о их исправлении, отсортированных по времени исправления.

> **Для читателя**
> Никакое программное обеспечение не бывает идеальным, даже самые внимательные разработчики могут оставлять небольшие ошибки. В этот трекер включены только те проблемы, которые реально влияют на работу. Те, которые слишком мелкие, чтобы даже считать их "незначительными", здесь не появятся. Список с пометкой "Критично" может показаться большим, но цель публикации — сделать отслеживание и откат более плавными, а не вызывать беспокойство: видимые, записанные и исправленные проблемы — это доказательство того, что проект становится лучше. Не стоит беспокоиться, увидев этот список, он служит инструментом для диагностики, а не источником страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ корневой причины, диапазон версий, в которых она возникла, номер версии, в которой была исправлена, краткое описание исправления, дата публикации, серьезность и тип. Рекомендуется перед обновлением проверять, охватывает ли "Версия, в которой возникла" текущую используемую версию.
> - Если нужно добавить новую запись об ошибке, вставьте её в соответствующее место, следуя формату полей и классификации серьезности/типа.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем. Старайтесь указать сообщения об ошибках или типичные сценарии |
| **Причина** | Анализ корневой причины, указывающий на конкретные дефекты кода (включая "цепочку корневых причин" для сложных сценариев) |
| **Версия, в которой возникла** | Влияющие версии, в формате `Версия, в которой возникла - Версия, в которой исправлена` (включая версии dev) |
| **Исправлено в версии** | Номер версии, в которой была исправлена ошибка |
| **Содержание исправления** | Краткое описание исправления, включая ключевые изменения кода |
| **Дата исправления** | Дата выпуска соответствующей версии, в формате `YYYY/MM/DD` |
| **Серьезность** | Определяется по классификации "Уровень серьезности" |
| **Тип** | Определяется по классификации "Тип ошибки", может быть комбинацией (например, `Адаптер / Маршрутизация`) |

### Необязательные поля

| Поле | Описание | Сценарий применения |
|------|------|---------|
| **Шаги воспроизведения** | Минимальный путь к воспроизведению ошибки | Рекомендуется для сложных или случайных ошибок |
| **Связанные** | Ссылки на связанные Issues / PR / Commit | Добавляется, если есть внешние обсуждения |
| **Тесты на повторное возникновение** | Пути к тестовым сценариям для проверки исправления | Добавляется, если написаны соответствующие тесты pytest |

## Классификация серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Критично | Приводит к краху процесса, потере/повреждению данных, полной недоступности основных функций, уязвимостей безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, неудачный горячий перезапуск |
| 🟡 | Средне | Функциональные сбои, но есть пути обхода, недоступность неосновных функций, случайные проблемы | Ошибки в определении состояния, повторное срабатывание, просроченный кэш, неточные сообщения об ошибках |
| 🟢 | Незначительно | Не влияет на основную функциональность, только проблемы качества кода или пользовательского опыта, потенциальные риски, не проявившиеся | Устаревшие API, мёртвый код, отсутствие предупреждающих логов |

## Исправленные ошибки

### [BUG-001] Повторная регистрация обработчика событий приводит к многократной обработке событий

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков одно и то же событие может быть запущено несколько раз, что приводит к многократному выполнению команд и повторному выводу логов.

**Причина**: `BaseEventHandler` регистрирует обработчик в событийной шине адаптера без логики дедупликации. Каждый декоратор добавляет обработчик в шину, что приводит к многократному вызову при отправке события.

**Версии влияния**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия исправления**: 2.2.1-dev.0

**Исправление**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался в адаптере только один раз, предотвращая повторную активацию.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-002] Некорректный тип пути конфигурации адаптера в команде инициализации

**Проблема**: При использовании команды `ep init` для интерактивной инициализации при выборе конфигурации адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Версии влияния**: 2.3.7 - 2.3.9-dev.1

**Версия исправления**: 2.3.9-dev.1

**Исправление**: Изменение типа параметра `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средняя

**Тип**: CLI

---

### [BUG-003] Команды не срабатывают после перезапуска

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные с помощью `@command`, не срабатывают, что проявляется в том, что бот не отвечает на отправленные команды.

**Причина**: `adapter.shutdown()` очищает событийную шину, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, из-за чего `_process_event` считает, что уже подключен к шине адаптера, и пропускает повторную регистрацию.

**Версии влияния**: 2.2.x - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Исправление**: Введение отслеживания состояния `_linked_to_adapter_bus`, после `shutdown()` и `clear()` следующая `register()` автоматически перерегистрируется, адаптировано для сценариев `shutdown`/`restart`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-004] Некорректная очистка обработчиков жизненного цикла

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно запускаются, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищается при `uninit()`, поэтому после перезапуска старые и новые обработчики существуют одновременно.

**Версии влияния**: 2.3.0 - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Исправление**: Очистка `lifecycle._handlers` в процессе очистки `Uninitializer` (после всех событий), чтобы избежать повторного запуска.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средняя

**Тип**: Время выполнения

### [BUG-005] Несоответствие `detail_type` для `Event.is_friend_add/is_friend_delete` и стандарта OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OB12 определяет `detail_type` как `"friend_increase"` и `"friend_decrease"`. Несоответствие с декораторами `on_friend_add`/`on_friend_remove` в `notice.py` приводит к тому, что соответствующие методы `is_friend_add()`/`is_friend_delete()` возвращают `False` при срабатывании обработчиков.

**Причина**: В `wrapper.py` используется нестандартное имя, в то время как `notice.py` использует правильные имена стандарта OB12.

**Версии влияния**: С момента внедрения

**Версия исправления**: 2.4.2-dev.1

**Исправление**: Изменение значения проверки в `is_friend_add()` с `"friend_add"` на `"friend_increase"`, в `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Система событий

### [BUG-006] `adapter.clear()` не очищает `_started_instances`, приводя к ошибкам состояния при перезапуске

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен и вызывается `clear()`, `_started_instances` сохраняет висячие ссылки, что приводит к ошибкам состояния при перезапуске.

**Причина**: При введении `_started_instances` в 2.4.0-dev.1 не было синхронной очистки в `clear()`.

**Версии влияния**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия исправления**: 2.4.2-dev.1

**Исправление**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-007] `command.wait_reply()` использует устаревший `asyncio.get_event_loop()`

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущего и получения временной метки, что устарело в Python 3.10+. В асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с методом `wait_for()` в `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, а последующий `wait_for()` использовал правильный API, но старый код не был исправлен.

**Версии влияния**: 2.3.0-dev.0

**Версия исправления**: 2.4.2-dev.1

**Исправление**: Замена `asyncio.get_event_loop()` на `asyncio.get_running_loop()` в `command.py`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкая

**Тип**: Система событий

### [BUG-008] Событие отключения бота при `shutdown()` повторно отправляется

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` повторно отправляет события отключения бота в процессе закрытия, что приводит к многократному отображению одного и того же бота как отключенного и многократному срабатыванию событий жизненного цикла `adapter.bot.offline`.

**Причина**: Система отслеживания состояния бота, введенная в 2.4.0-dev.1, не устанавливает флаг "в процессе закрытия" во время `shutdown()`, и `_update_bot_status()` не может различить нормальное отключение и повторное отключение в процессе закрытия.

**Версии влияния**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.1

**Исправление**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, который устанавливается в `True` в начале `shutdown()` и сбрасывается в конце; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к `LazyModule` приводит к незавершенному инициализации

**Проблема**: При синхронном доступе к атрибуту `LazyModule` модуль инициализируется асинхронно с помощью `loop.create_task()` без ожидания, что приводит к гонке состояний, когда атрибут может быть не инициализирован.

**Причина**: `_ensure_initialized()` использует `loop.create_task(self._initialize())` и немедленно возвращает, не обеспечив завершения инициализации.

**Версии влияния**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Исправление**: В синхронном контексте инициализация `BaseModule` заменена на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем вернуться. Сохраняется прозрачность прокси, пользователь не должен осознавать различий между синхронным и асинхронным контекстом.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Система загрузки

### [BUG-010] Многопоточная запись конфигурации приводит к потере данных

**Проблема**: При одновременном вызове `config.setConfig()` несколькими потоками из-за неатомарной операции чтения-записи `_flush_config()` может привести к потере данных.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты с помощью файлового блокировщика, и `Timer` может быть многократно запущен, вызывая перезапись.

**Версии влияния**: 2.3.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Исправление**:
1. Добавлена механизм файловой блокировки (`_file_lock`), чтобы обеспечить атомарность операций над файлом
2. Использование временного файла для записи, затем атомарное переименование с помощью `os.replace`/`os.rename`
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Критическая

**Тип**: Система конфигурации

### [BUG-011] Ctrl+C не может остановить программу в Windows

**Проблема**: При запуске `python main.py` в Windows нажатие Ctrl+C не останавливает программу. Программа запускается и выводит информацию о сервере маршрутизации, но Ctrl+C не реагирует, и программу можно остановить только через диспетчер задач. При запуске через `epsdk run` остановка работает, но `epsdk run` использует модель подпроцессов.

**Причина**: ASGI-сервер Hypercorn использует `signal.signal(SIGINT, handler)` для регистрации собственного обработчика SIGINT, который перехватывает стандартный механизм `KeyboardInterrupt` Python. При запуске Hypercorn как фоновой задачи с помощью `asyncio.create_task()` внутренний процесс остановки Hypercorn не срабатывает, так как ожидает режима `worker_serve`, что приводит к тому, что сигнал Ctrl+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Версии влияния**: 2.3.6 - 2.4.2

**Версия исправления**: 2.4.3-dev.0

**Исправление**:
1. Замена ASGI-сервера с Hypercorn на Uvicorn (`pyproject.toml` зависимость изменена)
2. Использование `uvicorn.Server._serve()` для запуска сервера, **пропуская** контекстный менеджер `capture_signals`
3. Использование `server.should_exit = True` для обеспечения корректной остановки, с отменой фоновой задачи при истечении таймаута
4. Синхронное удаление модели запуска подпроцессов и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Критическая

**Тип**: CLI / Время выполнения

### [BUG-022] Регрессия при解析е учетной записи (_accounts_data не заполнен)

**Проблема**: После рефакторинга системы конфигурации в 2.5.2, адаптеры с несколькими учетными записями, объявленные с `AccountConfigClass`, при вызове методов отправки сообщений, таких как `wait_reply`, `reply`, возникает ошибка `ValueError("Not declared AccountConfigClass, unable to resolve account")`. Даже если адаптер правильно настроен с информацией о нескольких учетных записях, разрешение учетной записи по-прежнему не удается.

**Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторинг в `_ensure_accounts_exist()` (только генерация шаблона конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда остается `None`, что приводит к тому, что `_resolve_account()` преждевременно возвращает `(None, None)`, и вызовы `_resolve_account` вниз по цепочке (например, `call_api`) получают `None`, что вызывает ошибку.

**Корневая цепочка**:
```
_load_accounts() удален
  → __init__ не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        → места, где используется _resolve_account (например, call_api), получают None
          → вызывает ошибку
```

**Версии влияния**: 2.5.2-dev.5 - 2.5.2

**Версия исправления**: 2.5.3

**Исправление**: В `BaseAdapter.__init__` после `self._ensure_accounts_exist()` восстановить заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # восстановить заполнение, источник данных - актуальные значения accounts
```
Логика `_resolve_account()` остается неизменной, полностью обратно совместима:
- Адаптеры, не объявляющие `AccountConfigClass`: `_accounts_data` остается `None` → возвращает `(None, None)`
- Адаптеры, объявляющие `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, перезаписывающие `_load_accounts` или вручную устанавливающие `_accounts_data`: в `super().__init__()` перезапись, с высоким приоритетом

**Дата исправления**: 2026/07/07

**Серьезность**: 🔴 Критическая

**Тип**: Адаптер / Система конфигурации

### [BUG-024] Запись больших числовых ID в storage вызывает OOM Kill

**Проблема**: Вызов `storage.set()` для записи вложенного ключа с большим числовым полем (например, ID группы QQ `871684833`) приводит к тому, что процесс уничтожается контейнером OOM Kill (код выхода -9), и сервис полностью крашится, не восстанавливаясь.

**Корневая цепочка**:
```

  → isdigit() ошибочно распознает как индекс массива
    → extend([None] * (871684833 - len(current) + 1))
      → Попытка выделить массив с миллиардами элементов
        → Исчерпание памяти → OOM Kill контейнера (код выхода -9)
```

**Версии влияния**: 2.5.1 - 2.5.5

**Версия исправления**: 2.5.5

### [BUG-030] Задержка записи конфигурации приводит к потере данных при нажатии Ctrl+C

**Проблема**: При использовании `config.setConfig(key, value)` (по умолчанию `immediate=False`) конфигурация не записывается в `config.toml`, а при следующем перезапуске теряется. Только при установке `immediate=True` (принудительная запись) данные сохраняются. Происходит так, что конфигурация, записанная во время выполнения, теряется после перезапуска, а конфигурация из шаблона сохраняется.

**Причина**: Две совпадающие ошибки:
1. **Логическая ошибка**: `_watch_loop` безусловно очищает `_dirty_keys` при `_check_file_change()` возвращающем `True`. Но `_check_file_change()` сравнивает только `!=` по mtime, и запись конфигурации самим фреймворком (`_flush_config`) также изменяет mtime — хотя `_flush_config` после записи обновляет `_config_mtime`, поток наблюдения может обнаружить разницу в mtime между записью файла и присвоением `_config_mtime` (а также на грубых файловых системах), ошибочно считая это "внешним изменением" и очищая все ожидающие ключи.
2. **Ошибки в потоке**: `_watch_loop` не захватывает `_lock` при операциях с `_write_timer`/`_dirty_keys`, что приводит к гонке данных с `setConfig` (захватывает `_dirty_keys`), `_schedule_write` (захватывает `_write_timer`).

**Корневая цепочка**:
```
Модуль A setConfig(immediate=True) → flush записывает файл, mtime меняется
  → Пользовательский модуль setConfig(immediate=False) → в `_dirty_keys`, через 5 секунд запись
    → Поток наблюдения, `_check_file_change` обнаруживает разницу mtime, вызванную записью самого фреймворка
      → `_dirty_keys.clear()` → ожидающие ключи пользователя теряются
        → После перезапуска конфигурация отсутствует
```

**Версии влияния**: 2.6.0 - 2.7.0

**Версия исправления**: 2.7.1

**Исправление**:
1. Добавлено `_last_self_write_mtime`, `config._flush_config` после записи обновляет это значение; `_check_file_change` при сравнении mtime сначала проверяет, совпадает ли с этим значением, и если да, возвращает `False`.
2. `_watch_loop` выполняет всю операцию с `_lock`; при обнаружении внешнего изменения сохраняет `_dirty_keys` (логика слияния), следующая запись объединяет с внешними данными (очищенные ключи не теряются).
3. `getConfig`/`_check_cache_validity` не затрагиваются (перезагрузка не очищает ожидаемые ключи).

### [BUG-036] Запись конфигурации в одновременном доступе к каталогу конфигурации приводит к потере данных (ENOENT)

**Проблема**: При развертывании в Docker (несколько контейнеров монтируют один каталог хоста конфигурации), логи периодически показывают две последовательные ошибки `Failed to write configuration file ... [Errno 2] No such file or directory: '...config.toml.tmp' -> '...config.toml'`. Эта запись конфигурации теряется (старая конфигурация сохраняется, без потери данных), но функциональность не нарушена, но предупреждения мешают отладке, и ожидающие записи должны ждать следующей записи, чтобы сохраниться.

**Причина**: Корневая цепочка: `_flush_config` / `setConfigTemplate` используют **фиксированное** имя временного файла `config.toml.tmp` для хранения новой информации, `write()` без `fsync` сразу переименовывает `rename()`; два экземпляра ErisPulse, разделяющие один каталог конфигурации, могут `B 实例 open("w")` **truncat** A 实例, который пишет временный файл → A rename пытается заменить уже взятый или обрезанный файл, вызывая ENOENT (как в логах). В отчетах случаев только логирование сбоя (старая конфигурация сохраняется); если перекрытие еще экстремальнее, rename может выдать пустой/полу-записанный `config.toml` (потенциальный риск, не проявился в реальных условиях). В одиночном режиме ext4 также существует "окно сбоя" между `rename` и `fsync` (SIGKILL / отключение питания). `_file_lock` — это `threading.RLock` внутри процесса, не ограничивает перекрытие между процессами/контейнерами.

**Версии влияния**: 2.2.0-dev.0 - 2.8.0

**Версия исправления**: 2.8.1

**Исправление**: Все записи конфигурации сводятся в `_atomic_write_text()`: с помощью `mkstemp` создается уникальный временный файл в том же каталоге (устраняет конфликт имен, в многоконтейнерном режиме сводится к последнему победителю, без ENOENT); запись завершается `flush + fsync` для принудительной записи данных (устраняет "окно сбоя, когда rename применился, но данные не записаны"); `os.replace` атомарно заменяет цель (POSIX/Windows атомарны, на диске всегда либо целая старая, либо целая новая); дополнительно `fsync` каталога на POSIX. Все три точки записи (`_flush_config`, `setConfigTemplate`, миграция корневой конфигурации) переключены; логика очистки путей изменена с уникальным именем временного файла. Добавлено **обнаружение нескольких экземпляров**: при запуске устанавливается блокировка на файл `.erispulse_config.lock` (POSIX `flock` / Windows `msvcrt.locking`), если занят — выводится предупреждение i18n (не блокирует запуск), блокировка автоматически освобождается при завершении процесса, без "зомби-блокировки".

**Дата исправления**: 2026/09/13

**Сценарий воспроизведения**: ① два контейнера монтируют один каталог `config/` и запускаются; ② любой из них вызывает запись конфигурации (например, регистрация модуля); ③ в логах появляются предупреждения об ошибке записи ENOENT, эта запись теряется (старая конфигурация сохраняется).

**Связано**: Отчеты пользователей (1Panel контейнер ×2)

**Тесты восстановления**: `tests/unit/test_unit_config_atomic_write.py` (полная запись содержимого / отсутствие временных файлов / отмена записи сохраняет файл / одновременная запись двух экземпляров всегда законна / создание файла блокировки / предупреждение о нескольких экземплярах / атомарная запись при миграции)

### [BUG-037] Команды с пробелами в имени не могут быть запущены

**Проблема**: При регистрации подкоманды с пробелом в имени (например, `@command("admin add")`) команда может быть зарегистрирована и отображена в списке помощи, но при отправке `/admin add` бот не реагирует — ввод распознается как `admin` + параметр `["add"]`; если родительская команда не зарегистрирована, реакции нет. Только при использовании точки в имени (например, `admin.reload`, как единый токен) можно избежать этой проблемы.

**Причина**: Команда сохраняется в `self.commands` как ключ со всеми пробелами, но при распределении `_try_execute_command` используется только первый токен (`cmd_name = parts[0]`) → команды с несколькими токенами как ключ не находятся. Регистрация и распределение используют разные предположения о пространстве имен команд, и нет предупреждений при регистрации (тихая ошибка).

**Версии влияния**: С момента появления системы команд - 2.8.0

**Версия исправления**: 2.8.1

**Исправление**: Механизм распределения изменен на **наибольшее соответствие префикса**: от самого длинного кандидата (`" ".join(parts[:n])`, n ограничено максимальным числом токенов в зарегистрированных командах/алиасах) постепенно уменьшается, если найдено соответствие, выполняется с оставшимися токенами в качестве параметров, последующие действия (домены/ACL/переопределения/master/цепочка прав) применяются к полному имени команды. Сопутствующая семантика: при наличии родительской и дочерней команды, если дочерняя команда не зарегистрирована, ввод попадает в родительскую команду (историческое поведение не меняется); если дочерняя команда не объявляет `permission`, наследует ближайшую родительскую команду с объявленным `permission` (защита родительской команды означает защиту всех ее дочерних команд); только при регистрации однотокеновой команды первый шаг находит соответствие, расход на распределение такой же, как и раньше. `unregister` / `unregister_by_owner` / полная очистка синхронно обновляют кэш числа токенов.

**Дата исправления**: 2026/09/13

**Сценарий воспроизведения**: ① модуль регистрирует `@command("admin add")`; ② отправляет `/admin add x`; ③ до исправления нет реакции (или принимается родительской командой как параметр), после исправления `admin add` срабатывает, а `get_command_args()` возвращает `["x"]`.

**Тесты восстановления**: `tests/unit/test_unit_command_subcommand.py` (наибольшее соответствие префикса / только срабатывает подкоманда / вложенные три уровня / большие и маленькие буквы в двух режимах / одиночные и множественные алиасы / событие полного имени / хуки жизненного цикла полного имени / наследование прав / ACL glob полного имени / master / отмена возврата и пересчет кэша)

**Дата исправления**: 2026/09/27

**Сценарий воспроизведения**: ① модуль выполняет `scope.set("bots.p.debug_mode", {"blocked": ["X"]}, persist=False)`; ② вызывается любая запись конфигурации (например, другой модуль вызывает `set_module`); ③ в `config/config.toml` появляется `debug_mode` (до исправления); ④ после выгрузки модуля (биндинг времени выполнения удален) при перезагрузке конфигурации `scope.get("bots.p.debug_mode")` все еще возвращает значение биндинга.

### [BUG-039] Несовместимость при одновременном использовании полной и точечной записи

**Проблема**: В окне задержки записи одновременно существуют полная запись (`setConfig("Mod", {...})`, например, `BaseModule.cfg` сохраняется) и точечная запись (`setConfig("Mod.key", v)`, например, теплый обмен / тестовый инструмент перезаписи); есть два варианта: вариант A (чтение) — `getConfig("Mod")` возвращает старую часть, не видя более поздней точечной перезаписи (точечный путь чтения работает нормально); вариант B (запись, более серьезный) — если точечная запись идет первой, а полная запись последней (инструмент тестирования вставляет перезапись → модуль `self.cfg = ...` сохраняет), flush применяет ключи по порядку вставки, и полная запись полностью заменяет эту часть, **точечная перезапись теряется в файле**. **Версия исправления**: 2.9.0-dev.1
