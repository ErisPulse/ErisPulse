# Трекер багов

В этом документе записаны известные ошибки и исправления в SDK ErisPulse.

## Исправленные ошибки

### [BUG-001] Ошибка типа в конфигурации адаптера команды init

**Проблема**: При интерактивной инициализации с помощью команды `ep init`, при выборе конфигурационного адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: В версии 2.3.7 при изменении пути к конфигурационному файлу типы параметров метода были不一致ыми. `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри использует оператор `/` объекта `Path` для конкатенации путей.

**Версии с ошибкой**: 2.3.7 - 2.3.9-dev.1

**Исправленная версия**: 2.3.9-dev.1

**Что исправлено**: Тип параметра метода `_configure_adapters_interactive_sync` изменен с `str` на `Path`, при вызове передается объект `Path`.

**Дата исправления**: 2026/03/23

### [BUG-002] Командные события перестают работать после перезагрузки

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные через `@command`, не могут быть вызваны; при отправке команды бот не реагирует.

**Причина**: После `adapter.shutdown()` очистки шины событий, состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, в результате метод `_process_event` считает, что он уже смонтирован к шине адаптера, и пропускает операцию повторного монтирования.

**Версии с ошибкой**: 2.2.x - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Что исправлено**: Введен отслеживание состояния `_linked_to_adapter_bus`; после разрыва соединения с шиной в `_clear_handlers()`, при следующем вызове `register()` происходит автоматическое повторное монтирование, что подходит для сценариев shutdown/restart.

**Дата исправления**: 2026/04/09

### [BUG-003] Обработчики событий жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно срабатывают, в результате одно и то же событие обрабатывается несколько раз.

**Причина**: Словарь `lifecycle._handlers` никогда не очищался при `uninit()`, после перезагрузки старые обработчики сосуществуют с новыми.

**Версии с ошибкой**: 2.3.0 - 2.4.0-dev.2

**Исправленная версия**: 2.4.0-dev.3

**Что исправлено**: В конце процесса очистки в `Uninitializer` (после передачи всех событий), очистить `lifecycle._handlers`.

**Дата исправления**: 2026/04/09

### [BUG-006] detail_type в Event.is_friend_add/is_friend_delete несовместим со стандартом OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, а `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Это несовместимо со значениями, используемыми декораторами `on_friend_add`/`on_friend_remove` в `notice.py`, что приводит к тому, что методы判断а `is_friend_add()`/`is_friend_delete()` возвращают `False` при срабатывании обработчиков, зарегистрированных через декораторы.

**Причина**: В `wrapper.py` использовались некорректные имена, а в `notice.py` — правильные имена в соответствии со стандартом OB12.

**Версии с ошибкой**: с момента реалтзации rq (Real implementation)

**Исправленная версия**: 2.4.2-dev.1

**Что исправлено**: Изменить значения сопоставления в `is_friend_add()` с `"friend_add"` на `"friend_increase"`, а в `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

### [BUG-007] adapter.clear() не очищает _started_instances, что приводит к некорректному состоянию после перезагрузки

**Причина**: При введении `_started_instances` в версии 2.4.0-dev.1 не была добавлена синхронная очистка в `clear()`.

**Версии с ошибкой**: 2.4.0-dev.1 - 2.4.2-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Что исправлено**: Добавить `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

### [BUG-008] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания future и получения временной метки; этот метод устарел в Python 3.10+ и в асинхронных контекстах следует использовать `asyncio.get_running_loop()`. Это несовместимо с методом `wait_for()` в том же файле `wrapper.py`, который использует `get_running_loop()`.

**Причина**: При разработке использовался старый API, а позже добавленный `wait_for()` использовал правильный API, но старый код не был исправлен заново.

**Версии с ошибкой**: 2.3.0-dev.0

**Исправленная версия**: 2.4.2-dev.1

**Что исправлено**: Заменить две встречающиеся в `command.py` конструкции `asyncio.get_event_loop()` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Дата исправления**: 2026/04/13

### [BUG-010] Синхронный доступ LazyModule к BaseModule приводит к незавершенному инициализации

**Проблема**: Когда пользователь обращается к свойству лениво загруженного BaseModule в синхронном контексте, модуль использует `loop.create_task()` для асинхронной инициализации, но не ждет её завершения, из-за чего доступ к свойству может произойти до завершения инициализации, что приводит к состоянию гонки.

**Причина**: `_ensure_initialized()` после использования `loop.create_task(self._initialize())` сразу возвращает управление, не гарантируя завершение инициализации.

**Версии с ошибкой**: 2.4.0-dev.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Что исправлено**: В синхронном контексте инициализация BaseModule изменена на использование `asyncio.run(self._initialize())`, чтобы гарантировать завершение инициализации перед возвратом. Прокси-объект остается прозрачным, пользователю не нужно различать синхронный и асинхронный режимы.

**Дата исправления**: 2026/04/21

### [BUG-011] Многопоточная запись в систему конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция чтения-модификации-записи в `_flush_config()` не является атомарной, что может привести к потере части записи.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты файловой блокировкой, а таймер `_schedule_write` может сработать несколько раз, приводя к перезаписи.

**Версии с ошибкой**: 2.3.0 - 2.4.2-dev.1

**Исправленная версия**: 2.4.2-dev.2

**Что исправлено**:
1. Добавлен механизм файловой блокировки (`_file_lock`) для обеспечения атомарности операций с файлом
2. Использование временного файла для записи, после чего атомарное переименование (`os.replace`/`os.rename`)
3. Улучшена логика отмены и повторного расписания таймера `_schedule_write`

**Дата исправления**: 2026/04/21

### [BUG-014] CTRL+C не останавливает программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие CTRL+C не может прервать программу. Программа корректно запускается и выводит информацию о сервере маршрутизации, после чего CTRL+C совершенно без ответа, остановить можно только через диспетчер задач принудительно. При запуске через `epsdk run` остановить можно нормально — но `epsdk run` работает через модель дочернего процесса.

**Причина**: Внутренняя функция `serve()` сервера ASGI Hypercorn регистрирует свой собственный обработчик SIGINT через `signal.signal(SIGINT, handler)`, переопределяя механизм обработки `KeyboardInterrupt` по умолчанию в Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()`, внутренний процесс выключения Hypercorn не может запуститься нормально (так как он ожидает режим `worker_serve`), из-за чего сигнал CTRL+C проглатывается Hypercorn, но не вызывает никаких действий по очистке.

**Версии с ошибкой**: [2.3.6 - 2.4.2]

**Исправленная версия**: 2.4.3-dev.0

**Что исправлено**:
1. Сервер ASGI переключен с Hypercorn на Uvicorn (изменение зависимости в `pyproject.toml`)
2. Сервер запускается напрямую через `uvicorn.Server._serve()`, **обходя** контекстный менеджер обработки сигналов `capture_signals()`
3. Гладкое завершение работы через `server.should_exit = True`, при превышении таймаута — отмена фоновой задачи
4. Синхронно удалена модель запуска через дочерний процесс и модуль очистки `runtime/cleanup.py` (механизм очистки дочерних процессов больше не требуется)

**Дата исправления**: 2026/04/28

### [BUG-015] Ошибка логики упорядочивания в стратегии загрузки модулей

**Проблема**: `ModuleLoadStrategy` предоставляет поле `priority` для объявления приоритета инициализации модулей, но в реализации стратегии допущена ошибка, в результате модули не инициализируются в ожидаемом порядке по приоритету, а загружаются в порядке по умолчанию из `entry_points()`. Когда между модулями существуют зависимости при загрузке, невозможно гарантировать правильный порядок инициализации через `priority`.

**Причина**: В реализации стратегии допущена ошибка в логике сортировки, и `initialize_modules()` не использует `priority` для сортировки списка модулей.

**Версии с ошибкой**: 2.3.4 - 2.4.5-dev.2

**Исправленная версия**: 2.4.5-dev.3

**Что исправлено**: Перед проходом в `initialize_modules()` отсортировать список модулей по убыванию `priority`. Модули с одинаковым `priority` сохраняют свой относительный порядок (стабильная сортировка).

**Дата исправления**: 2026/05/15

### [BUG-016] Возврат None адаптером middleware приводит к потере данных событий

**Проблема**: При выполнении цепочки middleware OneBot12 в `adapter.emit()`, если какой-либо middleware возвращает `None` (например, забыт `return data`), `processed_data` для всех последующих middleware и обработчиков событий становится `None`, что приводит к полному отключению обработки событий.

**Причина**: В реализации цепочки middleware `processed_data = await middleware(processed_data)` не проверяется, что возвращаемое значение не равно `None`, и происходит прямое перезапись результата предыдущего шага.

**Версии с ошибкой**: unknown - 2.4.5-dev.3

**Исправленная версия**: 2.4.5-dev.4

**Что исправлено**: Игнорировать возврат `None` от middleware, сохраняя исходные данные и продолжая передачу, а также выводить предупреждение (warning) в лог.

**Дата исправления**: 2026/05/15

### [BUG-017] Путь к конфигурационному файлу зависит от рабочего каталога

**Проблема**: Путь к конфигурационному файлу в `ConfigManager` по умолчанию является относительным `"config/config.toml"` и разрешается во время выполнения через `os.getcwd()`. Если рабочий каталог изменяется во время выполнения (например, через `os.chdir()`), операции чтения и записи конфигурационного файла будут указывать на неверное место, что приведет к потере конфигурации или чтению старых данных.

**Причина**: В `__init__` напрямую хранится относительный путь, и он не разрешается в абсолютный при инициализации.

**Версии с ошибкой**: 2.3.7 - 2.4.5-dev.3

**Исправленная версия**: 2.4.5-dev.4

**Что исправлено**: В `ConfigManager.__init__()`, если переданный путь относительный, автоматически преобразовать его в абсолютный через `os.path.abspath()`.

**Дата исправления**: 2026/05/15

### [BUG-018] Subprocess mode `ep run <script>` не находит подпакет в каталоге скрипта

**Проблема**: При запуске скрипта в режиме без перезагрузки (без `--reload`) с помощью `ep r .\main.py`, если у скрипта есть относительные импорты (например, `from qg import ...`), возникает ошибка `No module named 'qg'`. А режим `--reload` работает нормально.

**Причина**: Режим без перезагрузки напрямую вызывает `runpy.run_path()` для выполнения скрипта, эта функция не добавляет автоматически каталог скрипта в `sys.path`. Режим `--reload` выполняет скрипт через дочерний процесс `subprocess.Popen`, который автоматически наследует текущий рабочий каталог, поэтому `sys.path[0]` равен каталогу скрипта, и всё работает.

**Версии с ошибкой**: 2.5.0 - 2.5.2-dev.0

**Исправленная версия**: 2.5.2-dev.0

**Что исправлено**: Перед вызовом `runpy.run_path()` вручную вставить каталог, где находится скрипт, в `sys.path[0]`.

**Дата исправления**: 2026/06/27

### [BUG-019] SQL query builder отклоняет легальные маски и выражения столбцов

**Проблема**: В `_build_select_sql()` `SQLiteQueryBuilder` вызывает `_validate_identifier()` для всех столбцов SELECT. Эта функция использует строгий белый список регулярных выражений `^[a-zA-Z_][a-zA-Z0-9_]*$`, из-за чего легальный синтаксис SQL ошибочно распознается как небезопасное имя столбца:

- `SELECT *` — `*` — это стандартный маскировщик SQL
- `SELECT COUNT(*)` — агрегатная функция
- `SELECT users.name` — ограниченное имя столбца
- `SELECT col AS alias` — псевдоним столбца

При этом `Select("*")` используется модулями вроде Cron, что приводит к тому, что выполнение `on_load` модуля не проходит, и модуль не может быть загружен.

**Причина**: В версии 2.4.6 был усилен анализ защищенности от SQL-инъекций, введена валидация белым списком `_validate_identifier()`. Эта валидация применяется ко всем именам столбцов, но не различает считывающий конец (SELECT/ORDER BY) и записывающий конец (INSERT/UPDATE). В столбцах SELECT допустимы сложные SQL-выражения, они не должны быть ограничены простым белым списком идентификаторов.

**Версии с ошибкой**: 2.4.6 - 2.5.2-dev.1

**Исправленная версия**: 2.5.2-dev.2

**Что исправлено**: Изменить валидацию столбцов SELECT/ORDER BY с белого списка на черный список:
1. Добавлена новая функция `_validate_select_column()`, которая блокирует только опасные символы SQL-инъекций (`;` `'` `"` `--` `/*` `*/` `\x00` символ новой строки)
2. Разрешены любые легальные SQL-выражения столбцов (например, `*`, `table.*`, `table.column`, `COUNT(*)`, `col AS alias` и т.д.)
3. Имена столбцов для INSERT/UPDATE продолжают использовать строгую валидацию белым списком (только простые идентификаторы)

**Дата исправления**: 2026/06/29
