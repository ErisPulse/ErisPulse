# Трекер ошибок

Документация содержит информацию о известных ошибках ErisPulse SDK и их исправлениях, отсортированных по времени исправления.

> **Для читателя**
> Ни одно программное обеспечение не бывает идеальным с самого начала, даже самые внимательные разработчики могут оставить небольшие ошибки. В этот трекер включены только те проблемы, которые реально влияют на работу системы — те, что слишком незначительны, чтобы даже оценивать как "легкие", здесь не появятся. Хотя в списке может показаться много пунктов с уровнем "серьезный", цель публичной записи этих ошибок — сделать процесс отладки и отслеживания проще, а не вызывать беспокойство: видимость, запись и исправление проблем — это доказательство того, что проект постоянно улучшается. Не стоит беспокоиться, увидев этот список, он служит инструментом для диагностики, а не источником страха.

> **Как читать и правила поддержки**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ коренной причины, диапазон версий, влияющих на работу, и решение. Рекомендуется перед обновлением проверять, охватывает ли "Версия, на которую влияет" текущую используемую версию.
> - Если нужно добавить новую запись об ошибке, добавьте содержимое в соответствующее место, следуя спецификациям полей и классификации серьезности/типа, описанным ниже.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем. Постарайтесь указать сообщение об ошибке или типичную сцену |
| **Причина** | Анализ коренной причины, указывающий на конкретные дефекты кода (с визуальной "цепочкой причин" для сложных сценариев) |
| **Версии, на которые влияет** | Диапазон версий, затронутых ошибкой, в формате `Версия введения - Версия исправления` (включая обе версии dev) |
| **Версия исправления** | Конкретный номер версии, в которой была исправлена ошибка |
| **Содержание исправления** | Краткое описание решения, включая ключевые изменения кода |
| **Дата исправления** | Дата публикации соответствующей версии исправления, в формате `YYYY/MM/DD` |
| **Серьезность** | Уровень серьезности, указанный по следующей "шкале серьезности" |
| **Тип** | Тип ошибки, указанный по следующей "классификации типов", может быть комбинированным (например, `Адаптер / Роутер`) |

### Необязательные поля

| Поле | Описание | Применение |
|------|------|---------|
| **Шаги воспроизведения** | Минимальный путь для воспроизведения ошибки | Рекомендуется добавить для сложных или случайных ошибок |
| **Связанные** | Ссылки на связанные Issue / PR / Commit | Добавляются, если есть внешние обсуждения |
| **Тесты на регресс** | Пути к тестовым случаям для проверки исправления и предотвращения повторного возникновения | Добавляются, если соответствующие тесты pytest написаны |

## Шкала серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Серьезный | Приводит к сбою процесса, потере/повреждению данных, полной недоступности основных функций, уязвимостям безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Нарушения функциональности, но есть пути обхода, не основные функции не работают, случайные проблемы | Неправильное определение состояния, повторное срабатывание, истечение кэша, неточные сообщения об ошибках |
| 🟢 | Легкий | Не влияет на основные функции, только проблемы качества кода или пользовательского опыта, потенциальные риски не проявляются | Устаревшие API, мертвый код, отсутствие предупреждающих логов |

## Исправленные ошибки

### [BUG-001] Повторная регистрация обработчиков событий приводит к многократному обработанию событий

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков одно и то же событие будет запускаться несколько раз, что приведет к многократному выполнению команд и повторному выводу логов.

**Причина**: `BaseEventHandler` регистрирует обработчики в событийном бусе адаптера без логики удаления дубликатов, каждый декоратор добавляет обработчик в бус, что приводит к многократному вызову при распределении событий.

**Версии, на которые влияет**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия исправления**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался только один раз, предотвращая повторное срабатывание.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Серьезный

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера в команде Init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации при выборе конфигурации адаптера возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: В версии 2.3.7 при изменении пути конфигурационного файла метод `_configure_adapters_interactive_sync` принимает параметры типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Версии, на которые влияет**: 2.3.7 - 2.3.9-dev.1

**Версия исправления**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средний

**Тип**: CLI

---

### [BUG-003] После перезапуска команды события не активируются

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные с помощью `@command`, не могут быть активированы, что проявляется в отсутствии реакции бота на отправленные команды.

**Причина**: `adapter.shutdown()` очищает событийный бус, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, поэтому метод `_process_event` считает, что уже подключен к бусу адаптера, и пропускает повторную регистрацию.

**Версии, на которые влияет**: 2.2.x - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при `clear_handlers()` разрыв связи с бусом, при следующем `register()` автоматически перерегистрируется, адаптируется к сценариям shutdown/restart.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Серьезный

**Тип**: Система событий

### [BUG-004] Обработчики событий жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно срабатывают, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищается при `uninit()`, после перезапуска старые и новые обработчики существуют одновременно.

**Версии, на которые влияет**: 2.3.0 - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в конце процесса очистки `Uninitializer` (после всех событий), чтобы очистить старые обработчики.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средний

**Тип**: Рантайм

### [BUG-005] Event.is_friend_add/is_friend_delete detail_type не соответствует стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Несоответствие с использованными в `notice.py` `on_friend_add`/`on_friend_remove` декораторами приводит к тому, что при регистрации обработчиков через декораторы методы `is_friend_add()`/`is_friend_delete()` возвращают `False`.

**Причина**: В `wrapper.py` используется нестандартное наименование, а в `notice.py` — правильные наименования стандарта OB12.

**Версии, на которые влияет**: С момента реализации

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения соответствия `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, приводя к некорректному состоянию после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`、`_adapter_info`、обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен и вызывается `clear()`, `_started_instances` сохраняет висячие ссылки, что приводит к ошибочным состояниям после перезапуска.

**Причина**: При введении `_started_instances` в 2.4.0-dev.1 не было синхронной очистки в `clear()`.

**Версии, на которые влияет**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущего и получения временной метки, этот метод устарел в Python 3.10+ и в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с `get_running_loop()` в `wrapper.py` методом `wait_for()`.

**Причина**: При разработке использовался старый API, а новый `wait_for()` использовал правильный API, но старый код не был обновлен.

**Версии, на которые влияет**: 2.3.0-dev.0

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Замена двух вызовов `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкий

**Тип**: Система событий

### [BUG-008] Событие отключения бота при shutdown повторно отправляется

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров `_update_bot_status()` в процессе закрытия повторно отправляет события отключения бота, что приводит к многократному отмечанию одного и того же списка ботов как отключенных и многократному срабатыванию события жизненного цикла `adapter.bot.offline`.

**Причина**: Система отслеживания состояния ботов, введенная в 2.4.0-dev.1, не устанавливает флаг "в процессе закрытия" во время `shutdown()`, `_update_bot_status()` не может отличить нормальное отключение от каскадного отключения в процессе закрытия.

**Версии, на которые влияет**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Добавление флага `_is_being_shutdown` в `AdapterManager`, установка в `True` при начале `shutdown()` и сброс при завершении; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к BaseModule в LazyModule приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к атрибуту лениво загружаемого BaseModule модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает, что может привести к гонке состояний при не завершённой инициализации.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и сразу возвращает, не обеспечив завершения инициализации.

**Версии, на которые влияет**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule заменяется на `asyncio.run(self._initialize())`, чтобы убедиться, что инициализация завершена, прежде чем возвращать. Сохраняется прозрачность прокси, пользователь не должен знать о различии между синхронным и асинхронным контекстом.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Загрузчик

### [BUG-010] Многопоточная запись в систему конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция `_flush_config()` чтение-изменение-запись не является атомарной, что может привести к потере части записей.

**Причина**: `_flush_config()` использует `RLock`, но между чтением и записью файла нет защиты с помощью файлового блокировщика, и `Timer` `_schedule_write` может быть запущен несколько раз, что приводит к перезаписи.

**Версии, на которые влияет**: 2.3.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавление механизма файловой блокировки (`_file_lock`) для обеспечения атомарности операций с файлом
2. Использование временного файла для записи, а затем атомарное переименование (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Серьезный

**Тип**: Система конфигурации

### [BUG-011] CTRL+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие CTRL+C не останавливает программу. Программа нормально запускается и выводит информацию о сервере маршрутизации, но CTRL+C не вызывает никакой реакции, процесс можно остановить только через диспетчер задач. При запуске через `epsdk run` программа останавливается корректно, но `epsdk run` работает через модель подпроцессов.

**Причина**: ASGI-сервер Hypercorn в функции `serve()` внутри регистрирует свой обработчик SIGINT, перекрывая стандартный механизм обработки KeyboardInterrupt Python. При запуске Hypercorn как фоновая задача с помощью `asyncio.create_task()` внутренний процесс завершения Hypercorn не может быть нормально запущен (так как ожидается режим `worker_serve`), что приводит к тому, что сигнал CTRL+C поглощается Hypercorn, но не вызывает никаких действий по очистке.

**Версии, на которые влияет**: 2.3.6 - 2.4.2

**Версия исправления**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена ASGI-сервера Hypercorn на Uvicorn (`pyproject.toml` зависимость)
2. Использование `uvicorn.Server._serve()` для прямого запуска сервера, **обходя** контекстный менеджер `capture_signals()` для обработки сигналов
3. Использование `server.should_exit = True` для обеспечения корректной остановки, с отменой фоновой задачи при истечении таймера
4. Синхронное удаление модели подпроцессов и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Серьезный

**Тип**: CLI / Рантайм

**Проблема**: После рефакторинга системы конфигурации в 2.5.2, адаптер с множеством аккаунтов, объявивший `AccountConfigClass`, при вызове методов, требующих отправки сообщений, таких как `wait_reply`、`reply`, возникает ошибка `ValueError("не объявлен AccountConfigClass, невозможно解析 аккаунт")`. **Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был рефакторинг в `_ensure_accounts_exist()` (только генерирует шаблон конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`.
```
_load_accounts() удалён

    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
```

**Версия исправления**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `_ensure_accounts_exist()` восстановите заполнение `_accounts_data`:

```python
if self.AccountConfigClass is not None:

```
Логика `_resolve_account()` остается без изменений, полностью обратная совместимость:
- Адаптеры без объявления `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращается `(None, None)`
- Адаптеры с объявленным `AccountConfigClass`: `_accounts_data` заполняется → нормальное解析
- Адаптеры с перезаписью `_load_accounts` или ручным установкой `_accounts_data`: в `super().__init__()` перезапись, наивысший приоритет

### [BUG-025] on_config_update callback не поддерживается ядром

**Проблема**: `on_config_update(old, new)` callback определён в базовых классах (`BaseModule` / `BaseAdapter`), но ядро не подписывается на события изменения конфигурации. На практике: при изменении конфигурации через панель управления это срабатывает, но при ручном редактировании `config.toml` или вызове `setConfig()` `on_config_update` не срабатывает.

**Причина**: `ConfigManager` при изменении конфигурации издаёт события `config.set` / `config.updated` жизненного цикла, но отсутствует логика подписки этих событий на методы `on_config_update` компонентов.

**Коренная цепочка**:
```
Ядро не подписывается на config.set / config.updated
  → События изменения конфигурации не пересылаются
    → on_config_update не вызывается
      → Ручное редактирование файла / вызов setConfig() не запускает hot-update callback
```

**Версии, на которые влияет**: Все версии

**Версия исправления**: 2.6.2

**Содержание исправления**: `ModuleManager` / `AdapterManager` подписываются на события `config.set` (перекрывает путь кода `setConfig()`) и `config.updated` (перекрывает путь ручного редактирования файла), после сопоставления по префиксу конфигурации вызываются соответствующие компоненты `on_config_update`, передаются типобезопасные объекты конфигурации. Также исправлена проблема `_flush_config()` при записи файла без синхронизации `_config_mtime`, чтобы задача прослушивания файлов не ошибочно считала внешнее изменение и повторно запускала `config.updated`.

**Совместимость**: Hot-update конфигурации теперь поддерживается ядром. Логика, ранее выполнявшаяся панелью управления, удалена, после обновления фреймворка необходимо обновить панель управления, иначе будет дублирование вызовов (ядро + панель). Подпись и семантика метода `on_config_update` остаются неизменными, подклассам не нужно изменять код.

**Дата исправления**: 2026/07/23

**Серьезность**: 🟡 Средний

**Тип**: Система конфигурации

### [BUG-026] Ошибка определения цели reply в событиях notice/request

**Проблема**: При вызове `event.reply()` в событии уведомления о группе (например, добавление участника `group_member_increase`), сообщение отправляется в личную переписку пользователя, который вызвал событие, а не в группу, где произошло событие. Аналогично для событий уведомления о друзьях, цель ответа может быть неправильной.

**Причина**: `infer_receive_type()` возвращает `detail_type` как тип сессии. Для событий сообщений это правильно (значения `detail_type` `private`/`group` — это типы сессии), но для событий уведомлений/запросов `detail_type` — это семантические подтипы (например, `group_member_increase`、`friend_increase`), а не типы сессии. Последующие `convert_to_send_type()` и `get_id_field()` в картах отображения не находят это значение, возвращая по умолчанию `"user"` / `"user_id"`, что приводит к неправильной цели ответа.

**Коренная цепочка**:
```
detail_type уведомления = "group_member_increase"
  → infer_receive_type() возвращает "group_member_increase"
    → convert_to_send_type("group_member_increase") не в карте → возвращается "user"
    → get_id_field("group_member_increase") не в карте → возвращается "user_id"
      → target_id = event["user_id"]  ← Новый участник в личной переписке (а не в группе)
```

**Версии, на которые влияет**: Все версии

**Версия исправления**: 2.7.0-dev.3

**Содержание исправления**: `infer_receive_type()` добавляет проверку — `detail_type` возвращается как есть только если это известный тип сессии (стандартный или пользовательский тип); в противном случае по полю ID (`group_id` / `channel_id` / `user_id` и т.д.) определяется правильный тип сессии.

**Тесты на регресс**: `tests/unit/test_unit_session_type.py` → `TestNoticeRequestTypeInference` (10 тестов)

**Дата исправления**: 2026/07/29

### [BUG-027] Задача очистки ограничения частоты маршрута использует фиксированное окно, что делает правила ограничения для длинных окон недействительными

**Проблема**: При настройке ограничения частоты маршрута на длинное окно (например, `100/hour`、`{"requests": 100, "window": 3600}`), ограничение частоты не работает — фактически проявляется как `100/minute` (в час можно пропустить до ~6000 запросов), что полностью не обеспечивает защиту на уровне часа.

**Причина**: `_apply_rate_limit` получает фактическое `window` для маршрута (максимум 3600 секунд), проверка на каждый запрос действительно использует это окно; но фоновая задача очистки `_cleanup_expired_rate_limits` использует фиксированную константу `DEFAULT_RATE_LIMIT_WINDOW_SECS` (60 секунд) в качестве общего порога для всех маршрутов. Таким образом, `100/hour` маршруты с временными метками до 60 секунд удаляются задачей очистки, в часовом окне никогда не накапливается около 100 записей, ограничение частоты сильно ослабляется.

**Коренная цепочка**:
```
_apply_rate_limit анализирует window=3600 (100/hour)
  → Проверка на каждый запрос сохраняет временные метки в течение 3600 секунд (правильно)
  → Но _cleanup_expired_rate_limits использует фиксированный max_window=60 секунд для очистки
    → Временные метки до 60 секунд удаляются
      → В часовом окне остаются только записи за последние 1 минуту
        → 100/hour фактически ухудшается до ~100/minute (разрешение примерно в 60 раз)
```

**Версии, на которые влияет**: 2.6.0-dev.0 - 2.7.0-dev.4

**Версия исправления**: 2.7.0-dev.5

**Содержание исправления**: Добавлен `_rate_limit_windows: dict[str, int]` для записи каждого маршрута по store key; при первом создании записи `_apply_rate_limit` записывает окно; `_cleanup_expired_rate_limits` изменен на очистку по собственному окну каждого ключа (в случае отсутствия возвращается значение по умолчанию); при удалении записи и `stop()` синхронно обновляются оба словаря.

### [BUG-029] Задача прослушивания конфигурации транслирует незавершённый TOML и молча поглощает исключения

**Проблема**: Когда пользователь редактирует `config.toml` и сохраняет его на полпути (генерируя временный синтаксический сбой), фоновый поток прослушивания обнаруживает изменение mtime, перезагружает конфигурацию, но при сбое загрузки по-прежнему извещает `config.updated` пустой конфигурацией `{}`, что заставляет обработчики адаптеров/модулей `on_config_update` получать пустую конфигурацию и ошибочно полагать, что все параметры конфигурации были сброшены, возвращаясь к значениям по умолчанию. Кроме того, цикл прослушивания с `except Exception: pass` молча поглощает все исключения, что делает невозможным диагностику сбоев прослушивателя.

**Причина**: Два дефекта в совокупности:
1. `_load_config` при синтаксической ошибке/ошибке прав доступа стирает `self._cache` в `{}`, но фоновый поток прослушивания `_watch_loop` и путь истечения кэша `_check_cache_validity` после вызова `_load_config()` безусловно выполняют `_emit_config_updated()`, транслируя "пустой кэш, полученный из сбоя загрузки" как реальное изменение.
2. `except Exception` в `_watch_loop` не записывает никаких журналов.

**Коренная цепочка**:
```
Пользователь сохраняет на полпути → синтаксическая ошибка TOML
  → _load_config() стирает _cache = {}
    → _watch_loop безусловно _emit_config_updated(new_config={})
      → адаптер/модуль on_config_update получает пустую конфигурацию
        → ошибочно полагает, что конфигурация была сброшена, возвращается к значениям по умолчанию
```

**Версии, на которые влияет**: 2.6.2-dev.1 - 2.7.0-dev.4

**Версия исправления**: 2.7.0-dev.5

**Содержание исправления**:
1. `_load_config` изменен на возврат `bool`; при синтаксической ошибке/ошибке прав доступа и других ошибках **сохраняется** предыдущий действительный кэш (не стирается в `{}`), только записываются диагностические журналы и возвращается `False`
2. `_watch_loop` и `_check_cache_validity` извещают `config.updated` только если `_load_config()` возвращает `True`
3. `except Exception` в `_watch_loop` изменен на запись уровня warning (добавлен ключ i18n `core.config.watcher_error`, синхронно на пяти языках)

**Дата исправления**: 2026/07/31

**Тесты на регресс**: `tests/unit/test_unit_config.py` → `test_malformed_toml_preserves_last_valid_cache`、`test_permission_denied_logs_clear_message` (обновлено для проверки сохранения кэша и возврата False)

**Серьезность**: 🟡 Средний
