# Трекер ошибок

Данная документация содержит список известных ошибок ErisPulse SDK и информацию о их исправлении, отсортированную по времени исправления.

> **Обращение к читателю**
> Никакое программное обеспечение не бывает идеальным с самого начала, и даже самые внимательные разработчики могут допустить небольшие ошибки. В данный трекер включены только те проблемы, которые реально влияют на работу системы — слишком мелкие недочёты, не достигающие даже уровня «незначительных», здесь отсутствуют. Хотя в списке есть несколько пунктов с уровнем «критичности», но цель публикации этих ошибок — обеспечить более гладкое выявление и отслеживание проблем, а не создавать беспокойство: возможность видеть, записывать и исправлять ошибки — это доказательство постоянного улучшения проекта. Не стоит беспокоиться, увидев этот список: он служит инструментом для отладки, а не источником страха.

> **Как читать и правила ведения**
> - Каждая запись об ошибке содержит структурированные поля: описание проблемы, анализ причины, диапазон версий, подверженных влиянию, и решение. Рекомендуется перед обновлением проверять, охватывает ли «диапазон версий» используемую вами версию.
> - Если вы хотите добавить новую запись об ошибке, пожалуйста, добавьте её в соответствующее место, соблюдая формат полей и классификацию по уровню серьёзности и типу, описанные ниже.

## Описание полей

### Обязательные поля

| Поле | Описание |
|------|----------|
| **Проблема** | Внешнее проявление ошибки, наблюдаемое пользователем аномальное поведение. Следует указывать сообщения об ошибках или типичные сценарии |
| **Причина** | Анализ корневой причины, указывающий на конкретный дефект в коде (включая диаграмму "цепочки корневых причин" для сложных сценариев) |
| **Версии, подверженные влиянию** | Интервал версий, подверженных влиянию, формат `версия введения - версия исправления` (включая обе версии dev) |
| **Исправленная версия** | Конкретный номер версии, в котором была исправлена ошибка |
| **Содержание исправления** | Краткое описание решения, включая ключевые изменения в коде |
| **Дата исправления** | Дата публикации соответствующей версии исправления, в формате `YYYY/MM/DD` |
| **Серьезность** | Указывается согласно "Разделению на уровни серьезности" |
| **Тип** | Указывается согласно "Классификации типов", может быть комбинированным (например `адаптер / маршрутизация`) |

### Необязательные поля

| Поле | Описание | Сценарий применения |
|------|----------|---------------------|
| **Шаги воспроизведения** | Минимальный путь для воспроизведения ошибки | Рекомендуется добавлять для сложных ошибок и ошибок с редким проявлением |
| **Связанные** | Ссылки на связанные Issue / PR / Commit | Добавляется, если есть внешние обсуждения |
| **Тесты обратной проверки** | Расположение тестовых случаев для проверки исправления и предотвращения повторного появления ошибки | Добавляется, если соответствующие тесты pytest уже написаны |

## Уровни серьезности

| Идентификатор | Уровень | Критерии определения | Примеры проявления |
|---------------|---------|---------------------|-------------------|
| 🔴 | Критический | Причина аварийного завершения процесса, потеря/повреждение данных, полная недоступность ключевых функций, уязвимости безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Нарушение функциональности, но существуют пути обхода, не ключевые функции не работают, случайные проблемы | Ошибки в определении состояния, повторные срабатывания, истечение срока действия кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на ключевые функции, проблемы только с качеством кода или пользовательским опытом, потенциальные риски не проявляются | Устаревшие API, неиспользуемый код, отсутствие предупреждающих логов |

## Исправленные ошибки

### [BUG-001] Дублированная регистрация обработчиков событий, приводящая к многократной обработке событий

**Проблема**: При использовании нескольких декораторов `@message` / `@notice` и т.д. для регистрации обработчиков, одно и то же событие может быть запущено несколько раз, что приводит к многократному выполнению команд, повторному выводу логов.

**Причина**: `BaseEventHandler` при регистрации обработчиков в шине событий адаптера не содержит логики удаления дубликатов, каждый декоратор добавляет обработчик в шину, и при рассылке событий он вызывается несколько раз.

**Версии, затронутые проблемой**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия с исправлением**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался в шине адаптера только один раз, предотвращая многократное срабатывание.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-002] Ошибка типа пути конфигурации адаптера в команде init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` класса `Path` для объединения путей.

**Версии, затронутые проблемой**: 2.3.7 - 2.3.9-dev.1

**Версия с исправлением**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра метода `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средняя

**Тип**: CLI

---

### [BUG-003] После перезапуска события команды не срабатывают

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные через `@command`, не срабатывают, что проявляется в том, что бот не отвечает на отправленные команды.

**Причина**: `adapter.shutdown()` очищает шину событий, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, поэтому метод `_process_event` считает, что уже подключен к шине адаптера, и пропускает повторную регистрацию.

**Версии, затронутые проблемой**: 2.2.x - 2.4.0-dev.2

**Версия с исправлением**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при `clear()` отключение от шины, при следующем `register()` автоматическая повторная регистрация, адаптация к сценариям `shutdown/restart`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Критическая

**Тип**: Система событий

---

### [BUG-004] Обработчики жизненного цикла не очищаются

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла остаются и повторно срабатывают, что приводит к многократной обработке одного и того же события.

**Причина**: Словарь `lifecycle._handlers` никогда не очищается при `uninit()`, после перезапуска старые и новые обработчики существуют одновременно.

**Версии, затронутые проблемой**: 2.3.0 - 2.4.0-dev.2

**Версия с исправлением**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в процессе очистки `Uninitializer` (после всех событий), чтобы избежать дублирования обработчиков.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средняя

**Тип**: Время выполнения

### [BUG-005] Несоответствие detail_type в Event.is_friend_add/is_friend_delete и стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет `detail_type` как `"friend_increase"` и `"friend_decrease"`. Несоответствие с использованием в `notice.py` декораторов `on_friend_add`/`on_friend_remove`, что приводит к тому, что методы `is_friend_add()`/`is_friend_delete()` возвращают `False` при срабатывании соответствующих обработчиков.

**Причина**: В `wrapper.py` используется нестандартное наименование, в то время как `notice.py` использует правильные значения стандарта OB12.

**Версии, затронутые проблемой**: С момента реализации

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения сопоставления `is_friend_add()` с `"friend_add"` на `"friend_increase"`, `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, приводящее к ошибке состояния после перезапуска

**Проблема**: Метод `AdapterManager.clear()` очищает `_adapters`, `_adapter_info`, обработчики и `_bots`, но пропускает `_started_instances`. Если адаптер запущен и вызывается `clear()`, `_started_instances` сохраняет висячие ссылки, что приводит к ошибке состояния после перезапуска.

**Причина**: При введении `_started_instances` в 2.4.0-dev.1 не было синхронной очистки в `clear()`.

**Версии, затронутые проблемой**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущего и получения временной метки, этот метод устарел в Python 3.10+, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с `wait_for()` в `wrapper.py`, использующим `get_running_loop()`.

**Причина**: При разработке использовался старый API, в то время как `wait_for()` использует правильный API, но старый код не был обновлен.

**Версии, затронутые проблемой**: 2.3.0-dev.0

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: Замена `asyncio.get_event_loop()` в `command.py` на `asyncio.get_running_loop()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкая

**Тип**: Система событий

### [BUG-008] События отключения бота в процессе shutdown повторно отправляются

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` повторно отправляет события отключения бота в процессе закрытия, что приводит к многократной маркировке одних и тех же ботов как отключенных и многократному срабатыванию события `adapter.bot.offline`.

**Причина**: Введённая в 2.4.0-dev.1 система отслеживания состояния бота не устанавливает флаг "в процессе закрытия" в `shutdown()`, `update_bot_status()` не может отличить нормальное отключение от каскадного отключения в процессе закрытия.

**Версии, затронутые проблемой**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.1

**Содержание исправления**: В `AdapterManager` добавлен флаг `_is_being_shutdown`, устанавливаемый в `True` в начале `shutdown()` и сбрасываемый в конце; `update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к BaseModule в LazyModule приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к атрибуту лениво загружаемого BaseModule модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает завершения, что приводит к гонке за ресурсами при частичной инициализации.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и сразу возвращает, не обеспечивая завершение инициализации.

**Версии, затронутые проблемой**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule заменяется на `asyncio.run(self._initialize())`, чтобы обеспечить завершение инициализации перед возвратом. Сохраняется прозрачность прокси, пользователь не должен осознавать различия между синхронным и асинхронным.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средняя

**Тип**: Система загрузки

### [BUG-010] Многопоточная запись конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция `_flush_config()` не является атомарной, что может привести к потере частичной записи.

**Причина**: Хотя `_flush_config()` использует `RLock`, между чтением и записью файла нет защиты файловым блокировщиком, и `Timer` `_schedule_write` может быть запущен несколько раз, вызывая перезапись.

**Версии, затронутые проблемой**: 2.3.0 - 2.4.2-dev.1

**Версия с исправлением**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавление механизма файловой блокировки (`_file_lock`) для обеспечения атомарности операций с файлом
2. Использование временного файла для записи с последующей атомарной перезаписью (`os.replace`/`os.rename`)
3. Улучшение логики отмены и перезапуска таймера `_schedule_write`

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Критическая

**Тип**: Система конфигурации

### [BUG-011] Ctrl+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие Ctrl+C не останавливает программу. После нормального запуска и вывода информации о сервере маршрутизации, Ctrl+C не реагирует, процесс можно остановить только через диспетчер задач. При запуске через `epsdk run` остановка работает — но `epsdk run` использует модель подпроцессов.

**Причина**: Внутренний `serve()` сервера ASGI Hypercorn через `signal.signal(SIGINT, handler)` регистрирует свой обработчик SIGINT, перекрывающий механизм обработки KeyboardInterrupt Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()` внутренний процесс остановки Hypercorn не запускается (он ожидает режима `worker_serve`), что приводит к тому, что сигнал Ctrl+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Версии, затронутые проблемой**: 2.3.6 - 2.4.2

**Версия с исправлением**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена сервера ASGI с Hypercorn на Uvicorn (`pyproject.toml` зависимость)
2. Использование `uvicorn.Server._serve()` для запуска сервера, **обход** контекстного менеджера `capture_signals()`
3. Использование `server.should_exit = True` для обеспечения элегантной остановки, с отменой фоновой задачи при истечении таймаута
4. Синхронное удаление модели подпроцессов и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Критическая

**Тип**: CLI / Время выполнения

### [BUG-022] Регрессия в _resolve_account() (не заполняется _accounts_data)

**Проблема**: После рефакторинга системы конфигурации в 2.5.2 при вызове `wait_reply`, `reply` и других методов, требующих отправки сообщений, возникает ошибка `ValueError("未声明 AccountConfigClass，无法解析账户")`. **Причина**: В 2.5.2-dev.5 `_load_accounts()` (отвечает за чтение конфигурации + проверку + заполнение `_accounts_data`) был переработан в `_ensure_accounts_exist()` (генерирует только шаблон конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда равно `None`, что приводит к тому, что `_resolve_account()` возвращает `(None, None)` и разрешение учётной записи полностью теряется.

**Корневая цепочка**:
```
_load_accounts() удалён
  → __init__ не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → return (None, None)
        →下游 вызовы _resolve_account (например, call_api) получают None
          → вызывает ошибку
```

**Версии, затронутые проблемой**: 2.5.2-dev.5 - 2.5.2

**Версия с исправлением**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `_ensure_accounts_exist()` восстанавливается заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # восстановление заполнения, источник данных — актуальные accounts
```
Логика `_resolve_account()` остаётся неизменной, полностью обратная совместимость:
- Адаптеры, не объявляющие `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращается `(None, None)`
- Адаптеры, объявляющие `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, перезаписывающие `_load_accounts` или вручную устанавливающие `_accounts_data`: в `super().__init__()` после установки, приоритет высший

**Тип**: Адаптер / Система конфигурации

### [BUG-026] Неправильное определение целевого адреса reply в событиях notice/request

**Проблема**: При вызове `event.reply()` в событии уведомления (например, добавление участника в группу `group_member_increase`), сообщение отправляется в личный чат пользователя, вызвавшего событие, а не в группу, где произошло событие. **Причина**: `infer_receive_type()` возвращает `detail_type` как тип сессии. Для событий `message` это правильно (`detail_type` значения `private`/`group` — это тип сессии), но для событий `notice/request` `detail_type` — это семантический подтип (например, `group_member_increase`, `friend_increase`), а не тип сессии. Последующие `convert_to_send_type()` и `get_id_field()` в картах отображения не находят это значение и возвращаются к стандартным `"user"` / `"user_id"`, что приводит к неправильному целевому адресу.

**Корневая цепочка**:
```
detail_type уведомления = "group_member_increase"
  → infer_receive_type() возвращает "group_member_increase"
    → convert_to_send_type("group_member_increase") не в карте → возвращается "user"
    → get_id_field("group_member_increase") не в карте → возвращается "user_id"
      → target_id = event["user_id"]  ← новый участник в личный чат (а не в группу)
```

**Версии, затронутые проблемой**: Все версии

**Версия с исправлением**: 2.7.0-dev.3

**Содержание исправления**: `infer_receive_type()` добавляет проверку — `detail_type` возвращается как есть только если это известный тип сессии (стандартный или пользовательский); в противном случае по полю ID (например, `group_id`, `channel_id`, `user_id`) определяется правильный тип сессии.

### [BUG-029] Задача наблюдения за конфигурацией транслирует незавершённый TOML и тихо игнорирует ошибки

**Проблема**: При ручном редактировании `config.toml` и сохранении на полпути (создаётся временный файл с синтаксической ошибкой), фоновый поток наблюдения обнаруживает изменение mtime, перезагружает конфигурацию, но при сбое загрузки по-прежнему излучает событие `config.updated` с пустой конфигурацией `{}`, что приводит к тому, что `on_config_update` адаптеров/модулей получает пустую конфигурацию и ошибочно считает, что все параметры конфигурации были сброшены, возвращаясь к значениям по умолчанию. 1. `_load_config` при синтаксической ошибке/ошибке прав доступа перезаписывает `self._cache` в `{}`, но фоновый цикл `_watch_loop` и путь сброса кэша `_check_cache_validity` безусловно вызывают `_emit_config_updated()` с пустым конфигом, если `_load_config()` возвращает `False`.
2. `_watch_loop` с `except Exception: pass` не записывает никаких журналов.

**Корневая цепочка**:
```
Пользователь сохраняет на полпути → синтаксическая ошибка TOML
  → _load_config() перезаписывает _cache = {}
    → _watch_loop безусловно _emit_config_updated(new_config={})
      → on_config_update получает пустую конфигурацию
        → ошибочно считает, что конфигурация сброшена, возвращается к значениям по умолчанию
```

**Версии, затронутые проблемой**: 2.6.2-dev.1 - 2.7.0-dev.4

**Версия с исправлением**: 2.7.0-dev.5

**Содержание исправления**:
1. `_load_config` изменена на возврат `bool`; при синтаксической ошибке/ошибках прав доступа и других ошибках **сохраняется** предыдущий действующий кэш (не перезаписывается в `{}`), записываются диагностические журналы и возвращается `False`
2. `_watch_loop` и `_check_cache_validity` излучают `config.updated` только при возврате `True` из `_load_config()`
3. `except Exception` в `_watch_loop` заменён на запись предупреждения (добавлен i18n-ключ `core.config.watcher_error`, синхронно на 5 языках)

### [BUG-030] Гонка при наблюдении за конфигурацией приводит к тихой потере данных при отложенной записи

**Проблема**: Несколько пользователей сообщили, что при использовании `config.setConfig(key, value)` (по умолчанию `immediate=False`) конфигурация модуля не записывается в `config.toml`, в то время как конфигурация других модулей сохраняется. Установка `immediate=True` (принудительная запись) обходит проблему. Проявление: конфигурация, записанная в режиме выполнения, теряется после перезапуска, конфигурация, сгенерированная при запуске, сохраняется.

**Причина**: Два взаимодействующих дефекта:
1. **Логический дефект**: `_watch_loop` безусловно очищает `_dirty_keys`, если `_check_file_change()` возвращает `True`. Но `_check_file_change()` использует только `!=` для сравнения mtime, запись конфигурации фреймворком `_flush_config` также изменяет mtime — хотя `_flush_config` после записи обновляет `_config_mtime`, поток наблюдателя может обнаружить разницу mtime между записью файла и присвоением `_config_mtime` (а также на грубых файловых системах), ошибочно считая, что произошло внешнее изменение, и очищает все ключи для записи.
2. **Потоковой дефект**: `_watch_loop` не захватывает `_lock` при операциях с `_write_timer`/`_dirty_keys`, что приводит к гонке данных с `setConfig` (захватывает `_dirty_keys`), `_schedule_write` (захватывает `_write_timer`).

**Корневая цепочка**:
```
Модуль A setConfig(immediate=True) → flush запись, mtime меняется
  → Пользовательский модуль setConfig(immediate=False) → в `_dirty_keys`, через 5с запись
    → Наблюдательный цикл, _check_file_change обнаруживает разницу mtime от предыдущей записи
      → _dirty_keys.clear() → ключи для записи пользователя теряются
        → После перезапуска конфигурация отсутствует
```

**Версии, затронутые проблемой**: 2.6.0 - 2.7.0

**Версия с исправлением**: 2.7.1

**Содержание исправления**:
1. Добавлено `_last_self_write_mtime`, при `_flush_config` запись обновляется; в `_check_file_change` при изменении mtime сначала сравнивается с этим значением, если совпадает, возвращается `False`
2. Весь `_watch_loop` захватывает `_lock`; при реальном внешнем изменении `_dirty_keys` сохраняются (логика слияния), при следующей flush объединяются с внешними данными (ключи для записи имеют приоритет), `_dirty_keys` не очищаются
3. `getConfig`/`_check_cache_validity` не затрагиваются (перезагрузка не очищает ключи для записи)

**Дата исправления**: 2026/08/06

**Тесты на восстановление**: `tests/unit/test_unit_config.py` → `test_self_write_not_detected_as_external`, `test_external_change_preserves_dirty_keys`, `test_flush_merges_dirty_with_external`

### [BUG-032] Чтение после записи в конфигурации с задержкой возвращает старое значение

**Проблема**: `config.setConfig()` (по умолчанию `immediate=False`, задержка около 5 секунд) при записи по точечному ключу, немедленное чтение его родительского/предка (например, `set_erispulse_section("scope.actions.MyModule", {...})` после вызова `get_erispulse_config()`) возвращает старое значение, записанный подключенный элемент "исчезает", пока не произойдёт запись.
