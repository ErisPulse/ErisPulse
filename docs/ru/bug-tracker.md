# Баг-трекер

Данный документ содержит список известных багов ErisPulse SDK и информацию об их исправлении, отсортированную по времени исправления.

> **Для читателя**
> Ни одно программное обеспечение не бывает идеальным с самого начала, даже самые внимательные разработчики могут оставить небольшие ошибки. В этот трекер включены только проблемы, которые оказывают реальное влияние на работу приложения — те, что слишком мелкие или не достигают даже уровня "незначительного" бага, здесь не отображаются. Список содержит "серьезные" пункты, которых может показаться много, но публикация таких багов имеет цель сделать поиск и отслеживание проблем более гладким, а не вызывать беспокойство: проблемы, которые видны, записаны и исправлены, сами по себе являются свидетельством улучшения проекта. Не стоит беспокоиться, глядя на этот список — это инструмент для поиска проблем, а не источник страха.

> **Как читать и правила поддержки**
> - Каждая запись о баге содержит структурированные поля: описание проблемы, анализ причины, диапазон версий, в которых баг актуален, номер версии, в которой исправлен, краткое описание исправления, дата публикации, уровень серьезности и тип. Рекомендуется перед обновлением проверять, охватывает ли "диапазон версий" используемую вами версию.
> - Если требуется добавить новую запись о баге, дополните соответствующую позицию, следуя формату полей и классификации серьезности/типа, описанным ниже.

## Классификация серьезности

| Иконка | Уровень | Критерии | Типичные проявления |
|------|------|---------|---------|
| 🔴 | Серьезный | Причиняет сбой процесса, потерю/повреждение данных, полную недоступность основных функций, уязвимости безопасности | OOM Kill, невозможность отправки сообщений, невозможность загрузки модуля, сбой горячей перезагрузки |
| 🟡 | Средний | Нарушение функциональности, но есть пути обхода, неосновные функции не работают, случайные проблемы | Ошибочное определение состояния, повторный запуск, истечение кэша, неточное сообщение об ошибке |
| 🟢 | Легкий | Не влияет на основную функциональность, только проблемы качества кода или пользовательского опыта, потенциальные риски не проявляются | Устаревший API, мертвый код, отсутствие предупреждающего лога |

## Исправленные баги

### [BUG-001] Повторная регистрация обработчиков событий приводит к повторному обработанию событий

**Проблема**: При использовании нескольких `@message` / `@notice` и других декораторов для регистрации обработчиков, одно и то же событие будет обрабатываться несколько раз, что приводит к повторному выполнению команд и дублированию логов.

**Причина**: `BaseEventHandler` регистрирует обработчики в событийной шине адаптера без логики удаления дубликатов, каждый декоратор добавляет обработчик, и событие обрабатывается несколько раз.

**Влияющие версии**: 2.2.0-dev.0 - 2.2.1-dev.0

**Версия исправления**: 2.2.1-dev.0

**Содержание исправления**: Оптимизация `BaseEventHandler`, чтобы каждый тип события регистрировался только один раз, предотвращая повторное срабатывание.

**Дата исправления**: 2025/08/18

**Серьезность**: 🔴 Серьезный

**Тип**: Система событий

---

### [BUG-002] Ошибка типа при выборе конфигурации адаптера в команде init

**Проблема**: При использовании команды `ep init` для интерактивной инициализации возникает ошибка типа:

```
Интерактивная инициализация не удалась: unsupported operand type(s) for /: 'str' and 'str'
```

**Причина**: При изменении пути конфигурационного файла в версии 2.3.7 метод `_configure_adapters_interactive_sync` принимает параметр типа `str`, но внутри используется оператор `/` для объединения путей с `Path`.

**Влияющие версии**: 2.3.7 - 2.3.9-dev.1

**Версия исправления**: 2.3.9-dev.1

**Содержание исправления**: Изменение типа параметра `_configure_adapters_interactive_sync` с `str` на `Path`, передача объекта `Path` при вызове.

**Дата исправления**: 2026/03/23

**Серьезность**: 🟡 Средний

**Тип**: CLI

---

### [BUG-003] После перезапуска команды события не активны

**Проблема**: После вызова `sdk.restart()` команды, зарегистрированные с помощью `@command`, не срабатывают, что приводит к тому, что бот не отвечает на отправленные команды.

**Причина**: `adapter.shutdown()` очищает событийную шину, но состояние `_linked_to_adapter_bus` в `BaseEventHandler` не сбрасывается в `False`, поэтому `_process_event` считает, что уже подключен к шине, и пропускает повторную регистрацию.

**Влияющие версии**: 2.2.x - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Содержание исправления**: Введение отслеживания состояния `_linked_to_adapter_bus`, при `clear_handlers()` отключение от шины, при следующем `register()` автоматическая повторная регистрация, адаптация к сценариям `shutdown/restart`.

**Дата исправления**: 2026/04/09

**Серьезность**: 🔴 Серьезный

**Тип**: Система событий

### [BUG-004] Обработчики жизненного цикла не очищены

**Проблема**: После `sdk.restart()` старые обработчики событий жизненного цикла по-прежнему существуют и повторно срабатывают, что приводит к одному и тому же событию, обрабатываемому несколько раз.

**Причина**: Словарь `lifecycle._handlers` не очищается при `uninit()`, при перезапуске старые и новые обработчики существуют одновременно.

**Влияющие версии**: 2.3.0 - 2.4.0-dev.2

**Версия исправления**: 2.4.0-dev.3

**Содержание исправления**: Очистка `lifecycle._handlers` в процессе очистки `Uninitializer` (после всех событий), чтобы избежать повторного срабатывания.

**Дата исправления**: 2026/04/09

**Серьезность**: 🟡 Средний

**Тип**: Рантайм

### [BUG-005] Event.is_friend_add/is_friend_delete detail_type не соответствует стандарту OB12

**Проблема**: `Event.is_friend_add()` проверяет `detail_type == "friend_add"`, `Event.is_friend_delete()` проверяет `detail_type == "friend_delete"`, но стандарт OneBot12 определяет значения `detail_type` как `"friend_increase"` и `"friend_decrease"`. Соответственно, обработчики, зарегистрированные с помощью `on_friend_add`/`on_friend_remove`, не срабатывают при соответствующих методах `is_friend_add()`/`is_friend_delete()`.

**Причина**: `wrapper.py` использует нестандартные имена, а `notice.py` использует правильные имена стандарта OB12.

**Влияющие версии**: С момента реализации

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Изменение значения для `is_friend_add()` с `"friend_add"` на `"friend_increase"`, для `is_friend_delete()` с `"friend_delete"` на `"friend_decrease"`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Система событий

### [BUG-006] adapter.clear() не очищает _started_instances, приводя к ошибке состояния после перезапуска

**Причина**: При введении `_started_instances` в версии 2.4.0-dev.1 не было очищения в `clear()`.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.0

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Добавление `self._started_instances.clear()` в метод `clear()`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-007] command.wait_reply() использует устаревший asyncio.get_event_loop()

**Проблема**: Метод `CommandHandler.wait_reply()` использует `asyncio.get_event_loop()` для создания будущего и получения временной метки, этот метод устарел в Python 3.10+, в асинхронном контексте следует использовать `asyncio.get_running_loop()`. Несоответствие с `wait_for()` в файле `wrapper.py`, который использует `get_running_loop()`.

**Причина**: Использование старого API при разработке, последующий `wait_for()` использует правильный API, но старый код не был исправлен.

**Влияющие версии**: 2.3.0-dev.0

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Замена `asyncio.get_event_loop()` на `asyncio.get_running_loop()` в `command.py`.

**Дата исправления**: 2026/04/13

**Серьезность**: 🟢 Легкий

**Тип**: Система событий

### [BUG-008] Событие отключения Bot при shutdown повторно отправляется

**Проблема**: При вызове `adapter.shutdown()` для закрытия всех адаптеров, `_update_bot_status()` повторно отправляет события отключения Bot, приводя к многократному отображению статуса отключения и триггеру нескольких событий жизненного цикла `adapter.bot.offline`.

**Причина**: Введённая в 2.4.0-dev.1 система отслеживания статуса Bot не устанавливает флаг "в процессе закрытия" при `shutdown()`, `_update_bot_status()` не может отличить нормальное отключение от повторного отключения в процессе закрытия.

**Влияющие версии**: 2.4.0-dev.1 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.1

**Содержание исправления**: Добавление флага `_is_being_shutdown` в `AdapterManager`, установка True в начале `shutdown()` и сброс при завершении; `_update_bot_status()` проверяет этот флаг и пропускает повторную отправку в процессе закрытия.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Адаптер

### [BUG-009] Синхронный доступ к BaseModule при ленивой загрузке приводит к незавершённой инициализации

**Проблема**: При синхронном доступе к атрибуту лениво загруженного BaseModule модуль использует `loop.create_task()` для асинхронной инициализации, но не ожидает завершения, что приводит к гонке данных.

**Причина**: `_ensure_initialized()` для BaseModule использует `loop.create_task(self._initialize())` и сразу возвращает, не ожидая завершения инициализации.

**Влияющие версии**: 2.4.0-dev.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Содержание исправления**: В синхронном контексте инициализация BaseModule заменяется на `asyncio.run(self._initialize())`, чтобы убедиться в завершении инициализации перед возвратом. Сохраняется прозрачность прокси, пользователь не должен осознавать различий между синхронным и асинхронным контекстом.

**Дата исправления**: 2026/04/21

**Серьезность**: 🟡 Средний

**Тип**: Загрузка

### [BUG-010] Многопоточная запись в систему конфигурации приводит к потере данных

**Проблема**: В многопоточной среде, когда несколько потоков одновременно вызывают `config.setConfig()`, операция чтения-изменения-записи `_flush_config()` не является атомарной, что может привести к потере части записей.

**Причина**: Несмотря на использование `RLock` в `_flush_config()`, между чтением и записью файла нет атомарной защиты с помощью блокировки файла, а таймер `_schedule_write` может быть многократно запущен, вызывая перезапись.

**Влияющие версии**: 2.3.0 - 2.4.2-dev.1

**Версия исправления**: 2.4.2-dev.2

**Содержание исправления**:
1. Добавление механизма блокировки файла (`_file_lock`) для атомарности операций с файлом
2. Использование временного файла для записи, атомарное переименование (`os.replace`/`os.rename`)
3. Улучшение логики таймера `_schedule_write` для отмены и повторного запуска

**Дата исправления**: 2026/04/21

**Серьезность**: 🔴 Серьезный

**Тип**: Система конфигурации

### [BUG-011] Ctrl+C не может остановить программу в Windows

**Проблема**: При прямом запуске `python main.py` в Windows нажатие Ctrl+C не останавливает программу. Программа запускается и выводит информацию о сервере маршрутизации, но Ctrl+C не реагирует, можно только принудительно завершить процесс через диспетчер задач. При запуске через `epsdk run` остановка работает, но `epsdk run` использует модель подпроцессов.

**Причина**: ASGI-сервер Hypercorn использует `signal.signal(SIGINT, handler)` для регистрации своего обработчика SIGINT, перекрывая стандартный механизм обработки KeyboardInterrupt в Python. При запуске Hypercorn как фоновая задача через `asyncio.create_task()` внутренний процесс остановки Hypercorn не запускается, так как ожидается режим `worker_serve`, что приводит к тому, что сигнал Ctrl+C поглощается Hypercorn, но не вызывает никаких действий очистки.

**Влияющие версии**: 2.3.6 - 2.4.2

**Версия исправления**: 2.4.3-dev.0

**Содержание исправления**:
1. Замена ASGI-сервера Hypercorn на Uvicorn (`pyproject.toml` зависимость)
2. Использование `uvicorn.Server._serve()` для запуска сервера, **обход** контекстного менеджера `capture_signals()`
3. Использование `server.should_exit = True` для корректной остановки, по истечении времени отмена фоновой задачи
4. Синхронное удаление модели подпроцессов и модуля очистки `runtime/cleanup.py` (механизм очистки подпроцессов больше не нужен)

**Дата исправления**: 2026/04/28

**Серьезность**: 🔴 Серьезный

**Тип**: CLI / Рантайм

### [BUG-012] После горячей перезагрузки обновленный код модуля не применяется

**Проблема**: При выполнении `sdk.restart()` (мягкая перезагрузка) модули/адаптеры, обновленные с помощью `epsdk install`, не применяют новые коды (например, новые маршруты API), продолжая работать по старой логике. Необходим полный перезапуск процесса для загрузки последней версии кода.

**Причина**: `_do_restart()` при повторной инициализации вызывает `entry_point.load()`, но эта функция возвращает закэшированные объекты модулей из `sys.modules`, а не загружает их заново с диска.

### [BUG-022] Возврат _resolve_account() после обновления конфигурации (аккаунт _accounts_data не заполнен)

**Проблема**: После реорганизации системы конфигурации в 2.5.2, адаптеры с объявленным `AccountConfigClass`, вызывающие методы отправки сообщений, такие как `wait_reply` и `reply`, вызывают ошибку `ValueError("Не объявлен AccountConfigClass, невозможно разрешить аккаунт")`. Даже если адаптер правильно настроен с информацией о нескольких аккаунтах, разрешение аккаунта всё равно не удаётся.

**Причина**: В 2.5.2-dev.5 функция `_load_accounts()` (отвечающая за чтение конфигурации, проверку и заполнение `_accounts_data`) была реорганизована в `_ensure_accounts_exist()` (только генерация шаблона конфигурации), но `_resolve_account()` по-прежнему проверяет `self._accounts_data is None`. Поскольку `_ensure_accounts_exist()` больше не заполняет `_accounts_data`, это свойство всегда равно `None`, что приводит к тому, что `_resolve_account()` возвращает `(None, None)` и аккаунт не может быть разрешён.

**Цепочка корневых причин**:
```
_load_accounts() удалена
  → __init__ не заполняет _accounts_data
    → _accounts_data всегда None
      → _resolve_account() проверяет _accounts_data is None → возвращает (None, None)
        → методы, использующие _resolve_account (например, call_api), получают None
          → вызывается ошибка
```

**Влияющие версии**: 2.5.2-dev.5 - 2.5.2

**Версия исправления**: 2.5.3

**Содержание исправления**: В `BaseAdapter.__init__` после `_ensure_accounts_exist()` восстанавливается заполнение `_accounts_data`:
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # Восстановление заполнения, источник данных — актуальные значения accounts
```
Логика `_resolve_account()` остаётся без изменений, полностью обратная совместимость:
- Адаптеры, которые не объявляют `AccountConfigClass`: `_accounts_data` остаётся `None` → возвращает `(None, None)`
- Адаптеры, которые объявляют `AccountConfigClass`: `_accounts_data` заполняется → нормальное разрешение
- Адаптеры, которые переопределяют `_load_accounts` или вручную устанавливают `_accounts_data`: перекрываются после `super().__init__()`, с наивысшим приоритетом

**Дата исправления**: 2026/07/07

**Серьезность**: 🔴 Серьезный

**Тип**: Адаптер / Система конфигурации

### [BUG-026] Ошибка вывода ответа на события notice/request


**Версия исправления**: 2.7.0-dev.3

**Содержание исправления**: `infer_receive_type()` добавляет проверку — `detail_type` возвращается напрямую, только если это известный тип сессии (стандартный или пользовательский); в противном случае по полю ID (`group_id` / `channel_id` / `user_id` и т.д.) выводится правильный тип сессии.

### [BUG-029] Задача прослушивания конфигурации транслирует незавершённый TOML и молча поглощает исключения

**Проблема**: При ручном редактировании `config.toml` и сохранении в промежуточном состоянии (создаётся временный файл с синтаксической ошибкой), фоновый поток прослушивания обнаруживает изменение mtime, перезагружает конфигурацию, но при сбое загрузки по-прежнему транслирует пустую конфигурацию `{}` и издаёт событие `config.updated`, что приводит к тому, что `on_config_update` адаптеров/модулей получает пустую конфигурацию, ошибочно полагая, что все параметры были сброшены, и возвращает значения по умолчанию. **Цепочка корневых причин**:
```
Пользователь сохраняет в промежуточном состоянии → синтаксическая ошибка TOML
  → _load_config() перезаписывает _cache = {}
    → _watch_loop безусловно _emit_config_updated(new_config={})
      → адаптеры/модули on_config_update получают пустую конфигурацию
        → ошибочно полагают, что конфигурация была сброшена, возвращают значения по умолчанию
```

**Влияющие версии**: 2.6.2-dev.1 - 2.7.0-dev.4

**Версия исправления**: 2.7.0-dev.5

**Содержание исправления**:
1. `_load_config` изменён на возвращение `bool`; при синтаксической ошибке/ошибке доступа и других ошибках кэш не перезаписывается в `{}`, а только записываются диагностические логи и возвращается `False`
2. `_watch_loop` и `_check_cache_validity` издают событие `config.updated` только при возвращении `True` из `_load_config()`
3. `except Exception` в `_watch_loop` изменён на запись с уровнем `warning` (добавлен i18n-ключ `core.config.watcher_error`, синхронно на пяти языках)

### [BUG-030] Гонка при наблюдении за конфигурацией приводит к потере данных при задержанной записи

**Проблема**: Несколько пользователей сообщили, что после использования `config.setConfig(key, value)` (по умолчанию `immediate=False`) их конфигурация модуля не записывается в `config.toml`, в то время как конфигурация других модулей сохраняется. Установка `immediate=True` (принудительная запись) решает проблему. Происходит так, что конфигурация, записанная в процессе, теряется при следующем перезапуске, а конфигурация, сгенерированная при запуске, сохраняется.

**Причина**: Два складывающихся дефекта:
1. **Логический дефект**: `_watch_loop` при `_check_file_change()` возвращает `True` безусловно очищает `_dirty_keys`, удаляя все ключи для записи. Но `_check_file_change()` использует только `!=` для сравнения mtime, и запись, вызванная самим фреймворком `_flush_config`, также меняет mtime — хотя `_flush_config` обновляет `_config_mtime` после записи, поток прослушивания может наблюдать разницу mtime между записью файла и присвоением `_config_mtime` (а также на грубых системах файлов), ошибочно распознавая это как "внешнее изменение" и очищая все ключи для записи.
2. **Дефект потоков**: `_watch_loop` не использует `_lock` при операциях с `_write_timer`/`_dirty_keys`, что приводит к гонке данных с `setConfig` (блокировка `_dirty_keys`), `_schedule_write` (блокировка `_write_timer`).

**Цепочка корневых причин**:
```
Модуль A setConfig(immediate=True) → flush записывает, mtime меняется
  → Пользовательский модуль setConfig(immediate=False) → входит в _dirty_keys, через 5 секунд запись
    → Поток прослушивания, _check_file_change замечает разницу mtime от предыдущей записи
      → _dirty_keys.clear() → ключи для записи пользователя удаляются
        → При перезапуске конфигурация отсутствует
```

**Влияющие версии**: 2.6.0 - 2.7.0

**Версия исправления**: 2.7.1

**Содержание исправления**:
1. Добавлено `_last_self_write_mtime` поле, при `_flush_config` записывается значение; при `_check_file_change` сравнивается с этим значением, если совпадает, возвращается `False`
2. Весь `_watch_loop` выполняется с `_lock`; при реальном внешнем изменении `_dirty_keys` сохраняются (семантика объединения), при следующем flush объединяются с внешними данными (ключи для записи имеют приоритет), `_dirty_keys` не очищаются
3. `getConfig`/`_check_cache_validity` пути не затрагиваются (перезагрузка не очищает ключи для записи)

**Тесты на возврат**: `tests/unit/test_unit_config.py` → `test_self_write_not_detected_as_external`, `test_external_change_preserves_dirty_keys`, `test_flush_merges_dirty_with_external`
