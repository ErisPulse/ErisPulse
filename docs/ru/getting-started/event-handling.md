# Введение в обработку событий

В этом руководстве рассказывается о том, как обрабатывать различные типы событий в ErisPulse.

## Обзор типов событий

ErisPulse поддерживает следующие типы событий:

| Тип события | Описание | Сценарии использования |
|---------|------|---------|
| Событие сообщения | Любое сообщение, отправленное пользователем | Чат-боты, фильтрация контента |
| Событие команды | Сообщение с префиксом команды | Обработка команд, вход в функции |
| Событие уведомления | Системные уведомления (добавление друзей, изменение участников группы и т.д.) | Приветствия, уведомления о состоянии |
| Событие запроса | Запросы от пользователей (запросы на добавление друзей, приглашения в группы) | Автоматическая обработка запросов |
| Событие мета | Системные события (соединение, таймер) | Мониторинг подключения, проверка состояния |

## Обработка событий сообщения

> **Примечание**: Рекомендуется использовать аннотацию типа `Event` в обработчиках событий для получения подсказок IDE и поддержки проверки типов.

```python
from ErisPulse.Core.Event import Event  # Импорт типа события для аннотации
```

### Наблюдение за всеми сообщениями

```python
from ErisPulse.Core.Event import message, Event

@message.on_message()
async def message_handler(event: Event):
    text = event.get_text()
    user_id = event.get_user_id()
    sdk.logger.info(f"Получено сообщение от {user_id}: {text}")
```

### Наблюдение за личными сообщениями

```python
@message.on_private_message()
async def private_handler(event: Event):
    user_id = event.get_user_id()
    await event.reply(f"Привет, {user_id}! Это личное сообщение.")
```

### Наблюдение за сообщениями в группе

```python
@message.on_group_message()
async def group_handler(event: Event):
    group_id = event.get_group_id()
    user_id = event.get_user_id()
    sdk.logger.info(f"В группе {group_id} {user_id} отправил сообщение")
```

### Наблюдение за сообщениями с упоминанием

```python
@message.on_at_message()
async def at_handler(event: Event):
    # Получить список упомянутых пользователей
    mentions = event.get_mentions()
    await event.reply(f"Вы упомянули этих пользователей: {mentions}")
```

### Использование подстановочных знаков и регулярных выражений

Четыре декоратора сообщений (`on_message` / `on_private_message` / `on_group_message` /
`on_at_message`) поддерживают `pattern` (подстановочные знаки glob) и `regex` (регулярные выражения), несоответствующие сообщения **не вызывают** обработчик:

```python
# Подстановочные знаки glob: * любая строка, ? один символ, [seq] набор символов
@message.on_message(pattern="签到*")
async def signin_handler(event: Event):
    await event.reply("签到成功")

# Регулярное выражение: совпадение суммы
@message.on_message(regex=r"\d+\s*元")
async def price_handler(event: Event):
    await event.reply(f"Получена сумма: {event.get_text()}")

# pattern и regex одновременно — оба должны совпадать
@message.on_message(pattern="*元", regex=r"\d+\s*元")
async def combined_handler(event: Event):
    pass
```

`wait_reply` также поддерживает эти два параметра (см. [Функция ожидания ответа](../developer-guide/modules/event-wrapper.md#ожидание-ответа)).

## Обработка событий команды

### Основные команды

```python
from ErisPulse.Core.Event import command

@command("help", help="Показать справочную информацию")
async def help_handler(event):
    help_text = """
Доступные команды:
/help - Показать справку
/ping - Тест подключения
/info - Показать информацию
    """
    await event.reply(help_text)
```

### Псевдонимы команды

```python
@command(["help", "h"], aliases=["帮助"], help="Показать справочную информацию")
async def help_handler(event):
    await event.reply("Справочная информация...")
```

Пользователь может вызвать с помощью любого из следующих способов:
- `/help`
- `/h`
- `/帮助`

### Аргументы команды

```python
@command("echo", help="Повторить сообщение")
async def echo_handler(event):
    # Получить аргументы команды
    args = event.get_command_args()
    
    if not args:
        await event.reply("Введите сообщение для повторения")
    else:
        await event.reply(f"Вы сказали: {' '.join(args)}")
```

Аргументы сохраняют исходный регистр ввода пользователя (даже если настройки чувствительны к регистру, нормализация имени команды не влияет на содержимое аргументов).

### Декларативные аргументы и опции (args= / options=)

Ручная обработка аргументов требует самой обработки преобразования типов и сообщений об ошибках. После декларации `args=` / `options=` фреймворк автоматически анализирует аргументы команды и **вставляет их по имени в обработчик** после проверки прав; при вводе пользователем ошибки автоматически возвращается локализованное сообщение и пример использования (не будет генерироваться исключение, которое приведет к сбою), `/help <command>` также автоматически отображает пример использования:

```python
@command(
    "roll",
    args="<count:int> [sides:int=6]",
    options={"verbose": "-v/--verbose", "label": "--label"},
    help="Бросить кубик",
)
async def roll_handler(event, count: int, sides: int = 6, verbose: bool = False, label: str = ""):
    total = sum(random.randint(1, sides) for _ in range(count))
    await event.reply(f"Бросил {count} раз {sides}-гранного кубика, общая сумма очков: {total}")
```

Синтаксис позиционных аргументов `args=`: `<count:int>` обязательный, `[sides:int=6]` необязательный (с значением по умолчанию). Поддерживаемые типы:

| Тип | Пример ввода | Описание |
|------|---------|------|
| `str` | `hello` | Текст (тип по умолчанию) |
| `int` / `float` | `3` / `0.5` | Числа |
| `bool` | `是` / `yes` / `はい` / `да` / `true` / `no` / `取消` | Логическое значение, повторяет таблицу подтверждения взаимодействия (`Event.confirm()`) |
| `literal` | `<mode:literal=fast|slow>` | Перечисление, принимает только перечисленные значения; необязательная форма по умолчанию берет первый |
| `duration` | `90s`、`1h30m`、`1d` | Продолжительность, преобразуется в секунды как float |
| `rest` | `<text:rest>` | Оставшийся текст (должен быть в конце) |

`options=` опции объявляются в виде словаря: ключ — имя параметра обработчика, значение — формат флага (разделенные `/` множественные псевдонимы). Параметры, аннотированные как `bool`, являются логическими флагами (появление означает `True`); остальные (по умолчанию как `str`) являются опциями со значением, поддерживают `--label hello` и `--label=hello` для получения значений, тип следует аннотации обработчика. Опции сначала распознаются и удаляются, оставшиеся токены затем анализируются по `args=` (остаток `rest` заменяет оставшийся текст после удаления опций).

**Основные моменты поведения**:

- Проверка прав выполняется до анализа аргументов — пользователи без прав не вызывают анализ
- При неудачном анализе (неправильный тип / отсутствие параметров / слишком много параметров / неизвестная опция) автоматически возвращается локализованное сообщение об ошибке + пример использования, команда все еще учитывается
- Имена декларированных параметров должны присутствовать в сигнатуре обработчика, в противном случае при регистрации возникает `ValueError`
- Отсутствие декларации `args=` / `options=` не меняет поведение команды (обратная совместимость)

### Управление командами (cooldown= / rate_limit= / deprecated=)

Ручной таймер охлаждения, окно ограничения скорости, сообщения об устаревании можно заменить декларацией, все три могут быть произвольно объединены.

**Охлаждение** — длительность синтаксиса аналогична типу `duration` в `args=` (например, `"30s"`, `"1h30m"`, `"1d"`):

```python
@command("daily", cooldown="1d", cooldown_key="user", cooldown_reply="今天已签到")
async def daily_handler(event):
    await event.reply("签到成功！")
```

**Ограничение скорости** — декларация скользящего окна `"количество/окно"` (например, `"5/minute"`, `"10/s"`, `"3/2m"`):

```python
@command("search", rate_limit="5/minute", rate_limit_key="user")
async def search_handler(event):
    await event.reply("搜索结果")
```

**Устаревание** — автоматическое возвращение устаревшего текста при вызове, `deprecated_reject=True` отклоняет выполнение:

```python
@command("oldcmd", deprecated="请用 /newcmd", deprecated_reject=True)
async def old_handler(event): ...
```

Ключевая гранулярность (`cooldown_key=` / `rate_limit_key=`): `"user"` (по умолчанию, одинаковое для всех пользователей), `"session"` (одинаковое для одной сессии, например, одной группы), `"global"` (для всех пользователей и сессий).

**Основные моменты поведения**:

- При попадании в охлаждение / ограничение скорости по умолчанию **тихо отбрасываются** (в симметрии с тихой областью действия); при объявлении `cooldown_reply=` / `rate_limit_reply=` при попадании возвращается текст ответа
- Команда при попадании учитывается — управление попадания не пропускает низкоприоритетные обработчики сообщений
- Проверка прав и анализ аргументов выполняются до фактического выполнения: пользователи без прав не вызывают, ошибки в аргументах не расходуются
- При одновременном объявлении охлаждения и ограничения скорости сначала проверяется охлаждение (если охлаждение срабатывает, не занимает окно ограничения скорости)
- `deprecated=` по умолчанию возвращает текст и **продолжает выполнение**; `deprecated_reject=True` отклоняет выполнение (`command.executed` хук записывает `success=False, error="deprecated"`)
- `/help` список и справка по отдельной команде автоматически отображают метку устаревания и текст
- Состояние хранится в памяти процесса, при выгрузке модуля автоматически очищается; общее хранение / перезапуск / постоянная сохранность не входит в сферу ответственности
- Декларация проверяется на этапе регистрации (fail-fast): неправильный синтаксис, не белый список значений ключевой гранулярности, reply не сопровождается основной декларацией вызывают `ValueError`

### Ограничение скорости обработчиков (throttle=) и дебаунс (debounce=)

Декларация защиты от спама обработчиков сообщений — события с одинаковым ключом в интервале обрабатываются максимум один раз, остальные тихо отбрасываются:

```python
from ErisPulse import sdk

@sdk.message.on_message(throttle="2s", throttle_key="user")
async def handler(event): ...
```

Дебаунс и ограничение скорости дополняют друг друга: **в окне выполняется только последнее событие**, предыдущие ожидающие задачи автоматически отменяются (подходит для сценариев поисковой подсказки, где нужно "обработать после остановки ввода"):

```python
@sdk.message.on_message(debounce="2s", debounce_key="user")
async def search(event): ...
```

`on_message` / `on_private_message` / `on_group_message` / `on_at_message`
поддерживают; `throttle_key=` / `debounce_key=` и ключевая гранулярность управления команды (user / session / global), синтаксис длительности аналогичен `duration`. Ограничение скорости и `pattern=` / `regex=` и другие существующие условия применяются одновременно (все должны совпадать, чтобы сработать); в интервале отбрасываются только логи TRACE; декларация проверяется на этапе регистрации; `throttle=` и `debounce=` семантически взаимоисключающие (одновременная декларация вызывает `ValueError`).

### Зависимости (Depends)

Общие зависимости (сессия базы данных, чтение конфигурации и т.д.) можно вынести в функции зависимости, обработчики объявляют параметры по умолчанию как `Depends(функция_зависимости)`, фреймворк автоматически вызывает функцию зависимости с объектом контекста и вставляет результат по имени:

```python
from ErisPulse.Core import Depends

async def get_session(event):
    return await sdk.module.call("DB", "get_session")

@command("admin")
async def admin_handler(event, db=Depends(get_session)):
    ...
```

По умолчанию включено **кэширование на уровне запроса**: в рамках одного события обработки одна и та же функция зависимости анализируется только один раз, и все точки вставки разделяют результат (например, `get_db` в одном событии создает только одну сессию базы данных); между запросами автоматически не повторяется. Можно отключить кэширование для каждой отдельной зависимости с помощью `Depends(get_db, use_cache=False)`.

Охватывает все точки внедрения фреймворка — обработчики команд, обработчики событий (`message.on_message()` и т.д.), хуки жизненного цикла (`sdk.lifecycle.on`), маршруты SSE. Первый параметр функции зависимости — это объект контекста точки внедрения (в случае событий — `Event`, в случае жизненного цикла — `data`, в случае маршрута — `HttpRequest` / `SseEmitter`); можно объявить как синхронные, так и асинхронные функции зависимости.

**Синтаксис сахара для объявления сервисов других модулей**:

```python
@command("query")
async def query_handler(event, session=Depends.module("DB", "get_session")):
    ...
```

`Depends.module(модуль, метод, *фиксированные_аргументы)` эквивалентно вызову `sdk.module.call(...)` внутри зависимости. Инициализация модуля (`__init__`) не входит в сферу ответственности — при инициализации нет объекта контекста; для маршрутов HTTP, поддерживаемых FastAPI, используйте оригинальный `fastapi.Depends`.

**Основные моменты поведения**:

- Декларация проверяется на этапе регистрации (fail-fast): если зависимость вызвать нельзя, или она перекрывает `args=` / `options=` параметры, возникает `ValueError`
- Исключения, возникающие в функции зависимости, обрабатываются так же, как и исключения самого обработчика (команда автоматически возвращает ошибку)
- Обработчики без декларации `Depends` имеют нулевые накладные расходы (в фазе распределения нет отражения)
- Для маршрутов HTTP, поддерживаемых FastAPI, используйте оригинальный `fastapi.Depends`

### Группы команд

```python
@command("admin.reload", group="admin", help="Перезагрузить модуль")
async def reload_handler(event):
    await event.reply("Модуль перезагружен")

@command("admin.stop", group="admin", help="Остановить робота")
async def stop_handler(event):
    await event.reply("Робот остановлен")
```

Параметр `group` используется только для группировки в справке; в примере выше `admin.reload` — это **одно целое имя команды** (точка — это просто стиль именования, пользователь должен ввести `/admin.reload`).

### Подкоманды

Имена команд поддерживают **многосимвольный формат с разделением пробелами**, реализуя подкоманды вроде `/admin add`, `/admin user ban`:

```python
@command("admin", help="Команды управления")
async def admin_handler(event):
    await event.reply("Использование: /admin add | /admin remove")

@command("admin add", help="Добавить администратора")
async def admin_add_handler(event):
    target = event.get_command_args()[0]
    await event.reply(f"Добавлен {target}")

@command("admin remove", aliases=["a remove"], help="Удалить администратора")
async def admin_remove_handler(event):
    await event.reply("Удален")
```

Правила сопоставления (**наиболее длинный префикс**):

- `/admin add x` сначала попадает в `admin add`, `event.get_command_args()` возвращает `["x"]` (параметры после имени подкоманды)
- Если зарегистрирована только `admin`, то `/admin add x` попадает в `admin`, `get_command_args()` возвращает `["add", "x"]` (историческое поведение не изменилось)
- Алиасы поддерживают многосимвольные формы (например, `a remove`), также можно использовать односимвольные алиасы (например, `a`) для указания подкоманды
- При регистрации родительской и подкоманды, не зарегистрированная подкоманда (например, `/admin list x`) возвращается к родительской команде

**Наследование прав доступа**: если подкоманда не декларирует `permission`, автоматически наследует ближайшую предка, декларировавшего права — защита `/admin` автоматически защищает все подкоманды; права подкоманды имеют приоритет:

```python
def is_admin(event):
    return event.get_user_id() in {"user123"}

@command("admin", permission=is_admin, help="Команды управления")
async def admin_handler(event):
    ...

# Не нужно повторно декларировать permission, автоматически наследуется is_admin
@command("admin add", help="Добавить администратора")
async def admin_add_handler(event):
    ...
```

Примечание: `master=True` и `hidden` **не** наследуются, при необходимости декларируйте их отдельно в подкоманде; пользовательский ACL (белый и черный списки) сопоставляется по полному имени команды, правила glob, как `"admin*"` могут охватить целую группу подкоманд.

В общей сводке команд в `/help`, подкоманды автоматически вкладываются в видимые родительские команды с отступом (например, `admin` → `admin add` с отступом на один уровень, `admin user` → `admin user ban` с отступом на два уровня).

### Права доступа и управление доступом команд

Права доступа к командам разделены на три уровня, проверяются сверху вниз (если верхний уровень отклоняет, нижний не проверяется):

```python
# ① ACL команды (пользовательская конфигурация): по белому и черному спискам пользователей для команды, при отклонении возвращается "权限不足"
# ② master=True — только владелец фреймворка может выполнять (фреймворк автоматически проверяет, при отклонении возвращается "权限不足")
@command("restart", master=True, help="Перезапустить модуль")
async def restart_handler(event):
    await event.reply("Модуль перезапущен")

# ③ permission=вызов функции — логика управления самой команды (возвращает True только для выполнения)
def is_admin(event):
    return event.get_user_id() in {"user123", "user456"}

@command("panel", permission=is_admin, help="Панель управления")
async def panel_handler(event):
    await event.reply("Добро пожаловать на панель управления")
```

**ACL пользователей команды** (`ErisPulse.event.command.acl`): пользователи могут настроить белый и черный списки для любой команды, имена команд поддерживают точное и glob-сопоставление (например, `"roll*"`), при отклонении возвращается "权限不足":

```toml
# config.toml — разрешить только 123456 выполнить restart; 666 всегда отклонять
[ErisPulse.event.command.acl.restart]
allow = ["onebot11:123456"]
deny = ["onebot11:666"]
```

Порядок проверки: если `deny` совпадает → отклонить; если `allow` не пуст и не совпадает → отклонить; если ACL не настроена, следует `event.command.default_allow` (`false` = строгий режим, без ACL — отклонить; `true` — передать разработчику по умолчанию `master=True` / `permission`). API во время выполнения (поддержка glob-имен команд):

```python
from ErisPulse.Core.Event import command

command.allow_user("restart", "onebot11", "123456")   # белый список
command.deny_user("restart", "onebot11", "666")       # черный список
command.remove_acl("restart")                          # очистить белый и черный списки
command.get_acl("restart")                             # получить текущий список
```

> Командный обработчик импортируется из пакета событий: `from ErisPulse.Core.Event import command`；
> также можно получить через пакет SDK: `sdk.Event.command` (оба являются одним и тем же экземпляром单例)。
> В модуле обычно уже импортируется вместе с декоратором команды (``from ErisPulse.Core.Event import command``)。

Кросс-командная / кросс-пользовательская **событийная** система контроля доступа (некоторые люди / группы / боты могут получать сообщения или нет)
проходит через **идентификационные** области действия (``scope.identity``)；**модульный** доступ (какие модули могут использоваться)
проходит через **модульные** области действия (``scope.platforms / bots / sessions``)。
См. [Области (scope)](../advanced/scope.md)。

> Рекомендуется: для команд, требующих взаимодействия с бизнес-логикой, использовать `master=True` / `permission`；для чистого доступа по пользователю / группе
> использовать идентификационные области; для контроля доступности модуля использовать модульные области.

### Приоритет команд

```python
# Чем больше значение приоритета, тем раньше выполняется
@message.on_message(priority=10)
async def high_priority_handler(event):
    await event.reply("Высокоприоритетный обработчик")

@message.on_message(priority=1)
async def low_priority_handler(event):
    await event.reply("Низкоприоритетный обработчик")
```

### Параллельная обработка событий

Система событий ErisPulse использует модель планирования **параллельной обработки с одинаковым приоритетом и последовательной обработки с разным приоритетом**:

```
Событие пришло
    ↓
группа priority=10: [обработчик C || обработчик D] параллельно → объединить результаты
    ↓ (если не прервано)
группа priority=0: [обработчик A || обработчик B] параллельно → объединить результаты
    ↓
...
```

- **Параллельно с одинаковым приоритетом**: обработчики с одинаковым приоритетом выполняются одновременно, повышая пропускную способность
- **Последовательно с разным приоритетом**: группы с разным приоритетом выполняются последовательно (чем больше число, тем раньше выполняется), обеспечивая выполнение обработчиков с высоким приоритетом
- **Copy-On-Write**: обработчики без изменений не создают копию, обеспечивая нулевые накладные расходы
- **Обработка конфликтов**: при изменении одного поля несколькими обработчиками с одинаковым приоритетом используется последнее значение и записывается предупреждение в лог
- **Механизм прерывания**: при вызове `event.done()` (по умолчанию) или `event.done(claim=False)` любым обработчиком, пропускаются последующие группы с низким приоритетом. Разница между присвоением и блокировкой см. ниже в разделе [Управление цепочкой: присвоение и блокировка](#управление-цепочкой-присвоение-и-блокировка)

```python
# Пример: параллельное выполнение обработчиков с одинаковым приоритетом
@message.on_message(priority=0)
async def handler_a(event):
    # Обработка задачи A
    event['result_a'] = process_a()

@message.on_message(priority=0)
async def handler_b(event):
    # Выполняется параллельно с handler_a
    event['result_b'] = process_b()

# Последовательное выполнение с разным приоритетом
@message.on_message(priority=10)
async def handler_c(event):
    # Приоритет самый высокий, выполняется первым
    pass
```

> **Лимит параллелизма**: все соответствующие обработчики задач немедленно создаются, но ограничиваются сигналом, ограничивающим **количество одновременно выполняемых задач**, по умолчанию **64** (`ErisPulse.framework.handler_max_concurrency`, поддерживает горячую перезагрузку). Задачи, превышающие лимит, ждут в очереди на сигнале, пока предыдущие не завершатся. Это ваш "сброс давления" при пике событий.
>
> **Медленный лог**: если обработчик занимает более **1 секунды**, фреймворк выводит предупреждение в лог (`handler_slow`). Время ожидания `wait_reply` исключается из времени выполнения, чтобы избежать ложного срабатывания медленного лога из-за "ожидания ответа".

## Middleware: изменение или отклонение до распределения

Middleware выполняется **до** распределения событий, последовательно, это правильное место для реализации сценариев, таких как брандмауэр, ограничение скорости, удаление конфиденциальных данных из событий:

```python
from ErisPulse.Core import adapter

@adapter.middleware
async def firewall(data):
    if _is_banned(data.get("user_id")):
        return False          # Отклонение: событие отбрасывается, не попадает ни в один обработчик, без побочных эффектов
    data["checked"] = True    # Возврат dict: изменение данных события (сохраняется совместимость с предыдущим поведением)
    # Возврат None: пропуск, данные события не изменяются (историческое поведение)
    return data
```

| Возвращаемое значение | Поведение |
|--------|------|
| `False` | **Отклонение**: событие немедленно отбрасывается, не попадает ни в один обработчик |
| `dict` | Изменение данных события и продолжение распределения |
| `None` | Пропуск, данные события не изменяются |

При отклонении фреймворк выводит трассировку TRACE и запускает хук жизненного цикла `adapter.event.blocked` (с именем middleware и полным событием), что полезно для аудита "почему событие не ответило".

## Цепочка принятия решений по распределению команд: почему команда не сработала

Сообщение команды последовательно проходит через: **проверка текста команды → сопоставление имени/алиаса команды (при несовпадении с предложением исправления) → немедленное присвоение → область действия → пользовательский ACL → владелец → права → охлаждение/ограничение скорости → анализ аргументов → выполнение**. Любое условие, не выполняющееся, приводит к остановке; при попадании в управление (охлаждение/ограничение скорости) по умолчанию тихо отбрасывается, при отказе в правах возвращается пользователю сообщение.

В тестах `ErisPulse-Testing` `dispatch()` напрямую возвращает эту цепочку решений (``DispatchTrace``, `trace.explain()` выводит построчно причинно-следственную связь), в продакшене можно использовать `ErisPulse.Core.Event.start_dispatch_trace()` для сбора такой же записи.

Кроме того, `ErisPulse.runtime` предоставляет два набора диагностических API: `explain_module(модуль)` отвечает на вопрос "почему модуль не загрузился" (не зарегистрирован / ленивая загрузка / отключена конфигурацией / отсутствуют зависимости / не удовлетворяется версия SDK, пошагово указывает причину), `explain_event(событие)` отвечает на вопрос "почему событие не ответило" (адаптер не зарегистрирован / заблокирована идентификация / сеанс модуля заблокирован / команда не сработала); с `format_report()` форматирует вывод в человекочитаемый вид.

## Фильтрация по области действия: почему мой модуль не получил сообщение

После поступления события применяются две **тихие** фильтрации (ничего не возвращают, не сообщают об ошибках):

1. **Область действия идентификации** (`ErisPulse.scope.identity`): при входе события в точку распределения проверяется, принимать ли его по пользователю > группе > боту > адаптеру.
   Отклоненные **все события** немедленно отбрасываются, и ни один обработчик (включая диспетчер команд) не будет запущен.
2. **Область действия модуля** (`ErisPulse.scope`): при поступлении события в обработчик/команду модуля проверяется, доступен ли модуль, **если нет, то тихо пропускается**.

```toml
# Пример 1: все сообщения в группе не распространяются
[ErisPulse.scope.identity.sessions.onebot11."group_123"]
deny = true

# Пример 2: блокировка MyModule для определенного бота
[ErisPulse.scope.bots.onebot11."123456"]
blocked = ["MyModule"]
```

В этом случае сообщения в этой группе, поступающие, `MyModule` не будет вызван ни один обработчик команды или события. Это не ошибка, а механизм фильтрации — при диагностике "модуль не реагирует" в первую очередь проверяйте области действия идентификации и модуля.

- Логи фильтрации видны только на уровне **TRACE** (`core.scope.identity_denied` / `core.scope.denied`), по умолчанию на уровне INFO ничего не видно
- Обработчики фреймворка (например, диспетчер команд `scope_exempt=True`) не подвержены влиянию **области действия модуля**, но подвержены влиянию **области действия идентификации** (все событие уже отброшено)
- Перед выполнением команды есть третья проверка: пользовательский ACL (при отклонении возвращается "权限不足", см. предыдущий раздел)
- Четвертая проверка — **перезапись событий** (см. следующий раздел)

> [!NOTE]
> **Отношение между фильтрацией области действия и присвоением (claim)**: обе тихие фильтрации происходят **до** распределения обработчиков — отфильтрованные обработчики не имеют возможности выполниться, следовательно, не участвуют в состоянии `event.done()` / `mark_processed()`. Было ли событие присвоено, определяется **фактически выполненным** обработчиком (присвоение команды, присвоение ответа, явный вызов); фильтрация области действия сама по себе не присваивает и не блокирует (тихо пропускает, сообщение продолжает проходить оставшуюся цепочку распределения).

> Конфигурация области действия, сопоставление, API во время выполнения см. [Области (scope)](../../advanced/scope.md)。

## Перезапись событий: без изменения кода модуля, перезаписать поведение любого типа событий

> [!NOTE]
> Эта функция требует ErisPulse **2.8.0+**.

Параметры, декларированные при регистрации обработчиков событий (pattern / regex / master / hidden и т.д.), являются **по умолчанию для разработчика**.
Система универсальной перезаписи позволяет пользователям перезаписывать поведение любого модуля по типу события — OneBot12 стандартные типы (meta / message / notice / request) и расширенные типы ErisPulse (command) имеют свои собственные перезаписываемые параметры:

| Тип события | Перезаписываемые параметры | Действие |
|---------|-----------|------|
| `message` | `pattern` / `regex` / `detail_types` | Условия срабатывания текста + белый список подтипов сообщения |
| `notice` | `detail_types` / `pattern` / `regex` | Белый список подтипов уведомления + текстовые условия |
| `request` | `detail_types` / `pattern` / `regex` | Белый список подтипов запроса + текстовые условия |
| `meta` | `detail_types` | Белый список подтипов мета-события (connect / heartbeat и т.д.) |
| `command` | `master` / `hidden` / `aliases` / `prefix` / `help` / `usage` | Параметры реализации команды (приоритет для пользователя) |
| `acl` (специфично для command) | `allow` / `deny` | Белый и черный списки пользователей команды (по имени команды с помощью glob) |

```toml
# message: перезаписать условия срабатывания текста (и условия в коде AND)
[ErisPulse.event.overrides.message.ChatModule]
pattern = "闲聊*"

# notice: только определенные подтипы уведомления
[ErisPulse.event.overrides.notice.MyModule]
detail_types = ["group_increase"]

# command: перезаписать параметры реализации (приоритет для пользователя — можно усилить или ослабить настройки разработчика)
[ErisPulse.event.overrides.command.MyModule.restart]
master = true
hidden = true

# acl: черно-белые списки пользователей команды (по glob-именам команд)
[ErisPulse.event.overrides.acl."roll*"]
allow = ["onebot11:u_vip"]

# ACL по умолчанию (false = строгий режим: без ACL — отклонить)
acl_default_allow = true
```

API во время выполнения (``from ErisPulse.Core.Event import overrides`` или `sdk.Event.overrides`，
**типовая иерархия подпространств** — для каждого типа симметричный набор `set` / `get` / `delete`):

```python
from ErisPulse.Core.Event import overrides

overrides.message.set("ChatModule", pattern="闲聊*")   # условия текста для message
overrides.notice.set("MyModule", detail_types=["group_increase"])
overrides.command.set("MyModule", "restart", master=True)  # параметры команды
overrides.acl.set("roll*", deny=["onebot11:u_bad"])    # черный список пользователей команды

overrides.message.get("ChatModule")     # {"pattern": "闲聊*"}
overrides.message.delete("ChatModule")  # восстановить настройки разработчика
```

- Условия перезаписи и условия в коде обработчика **одновременно действуют** (логическое И); параметры `command` и декларации разработчика **глубоко объединяются** (приоритет перезаписи)
- `detail_types`: событие без `detail_type` проходит (не убивает неизвестные события)
- `pattern` / `regex`: события без текста (connect / heartbeat и т.д.) не подпадают под ограничения, сразу проходят
- `command` ключ перезаписи `master` синхронно отображается в ключ хранения `must_master`；отключение команды проходит через `acl` deny
- **Отображение ключей**: `overrides.command.set("My", "restart", master=True)` параметр `master` является просто псевдонимом конфигурации, фактический ключ хранения и ключ возвращаемого значения `get()` унифицированы как **`must_master`** (возвращаемое значение `get()` — `{"must_master": true}`) — при чтении во время выполнения используется ключ хранения, не используйте ключ `master` для чтения
- Изменения конфигурации вступают в силу немедленно (горячая перезагрузка), проверка формата предупреждает (неизвестные параметры / плохие записи игнорируются)

## Управление цепочкой: присвоение и блокировка

> [!NOTE]
> Параметры `event.done()` / `event.mark_processed()` `claim=` / `stop=` для этой функции требуют ErisPulse **2.7.1+**.

ErisPulse разделяет понятия "присвоение" и "блокировка" и объединяет их с помощью `event.done()`, что удобно для добавления слоев наблюдения, таких как логирование, аудит, права доступа, вокруг обработки команд.

**Точное определение двух понятий:**

- **Присвоение (claim)**: пометить событие как обработанное данным обработчиком (записать `_processed`). Диспетчер команд, увидев присвоенное событие, **пропустит** его — предотвращает повторную обработку одного и того же сообщения несколькими обработчиками команд. Типичный сценарий: после успешного сопоставления команды присвоить, чтобы диспетчер команд больше не вмешивался.
- **Блокировка (stop)**: предотвратить распространение события на **менее приоритетные** обработчики (записать `_propagation_stopped`). Обработчики с низким приоритетом больше не увидят это событие. Типичный сценарий: высокоприоритетный обработчик полностью обработал событие, не хочет, чтобы низкоприоритетные обработчики выполнялись.

| `event.done(...)` | Присвоение | Блокировка | Сценарий |
|-------------------|------|------|------|
| `event.done()` | ✔ | ✔ | Стандартная практика завершения команды / обработчика |
| `event.done(stop=False)` | ✔ | ✘ | Только присвоение: низкоприоритетные наблюдатели (логи / статистика) продолжают видеть |
| `event.done(claim=False)` | ✘ | ✔ | Только блокировка (например, брандмауэр / ограничение скорости), но не делает дублирование |

`event.done(claim=, stop=)` является псевдонимом `event.mark_processed(claim=, stop=)`, параметры и поведение полностью идентичны.

```python
@command("help")
async def help_cmd(event):
    event.done()            # Присвоение + блокировка (стандартная практика завершения команды)

@message.on_message(priority=50)
async def observer(event):
    event.done(stop=False)  # Только присвоение: низкоприоритетные обработчики продолжают выполняться (логи / статистика)

@message.on_message(priority=100)
async def firewall(event):
    if denied(event):
        event.done(claim=False)  # Только блокировка: низкоприоритетные обработчики не выполняются, но не делает дублирование
```

### Настройки block для команд и ответов

**Присвоение при срабатывании команды**: сообщение, как только оно сопоставляется с зарегистрированным именем команды (включая подкоманды/алиасы), независимо от последующих проверок области действия или прав, будет присвоено и по умолчанию заблокировано — команда, отклоненная правами, больше не будет передана низкоприоритетным обработчикам сообщений (устраняет "повторное срабатывание" после того, как команда отклонена и `on_message` срабатывает еще раз).

Можно настроить, чтобы разрешить блокировку, чтобы низкоприоритетные наблюдатели (логи / аудит / права) все еще могли видеть эти сообщения:

```toml
[ErisPulse.event.command]
block = false   # Сообщения команд продолжают попадать в низкоприоритетные обработчики (присвоение не влияет, дублирование не будет повторяться)

[ErisPulse.event.wait_reply]
block = false   # Ответы, потребленные wait_reply, продолжают попадать в низкоприоритетные обработчики
```

> Примечание: `block` контролирует только **блокировку** (stop), не влияет на **присвоение** (claim) — команда, сработавшая, никогда не будет повторно потреблена обработчиком сообщений; сообщения, не сработавшие ни на одну команду, по-прежнему попадают в обработчик сообщений.

```python
@notice.on_friend_add()
async def friend_add_handler(event):
```

### Увеличение участников группы


## Интерактивная обработка

### Использование метода reply для отправки ответа

Метод `event.reply()` поддерживает различные параметры модификации, удобные для отправки сообщений с упоминанием, ответом и т.д.:

```python
# Простой ответ
await event.reply("你好")

# Отправка сообщений разных типов
await event.reply("http://example.com/image.jpg", method="Image")  # изображение
await event.reply("http://example.com/voice.mp3", method="Voice")  # голос

# Упоминание одного пользователя
await event.reply("你好", at_users=["user123"])

# Упоминание нескольких пользователей
await event.reply("大家好", at_users=["user1", "user2", "user3"])

# Ответ на сообщение
await event.reply("回复内容", reply_to="msg_id")

# Упоминание всех пользователей
await event.reply("公告", at_all=True)

# Комбинирование: упоминание пользователей + ответ на сообщение
await event.reply("内容", at_users=["user1"], reply_to="msg_id")
```

### Ожидание ответа пользователя

```python
@command("ask", help="询问用户")
async def ask_handler(event):
    await event.reply("请输入你的名字:")
    
    # Ожидание ответа пользователя, таймаут 30 секунд
    reply = await event.wait_reply(timeout=30)
    
    if reply:
        name = reply.get_text()
        await event.reply(f"你好，{name}！")
    else:
        await event.reply("等待超时，请重新输入。")
```

> [!TIP]
> **Во время ожидания команды все еще доступны** (2.8.3+): сообщения, начинающиеся с префикса команды и соответствующие уже зарегистрированной команде (например, `/cancel`), будут **выполнены как команда**, а не как содержимое ответа, ожидание продолжает оставаться — пользователь может в любой момент отменить/переключить, команда выполнится, и можно продолжить ответ. Для старого поведения, когда "ожидание поглощает весь текст", можно настроить `ErisPulse.event.wait_reply.cmdpass = true`, или однократно `wait_reply(cmdpass=True)`.

### Ожидание с проверкой

```python
@command("age", help="询问 возраст")
async def age_handler(event):
    def validate_age(event_data):
        """Проверка возраста на корректность"""
        try:
            age = int(event_data.get_text())
            return 0 <= age <= 150
        except ValueError:
            return False
    
    await event.reply("请输入你的 возраст (0-150):")
    
    reply = await event.wait_reply(
        timeout=60,
        validator=validate_age
    )
    
    if reply:
        age = int(reply.get_text())
        await event.reply(f"你的 возраст是 {age} 岁")
    else:
        await event.reply("输入无效或超时")
```

### Ожидание с обратным вызовом

```python
@command("confirm", help="确认 действие")
async def confirm_handler(event):
    async def handle_confirmation(reply_event):
        text = reply_event.get_text().lower()
        
        if text in ["是", "yes", "y"]:
            await event.reply("操作已确认！")
        else:

    )
```

### Подтверждение диалога (confirm)

Ожидание подтверждения или отрицания пользователя, автоматически распознает встроенные слова подтверждения на китайском и английском:

```python
@command("confirm", help="确认操作")
async def confirm_handler(event):
    if await event.confirm("确定要执行此操作吗？"):
        await event.reply("已确认，执行中...")
    else:
        await event.reply("已取消")

# Пользовательские слова подтверждения
if await event.confirm("继续吗？", yes_words={"go", "继续"}, no_words={"stop", "停止"}):
    pass
```

### Выбор меню (choose)

Пользователь может ответить номером опции или текстом опции:

```python
@command("choose", help="选择")
async def choose_handler(event):
    choice = await event.choose(
        "请选择颜色：",
        ["红色", "绿色", "蓝色"]
    )
    
    if choice is not None:
        colors = ["红色", "绿色", "蓝色"]
        await event.reply(f"你选择了：{colors[choice]}")
    else:
        await event.reply("超时未选择")
```

**Слияние режима**: `merge_prompt=True` при объединении опций в одно сообщение с использованием заданного `method`:

```python
# Отправка объединенного сообщения с опциями в Markdown
choice = await event.choose(
    "## 请选择颜色\n{options}\n请回复编号",
    ["红色", "绿色", "蓝色"],
    method="Markdown",
    merge_prompt=True,
)
```

> `{options}` — метка для вставки опций; если не указана, добавляется в конец prompt. Можно использовать `placeholder` для кастомизации метки (например, `placeholder="[choices]"`).
> `options_format="auto"` (по умолчанию) автоматически выбирает стиль в зависимости от method: Markdown → неперечисленный список, Html → перечисленный список, другие → текстовый список.
> Для текстовых методов (Text/Markdown/Html и т.д.) по умолчанию объединяются опции в конец; для не текстовых методов (Image и т.д.) по умолчанию разделяются на две сообщения.

### Сбор анкеты (collect)

Сбор ввода пользователя в несколько шагов:

```python
@command("register", help="注册")
async def register_handler(event):
    data = await event.collect([
        {"key": "name", "prompt": "请输入姓名："},
        {"key": "age", "prompt": "请输入年龄：", 
         "validator": lambda e: e.get_text().isdigit()},
        {"key": "email", "prompt": "请输入邮箱："}
    ])
    
    if data:
        await event.reply(f"注册成功！\n姓名：{data['name']}\n年龄：{data['age']}\n邮箱：{data['email']}")
    else:
        await event.reply("注册超时或输入无效")
```

### Ожидание произвольного события (wait_for)

Ожидание события, удовлетворяющего условиям, не ограничено одним пользователем:

```python
@command("wait_member", help="等待新成员")
async def wait_member_handler(event):
    await event.reply("等待群成员加入...")
    
    evt = await event.wait_for(
        event_type="notice",
        condition=lambda e: e.get_detail_type() == "group_member_increase",
        timeout=120
    )
    
    if evt:
        await event.reply(f"欢迎新成员：{evt.get_user_id()}")
    else:
        await event.reply("等待超时")
```

### Многоэтапный диалог (conversation)

Создание интерактивного многоэтапного диалогового контекста:

```python
@command("survey", help="问卷调查")
async def survey_handler(event):
    conv = event.conversation(timeout=60)
    
    await conv.say("欢迎参与问卷调查！")
    
    while conv.is_active:
        reply = await conv.wait()
        
        if reply is None:
            await conv.say("对话超时，再见！")
            break
        
        text = reply.get_text()
        
        if text == "退出":
            await conv.say("再见！")
            break
        
        await conv.say(f"你说了：{text}，继续输入或回复'退出'结束")
```

### Встроенные слова подтверждения

ErisPulse включает в себя встроенные наборы слов подтверждения на китайском и английском:

- **Слова подтверждения** (`CONFIRM_YES_WORDS`): 是、yes、y、确认、确定、好、好的、ok、true、对、嗯、行、同意、没问题...
- **Слова отрицания** (`CONFIRM_NO_WORDS`): 否、no、n、取消、不、不要、不行、cancel、false、错、拒绝、不可以...

### Платформенные расширения

```python
from ErisPulse.Core.Event import message

@message.on_message()
async def handle_message(event):
    platform = event.get_platform()

    # Вызов платформенно-специфичных методов в зависимости от платформы
    if platform == "telegram":
        chat_type = event.get_chat_type()      # Telegram специфичный метод
    elif platform == "email":
        subject = event.get_subject()           # Email специфичный метод
```

Если неизвестно, зарегистрирован ли метод для платформы, можно запросить, какие методы зарегистрированы для определенной платформы:

```python
from ErisPulse.Core.Event import get_platform_event_methods

methods = get_platform_event_methods("telegram")
```

## Лучшие практики обработки событий

### 1. Обработка исключений

```python
@command("process")
async def process_handler(event):
    try:
        # бизнес-логика
        result = await do_some_work()
        await event.reply(f"Результат: {result}")
    except ValueError as e:
        # ожидаемая бизнес-ошибка
        await event.reply(f"Ошибка параметров: {e}")
    except Exception as e:
        # неожиданная ошибка
        sdk.logger.error(f"Обработка не удалась: {e}")
        await event.reply("Обработка не удалась, пожалуйста, попробуйте позже")
```

### 2. Логирование

```python
@message.on_message()
async def message_handler(event):

    sdk.logger.info(f"Обработка сообщения: {user_id} - {text}")

```

### 3. Условная обработка

```python
@message.on_message(priority=0)
async def conditional_handler(event):
    """Условная обработка - проверка внутри обработчика"""
    # Обрабатывать только сообщения определенного пользователя

    await event.reply("Условие выполнено, обработка сообщения")
```
