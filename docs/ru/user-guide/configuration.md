# Конфигурационный файл
> Этот документ описывает конфигурационный файл фреймворка. Если у стороннего модуля есть конфигурация, обратитесь к документации модуля.

ErisPulse использует конфигурационный файл в формате TOML `config/config.toml` для управления конфигурацией проекта.

## Позиция конфигурационного файла

Конфигурационный файл находится в папке `config/` в корне проекта:

```
project/
├── config/
│   └── config.toml
├── main.py
```

### Подсказка по нескольким экземплярам и файлу блокировки

При запуске фреймворка в папке `config/` создается файл блокировки `.erispulse_config.lock`, который удерживается до выхода процесса (используется для обнаружения нескольких экземпляров, использующих одну и ту же папку конфигурации). Если в журнале появляется предупреждение «Обнаружено, что конфигурационный файл, возможно, используется другим экземпляром ErisPulse», означает, что **два или более процессов ErisPulse записывают в один и тот же файл конфигурации** (типичный сценарий: несколько контейнеров монтируют одну и ту же папку `config/` хоста) — одновременная запись будет перезаписывать друг друга. Используйте отдельную папку конфигурации для каждого экземпляра.

## Обработка ошибок загрузки конфигурации

Фреймворк при загрузке `config.toml` различает три состояния ошибок и предоставляет **действенные диагностические сообщения**, а не просто возвращает к настройкам по умолчанию:

| Состояние ошибки | Условия срабатывания | Поведение фреймворка |
|---------|---------|---------|
| Файл отсутствует | `config.toml` не существует | Нормальный запуск, пустая конфигурация (без предупреждений) |
| Синтаксическая ошибка TOML | Файл существует, но формат неправильный (например, отсутствуют кавычки, не закрыты скобки) | Выводит **номер строки/столбца и причину ошибки**, и **сохраняет предыдущую действительную конфигурацию** для продолжения работы (изменения в файле не вступают в силу) |
| Ошибка прав доступа и другие | Нет прав на чтение, ошибки ввода-вывода и т.д. | Выводит **ясную причину**, и **сохраняет предыдущую действительную конфигурацию** для продолжения работы |

> **Важно:** «Предыдущая действительная конфигурация» ≠ «Конфигурация по умолчанию»: при повреждении файла фреймворк использует **последнюю успешно распарсенную конфигурацию** (при изменении файла во время работы используется старое значение), а не сбрасывает все параметры на заводские. При устранении неисправностей не предполагайте, что «конфигурация была сброшена».

Например, если вы случайно написали `port = 8000` (без кавычек для строки), журнал выведет примерно следующее:

```
[ERROR] [Config] Синтаксическая ошибка в конфигурационном файле config/config.toml (строка 3, столбец 1): ...
[WARNING] [Config] Не удалось прочитать конфигурационный файл. Продолжение работы с предыдущей действительной конфигурацией, изменения в файле не вступили в силу — пожалуйста, исправьте файл и перезагрузите или перезапустите
```

Таким образом, вы можете сразу определить проблему на уровне `INFO`, а не задаваться вопросом «почему мои изменения не вступили в силу».

> **Изменение конфигурационного файла во время работы?** Если вы вручную редактируете `config.toml` во время работы робота и вносите синтаксическую ошибку, фреймворк при следующей записи (объединении конфигурации) выведет «Конфигурационный файл поврежден (синтаксическая ошибка, строка X), невозможно записать — пожалуйста, сначала исправьте конфигурационный файл и перезапустите», а не запутанное «Запись не удалась». Записываемые параметры сохраняются, не теряются.

## Сохранение комментариев и минимизация записи

Комментарии и порядок ключей в `config.toml` **полностью сохраняются** при записи фреймворком: будь то `setConfig()`, сохранение через конфигурационный помощник CLI или генерация шаблона конфигурации адаптером/модулем, фреймворк изменяет только соответствующие ключи, ваши комментарии и порядок не будут стерты или перестроены (на основе сохранения комментариев tomlkit).

Фреймворк сдержан в записи:

- **Настройки по умолчанию не записываются автоматически**: `gc`, `scope`, `transcript` и другие встроенные значения хранятся только в памяти, `config.toml` содержит только явно заданные ключи, сохраняя минимальное количество. Полный список настраиваемых параметров см. в `config/config.full.example` проекта, скопируйте его в `config.toml` и измените по мере необходимости (не настроенные параметры по-прежнему используют встроенные значения по умолчанию, поведение не меняется).
- **Автоматическое обслуживание `config.full.example`**: Независимо от того, выполняли ли вы `epsdk init`, при запуске фреймворка (через `epsdk run` / `main.py`) файл `config/config.full.example` автоматически генерируется, если он отсутствует. В первой строке находится метка, управляемая фреймворком; при обновлении генератора (например, при добавлении новых конфигурационных параметров, при установке новых компонентов) файл обновляется при запуске; удаление/изменение первой строки означает, что файл теперь контролируется вручную, и фреймворк больше не перезаписывает его.
- **Шаблоны конфигурации адаптеров/модулей**: При первом инициализации шаблон с комментариями сохраняется на диск (описание полей — это комментарии); поля, помеченные как `example`, не сохраняются на диск, а только записываются в `config.full.example` для справки.

## Переменные окружения

Фреймворк поддерживает **переопределение** конфигурационных параметров `ErisPulse.*` с помощью переменных окружения (подходит для Docker / контейнеризации / CI-развертывания, без необходимости изменения `config.toml`).

Правила именования: замените точечный путь `ErisPulse.<section>.<key>` на все заглавные буквы, замените `.` на `_` и добавьте префикс `ERISPULSE_`:

| Параметр | Переменная окружения | Пример значения |
|--------|---------|--------|
| `ErisPulse.server.port` | `ERISPULSE_SERVER_PORT` | `9000` |
| `ErisPulse.server.host` | `ERISPULSE_SERVER_HOST` | `0.0.0.0` |
| `ErisPulse.logger.level` | `ERISPULSE_LOGGER_LEVEL` | `DEBUG` |
| `ErisPulse.framework.strict_mode` | `ERISPULSE_FRAMEWORK_STRICT_MODE` | `false` |

Описание поведения:
- **Наивысший приоритет**: Переменные окружения переопределяют «конфигурационный файл» и «значения по умолчанию», автоматически преобразуются по типу (bool / int / float / список, разделенный запятыми / строка)
- **Не сохраняются**: Переопределение действует только в процессе выполнения, не записывается обратно в `config.toml`
- **Поддержка горячей перезагрузки**: После изменения переменной окружения во время работы, в сочетании с перезагрузкой конфигурации, изменения вступают в силу

```bash
# Пример развертывания с Docker: без изменения config.toml, просто переопределение порта
ERISPULSE_SERVER_PORT=9000 docker compose up -d
```

> Примечание: `ErisPulse.server.port` и другие конфигурационные параметры фреймворка, читаемые через `get_server_config()` и другие API, подвержены влиянию переменных окружения.

### Связывание переменных окружения с конфигурацией модуля (2.9.0+)

Конфигурационные параметры модуля, объявленные декларативно (`ConfigClass`), поддерживают привязку переменных окружения на уровне полей — в `field(metadata=...)` объявите `env`:

```python
@dataclass
class MyConfig(BaseConfig):
    api_key: str = field(default="", metadata={
        "description": "API ключ",
        "env": "MYMODULE_API_KEY",   # привязка к переменной окружения
    })
    retries: int = field(default=3, metadata={"env": "MYMODULE_RETRIES"})
```

Описание поведения:

- **Приоритет**: переменная окружения > `config.toml` > значение по умолчанию (конфигурация горячей перезагрузки сохраняет этот приоритет)
- **Тип преобразования**: значение переменной окружения автоматически преобразуется по аннотации поля — `str` останется без изменений, `int` / `float` / `bool` (`true` / `1` / `yes` / `on`) автоматически преобразуются, `list` / `dict` парсятся через JSON; при неудачном преобразовании переопределение игнорируется (возвращается конфигурация файла / значение по умолчанию) и выводится предупреждение
- **Одно объявление — везде**: конфигурация, горячая перезагрузка, проверка используют один и тот же канал; схема конфигурационной панели помечает `env` имя, комментарии в шаблоне config.toml также указывают доступные переменные окружения (шаблон не записывает фактические значения переменных окружения, чтобы избежать утечки)
- **Полная совместимость**: поведение полей, не объявленных с `env`, не меняется; прямая инициализация ConfigClass (без использования конфигурационного канала фреймворка) не подвержена влиянию переменных окружения

```bash
# Пример развертывания с Docker: без изменения config.toml, просто вставьте ключ модуля
MYMODULE_API_KEY=sk-xxx docker compose up -d
```

> **Конфигурационный класс или модель полей?** Конфигурационный класс управляет «как модуль работает» (параметры поведения, горячая перезагрузка), `ORM` `Field()` управляет «какие данные создал пользователь» (таблица базы данных, запросы). Оба используют одну и ту же систему ограничений и движок проверки; таблица сравнения доступна в [Слое модели данных · Когда использовать какой тип объявления](../developer-guide/orm.md#когда-использовать-какой-тип-объявления).

## Горячая перезагрузка конфигурации

Начиная с версии 2.7.0, фреймворк систематически поддерживает горячую перезагрузку конфигурации. После внешнего изменения `config.toml` (фоновый watcher каждые 5 секунд обнаруживает изменения) или вызова кодом `setConfig()`, компоненты автоматически реагируют:

| Компонент | Поддерживаемые конфигурации | Поведение |
|------|----------------|------|
| **Logger** | `logger.level` / `log_files` / `log_dir` (включая параметры сегментации) / `memory_limit` / `format` / `exclude_levels` | Автоматически переприменяются (с обнаружением изменений) |
| **CommandHandler** | `event.command.prefix` / `case_sensitive` / `allow_space_prefix` / `must_at_bot` | Вступают в силу с следующего сообщения |
| **Адаптеры (параллелизм)** | `framework.handler_max_concurrency` | Сигнал об отключении кэша, по новому значению перестраивается |
| **Активный GC** | `framework.proactive_gc_*` | Изменения конфигурации немедленно перезапускают задачи GC, поддерживают изменение/отключение/переактивацию во время выполнения |
| **Система владельцев** | `master.users` | Каждый вызов `is_master()` проверяет актуальные данные, без перезапуска |
| **Конфигурации модулей/адаптеров** | их собственные конфигурационные параметры | Вызывается `on_config_update(old, new)`回调 |

**Конфигурации, требующие перезапуска** (небезопасно переключать во время выполнения, при изменении выводится предупреждение «Требуется перезапуск процесса»):

| Конфигурация | Причина |
|------|------|
| `router.cors.*` / `router.security.*` | Промежуточные слои записываются в FastAPI при запуске службы, безопасное горячее переключение во время выполнения невозможно |
| `storage.use_global_db` | Файловый дескриптор SQLite уже открыт во время выполнения, безопасная смена пути невозможна |

> **Ошибка при редактировании?** Если при редактировании `config.toml` возникает временная синтаксическая ошибка, фреймворк **сохраняет последнюю действительную конфигурацию** и выводит диагностическое сообщение, не распространяя пустую конфигурацию на компоненты (чтобы избежать `on_config_update` получения пустых значений и возврата к значению по умолчанию).

### Внутреннее разбиение цепочки горячей перезагрузки

«Как компоненты узнают, что конфигурация изменилась?» — за этим стоит цепочка обнаружения → перезагрузки → рассылки:

```mermaid
flowchart TD
    A["Внешнее редактирование config.toml"] --> B{"Кто первым узнает?"}
    B -->|"Фоновый поток-наблюдатель<br/>каждые 5 секунд опрашивает mtime"| C["_check_file_change определяет изменение"]
    B -->|"При чтении конфигурации<br/>кэш старше 60 секунд"| C
    C --> D["_load_config повторно парсит TOML"]
    D --> E{"Удалось ли парсинг?"}
    E -->|"Нет (синтаксическая ошибка)"| F["Сохраняет последнюю действительную конфигурацию<br/>не рассылает, выводит диагностическое сообщение"]
    E -->|"Да"| G["lifecycle.emit config.updated<br/>содержит old_config / new_config"]
    G --> H["Слушатели компонентов реагируют<br/>（logger / scope / command / GC ...）"]
```

**Две пути обнаружения** (достаточно одного, оба могут обеспечить):

| Путь | Механизм | Время срабатывания |
|------|------|---------|
| Фоновый наблюдатель | демон-поток `config-watcher` каждые **5 секунд** `wait` опрашивает `mtime` файла | максимум через 5 секунд после изменения файла |
| Ленивое обнаружение | при любом `getConfig()` чтении, если кэш старше **60 секунд**, сначала проверяет файл | при следующем чтении конфигурации |

> **Фреймворк не повредит сам себя**: `setConfig()` при записи файла сохраняет «mtime, записанное самим», watcher при сравнении исключает его, рассматривая как изменение только **внешние редакции**.

**Два типа событий изменения конфигурации:**

| Событие | Инициатор | Данные | Типичный сценарий |
|------|--------|------|---------|
| `config.set` | код / Dashboard вызывает `setConfig()` | `{key, old_value, new_value}` | одиночное значение (генерация шаблона, запись состояния, изменение конфигурации во время выполнения) |
| `config.updated` | внешнее редактирование после обнаружения watcher/ленячего обнаружения | `{old_config, new_config, config_file}` | ручное изменение `config.toml` |

> `setConfig()` по умолчанию **задерживает запись на диск на 5 секунд** (объединяет несколько записей), `immediate=True` — немедленно. watcher, обнаружив внешнее изменение, обновляет только кэш в памяти, **не перезаписывает** изменения в файл.

**Список компонентов-подписчиков** (оба события обычно подписываются, реакция одинаковая):

| Компонент | Подписка | Реакция |
|------|------|------|
| Logger | `config.set` + `config.updated` | уровень/файлы/каталог сегментации/память лимит/формат/уровни исключения переприменяются (с обнаружением изменений, без изменений — не трогать) |
| Scope | `config.updated` | перестраивается кэш привязки области |
| Система команд | `config.updated` | параметры префикса/регистра/пробел префикса/must_at_bot пересчитываются, вступают в силу с следующего сообщения |
| Адаптеры (параллелизм) | `config.set` + `config.updated` | `handler_max_concurrency` сигнал об отключении перестраивается семафор |
| Активный GC | `config.set` + `config.updated` | `proactive_gc_*` немедленно перезапускает фоновую задачу GC |
| Адаптеры | маршрутизация в `on_config_update` |回调 `on_config_update(old, new)` каждого адаптера |
| Модули | маршрутизация в `on_config_update` |回调 `on_config_update(old, new)` каждого модуля |
| Хранилище | `config.updated` | `use_global_db` изменение **только предупреждение** (требуется перезапуск) |
| Роутер | `config.updated` | `cors.*` / `security.*` изменение **только предупреждение** (требуется перезапуск) |


## API чтения и удаления конфигурации

### getAllConfig: полный снимок конфигурации

Вместо прямого чтения приватного `_cache` (чтение приватных свойств не защищено обратной совместимостью):

```python
config = sdk.config.getAllConfig()     # глубокая копия снимка, изменение на месте не влияет на состояние фреймворка
config["ErisPulse"]["server"]["port"]
```

Вид с точки зрения `getConfig` одинаков: все `setConfig` / `delete` отложенные записи уже отражены, строго согласованы с содержимым файла после отложенной записи.

### delConfig: удаление ключа конфигурации

`setConfig(key, None)` просто устанавливает пустое значение, ключ остается в файле; `delConfig` удаляет ключ из файла **полностью**:

```python
sdk.config.delConfig("ErisPulse.modules.status.OldModule")            # отложенная запись
sdk.config.delConfig("OneBot.deprecated_key", immediate=True)         # немедленная запись
```

- Поддерживает точечные пути; возвращает `False`, если ключ не существует
- Запись проходит через путь сохранения комментариев, остальное содержимое и порядок файла не изменяются
- Повторно использует событие `config.set` (с `new_value=None`): существующие слушатели адаптеров / модулей `on_config_update` и т.д. без изменений могут воспринимать удаление

## Полный пример конфигурации

```toml
[ErisPulse.server]
host = "0.0.0.0"
port = 8000
auto_start = true
ssl_certfile = ""
ssl_keyfile = ""

[ErisPulse.master]
# users поддерживает два способа записи (выберите один):
#   глобальный владелец (действует на всех платформах): users = ["123456", "789012"]
#   владелец по платформе: users = { yunhu = ["123456"], telegram = ["789012"] }
users = {}

[ErisPulse.logger]
level = "INFO"
format = "rich"
log_files = []
log_dir = ""
log_rotation = "size"
log_max_size_mb = 10
log_backup_count = 5
log_rotation_when = "midnight"
memory_limit = 1000
exclude_levels = []

[ErisPulse.framework]
enable_lazy_loading = true
uninit_timeout = 30
strict_mode = 0

[ErisPulse.framework.strict_mode_exceptions]
modules = []
adapters = []

[ErisPulse.storage]
backend = "sqlite"
use_global_db = false

[ErisPulse.event.command]
prefix = "/"
case_sensitive = true
allow_space_prefix = false
must_at_bot = false

[ErisPulse.event.message]
ignore_self = true

[ErisPulse.i18n]
language = "auto"
```

## Конфигурация сервера

```toml
[ErisPulse.server]
host = "0.0.0.0"
port = 8000
auto_start = true
ssl_certfile = "/path/to/cert.pem"
ssl_keyfile = "/path/to/key.pem"
# В сценариях контейнера / без монтирования файлов можно встроить PEM содержимое (приоритет над certfile/keyfile путями)
# ssl_cert = """-----BEGIN CERTIFICATE-----
# ...
# -----END CERTIFICATE-----"""
# ssl_key = """-----BEGIN PRIVATE KEY-----
# ...
# -----END PRIVATE KEY-----"""
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| host | string | 0.0.0.0 | Адрес прослушивания, 0.0.0.0 означает все интерфейсы |
| port | integer | 8000 | Номер порта прослушивания |
| auto_start | boolean | true | Автоматически запускать сервер маршрутизации при `sdk.init()`? Установите в `false`, чтобы пропустить запуск сервера маршрутизации (чистый сценарий событий/без WebUI) |
| ssl_certfile | string | пустая строка | Путь к файлу сертификата SSL |
| ssl_keyfile | string | пустая строка | Путь к файлу приватного ключа SSL |
| ssl_cert | string | пустая строка | **Встроенное содержимое PEM сертификата** (не путь). При совместном использовании с `ssl_key` имеет приоритет над `ssl_certfile`/`ssl_keyfile` путями; фреймворк временно сохраняет и удаляет временный файл при создании SSL-контекста |
| ssl_key | string | пустая строка | **Встроенное содержимое PEM приватного ключа** (не путь), смысл тот же |

> **Занятый порт не является фатальной ошибкой**: при запуске, если обнаруживается, что `port` уже занят, фреймворк пропускает запуск сервера маршрутизации и выдает предупреждение, **адаптеры и модули продолжают работать** (только HTTP/WS/SSE маршрутизация и WebUI недоступны). При диагностике «робот запущен, но WebUI не открывается» сначала проверьте порт.

## Конфигурация системы владельцев

Система владельцев используется для идентификации «владельца» (например, администратора бота). `master.users` поддерживает два способа записи:

```toml
[ErisPulse.master]
# Способ 1: глобальный владелец (действует на всех платформах)
users = ["123456", "789012"]

# Способ 2: владелец по платформе (dict)
# users = { yunhu = ["123456"], telegram = ["789012"] }
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| users | array / object | пустой | Список владельцев. `list` форма — глобальный владелец (действует на всех платформах); `dict` форма — по платформе (ключ — имя платформы, значение — список владельцев на этой платформе) |

В коде проверка через `master.is_master(event)` или `master.is_master(platform, user_id)` выполняется каждый раз в реальном времени (поддерживает горячую перезагрузку, перезапуск не требуется):

```python
from ErisPulse.Core import master

if master.is_master(event):
    await event.reply("Привет, хозяин")
```

### Цепочка проверки и добавление удаление во время выполнения

Цепочка проверки владельца: **конфигурационный владелец → запись во время выполнения → провайдер цепочки**:

```python
from ErisPulse.Core import master

master.is_master(event)                      # проверка по событию
master.is_master("yunhu", "123")             # явная проверка
master.add("yunhu", "123")                   # добавление во время выполнения (по умолчанию сохраняется; persist=False только в памяти)
master.remove("yunhu", "123")                # удаление (по умолчанию сохраняется)
master.list()                                # сборка: {"global": [...], "<platform>": [...]}
```

### Пользовательские источники идентификации (провайдеры)

Помимо конфигурации, можно зарегистрировать пользовательские источники идентификации: `fn(platform, user_id) -> bool`, встроенные источники идентификации (конфигурация + запись во время выполнения) не срабатывают, поочередно проверяются, если один провайдер разрешает, считается владельцем.
Подходит для подключения администраторских интерфейсов адаптеров, ролей базы данных и других внешних систем идентификации.

Входная точка `master.provider` поддерживает два способа: декоратор и функциональный, удаление — через `fn.unregister()` зарегистрированной функции:

```python
from ErisPulse.Core import master

# Способ 1: декоратор (рекомендуется, постоянный источник идентификации)
@master.provider
def admin_provider(platform, user_id):
    return user_id in {"999"}     # пользовательская логика проверки

master.is_master("yunhu", "999")   # True
admin_provider.unregister()        # при необходимости отменить

# Способ 2: функциональный (регистрация на этапе загрузки модуля / отмена на этапе выгрузки)
fn = master.provider(admin_provider)
fn.unregister()
```

> Исключения провайдера перехватываются и пропускаются, не блокируют цепочку проверки идентификации.
> Привязка метода экземпляра не может быть связана с `unregister`, для сценариев с парной регистрацией/отменой используйте **функцию уровня модуля**.

### Приоритет пользователя: область действия владельца определяется пользователем

`master=True` в команде — это **по умолчанию разработчика**: пользователь может перезаписать или ослабить с помощью
`ErisPulse.event.overrides.command.<module>.<cmd>.master = true/false` (см. [Единая конфигурация перезаписи событий (event.overrides)](#единая-конфигурация-перезаписи-событий-eventoverrides), явная конфигурация пользователя вступает в силу).

## Конфигурация логирования

```toml
[ErisPulse.logger]
level = "INFO"
log_files = []                # явный список файлов логов (взаимоисключает log_dir, имеет более высокий приоритет)
log_dir = ""                  # каталог логов (автоматически создается). При установке автоматически сегментируется, с `log_rotation` по умолчанию; `log_files` имеет приоритет над `log_dir`
log_rotation = "size"         # способ сегментации: "size" / "date" / "none"
log_max_size_mb = 10          # максимальный размер файла при сегментации по размеру (МБ)
log_backup_count = 5          # количество сохраняемых файлов логов
log_rotation_when = "midnight"  # период сегментации по времени: S/M/H/D/midnight (по умолчанию каждый день в полночь)
memory_limit = 1000
exclude_levels = ["EVENT"]
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| level | string | INFO | Уровень логирования: TRACE, DEBUG, INFO, WARNING, ERROR, CRITICAL (TRACE — самый низкий уровень, выводит подробную отладочную информацию фреймворка) |
| format | string | rich | Формат вывода логов: `rich` (цветной, по умолчанию), `plain` (чистый текст без цвета, подходит для лог-сборки/перенаправления), `json` (структурированный JSON, подходит для ELK и т.д.) |
| log_files | array | пустой | Список файлов вывода логов (явные пути, без сегментации) |
| log_dir | string | пустая строка | Каталог вывода логов (автоматически создается). При установке в него записывается `erispulse.log` и автоматически сегментируется по `log_rotation`; взаимоисключает `log_files`, `log_files` имеет приоритет |
| log_rotation | string | size | Способ сегментации: `size` (по размеру) / `date` (по времени) / `none` (без сегментации) |
| log_max_size_mb | float | 10 | Максимальный размер файла при сегментации по размеру (МБ), после чего происходит ротация в `.1`/`.2` резервные копии |
| log_backup_count | integer | 5 | Количество сохраняемых резервных файлов логов, старые резервные копии автоматически удаляются |
| log_rotation_when | string | midnight | Период сегментации по времени: `S`/`M`/`H`/`D`/`midnight` (по умолчанию каждый день в полночь) |
| memory_limit | integer | 1000 | Количество записей логов, хранящихся в памяти |
| exclude_levels | array | пустой | Уровни логов для исключения. Логи с исключенным уровнем **полностью отбрасываются** (не записываются в память, не передаются подписчикам, не выводятся, не записываются в файл). Поддерживает горячую перезагрузку |

Также можно динамически переключать в коде:

```python
from ErisPulse.Core import logger

# Сегментация по размеру: файл 10 МБ, 5 резервных копий
logger.set_output_dir("logs", rotation="size", max_size_mb=10, backup_count=5)

# Сегментация по времени: каждый день в полночь, 7 резервных копий
logger.set_output_dir("logs", rotation="date", backup_count=7)
```

> [!NOTE]
> `log_dir` и связанные с ним параметры сегментации требуют ErisPulse **2.8.0+**.

> **Защита конфиденциальности**: содержимое сообщений отправки и получения записывается на уровне **EVENT** (значение 21). Установка `exclude_levels = ["EVENT"]` позволяет фоновому (например, панели логов Dashboard) не видеть содержимого сообщений в группах/личных чатах, при этом не влияя на другие уровни логов.

> [!NOTE]
> Эта функция `exclude_levels` требует ErisPulse **2.8.0+**.

### Конфигурация активного GC

После инициализации SDK запускается фоновая задача активного GC, периодически выполняющая сборку мусора Python и внутреннюю очистку ресурсов (очистка неактивных ботов и т.д.). Все параметры поддерживают горячую перезагрузку, изменения немедленно перезапускают задачу.

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| proactive_gc_interval | number | 300 | Интервал сборки (секунды), поддерживает десятичные значения. 0 означает отключение активного GC |
| proactive_gc_generation | integer | 0 | Обычный цикл сборки поколений (0/1/2, ограничивается до 0..2). Обратите внимание, что `gc.collect(2)` эквивалентен полной сборке, по умолчанию 0 сохраняет легкость; глубокая сборка вызывается `proactive_gc_full_every` периодически |
| proactive_gc_full_every | integer | 20 | Каждые N циклов выполняется полная сборка, 0 означает отключение периодической полной. Полная сборка ограничена порогом `proactive_gc_memory_growth_mb` |
| proactive_gc_memory_growth_mb | integer | 32 | Порог роста памяти для полной сборки (МБ): по сравнению с базой памяти после предыдущей полной сборки (в первую очередь tracemalloc, затем RSS), только если рост достигает этого значения, выполняется полная сборка. 0 означает отсутствие порога |
| proactive_gc_idle_only | boolean | false | При включении, в периоде событий (существуют незавершенные pending handler) этот цикл пропускается, избегая пауз и конкуренции с обработкой сообщений; внутренняя очистка ресурсов не затрагивается |
| proactive_gc_gen0_min | integer | 500 | Порог срабатывания обычного цикла сборки gen0 мусора: `gc.get_count()[0]` ниже этого значения — пропуск (цикл с нулевой нагрузкой). 0 означает всегда выполнять сборку |

> **Изменение 2.7.1**: по умолчанию `proactive_gc_generation` изменился с `2` на `0`, `proactive_gc_full_every` изменился с `0` на `20`. Ранее `generation=2` означало, что каждый цикл выполняется самая тяжелая полная сборка; новое значение по умолчанию при сохранении охвата сборки значительно снижает нагрузку пустых циклов. Явно заданные старые значения по-прежнему действуют по смыслу.

### Строгий режим

Строгий режим управляет стратегией обработки компонентов, которые не соответствуют требованиям или завершаются с ошибкой на этапе загрузки. Современные модули/адаптеры должны наследовать соответствующие базовые классы (`BaseModule`/`BaseAdapter`), компоненты, не наследующие базовый класс, влияют на систему контекста фреймворка и на обработку утечек ресурсов, что может привести к утечкам ресурсов.

> **Изменение 2.5.2**: уровень по умолчанию изменился с `1` (пропуск) на `0` (допускающий), чтобы уменьшить количество проблем при первом использовании новыми пользователями. Компоненты, не наследующие базовый класс, будут предупреждаться и попытаться загрузиться, а не отклоняться. Чтобы восстановить старое поведение, явно установите `strict_mode = 1`.

| Уровень | Название | Поведение |
|------|------|------|
| 0 | Допускающий (по умолчанию) | Нарушения только предупреждения, компоненты, не наследующие базовый класс, все еще будут пытаться загрузиться (совместимость со старыми компонентами) |
| 1 | Строгий-пропуск | Отклонять компоненты, не наследующие базовый класс, и пропускать, остальное нормально запускается |
| 2 | Строгий-фатальный | Собирать все нарушения и сообщать о них, завершая запуск |

Во всех уровнях, «ошибки на этапе загрузки/регистрации/инициализации» (самокомпоненты падают) всегда будут пропущены; различие заключается в том, что:

- **0 → 1**: единственное поведение — «не наследующий базовый класс» из «все еще загружать» в «пропускать».
- **1 → 2**: все нарушения (не наследующий базовый класс, загрузка не удалась, регистрация не удалась, инициализация не удалась и т.д.) повышаются до фатального, будут собраны на контрольной точке запуска и выведены в список нарушений, затем завершится.

#### Список исключений

Если некоторые компоненты действительно не могут быть обновлены (например, зависимые старые модули), их можно включить в список исключений, и даже если они не соответствуют требованиям, они будут обрабатываться как допускающие, продолжая загрузку:

```toml
[ErisPulse.framework.strict_mode_exceptions]
modules = ["SeTu", "SomeLegacyModule"]
adapters = ["OldAdapter"]
```

> Когда компонент отклоняется строгим режимом, журнал четко указывает, как восстановить загрузку (включение в список исключений или понижение уровня).

## Конфигурация хранилища

Начиная с версии 2.8.0, движок хранилища поддерживает три асинхронных бэкенда, **API полностью идентичны, конфигурация переключается одним кликом**:

| Бэкенд | Драйвер | Установка | Особенности |
|------|------|------|------|
| SQLite (по умолчанию) | aiosqlite | Готово к использованию | Нулевая конфигурация, одиночный файл, WAL для параллелизма |
| MySQL / MariaDB | aiomysql | `pip install ErisPulse[mysql]` | Существующая инфраструктура MySQL, многократное использование |
| PostgreSQL | asyncpg | `pip install ErisPulse[postgres]` | Сильная транзакционность, высокая параллельность |

```toml
[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использовать глобальную базу данных пакета data/config.db

[ErisPulse.storage.mysql]      # backend = "mysql" действует
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
# charset = "utf8mb4"
# pool_min = 1
# pool_max = 10

[ErisPulse.storage.postgres]   # backend = "postgres" действует
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
# pool_min = 1
# pool_max = 10
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| backend | string | sqlite | Бэкенд хранения: `sqlite` / `mysql` / `postgres`, переключение без изменения кода |
| use_global_db | boolean | false | Только для SQLite: использовать глобальную базу данных пакета, а не независимую базу данных проекта |
| storage.mysql.* | table | см. выше | Параметры подключения MySQL (host / port / user / password / database / charset / pool) |
| storage.postgres.* | table | см. выше | Параметры подключения PostgreSQL (host / port / user / password / database / pool) |

Также поддерживаются переменные окружения (Docker / 12-factor): `ErisPulse.storage.postgres.host` → `ERISPULSE_STORAGE_POSTGRES_HOST`.

> [!TIP]
> - После изменения параметров подключения необходимо перезапустить фреймворк; временные сбои при создании пула повторно перепробуют с экспоненциальной задержкой
> - Перед переключением бэкенда можно использовать скрипт проверки: `python tests/devs/test_storage_backend_verify.py --backend mysql`
> - Детальное описание транзакций / диалектов / пользовательских бэкендов смотри в [Хранилищные бэкенды](../advanced/storage-backends.md)

|---------|------|---------|------|
| language | string | auto | Язык отображения встроенных текстов фреймворка. Установите `auto` для автоматического определения системного языка, или укажите конкретный код: `zh-CN`, `zh-TW`, `en`, `ja`, `ru` |

## Конфигурация модуля

Каждый модуль может определить свою конфигурацию в файле конфигурации:

```toml
[MyModule]
api_url = "https://api.example.com"
timeout = 30
enabled = true
```

В модуле читать и записывать конфигурацию:

```python
from ErisPulse import sdk

# Чтение конфигурации
config = sdk.config.getConfig("MyModule", {})
api_url = config.get("api_url", "https://default.api.com")

# Запись конфигурации во время выполнения (отложенная запись)
sdk.config.setConfig("MyModule.timeout", 60)

# Немедленная запись в файл
sdk.config.setConfig("MyModule.timeout", 60, immediate=True)
```

> `setConfig` по умолчанию использует отложенную запись (примерно каждые 5 секунд пакетная запись в файл), установка `immediate=True` немедленно сохраняет. Изменения конфигурации вызывают событие `config.set` жизненного цикла.

## Конфигурация области действия (scope)

> [!NOTE]
> Эта функция требует ErisPulse **2.8.0+**.

Область действия определяет **в каком контексте что действует** — какие модули доступны на какой платформе / боте / сессии (1. по модулям), какие события принимаются для какой пользовательской / групповой / бот / адаптерной сессии (2. по идентификации), какие исходящие вызовы может делать модуль (3. по исходящим):

```toml
[ErisPulse.scope]
default_allow = true        # Глобальный флаг по умолчанию (false = строгий режим отвержения; не влияет на исходящие)
cache_size = 1024           # Размер LRU кэша

# ① По модулям (приоритет: сессия > бот > платформа; записи поддерживают точную / glob / re: регулярные выражения)
[ErisPulse.scope.platforms.onebot11]
modules = ["Chat", "Tool*"]
blocked = ["re:^Danger"]

# Подуровни привязки с merge = true объединяются с низшим приоритетом по элементам (по умолчанию общее перезаписывание)
[ErisPulse.scope.bots.onebot11."123456"]
modules = ["Music"]
merge = true

# ② По идентификации (приоритет: пользователь > сессия > бот > адаптер; на каждом уровне записывается только allow или deny)
[ErisPulse.scope.identity.adapters.onebot11]
deny = true                 # Все события на этой платформе отбрасываются на входе
[ErisPulse.scope.identity.users.onebot11]
allow = ["u_admin"]         # Ключи пользователей поддерживают glob / re: регулярные выражения
deny = ["u_bad", "spam_*"]

# ③ По исходящим (по умолчанию разрешено все; правила — встроенные таблицы, записи поддерживают точную / glob / re: регулярные выражения)
[ErisPulse.scope.actions.MyModule]
send = { deny = true }                    # Полный запрет отправки
api = { allow = ["get_*"] }               # Только стандартные API-запросы
request = { deny = true }                 # Запрет обработки запросов
```

| Параметр | Тип | Описание |
|---------|------|------|
| `scope.default_allow` | boolean | Глобальный флаг по умолчанию: разрешение/отвержение для правил, не найденных модулями/идентификацией (true) |
| `scope.cache_size` | integer | Размер LRU кэша (по умолчанию 1024) |
| `scope.platforms / bots / sessions` | table | ① Три уровня привязки модуля: `{modules=[...], blocked=[...], merge=bool?}` |
| `scope.identity.adapters / bots / sessions / users` | table | ② Четыре уровня привязки идентификации: `{allow=true}` / `{deny=true}` |
| `scope.actions.<module>.<action>` | table | ③ Правила исходящих: `{allow=[...], deny=true|[...]}` (действия — send / api / request) |

> Подробное объяснение и API (дименсионные `sdk.scope.set_module()` / `set_identity()` / `set_action()`, проверки `is_allowed()` / `is_identity_allowed()` / `is_action_allowed()`, а также словарный доступ `get()` / `set()` / `delete()`) см. в [Область действия (scope)](../advanced/scope.md).

## Единая конфигурация перезаписи событий (event.overrides)

Система перезаписи: перезапись любых параметров обработчика модуля по **типу события**, без изменения кода модуля. Стандартные типы OneBot12 (meta / message / notice / request) и расширенные типы (command) имеют собственные перезаписываемые параметры:

```toml
[ErisPulse.event.overrides]

# message: текстовые условия (AND с условиями в коде)
[ErisPulse.event.overrides.message.ChatModule]
pattern = "闲聊*"

# notice / request / meta: white-list detail_type (записи поддерживают точную / glob / re: регулярные выражения)
[ErisPulse.event.overrides.notice.MyModule]
detail_types = ["group_increase"]

# command (расширенный тип): перезапись параметров реализации (приоритет пользователя; отключение через acl deny)
[ErisPulse.event.overrides.command.MyModule.restart]
master = true               # перезапись только для владельца фреймворка (false — разрешить ограничения владельца разработчика)
hidden = true               # скрыть в списке помощи
aliases = ["rs"]            #生效别名

# acl (command专属): пользовательские белый и черный списки (имена команд поддерживают glob / re: регулярные выражения, точные ключи имеют приоритет)
[ErisPulse.event.overrides.acl."roll*"]
allow = ["onebot11:u_vip"]  # пользовательский идентификатор "platform:user_id"
deny = ["onebot11:u_bad"]

# ACL по умолчанию: разрешение (true) / строгое отвержение (false) для команд без ACL
acl_default_allow = true
```

| Параметр | Тип | Описание |
|---------|------|------|
| `event.overrides.message.<module>` | table | Текстовые условия: `{pattern="...", regex="..."}` |
| `event.overrides.notice / request.<module>` | table | `{detail_types=[...], pattern, regex}` |
| `event.overrides.meta.<module>` | table | `{detail_types=[...]}` |
| `event.overrides.command.<module>` | table | Параметры перезаписи модуля (scalar-параметры, такие как `hidden = true`) |
| `event.overrides.command.<module>.<command>` | table | Перезапись параметров команды (имеет приоритет) |
| `event.overrides.acl.<command name>` | table | Белый и черный списки пользователей: `{allow=[...], deny=[...]}` |
| `event.overrides.acl_default_allow` | boolean | ACL по умолчанию: разрешение (true) / строгое отвержение (false) для команд без ACL |

> API во время выполнения (после `from ErisPulse.Core.Event import overrides` по подпространствам типа вызывать `overrides.message.set()` / `overrides.command.set()` / `overrides.acl.set()` и т.д., или через `sdk.Event.overrides` доступ)
> см. в [Введение в обработку событий · Перезапись событий](../getting-started/event-handling.md#перезапись-событий-без-изменения-кода-модуля-перезапись-любого-типа-событий).
