# Конфигурационный файл

> [!NOTE]
> **Обязательное к прочтению для ядра L1** — один из пяти основных документов в разделе "Читать путь" на главной странице, необходимый для разработки модулей.

> В этом документе будут описаны конфигурационные файлы фреймворка. Если у стороннего модуля есть настройки, обратитесь к документации модуля.

ErisPulse использует конфигурационный файл формата TOML `config/config.toml` для управления настройками проекта.

## Позиция конфигурационного файла

Конфигурационный файл находится в папке `config/` в корне проекта:

```
project/
├── config/
│   └── config.toml
├── main.py
```

### Подсказка по нескольким экземплярам и файлу блокировки

При запуске фреймворк создает файл блокировки `.erispulse_config.lock` в директории `config/` и удерживает его до завершения процесса (используется для обнаружения нескольких экземпляров, использующих одну и ту же директорию конфигурации). Если в логах появляется предупреждение «Обнаружено, что конфигурационный файл, возможно, используется другим экземпляром ErisPulse одновременно», это означает, что **два или более процессов ErisPulse записывают в один и тот же файл конфигурации** (типичный сценарий: несколько контейнеров монтируют одну и ту же директорию `config/` хоста) — параллельная запись будет перезаписывать друг друга, поэтому для каждого экземпляра используйте отдельную директорию конфигурации.

## Обработка ошибок при загрузке конфигурации

Фреймворк различает три состояния ошибок при загрузке `config.toml` и предоставляет **действенные инструкции по диагностике**, а не просто переключается на значения по умолчанию:

| Состояние ошибки | Условие срабатывания | Поведение фреймворка |
|---------|---------|---------|
| Файл отсутствует | `config.toml` не существует | Нормальный запуск, используется пустая конфигурация (без предупреждений) |
| Ошибка синтаксиса TOML | Файл существует, но формат неправильный (например, отсутствуют кавычки, не закрыты скобки) | Выводится **номер строки и столбца с ошибкой и причина**, и **предыдущая действительная конфигурация сохраняется для продолжения работы** (изменения в файле на этот раз не применяются) |
| Ошибка прав / другие ошибки | Отсутствие прав на чтение, ошибки ввода-вывода и т.д. | Выводится **ясная причина**, и **предыдущая действительная конфигурация сохраняется для продолжения работы** |

> **Важно**: «Предыдущая действительная конфигурация» ≠ «значения по умолчанию». При повреждении файла фреймворк использует **последнюю успешно проанализированную конфигурацию перед запуском** (если во время работы повредить файл, используется старое значение), а не сбрасывает все параметры на заводские значения. При устранении неисправностей не предполагайте, что «конфигурация была сброшена».

Например, если вы случайно напишете `port = 8000` (без кавычек для строки), в логах появится что-то вроде:

```
[ERROR] [Config] Синтаксическая ошибка в конфигурационном файле config/config.toml (строка 3, столбец 1): ...
[WARNING] [Config] Не удалось прочитать конфигурационный файл. Продолжаем работу с предыдущей действительной конфигурацией, изменения в файле на этот раз не применились — пожалуйста, исправьте файл и перезагрузите или перезапустите
```

Таким образом, вы можете сразу локализовать проблему на уровне **INFO**, а не задаваться вопросом «почему мои изменения в конфигурации не вступили в силу».

> **Изменение конфигурационного файла во время работы?** Если вы вручную редактируете `config.toml` во время работы бота и вводите синтаксическую ошибку, фреймворк при следующей попытке записи (объединения конфигурации) выведет «Конфигурационный файл поврежден (ошибка синтаксиса, строка X), невозможно записать — пожалуйста, сначала исправьте конфигурационный файл, затем перезапустите», а не запутанное «ошибка записи». Конфигурационные параметры, ожидающие записи, будут сохранены, не будет потери данных.

## Сохранение комментариев и минимальное сохранение на диск

**Комментарии и порядок ключей в config.toml сохраняются полностью после записи фреймворком**: будь то вызов `setConfig()`, сохранение через конфигурационный помощник CLI или генерация конфигурационного шаблона адаптером/модулем, фреймворк изменяет только соответствующие ключи, ваши комментарии и упорядоченный порядок не будут удалены или перестроены (на основе сохранения комментариев tomlkit).

Фреймворк сдержан в записи на диск:

- **Значения по умолчанию фреймворка не записываются автоматически**: `gc`, `scope`, `transcript` и другие встроенные значения остаются в памяти, в `config.toml` записываются только явно установленные ключи, обеспечивая минимальный размер. Полный список настраиваемых параметров см. в `config/config.full.example` проекта, копируйте по необходимости в `config.toml` и изменяйте (не настроенные параметры по-прежнему используют встроенные значения по умолчанию, поведение не меняется)
- **`config.full.example` автоматически поддерживается**: независимо от того, выполняли ли вы `epsdk init`, при запуске фреймворка (через `epsdk run` / `main.py`) в случае отсутствия `config/config.full.example` будет автоматически сгенерирован полный файл конфигурации-пример; в первой строке файла — метка, поддерживаемая фреймворком, при обновлении генератора (например, при добавлении новых конфигурационных параметров, установке новых компонентов) при запуске будет обновлен один раз, при удалении/изменении первой строки — контроль переходит в ручное управление, фреймворк больше не будет перезаписывать
- **Конфигурационные шаблоны адаптеров/модулей**: при первом инициализации шаблон с комментариями записывается на диск (описание полей — это комментарии); поля с меткой `example` не записываются, только в `config.full.example` для справки

## Перекрытие через переменные окружения

Фреймворк поддерживает **перекрытие** конфигурационных параметров `ErisPulse.*` с помощью переменных окружения (подходит для Docker / контейнеризации / CI-деплоймента, без необходимости изменять `config.toml`).

Правило именования: замените точечный путь `ErisPulse.<section>.<key>` на все заглавные буквы, замените `.` на `_`, и добавьте префикс `ERISPULSE_`:

| Параметр конфигурации | Переменная окружения | Пример значения |
|--------|---------|--------|
| `ErisPulse.server.port` | `ERISPULSE_SERVER_PORT` | `9000` |
| `ErisPulse.server.host` | `ERISPULSE_SERVER_HOST` | `0.0.0.0` |
| `ErisPulse.logger.level` | `ERISPULSE_LOGGER_LEVEL` | `DEBUG` |
| `ErisPulse.framework.strict_mode` | `ERISPULSE_FRAMEWORK_STRICT_MODE` | `false` |

Описание поведения:

- **Наивысший приоритет**: переменные окружения перекрывают «конфигурационный файл» и «значения по умолчанию», автоматически преобразуются по типу (bool / int / float / список, разделенный запятыми / строка)
- **Не сохраняются**: перекрытие действует только во время выполнения, не записывается обратно в `config.toml`
- **Поддержка горячего обновления**: при изменении переменных окружения во время выполнения, при перезагрузке с прослушиванием конфигурации изменения вступят в силу

```bash
# Пример развертывания в Docker: без изменения config.toml, напрямую перекрываем порт
ERISPULSE_SERVER_PORT=9000 docker compose up -d
```

> Примечание: `ErisPulse.server.port` и другие конфигурационные параметры фреймворка, читаются через API `get_server_config()` и т.д., подвержены влиянию переменных окружения.

### Привязка переменных окружения к конфигурации модуля (2.9.0+)

Сама декларативная конфигурация модуля (`ConfigClass`) поддерживает привязку переменных окружения на уровне полей — в `field(metadata=...)` объявите `env`:

```python
@dataclass
class MyConfig(BaseConfig):
    api_key: str = field(default="", metadata={
        "description": "Ключ API",
        "env": "MYMODULE_API_KEY",   # Привязка к переменной окружения
    })
    retries: int = field(default=3, metadata={"env": "MYMODULE_RETRIES"})
```

Описание поведения:

- **Приоритет**: переменная окружения > `config.toml` > значение по умолчанию (после горячего обновления конфигурационного файла сохраняется этот приоритет)
- **Тип преобразования**: значение переменной окружения автоматически преобразуется по аннотации поля — `str` как есть, `int` / `float` / `bool` (`true` / `1` / `yes` / `on`) автоматически преобразуются, `list` / `dict` парсятся через JSON; при неудачном преобразовании пропускается это перекрытие (возвращается конфигурационный файл / значение по умолчанию) и выводится предупреждение
- **Одно объявление, везде используется**: конфигурация читается, горячее обновление, валидация используют одну и ту же цепочку; схема панели конфигурации будет помечена `env`-именем, комментарии в шаблоне config.toml также укажут доступные переменные окружения (шаблон не записывает фактическое значение переменной окружения, чтобы избежать утечки)
- **Полная совместимость**: поведение без объявления `env` не меняется; непосредственное создание экземпляра ConfigClass (без цепочки конфигурации фреймворка) не подвержено влиянию переменных окружения

```bash
# Пример развертывания в Docker: без изменения config.toml, напрямую вставляем ключ модуля
MYMODULE_API_KEY=sk-xxx docker compose up -d
```

> **Как выбрать между классом конфигурации и полем модели?** Конфигурационный класс управляет «как работает модуль» (параметры поведения, горячее обновление), `ORM` `Field()` управляет «какие данные создал пользователь» (таблица базы данных, запросы). Оба используют одну и ту же систему тегов и движок валидатора; таблица сравнения см. в [Слое модели данных · Когда использовать какой тип объявления](../developer-guide/orm.md#когда-использовать-какой-тип-объявления).

## Горячее обновление конфигурации

Начиная с 2.7.0, фреймворк систематически поддерживает **горячее обновление конфигурации**. После внешнего изменения `config.toml` (фоновый watcher каждые 5 секунд обнаруживает изменения) или вызова `setConfig()` из кода, компоненты автоматически реагируют:

| Компонент | Поддержка горячего обновления | Поведение |
|------|----------------|------|
| **Logger** | `logger.level` / `log_files` / `log_dir` (включая параметры сегментации) / `memory_limit` / `format` / `exclude_levels` | Автоматически переприменяются (с обнаружением изменений) |
| **CommandHandler** | `event.command.prefix` / `case_sensitive` / `allow_space_prefix` / `must_at_bot` | Вступают в силу с следующего сообщения |
| **Адаптеры (параллельность)** | `framework.handler_max_concurrency` | Сигнал к сбросу кэша, перестроение по новому значению |
| **Активный GC** | `framework.proactive_gc_*` | Изменение конфигурации немедленно перезапускает задачи GC, поддержка настройки/отключения/перезапуска в режиме выполнения |
| **Система мастеров** | `master.users` | Каждая проверка `is_master()` читает в реальном времени, без перезапуска |
| **Конфигурация модулей/адаптеров** | Собственные конфигурационные параметры | Вызывается обратный вызов `on_config_update(old, new)` |

**Конфигурация, требующая перезапуска** (небезопасно горячее переключение, при изменении выводится предупреждение «Требуется перезапуск процесса для вступления в силу»):

| Конфигурация | Причина |
|------|------|
| `router.cors.*` / `router.security.*` | Промежуточные слои записываются в FastAPI при запуске службы, безопасное горячее переключение во время выполнения невозможно |
| `storage.use_global_db` | Файловый дескриптор SQLite уже открыт во время выполнения, безопасное переключение пути невозможно |

> **Ошибка при редактировании и сохранении?** Если при редактировании `config.toml` возникает временная синтаксическая ошибка, фреймворк **сохранит предыдущую действительную конфигурацию** и выведет диагностические логи, не будет рассылать пустую конфигурацию компонентам (избегает того, что `on_config_update` получит пустое значение и ошибочно вернется к значению по умолчанию).

### Внутреннее разбиение цепочки горячего обновления

«Изменили конфигурацию, как узнают компоненты?» — за этим стоит цепочка обнаружения → перезагрузки → рассылки:

```mermaid
flowchart TD
    A["Внешнее редактирование config.toml"] --> B{"Кто первым обнаружит?"}
    B -->|"Фоновый поток watcher<br/>каждые 5 секунд опрашивает mtime"| C["_check_file_change определяет изменение"]
    B -->|"При чтении конфигурации<br/>кэш просрочен на 60 секунд"| C
    C --> D["_load_config повторно анализирует TOML"]
    D --> E{"Анализ прошел успешно?"}
    E -->|"Нет (ошибка синтаксиса)"| F["Сохраняет предыдущую действительную конфигурацию<br/>не рассылает, выводит диагностические логи"]
    E -->|"Да"| G["lifecycle.emit config.updated<br/>передает old_config / new_config"]
    G --> H["Слушатели компонентов реагируют<br/>（logger / scope / command / GC ...）"]
```

**Две пути обнаружения** (достаточно одного, оба обеспечивают резерв):

| Путь | Механизм | Триггер |
|------|------|---------|
| Фоновый watcher | демон-поток `config-watcher` каждые **5 секунд** `wait` опрашивает `mtime` файла | после изменения файла максимум через 5 секунд |
| Ленивая проверка | любое `getConfig()` чтение, если кэш просрочен более **60 секунд**, сначала проверяет файл | при следующем чтении конфигурации |

> **Фреймворк не повредит сам себя**: `setConfig()` при записи файла сохраняет «время модификации, записанное самим», watcher при сравнении исключает его, обнаруживает только **внешние изменения** как изменения.

**Два типа событий изменения конфигурации**:

| Событие | Инициатор | Данные | Типичный сценарий |
|------|--------|------|---------|
| `config.set` | код / Dashboard вызывает `setConfig()` | `{key, old_value, new_value}` | Одиночное изменение (генерация шаблона, запись состояния, изменение конфигурации в режиме выполнения) |
| `config.updated` | внешнее редактирование после обнаружения watcher/Ленивой проверки | `{old_config, new_config, config_file}` | Ручное изменение `config.toml` |

> `setConfig()` по умолчанию **задерживает запись на диск на 5 секунд** (объединяет несколько записей), `immediate=True` — записывает немедленно. watcher при обнаружении внешнего изменения обновляет только кэш в памяти, **не** перезаписывает изменения во внешний файл.

**Список автоматических ответчиков** (обычно оба события подписываются, поведение одинаковое):

| Компонент | Подписка | Реакция |
|------|------|------|
| Logger | `config.set` + `config.updated` | Уровень/файлы/директория сегментации/память лимит/формат/уровни исключения переприменяются (с обнаружением изменений, без изменений — не трогать) |
| Scope | `config.updated` | Перестроение кэша привязки области |
| Система команд | `config.updated` | Параметры префикса/регистр/пробел-префикс/must_at_bot пересчитываются, вступают в силу с следующего сообщения |
| Адаптеры (параллельность) | `config.set` + `config.updated` | `handler_max_concurrency` сбрасывает и перестраивает семафор |
| Активный GC | `config.set` + `config.updated` | `proactive_gc_*` немедленно перезапускает фоновую задачу GC |
| Адаптеры | Перенаправляется в `on_config_update` | Обратный вызов `on_config_update(old, new)` для каждого адаптера |
| Модули | Перенаправляется в `on_config_update` | Обратный вызов `on_config_update(old, new)` для каждого модуля |
| Хранилище | `config.updated` | Изменение `use_global_db` **только предупреждение** (требуется перезапуск) |
| Роутер | `config.updated` | Изменение `cors.*` / `security.*` **только предупреждение** (требуется перезапуск) |


## API чтения и удаления конфигурации

### getAllConfig: полный снимок конфигурации

Вместо прямого чтения приватного `_cache` (внешнее чтение приватных свойств не защищено обратной совместимостью):

```python
config = sdk.config.getAllConfig()     # Глубокая копия снимка, изменение на месте не влияет на состояние фреймворка
config["ErisPulse"]["server"]["port"]
```

Вид с точки зрения `getConfig` идентичен: `setConfig` / `delete` без задержки записи отражены, строго согласованы с содержимым файла после задержки записи.

### delConfig: удаление ключа конфигурации

`setConfig(key, None)` просто устанавливает значение в пустое, ключ остается в файле; `delConfig` удаляет ключ из файла:

```python
sdk.config.delConfig("ErisPulse.modules.status.OldModule")            # Задержка записи
sdk.config.delConfig("OneBot.deprecated_key", immediate=True)         # Немедленная запись
```

- Поддерживает точечные пути; возвращает `False`, если ключ не существует
- Запись по пути сохранения комментариев, остальное содержимое файла и порядок не изменяются
- Повторное использование события `config.set` (с广播ом `new_value=None`): существующие слушатели адаптеров / модулей `on_config_update` и т.д. без изменений реагируют на удаление

## Полный пример конфигурации

```toml
[ErisPulse.server]
host = "0.0.0.0"
port = 8000
auto_start = true
ssl_certfile = ""
ssl_keyfile = ""

[ErisPulse.master]
# users поддерживает два способа записи (выберите один):
#   Глобальные хозяева (действуют на всех платформах): users = ["123456", "789012"]
#   Хозяева по платформам: users = { yunhu = ["123456"], telegram = ["789012"] }
users = {}

[ErisPulse.logger]
level = "INFO"
format = "rich"
log_files = []
log_dir = ""
log_rotation = "size"
log_max_size_mb = 10
log_backup_count = 5
log_rotation_when = "midnight"
memory_limit = 1000
exclude_levels = []

[ErisPulse.framework]
enable_lazy_loading = true
```

```toml
[ErisPulse.server]
host = "0.0.0.0"

ssl_keyfile = "/path/to/key.pem"
# Для сценариев контейнеров / без монтирования файлов можно встроить PEM-содержимое (приоритет над путями certfile/keyfile)
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| host | string | 0.0.0.0 | Адрес прослушивания, 0.0.0.0 означает все интерфейсы |
| port | integer | 8000 | Номер порта прослушивания |
| auto_start | boolean | true | Автоматически запускать сервер маршрутизации при `sdk.init()`? Установите в `false`, чтобы пропустить запуск сервера маршрутизации (сценарии без WebUI) |
| ssl_certfile | string | пустая строка | Путь к файлу SSL-сертификата |
| ssl_keyfile | string | пустая строка | Путь к файлу SSL-ключа |
| ssl_cert | string | пустая строка | **Встроенное PEM-содержимое сертификата** (не путь). Приоритет над `ssl_certfile`/`ssl_keyfile`, фреймворк временно сохраняет SSL-контекст и сразу удаляет временный файл |
| ssl_key | string | пустая строка | **Встроенное PEM-содержимое ключа** (не путь), семантика аналогична предыдущему |

При диагностике «бот работает, но WebUI не открывается» сначала убедитесь в занятости порта.

## Конфигурация системы хозяев

Система хозяев используется для определения «хозяев» (например, администраторов бота). `master.users` поддерживает два способа записи:

```toml
[ErisPulse.master]
# Способ 1: глобальные хозяева (действуют на всех платформах)
users = ["123456", "789012"]

# Способ 2: хозяева по платформам (dict)
# users = { yunhu = ["123456"], telegram = ["789012"] }
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| users | array / object | пустой | Список аккаунтов хозяев. `list` означает глобальных хозяев (действуют на всех платформах); `dict` означает хозяев по платформам (ключ — название платформы, значение — список хозяев на этой платформе) |

В коде проверка осуществляется через `master.is_master(event)` или `master.is_master(platform, user_id)`, каждый вызов читает конфигурацию в реальном времени (поддерживает горячее обновление, перезапуск не требуется):

```python
from ErisPulse.Core import master

if master.is_master(event):
    await event.reply("Привет, хозяин")
```

### Цепочка определения и добавление удаление во время выполнения

Цепочка определения хозяев: **конфигурационные хозяева → записи во время выполнения → провайдер цепи**:

```python
from ErisPulse.Core import master

master.is_master(event)                      # Определение по событию
master.is_master("yunhu", "123")             # Явное определение
master.add("yunhu", "123")                   # Добавление во время выполнения (по умолчанию сохраняется; persist=False — только в памяти)
master.remove("yunhu", "123")                # Удаление (по умолчанию сохраняется)
master.list()                                # Сводка: {"global": [...], "<platform>": [...]}
```

### Пользовательские источники идентификации (провайдеры)

Помимо конфигурации, можно зарегистрировать пользовательские источники идентификации: `fn(platform, user_id) -> bool`, встроенные источники идентификации (конфигурация + записи во время выполнения) не срабатывают, последовательно проверяются, при первом срабатывании хозяин определяется. Подходит для подключения адаптера, базы данных ролей и других внешних систем идентификации.

Точка регистрации `master.provider` поддерживает декораторы и функциональный стиль, удаление происходит через `fn.unregister()`:

```python
from ErisPulse.Core import master

# Стиль 1: декоратор (рекомендуется, постоянный источник идентификации)
@master.provider
def admin_provider(platform, user_id):
    return user_id in {"999"}     # Пользовательская логика определения

master.is_master("yunhu", "999")   # True
admin_provider.unregister()        # При необходимости отменить регистрацию

# Стиль 2: функциональный стиль (регистрация при загрузке модуля / отмена при выгрузке)
fn = master.provider(admin_provider)
fn.unregister()
```

> Исключения провайдеров перехватываются и пропускаются, не блокируют цепочку определения идентификации.
> Привязка метода экземпляра не может быть связана с `unregister`, для сценариев с парной регистрацией/отменой используйте **функцию на уровне модуля**.

### Приоритет пользователя: хозяин определяется пользователем

Параметр `master=True` команды — это **по умолчанию для разработчика**: пользователь может перезаписать сужение или расширение через
`ErisPulse.event.overrides.command.<module>.<cmd>.master = true/false` (см. [Единая конфигурация перезаписи событий (event.overrides)], где явная конфигурация пользователя вступает в силу).

## Конфигурация логов

```toml
[ErisPulse.logger]
level = "INFO"
log_files = []                # Явный список файлов логов (взаимоисключительно с log_dir, приоритет выше)
log_dir = ""                  # Директория логов (автоматически создается). При установленном значении автоматически сегментируется в `erispulse.log` в директории и по `log_rotation`; взаимоисключительно с `log_files`, `log_files` имеет приоритет
log_rotation = "size"         # Способ сегментации: "size" / "date" / "none"
log_max_size_mb = 10          # Максимальный размер файла в режиме "size" (МБ), при превышении пересекается в `.1`/`.2`
log_backup_count = 5          # Количество сохраняемых файлов логов
log_rotation_when = "midnight"  # Период сегментации в режиме "date": S/M/H/D/midnight (по умолчанию каждый день в полночь)
memory_limit = 1000
exclude_levels = ["EVENT"]
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| level | string | INFO | Уровень логирования: TRACE, DEBUG, INFO, WARNING, ERROR, CRITICAL (TRACE — самый низкий уровень, выводит подробную отладочную информацию фреймворка) |
| format | string | rich | Формат вывода логов: `rich` (цветной, по умолчанию), `plain` (простой текст без цвета, подходит для лог-коллекторов/перенаправления), `json` (структурированный JSON, подходит для ELK и др.) |
| log_files | array | пустой | Список файлов вывода логов (явные пути, без сегментации) |
| log_dir | string | пустая строка | Директория вывода логов (автоматически создается). При установленном значении в директории `erispulse.log` записывается и по `log_rotation` автоматически сегментируется; взаимоисключительно с `log_files`, `log_files` имеет приоритет |
| log_rotation | string | size | Способ сегментации: `size` (по размеру), `date` (по времени), `none` (без сегментации) |
| log_max_size_mb | float | 10 | Максимальный размер файла в режиме "size" (МБ), при превышении пересекается в `.1`/`.2` |
| log_backup_count | integer | 5 | Количество сохраняемых файлов логов, самые старые автоматически удаляются |
| log_rotation_when | string | midnight | Период сегментации в режиме "date": `S`/`M`/`H`/`D`/`midnight` (по умолчанию каждый день в полночь) |
| memory_limit | integer | 1000 | Количество записей логов, хранящихся в памяти |
| exclude_levels | array | пустой | Уровни логирования, которые нужно исключить. Логи с исключенным уровнем **полностью отбрасываются** (не записываются в память, не отправляются подписчикам, не выводятся, не записываются в файл). Поддерживается горячее обновление |

Также можно динамически переключать в коде:

```python
from ErisPulse.Core import logger

# Сегментация по размеру: файл 10 МБ, сохранять 5 копий
logger.set_output_dir("logs", rotation="size", max_size_mb=10, backup_count=5)

# Сегментация по времени: каждый день в полночь, сохранять 7 копий
logger.set_output_dir("logs", rotation="date", backup_count=7)
```

> [!NOTE]
> `log_dir` и связанные с ним параметры сегментации требуют ErisPulse **2.8.0+**.

> **Защита конфиденциальности**: содержимое сообщений отправки и получения записывается на уровне **EVENT** (значение 21). Установка `exclude_levels = ["EVENT"]` позволит панели логов (например, панель логов Dashboard) не видеть содержимого сообщений в группах или личных чатах, при этом не влияя на другие уровни логирования.

> [!NOTE]
> Эта функция `exclude_levels` требует ErisPulse **2.8.0+**.

### Конфигурация активного GC

После инициализации SDK запускается фоновая задача активного GC, периодически выполняющая сборку мусора Python и внутреннюю очистку ресурсов (очистка неактивных ботов и т.д.). Все параметры поддерживают горячее обновление, при изменении задача перезапускается.

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| proactive_gc_interval | number | 300 | Интервал сборки (секунды), поддерживает дробные значения. 0 означает отключение активного GC |
| proactive_gc_generation | integer | 0 | Обычный цикл сборки поколений (0/1/2, ограничено до 0..2). Обратите внимание, что `gc.collect(2)` эквивалентно полной сборке, по умолчанию 0 сохраняет легкую нагрузку; глубокая сборка запускается периодически по `proactive_gc_full_every` |
| proactive_gc_full_every | integer | 20 | Каждые N циклов выполняется полная сборка, 0 означает отключение периодической полной. Полная сборка ограничена порогом `proactive_gc_memory_growth_mb` |
| proactive_gc_memory_growth_mb | integer | 32 | Порог роста памяти для полной сборки (МБ): по сравнению с базой памяти после предыдущей полной сборки (в первую очередь tracemalloc, затем RSS), только при достижении этого порога выполняется полная сборка. 0 означает отсутствие порога |
| proactive_gc_idle_only | boolean | false | При включении, в периоды пиковой нагрузки (существуют незавершенные pending handler), текущий цикл пропускает сборку Python, избегая пауз и конкуренции с обработкой сообщений; внутренняя очистка ресурсов не затрагивается |
| proactive_gc_gen0_min | integer | 500 | Порог запуска обычной сборки для мусора gen0: `gc.get_count()[0]` ниже этого значения — пропускать (пустые циклы почти без накладных расходов). 0 означает всегда выполнять сборку |

> **Изменение 2.7.1**: по умолчанию `proactive_gc_generation` изменен с `2` на `0`, `proactive_gc_full_every` изменен с `0` на `20`. Ранее `generation=2` означало, что каждый цикл выполняется самая тяжелая полная сборка; новое значение по умолчанию, сохраняя охват сборки, значительно снижает накладные расходы пустых циклов. Явно заданные старые значения по-прежнему действуют по смыслу.

### Строгий режим

Строгий режим управляет стратегией обработки компонентов, которые не соответствуют требованиям или не удались при загрузке. Современные модули/адаптеры должны наследовать соответствующие базовые классы (`BaseModule`/`BaseAdapter`), компоненты, не наследующие базовый класс, влияют на систему контекста фреймворка и на бэкап-очистку, что может привести к утечке ресурсов.

> **Изменение 2.5.2**: уровень по умолчанию изменился с `1` (пропуск) на `0` (мягкий), чтобы уменьшить проблемы, с которыми сталкиваются новые пользователи при первом использовании. Компоненты, не наследующие базовый класс, будут предупреждены и попытаться загрузиться, а не отклонены. Чтобы восстановить старое поведение, явно установите `strict_mode = 1`.

| Уровень | Название | Поведение |
|------|------|------|
| 0 | Мягкий (по умолчанию) | Нарушения только предупреждаются, компоненты, не наследующие базовый класс, все еще будут пытаться загрузиться (совместимость со старыми компонентами) |
| 1 | Строгий-пропуск | Отклонение компонентов, не наследующих базовый класс, и пропуск, остальное нормально запускается |
| 2 | Строгий-фатальный | Сбор всех нарушений и единое сообщение с последующим завершением запуска |

На всех уровнях, «ошибки в этапах загрузки/регистрации/инициализации» — это сбои компонентов, которые всегда будут пропущены; различие заключается в том, что:

- **0 → 1**: единственное изменение поведения — «не наследующие базовый класс» из «все еще загружаются» в «пропускаются».
- **1 → 2**: все нарушения (не наследуют базовый класс, загрузка не удалась, регистрация не удалась, инициализация не удалась и т.д.) повышаются до фатального уровня, все нарушения собираются на этапе запуска и выводятся в виде списка, после чего запуск завершается.

#### Список исключений

Если некоторые компоненты действительно временно не могут быть обновлены (например, зависящие от старого модуля), их можно добавить в список исключений, и даже если они не соответствуют требованиям, они будут обработаны как мягкий режим и продолжат загрузку:

```toml
[ErisPulse.framework.strict_mode_exceptions]
modules = ["SeTu", "SomeLegacyModule"]
adapters = ["OldAdapter"]
```

> Когда компонент отклоняется строгим режимом, в логах будет четко указано, как восстановить загрузку (добавить в список исключений или понизить уровень).

## Конфигурация хранилища

Начиная с 2.8.0, движок хранилища поддерживает три асинхронных бэкенда, **API полностью идентичны, конфигурация переключается одним кликом**:

| Бэкенд | Драйвер | Установка | Особенности |
|------|------|------|------|
| SQLite (по умолчанию) | aiosqlite | Готово | Нулевая конфигурация, одиночный файл, WAL для параллелизма |
| MySQL / MariaDB | aiomysql | `pip install ErisPulse[mysql]` | Существующая инфраструктура MySQL, общие многоэкземплярные |
| PostgreSQL | asyncpg | `pip install ErisPulse[postgres]` | Сильная транзакционность, высокая параллельность |

```toml
[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использовать глобальную базу данных пакета data/config.db

[ErisPulse.storage.mysql]      # backend = "mysql" действует
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
# charset = "utf8mb4"
# pool_min = 1
# pool_max = 10

[ErisPulse.storage.postgres]   # backend = "postgres" действует
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
# pool_min = 1
# pool_max = 10
```

| Параметр | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| backend | string | sqlite | Бэкенд хранилища: `sqlite` / `mysql` / `postgres`, переключение без изменений кода |
| use_global_db | boolean | false | Только для SQLite: использовать глобальную базу данных пакета, а не независимую базу данных проекта |
| storage.mysql.* | table | см. выше | Параметры подключения MySQL (host / port / user / password / database / charset / pool) |
| storage.postgres.* | table | см. выше | Параметры подключения PostgreSQL (host / port / user / password / database / pool) |

Также поддерживаются переменные окружения (Docker / 12-factor): `ErisPulse.storage.postgres.host` → `ERISPULSE_STORAGE_POSTGRES_HOST`.

> [!TIP]
> - После изменения параметров подключения перезапустите фреймворк для вступления в силу; временные ошибки создания пула автоматически повторяются с экспоненциальной задержкой
> - Перед переключением бэкенда можно использовать скрипт проверки: `python tests/devs/test_storage_backend_verify.py --backend mysql`
> - Полное описание транзакций, диалектов, пользовательских бэкендов см. в [Хранилищные бэкенды](../advanced/storage-backends.md)

## Конфигурация модуля

Каждый модуль может определить свою конфигурацию в конфигурационном файле:

```toml
[MyModule]
api_url = "https://api.example.com"
timeout = 30
enabled = true
```

В модуле читать и записывать конфигурацию:

```python
from ErisPulse import sdk

# Чтение конфигурации
config = sdk.config.getConfig("MyModule", {})
api_url = config.get("api_url", "https://default.api.com")

# Запись конфигурации во время выполнения (отложенная запись)
sdk.config.setConfig("MyModule.timeout", 60)

# Немедленная запись в файл
sdk.config.setConfig("MyModule.timeout", 60, immediate=True)
```

> `setConfig` по умолчанию использует отложенную запись (примерно каждые 5 секунд пакетная запись в файл), установка `immediate=True` немедленно сохраняет. Изменения конфигурации запускают событие жизненного цикла `config.set`.

## Конфигурация области действия (scope)

> [!NOTE]
> Эта функция требует ErisPulse **2.8.0+**.

Область действия определяет «**в каком диапазоне действует**» — какие модули доступны на какой платформе / боте / сессии (1. по модулям), какие события принимаются для какой пользовательской / групповой / бот / адаптерной сессии (2. по идентификации), какие исходящие вызовы может выполнять модуль (3. по исходящим):

```toml
[ErisPulse.scope]
default_allow = true        # Глобальная базовая настройка (false = строгий режим с явным отклонением; не влияет на исходящие параметры)
cache_size = 1024           # Размер кэша LRU

# ① Модульные правила (приоритет: сессия > бот > платформа; элементы поддерживают точные / glob / re: регулярные выражения)
[ErisPulse.scope.platforms.onebot11]
modules = ["Chat", "Tool*"]
blocked = ["re:^Danger"]

# Подчиненные правила с merge=true объединяются с низшим приоритетом по элементам (по умолчанию общее перезаписывание)
[ErisPulse.scope.bots.onebot11."123456"]
modules = ["Music"]
merge = true

# ② Правила идентификации (приоритет: пользователь > сессия > бот > адаптер; на каждом уровне только allow или deny)
[ErisPulse.scope.identity.adapters.onebot11]
deny = true                 # Все события на этой платформе отбрасываются на входе
[ErisPulse.scope.identity.users.onebot11]
allow = ["u_admin"]         # Поддержка glob / re: регулярных выражений
deny = ["u_bad", "spam_*"]

# ③ Исходящие правила (по умолчанию разрешено все; правила в виде встроенных таблиц, элементы поддерживают точные / glob / re: регулярные выражения)
[ErisPulse.scope.actions.MyModule]
send = { deny = true }                    # Полный запрет отправки
api = { allow = ["get_*"] }               # Только стандартные API для запросов
request = { deny = true }                 # Запрет обработки запросов
```

| Параметр | Тип | Описание |
|---------|------|------|
| `scope.default_allow` | boolean | Глобальная базовая настройка: разрешение/отклонение для правил, не заданных модулями/идентификацией (true) |
| `scope.cache_size` | integer | Размер кэша LRU (по умолчанию 1024) |
| `scope.platforms / bots / sessions` | table | ① Правила модуля по трем уровням: `{modules=[...], blocked=[...], merge=bool?}` |
| `scope.identity.adapters / bots / sessions / users` | table | ② Правила идентификации по четырем уровням: `{allow=true}` / `{deny=true}` |
| `scope.actions.<module>.<action>` | table | ③ Правила исходящих действий: `{allow=[...], deny=true|[...]}` (действия: send / api / request) |

> Подробности и API во время выполнения (модульная `sdk.scope.set_module()` / `set_identity()` / `set_action()`, проверка `is_allowed()` / `is_identity_allowed()` / `is_action_allowed()`, а также словарный `get()` / `set()` / `delete()`) см. в [Область действия (scope)](../advanced/scope.md).

## Единая конфигурация перезаписи событий (event.overrides)

Система перезаписи: перезапись поведения любого обработчика модуля по **типу события**, без изменения кода модуля. Стандартные типы OneBot12 (meta / message / notice / request) и расширенные типы (command) имеют собственные настраиваемые параметры:

```toml
[ErisPulse.event.overrides]

# message: текстовые условия (AND с условиями в коде)
[ErisPulse.event.overrides.message.ChatModule]
pattern = "闲聊*"

# notice / request / meta: whitelist detail_type (элементы поддерживают точные / glob / re: регулярные выражения)
[ErisPulse.event.overrides.notice.MyModule]
detail_types = ["group_increase"]

# command (расширенный тип): параметры перезаписи (приоритет пользователя; отключение через acl deny)
[ErisPulse.event.overrides.command.MyModule.restart]
master = true               # Перезапись в хозяина фреймворка (false — разрешить ограничение хозяина разработчика)
hidden = true               # Скрыть в списке помощи
aliases = ["rs"]            # Действующие псевдонимы

# acl (только для command): белый/черный список пользователей (имена команд поддерживают glob / re: регулярные выражения, точные ключи имеют приоритет)
[ErisPulse.event.overrides.acl."roll*"]
allow = ["onebot11:u_vip"]  # Идентификатор пользователя "platform:user_id"
deny = ["onebot11:u_bad"]

# ACL базовая настройка: разрешение (true) / строгое отклонение (false) команд, не имеющих ACL
acl_default_allow = true
```

| Параметр | Тип | Описание |
|---------|------|------|
| `event.overrides.message.<module>` | table | Текстовые условия: `{pattern="...", regex="..."}` |
| `event.overrides.notice / request.<module>` | table | `{detail_types=[...], pattern, regex}` |
| `event.overrides.meta.<module>` | table | `{detail_types=[...]}` |
| `event.overrides.command.<module>` | table | Параметры перезаписи модуля (scalar значения `hidden = true` и т.д.) |
| `event.overrides.command.<module>.<command>` | table | Перезапись команды (приоритет команды) |
| `event.overrides.acl.<command>` | table | Белый/черный список пользователей: `{allow=[...], deny=[...]}` |
| `event.overrides.acl_default_allow` | boolean | ACL базовая настройка: разрешение (true) / строгое отклонение (false) команд без ACL |

> API во время выполнения (после `from ErisPulse.Core.Event import overrides` по подпространствам типа вызывать `overrides.message.set()` / `overrides.command.set()` / `overrides.acl.set()` и т.д., или через `sdk.Event.overrides` доступ к `overrides` см. в [Введение в обработку событий · Перезапись событий](../getting-started/event-handling.md#перезапись-событий-без-изменения-кода-модуля-перезапись-поведения-любого-типа-события) .
