# Конфигурационный файл

> [!NOTE]
> **Обязательный к прочтению для L1** — один из пяти основных документов в разделе "Путь к чтению" на главной странице, необходим для разработки модулей.

> Этот документ расскажет о конфигурационных файлах фреймворка. Если у стороннего модуля есть какие-либо настройки, обратитесь к документации модуля.

ErisPulse использует конфигурационный файл в формате TOML `config/config.toml` для управления конфигурацией проекта.

## Позиция конфигурационного файла

Конфигурационный файл находится в папке `config/` в корне проекта:

```
project/
├── config/
│   └── config.toml
├── main.py
```

### Подсказка по нескольким экземплярам и файлам блокировки

При запуске фреймворка в папке `config/` создается файл блокировки `.erispulse_config.lock` и удерживается до завершения процесса (используется для обнаружения нескольких экземпляров, использующих одну и ту же папку конфигурации). Если в журнале появляется предупреждение «Обнаружено, что файл конфигурации, возможно, используется другим экземпляром ErisPulse одновременно», это означает, что **более двух экземпляров ErisPulse записывают в один и тот же файл конфигурации** (типичная сцена: несколько контейнеров монтируют одну и ту же папку `config/` хоста) — одновременная запись будет перезаписывать друг друга, поэтому для каждого экземпляра используйте отдельную папку конфигурации.

## Обработка ошибок при загрузке конфигурации

Фреймворк при загрузке `config.toml` различает три состояния ошибок и предоставляет **действенные диагностические сообщения**, а не просто переключается на конфигурацию по умолчанию:

| Состояние ошибки | Условие срабатывания | Поведение фреймворка |
|---------|---------|---------|
| Файл отсутствует | `config.toml` не существует | Нормальный первый запуск, тихо использует пустую конфигурацию (не выдает предупреждения) |
| Ошибка синтаксиса TOML | Файл существует, но формат некорректен (например, отсутствуют кавычки, не закрыты скобки) | Выводит **номер строки/столбца и причину ошибки**, и **сохраняет предыдущую действительную конфигурацию и продолжает работу** (изменения в текущем файле не применяются) |
| Ошибка прав доступа и другие | Отсутствие прав на чтение, ошибки ввода/вывода и т.д. | Выводит **ясную причину** и **сохраняет предыдущую действительную конфигурацию и продолжает работу** |

> **Важно:** "Предыдущая действительная конфигурация" ≠ "Конфигурация по умолчанию": при повреждении файла фреймворк использует **последнюю успешно проанализированную конфигурацию перед запуском** (при изменении файла во время работы используется старое значение), а не сбрасывает все параметры на заводские. При устранении сбоя не предполагайте, что "конфигурация была сброшена".

Например, если вы случайно напишете конфигурацию как `port = 8000` (без кавычек строки), журнал выведет примерно следующее:

```
[ERROR] [Config] Синтаксическая ошибка в файле конфигурации config/config.toml (строка 3, столбец 1): ...
[WARNING] [Config] Не удалось прочитать файл конфигурации. Продолжаем использовать предыдущую действительную конфигурацию, изменения в файле не применились — пожалуйста, исправьте и перезагрузите или перезапустите
```

Таким образом, вы можете сразу определить проблему на уровне `INFO`, а не задаваться вопросом "почему мои изменения в конфигурации не вступили в силу".

> **Изменение поврежденного файла во время работы?** Если вы вручную отредактируете `config.toml` во время работы робота и внесете синтаксическую ошибку, фреймворк при следующей попытке записи (объединения конфигурации) выведет «Файл конфигурации поврежден (синтаксическая ошибка, строка X), невозможно записать — пожалуйста, сначала исправьте файл конфигурации и перезапустите», а не запутанное «Запись не удалась». Конфигурационные параметры, которые должны быть записаны, сохраняются, не теряются.

## Сохранение комментариев и минимизация записи

**Комментарии и порядок ключей в config.toml сохраняются без изменений** после записи фреймворком: будь то `setConfig()`, сохранение с помощью конфигурационного мастера CLI или генерация шаблона конфигурации адаптером/модулем, фреймворк изменяет только соответствующие ключи, ваши комментарии и упорядоченный порядок не будут удалены или перестроены (используется безвредный движок TOML tomlclass, не затрагивающий неизмененные данные байт-на-байт, стиль конца строки CRLF/LF также не изменяется).

Фреймворк сдержан в записи данных:

- **Конфигурация по умолчанию не записывается автоматически**: `gc`, `scope`, `transcript` и другие встроенные значения по умолчанию хранятся только в памяти, в `config.toml` содержатся только явно установленные ключи, сохраняя минимальный объем. Полный список настраиваемых параметров можно найти в `config/config.full.example` проекта, копируйте нужные в `config.toml` и изменяйте (не настроенные параметры по-прежнему используют встроенные значения по умолчанию, поведение не меняется)
- **`config.full.example` автоматически поддерживается**: независимо от того, выполняли ли вы `epsdk init`, при запуске фреймворка (`epsdk run` / `main.py`) будет автоматически сгенерирован `config/config.full.example`, если файл отсутствует; первая строка файла — маркер, поддерживаемый фреймворком, содержимое генератора обновляется (например, добавление новых конфигурационных параметров, установка новых компонентов) при запуске, если удалить/изменить первую строку, файл переходит в ручное управление, и фреймворк больше не будет его перезаписывать
- **Шаблоны конфигурации адаптеров/модулей**: при первом инициализации шаблон с комментариями записывается на диск (описание полей — это комментарии); поля, помеченные как `example`, не записываются на диск, только отмечаются в `config.full.example` для справки
- **Читаемость комментариев**: комментарии в файле конфигурации являются документацией — `ep doctor` и сообщения о проверке конфигурации будут ссылаться на оригинальный комментарий в файле (даже если вы вручную изменили комментарий, сообщение будет соответствовать текущему состоянию файла), при ошибке не нужно снова открывать документацию для поиска значения поля

## Переменные окружения для перекрытия

Фреймворк поддерживает **перекрытие** конфигурационных параметров `ErisPulse.*` с помощью переменных окружения (подходит для Docker / контейнеризации / CI-развертывания, без необходимости изменения `config.toml`).

Правила именования: измените точечный путь `ErisPulse.<section>.<key>` на все заглавные буквы, замените `.` на `_` и добавьте префикс `ERISPULSE_`:

| Параметр конфигурации | Переменная окружения | Пример значения |
|--------|---------|--------|
| `ErisPulse.server.port` | `ERISPULSE_SERVER_PORT` | `9000` |
| `ErisPulse.server.host` | `ERISPULSE_SERVER_HOST` | `0.0.0.0` |
| `ErisPulse.logger.level` | `ERISPULSE_LOGGER_LEVEL` | `DEBUG` |
| `ErisPulse.framework.strict_mode` | `ERISPULSE_FRAMEWORK_STRICT_MODE` | `false` |

Описание поведения:

- **Наивысший приоритет**: переменные окружения перекрывают «конфигурационный файл» и «значения по умолчанию», автоматически преобразуются по типу (bool / int / float / список, разделенный запятыми / строка)
- **Не сохраняются**: перекрытие действует только во время выполнения, не записывается обратно в `config.toml`
- **Поддержка горячего обновления**: после изменения переменной окружения во время выполнения, в сочетании с перезагрузкой конфигурации по监听у, изменения вступают в силу

```bash
# Пример развертывания в Docker: без изменения config.toml, непосредственно перекрывая порт
ERISPULSE_SERVER_PORT=9000 docker compose up -d
```

> Примечание: `ErisPulse.server.port` и другие конфигурационные параметры фреймворка, доступные через `get_server_config()` и другие API, подвержены влиянию переменных окружения.

### Привязка переменных окружения к конфигурации модуля (2.9.0+)

Конфигурация модуля в виде объявленного класса (`ConfigClass`) поддерживает привязку переменных окружения на уровне полей — в `field(metadata=...)` объявите `env`:

```python
@dataclass
class MyConfig(BaseConfig):
    api_key: str = field(default="", metadata={
        "description": "API ключ",
        "env": "MYMODULE_API_KEY",   # привязка переменной окружения
    })
    retries: int = field(default=3, metadata={"env": "MYMODULE_RETRIES"})
```

Описание поведения:

- **Приоритет**: переменная окружения > `config.toml` > значение по умолчанию (конфигурация горячего обновления сохраняет этот приоритет)
- **Тип преобразования**: значение переменной окружения автоматически преобразуется по аннотации поля — `str` останется без изменений, `int` / `float` / `bool` (`true` / `1` / `yes` / `on`) преобразуются автоматически, `list` / `dict` преобразуются через JSON-парсер; при неудачном преобразовании перекрытие игнорируется (возвращается конфигурация / значение по умолчанию) и выводится предупреждение
- **Одно объявление, везде生效**: конфигурация читается, горячий обновления, проверка используют одну и ту же трубу; схема конфигурационной панели будет отмечать `env` имя, комментарии в шаблоне config.toml также будут подсказывать доступные переменные окружения (шаблон не записывает фактическое значение переменной окружения, чтобы избежать утечки)
- **Полная совместимость**: поведение полей, не объявленных с `env`, не меняется; непосредственное создание экземпляра ConfigClass (без использования конфигурационной трубы фреймворка) не подвержено влиянию переменных окружения

```bash
# Пример развертывания в Docker: без изменения config.toml, непосредственно вставляя модульный ключ
MYMODULE_API_KEY=sk-xxx docker compose up -d
```

> **Как выбрать между конфигурационным классом и моделью полей?** Конфигурационный класс управляет "как работает модуль" (параметры поведения, горячее обновление), ORM `Field()` управляет "какие данные создал пользователь" (таблица базы данных, запросы). Оба используют одну и ту же систему ограничений и движок проверки; таблица сопоставления см. в [Слой данных модели · Когда использовать какое объявление](../developer-guide/orm.md#когда-использовать-какое-объявление).

## Горячее обновление конфигурации

Начиная с 2.7.0, фреймворк системно поддерживает **горячее обновление конфигурации**. После внешнего изменения `config.toml` (фоновый watcher каждые 5 секунд проверяет), или после вызова `setConfig()` в коде, компоненты автоматически реагируют:

| Компонент | Поддерживаемые конфигурации для горячего обновления | Поведение |
|------|----------------|------|
| **Logger** | `logger.level` / `log_files` / `log_dir` (включая параметры сегментации) / `memory_limit` / `format` / `exclude_levels` | Автоматически переприменяются (с обнаружением изменений) |
| **CommandHandler** | `event.command.prefix` / `case_sensitive` / `allow_space_prefix` / `must_at_bot` | Действует с первой следующей сообщения |
| **Адаптеры (конкурентность)** | `framework.handler_max_concurrency` | Сигналы кэша истекают, пересоздаются по новому значению |
| **Активный GC** | `framework.proactive_gc_*` | Конфигурация изменяется немедленно, можно настроить/отключить/включить во время выполнения |
| **Система хозяев** | `master.users` | Каждый вызов `is_master()` проверяет в реальном времени, без перезапуска |
| **Конфигурации модулей/адаптеров** | Собственные конфигурационные параметры | Запускается `on_config_update(old, new)` обратный вызов |

**Конфигурации, требующие перезапуска** (небезопасно горячее переключение, при изменении выводится предупреждение "необходим перезапуск процесса, чтобы изменения вступили в силу"):

| Конфигурация | Причина |
|------|------|
| `router.cors.*` / `router.security.*` | Промежуточные слои записываются в FastAPI при запуске службы, безопасное горячее переключение во время выполнения невозможно |
| `storage.use_global_db` | SQLite файловый дескриптор уже открыт во время выполнения, безопасная смена пути невозможна |

> **Что делать, если произошла ошибка при редактировании и сохранении?** Если при редактировании `config.toml` возникает временная синтаксическая ошибка, фреймворк **сохранит предыдущую действительную конфигурацию** и выведет диагностическое сообщение, не будет рассылать пустую конфигурацию по компонентам (чтобы избежать `on_config_update` получения пустого значения и ошибочного возврата к значению по умолчанию).

### Внутренняя разбивка цепочки горячего обновления

«После изменения конфигурации, как компоненты узнают об этом?» — за этим стоит цепочка обнаружения → перезагрузки → рассылки:

```mermaid
flowchart TD
    A["Внешнее редактирование config.toml"] --> B{"Кто первым узнает?"}
    B -->|"Фоновый поток watcher<br/>каждые 5 секунд опрашивает mtime"| C["_check_file_change определяет изменение"]
    B -->|"При чтении конфигурации<br/>кэш истек более 60 секунд"| C
    C --> D["_load_config повторно анализирует TOML"]
    D --> E{"Анализ успешен?"}
    E -->|"Нет (синтаксическая ошибка)"| F["Сохраняет предыдущую действительную конфигурацию<br/>не рассылает, выводит диагностическое сообщение"]
    E -->|"Да"| G["lifecycle.emit config.updated<br/>передает old_config / new_config"]
    G --> H["Компоненты-слушатели реагируют<br/>（logger / scope / command / GC ...）"]
```

**Две цепочки обнаружения** (достаточно одной, обе могут служить резервом):

| Цепочка | Механизм | Время срабатывания |
|------|------|---------|
| Фоновый watcher | daemon-поток `config-watcher` каждые **5 секунд** `wait` опрашивает файл `mtime` | После внешнего изменения файла максимум через 5 секунд |
| Ленивое обнаружение | При любом `getConfig()` чтении, если кэш более **60 секунд** старый, сначала проверяет файл | При следующем чтении конфигурации |

> **Фреймворк не повредит сам себя**: `setConfig()` при записи файла помечает «время модификации, записанное самим», watcher при сравнении исключает его, рассматривая только **внешние изменения** как изменение.

**Два типа событий изменения конфигурации**:

| Событие | Инициатор | Данные | Типичный сценарий |
|------|--------|------|---------|
| `config.set` | Код / Dashboard вызывает `setConfig()` | `{key, old_value, new_value}` | Одиночное изменение (генерация шаблона, запись состояния, изменение конфигурации во время выполнения) |
| `config.updated` | Наблюдатель/Ленивое обнаружение ловит внешнее изменение | `{old_config, new_config, config_file}` | Ручное редактирование `config.toml` |

> `setConfig()` по умолчанию **задерживает запись на диск на 5 секунд** (объединяет несколько записей), `immediate=True` немедленно записывает. watcher, обнаружив внешнее изменение, обновляет только кэш в памяти, **не** возвращает внешние изменения в файл.

**Список компонентов, реагирующих на события** (обычно оба события подписываются, реакция одинаковая):

| Компонент | Подписка | Реакция |
|------|------|------|
| Logger | `config.set` + `config.updated` | Уровень/файл/директория сегментации/память/формат/уровень исключения переприменяются (с обнаружением изменений, без изменений не двигаются) |
| Scope | `config.updated` | Перестраивается кэш привязки области |
| Система команд | `config.updated` | Параметры префикса/регистра/пробела/must_at_bot пересчитываются, действует с первой следующей сообщения |
| Адаптеры (конкурентность) | `config.set` + `config.updated` | `handler_max_concurrency` сигнализирует кэш, пересоздается |
| Активный GC | `config.set` + `config.updated` | `proactive_gc_*` немедленно перезапускает фоновую задачу GC |
| Адаптеры | Перенаправление на `on_config_update` | Обратный вызов `on_config_update(old, new)` для каждого адаптера |
| Модули | Перенаправление на `on_config_update` | Обратный вызов `on_config_update(old, new)` для каждого модуля |
| Хранилище | `config.updated` | Изменение `use_global_db` **только предупреждение** (требуется перезапуск) |
| Роутер | `config.updated` | Изменение `cors.*` / `security.*` **только предупреждение** (требуется перезапуск) |


## API чтения и удаления конфигурации

### getAllConfig: полный снимок конфигурации

Вместо прямого чтения приватного `_cache` (внешнее чтение приватных свойств не защищено версионной совместимостью):

```python
config = sdk.config.getAllConfig()     # Глубокая копия снимка, локальное изменение не влияет на состояние фреймворка
config["ErisPulse"]["server"]["port"]
```

Вид с точки зрения представления и `getConfig` одинаков: не записанные `setConfig` / `delete` уже отражены, строго согласуются с содержимым файла после задержки записи.

### delConfig: удаление конфигурационного ключа

`setConfig(key, None)` просто устанавливает значение в пустое, ключ остается в файле; `delConfig` удаляет ключ из файла:

```python
sdk.config.delConfig("ErisPulse.modules.status.OldModule")            # Задержанная запись
sdk.config.delConfig("OneBot.deprecated_key", immediate=True)         # Немедленная запись
```

- Поддерживает точечные пути; если ключ не существует, возвращает `False`
- Запись проходит через путь сохранения комментариев, остальное содержимое и порядок файла не затрагиваются
- Повторно использует событие `config.set` (событие `new_value=None`): существующие обработчики адаптеров / модулей `on_config_update` нулевой изменений могут воспринимать удаление

## Полный пример конфигурации


## Конфигурация сервера

```toml
[ErisPulse.server]
host = "0.0.0.0"
port = 8000
auto_start = true
ssl_certfile = "/path/to/cert.pem"
ssl_keyfile = "/path/to/key.pem"
# В сценариях контейнера / без монтирования файлов можно встроить PEM содержимое (приоритет выше, чем путь к certfile/keyfile)
# ssl_cert = """-----BEGIN CERTIFICATE-----
# ...
# -----END CERTIFICATE-----"""
# ssl_key = """-----BEGIN PRIVATE KEY-----
# ...
# -----END PRIVATE KEY-----"""
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| host | string | 0.0.0.0 | Адрес для прослушивания, 0.0.0.0 означает все интерфейсы |
| port | integer | 8000 | Номер порта для прослушивания |
| auto_start | boolean | true | Автоматически запускать сервер маршрутизации при `sdk.init()`. Установите в `false`, чтобы пропустить запуск сервера маршрутизации (чистый сценарий событий/без WebUI) |
| ssl_certfile | string | пустая строка | Путь к файлу SSL-сертификата |
| ssl_keyfile | string | пустая строка | Путь к файлу SSL-ключа |
| ssl_cert | string | пустая строка | **Встроенное PEM-содержимое сертификата** (не путь). При использовании вместе с `ssl_key` имеет приоритет над `ssl_certfile`/`ssl_keyfile`; фреймворк временно записывает и создает SSL-контекст, затем немедленно удаляет временный файл |
| ssl_key | string | пустая строка | **Встроенное PEM-содержимое ключа** (не путь), семантика такая же, как выше |

> **Занятость порта не является фатальной ошибкой**: при запуске, если обнаружено, что порт занят, фреймворк пропускает запуск сервера маршрутизации и выдает предупреждение, **адаптеры и модули продолжают работать** (только HTTP/WS/SSE-маршруты и WebUI недоступны). При диагностике "бот работает, но WebUI не открывается" сначала проверьте порт.

## Конфигурация системы хозяев

Система хозяев используется для определения "хозяина фреймворка" (например, администратор бота). `master.users` поддерживает два способа записи:

```toml
[ErisPulse.master]
# Способ 1: Глобальный хозяин (действует на всех платформах)
users = ["123456", "789012"]

# Способ 2: Хозяин по платформам (словарь)
# users = { yunhu = ["123456"], telegram = ["789012"] }
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| users | array / object | пустой | Список аккаунтов хозяев. `list`-формат — глобальный хозяин (действует на всех платформах); `dict`-формат — хозяин по платформам (ключ — имя платформы, значение — список аккаунтов хозяев на этой платформе) |

В коде проверка осуществляется через `master.is_master(event)` или `master.is_master(platform, user_id)`, каждый вызов читает конфигурацию в реальном времени (поддерживает горячее обновление, перезапуск не требуется):

```python
from ErisPulse.Core import master

if master.is_master(event):
    await event.reply("Привет, хозяин")
```

### Цепочка проверки и добавление/удаление во время выполнения

Цепочка проверки хозяина: **конфигурационный хозяин → запись во время выполнения → провайдер-цепочка**:

```python
from ErisPulse.Core import master

master.is_master(event)                      # Проверка по событию
master.is_master("yunhu", "123")             # Явная проверка
master.add("yunhu", "123")                   # Добавление во время выполнения (по умолчанию сохраняется; persist=False только в памяти)
master.remove("yunhu", "123")                # Удаление (по умолчанию сохраняется)
master.list()                                # Сводка: {"global": [...], "<platform>": [...]}
```

### Пользовательские источники идентификации (провайдеры)

Помимо конфигурации, можно зарегистрировать пользовательские источники идентификации: `fn(platform, user_id) -> bool`, встроенные источники идентификации (конфигурация + запись во время выполнения) не совпадают, проверяются последовательно, если один провайдер разрешает, то признается хозяином. Подходит для подключения адаптеров администратора, ролей базы данных и других внешних систем идентификации.

Вход для регистрации `master.provider` поддерживает два способа: декоратор и функциональный, удаление происходит через `fn.unregister()`:

```python
from ErisPulse.Core import master

# Способ 1: Декоратор (рекомендуется, постоянный источник идентификации)
@master.provider
def admin_provider(platform, user_id):
    return user_id in {"999"}     # Пользовательская логика проверки

master.is_master("yunhu", "999")   # True
admin_provider.unregister()        # Удалить, когда больше не нужно

# Способ 2: Функциональный (регистрация при загрузке модуля / удаление при выгрузке)
fn = master.provider(admin_provider)
fn.unregister()
```

> Исключения провайдера перехватываются и пропускаются, не блокируют цепочку проверки идентификации.
> Привязка экземпляра метода не может быть зарегистрирована с `unregister`, для сценариев, требующих парной регистрации/удаления, используйте **модульный функционал**.

### Приоритет пользователя: зона действия хозяина определяется пользователем

Параметр `master=True` команды — это **по умолчанию разработчика**: пользователь может перезаписать сужение или расширение (см. [Единая конфигурация перезаписи событий (event.overrides)](#единственная-конфигурация-перезаписи-событий-eventoverrides), пользовательская конфигурация вступает в силу немедленно).

## Конфигурация логов

```toml
[ErisPulse.logger]
level = "INFO"
log_files = []                # Явный список файлов логов (исключает log_dir, имеет более высокий приоритет)
log_dir = ""                  # Директория логов (автоматически создается). При установке записывается в erispulse.log в директории и автоматически сегментируется по log_rotation; log_files имеет приоритет над log_dir
log_rotation = "size"         # Способ сегментации: "size" / "date" / "none"
log_max_size_mb = 10          # Максимальный размер файла в режиме size (МБ), при превышении переключается на .1/.2 резервные файлы
log_backup_count = 5          # Количество сохраняемых файлов логов, старые резервные файлы удаляются
log_rotation_when = "midnight"  # Период смены сегментации в режиме date: S/M/H/D/midnight (по умолчанию каждый день в полночь)
memory_limit = 1000
exclude_levels = ["EVENT"]
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| level | string | INFO | Уровень логирования: TRACE, DEBUG, INFO, WARNING, ERROR, CRITICAL (TRACE — самый низкий уровень, выводит подробную отладочную информацию фреймворка) |
| format | string | rich | Формат вывода логов: `rich` (цветной, по умолчанию), `plain` (чистый текст без цвета, подходит для сбора логов/перенаправления потока), `json` (структурированный JSON, подходит для ELK и т.д.) |
| log_files | array | пустой | Список файлов вывода логов (явные пути, без сегментации) |
| log_dir | string | пустая строка | Директория вывода логов (автоматически создается). При установке записывается в `erispulse.log` в директории и автоматически сегментируется по `log_rotation`. `log_files` имеет приоритет над `log_dir`, `log_files` имеет более высокий приоритет |
| log_rotation | string | size | Способ сегментации: `size` (по размеру) / `date` (по времени) / `none` (без сегментации) |
| log_max_size_mb | float | 10 | Максимальный размер файла в режиме size (МБ), при превышении переключается на `.1`/`.2` резервные файлы |
| log_backup_count | integer | 5 | Количество сохраняемых файлов логов, старые резервные файлы удаляются |
| log_rotation_when | string | midnight | Период смены сегментации в режиме date: `S`/`M`/`H`/`D`/`midnight` (по умолчанию каждый день в полночь) |
| memory_limit | integer | 1000 | Количество записей логов, хранящихся в памяти |
| exclude_levels | array | пустой | Уровни логирования, которые нужно исключить. Исключенные уровни логов **полностью отбрасываются** (не записываются в память, не отправляются на панель логов Dashboard и другие подписчики, не выводятся, не записываются в файл). Поддерживает горячее обновление |

Также можно динамически переключать в коде:

```python
from ErisPulse.Core import logger

# Сегментация по размеру: файл 10MB, сохранять 5 копий
logger.set_output_dir("logs", rotation="size", max_size_mb=10, backup_count=5)

# Сегментация по времени: смена каждый день в полночь, сохранять 7 копий
logger.set_output_dir("logs", rotation="date", backup_count=7)
```

> [!NOTE]
> `log_dir` и связанные с сегментацией параметры требуют ErisPulse **2.8.0+**.

> **Защита конфиденциальности**: содержимое сообщений поступления и отправки записывается на уровне **EVENT** (значение 21). Установка `exclude_levels = ["EVENT"]` позволит фону (например, панели логов Dashboard) не видеть содержимое сообщений в группах/личных чатах, при этом не влияя на другие уровни логов.

> [!NOTE]
> Эта функция `exclude_levels` требует ErisPulse **2.8.0+**.

### Конфигурация активного GC

После инициализации SDK запускается фоновая задача активного GC, периодически выполняющая сборку мусора Python и внутреннее освобождение ресурсов (очистка неактивных ботов и т.д.). Все параметры поддерживают горячее обновление, изменения немедленно перезапускают задачу.

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| proactive_gc_interval | number | 300 | Интервал сборки мусора (секунд), поддерживает десятичные числа. 0 означает отключить активный GC |
| proactive_gc_generation | integer | 0 | Обычный раунд сборки поколений (0/1/2, ограничено до 0..2). Обратите внимание, что `gc.collect(2)` эквивалентно полной сборке, по умолчанию 0 сохраняет легкость; глубокая сборка запускается периодически с помощью `proactive_gc_full_every` |
| proactive_gc_full_every | integer | 20 | Каждые N раундов делается полная сборка, 0 означает отключить периодическую полную. Полная сборка ограничена порогом `proactive_gc_memory_growth_mb` |
| proactive_gc_memory_growth_mb | integer | 32 | Порог роста памяти для полной сборки (МБ): по сравнению с базой памяти после последней полной сборки (предпочтительно tracemalloc, затем RSS), только при росте достигнутом этого значения выполняется полная сборка. 0 означает не устанавливать порог |
| proactive_gc_idle_only | boolean | false | При включении, в периоды пиковой нагрузки (существуют незавершенные pending handler) этот раунд пропускает сборку Python, избегая пауз и конкуренции с обработкой сообщений; внутреннее освобождение ресурсов не затрагивается |
| proactive_gc_gen0_min | integer | 500 | Порог запуска сборки gen0 мусора: `gc.get_count()[0]` ниже этого значения напрямую пропускается (пустые раунды почти без накладных расходов). 0 означает всегда собирать |

> **2.7.1 изменение**: значение по умолчанию `proactive_gc_generation` было изменено с `2` на `0`, значение по умолчанию `proactive_gc_full_every` было изменено с `0` на `20`. Ранее `generation=2` означало, что каждый раунд делает самую тяжелую полную сборку; новое значение по умолчанию при сохранении охвата сборки значительно снижает накладные расходы пустых раундов. Явно заданные старые значения по-прежнему действуют по буквальному значению.

### Строгий режим

Строгий режим контролирует стратегию обработки компонентов, которые нарушают правила или терпят неудачу при загрузке. Современные модули/адаптеры должны наследовать соответствующие базовые классы (`BaseModule`/`BaseAdapter`), компоненты, не наследующие базовые классы, влияют на систему контекста фреймворка и на базовую очистку, что может привести к утечке ресурсов.

> **2.5.2 изменение**: значение по умолчанию было изменено с `1` (пропуск) на `0` (мягкий), чтобы уменьшить проблемы с загрузкой при первом использовании новыми пользователями. Компоненты, не наследующие базовые классы, будут предупреждаться и попытаться загрузиться, а не отклоняться. Чтобы восстановить старое поведение, явно установите `strict_mode = 1`.

| Уровень | Название | Поведение |
|------|------|------|
| 0 | Мягкий (по умолчанию) | Нарушения только предупреждаются, компоненты, не наследующие базовые классы, все еще будут попытаться загрузиться (совместимость со старыми компонентами) |
| 1 | Строгий-пропуск | Отклоняются компоненты, не наследующие базовые классы, и пропускаются, остальное нормально запускается |
| 2 | Строгий-фатальный | Собираются все нарушения и сообщаются единовременно, затем запуск прерывается |

Во всех уровнях, "ошибки на этапе загрузки/регистрации/инициализации" компонентов, которые сами аварийно завершаются, всегда будут пропущены; различие заключается в том, что:

- **0 → 1**: единственное изменение поведения — "не наследующие базовые классы" перестают "загружаться" и переходят в "пропуск".
- **1 → 2**: все нарушения (не наследующие базовые классы, загрузка не удалась, регистрация не удалась, инициализация не удалась и т.д.) повышаются до фатальных, все нарушения собираются на точке запуска, затем выводится список нарушений и запуск прерывается.

#### Список исключений

Если некоторые компоненты действительно временно не могут быть перенесены (например, зависимые от старого модуля), их можно добавить в список исключений, и компоненты, даже если они не соответствуют требованиям, будут обрабатываться в соответствии с мягким режимом и продолжат загрузку:

```toml
[ErisPulse.framework.strict_mode_exceptions]
modules = ["SeTu", "SomeLegacyModule"]
adapters = ["OldAdapter"]
```

> Когда компонент отклоняется строгим режимом, журнал будет четко указывать, как восстановить загрузку (добавить в список исключений или понизить уровень).

## Конфигурация хранилища

Начиная с версии 2.8.0, движок хранилища поддерживает три асинхронных бэкенда, **API полностью одинаковы, конфигурация переключается одним кликом**:

| Бэкенд | Драйвер | Установка | Особенности |
|------|------|------|------|
| SQLite (по умолчанию) | aiosqlite | по умолчанию | без настройки, одиночный файл, WAL для параллелизма |
| MySQL / MariaDB | aiomysql | `pip install ErisPulse[mysql]` | уже есть инфраструктура MySQL, многократное использование |
| PostgreSQL | asyncpg | `pip install ErisPulse[postgres]` | сильная транзакционность, высокая параллельность |

```toml
[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использовать глобальную базу данных в пакете data/config.db

[ErisPulse.storage.mysql]      # backend = "mysql" действует
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
# charset = "utf8mb4"
# pool_min = 1
# pool_max = 10

[ErisPulse.storage.postgres]   # backend = "postgres" действует
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
# pool_min = 1
# pool_max = 10
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| backend | string | sqlite | Хранилище бэкенд: `sqlite` / `mysql` / `postgres`, переключение без изменения кода |
| use_global_db | boolean | false | Только для SQLite: использовать глобальную базу данных пакета, а не независимую базу данных проекта |
| storage.mysql.* | таблица | см. выше | Параметры подключения MySQL (host / port / user / password / database / charset / pool) |
| storage.postgres.* | таблица | см. выше | Параметры подключения PostgreSQL (host / port / user / password / database / pool) |

Также поддерживается перекрытие переменными окружения (Docker / 12-factor): `ErisPulse.storage.postgres.host` → `ERISPULSE_STORAGE_POSTGRES_HOST`.

> [!TIP]
> - После изменения параметров подключения необходимо перезапустить фреймворк для применения изменений; временные ошибки создания пула соединений будут автоматически повторяться с экспоненциальной задержкой
> - Перед переключением бэкенда можно использовать скрипт проверки: `python tests/devs/test_storage_backend_verify.py --backend mysql`
> - Полное описание транзакций, диалектов, пользовательских бэкендов см. в [Хранилище бэкендов](../advanced/storage-backends.md)

## Конфигурация событий

### Конфигурация команд

```toml
[ErisPulse.event.command]
prefix = "/"
case_sensitive = true
allow_space_prefix = false
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| prefix | string | / | Префикс команды |
| case_sensitive | boolean | true | Регистр чувствителен (например, `/Help` и `/help` — разные команды) |
| allow_space_prefix | boolean | false | Пробел может быть префиксом |
| must_at_bot | boolean | false | Команду можно вызвать только с упоминанием бота (в личных сообщениях не ограничено) |

### Конфигурация сообщений

```toml
[ErisPulse.event.message]
ignore_self = true
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| ignore_self | boolean | true | Игнорировать собственные сообщения бота |

## Конфигурация локализации

```toml
[ErisPulse.i18n]
language = "auto"
```

| Конфигурация | Тип | Значение по умолчанию | Описание |
|---------|------|---------|------|
| language | string | auto | Язык отображения встроенных текстов фреймворка. Установите `auto` для автоматического определения системного языка, или укажите конкретный код: `zh-CN`, `zh-TW`, `en`, `ja`, `ru` |

## Конфигурация модуля

Каждый модуль может определить свою конфигурацию в файле конфигурации:

```toml
[MyModule]
api_url = "https://api.example.com"
timeout = 30
enabled = true
```

В модуле читать и записывать конфигурацию:

```python
from ErisPulse import sdk

# Чтение конфигурации
config = sdk.config.getConfig("MyModule", {})
api_url = config.get("api_url", "https://default.api.com")

# Запись конфигурации во время выполнения (отложенная запись)
sdk.config.setConfig("MyModule.timeout", 60)

# Немедленная запись в файл
sdk.config.setConfig("MyModule.timeout", 60, immediate=True)
```

> `setConfig` по умолчанию использует отложенную запись (примерно каждые 5 секунд массовая запись в файл), установка `immediate=True` немедленно сохраняет. Изменения конфигурации запускают событие `config.set` жизненного цикла.

## Конфигурация области действия (scope)

> [!NOTE]
> Эта функция требует ErisPulse **2.8.0+**.

Область действия определяет **в каком контексте действует** — какие модули доступны в определенной платформе / боте / сессии (1. по модулям), какие события принимаются для определенного пользователя / группы / бота / адаптера (2. по идентификации), какие исходящие вызовы может выполнять модуль (3. по исходящим действиям):

```toml
[ErisPulse.scope]
default_allow = true        # Общее по умолчанию (false = явное отклонение строгого режима; не влияет на исходящие действия)
cache_size = 1024           # Размер LRU кэша

# ① По модулям (приоритет: сессия > бот > платформа; записи поддерживают точные / glob / re: регулярные выражения)
[ErisPulse.scope.platforms.onebot11]
modules = ["Chat", "Tool*"]
blocked = ["re:^Danger"]

# Подчиненные привязки с merge = true объединяются с низшим приоритетом по каждому элементу (по умолчанию общее перезаписывание)
[ErisPulse.scope.bots.onebot11."123456"]
modules = ["Music"]
merge = true

# ② По идентификации (приоритет: пользователь > сессия > бот > адаптер; на каждом уровне только allow или deny)
[ErisPulse.scope.identity.adapters.onebot11]
deny = true                 # Все события этой платформы отбрасываются на входе
[ErisPulse.scope.identity.users.onebot11]
allow = ["u_admin"]         # Поддержка glob / re: регулярных выражений
deny = ["u_bad", "spam_*"]

# ③ По исходящим действиям (по умолчанию все разрешено; правила — встроенные таблицы, записи поддерживают точные / glob / re: регулярные выражения)
[ErisPulse.scope.actions.MyModule]
send = { deny = true }                    # Полный запрет отправки
api = { allow = ["get_*"] }               # Только разрешены стандартные API запросов
request = { deny = true }                 # Запрет обработки запросов
```

| Конфигурация | Тип | Описание |
|---------|------|------|
| `scope.default_allow` | boolean | Общее по умолчанию: разрешение/отклонение модулей/идентификации, не попавших под правила (true) |
| `scope.cache_size` | integer | Размер LRU кэша (по умолчанию 1024) |
| `scope.platforms / bots / sessions` | table | ① Трехуровневая привязка модулей: `{modules=[...], blocked=[...], merge=bool?}` |
| `scope.identity.adapters / bots / sessions / users` | table | ② Четырехуровневая привязка идентификации: `{allow=true}` / `{deny=true}` |
| `scope.actions.<module>.<action>` | table | ③ Правила исходящих действий: `{allow=[...], deny=true|[...]}` (действия — send / api / request) |

> Подробности и API времени выполнения (модульные `sdk.scope.set_module()` / `set_identity()` / `set_action()`, проверка `is_allowed()` / `is_identity_allowed()` / `is_action_allowed()`, а также словарный `get()` / `set()` / `delete()`) см. в [Область действия (scope)](../advanced/scope.md).

## Единая конфигурация перезаписи событий (event.overrides)

Система перезаписи событий: перезапись поведения любого модуля по типу события, без изменения кода модуля. Стандартные типы OneBot12 (meta / message / notice / request) и расширенные типы (command) имеют свои собственные настраиваемые параметры:

```toml
[ErisPulse.event.overrides]

# message: текстовые условия (AND с условиями в коде)
[ErisPulse.event.overrides.message.ChatModule]
pattern = "闲聊*"

# notice / request / meta: detail_type белый список (поддержка точных / glob / re: регулярных выражений)
[ErisPulse.event.overrides.notice.MyModule]
detail_types = ["group_increase"]

# command (расширенный тип): перезапись параметров реализации (приоритет пользователя; отключение через acl deny)
[ErisPulse.event.overrides.command.MyModule.restart]
master = true               # Перезапись на хозяина фреймворка (false — разрешить ограничения хозяина разработчика)
hidden = true               # Скрыть в списке помощи
aliases = ["rs"]            # Активные псевдонимы

# acl (только для command): черный/белый список пользователей (имена команд поддерживают glob / re: регулярные выражения, точные ключи имеют приоритет)
[ErisPulse.event.overrides.acl."roll*"]
allow = ["onebot11:u_vip"]  # Идентификатор пользователя "platform:user_id"
deny = ["onebot11:u_bad"]

# ACL по умолчанию: разрешить команды, не настроенные в acl (true) / строго отклонить (false)
acl_default_allow = true
```

| Конфигурация | Тип | Описание |
|---------|------|------|
| `event.overrides.message.<module>` | table | Условия текста: `{pattern="...", regex="..."}` |
| `event.overrides.notice / request.<module>` | table | `{detail_types=[...], pattern, regex}` |
| `event.overrides.meta.<module>` | table | `{detail_types=[...]}` |
| `event.overrides.command.<module>` | table | Параметры перезаписи модуля (символьные значения `hidden = true` и т.д.) |
| `event.overrides.command.<module>.<command>` | table | Перезапись команды (приоритет команды) |
| `event.overrides.acl.<command>` | table | Черный/белый список пользователей: `{allow=[...], deny=[...]}` |
| `event.overrides.acl_default_allow` | boolean | ACL по умолчанию: разрешить команды, не настроенные в acl (true) / строго отклонить (false) |

> API во время выполнения (после `from ErisPulse.Core.Event import overrides` вызовите `overrides.message.set()` / `overrides.command.set()` / `overrides.acl.set()` по подпространствам типов, или через `sdk.Event.overrides` доступ к `overrides.message.set()` / `overrides.command.set()` / `overrides.acl.set()` и т.д.)
> См. [Введение в обработку событий · Перезапись событий](../getting-started/event-handling.md#перезапись-событий-без-изменения-кода-модуля-перезапись-поведения-любого-типа-событий) для получения дополнительной информации.
