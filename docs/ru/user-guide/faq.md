# Часто задаваемые вопросы (FAQ)

> [!TIP]
> **Когда стоит прочитать этот документ**: если во время работы наблюдаются такие симптомы, как «бот не реагирует / сообщения теряются / database is locked / память постоянно растёт», сначала сверьтесь здесь с симптомами, чтобы найти причину и путь устранения неполадок; если ничего не подошло, обратитесь к соответствующему профильному документу.

## Сообщения и события

### Бот не реагирует на упоминание @ в группе?

Проверьте по порядку:

1. **Мультиаккаунтное развёртывание + `cross_account_policy = "drop"`**: копия события в упомянутом через @ аккаунте имеет привилегию прямого упоминания (всегда пропускается), но убедитесь в корректности идентификации целевого аккаунта — таблица привязок и определение принадлежности используют двойной критерий: `self.user_id` и `self.account_id` (см. [Повторная обработка событий между аккаунтами](../developer-guide/adapters/core-concepts.md))
2. **`ignore_self`**: событие фильтруется, когда отправитель == сам принимающий аккаунт (включено по умолчанию); убедитесь, что это не эхо собственного сообщения
3. **Условия обработчиков**: соответствуют ли `detail_type` / текстовые условия, зарегистрированные через `on()`, фактическим полям события; если у события отсутствует `detail_type`, обработчики с объявленными условиями больше не срабатывают
4. **Спящий режим/ленивая загрузка модулей**: модули, у которых не сработал `activate_on`, не загружаются (см. [Ленивая загрузка и спящий режим](../advanced/lazy-loading.md))

### Бот ответил дважды на одно и то же сообщение?

- Несколько аккаунтов в одной группе: каждый из двух аккаунтов получил свою копию события — включите `cross_account_policy` (дедупликация на уровне содержимого) или настройте `session_accounts` (точная привязка сессии к аккаунту, см. [Конфигурация](configuration.md))
- Несколько обработчиков одного приоритета сработали на одно событие: каждый выполняется параллельно со своей независимой копией, и только `mark_processed` обработчика блокирует последующие — проверьте условия регистрации ваших обработчиков

## Хранилище и базы данных

### Ошибка `database is locked` возникает повторно?

Взаимоисключение блокировок в SQLite возникает только между операциями **записи и записи** (в режиме WAL чтение и запись не блокируют друг друга). При частом срабатывании проверяйте в следующем порядке:

1. **Долгие транзакции**: платформа выводит предупреждение для транзакций, удерживающих блокировку дольше 1 с, с указанием места их открытия (`транзакция удерживает блокировку x.xx с ...`) — руководствуясь предупреждением, выносите медленные операции за пределы блока транзакции
2. **Блокировка синхронным API**: перенесите точки вызова, указанные в предупреждении `синхронный API хранилища вызван в асинхронном контексте`, на асинхронные методы с префиксом a (`set` → `aset`) — таймауты handler'ов имеют ту же первопричину и решаются тем же способом, см. шаги 1 и 2 данного списка
3. **Ожидание в очереди на блокировку записи**: увеличьте значение `ErisPulse.storage.sqlite.busy_timeout` (вступает в силу после перезапуска)
4. Если проблема не решена → полную матрицу диагностики см. в [Бэкендах хранилища](../advanced/storage-backends.md)

### После обновления при записи возникает ошибка `StorageOperationError`?

Начиная с 2.12.0 при сбое записи **выбрасывается исключение, а не молча возвращается `False`** — следуя [руководству по миграции при обновлении](migration.md), перейдите на try/except.

## Среда выполнения

### Массовые таймауты обработчиков (handler) / бот периодически не реагирует?

Типичная первопричина: **внутри handler'а вызывается синхронный API хранилища** (каждый вызов блокирует цикл событий до завершения). Признаки: срабатывающее с ограничением частоты предупреждение `синхронный API хранилища вызван в асинхронном контексте` + массовый всплеск таймаутов handler'ов. Решение: мигрируйте указанные в предупреждениях места вызовов на `aset` / `aget` / `aExecute` (см. [руководство по обновлению и миграции](migration.md)).

### Что делать при постоянном росте потребления памяти?

1. Включите `ErisPulse.framework.memory_tracing = true` (включать для диагностики, в обычном режиме держать выключенным) — в `/metrics` и снимках памяти будут выводиться отслеживаемая память и точки наибольших выделений
2. Наблюдайте за трендом снимков в логах циклов GC (`log_snapshot`); активная задача GC фреймворка автоматически выполняет полную сборку при росте памяти
3. Рост памяти после интенсивного использования горячей перезагрузки: начиная с 2.12.1 цепочка выгрузки выполняет размораживание и сборку (слепая зона `gc.freeze` в старых версиях исправлена) — обновите фреймворк
4. Неограниченный рост контейнеров самого модуля — зона ответственности модуля: регистрируйте принадлежащие ресурсы через owner-контекст (см. [систему владения ресурсами](../advanced/ownership.md))

### Модуль «исчез» после горячей перезагрузки?

При выгрузке во время горячей перезагрузки отменяются принадлежащие задачи и освобождаются принадлежащие ресурсы; если модуль самостоятельно создаёт задачи/потоки вне `on_unload` и не регистрирует их принадлежность, фреймворк не сможет их подстраховывать — создавайте их единообразно через `self.spawn()` / `spawn_background(owner=...)` (см. [систему владения ресурсами](../advanced/ownership.md)).

## Конфигурация и развертывание

### Изменили конфигурацию, но изменения не применились?

- Ключи с **поддержкой горячей перезагрузки** (например, `cross_account_policy`, `event_dedupe`, `memory_tracing`, параметры GC) применяются сразу после изменения
- Ключи, **требующие перезапуска** (`storage.use_global_db`, `storage.sqlite.busy_timeout`, router cors/security), при изменении вызывают от фреймворка предупреждение «для вступления в силу требуется перезапуск процесса» — увидели предупреждение, выполните перезапуск; изменение `storage.backend` также требует перезапуска (в настоящее время предупреждение не выводится, не забудьте перезапустить после изменения)
- Синтаксическая ошибка во время редактирования: фреймворк сохраняет последнюю действительную конфигурацию и выводит диагностику (пустая конфигурация транслироваться не будет)

### После `epsdk restart` в контейнере контейнер завершает работу?

Команда restart внутри контейнера (PID 1) была изменена: теперь она отправляет `SIGUSR1`, запускающий мягкую перезагрузку внутри процесса — если требуется такое поведение, обновитесь до версии 2.12.0+; полный перезапуск процесса доверьте политике перезапуска контейнера (restart policy).
