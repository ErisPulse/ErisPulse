# Модульное тестирование (ErisPulse-Testing)

> [!TIP]
> **Когда читать эту статью:** при написании автоматизированных тестов для собственного модуля. При необходимости пропустите, это не повлияет на использование других функций.

[ErisPulse-Testing](https://github.com/ErisPulse/ErisPulse-Testing) — официальный инструмент для тестирования:
предоставляет `TestBot`, фабрику тестовых событий, захват и утверждение исходящих сообщений, что делает модульное тестирование таким же простым, как обычные pytest.

```bash
pip install ErisPulse-Testing
```

> Односторонняя зависимость от фреймворка как инструмент разработки, нулевое вмешательство во время выполнения. Для тестов, имитирующих платформу адаптера, используйте `tests/devs/test_adapter.py` из репозитория фреймворка.

## Быстрый старт

```python
import pytest
from ErisPulse.Core.Event.command import command
from ErisPulse_Testing import TestBot, create_command_event

async def test_daily(make_testbot):
    async with make_testbot(prefix="/") as bot:
        @command("daily", cooldown="1d", cooldown_reply="Сегодня уже подписан")
        async def daily(event):
            await event.reply("Подписка успешна!")

        await bot.dispatch(create_command_event("daily", user_id="123"))
        assert bot.last_reply.text == "Подписка успешна！"

        await bot.dispatch(create_command_event("daily", user_id="123"))
        bot.assert_reply_contains("Сегодня уже подписан")   # Второй раз попадаем на кулдаун
```

Рекомендуется использовать `TestBot` в `async with`: при запуске регистрируется MockAdapter (захват всех исходящих сообщений), отключается дедупликация событий, применяются переопределения конфигурации; при выходе автоматически очищаются глобальные состояния фреймворка, тесты не влияют друг на друга.

Сопутствующие pytest fixtures (автоматически доступны после установки):

- `testbot`: стандартный TestBot уровня функции (`platform='test'`, префикс `/`)
- `make_testbot(**kwargs)`: фабрика с пользовательскими параметрами (`prefix` / `config` / `platform` / `bot_id` и т.д.)

Рекомендуется в конфигурации тестового проекта установить `asyncio_mode = "auto"` (`[tool.pytest.ini_options]`),
или добавить `@pytest.mark.asyncio` к тестовым функциям.

## Фабрика событий

| Функция | Описание |
|------|------|
| `create_message_event(text, user_id=..., group_id=None, ...)` | Событие сообщения; если `group_id` отсутствует, это личное сообщение |
| `create_command_event("roll 3", prefix="/")` | Командное сообщение (автоматически добавляет префикс, если уже есть — не повторяет) |
| `create_notice_event(type, ...)` | Уведомление (например, `friend_add`) |
| `create_request_event(type, ...)` | Запрос (например, заявка в друзья) |
| `create_meta_event("connect", ...)` | Мета-событие (например, `connect` позволяет включить бота) |

Все события имеют уникальный id (uuid), что избегает дедупликации в фреймворке.

Важно: сгенерированные события **не содержат оригинальных платформенных данных** (`event.get_raw()` возвращает пустой словарь). Для определения сценариев (например, групповой чат или личный чат) используйте доступоры `event.is_group_message()` / `event.get_detail_type()` / `event.get_group_id()` и т.д., не читайте raw.

## API TestBot

### Диспетчеризация

```python
trace = await bot.dispatch(event)          # Диспетчеризация и ожидание обработки, возвращает цепочку решений
await bot.dispatch(event, drain=False)     # Первая взаимодействующая отправка: без ожидания (wait_reply обработчики остаются активными)
await bot.send_message("Привет")             # Упрощённый способ отправки сообщения
await bot.reply_as("18", user_id="u1")     # Симуляция ответа пользователя (автоматически ожидает готовности waiter)
```

`dispatch()` после эмитирования собирает все обработчики Task, возвращает сразу после завершения обработки — **в тестах не нужно использовать sleep**.

### Утверждения исходящих сообщений

```python
bot.replies                # Все исходящие (список SentMessage)
bot.last_reply.text        # Текст последнего ответа
bot.replies_to("123")      # Фильтрация по цели
bot.clear_replies()        # Изоляция утверждений между этапами
bot.assert_replied()                       # Существование исходящих сообщений
bot.assert_replied(contains="Подписка", to="123")
bot.assert_not_replied()                   # Нет исходящих сообщений
bot.assert_reply_contains("Подписка успешна")       # Существование исходящих сообщений, содержащих указанный текст
await bot.wait_for_reply(timeout=2)        # Ожидание асинхронного ответа
```

Поля `SentMessage`: `text` (первый текстовый сегмент), `segments` (полный набор сегментов),
`target_type` / `target_id` / `bot_id` (контекст отправки), `has_modifier("at")` и т.д.

### Загрузка модуля

```python
await bot.load_module("MyModule")   # Имя уже зарегистрированного модуля (требуется инициализация entry-point)
await bot.load_module(MyModule)     # Или подкласс BaseModule (автоматически register + load, рекомендуется)
await bot.unload_module("MyModule")
```

Обработчики, зарегистрированные в `on_load`, принадлежат модулю, при выгрузке автоматически удаляются, можно напрямую утверждать "после выгрузки команда не работает".
Важно: строковая форма **не выполняет scan entry-point** (TestBot не инициализирует процесс обнаружения фреймворка); для тестирования модулей с мягкими зависимостями передавайте объект класса (или самостоятельно используйте `module.register` и передавайте имя).

### Замена зависимостей (требуется EP>=2.9.0-dev)

```python
with bot.patch_dependency(get_session, fake_session) as mock:
    await bot.dispatch(create_command_event("query"))
    assert mock.called
```

Заменяется функция, объявленная в `Depends(get_session)` в таблице команд, автоматически восстанавливается при выходе из `with`.

### Переопределение конфигурации

```python
bot = TestBot(prefix="//", config={
    "ErisPulse.event.command.case_sensitive": False,
    "MyModule.api_key": "test-key",     # Конфигурация модуля (self.cfg доступна для чтения)
})
```

Конфигурация внедряется на уровне памяти, префикс команды и т.п. применяются немедленно. Два важных замечания:

1. **Запись на диск**: переопределение будет сохранено в `config/config.toml` по стратегии отложенной записи фреймворка (по умолчанию около 5 секунд) — если проект находится в репозитории, добавьте `config/` в `.gitignore`;
2. **Конфликт с конфигурацией, записанной во время выполнения (известное ограничение)**: если модуль записывает конфигурацию целиком (`self.cfg = ...`, например, подписки), и здесь переопределяются отдельные параметры, возникает проблема согласованности ConfigManager — модуль может не видеть переопределённые значения, а переопределение может быть перезаписано при записи на диск (исправлено в ErisPulse 2.9.0-dev.2, в 2.8.x всё ещё актуально). В тестах, где используется "запись конфигурации во время выполнения", в 2.8.x рекомендуется сбрасывать соответствующие секции конфигурации в fixture целиком.

## Цепочка диспетчеризации (для отладки "почему команда не сработала"; требуется EP>=2.9.0-dev)

`dispatch()` возвращает `DispatchTrace` — цепочку причинно-следственных связей каждого этапа диспетчеризации:

```python
trace = await bot.dispatch(create_command_event("dailyx", user_id="123"))

trace.verdict        # executed / rejected / dropped / failed / no_match / passed
trace.explain()      # Пошаговое объяснение причинно-следственных связей (текущий язык)
trace.command        # Найденная команда (None, если не найдена)
trace.steps("cooldown")  # Фильтрация по этапу

trace.assert_executed("daily")  # Утверждение выполнения (при ошибке выводится полная цепочка)
trace.assert_rejected()         # Утверждение отказа по правилам доступа
trace.assert_dropped()          # Утверждение отбрасывания (например, кулдаун)
trace.assert_no_match()         # Утверждение отсутствия совпадения с командой
```

Покрытие проверок: текст команды, совпадение команды (при отсутствии совпадения — предложение по исправлению), область действия, ACL пользователя, проверка владельца, функции прав, отбрасывание из-за кулдауна, парсинг параметров, результат выполнения, отрицание промежуточными обработчиками.

В продакшене доступны встроенные средства фреймворка `ErisPulse.Core.Event.trace` (`start_dispatch_trace()` / `format_dispatch_trace()`) для сбора и отображения цепочки диспетчеризации.
