# Тестирование модулей (ErisPulse-Testing)

> [!TIP]
> **Когда читать этот документ**: когда вы пишете автоматические тесты для собственного модуля. Если это не требуется — пропустите, на использование остальных функций это не влияет.


[ErisPulse-Testing](https://github.com/ErisPulse/ErisPulse-Testing) — официальный набор инструментов для тестирования:
предоставляет `TestBot`, фабрики тестовых событий, перехват исходящих сообщений и средства для проверок (assertions),
делая тестирование модулей таким же простым, как написание обычного pytest.

```bash
pip install ErisPulse-Testing
```

> Инструмент этапа разработки с односторонней зависимостью от фреймворка и нулевым вмешательством во время выполнения. Для smoke-тестов с реальным подключением к платформам адаптеров используйте `tests/devs/test_adapter.py` из репозитория фреймворка.

## Быстрый старт

```python
import pytest
from ErisPulse.Core.Event.command import command
from ErisPulse_Testing import TestBot, create_command_event

async def test_daily(make_testbot):
    async with make_testbot(prefix="/") as bot:
        @command("daily", cooldown="1d", cooldown_reply="Сегодня уже отмечено")
        async def daily(event):
            await event.reply("Успешная отметка!")

        await bot.dispatch(create_command_event("daily", user_id="123"))
        assert bot.last_reply.text == "Успешная отметка!"

        await bot.dispatch(create_command_event("daily", user_id="123"))
        bot.assert_reply_contains("Сегодня уже отмечено")   # второй вызов попадает в кулдаун
```

`TestBot` рекомендуется использовать с `async with`: при запуске регистрируется MockAdapter (перехватывает все исходящие сообщения), отключается дедупликация событий и применяются переопределения конфигурации; при выходе автоматически очищается глобальное состояние фреймворка, поэтому тесты не влияют друг на друга.

Сопутствующие pytest-фикстуры (доступны автоматически после установки):

- `testbot`: стандартный TestBot уровня function (platform=`test`, префикс `/`)
- `make_testbot(**kwargs)`: фабрика с настраиваемыми параметрами (`prefix` / `config` / `platform` / `bot_id` ...)

Рекомендуется задать в конфигурации тестового проекта `asyncio_mode = "auto"` (`[tool.pytest.ini_options]`) или добавить к тестам декоратор `@pytest.mark.asyncio`.

## Фабрики событий

| Функция | Описание |
|------|------|
| `create_message_event(text, user_id=..., group_id=None, ...)` | Событие сообщения; если `group_id` пуст — личное сообщение |
| `create_command_event("roll 3", prefix="/")` | Командное сообщение (префикс добавляется автоматически, при наличии префикса повторно не добавляется) |
| `create_notice_event(type, ...)` | Событие уведомления (например, `friend_add`) |
| `create_request_event(type, ...)` | Событие запроса (например, заявка в друзья) |
| `create_meta_event("connect", ...)` | meta-событие (`connect` переводит бота в онлайн) |

Все события используют уникальный `id` на основе uuid, что естественным образом обходит дедупликацию событий фреймворка.

Примечание: синтетические события **не содержат исходных платформенных данных** (`event.get_raw()` возвращает пустой dict). Для определения сценариев типа группового или личного чата используйте аксессоры `event.is_group_message()` / `event.get_detail_type()` / `event.get_group_id()` и т.д., не читайте raw.

## TestBot API

### Диспетчеризация

```python
trace = await bot.dispatch(event)          # диспетчеризация с ожиданием завершения обработчиков, возвращает цепочку решений
await bot.dispatch(event, drain=False)     # первое сообщение интерактивного сценария: без ожидания (обработчик wait_reply работает постоянно)
await bot.send_message("Привет")           # быстрый способ диспетчеризации сообщения
await bot.reply_as("18", user_id="u1")     # имитация ответа пользователя в wait_reply (автоматически ждёт готовности waiter)
```

`dispatch()` после emit собирает (gather) все запущенные задачи обработчиков — возврат означает завершение обработки, поэтому **в тестах не нужен sleep**.

### Проверки исходящих сообщений

```python
bot.replies                # все исходящие (список SentMessage)
bot.last_reply.text        # текст последнего ответа
bot.replies_to("123")      # фильтрация по адресату
bot.clear_replies()        # изоляция проверок между этапами
bot.assert_replied()                       # есть исходящие
bot.assert_replied(contains="отметка", to="123")
bot.assert_not_replied()                   # нет ни одного исходящего
bot.assert_reply_contains("Успешная отметка")  # есть исходящее, содержащее указанный текст
await bot.wait_for_reply(timeout=2)        # дождаться появления асинхронного ответа
```

Поля `SentMessage`: `text` (первый text-сегмент), `segments` (полные сегменты сообщения), `target_type` / `target_id` / `bot_id` (контекст отправки), `has_modifier("at")` и т.д.

### Загрузка модулей

```python
await bot.load_module("MyModule")   # имя зарегистрированного модуля (требуется sdk.init() фреймворка для обнаружения entry-point)
await bot.load_module(MyModule)     # или подкласс BaseModule (автоматические register + load, рекомендуется)
await bot.unload_module("MyModule")
```

Команды и обработчики событий, зарегистрированные внутри `on_load`, принадлежат модулю и автоматически очищаются при выгрузке, что позволяет напрямую проверять, что «после выгрузки команда перестаёт срабатывать».
Примечание: строковая форма **не выполняет сканирование entry-point** (TestBot не инициализирует процесс обнаружения фреймворка); для тестирования модулей, являющихся мягкими (необязательными) зависимостями, передавайте напрямую объект класса (или самостоятельно выполните `module.register` и передайте имя).

### Подмена зависимостей (требуется EP>=2.9.0-dev)

```python
with bot.patch_dependency(get_session, fake_session) as mock:
    await bot.dispatch(create_command_event("query"))
    assert mock.called
```

Заменяется функция, на которую ссылается объявление `Depends(get_session)` в реестре команд; при выходе из `with` всё автоматически восстанавливается.

### Переопределение конфигурации

```python
bot = TestBot(prefix="//", config={
    "ErisPulse.event.command.case_sensitive": False,
    "MyModule.api_key": "test-key",     # конфигурация модуля (доступна через self.cfg)
})
```

Инжектируется через слой конфигурации в памяти, префикс команд и т.п. вступают в силу сразу благодаря горячему обновлению. Два замечания:

1. **Запись на диск**: переопределения в соответствии со стратегией отложенной записи фреймворка (по умолчанию около 5 секунд) попадают в `config/config.toml` в cwd — добавьте `config/` в `.gitignore` репозитория тестируемого проекта;
2. **Конфликт с записью конфигурации модулем во время выполнения (известное ограничение)**: когда тестируемый модуль записывает конфигурацию целыми секциями (`self.cfg = ...`, например список подписок) одновременно с точечными переопределениями здесь, возникает проблема согласованности чтения/записи в ConfigManager — при чтении целой секцией модуль может не видеть переопределённых значений, а переопределения могут быть перезаписаны при записи на диск целой секцией (исправлено в ErisPulse 2.9.0-dev.2, в 2.8.x проблема сохраняется). Для тестов, связанных с «записью конфигурации во время выполнения», в 2.8.x рекомендуется в fixture сбрасывать соответствующие секции конфигурации путём записи целой секцией.

## Цепочка решений диспетчеризации (диагностика «почему команда не сработала»; требуется EP>=2.9.0-dev)

`dispatch()` возвращает `DispatchTrace` — причинно-следственную цепочку каждой точки принятия решений при текущей диспетчеризации:

```python
trace = await bot.dispatch(create_command_event("dailyx", user_id="123"))

trace.verdict        # executed / rejected / dropped / failed / no_match / passed
trace.explain()      # построчное причинно-следственное объяснение (на текущем языке)
trace.command        # имя совпавшей команды (None, если совпадения нет)
trace.steps("cooldown")  # записи решений, отфильтрованные по этапу

trace.assert_executed("daily")  # проверить выполнение (при неудаче прикладывает полную цепочку решений)
trace.assert_rejected()         # проверить отклонение решением класса прав доступа
trace.assert_dropped()          # проверить тихое отбрасывание (кулдаун и т.п.)
trace.assert_no_match()         # проверить отсутствие совпадения команды
```

Охват решений: проверка текста команды, совпадение команды (при несовпадении — подсказки по опечаткам), scope, ACL пользователя, проверка владельца, функции прав, тихое отбрасывание по кулдауну, разбор аргументов, результат выполнения, вето middleware.

В производственной среде для сбора и отображения цепочки решений также доступен встроенный в фреймворк `ErisPulse.Core.Event.trace` (`start_dispatch_trace()` / `format_dispatch_trace()`).
