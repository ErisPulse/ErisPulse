# Руководство по диагностике модулей

> [!TIP]
> **Когда читать эту статью**: когда бот "не реагирует" — модуль установлен, но не загружен, отправлено сообщение, но нет ответа, обработчик события не срабатывает, после перезагрузки изменений кода поведение осталось прежним, модуль включен, но события не поступают — выберите подходящий сценарий по симптомам. Если не требуется — пропустите, это не повлияет на другие функции.

Когда модуль "не реагирует", используйте подходящий сценарий для диагностики; первые три сценария имеют диагностические инструменты, которые дают прямой вывод:

| Симптом | Инструмент диагностики | Уровень диагностики |
|--------|------------------------|---------------------|
| Модуль не загружен | `ErisPulse.runtime.explain_module(name)` | Проверка цепочки регистрации и загрузки |
| Событие не обрабатывается | `ErisPulse.runtime.explain_event(event)` | Проверка входной точки распределения |
| Команда не запускается | Цепочка принятия решения о распределении (тестовая `DispatchTrace` / встроенный в фреймворк `trace`) | Цепочка определения команды |

Два диагностических функции являются **чистыми чтениями**, не изменяют состояние, могут вызываться в любое время; возвращают машинно-читаемый словарь, который можно отобразить в человеко-читаемый текст с помощью `format_report()`.

## Сценарий 1: Модуль не загружен

```python
from ErisPulse.runtime import explain_module, format_report

report = explain_module("MyModule")
print(format_report(report))
```

`explain_module()` проверяет пошагово и выдает вывод, охватывающий следующие причины:

| Проверяемый элемент | Описание |
|---------------------|----------|
| Не зарегистрирован | Пакет не установлен, неверное имя группы entry-point или имя регистрации не совпадает с именем запроса |
| Ленивая загрузка не инициализирована | **Нормальное состояние, а не ошибка**: ленивые модули инициализируются в первый раз при вызове (`module.call` / запуск команды и т.д.) |
| Отключена в конфигурации | `ErisPulse.modules.status.<имя модуля> = false` (если не настроено — по умолчанию включено) |
| Зависимости не загружены | В списке `depends` модуля есть модули, которые не готовы |
| Несовместимая версия SDK | В метаданных модуля указано `min_sdk_version`, превышающее текущую версию фреймворка |
| Ошибка в on_load | Регистрация прошла успешно, но модуль не загружен и нет вышеуказанных причин — проверьте лог запуска на записи ERROR, соответствующие имени модуля |

Возвращаемый словарь имеет структурированные поля: `registered` / `loaded` / `lazy` / `enabled` (значение `None` означает, что по умолчанию включено, если не настроено) / `missing_dependencies` / `sdk_version_ok` / `conclusion` (однострочное заключение) / `reasons` (список причин).

## Сценарий 2: Событие не обрабатывается

```python
from ErisPulse.runtime import explain_event, format_report

report = explain_event(event)   # Обработчик внутри Event или исходный словарь события
print(format_report(report))
```

`explain_event()` выводит по порядку фактических проверок входной точки:

1. **Адаптер платформы не зарегистрирован**: экземпляр адаптера для `platform` отсутствует — событие не попадает в фреймворк.
2. **Отклонено из-за действия области**: пользователь / сессия / Bot / адаптер заблокированы — событие полностью отбрасывается на входной точке. Настройки области см. в [конфигурации модуля](../user-guide/configuration.md).
3. **Модуль заблокирован сессией**: различие между `available_modules` (доступен) и `blocked_modules` (заблокирован областью).
4. **Текст похож на команду, но не соответствует**: текст с префиксом команды, но не соответствует ни одной зарегистрированной команде — проверьте настройки префикса и названия команды.

Если все проверки входной точки пройдены, но реакции нет, вывод указывает на дальнейшую проверку двух мест:

- **Фильтры обработчика**: условия `detail_type` / `pattern=` / `regex=` не выполняются;
- **Промежуточное ПО отклоняет**: промежуточное ПО, явно возвращающее `False`, отбрасывает событие на уровне события и вызывает хук жизненного цикла `adapter.event.blocked` (с именем промежуточного ПО и полным событием) — можно зарегистрировать этот хук для аудита "кто отбросил событие".

## Сценарий 3: Команда не запускается (цепочка принятия решения о распределении)

Для того чтобы сообщение с префиксом действительно выполнило команду, необходимо последовательно пройти: определение текста команды → соответствие команде (если не соответствует, приводится предложение по исправлению) → область → ACL пользователя → проверка владельца → функция разрешения → охлаждение / ограничение скорости / ограничение использования → отклонение устаревших команд и уведомление → парсинг параметров → выполнение. Фреймворк фиксирует каждый этап принятия решения в причинно-следственной цепочке и дает заключение о том, почему команда не была запущена.

### В тестировании: TestBot.dispatch возвращает DispatchTrace

Рекомендуется использовать тесты для воспроизведения проблемы и непосредственно читать причинно-следственную цепочку (использование инструмента см. в [модульном тестировании](testing.md)):

```python
trace = await bot.dispatch(create_command_event("dailyx", user_id="123"))

trace.verdict          # executed / rejected / dropped / failed / no_match / passed
print(trace.explain()) # Пошаговое объяснение причин (текущий язык)
trace.assert_no_match()
```

### Встроенный в фреймворк модуль trace

Цепочка принятия решения предоставляется `ErisPulse.Core.Event.trace` и имеет **нулевые накладные расходы** — если не в контексте сбора данных, этапы принятия решения просто пропускаются, производственный путь не замечает этого:

```python
from ErisPulse.Core.Event import (
    start_dispatch_trace,
    format_dispatch_trace,
    final_verdict,
)

with start_dispatch_trace() as records:
    ...  # Сбор данных о распределении в контексте сбора (включая производные задачи обработчиков)

print(format_dispatch_trace(records))   # Причинно-следственная цепочка в человеко-читаемом виде (текущий язык)
print(final_verdict(records))           # Общее заключение
```

Значения `final_verdict()`:

| Заключение | Значение |
|------------|----------|
| `executed` | Команда выполнена |
| `rejected` | Отклонена по правилам разрешения (область / ACL / владелец / функция разрешения) |
| `dropped` | Тихо отброшена (охлаждение / ограничение скорости / использование / отклонение промежуточным ПО) |
| `failed` | Ошибка выполнения |
| `no_match` | С префиксом, но не соответствует ни одной команде |
| `passed` | Не текст команды, передан обработчику сообщений |

Запись представлена в виде машинно-читаемого словаря (`stage` / `verdict` / `message_key` / `params`), при пользовательском отображении можно фильтровать по `stage` (например, только `cooldown`).

### Различение статуса тихого отбрасывания

При срабатывании `cooldown=` / `rate_limit=` / `usage_limit=` по умолчанию команда отбрасывается тихо (команда все еще учитывается, не передается более низкому приоритету обработчикам), что может быть ошибочно интерпретировано как "команда не работает": наблюдается, что у некоторых пользователей работает, у других — нет ответа, и в цепочке принятия решения появляется соответствующая запись `stage` с `dropped`. Команда с `deprecated=` при вызове автоматически возвращает текст об устаревании (если `deprecated_reject=True`, выполнение отклоняется).

## Сценарий 4: Изменения кода после reload по-прежнему ведут себя как раньше (2.11+)

Проверьте по порядку:

1. **Проверьте возвращаемое значение и место сбоя**: если `reload` / `load` возвращает `False`, вызовите `sdk.module.last_error("имя модуля")` — вернется исключение и полный traceback (включая номер строки ошибки), без необходимости просматривать файлы логов; `module.get_info(имя)["last_error"]` — аналогичный источник.
2. **Синтаксические ошибки не приводят к отключению**: `reload` выполняет предварительную проверку синтаксиса перед отключением, при неудаче отказывает (старый экземпляр продолжает обслуживать), в логах указывается файл + строка; исправьте синтаксис и повторите `reload`.
3. **Предупреждение о неизменности идентичности**: если в логах появляется "после перезагрузки идентичность кода не изменилась" или событие `identity_changed: false`, это означает, что в процессе все еще выполняется старый код (часто встречается с C-расширениями и т.д., где невозможно очистить кэш) — такие модули требуют перезапуска фреймворка.
4. **Убедитесь, что источник модуля можно перезагрузить**: модули, зарегистрированные во время выполнения (`sdk.module.register()`), если класс определен в `__main__` / входном скрипте, отклоняют перезагрузку (предупреждение стража); переместите класс в загружаемый модуль.
5. **Ленивые модули активированы принудительно**: перезагрузка активирует модули, которые изначально были ленивыми (лог сообщения); модули, находящиеся в спящем режиме, остаются в спящем режиме.

## Сценарий 5: Модуль "включен, но не получает события" (спящий режим ленивой загрузки, 2.11+)

Модули, объявленные с `dormant_after`, автоматически переходят в **спящий режим** после превышения порога бездействия: освобождаются ресурсы во время выполнения, обработчики событий отменяются, поэтому события больше не поступают (исключение составляют события, объявленные в `activate_on` — события сначала пробуждают, затем пересылают).

- Убедитесь, что модуль находится в спящем режиме: в логах ищите "перешел в спящий режим" / событие `module.sleep`, или наблюдайте, что `sdk.module.get_status_summary()` показывает, что модуль больше не в состоянии `loaded`.
- Пробудите немедленно: любое обращение к атрибуту (например, `sdk.имя_модуля.любой_атрибут`) или `await sdk.module.call(...)`.
- Не хотите автоматического перехода в спящий режим: удалите объявление `dormant_after` из `get_load_strategy()`.
- Сохраняется ли состояние: перед переходом в спящий режим вызывается `on_before_unload(reason="dormant")`, если модуль не реализует этот хук для сохранения состояния, при переходе в спящий режим теряется состояние в памяти (аналогично отключению) — для продолжения состояния см. [спящий режим ленивой загрузки](../advanced/lazy-loading.md#спящий-режим-модуля-dormant_after).

## Общие рекомендации

- Перед диагностикой установите уровень логирования на `DEBUG` / `TRACE` (настройки см. в [руководстве для разработчиков](README.md#техники-отладки)), чтобы увидеть внутренние процессы фреймворка, такие как загрузка модулей, регистрация маршрутов, распределение событий;
- `explain_module` / `explain_event` можно вызывать в любое время, они являются чистыми чтениями и не имеют побочных эффектов, подходит для прямого добавления в команды эксплуатации или панели управления;
- В случае проблем с запуском команд сначала напишите тест с `DispatchTrace`, чтобы воспроизвести — `assert_executed` / `assert_rejected` и другие утверждения при неудаче автоматически прикрепляют полную причинно-следственную цепочку.

## Проблема не решена

- **Сначала проверьте известные проблемы**: сравните с [отслеживанием ошибок](../bug-tracker.md), чтобы убедиться, что это не уже известная проблема и ее методы обхода;
- **Отправьте отчет**: при сообщении проблемы на [GitHub Issues](https://github.com/ErisPulse/ErisPulse/issues) приложите вывод `explain_module` / `explain_event`, причинно-следственную цепочку `DispatchTrace` и номер версии фреймворка, это значительно сократит время диагностики;
- **Обсуждение и помощь**: если не уверены, является ли это ошибкой, сначала опишите симптомы и шаги воспроизведения в [Discussions](https://github.com/ErisPulse/ErisPulse/discussions).
