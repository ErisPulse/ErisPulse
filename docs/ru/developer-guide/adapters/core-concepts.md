Если вам нужно лишь начать работу, сначала прочитайте [Введение в разработку адаптеров](getting-started.md), а к этому документу возвращайтесь при возникновении вопросов уровня «почему».

Этот документ объясняет, как работают адаптеры: как AdapterManager регистрирует и распределяет события, что `BaseAdapter` делает за вас при инициализации, как объявлять конфигурацию и поддержку нескольких аккаунтов — если при написании адаптера возникает вопрос «почему нужно писать именно так», ищите ответ здесь.

## Архитектура адаптера

### Отношения между компонентами

```
Прямое преобразование (направление приёма)                      Обратное преобразование (направление отправки)
─────────────────                                           ─────────────────
                                                             
┌──────────────────┐                                        ┌──────────────────┐
│ Платформа-специфич. события │                                        │ Модуль формирует сообщение │
└────────┬─────────┘                                        └────────┬─────────┘
         │                                                           │
         ↓                                                           ↓
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│                  │   │ Адаптер (MyAdapter) │   │ Send.Raw_ob12()  │
│  Converter       │   │ ┌──────────────┐ │   │ (точка входа обратного преобразования)   │
│  (конвертер событий)    │──→│ │              │ │   │                  │
│                  │   │ │              │ │   │                  │
└──────────────────┘   │ └──────────────┘ │   └────────┬─────────┘
                       └──────────────────┘            │
                                │                      ↓
                                ↓              ┌──────────────────┐
                       ┌──────────────────┐    │ Вызов API платформы    │
                       │ Стандартные события OneBot12 │    └────────┬─────────┘
                       └────────┬─────────┘             │
                                │                      ↓
                                ↓              ┌──────────────────┐
                       ┌──────────────────┐    │ Стандартный формат ответа     │
                       │ Система событий         │    └──────────────────┘
                       └────────┬─────────┘
                                │
                                ↓
                       ┌──────────────────┐
                       │ Модуль (обработка событий)  │
                       └──────────────────┘
```

**Основная симметрия**:
- **Прямое преобразование** (Converter): платформа-специфич. события → события OneBot12, оригинальные данные сохраняются в `{platform}_raw`
- **Обратное преобразование** (Raw_ob12): сообщения OneBot12 → вызов API платформы, возвращается стандартный формат ответа

## AdapterManager адаптер-менеджер

`AdapterManager` — это основной компонент адаптерной системы ErisPulse, отвечающий за управление регистрацией, запуском, остановкой и распределением событий всех адаптеров платформ.

### Основные функции

- **Регистрация адаптеров**: Регистрация и управление несколькими адаптерами платформ.
- **Управление жизненным циклом**: Контроль запуска и остановки адаптеров.
- **Распределение событий**: Распределение событий по стандарту OneBot12 и событий оригинальных платформ.
- **Управление конфигурацией**: Управление включением/отключением адаптеров.
- **Поддержка промежуточных обработчиков**: Поддержка промежуточных обработчиков событий OneBot12.

### Основное использование

```python
from ErisPulse import sdk

# Регистрация адаптера (обычно выполняется автоматически загрузчиком)
sdk.adapter.register("myplatform", MyPlatformAdapter)

# Запуск всех адаптеров
await sdk.adapter.startup()

# Запуск указанных адаптеров
await sdk.adapter.startup(["myplatform"])
# Запуск всех адаптеров
await sdk.adapter.startup()

# Получение экземпляра адаптера
my_adapter = sdk.adapter.get("myplatform")
# Или доступ через свойство
my_adapter = sdk.adapter.myplatform

# Остановка всех адаптеров
await sdk.adapter.shutdown()
```

### Запуск и остановка

#### Запуск адаптера

```python
# Запуск всех зарегистрированных адаптеров
await sdk.adapter.startup()

# Запуск указанной платформы
await sdk.adapter.startup(["platform1", "platform2"])
```

**Процесс запуска:**

1. Отправка события жизненного цикла `adapter.start`.
2. Отправка события `adapter.status.change` (starting).
3. Параллельный запуск каждого адаптера.
4. Автоматическая повторная попытка при сбое (стратегия экспоненциальной задержки).
5. Отправка события `adapter.status.change` (started) после успешного запуска.

**Механизм повторных попыток:**

- Первые 4 попытки: 60 секунд, 10 минут, 30 минут, 60 минут.
- С пятой попытки и далее: фиксированный интервал в 3 часа.

#### Остановка адаптера

```python
# Остановка всех адаптеров
await sdk.adapter.shutdown()
```

**Процесс остановки:**

1. Отправка события жизненного цикла `adapter.stop`.
2. Вызов метода `shutdown()` всех адаптеров.
3. Остановка маршрутизирующего сервера.
4. Очистка обработчиков событий.
5. Отправка события жизненного цикла `adapter.stopped`.

### Управление конфигурацией

#### Проверка статуса платформы

```python
# Проверка, зарегистрирована ли платформа
exists = sdk.adapter.exists("myplatform")

# Проверка, включена ли платформа
enabled = sdk.adapter.is_enabled("myplatform")

# Использование оператора in
if "myplatform" in sdk.adapter:
    print("Платформа существует и включена")
```

#### Список платформ

```python
# Получение списка всех зарегистрированных платформ
platforms = sdk.adapter.list_registered()

# Получение списка всех платформ и их статусов
status_dict = sdk.adapter.list_items()
# Возвращает: {"platform1": true, "platform2": false, ...}

# Получение списка включённых платформ
enabled_platforms = [p for p, enabled in status_dict.items() if enabled]
```

### Слушатели событий

#### Стандартные события OneBot12

```python
from ErisPulse import sdk

# Слушатель всех стандартных событий сообщений по OneBot12
@sdk.adapter.on("message")
async def handle_message(data):
    print(f"Получено сообщение OneBot12: {data}")

# Слушатель стандартных событий сообщений для определённой платформы
@sdk.adapter.on("message", platform="myplatform")
async def handle_platform_message(data):
    print(f"Получено сообщение myplatform: {data}")

# Слушатель всех событий
@sdk.adapter.on("*")
async def handle_any_event(data):
    print(f"Получено событие: {data.get('type')}")
```

#### Оригинальные события платформы

```python
# Слушатель оригинальных событий для определённой платформы
@sdk.adapter.on("raw_event_type", raw=True, platform="myplatform")
async def handle_raw_event(data):
    print(f"Получено оригинальное событие: {data}")

# Слушатель оригинальных событий для всех платформ (с использованием подстановочного знака)
@sdk.adapter.on("*", raw=True)
async def handle_all_raw_events(data):
    print(f"Получено оригинальное событие: {data}")
```

#### Механизм распределения событий

При вызове `adapter.emit(event_data)`:

1. **Обработка промежуточными обработчиками**: Сначала выполняются все промежуточные обработчики OneBot12.
2. **Распределение стандартных событий**: Распределяются на соответствующие обработчики стандартных событий OneBot12.
3. **Распределение оригинальных событий**: Если есть оригинальные данные, они распределяются на обработчики оригинальных событий.

**Правила сопоставления:**

- Точное совпадение: `@sdk.adapter.on("message")` сопоставляется только с событием `message`.
- Подстановочный знак: `@sdk.adapter.on("*")` сопоставляется со всеми событиями.
- Фильтрация по платформе: `platform="myplatform"` сопоставляется только с событиями указанной платформы.

### Промежуточные обработчики

#### Добавление промежуточного обработчика

```python
@sdk.adapter.middleware
async def logging_middleware(data):
    """Промежуточный обработчик для логирования"""
    print(f"Обработка события: {data.get('type')}")
    return data  # Обязательно вернуть данные

@sdk.adapter.middleware
async def filter_middleware(data):
    """Промежуточный обработчик для фильтрации событий"""
    # Фильтрация ненужных событий
    if data.get("type") == "notice":
        return None  # При возврате None промежуточная цепочка игнорирует результат, оставляя исходные данные для передачи
    return data  # Обязательно вернуть данные для продолжения передачи
```

#### Соглашение о возвращаемых значениях промежуточного обработчика

| Возвращаемое значение | Поведение |
|-----------------------|-----------|
| `dict`                | Изменение полезной нагрузки события (последующие обработчики получают изменённое событие) |
| `None`                | Пропуск, полезная нагрузка не изменяется (вывод предупреждения — рекомендуется явно `return data`) |
| `False`               | **Отклонение**: событие отбрасывается, не поступает в обработчики и не вызывает побочных эффектов |

Отклонение подходит для сценариев "отбрасывания события на уровне", таких как брандмауэр, ограничение скорости, чёрный список (ранее это можно было реализовать только с помощью обработчиков высокого приоритета). При отклонении фреймворк записывает трассировку и запускает хук жизненного цикла `adapter.event.blocked` (содержит имя промежуточного обработчика `middleware`, полное событие `event`, `platform` / `event_type` / `detail_type`), что помогает выяснить, почему событие не было обработано:

```python
@sdk.adapter.middleware
async def rate_limit_middleware(data):
    """Промежуточный обработчик для ограничения скорости"""
    if _is_rate_limited(data):
        return False  # Отклонение: событие отбрасывается
    data["rate_marked"] = True
    return data

@sdk.lifecycle.on("adapter.event.blocked")
async def on_event_blocked(data):
    print(f"Событие отброшено {data['middleware']}: {data['event_type']}")
```

#### Порядок выполнения промежуточных обработчиков

Промежуточные обработчики выполняются в порядке их регистрации, последние зарегистрированные обработчики выполняются первыми.

> **Внимание**: если промежуточный обработчик возвращает `None` (например, забыли `return data`), фреймворк игнорирует этот результат и сохраняет исходные данные для передачи, при этом выводится предупреждение. Это гарантирует, что ошибка одного промежуточного обработчика не приведёт к прерыванию всей цепочки событий.

```python
# Порядок регистрации
sdk.adapter.middleware(middleware1)  # Выполняется последним
sdk.adapter.middleware(middleware2)  # Выполняется посередине
sdk.adapter.middleware(middleware3)  # Выполняется первым

# Порядок выполнения: middleware3 -> middleware2 -> middleware1
```

## Базовый класс BaseAdapter

### Базовая структура

```python
from dataclasses import dataclass, field
from ErisPulse.Core import BaseAdapter
from ErisPulse.Core.Bases import BaseConfig, BotAccountConfig

@dataclass
class MyConfig(BaseConfig):
    """Конфигурация адаптера (после объявления автоматически управляется фреймворком)"""
    token: str = field(
        default="",
        metadata={
            "description": {"i18n": "my_adapter.token", "default": "Bot Token"},
            "required": True,
            "secret": True,
            "ui": {"widget": "password", "group": "basic", "order": 1},
        },
    )

class MyAdapter(BaseAdapter):
    ConfigClass = MyConfig  # объявление класса конфигурации
    
    # нет необходимости переопределять __init__, фреймворк автоматически обрабатывает:
    # - self.sdk, self.logger
    # - self.cfg (типобезопасный экземпляр конфигурации, читается в реальном времени)
    # - self.Send, self.Request
    
    async def start(self):
        """Запуск адаптера (обязательно к реализации)"""
        cfg = self.cfg  # автоматически загруженная типобезопасная конфигурация
        pass
    
    async def shutdown(self):
        """Остановка адаптера (обязательно к реализации)"""
        pass
    
    async def call_api(self, endpoint: str, **params):
        """Вызов API платформы (обязательно к реализации)"""
        pass
```

### Управление конфигурацией

Фреймворк предоставляет декларативное управление конфигурацией: структура конфигурации определяется через dataclass, а фреймворк автоматически обрабатывает загрузку, валидацию и генерацию шаблонов.

#### Конфигурация одного аккаунта

```python
from dataclasses import dataclass, field
from ErisPulse.Core.Bases import BaseConfig

@dataclass
class TelegramConfig(BaseConfig):
    token: str = field(default="", metadata={
        "description": {"i18n": "telegram.token", "default": "Bot Token"},
        "required": True,
        "secret": True,
        "ui": {"widget": "password", "group": "basic", "order": 1},
    })
    proxy: str = field(default="", metadata={
        "description": {"i18n": "telegram.proxy", "default": "Адрес прокси"},
        "ui": {"widget": "text", "group": "advanced", "order": 10},
    })

class TelegramAdapter(BaseAdapter):
    ConfigClass = TelegramConfig
    
    async def start(self):
        cfg = self.cfg  # типобезопасно, читается в реальном времени
        if not cfg.token:
            raise ValueError("Token не настроен")
        await self._connect(cfg.token, proxy=cfg.proxy)
```

#### Конфигурация нескольких аккаунтов

Базовый класс `BotAccountConfig` предоставляет поля `enabled` и `name`. Подавляющее большинство адаптеров может автоматически получать bot_id из протокола платформы или из ответа на вход, внедряя его в конфигурацию аккаунта при преобразовании событий:

```python
from dataclasses import dataclass, field
from ErisPulse.Core.Bases import BotAccountConfig

# большинство адаптеров: bot_id автоматически получается во время выполнения, настройка не требуется
@dataclass
class MyBotConfig(BotAccountConfig):
    token: str = field(default="", metadata={
        "description": {"i18n": "my_adapter.bot_token", "default": "Token"},
        "required": True,
    })

# если при входе невозможно получить bot_id, можно предложить пользователю указать его в конфигурации
@dataclass
class YunhuBotConfig(BotAccountConfig):
    bot_id: str = field(default="", metadata={
        "description": {"i18n": "yunhu.bot_id", "default": "ID бота"},
        "required": True,
    })
    token: str = field(default="", metadata={
        "description": {"i18n": "yunhu.token", "default": "Token"},
        "required": True,
    })

class MyAdapter(BaseAdapter):
    AccountConfigClass = MyBotConfig
    
    async def start(self):
        for name, account in self.enabled_accounts.items():
            user_id = await self._login(name, account)
            await self.emit_meta("connect", user_id)
```

#### Соглашения о metadata

Metadata поля одновременно служит для генерации комментариев TOML и рендеринга форм WebUI:

```python
metadata = {
    "description": str | dict,  # описание поля (поддержка i18n)
    "required": bool,         # обязательность (валидация + метка обязательности в WebUI)
    "secret": bool,           # конфиденциальность (в WebUI отображается как ***, в журналах маскируется)
    "example": bool,          # флаг «не сохранять на диск»: не записывается в config.toml (исключается из значений по умолчанию и шаблонов),
                              # рендерится только в config.full.example; схема содержит метку "example": true,
                              # мастер настройки CLI по умолчанию пропускает; после ручной установки пользователем сохраняется как обычно
    "min": number, "max": number,  # валидация числового диапазона
    "ui": {                   # конфигурация элементов управления WebUI (старое имя "webui" всё ещё поддерживается)
        "widget": str,        # тип элемента управления: "text" | "switch" | "select" | "number" | "password"
        "group": str,         # группа: "basic" | "advanced" | "connection" и т.д.
        "order": int,         # вес сортировки (меньше — выше в списке)
        "options": list,      # доступные варианты элемента select [{label, value}], label поддерживает i18n
        "placeholder": str | dict,  # заполнитель поля ввода (поддержка i18n)
    },
    "extra": dict,            # дополнительные поля расширения (передаются в схему)
}
```

Все видимые пользователю текстовые поля поддерживают i18n и используют единый формат `{"i18n": "key", "default": "текст"}`,
чистые строки передаются как есть (обратная совместимость). Поддерживаемые i18n-поля:

| Поле | Расположение | Описание |
|------|------|------|
| `description` | field metadata | Описание поля |
| `options[].label` | `ui.options` | Метки вариантов элемента управления select |
| `placeholder` | `ui.placeholder` | Заполнитель поля ввода |
| `group_labels` | `_schema_meta` | Отображаемые названия групп (заголовки разделов Dashboard) |

При использовании i18n необходимо заранее зарегистрировать ключи перевода в системе i18n (подробнее см. [документацию i18n](../../advanced/i18n.md#многоязычность-полей-конфигурации)).

Пример **description / placeholder / options label**:

```python
token: str = field(
    default="",
    metadata={
        "description": {"i18n": "my_adapter.token", "default": "Bot Token"},
        "ui": {
            "widget": "text",
            "placeholder": {"i18n": "my_adapter.token.ph", "default": "Введите Token"},
        },
    },
)
mode: str = field(
    default="a",
    metadata={
        "description": {"i18n": "my_adapter.mode", "default": "Режим"},
        "ui": {
            "widget": "select",
            "options": [
                {"label": {"i18n": "my_adapter.mode.a", "default": "Вариант A"}, "value": "a"},
                {"label": "метка простой строкой", "value": "b"},  # простая строка передаётся как есть
            ],
        },
    },
)
```

Пример **group_labels** (объявляется после определения класса конфигурации):

```python
MyConfig._schema_meta = {
    "group_labels": {
        "basic": {"i18n": "my_adapter.group.basic", "default": "Основные настройки"},
        "advanced": {"i18n": "my_adapter.group.advanced", "default": "Расширенные настройки"},
    }
}
```

`resolve_config_schema()` фреймворка автоматически разрешает i18n-ключи всех перечисленных выше полей в соответствии с текущим языком;
`get_config_schema()` же передаёт i18n-словарь как есть, оставляя его разрешение фронтенду.

#### Автоматическая генерация описаний полей из docstring (v2.8.0+)

Для полей, у которых в metadata не объявлен `description`, фреймворк автоматически извлекает
описание поля из docstring класса конфигурации в качестве запасного варианта; поддерживаются два распространённых стиля (их можно смешивать):

```python
@dataclass
class MyConfig(BaseConfig):
    """
    Конфигурация MyAdapter

    :ivar endpoint: адрес API платформы        # стиль reST
    :ivar timeout: таймаут запроса в секундах
    """

    endpoint: str = "https://api.example.com"   # нет description в metadata → комментарий/описание берётся из docstring
    timeout: int = 30

    # также поддерживается стиль Google (секция Attributes:):
    # Attributes:
    #     endpoint: адрес API платформы
```

Приоритет: **description из metadata > описание поля из docstring > пусто**.
description в виде i18n-словаря не затрагивается (всегда имеет приоритет).

#### Вложенная конфигурация (v2.8.0+)

Когда тип поля — вложенный dataclass, фреймворк обрабатывает его рекурсивно: схема представляется поддеревом
`"type": "table"` + `"fields"` (WebUI рендерит как сворачиваемые вложенные группы), TOML-шаблон рендерится как секция `[подтаблица]`,
а значения по умолчанию / заполнение / валидация / разрешение i18n применяются рекурсивно.

```python
@dataclass
class RetryConfig(BaseConfig):
    """Стратегия повторных попыток

    :ivar max_retries: максимальное число повторных попыток
    """
    max_retries: int = 3
    backoff: float = 0.5

@dataclass
class MyConfig(BaseConfig):
    """Конфигурация MyAdapter"""
    endpoint: str = "https://api.example.com"
    retry: RetryConfig = field(default_factory=RetryConfig)   # секция вложенной конфигурации
```

Сгенерированный TOML-шаблон:

```toml
endpoint = "https://api.example.com"

[retry]
# максимальное число повторных попыток
max_retries = 3
backoff = 0.5
```

> Для вложенных типов рекомендуется использовать прямые аннотации типов; при строковых аннотациях (например, в сценариях отложенного вычисления) необходимо,
> чтобы тип можно было разрешить по имени из глобального пространства имён модуля класса конфигурации, из пространства имён внешних классов `__qualname__` или из атрибутов класса.

#### Поля example, не сохраняемые на диск (v2.8.0+)

```python
gc_interval: int = field(default=300, metadata={"example": True})
```

Поля с `example: True`:

- не записываются в config.toml (исключаются как из шаблонов конфигурации адаптеров/модулей, так и из значений по умолчанию; во время выполнения используются значения по умолчанию из кода)
- рендерятся только в `config.full.example` проекта (для справки пользователю; при необходимости вручную копируются в config.toml)
- в схеме содержат метку `"example": true` (панель сама решает стратегию отображения), мастер настройки CLI по умолчанию их пропускает
- после ручной установки ключа пользователем нормально сохраняются и нормально горячо обновляются (явное намерение пользователя имеет приоритет)

Подходят для «громоздких и редко изменяемых» расширенных параметров конфигурации, сохраняя config.toml пользователя минималистичным.

> ⚠️ `_schema_meta` — это метаданные уровня класса (не поле конфигурации). Если объявлять её
> внутри тела dataclass, необходимо добавить аннотацию `ClassVar` (`_schema_meta: ClassVar[dict] = {...}`),
> иначе dataclass будет считать её обычным полем. Фреймворк уже защитно исключает поля с префиксом
> подчёркивания (они не попадают ни в схему, ни в шаблоны, ни в значения по умолчанию, ни в результаты
> валидации), однако рекомендуется объявлять её корректно.

### Декларативные ключи перевода (v2.7.0+)

Адаптер может, подобно объявлению `ConfigClass`, централизованно объявить ключи перевода через вложенный класс `I18nClass`.
Фреймворк автоматически зарегистрирует все объявленные ключи перевода на этапе `__init__` (до генерации шаблона конфигурации),
гарантируя, что i18n-ключи, на которые ссылаются описания конфигурации, будут доступны при генерации шаблона.

```python
from ErisPulse.Core.Bases import BaseAdapter, BaseI18n, I18nKey

class MyAdapter(BaseAdapter):
    class I18nClass(BaseI18n):
        endpoint: I18nKey = I18nKey(
            default="API Endpoint",
            zh_CN="API-адрес",
            zh_TW="API-адрес",
            en="API Endpoint",
            ja="APIアドレス",
            ru="API адрес",
        )
        token: I18nKey = I18nKey(
            default="Platform Token",
            zh_CN="Токен платформы",
            zh_TW="Токен платформы",
            en="Platform Token",
            ja="プラットフォームトークン",
            ru="Токен платформы",
        )
```

> ``I18nKey.default`` — это **не зависящий от языка запасной текст**, он не регистрируется ни для одного языка.
> Чтобы перевод вступил в силу, необходимо явно передать хотя бы один языковой параметр.

Подробное использование (правила путей ключей, явный параметр key и т.д.) см. в [документации i18n](../../advanced/i18n.md#рекомендуемый-способ-объявление-ключей-перевода-через-i18nclass-v270).

### Декларативные методы расширения событий (v2.7.0+)

Адаптер может через `EventMixin` централизованно объявлять специфичные для платформы методы расширения событий; фреймворк автоматически регистрирует их на текущей платформе.

```python
from ErisPulse.Core import BaseAdapter

class MyAdapter(BaseAdapter):
    class EventMixin:
        def get_chat_name(self):
            """Получить название чата"""
            return self.get("myplatform_raw", {}).get("chat", {}).get("name", "")

        def is_official_message(self):
            """Определить, является ли сообщение официальным"""
            raw = self.get("myplatform_raw", {})
            return raw.get("sender", {}).get("is_official", False)
```

После регистрации объекты событий вызывают эти методы напрямую:

```python
@message.on_group_message()
async def handler(event):
    if event.is_official_message():
        chat_name = event.get_chat_name()
        await event.reply(f"[{chat_name}] Официальное сообщение получено")
```

> Методы расширения событий адаптера регистрируются на его собственной платформе (``self._platform``).
> Если модулю нужны межплатформенные расширения событий, используйте существующий API ``register_event_mixin()``.

#### Разрешение аккаунта

При реализации `call_api` адаптеру необходимо разрешить идентификатор аккаунта в конкретную конфигурацию аккаунта. Фреймворк передаёт привязку аккаунта (результат `Using()` или автоматической привязки по цепочке событий) в `call_api` через стандартное поле `account_id` и автоматически адаптирует её в соответствии с фактическим способом потребления адаптером — можно выбрать любую из трёх форм потребления; фреймворк определяет её по именам параметров сигнатуры и константам в теле функции, независимо от позиции параметров:

```python
# Форма 1 (рекомендуется): стандартное имя в сигнатуре
async def call_api(self, endpoint: str, account_id: str | None = None, **params):
    name, account = self._resolve_account(account_id)
    # name: имя аккаунта, account: экземпляр конфигурации

# Форма 2 (совместимость с существующим кодом): старое имя _account_id, фреймворк автоматически переименовывает account_id в старое имя при передаче
async def call_api(self, endpoint: str, _account_id: str | None = None, **params):
    name, account = self._resolve_account(_account_id)

# Форма 3: извлечение из params в теле функции (распознаётся константным анализом)
async def call_api(self, endpoint: str, **params):
    account_id = params.pop("account_id", None)
    name, account = self._resolve_account(account_id)
```

> Если адаптер не потребляет поле аккаунта, фреймворк удаляет его (чтобы избежать утечки в параметры платформы) и выдаёт одно предупреждение WARNING; одноаккаунтный адаптер может его не потреблять (разрешение откатывается к первому включённому аккаунту).

Стратегия разрешения: совпадение по имени аккаунта → совпадение по полю `bot_id` → совпадение по другим str-полям → первый включённый аккаунт.

#### Горячее обновление конфигурации

Подклассы могут переопределить `on_config_update()` для реакции на изменения конфигурации:

```python
class MyAdapter(BaseAdapter):
    ConfigClass = MyConfig
    
    def on_config_update(self, old_config, new_config):
        if old_config.token != new_config.token:
            self.logger.info("Token обновлён, будет выполнено переподключение")
```

### Процесс инициализации

Фреймворк в `BaseAdapter.__init__(self, sdk=None)` автоматически выполняет следующее:

1. **Ссылка на SDK**: установка `self.sdk`, `self.logger`
2. **Фабрика Send/Request**: создание `self.Send` и `self.Request`
3. **Шаблон конфигурации**: если объявлен `ConfigClass`, автоматически генерируется шаблон конфигурации по умолчанию (при первом запуске)
4. **Шаблон аккаунтов**: если объявлен `AccountConfigClass`, автоматически генерируется шаблон аккаунтов по умолчанию (при первом запуске)
5. **Регистрация EventMixin**: если объявлен `EventMixin`, автоматически регистрируется после того, как `AdapterManager` внедрит имя платформы

Конфигурация читается в реальном времени через `self.cfg` / `self.accounts` (при каждом обращении из хранилища конфигурации считывается актуальное значение). `self.config` остаётся доступен как совместимый псевдоним `self.cfg`.

Большинству адаптеров не требуется переопределять `__init__`. Если нужна кастомная инициализация:

```python
class MyAdapter(BaseAdapter):
    ConfigClass = MyConfig
    
    def __init__(self, sdk=None):
        super().__init__(sdk)  # передать sdk
        self.converter = self._setup_converter()
        self.convert = self.converter.convert
```

### Иерархия наследования

```python
class MyAdapter(BaseAdapter):
```

### Доступные атрибуты

Класс `Send` при вызове автоматически устанавливает следующие атрибуты:

| Атрибут | Описание | Способ установки |
|-----|------|---------|
| `_target_id` | ID цели | `To(id)` или `To(type, id)` |
| `_target_type` | Тип цели | `To(type, id)` |
| `_target_to` | Упрощённый ID цели | `To(id)` |
| `_account_id` | ID аккаунта отправки | `Using(account_id)` |
| `_adapter` | Экземпляр адаптера | Устанавливается автоматически |
| `_at_user_ids` | Список пользователей для @ | `At(user_id)` |
| `_reply_message_id` | ID сообщения для ответа | `Reply(message_id)` |
| `_at_all` | Упоминание всех | `AtAll()` |

> **Рекомендация**: используйте атрибут `self.send_context`, чтобы получить `target_type`, `target_id` и `account_id` одним обращением — это понятнее, чем прямой доступ к переменным экземпляра.

### Вспомогательные методы фреймворка

| Метод/атрибут | Описание |
|-----------|------|
| `self._apply_modifiers(message)` | Объединяет состояние модификаторов At/AtAll/Reply в список сегментов сообщения |
| `self.send_context` | Возвращает словарь `{target_type, target_id, account_id}`; если `account_id` не задан явно, в качестве запасного значения используется аккаунт-инициатор из текущей цепочки диспетчеризации событий |

### Основные методы

Адаптеру достаточно реализовать только `Raw_ob12`; стандартные методы (Text/Image/Voice/Video/File) уже унаследованы от базового класса `SendDSL` и по умолчанию делегируют вызовы ему:

```python
class Send(BaseAdapter.Send):
    def Raw_ob12(self, message, **kwargs):
        """Обязательна к реализации: сегменты сообщений OneBot12 → API платформы"""
        async def _do_send():
            segments = self._apply_modifiers(message)
            return await self._adapter.call_api(
                endpoint="/send_message",
                message=segments,
                **self.send_context,
                **kwargs
            )
        return asyncio.create_task(_do_send())

    # Text/Image/Voice/Video/File уже унаследованы от базового класса и автоматически делегируют Raw_ob12, повторная реализация не требуется
    # Если требуется специфичная для платформы логика, можно переопределить отдельный метод:
    # def Text(self, text: str):
    #     return self.Raw_ob12([{"type": "text", "data": {"text": text}}])
```

## Конвертеры событий

### Процесс конвертации

```
Исходное событие платформы
    ↓
Converter.convert()
    ↓
Стандартное событие OneBot12
```

### Обязательные поля

Все сконвертированные события должны содержать:

```python
{
    "id": "уникальный идентификатор события",          # должен быть одинаковым при повторной отправке того же события тем же аккаунтом (фреймворк использует это для дедупликации)
    "time": 1234567890,           # 10-значная метка времени Unix
    "type": "message/notice/request/meta",
    "detail_type": "подробный тип события",
    "platform": "название платформы",
    "message_id": "ID сообщения",        # обязательно для событий типа message
    "self": {
        "platform": "название платформы",
        "user_id": "ID бота"     # должно совпадать с bot_id
    },
    "{platform}_raw": {...},       # исходные данные (обязательно)
    "{platform}_raw_type": "..."    # исходный тип (обязательно)
}
```

> Идентификатор события `id` должен учитывать аккаунт: при повторной отправке того же события тем же аккаунтом `id` остается прежним, но когда разные аккаунты получают одно и то же групповое сообщение, их `id` должны различаться (например, `f"{self.user_id}:{post_type}:{message_id}"`).

### Повторный прием между аккаунтами (поля, внедряемые фреймворком)

Когда несколько аккаунтов мультиаккаунтного адаптера находятся в одной группе/диалоге, одно и то же физическое сообщение приходит последовательно через каждый аккаунт. При `ErisPulse.framework.cross_account_policy != "off"` фреймворк автоматически выполняет сопоставление на уровне содержимого (та же платформа + тот же диалог + тот же отправитель + тот же `alt_message` в коротком временном окне), адаптеру участвовать в этом не нужно:

- `mark`: в последующие копии внедряется поле верхнего уровня `"multi_receipt": {"event_id": id первого принятого события, "self_id": первый принявший аккаунт}`, после чего они распределяются как обычно; модуль считывает это поле и принимает решение самостоятельно
- `drop`: последующие копии отбрасываются прямо на входе диспетчеризации

`multi_receipt` — необязательное поле, внедряемое фреймворком; Converter адаптера его не создает и не потребляет; при значении политики по умолчанию `off` структура событий полностью соответствует существующему контракту.

#### Распределение обязанностей трехуровневого механизма дедупликации

| Механизм | Конфигурация | Что перехватывает | Критерий определения |
|------|------|----------|----------|
| Идемпотентная дедупликация событий | `ErisPulse.framework.event_dedupe` (по умолчанию вкл.) | Повторные отправки того же id события при переподключении (то же соединение) | `id` события |
| Фильтрация эха собственного аккаунта | `ErisPulse.event.message.ignore_self` (по умолчанию вкл.) | Сообщения самого принимающего аккаунта (отправитель == принимающий аккаунт) | `self.user_id` vs `user_id` |
| Повторный прием между аккаунтами | `ErisPulse.framework.cross_account_policy` (по умолчанию `off`, включается значением `drop`) | **Копии одного и того же физического сообщения, приходящие через другие аккаунты** — когда несколько аккаунтов в одной группе, bot A пишет сообщение, и bot B тоже получает его копию | Сопоставление на уровне содержимого (та же платформа + тот же диалог + тот же отправитель + то же содержимое, короткое временное окно), ключ не содержит self_id |

**Типичный сценарий — повторение сообщения в группе с несколькими аккаунтами**: bot A пишет сообщение, другие аккаунты той же группы (bot B) также получают его копию, и модули повторения видят одно и то же содержимое дважды. После включения `cross_account_policy = "drop"` копии, приходящие через последующие аккаунты, отбрасываются на входе диспетчеризации, и любой модуль видит сообщение не более одного раза.

Семантика ортогональна `ignore_self`; их комбинация определяет, сколько раз сообщение будет видно:

| Комбинация | Сколько раз модуль повторения видит сообщение bot A |
|------|--------------------------|
| `drop` + `ignore_self = true` (по умолчанию) | 0 или 1 раз (если первая копия пришла через собственное соединение A, она перехватывается ignore_self) — **никогда 2 раза** |
| `drop` + `ignore_self = false` | Всегда ровно 1 раз |

> Не рекомендуется расширять семантику `ignore_self` до «исключать все аккаунты на данном устройстве»: эта проверка полагается на `self.user_id` принимаемого события (в период, когда привязка еще не установлена, она не работает — см. выше про границы времени выполнения), тогда как сопоставление между аккаунтами выполняется на уровне содержимого и не зависит от информации self; кроме того, «прием каждым аккаунтом по отдельности» — устоявшаяся зависимость модулей кросс-аккаунтного журналирования / синхронизации, и сужение семантики было бы неявным нарушением. Дедупликацию между аккаунтами следует доверить `cross_account_policy`.

### Пример конвертера

```python
class MyPlatformConverter:
    def convert(self, raw_event):
        """Конвертирует нативное событие платформы в стандартный формат OneBot12"""
        if not isinstance(raw_event, dict):
            return None
        
        # Генерация ID события
        event_id = raw_event.get("event_id") or str(uuid.uuid4())
        
        # Конвертация метки времени
        timestamp = raw_event.get("timestamp")
        if timestamp and timestamp > 10**12:
            timestamp = int(timestamp / 1000)
        else:
            timestamp = int(timestamp) if timestamp else int(time.time())
        
        # Конвертация типа события
        event_type = self._convert_type(raw_event.get("type"))
        detail_type = self._convert_detail_type(raw_event)
        
        # Построение стандартного события
        onebot_event = {
            "id": str(event_id),
            "time": timestamp,
            "type": event_type,
            "detail_type": detail_type,
            "platform": "myplatform",
            "self": {
                "platform": "myplatform",
                "user_id": str(raw_event.get("bot_id", ""))
            },
            "myplatform_raw": raw_event,
            "myplatform_raw_type": raw_event.get("type", "")
        }
        
        return onebot_event
```

## Управление соединениями

### Два корректных способа реализации start()

Адаптерам клиентского режима (WebSocket-клиент, HTTP-опрос и т.д.) необходимо запускать в `start()` резидентный цикл соединения. Фреймворк поддерживает два способа написания — **оба корректны, но выбрать можно только один из них**:

**Способ 1: spawn с немедленным возвратом (рекомендуется)** — через `spawn_client_loop()` цикл планируется как фоновая задача, принадлежащая данной платформе, при этом `start()` сразу возвращает управление:

```python
class MyAdapter(BaseAdapter):
    async def start(self):
        # Задача цикла принадлежит self._platform: при shutdown фреймворк отменяет её автоматически
        self.spawn_client_loop(self._connect_loop())
        # Здесь start() завершается — «запуск = успех», сбои соединения обрабатываются повторами внутри цикла

    async def _connect_loop(self):
        while True:
            try:
                await self._connect_and_receive()   # при разрыве выбрасывается исключение → отсрочка ниже
            except asyncio.CancelledError:
                raise
            except Exception:
                await asyncio.sleep(5)              # самостоятельная отсрочка и переподключение внутри цикла
```

**Способ 2: резидентный** — `start()` напрямую выполняет `await` цикла соединения и никогда не возвращает управление:

```python
class MyAdapter(BaseAdapter):
    async def start(self):
        await self._connect_loop()   # резидентный, не возвращает управление; исключение в цикле = сбой start()
```

Различия и общие черты двух способов:

| | Способ 1: spawn с возвратом | Способ 2: резидентный |
|---|---|---|
| Момент возврата `start()` | сразу после запуска цикла | при выходе/сбое цикла соединения (фреймворк повторяет попытку согласно стратегии отсрочки) |
| Обработка сбоя соединения | самостоятельный перехват и отсрочка внутри цикла | исключение передаётся выше, в цепочку повторных попыток фреймворка |
| Применимые сценарии | требуется быстрый возврат подтверждения запуска (несколько соединений, после регистрации маршрутов нужно запустить другие задачи) | простая реализация с семантикой «соединение = запуск» |

`spawn_client_loop(coro, *, name="client_loop")` — точка входа планирования для способа 1: задача регистрируется по принадлежности к `self._platform`, при `shutdown()` адаптера фреймворк автоматически отменяет её в соответствии с этой принадлежностью, поэтому управлять дескрипторами задач вручную не нужно; неперехваченные исключения внутри цикла автоматически фиксируются в логах (ожидаемые разрывы с последующим переподключением перехватывайте внутри цикла самостоятельно).

> **Единственно ошибочный способ — их смешивание**: после spawn выполнить `await` того же цикла — это лишит `start()` семантики немедленного возврата, а путь отмены задачи станет непредсказуемым.

### Полуготовые базовые классы режимов соединения

Помимо двух способов из предыдущего раздела, для двух самых распространённых режимов соединения фреймворк предоставляет «полуготовые» базовые классы (`ErisPulse.Core.Bases.adapter_patterns`, импортируются напрямую из корневого пакета): вся оркестрация жизненного цикла `start` / `shutdown` выполняется базовым классом, а подкласс реализует только бизнес-хуки.

#### PollingAdapter (HTTP-опрос)

Подходит для платформ с «регулярной выборкой событий клиентом» (типа Telegram getUpdates). Базовый класс в стиле spawn с возвратом запускает резидентный цикл опроса; при сбое выборки сбой автоматически фиксируется в логах и применяется экспоненциальная отсрочка (база — 1 секунда, максимум — 60 секунд, после успеха сбрасывается в ноль; константы `POLLING_ADAPTER_BACKOFF_BASE_SECS` / `POLLING_ADAPTER_BACKOFF_MAX_SECS` можно настроить в `Core/constants.py`):

```python
from ErisPulse import PollingAdapter

class MyAdapter(PollingAdapter):
    # Интервал опроса по умолчанию 5 секунд; после объявления поля poll_interval в ConfigClass приоритет имеет значение из конфигурации (применяется при горячем обновлении)
    poll_interval = 5.0

    async def fetch_events(self):
        """Выбирает пакет нативных событий платформы (исключения обрабатываются базовым классом через отсрочку, try/except не нужен)"""
        resp = await self.sdk.client.get(f"{self.cfg.endpoint}/getUpdates")
        data = await resp.json()
        return data.get("result", [])

    def convert_one(self, raw):
        """Преобразует одно нативное событие в OneBot12; возвращает None для пропуска"""
        return self.converter.convert(raw)

    async def call_api(self, endpoint: str, **params):
        ...  # как у обычного адаптера
```

Минимальный набор для реализации: `fetch_events` / `convert_one` / `call_api`. `start()` сразу возвращает управление после запуска цикла; `shutdown()` не требует реализации в подклассе (цикл опроса автоматически отменяется по принадлежности к owner).

#### WebhookAdapter (HTTP-колбэк)

Подходит для платформ с «активной отправкой колбэков со стороны платформы». `start()` базового класса регистрирует маршрут приёма на роутере фреймворка (итоговый путь `/{имя платформы}/webhook`, метод POST), а регистрация обёрнута в `owner_scope` — при выгрузке адаптера всё автоматически очищается по owner, отменять регистрацию вручную не нужно:

```python
from ErisPulse import WebhookAdapter

class MyAdapter(WebhookAdapter):
    def verify_request(self, request) -> bool:
        """Необязательный хук: проверка колбэка (по умолчанию пропускает; при возврате False базовый класс отвечает 403)"""
        cfg = self.cfg
        if not cfg.token:
            return True
        auth = request.headers.get("authorization", "")
        return auth == f"Bearer {cfg.token}"

    def convert(self, payload):
        """Преобразует полезную нагрузку колбэка в OneBot12; возвращает None для пропуска"""
        return self.converter.convert(payload)

    async def call_api(self, endpoint: str, **params):
        ...  # как у обычного адаптера
```

Минимальный набор для реализации: `convert` / `call_api` (`verify_request` необязателен). Адрес колбэка получают через `sdk.adapter.get_connection_info(platform)` и указывают в панели управления платформы; при неудачной проверке запрос возвращает 403, при ошибке разбора полезной нагрузки — 400, при успехе возвращается `{"status": "ok"}`.

#### Как выбрать между тремя режимами

| Протокол платформы | Наследование | Скаффолд |
|---|---|---|
| Платформа подключается сама (WebSocket-сервер) | `BaseAdapter` | `epsdk create adapter` (по умолчанию ws-server) |
| Мы сами опрашиваем (HTTP-опрос) | `PollingAdapter` | `epsdk create adapter --template polling` |
| Платформа сама присылает данные (HTTP-колбэк) | `WebhookAdapter` | `epsdk create adapter --template webhook` |

Полностью работоспособные примеры см. в репозитории: `examples/example-adapter/` (ws-server), `examples/example-adapter-polling/`, `examples/example-adapter-webhook/`.

### WebSocket-соединение

```python
class MyAdapter(BaseAdapter):
    async def start(self):
        """Регистрация WebSocket-маршрута"""
        router.register_websocket(
            module_name="myplatform",
            path="/ws",
            handler=self._ws_handler,
            auth_handler=self._auth_handler
        )
    
    async def _ws_handler(self, websocket):
        """Обработчик WebSocket-соединения"""
        self.connection = websocket
        
        try:
            while True:
                data = await websocket.receive_text()
                onebot_event = self.convert(data)
                if onebot_event:
                    await self.adapter.emit(onebot_event)
        except WebSocketDisconnect:
            self.logger.info("Соединение разорвано")
        finally:
            self.connection = None
    
    async def _auth_handler(self, websocket) -> bool:
        """Аутентификация WebSocket"""
        token = websocket.query_params.get("token")
        return token == "valid_token"
```

### WebHook-соединение

```python
class MyAdapter(BaseAdapter):
    async def start(self):
        """Регистрация WebHook-маршрута"""
        router.register_http_route(
            module_name="myplatform",
            path="/webhook",
            handler=self._webhook_handler,
            methods=["POST"]
        )
    
    async def _webhook_handler(self, request):
        """Обработчик WebHook-запросов"""
        data = await request.json()
        onebot_event = self.convert(data)
        if onebot_event:
            await self.adapter.emit(onebot_event)
        return {"status": "ok"}
```

> Платформам чисто колбэк-типа не нужно вручную описывать показанную выше оркестрацию регистрации/проверки/очистки — достаточно напрямую унаследоваться от [«полуготового» базового класса `WebhookAdapter`](#полуготовые-базовые-классы-режимов-соединения) и реализовать только `convert` (при желании переопределив `verify_request`).

> **Запрос информации о маршрутах**: маршруты, зарегистрированные адаптером (HTTP, WebSocket, SSE), позволяют получить полный адрес соединения (включающий `base_url` + путь) через `sdk.adapter.get_connection_info(platform)` и `sdk.router.get_module_urls(module_name)`. Подробнее см. [Введение в разработку адаптеров - Информация о соединении и обнаружение маршрутов](getting-started.md#9-информация-о-соединении-и-обнаружение-маршрутов) и [Поддержка SSE](getting-started.md#10-поддержка-sse-server-sent-events).

## Стандартные ответы API

Фреймворк предоставляет методы `make_response()` и `make_error()` для построения стандартизированных ответов, не нужно вручную создавать словарь ответа.

### Успешный ответ

```python
async def call_api(self, endpoint: str, **params):
    try:
        raw_response = await self._platform_api_call(endpoint, **params)
        
        return self.make_response(
            data=raw_response.get("data"),
            message_id=raw_response.get("data", {}).get("message_id", ""),
            raw=raw_response,
        )
    except Exception as e:
        return self.make_error(message=str(e), raw=None)
```

### Ручное построение ответа (старый способ по-прежнему совместим)

```python
async def call_api(self, endpoint: str, **params):
    return {
        "status": "ok",
        "retcode": 0,
        "data": {...},
        "message_id": "msg_id",
        "message": "",
        "myplatform_raw": raw_response
    }
```

## Поддержка нескольких аккаунтов

### Декларативная конфигурация (рекомендуется)

После объявления класса конфигурации с помощью `AccountConfigClass` фреймворк автоматически управляет загрузкой, валидацией и генерацией шаблонов нескольких аккаунтов:

```python
from dataclasses import dataclass, field
from ErisPulse.Core.Bases import BotAccountConfig

@dataclass
class MyBotConfig(BotAccountConfig):
    bot_id: str = field(default="", metadata={"description": "Bot ID", "required": True})
    token: str = field(default="", metadata={"description": "Token", "required": True, "secret": True})

class MyAdapter(BaseAdapter):
    AccountConfigClass = MyBotConfig
    
    async def start(self):
        for name, account in self.enabled_accounts.items():
            self.logger.info(f"Запуск аккаунта {name}: {account.bot_id}")
            await self._connect(name, account)
    
    async def call_api(self, endpoint: str, account_id: str | None = None, **params):
        name, account = self._resolve_account(account_id)
        # Использование полей account.token, account.bot_id и т.д.
```

### Файл конфигурации аккаунтов

```toml
enabled = true

[MyAdapter.accounts.account2]

```

### Отправка с указанием аккаунта

```python
# Указание аккаунта с помощью метода Using
my_adapter = adapter.get("myplatform")

# Через self.user_id из события (рекомендуется, наиболее универсально)
await my_adapter.Send.Using(event["self"]["user_id"]).To("user", "123").Text("Hello")

# Через имя аккаунта
await my_adapter.Send.Using("account1").To("user", "123").Text("Hello")
```

### Связь между идентификатором аккаунта события и Using

Механизм ответа на события во фреймворке автоматически извлекает идентификатор аккаунта из поля `self` события (приоритет у подстановки `account_id`, иначе `user_id`), инъецирует его в `Using` и отправляет. Разработчикам адаптеров необходимо убедиться, что идентификатор аккаунта, формируемый Converter, совпадает с конфигурацией аккаунта (имя аккаунта или поля вроде `bot_id`).

**Поведение инъекции фреймворка**:

```python
# Логика извлечения идентификатора аккаунта фреймворком (приоритет у account_id, user_id в качестве запасного варианта)
account = self.get("self", {}).get("account_id", "") or self.get("self", {}).get("user_id", "")

# Инъекция Using только если идентификатор не пуст
if account:
    send_chain = send_chain.Using(account)
```

> **Ключевой момент**: даже если адаптер использует только одну конфигурацию бота, фреймворк инъецирует её в `Using`, пока Converter правильно устанавливает идентификатор аккаунта. Адаптер должен убедиться, что этот идентификатор совпадает с именем аккаунта или полями вроде `bot_id` в `AccountConfigClass`, чтобы разрешить правильный аккаунт. Если идентификатор пуст, фреймворк не инъецирует `Using`, и отправка обрабатывается как отправка без указания аккаунта — с откатом к первому включённому аккаунту.

Если явно переданный `account_id` не удаётся разрешить, фреймворк записывает WARNING и откатывается к первому включённому аккаунту; `platform` / `account_id` / `account` в WARNING можно использовать для определения источника события, не привязанного к аккаунту.

**Автоматическая привязка внутри цепочки обработки событий**: при вызове методов отправки внутри цепочки обработки события **явный `Using()` не требуется** — фреймворк на входе в цепочку распределения событий инъецирует идентификатор аккаунта, вызвавшего событие, в контекст вызова, и если цепочки `Send` / `Api` / `Request` не указывают аккаунт явно, привязка выполняется на этой основе (явный `Using()` всегда имеет приоритет; в сценариях без контекста события, таких как таймеры / задачи при запуске, сохраняется семантика аккаунта по умолчанию). Автоматическая привязка цепочки событий требует ErisPulse **2.12+**.

> Контракт формирования значений для подстановки `self.user_id` / `self.account_id` события см. в [Стандарте преобразования событий](../../standards/event-conversion.md); постоянное наличие этого поля является предпосылкой семантики отката при разрешении аккаунта — при его отсутствии происходит откат к первому включённому аккаунту, что при нескольких аккаунтах означает «отправку от аккаунта по умолчанию».

## Обработка ошибок

### Повторное подключение

```python
import asyncio

class MyAdapter(BaseAdapter):
    async def start(self):
        retry_count = 0
        max_retries = 5
        
        while retry_count < max_retries:
            try:
                await self._connect_to_platform()
                break
            except Exception as e:
                retry_count += 1
                if retry_count < max_retries:
                    wait_time = min(60 * (2 ** retry_count), 600)
                    self.logger.warning(f"Подключение не удалось, повтор через {wait_time} секунд")
                    await asyncio.sleep(wait_time)
                else:
                    raise
```

### Обработка ошибок API

```python
async def call_api(self, endpoint: str, **params):
    try:
        # Рекомендуется использовать клиент SDK
        from ErisPulse.Core import client
        from ErisPulse.Core.Bases.errors import ClientError, ClientTimeoutError
        resp = await client.post(
            f"https://api.platform.com/{endpoint}",
            json=params,
            max_retries=2,
        )
        response = await resp.json()
        return self._standardize_response(response)
    except ClientTimeoutError:
        self.logger.error(f"Запрос таймаут: {endpoint}")
        return self._error_response("Запрос таймаут", 32000)
    except ClientError as e:
        self.logger.error(f"Ошибка сети: {e}")
        return self._error_response("Ошибка сети", 33000)
    except Exception as e:
        self.logger.error(f"Неизвестная ошибка: {e}")
        return self._error_response(str(e), 34000)
```

> **Обратная совместимость**: код старых адаптеров, использующих `aiohttp.ClientSession`, не затрагивается, по-прежнему можно перехватывать `aiohttp.ClientError`. Два способа могут сосуществовать. Рекомендуется использовать `sdk.client` + систему исключений ErisPulse для нового кода.

## Управление состоянием ботов

AdapterManager включает встроенную систему отслеживания состояния ботов, которая автоматически поддерживает статус онлайн, время активности и метаданные всех зарегистрированных ботов.

### Механизм автоматического обнаружения

Когда адаптер отправляет событие через `adapter.emit()`, фреймворк автоматически проверяет поле `self` в событии:

- **События meta**: выполняют соответствующие действия в зависимости от `detail_type` (connect — регистрация / disconnect — пометка офлайн / heartbeat — обновление времени активности)
- **Обычные события** (message/notice/request): автоматическое обнаружение бота и обновление времени активности

```python
# Любое событие, содержащее поле self, запускает автоматическое обнаружение
await self.adapter.emit({
    "type": "message",
    "platform": "myplatform",
    "self": {"platform": "myplatform", "user_id": "bot123"},
    # ...
})
# Бот "bot123" автоматически зарегистрирован (при первом появлении) и время активности обновлено
```

### Типы Meta-событий

| `detail_type` | Описание | Поведение фреймворка |
|---|---|---|
| `connect` | Подключение бота | Регистрирует бота и запускает событие жизненного цикла `adapter.bot.online` |
| `disconnect` | Отключение бота | Помечает бота офлайн и запускает событие жизненного цикла `adapter.bot.offline` |
| `heartbeat` | Heartbeat бота | Обновляет время активности и метаданные бота |

### Отправка Meta-событий адаптером

Способы отправки (отправка одной строкой через `emit_meta()`, события heartbeat и ручное формирование формата) описаны в разделе [Лучшие практики адаптеров - Управление состоянием ботов и Meta-события](best-practices.md#bot-状态管理与-meta-事件).

Помимо обязательных полей `platform` и `user_id`, поле `self` поддерживает следующие необязательные поля:

| Поле | Описание |

| `user_name` | Имя пользователя бота |
| `nickname` | Никнейм бота |
