# Уровень модели данных (ORM)

> [!TIP]
> **Когда нужно читать эту статью**: при необходимости работы с моделями данных, автоматического создания таблиц или сопоставления отношений. Если нет — пропустите, это не повлияет на использование других функций.

Начиная с версии 2.9.0, фреймворк включает декларативный уровень моделей данных: наследуя `Model` и объявляя поля через `Field`, вы получаете возможность автоматического создания таблиц и CRUD-операций. Модели строятся на базе встроенной системы хранения — SQLite / MySQL / PostgreSQL определяется параметром `ErisPulse.storage.backend`, **смена бэкенда не требует изменений кода моделей**.

## Объявление модели

```python
from ErisPulse.Core.Bases import Model, Field

class User(Model):
    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0, ge=0, le=150)
    role: str = Field(default="user", choices=["user", "admin"])
    tags: list = Field(default_factory=list)          # JSON-столбец, автоматическая сериализация при чтении/записи
    bio: str = Field(default="", description={"i18n": "user.bio", "default": "Биография"})
```

- Имя таблицы по умолчанию — имя класса в snake_case (`UserProfile → user_profile`), можно переопределить через `__tablename__ = "xxx"`
- Ограничения `Field` и декларативные параметры класса конфигурации идентичны (`choices` / `ge` / `le` / `max_length`, `description` поддерживает словарь i18n); движок валидации совпадает с движком валидации конфигурации

## Параметры поля

| Параметр | Описание |
|------|------|
| `default` | Значение по умолчанию (если не задано и не автоинкремент → обязательное поле NOT NULL) |
| `default_factory` | Фабрика для изменяемых значений по умолчанию (например, `list`) |
| `primary_key` | Первичный ключ |
| `autoincrement` | Автоинкрементный первичный ключ (включает `primary_key`, `create` автоматически заполняет обратно) |
| `max_length` | Максимальная длина строки (генерирует `VARCHAR(n)`, проверка при записи) |
| `nullable` | Разрешено ли NULL (по умолчанию False) |
| `index` | Создание обычного индекса |
| `unique` | Уникальное ограничение |
| `choices` / `ge` / `le` | Перечисление / диапазон значений (проверка при записи) |
| `description` | Описание (словарь i18n, формат такой же, как в классе конфигурации) |
| `column_type` | Переопределение определения типа SQL-столбца |

## Создание таблицы и CRUD

```python
await User.create_table()                      #幂等（IF NOT EXISTS）

user = await User.create(name="Alice", age=20) # 插入（自增主键自动回填）
got = await User.get(id=user.id)               # 等值查询首条

users = await User.where(User.age > 18).order_by("-age").limit(10).all()
first = await User.where(User.name == "Alice").first()
total = await User.count(User.age > 18)

user.age = 21
await user.save()                              # 按主键更新（先约束校验）；主键缺失时退化为插入（自增主键同样回填到实例）
await user.delete()                            # 按主键删除

await User.update_all(User.age > 18, role="adult")  # 批量更新
await User.delete_all(User.age > 100)               # 批量删除
```

Выражения запросов поддерживают `> >= < <= == !=`、`in_([...])` и операторы `&` (и) / `|` (или):

```python
await User.where((User.age > 18) & User.name.in_(["Alice", "Bob"])).all()
```

## Транзакции

ORM-запись и чтение используют одну и ту же систему транзакций, что и фреймворк хранилища: если вы находитесь в окружении `storage.atransaction()`, `create` / `save` / `delete` и запросы автоматически используют текущую транзакцию, подтверждая или откатывая транзакцию вместе, без независимого подтверждения.

```python
async with storage.atransaction():
    await User.create(name="Alice")
    ...  # Если в блоке возникнет исключение, INSERT-запрос откатится
```

## Отношения с декларативным классом конфигурации

Объявление моделей и `ConfigClass` (`@dataclass + field(metadata=...)`) **разделяют одну и ту же базовую систему** — таблицу ограничений, движок валидатора (`validate_field_constraints`), регистрацию типов (`python_type_category`); но базовые классы намеренно разделены: поля конфигурации — это обычные значения (TOML-перевод, горячая перезагрузка), поля моделей — это описатели столбцов (доступ к классу = выражение запроса, доступ к экземпляру = значение строки). Один и тот же синтаксис объявления, два разных базовых класса.

### Когда использовать какой тип объявления

| Аспект | Поля конфигурации `field(metadata=...)` | Поля модели `Field()` |
|------|------------------------------|---------------------|
| Сценарий использования | Параметры поведения модуля (мало, человекочитаемо, горячая перезагрузка) | Данные бизнес-объектов (много строк, программное чтение/запись, запросы) |
| Формат хранения | `config.toml` (сохранение комментариев, TOML-перевод) | Таблицы базы данных (автоматическое создание, SQL-диалект) |
| Формат значений | Обычные значения (прямое чтение свойств dataclass) | Описатели (доступ к классу = выражение столбца, доступ к экземпляру = значение строки) |
| Ограничения | `metadata={"choices": ..., "min": ..., "max": ...}` | `Field(choices=..., ge=..., le=..., max_length=...)` |
| Общая базовая система | Движок валидатора + таблица ограничений + регистрация типов (одинаковая) | То же самое |

Эмпирическое правило: **"как модуль работает" — используйте класс конфигурации, "какие данные создал пользователь" — используйте модель**.

## Ограничения и замечания

- Бэкенд определяется глобальной конфигурацией хранилища; модель может переопределить `__storage__` для использования пользовательского экземпляра `BaseStorage` (для тестирования)
- Поля `list` / `dict` (с параметризованными типами, например `list[int]`, `dict[str, int]`) хранятся как текст JSON-столбцов, чтение/запись автоматически сериализуются
- При записи (`create` / `save`) автоматически выполняется проверка ограничений, при ошибке выбрасывается `ValueError` (локализованные сообщения)
- Автоматическое миграция поддерживает сценарий **добавления новых столбцов** (см. ниже); изменение типа столбца и удаление столбцов требуют ручного вмешательства
- При сбое подключения к хранилищу поведение такое же, как у слоя хранилища: фреймворк не падает, после паузы автоматически переподключается

## Автоматическая миграция (второй этап)

`create_table()` при наличии таблицы автоматически сравнивает существующие столбцы с полями модели: **новые поля** автоматически выполняют `ALTER TABLE ADD COLUMN` (удаляя ограничение `NOT NULL`, заполняя NULL для существующих строк), новые столбцы с `index=True` также создают индекс. Не требуется ручной написания скриптов миграции.

```python
# После запуска v1 модели: добавление email / bio
class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0)
    email: str = Field(default="")     # Новое поле: при следующем create_table() будет добавлено
    bio: str = Field(default="")

await User.create_table()              #幂等：仅迁移新增列
```

**Ограничения**: поддерживается только добавление столбцов; изменение первичного ключа, типов столбцов и удаление столбцов требует ручного вмешательства (чтобы избежать ошибочных ALTER).

## Внешние ключи (основа сопоставления отношений)

`foreign_key="table.column"` объявляет внешний ключ на уровне столбца, DDL генерирует `REFERENCES`:

```python
class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id")

    content: str = Field(max_length=255)
```

## Сопоставление отношений (relationship)

В теле класса модели объявляется `relationship()` как атрибут класса, **направление определяется автоматически по месту объявления внешнего ключа**:

```python
from ErisPulse.Core.Bases import Model, Field, relationship

class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)

    posts = relationship("Post", foreign_key="author")   # Внешний ключ в другой таблице → has-many

class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id")
    content: str = Field(max_length=255)

    writer = relationship("User", foreign_key="author")  # Внешний ключ в текущей таблице → belongs-to
```

**has-many**: свойство экземпляра возвращает набор запросов, доступны все возможности `QuerySet`, `create` автоматически заполняет первичный ключ текущей таблицы в столбец внешнего ключа:

```python
alice = await User.get(name="Alice")

posts = await alice.posts.all()                          # Все статьи пользователя
latest = await alice.posts.order_by("-id").first()
total = await alice.posts.count()
hot = await alice.posts.where(Post.content != "").all()  # Дополнительные условия по столбцам другой таблицы
await alice.posts.delete()                               # Удалить только статьи пользователя

new_post = await alice.posts.create(content="hi")        # author автоматически = alice.id
```

**belongs-to**: при `await` получается экземпляр другой модели (если нет соответствия или внешний ключ NULL — возвращается `None`):

```python
post = await Post.get(id=1)
writer = await post.writer          # Экземпляр User или None
await writer.posts.count()          # Двусторонняя связь
```

**Особенности**:

- `related` принимает строку с названием класса (ленивое разрешение по таблице регистрации моделей, порядок объявления не важен) или напрямую передает класс модели
- Запросы отношений и модели используют свои собственные бэкенды хранилища (не поддерживаются JOIN между разными бэкендами — запросы отношений — это отдельные SQL-запросы)
- Запросы отношений не кэшируются, каждый вызов — это немедленный запрос; для произвольных запросов по-прежнему можно использовать `User.where(...)`
