# Уровень модели данных (ORM)

Начиная с версии 2.9.0, фреймворк включает декларативный уровень модели данных: наследуйте `Model` и объявляйте поля с помощью `Field`, чтобы получить автоматическое создание таблиц и функции добавления, удаления, изменения и получения данных. Модели напрямую строятся на основе встроенного слоя хранения — SQLite / MySQL / PostgreSQL определяется конфигурацией `ErisPulse.storage.backend`, **переключение бэкенда не требует изменений в коде моделей**.

## Объявление модели

```python
from ErisPulse.Core.Bases import Model, Field

class User(Model):
    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0, ge=0, le=150)
    role: str = Field(default="user", choices=["user", "admin"])
    tags: list = Field(default_factory=list)          # JSON-столбец, автоматическая сериализация при чтении и записи
    bio: str = Field(default="", description={"i18n": "user.bio", "default": "Биография"})
```

- Имя таблицы по умолчанию берётся из названия класса в snake_case (`UserProfile → user_profile`), можно переопределить с помощью `__tablename__ = "xxx"`
- Ограничения `Field` идентичны конфигурационному классу декларативного стиля (например, `choices` / `ge` / `le` / `max_length`, `description` также поддерживает словарь i18n); движок валидаторов совпадает с движком проверки конфигурации

## Параметры полей

| Параметр | Описание |
|------|------|
| `default` | Значение по умолчанию (обязательно NOT NULL, если не указано и не автоинкремент) |
| `default_factory` | Фабрика значений по умолчанию для изменяемых типов (например, `list`) |
| `primary_key` | Первичный ключ |
| `autoincrement` | Автоинкрементный первичный ключ (является скрытым первичным ключом, значение возвращается после `create`) |
| `max_length` | Максимальная длина строки (генерирует `VARCHAR(n)`, проверка при записи) |
| `nullable` | Разрешить NULL (по умолчанию False) |
| `index` | Создание обычного индекса |
| `unique` | Уникальное ограничение |
| `choices` / `ge` / `le` | Перечисление / числовые диапазоны (проверка при записи) |
| `description` | Описание (словарь i18n, формат аналогичен конфигурационному классу) |
| `column_type` | Переопределение определения типа SQL-столбца |

## Создание таблицы и CRUD

```python
await User.create_table()                      #幂等操作 (IF NOT EXISTS)

user = await User.create(name="Alice", age=20) # Вставка (автоматически заполняется автоинкрементный первичный ключ)
got = await User.get(id=user.id)               # Поиск первой записи по равенству

users = await User.where(User.age > 18).order_by("-age").limit(10).all()
first = await User.where(User.name == "Alice").first()
total = await User.count(User.age > 18)

user.age = 21
await user.save()                              # Обновление по первичному ключу (сначала проверка ограничений); при отсутствии первичного ключа операция сводится к вставке (автоинкрементный первичный ключ также заполняется в экземпляре)
await user.delete()                            # Удаление по первичному ключу

await User.update_all(User.age > 18, role="adult")  # Массовое обновление
await User.delete_all(User.age > 100)               # Массовое удаление
```

Выражения запросов поддерживают `> >= < <= == !=` и `in_([...])`, а также комбинирование с помощью `&` (И) и `|` (ИЛИ):

```python
await User.where((User.age > 18) & User.name.in_(["Alice", "Bob"])).all()
```

## Транзакции

ORM для чтения и записи использует один и тот же маршрутизатор транзакций, который совместно используется с хранилищем фреймворка: при нахождении в окружении `storage.atransaction()`, операции `create` / `save` / `delete` и запросы автоматически используют одну и ту же транзакционную соединение, и все они подлежат единым подтверждению или откату, а не независимому подтверждению.

```python
async with storage.atransaction():
    await User.create(name="Alice")
    ...  # Если в блоке возникнет исключение, вышеуказанный INSERT откатится вместе с ним
```

## Отношение к классам декларативной конфигурации

Объявление моделей и `ConfigClass` (`@dataclass + field(metadata=...)`) **используют одну и ту же базовую систему** — словарь ограничений, движок валидатора (`validate_field_constraints`), регистр категорий типов (`python_type_category`); но базовые классы намеренно разделены: поля конфигурации представляют собой обычные значения (возврат через TOML, горячая перезагрузка при однократной загрузке), поля моделей — это описатели столбцов (доступ к классу = выражение запроса, построчная загрузка экземпляров). Один синтаксис объявления, две отдельные базовые системы.

## Ограничения и замечания

- Бэкенд определяется глобальной конфигурацией хранилища; модель может переопределить это с помощью атрибута класса `__storage__`, задав пользовательский экземпляр `BaseStorage` (для тестирования с подменой зависимостей)
- Поля `list` / `dict` (включая параметризованные генерики, такие как `list[int]` и `dict[str, int]`) хранятся в виде текста JSON в столбце, соответствующем типу контейнера, с автоматической сериализацией при чтении и записи
- Перед записью (`create` / `save`) автоматически выполняется проверка ограничений, при неудаче выбрасывается исключение `ValueError` с локализованным сообщением
- Автоматическое миграция (сравнение схемы) и отображение отношений — функции, доступные в будущих версиях
- При сбое подключения к хранилищу поведение соответствует слою хранилища: фреймворк не падает, после паузы происходит автоматическая повторная попытка подключения
