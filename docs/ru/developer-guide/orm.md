# Модель данных (ORM)

С версии 2.9.0 фреймворк включает декларативный слой модели данных: унаследовавшись от `Model` и объявив поля с помощью `Field`, вы получаете автоматическое создание таблиц и возможности для добавления, удаления, изменения и получения данных. Модели строятся непосредственно на базе встроенной системы хранения — SQLite / MySQL / PostgreSQL определяется настройкой `ErisPulse.storage.backend`, **смена бэкенда не требует изменений кода моделей**.

## Объявление модели

```python
from ErisPulse.Core.Bases import Model, Field

class User(Model):
    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0, ge=0, le=150)
    role: str = Field(default="user", choices=["user", "admin"])
    tags: list = Field(default_factory=list)          # JSON-столбец, автоматическая сериализация при чтении/записи
    bio: str = Field(default="", description={"i18n": "user.bio", "default": "Биография"})
```

- Имя таблицы по умолчанию берётся из имени класса в snake_case (`UserProfile → user_profile`), можно переопределить с помощью `__tablename__ = "xxx"`
- Ограничения `Field` и декларативная конфигурация класса идентичны (`choices` / `ge` / `le` / `max_length`, `description` поддерживает словарь i18n); движок валидации совпадает с тем, что используется для конфигурации

## Параметры поля

| Параметр | Описание |
|----------|----------|
| `default` | Значение по умолчанию (если не задано и не автоинкремент → обязательное поле NOT NULL) |
| `default_factory` | Фабрика для изменяемых значений по умолчанию (например, `list`) |
| `primary_key` | Первичный ключ |
| `autoincrement` | Автоинкрементный первичный ключ (является ключом, значение возвращается после `create`) |
| `max_length` | Максимальная длина строки (генерирует `VARCHAR(n)`, проверка при записи) |
| `nullable` | Разрешить NULL (по умолчанию False) |
| `index` | Генерация обычного индекса |
| `unique` | Уникальное ограничение |
| `choices` / `ge` / `le` | Перечисление / диапазон значений (проверка при записи) |
| `description` | Описание (словарь i18n, формат совпадает с конфигурационным классом) |
| `column_type` | Переопределение SQL-типа столбца |

## Создание таблицы и CRUD

```python
await User.create_table()                      #幂等（IF NOT EXISTS）

user = await User.create(name="Alice", age=20) # Вставка (автоинкрементный ключ автоматически возвращается)
got = await User.get(id=user.id)               # Поиск по первичному ключу

users = await User.where(User.age > 18).order_by("-age").limit(10).all()
first = await User.where(User.name == "Alice").first()
total = await User.count(User.age > 18)

user.age = 21
await user.save()                              # Обновление по первичному ключу (сначала проверка ограничений); если первичный ключ отсутствует, вставляется (автоинкрементный ключ также возвращается в экземпляр)
await user.delete()                            # Удаление по первичному ключу

await User.update_all(User.age > 18, role="adult")  # Массовое обновление
await User.delete_all(User.age > 100)               # Массовое удаление
```

Выражения для запросов поддерживают `> >= < <= == !=` и `in_([...])`, а также `&` (И) / `|` (ИЛИ):

```python
await User.where((User.age > 18) & User.name.in_(["Alice", "Bob"])).all()
```

## Транзакции

Операции ORM и хранилище используют один и тот же маршрутизатор транзакций: при нахождении в транзакции `storage.atransaction()`, `create` / `save` / `delete` и запросы автоматически используют одну и ту же транзакцию, синхронно подтверждаются или откатываются, не выполняют независимые операции.

```python
async with storage.atransaction():
    await User.create(name="Alice")
    ...  # При возникновении исключения в блоке, INSERT откатывается
```

## Отношение к декларативным конфигурационным классам

Объявление модели и `ConfigClass` (`@dataclass + field(metadata=...)`) **используют одну и ту же базовую систему** — одинаковые ограничения, движок валидации (`validate_field_constraints`), регистр типов (`python_type_category`); но классы намеренно разделены: поля конфигурации — обычные значения (TOML-перевод, горячая перезагрузка), поля модели — описатели столбцов (обращение к классу = выражение запроса, экземпляр строки). Один синтаксис объявления, два разных базовых класса.

## Ограничения и замечания

- Бэкенд определяется настройкой хранилища; модель может переопределить `__storage__` для использования пользовательского экземпляра `BaseStorage` (для тестирования)
- Поля `list` / `dict` (включая параметризованные типы, например `list[int]`, `dict[str, int]`) хранятся как текстовые JSON-столбцы, чтение и запись автоматически сериализуются
- Перед записью (`create` / `save`) автоматически выполняется проверка ограничений, при ошибке выбрасывается `ValueError` (локализованное сообщение)
- Автоматическая миграция реализована для сценариев **добавления новых столбцов** (см. ниже); изменение типа столбца, удаление столбца и отношения ORM — функции будущих версий
- При сбое подключения к хранилищу поведение совпадает с поведением хранилища: фреймворк не падает, после паузы автоматически переподключается

## Автоматическая миграция (шаг 2)

`create_table()` при наличии таблицы автоматически сравнивает существующие столбцы с полями модели: **новые поля** автоматически добавляются командой `ALTER TABLE ADD COLUMN` (удаляются ограничения `NOT NULL`, заполняются NULL для существующих строк), новые поля с `index=True` также создаются с индексом. Не требуется ручной миграционный скрипт.

```python
# После выхода v1, модель эволюционирует: добавляются поля email / bio
class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0)
    email: str = Field(default="")     # Новое: при следующем вызове create_table() автоматически добавится столбец
    bio: str = Field(default="")

await User.create_table()              #幂等: миграция только новых столбцов
```

**Ограничения**: поддерживается только добавление столбцов; изменение первичного ключа, типа столбца, удаление столбца требуют ручной обработки (чтобы избежать разрушительных ALTER).

## Внешние ключи (основа для отношений)

Объявление `foreign_key="таблица.столбец"` создаёт ограничение внешнего ключа на уровне столбца, DDL генерирует подфразу `REFERENCES`:

```python
class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id")

    content: str = Field(max_length=255)
```

Внешний ключ — это ограничение DDL-уровня (база данных гарантирует целостность ссылок); ORM-уровень отношений (`relationship` / обратные запросы) — функция будущих версий.
