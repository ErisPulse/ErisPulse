# Уровень модели данных (ORM)

> [!TIP]
> **Когда нужно читать эту статью**: при необходимости работы с моделями данных, автоматического создания таблиц или сопоставления отношений. Если не требуется — можно пропустить, это не повлияет на использование других функций.

> [!NOTE]
> **ORM является нативно асинхронным**: все методы CRUD (`create` / `get` / `save` / `delete` / `create_table` / операции QuerySet) являются `async def`, и их можно вызывать напрямую в цикле событий с помощью `await` — базовый драйвер — aiosqlite / aiomysql / asyncpg (в зависимости от выбранного хранилища), синхронные блокировки отсутствуют. Синхронные `get`/`set` для хранилища ключ-значение — это совместимый слой, не имеющий отношения к ORM.

Начиная с версии 2.9.0, в фреймворке встроен декларативный уровень моделей данных: наследуя `Model` и объявляя поля с помощью `Field`, можно получить возможность автоматического создания таблиц и CRUD-операций. Модели строятся непосредственно на базе встроенного хранилища — SQLite / MySQL / PostgreSQL определяются параметром `ErisPulse.storage.backend`, **смена хранилища не требует изменения кода моделей**.

## Декларация модели

```python
from ErisPulse.Core.Bases import Model, Field

class User(Model):
    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0, ge=0, le=150)
    role: str = Field(default="user", choices=["user", "admin"])
    tags: list = Field(default_factory=list)          # JSON-столбец, автоматическая сериализация при чтении/записи
    bio: str = Field(default="", description={"i18n": "user.bio", "default": "简介"})
```

- Имя таблицы по умолчанию — имя класса в snake_case (`UserProfile → user_profile`), можно переопределить с помощью `__tablename__ = "xxx"`
- Ограничения `Field` и декларативные параметры совпадают с классами конфигурации (`choices` / `ge` / `le` / `max_length`, `description` поддерживает словарь i18n); движок проверки совпадает с проверкой конфигурации

## Параметры поля

| Параметр | Описание |
|------|------|
| `default` | Значение по умолчанию (если не задано и не автоинкремент → обязательное поле NOT NULL) |
| `default_factory` | Фабрика для изменяемых значений по умолчанию (например, `list`) |
| `primary_key` | Первичный ключ |
| `autoincrement` | Автоинкрементный ключ (явно указывает на первичный ключ, после `create` автоматически заполняется) |
| `max_length` | Максимальная длина строки (генерирует `VARCHAR(n)`, проверка при записи) |
| `nullable` | Разрешить NULL (по умолчанию False) |
| `index` | Создать обычный индекс |
| `unique` | Уникальное ограничение |
| `choices` / `ge` / `le` | Перечисление / диапазон значений (проверка при записи) |
| `description` | Описание (словарь i18n, формат такой же, как у класса конфигурации) |
| `column_type` | Переопределение определения типа SQL-столбца |

## Создание таблицы и CRUD

```python
await User.create_table()                      #幂等（IF NOT EXISTS）

user = await User.create(name="Alice", age=20) # 插入（自增主键自动回填）
got = await User.get(id=user.id)               # 等值查询首条

users = await User.where(User.age > 18).order_by("-age").limit(10).all()
first = await User.where(User.name == "Alice").first()
total = await User.count(User.age > 18)

user.age = 21
await user.save()                              # 按主键更新（先约束校验）；主键缺失时退化为插入（自增主键同样回填到实例）
await user.delete()                            # 按主键删除

await User.update_all(User.age > 18, role="adult")  # 批量更新
await User.delete_all(User.age > 100)               # 批量删除
```

Выражения для запросов поддерживают `> >= < <= == !=`、`in_([...])` и операции `&` (И) / `|` (ИЛИ):

```python
await User.where((User.age > 18) & User.name.in_(["Alice", "Bob"])).all()
```

## Транзакции

ORM и хранилище фреймворка используют одну и ту же систему маршрутизации транзакций: если операции `create` / `save` / `delete` и запросы находятся в окружении `storage.atransaction()`, они автоматически используют одинаковое соединение транзакции, и все изменения подлежат единым коммиту или откату, не подлежат отдельному коммиту.

```python
async with storage.atransaction():
    await User.create(name="Alice")
    ...  # При возникновении исключения в блоке, INSERT откатывается
```

## Отношения с декларативными конфигурационными классами

Декларация моделей и `ConfigClass` (`@dataclass + field(metadata=...)`) **разделяют одну и ту же базовую систему** — словарь ограничений, движок проверки (`validate_field_constraints`), регистр типов (`python_type_category`); но базовые классы намеренно разделены: поля конфигурации — это обычные значения (TOML-формат, однократная загрузка с горячим обновлением), поля моделей — это описатели столбцов (доступ к классу = выражение запроса, доступ к экземпляру = значение строки). Одна и та же декларация, два разных базовых класса.

### Когда использовать какой тип декларации

| Критерий | Поля конфигурационного класса `field(metadata=...)` | Поля модели `Field()` |
|------|------------------------------|---------------------|
| Сценарий использования | Параметры модуля (малое количество, человекочитаемые, нуждаются в горячем обновлении) | Бизнес-данные (много строк, программное чтение и запись, нуждаются в запросах) |
| Формат хранения | `config.toml` (сохранение комментариев, TOML-формат) | Таблицы базы данных (автоматическое создание таблиц, SQL-диалект) |
| Формат значений | Обычные значения (прямой доступ через свойства dataclass) | Описатели (доступ к классу = выражение столбца, доступ к экземпляру = значение строки) |
| Ограничения | `metadata={"choices": ..., "min": ..., "max": ...}` | `Field(choices=..., ge=..., le=..., max_length=...)` |
| Общая база | Движок проверки + словарь ограничений + регистр типов (одинаковый) | То же самое |

Эмпирическое правило: **"как модуль работает" — используйте класс конфигурации, "какие данные создал пользователь" — используйте модель**.

## Ограничения и замечания

- Хранилище определяется глобальной конфигурацией; модель может переопределить хранилище через атрибут класса `__storage__` для использования пользовательского экземпляра `BaseStorage` (для тестов)
- Поля `list` / `dict` (включая параметризированные типы, такие как `list[int]`, `dict[str, int]`) хранятся в виде JSON-столбцов, автоматическая сериализация при чтении/записи
- Перед записью (`create` / `save`) автоматически выполняется проверка ограничений, при ошибке выбрасывается `ValueError` (локализованное сообщение)
- Автоматическая миграция поддерживает сценарии **добавления новых столбцов** (см. ниже); изменение типа столбца и удаление столбцов требуют ручного управления
- При сбое подключения к хранилищу поведение такое же, как у слоя хранилища: фреймворк не падает, после перезапуска автоматически переподключается

## Автоматическая миграция (шаг 2)

`create_table()` при наличии таблицы автоматически сравнивает существующие столбцы с полями модели: **новые поля** автоматически обрабатываются с помощью `ALTER TABLE ADD COLUMN` (удаляются ограничения `NOT NULL`, заполняются NULL для существующих строк), индекс для новых полей с `index=True` также создается. Не требуется ручной написания скриптов миграции.

```python
# После запуска v1 модели: добавление полей email / bio
class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0)
    email: str = Field(default="")     # Новое: при следующем create_table() автоматически добавит столбец
    bio: str = Field(default="")

await User.create_table()              #幂等：仅迁移新增列
```

**Ограничения**: поддерживается только добавление столбцов; изменение первичного ключа, типа столбца и удаление столбцов требуют ручного управления (чтобы избежать ошибок при разрушительных ALTER).

## Внешние ключи (основа сопоставления отношений)

`foreign_key="table.column"` объявляет внешний ключ на уровне столбца, DDL генерирует подфразу `REFERENCES`:

```python
class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id")

    content: str = Field(max_length=255)
```

## Сопоставление отношений (relationship)

В теле класса модели объявляется `relationship()` в виде атрибута класса, **направление определяется автоматически в зависимости от того, где объявлен внешний ключ**:

```python
from ErisPulse.Core.Bases import Model, Field, relationship

class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)

    posts = relationship("Post", foreign_key="author")   # Внешний ключ в другой таблице → has-many

class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id")
    content: str = Field(max_length=255)

    writer = relationship("User", foreign_key="author")  # Внешний ключ в этой таблице → belongs-to
```

**has-many**: атрибут экземпляра возвращает набор запросов, доступны все возможности `QuerySet`, `create` автоматически возвращает первичный ключ текущей таблицы в столбец внешнего ключа другой таблицы:

```python
alice = await User.get(name="Alice")

posts = await alice.posts.all()                          # Все статьи пользователя
latest = await alice.posts.order_by("-id").first()
total = await alice.posts.count()
hot = await alice.posts.where(Post.content != "").all()  # Дополнительные условия по столбцам другой таблицы
await alice.posts.delete()                               # Удалить только статьи пользователя

new_post = await alice.posts.create(content="hi")        # author автоматически = alice.id
```

**belongs-to**: при `await` получается экземпляр другой модели (если нет соответствия или внешний ключ NULL, возвращается `None`):

```python
post = await Post.get(id=1)
writer = await post.writer          # Экземпляр User или None
await writer.posts.count()          # Двусторонняя связь
```

**Особенности**:

- `related` принимает имя класса в виде строки (ленивое разрешение по таблице зарегистрированных моделей, порядок определения не имеет значения) или передает сам класс модели
- Запросы отношений и модели другой таблицы используют разные хранилища (не поддерживается JOIN между разными хранилищами — запросы отношений — это отдельные SQL-запросы)
- Запросы отношений не кэшируются, каждый вызов — это немедленный запрос; для любых пользовательских запросов можно использовать `User.where(...)`
