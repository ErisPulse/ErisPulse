# Практическое руководство по первому вкладу

> Впервые отправлять PR может быть немного неуверенно, и это нормально. В этом руководстве весь процесс разбит на несколько небольших шагов, просто следуйте по ним. Если возникнут какие-либо вопросы, вы можете задать их в Issue или Discussions — никто не скажет вам, что ваш вопрос «слишком базовый», все больше интересуются тем, двигаетесь ли вы вперед.

В этой статье в качестве примера используется «добавление ключа перевода i18n», потому что это изменение самое минимальное и проще всего реализовать. Однако тот же самый процесс подходит и для других типов вклада.

## Подготовка

Перед началом вам нужно подготовить:

- аккаунт на GitHub
- локально установленный [uv](https://docs.astral.sh/uv/) (менеджер пакетов ErisPulse)
- Python 3.10+

## 1. Fork и клонирование репозитория

Перейдите в [репозиторий ErisPulse](https://github.com/ErisPulse/ErisPulse) и нажмите **Fork** в правом верхнем углу, чтобы скопировать его в свой аккаунт, а затем клонируйте его локально (замените «ваше имя пользователя» на фактическое имя):

```bash
git clone -b Develop/v2 https://github.com/ваше имя пользователя/ErisPulse.git
cd ErisPulse
```

Добавьте адрес «upstream», чтобы в будущем можно было синхронизировать обновления из основного репозитория:

```bash
git remote add upstream https://github.com/ErisPulse/ErisPulse.git
```

## 2. Установка среды разработки

```bash
uv sync                       # Установка зависимостей и создание .venv
```

Проверка корректности среды:

```bash
uv run pytest -m unit -q      # Все тесты должны пройти успешно
```

## 3. Создание функциональной ветки

Всегда создавайте ветку от `Develop/v2`:

```bash
git checkout Develop/v2
git pull upstream Develop/v2   # Сначала синхронизируйте с последними изменениями
git checkout -b docs/add-hello-translation
```

Название ветки может быть любым, главное — чтобы было понятно, что вы собираетесь делать.

## 4. Внесение изменений

В качестве примера добавим ключ перевода, предположим, что нужно добавить фразу `mymodule.hello`.

Есть только одно правило: **при добавлении ключа перевода, необходимо добавить его во все 5 языков (zh-CN / en / zh-TW / ja / ru)**, иначе пользователи других языков увидят отсутствие перевода.

Откройте 5 файлов в директории `src/ErisPulse/Core/i18n/locales/` и добавьте в каждый по одной строке:

```python
# zh_cn.py
"mymodule.hello": "你好",
# en.py
"mymodule.hello": "Hello",
# zh_tw.py
"mymodule.hello": "你好",
# ja.py
"mymodule.hello": "こんにちは",
# ru.py
"mymodule.hello": "Привет",
```

> Если изменения затрагивают новые публичные методы, не забудьте добавить к ним документационные комментарии, см. [Спецификацию документационных комментариев](../styleguide/docstring.md).

## 5. Локальная проверка

```bash
uv run ruff check .            # Проверка стиля кода
uv run basedpyright src/ErisPulse   # Проверка типов (только если меняли исходный код) - возможно, увидите сотни предупреждений (не обращайте внимания, просто проигнорируйте... ха..хаха)
uv run pytest -m unit -q       # Запуск тестов
```

Достаточно, чтобы все три прошли успешно. Предупреждения `reportAny` / `Unknown*` в проверке типов относятся к тому, что типы всё ещё находятся в процессе доработки, и не будут мешать слиянию.

> Если вы меняли основные модули (Bases / runtime / config / loaders), рекомендуется добавить соответствующие тестовые случаи, чтобы облегчить последующее обслуживание.

## 6. Обновление CHANGELOG

Откройте файл `CHANGELOG.md`, найдите версию, которая находится в разработке (находится в самом верху), и добавьте соответствующую запись в нужную категорию:

```markdown
### Оптимизация

- Добавлен ключ перевода `mymodule.hello` в `Core/i18n/locales` (zh-CN / en / zh-TW / ja / ru)
```

## 7. Подтверждение и отправка

```bash
git add .
git commit -m "i18n: добавить перевод mymodule.hello"
git push origin docs/add-hello-translation
```

## 8. Отправка Pull Request

После отправки (push) GitHub предложит **Compare & pull request**. Нажмите на него:

1. Убедитесь, что целевой веткой является **`Develop/v2`** (не выбирайте `main`)
2. Отметьте тип изменений и кратко опишите, что вы изменили
3. Отправьте запрос на рассмотрение, дождитесь проверки от администратора

Если администратор оставит замечания — это нормально, это не означает, что вы сделали что-то не так. Просто внесите изменения по их рекомендациям и отправьте изменения ещё раз. После прохождения проверки ваши изменения будут включены в `Develop/v2`, и вы сможете использовать их в следующей версии.

## Вклад в модули или адаптеры

Модули и адаптеры — это небольшие пакеты с полной структурой, для начала работы с которыми лучше всего использовать инструмент генерации:

```bash
epsdk create    # выберите module или adapter
```

После создания можно следовать этим документам:

- [Начало разработки модуля](../developer-guide/modules/getting-started.md)
- [Начало разработки адаптера](../developer-guide/adapters/getting-started.md)
- [Публикация в PyPI и в каталог модулей](../developer-guide/publishing.md)

> Рекомендуется перед началом разработки упомянуть о своих планах в [Issues](https://github.com/ErisPulse/ErisPulse/issues), используя шаблон «Новый адаптер или модуль». Так разработчики смогут помочь вам соблюдать стандарты и избежать распространённых ошибок.

Модули и адаптеры обычно находятся в отдельных репозиториях, а не в основном. `examples/example-module/` и `examples/example-adapter/` — это примеры для ознакомления.

## Возможные проблемы

**Сколько времени пройдет, прежде чем кто-нибудь посмотрит на мой PR?**
Обычно это занимает несколько дней. Разработчики оставят комментарии к обзору, и вам нужно будет внести соответствующие изменения и снова отправить их (push).

**Появилось сообщение об ошибке при проверке кода?**
Сначала попробуйте выполнить команду `uv run ruff check . --fix`, она автоматически исправит большинство ошибок.

**Произошло конфликтование с основным репозиторием?**
Используйте команду `git pull upstream Develop/v2`, решите конфликты и снова отправьте изменения (push).

**Можно ли отправить изменения напрямую в `main`?**
Нет, все изменения должны проходить через `Develop/v2`, а затем будут опубликованы в `main` разработчиками.
