# Стандартизированные правила преобразования адаптеров

> [!TIP]
> **Когда нужно читать эту статью**: когда вы конвертируете нативные события платформы в стандартные события OneBot12 в адаптере — проверьте обязательные поля, структуру сегментов сообщений, именование расширенных полей (`{platform}_` префикс), вывод типа сессии, сопоставляя с этой статьей. Если не нужно, пропустите.

## 1. Основные принципы
1. Строгое соответствие: все стандартные поля должны полностью соответствовать спецификации OneBot12
2. Ясное расширение: функции, специфичные для платформы, должны иметь префикс `{platform}_` (например, yunhu_form)
3. Полная целостность данных: исходные данные события должны сохраняться в поле `{platform}_raw`, тип исходного события — в поле `{platform}_raw_type`
4. Единое время: все временные метки должны быть преобразованы в 10-значные Unix-временные метки (в секундах)
5. Единое имя платформы: поле `platform` должно соответствовать названию или псевдониму, зарегистрированному в ErisPulse

## 2. Требования к стандартным полям

### 2.1 Обязательные поля
| Поле | Тип | Описание |
|------|------|------|
| id | string | Уникальный идентификатор события |
| time | integer | Unix-временная метка (в секундах) |
| type | string | Тип события |
| detail_type | string | Подтип события (см. [Стандарт типов сессий](session-types.md)) |
| platform | string | Название платформы |
| self | object | Информация о боте |
| self.platform | string | Название платформы |
| self.user_id | string | ID пользователя бота |

**Правила для `detail_type`**:
- Должен использовать стандартные типы сессий ErisPulse (см. [Стандарт типов сессий](session-types.md))
- Поддерживаемые типы: `private`, `group`, `user`, `channel`, `guild`, `thread`
- Адаптер отвечает за сопоставление типов платформы со стандартными типами

### 2.2 Поля для событий сообщений
| Поле | Тип | Описание |
|------|------|------|
| message | array | Массив сегментов сообщения |
| alt_message | string | Запасной текст сегментов сообщения |
| user_id | string | ID пользователя |
| user_nickname | string | Имя пользователя (необязательно) |

### 2.3 Поля для уведомлений
| Поле | Тип | Описание |
|------|------|------|
| user_id | string | ID пользователя |
| user_nickname | string | Имя пользователя (необязательно) |
| operator_id | string | ID оператора (необязательно) |

### 2.4 Поля для запросов
| Поле | Тип | Описание |
|------|------|------|
| user_id | string | ID пользователя |
| user_nickname | string | Имя пользователя (необязательно) |
| comment | string | Комментарий к запросу (необязательно) |
| request_id | string | Идентификатор запроса (**рекомендуется** для согласования/отклонения запроса) |

**Описание поля `request_id`**:
- `request_id` — уникальный идентификатор запроса, используемый для согласования/отклонения запроса через DSL `HandleRequest`
- Адаптер должен сопоставлять идентификатор запроса платформы с этим полем
- Если платформа не предоставляет идентификатор запроса, адаптер должен сгенерировать уникальный идентификатор (например, хэш из временной метки и ID пользователя)
- При отсутствии `request_id` вызов `event.approve()` / `event.reject()` будет генерировать `ValueError`

## 4. Стандартные сегменты сообщений

### 4.1 Стандартные сегменты сообщений

Стандартные сегменты сообщений **не требуют** префикса платформы.

| Тип | Описание | Поля `data` |
|------|------|----------|
| `text` | Текст | `text: str` |
| `image` | Изображение | `file`, `url: str` |
| `audio` | Аудио | `file`, `url: str` |
| `video` | Видео | `file`, `url: str` |
| `file` | Файл | `file`, `url: str`, `filename: str` |
| `mention` | Упоминание пользователя | `user_id: str`, `user_name: str` |
| `reply` | Ответ | `message_id: str` |
| `face` | Эмодзи | `id: str` |
| `location` | Геолокация | `latitude: float`, `longitude: float` |
| `keyboard` | Кнопки/внутренняя клавиатура | `rows: list[list[button]]` (см. 4.1.1) |

**Формат поля `file` для медиа-сегментов** (направление отправки, общий для `image` / `audio` / `video` / `file`):

| Формат | Пример | Требования адаптера |
|------|------|-----------|
| HTTP(S) URL | `https://example.com/a.png` | **Обязательно** принимать |
| Локальный путь к файлу | `/tmp/a.png`, `C:\tmp\a.png` | **Обязательно** принимать |
| Бинарные данные | `bytes` | **Обязательно** принимать |
| URI `file://` / Base64 / Data URI | `file:///tmp/a.png`, `data:image/png;base64,...` | **Рекомендуется** принимать |

> Полный протокол отправки медиа (порядок определения формата, вывод имени файла, иерархия возможностей) см. в
> [Спецификации методов отправки §2.1](send-method-spec.md#21-протокол-отправки-медиа-image--voice--video--file).

**Семантика направления полей**:

- `file`: **Направление отправки** — источник содержимого (указанные форматы); **Направление получения** — заполняется адаптером в виде формата, доступного для скачивания (обычно это URL, или идентификатор ресурса, доступного через `get_file`)
- `url`: URL-ссылка, возвращаемая платформой (адаптер должен заполнять, если возможно, для прямого использования модулями); направление отправки может быть не указано
- `filename`: Имя файла для сегмента `file` (направление отправки — необязательно, если не указано, адаптер генерирует имя по [Спецификации методов отправки §2.1.3](send-method-spec.md) иначе); направление получения **должно** содержать оригинальное имя файла платформы

```json
{
  "type": "text",
  "data": {
    "text": "Привет, мир"
  }
}
```

### 4.1.1 Сегмент кнопок/внутренней клавиатуры `keyboard` (универсальный для платформ)

Кнопки/внутренняя клавиатура есть на нескольких платформах (Telegram / Yunhu / QQBot / Kook / Discord и др.), и являются **универсальной концепцией**, поэтому они являются стандартным сегментом (без префикса платформы). Адаптер должен преобразовывать стандартный сегмент в платформенный формат; платформенные расширенные сегменты (например, `telegram_inline_keyboard`) должны сохраняться и передаваться без изменений.

```json
{
  "type": "keyboard",
  "data": {
    "rows": [
      [
        {"label": "Вариант A", "type": "callback", "data": "vote:A"},
        {"label": "Официальный сайт", "type": "link", "data": "https://example.com"}
      ]
    ]
  }
}
```

**Описание полей:**

| Поле | Тип | Обязательно | Описание |
|------|------|------|------|
| `rows` | Двумерный массив | Да | Каждый подмассив — строка кнопок |
| `rows[][].label` | str | Да | Текст кнопки |
| `rows[][].type` | str | Да | `callback` (отправка данных при нажатии) / `link` (переход по URL) |
| `rows[][].data` | str | Да | Данные для callback (type=callback) или адрес для перехода (type=link) |
| `rows[][].*` | Any | Нет | Платформенные необязательные поля (например, `web_app`, `menus`), адаптер отображает по возможностям или игнорирует |

**Примеры преобразования адаптера** (полное отображение и стандарт для событий взаимодействия см. в [Стандарте кросс-платформенных компонентов взаимодействия](standardization-guide.md)):

| Платформа | Стандартный сегмент → Платформенный формат |
|------|------------------|
| Telegram | `inline_keyboard`: `[{text, callback_data \| url}]` |
| Yunhu | `buttons`: `[{label, action_type: 2=callback \| 1=link, ...}]` |
| QQBot | `keyboard.content.rows`: `[{label, type: 2=callback \| 0=link, data}]` (требуется сообщение в формате markdown) |
| Kook | Модуль action-group в карточке |
| Discord | components: `action_row` + `buttons` (custom_id/url) |

### 4.2 Платформенные расширенные сегменты сообщений

Сегменты сообщений, специфичные для платформы, должны иметь платформенный префикс:

```json
// Yunhu - форма
{"type": "yunhu_form", "data": {"form_id": "123456", "form_name": "Форма регистрации"}}

// Telegram - стикер
{"type": "telegram_sticker", "data": {"file_id": "CAACAgIAAxkBAA...", "emoji": "😂"}}
```

**Требования к расширенным сегментам сообщений**:
1. **Поля внутри `data` не должны иметь префикса**: `{"type": "yunhu_form", "data": {"form_id": "..."}}`, а не `{"type": "yunhu_form", "data": {"yunhu_form_id": "..."}}`
2. **Обеспечьте механизм понижения**: модуль может не распознавать расширенные сегменты сообщений, адаптер должен предоставить текстовое замещение в `alt_message`
3. **Документация**: каждый расширенный сегмент сообщения должен быть подробно описан в документации адаптера: `type`, структура `data` и сценарии использования

## 5. Обработка неизвестных событий

Для неопознанных типов событий следует генерировать событие предупреждения:
```json
{
  "id": "1234567893",
  "time": 1752241223,
  "type": "unknown",
  "platform": "yunhu",
  "yunhu_raw": {...},
  "yunhu_raw_type": "unknown",
  "warning": "Неизвестный тип события: special_event",
  "alt_message": "Этот тип события не поддерживается системой."
}
```

## 6. Стандарты именования расширений

### 6.1 Именование полей

**Правило**: `{platform}_{field_name}`

```
Платформенный префикс    Имя поля            Полное имя поля
────────    ───────          ──────────
yunhu       command           yunhu_command
telegram    sticker_file_id   telegram_sticker_file_id
onebot11    anonymous         onebot11_anonymous
email       subject           email_subject
```

**Требования**:
- `platform` должен полностью соответствовать названию платформы, зарегистрированному в адаптере (регистрозависимо)
- `field_name` должно использовать стиль `snake_case`
- Запрещено использовать двойное подчёркивание `__` в начале (зарезервировано Python)
- Запрещено использовать имя, совпадающее со стандартным полем (например, `type`, `time`, `message` и т.д.)

### 6.2 Именование типов сегментов сообщений

**Правило**: `{platform}_{segment_type}`

Стандартные типы сегментов сообщений (`text`, `image`, `audio`, `video`, `mention`, `reply` и т.д.) **не должны** иметь платформенный префикс. Только платформенные специфичные типы сегментов сообщений должны иметь префикс.

### 6.3 Именование полей исходных данных

Следующие имена полей являются **зарезервированными**, все адаптеры должны соблюдать:

| Зарезервированное поле | Тип | Описание |
|---------|------|------|
| `{platform}_raw` | `any` | Полная копия исходных данных события платформы |
| `{platform}_raw_type` | `string` | Идентификатор типа исходного события платформы |

**Требования**:
- `{platform}_raw` должен быть глубокой копией исходных данных, а не ссылкой
- `{platform}_raw_type` должен быть строкой, даже если платформа использует числовой тип, его нужно преобразовать в строку
- Эти два поля должны **присутствовать** во всех событиях (если данные недоступны, то `null` и пустая строка `""`)

### 6.4 Примеры платформенных специфичных полей

```json
{
  "yunhu_command": {
    "name": "Розыгрыш",
    "args": "Суперприз"
  },
  "yunhu_form": {
    "form_id": "123456"
  },
  "telegram_sticker": {
    "file_id": "CAACAgIAAxkBAA..."
  }
}
```

### 6.5 Вложенные расширенные поля

Расширенные поля могут быть простыми значениями, а также вложенными объектами:

```json
{
  "telegram_chat": {
    "id": 123456,
    "type": "supergroup",
    "title": "Моя группа"
  },
  "telegram_forward_from": {
    "user_id": "789",
    "user_name": "ForwardUser"
  }
}
```

**Требования к вложенным полям**:
- Ключи верхнего уровня должны иметь платформенный префикс
- Вложенные поля **не должны** иметь платформенный префикс
- Рекомендуемая глубина вложенности не превышает 3 уровней

### 6.6 Расширение поля `self`

Стандартные обязательные поля `self` (см. §2.1): `platform`, `user_id`, а также расширения ErisPulse:

| Поле | Тип | Описание |
|------|------|------|
| `self.user_name` | `string` | Имя бота |
| `self.avatar` | `string` | URL аватара бота |
| `self.account_id` | `string` | Идентификатор аккаунта в режиме множественных аккаунтов |

> **Отслеживание состояния бота**: адаптер сообщает фреймворку о состоянии подключения бота, отправляя событие `type: "meta"`. Поддерживаемые `detail_type`: `connect` (онлайн), `heartbeat` (пинг), `disconnect` (офлайн). Система автоматически извлекает информацию о боте из поля `self` для отслеживания состояния. Кроме того, поле `self` в обычных событиях также автоматически обнаруживается. Подробнее см. в [API адаптера - Управление состоянием бота](../api-reference/adapter-system.md).

## 7. Расширение типов сессий

ErisPulse расширяет стандартные типы сессий OneBot12 (`private`, `group`) следующими типами:

| Тип | Стандарт OneBot12 | Расширение ErisPulse | Описание |
|------|:-----------:|:------------:|------|
| `private` | ✅ | — | Личный чат |
| `group` | ✅ | — | Групповой чат |
| `user` | — | ✅ | Тип пользователя (Telegram и др.) |
| `channel` | — | ✅ | Канал (трансляционный) |
| `guild` | — | ✅ | Сервер/сообщество |
| `thread` | — | ✅ | Тема/подканал |

**Расширение типов сессий адаптером**:

```python
from ErisPulse.Core.Event.session_type import register_custom_type

# Регистрация в начале работы адаптера
register_custom_type(
    receive_type="email",      # detail_type для входящих событий
    send_type="email",         # тип цели при отправке
    id_field="email_id",       # соответствующее имя поля ID
    platform="email"           # идентификатор платформы
)
```

**Требования к пользовательским типам**:
- Должны быть зарегистрированы в `start()` адаптера и отменены в `shutdown()`
- `receive_type` не должен совпадать со стандартными типами
- `id_field` должен соответствовать шаблону `{цель}_id`

> Полное определение и сопоставление типов сессий см. в [Стандарте типов сессий](session-types.md).

## 8. Руководство для разработчиков модулей

### 8.1 Доступ к расширенным полям

```python
from ErisPulse.Core.Event import message

@message()
async def handle_message(event):
    # Доступ к стандартным полям
    text = event.get_text()
    user_id = event.get_user_id()

    # Доступ к платформенным расширенным полям - способ 1: прямой get
    yunhu_command = event.get("yunhu_command")

    # Доступ к платформенным расширенным полям - способ 2: точечный доступ (обёртка Event)
    # event.yunhu_command

    # Доступ к исходным данным
    raw_data = event.get("yunhu_raw")
    raw_type = event.get_raw_type()

    # Определение платформы
    platform = event.get_platform()
    if platform == "yunhu":
        pass
    elif platform == "telegram":
        pass
```

### 8.2 Обработка расширенных сегментов сообщений

```python
@message()
async def handle_message(event):
    message_segments = event.get("message", [])

    for segment in message_segments:
        seg_type = segment.get("type")
        seg_data = segment.get("data", {})

        if seg_type == "text":
            text = seg_data["text"]
        elif seg_type.startswith("yunhu_"):
            if seg_type == "yunhu_form":
                form_id = seg_data["form_id"]
        elif seg_type.startswith("telegram_"):
            if seg_type == "telegram_sticker":
                file_id = seg_data["file_id"]
```

### 8.3 Рекомендуемые практики

1. **Приоритет стандартных полей**: не предполагайте, что расширенные поля всегда существуют
2. **Определение платформы**: используйте `event.get_platform()` для определения платформы, а не по наличию расширенных полей
3. **Плавное понижение**: при невозможности обработки расширенных сегментов сообщений используйте `alt_message` как резервный вариант
4. **Не жёстко кодируйте префиксы**: используйте переменную `platform` для динамического составления

```python
# ✅ Рекомендуется
platform = event.get_platform()
raw_data = event.get(f"{platform}_raw")

# ❌ Не рекомендуется
raw_data = event.get("yunhu_raw")
```

### 8.4 Обработка запросов

Разработчики модулей могут использовать `event.approve()` и `event.reject()` для обработки запросов:

```python
from ErisPulse.Core.Event import request

# Автоматическое согласование запроса на добавление в друзья
@request.on_friend_request()
async def handle_friend_request(event):
    user_name = event.get_user_nickname() or event.get_user_id()
    comment = event.get_comment()
    
    # Согласование запроса
    result = await event.approve()
    if result.get("status") == "ok":
        print(f"Согласован запрос на добавление в друзья от {user_name}")
    else:
        print(f"Ошибка согласования запроса: {result.get('message')}")

# Запрос на вступление в группу: решение по условиям
@request.on_group_request()
async def handle_group_request(event):
    comment = event.get_comment()
    
    # Отклонение запроса
    result = await event.reject(comment="Временно не принимаю новые группы")
```

from ErisPulse import adapter

## 9. Вывод типа сессии для событий notice / request

### 9.1 Проблемный фон

Типы `detail_type` событий `notice` и `request` — это **семантические подтипы** (например, `group_member_increase`, `friend_increase`), а не типы сессии (например, `group`, `private`).

```
type        detail_type                  Смысл            Тип сессии
────        ───────────                  ────            ────────
message     group                        Сообщение в группе         group (detail_type — тип сессии)
message     private                      Личное сообщение          private (detail_type — тип сессии)
notice      group_member_increase        Увеличение участников группы    group (выводится по group_id)
notice      friend_increase              Увеличение друзей           private (выводится по user_id)
request     friend                       Запрос на добавление в друзья     private (выводится по user_id)
request     group                        Запрос на вступление в группу      group (detail_type — тип сессии)
```

### 9.2 Правила вывода

Порядок вывода `infer_receive_type()`:

1. Если `detail_type` — известный тип сессии (`private`/`group`/`channel`/`guild`/`thread`/`user`), используйте его
2. Если `detail_type` — пользовательский тип сессии, используйте его
3. В противном случае (семантические подтипы `notice`/`request`), выводите по ID-полю:
   - Если есть `group_id` → `"group"`
   - Если есть `channel_id` → `"channel"`
   - Если есть `guild_id` → `"guild"`
   - Если есть `thread_id` → `"thread"`
   - Если есть `user_id` → `"private"`

### 9.3 Вывод цели `event.reply()`

Цель отправки `event.reply()` в событиях `notice`/`request` определяется выводом типа сессии:

- События уведомления о группе (с `group_id`) → отправка в **группу**
- События уведомления о друзьях (только `user_id`) → отправка в **личный чат**

```python
from ErisPulse.Core.Event import notice

@notice.on_group_increase()
async def handle_welcome(event):
    group_id = event.get("group_id")    # "group_789"
    user_id = event.get("user_id")      # "user_456"

    # event.reply() отправляется в группу (group/group_789)
    await event.reply("Добро пожаловать в группу!")

    # Если нужно уведомить администратора (личный чат), явно укажите цель:
    await adapter.Send.To("user", "admin_id").Text(f"Новый участник {user_id} присоединился к {group_id}")
```

### 9.4 Рекомендации для разработчиков адаптеров

Убедитесь, что события `notice`/`request` содержат правильные ID-поля:

| detail_type | Обязательные ID-поля | Выводимый тип сессии |
|-------------|-------------------|---------------|
| `group_member_increase` | `group_id` + `user_id` | `group` |
| `group_member_decrease` | `group_id` + `user_id` | `group` |
| `friend_increase` | `user_id` | `private` |
| `friend_decrease` | `user_id` | `private` |
| `friend` (запрос) | `user_id` | `private` |
| `group` (запрос) | `group_id` | `group` |
