# Спецификация операций запросов ErisPulse

> [!TIP]
> **Когда нужно читать эту статью**: когда вашему адаптеру нужно обрабатывать запросы от друзей/приглашения в группы (преобразование событий запросов, реализация `accept`/`reject`, сохранение контекста запросов с гетерогенными эндпоинтами), или когда модули используют `event.approve()` / `event.reject()` для одобрения запросов. Если не нужно, то можно пропустить.

В этом документе определены стандартизированные спецификации операций запросов в адаптере ErisPulse, включая требования к полям запроса, использование DSL для запроса и требования к реализации адаптера.

## 1. Обзор

Событие запроса (`type: "request"`) — это специальный тип события, определенный в OneBot12, представляющий запрос, требующий принятия решения ботом (например, запрос на добавление в друзья, приглашение в группу и т.д.).

В отличие от событий сообщений, запросы требуют **двустороннего взаимодействия**:
1. **Прием**: адаптер преобразует платформенный оригинальный запрос в стандартное событие запроса
2. **Ответ**: модуль выполняет операции через DSL для запроса или `Event.approve()`/`Event.reject()`.

```
Событие платформенного запроса
    │
    ▼
Converter.convert()        ← Реализация адаптера (прямое преобразование)
    │
    ▼
Стандартное событие запроса (с request_id)
    │
    ├─→ Обработчик модуля @request.on_friend_request()
    │       │
    │       ├─→ event.approve()     ← Согласие с запросом
    │       └─→ event.reject()      ← Отказ в запросе
    │               │
    │               ▼
    │       adapter.Request(request_id).accept()
    │               │
    │               ▼
    │       BaseAdapter.Request.accept()  ← Переопределение адаптером
    │               │
    │               ▼
    │       Вызов API платформы
    │
    └─→ Или напрямую через операции адаптера
            await adapter.Request("req_id").accept()
```

## 2. Требования к полям запроса

### 2.1 Стандартные поля

Событие запроса, помимо обязательных полей OneBot12, должно содержать следующие поля:

| Поле | Тип | Обязательно | Описание |
|------|------|------|------|
| `request_id` | string | **Рекомендуется** | Идентификатор запроса, используется для согласия/отказа |
| `user_id` | string | Да | Идентификатор отправителя запроса |
| `user_nickname` | string | Нет | Никнейм отправителя запроса |
| `comment` | string | Нет | Комментарий к запросу |

### 2.2 Поле `request_id`

`request_id` является ключевым идентификатором для запроса:

- **Назначение**: идентификация запроса, используемого для операций через DSL для запроса
- **Правила генерации**:
  - В первую очередь использовать оригинальный идентификатор платформы (например, `flag` из OneBot11, `chat_invite_link` из Telegram и т.д.)
  - Если платформа не предоставляет оригинальный идентификатор, адаптер должен сгенерировать уникальный идентификатор (рекомендуемый формат: `{platform}_{timestamp}_{user_id}`)
- **Уникальность**: в рамках одной платформы должен быть уникален
- **Поведение при отсутствии**: если `request_id` отсутствует, `event.approve()` / `event.reject()` выбросят `ValueError`

### 2.3 Пример события запроса

```json
{
  "id": "evt_123456",
  "time": 1752241225,
  "type": "request",
  "detail_type": "friend",
  "platform": "onebot11",
  "self": {
    "platform": "onebot11",
    "user_id": "bot_123"
  },
  "user_id": "user_456",
  "user_nickname": "YingXinche",
  "comment": "Пожалуйста, добавьте в друзья",
  "request_id": "flag_abc123",
  "onebot11_raw": {...},
  "onebot11_raw_type": "request"
}
```

## 3. DSL для запроса

### 3.1 Цепочечные вызовы

`Request` предоставляет интерфейс цепочечных вызовов, аналогичный `Send`:

```python
# Базовое использование
await adapter.Request("req_id").accept()
await adapter.Request("req_id").reject()

# Указание аккаунта бота
await adapter.Request("req_id").Using("bot1").accept()

# Добавление комментария (через kwargs)
await adapter.Request("req_id").accept(comment="Добро пожаловать")
await adapter.Request("req_id").reject(comment="Временно не добавляю")

# Комбинированные вызовы
await adapter.Request("req_id").Using("bot1").accept(comment="Добро пожаловать")
```

### 3.2 Список методов

| Метод | Описание | Возвращаемое значение |
|------|------|--------|
| `Using(account_id)` | Указывает аккаунт бота для выполнения операции | `RequestDSL` (поддерживает цепочечные вызовы) |
| `accept(**kwargs)` | Согласие с запросом | `asyncio.Task` (возвращает стандартный ответ после await) |
| `reject(**kwargs)` | Отказ в запросе | `asyncio.Task` (возвращает стандартный ответ после await) |

### 3.3 Формат возвращаемых значений

Операции возвращают стандартный формат ответа API:

**Успех**:
```json
{
    "status": "ok",
    "retcode": 0,
    "data": null,
    "message_id": "",
    "message": ""
}
```

**Ошибка**:
```json
{
    "status": "failed",
    "retcode": 34001,
    "data": null,
    "message_id": "",
    "message": "Запрос просрочен или не существует"
}
```

**Не реализовано** (адаптер не переопределил `_do_accept`/`_do_reject`):
```json
{
    "status": "failed",
    "retcode": 10002,
    "data": null,
    "message_id": "",
    "message": "Платформа MyAdapter не реализовала операцию запроса (accept)"
}
```

## 4. Удобные методы Event

Класс `Event` предоставляет удобные методы, подходящие для использования в обработчиках событий запроса:

```python
from ErisPulse.Core.Event import request

@request.on_friend_request()
async def handle_friend_request(event):
    # Проверка идентификатора запроса
    request_id = event.get_request_id()
    if not request_id:
        print("Предупреждение: событие запроса не содержит request_id")
        return
    
    # Согласие с запросом
    result = await event.approve()
    
    # Или отказ в запросе
    # result = await event.reject(comment="Временно не добавляю в друзья")
    
    # Проверка результата
    if result.get("status") == "ok":
        print("Операция выполнена успешно")
    else:
        print(f"Операция не удалась: {result.get('message')}")
```

### 4.1 Список методов Event

| Метод | Описание | Возвращаемое значение |
|------|------|--------|
| `get_request_id()` | Получает идентификатор запроса | `str` |
| `approve(comment=None)` | Согласие с текущим событием запроса | Стандартный формат ответа |
| `reject(comment=None)` | Отказ в текущем событии запроса | Стандартный формат ответа |

## 5. Требования к реализации адаптера

### 5.1 Требования к конвертеру

Конвертер адаптера при преобразовании событий запроса **должен** правильно задать поле `request_id`:

```python
def convert_request_event(self, raw_event: dict) -> dict:
    """Конвертирует платформенный оригинальный запрос"""
    return {
        "id": self._generate_event_id(raw_event),
        "time": int(time.time()),
        "type": "request",
        "detail_type": self._map_request_type(raw_event),  # "friend" или "group"
        "platform": self._platform_name,
        "self": {
            "platform": self._platform_name,
            "user_id": str(self._bot_id),
        },
        "user_id": str(raw_event.get("user_id", "")),
        "user_nickname": raw_event.get("nickname", ""),
        "comment": raw_event.get("message", ""),
        "request_id": self._extract_request_id(raw_event),  # ← Ключевое поле
        f"{self._platform_name}_raw": raw_event,
        f"{self._platform_name}_raw_type": raw_event.get("type", ""),
    }

def _extract_request_id(self, raw_event: dict) -> str:
    """
    Извлекает идентификатор запроса из платформенного оригинального события
    
    В первую очередь использует оригинальный идентификатор платформы, если нет — генерирует уникальный ID
    """
    # В первую очередь используем оригинальный идентификатор платформы
    if flag := raw_event.get("flag"):
        return str(flag)
    if request_key := raw_event.get("request_key"):
        return str(request_key)
    
    # Запасной вариант: генерируем уникальный ID
    import hashlib
    raw = f"{self._platform_name}_{raw_event.get('user_id')}_{raw_event.get('timestamp')}"
    return hashlib.md5(raw.encode()).hexdigest()
```

### 5.2 Реализация внутреннего класса Request

Публичные методы `accept()` / `reject()` базового класса являются входными точками: они содержат внутренний механизм авторизации (scope.actions.<owner>.request, если отключен — возвращается ответ с кодом 34601) и упаковку задачи, **адаптер не должен переопределять публичные входные точки** — переопределение приведет к обходу механизма авторизации. Адаптер переопределяет `_do_accept` / `_do_reject` (асинхронные методы, возвращающие стандартный словарь ответа).

> **Напоминание о многоаккаунтности**: в `_do_accept` / `_do_reject` адаптер сам вызывает `call_api`, аккаунт не вставляется автоматически — аккаунт получается через `self.request_context.get("account_id")` (явное указание через `Using()` > автоматическое привязывание через цепочку событий, аналогично `send_context` в Send), и передается в `call_api` как `account_id`, иначе при развертывании с несколькими аккаунтами запросы попадут в дефолтный аккаунт.

```python
from ErisPulse.Core import BaseAdapter, RequestDSL

class MyAdapter(BaseAdapter):
    
    class Request(RequestDSL):
        """Реализация операций запроса для MyPlatform"""
        
        async def _do_accept(self, **kwargs) -> dict:
            """
            Согласие с запросом
            
            :param kwargs: дополнительные параметры, например comment="заметка"
            :return: словарь в формате стандартного ответа
            """
            try:
                result = await self._adapter.call_api(
                    endpoint="/set_request",
                    request_id=self._request_id,
                    account_id=self.request_context.get("account_id"),
                    approve=True,
                    **kwargs,
                )
                return {
                    "status": "ok" if result.get("code") == 0 else "failed",
                    "retcode": result.get("code", 0),
                    "data": None,
                    "message_id": "",
                    "message": result.get("message", ""),
                }
            except Exception as e:
                return {
                    "status": "failed",
                    "retcode": 34001,
                    "data": None,
                    "message_id": "",
                    "message": f"Операция запроса не удалась: {e}",
                }
        
        async def _do_reject(self, **kwargs) -> dict:
            """Отказ в запросе (структура аналогична _do_accept: approve=False)"""
```

### 5.3 Сохранение контекста типа запроса (обязательно для адаптеров с гетерогенными эндпоинтами)

#### 5.3.1 Проблема несоответствия контрактов

`Request` DSL является безгосударственным обработчиком: вызывающая сторона знает только `request_id` ([§3](#3-request-dsl)), тип запроса не передается в параметрах. Однако у многих платформ эндпоинты для согласия/отказа являются **гетерогенными** — на примере OneBot11:

| Тип запроса | Эндпоинт |
|---|---|
| Добавление в друзья | `set_friend_add_request(flag, approve)` |
| Запрос в группу / приглашение | `set_group_add_request(flag, sub_type, approve)`, `sub_type ∈ {"add", "invite"}` |

Вызывающая сторона знает только `request_id`, выбор эндпоинта зависит от типа. Этот контекст может быть только заполнен адаптером: событие запроса получено и преобразовано адаптером (информация о типе уже есть), и тип запроса для одного `request_id` не меняется. Если адаптер не сохранит контекст, придется угадывать эндпоинт или полагаться на нестандартные параметры — типичная ошибка: **приглашение в группу попадает в эндпоинт для добавления в друзья**, `flag` интерпретируется как `user_id` и вызывает ошибку.

#### 5.3.2 Требования спецификации

Адаптеры с гетерогенными эндпоинтами (согласие/отказ по типу запроса) должны удовлетворять следующим требованиям:

1. **Сохранение контекста на стороне события**: в точке входа адаптера, где получает событие запроса, сохранить `request_id → {тип запроса, sub_type, group_id, аккаунт}` в внутренний кэш экземпляра (единый набор полей см. §5.3.3), и удалять просроченные записи
2. **Маршрутизация на стороне операции**: в `_do_accept` / `_do_reject` выбор эндпоинта происходит в следующем порядке: явный параметр kwargs > кэш > эндпоинт по умолчанию с WARNING — при неизвестном типе необходимо логировать (наблюдаемость), нельзя молча выбирать эндпоинт
3. **Сохранение имен параметров**: явные параметры для перезаписи называются `request_type` / `sub_type` / `group_id` (без подчеркивания, одинаковые имена для всех адаптеров); не используйте `_request_type` и подобные частные имена (стандартные вызывающие стороны не будут передавать такие параметры)
4. **Чтение аккаунта**: аккаунт для операции получается через базовое свойство `self.request_context.get("account_id")` (явное указание через `Using()` > автоматическая привязка через цепочку событий, аналогично `send_context` в Send); кэш сохраняет аккаунт события как резервный при отсутствии в цепочке событий (например, синтезированные события от опроса, восстановление после перезапуска)
5. **Очистка после обработки**: после успешной операции удалить запись `request_id` из кэша

Платформы с единым эндпоинтом запроса (например, `/set_request`) не нуждаются в сохранении, достаточно прозрачной передачи. Это спецификация реализации адаптера, контракт `Request` DSL не затрагивается.

#### 5.3.3 Единый формат записей (независимо от носителя)

Контекстные записи сохраняются в следующем единым формате. **Формат записи — это контракт взаимодействия**: dict в памяти, значение KV, строка ORM — все сохраняются в одном формате, что обеспечивает согласованность при миграции или объединении между адаптерами; носитель хранения выбирается самим адаптером, без изменения семантики полей.

| Поле | Тип | Обязательно | Семантика и источник |
|---|---|---|---|
| `request_type` | `str` | Да | Тип запроса, взят из события `detail_type` (`"friend"` / `"group"`) |
| `sub_type` | `str \| None` | Обязательно для групповых запросов | Подтип группы `"add"` / `"invite"`, взят из платформенного события (sub_type в OneBot11) |
| `group_id` | `str \| None` | Обязательно для групповых запросов | Идентификатор группы, взят из платформенного события |
| `account` | `str \| None` | Обязательно при многоаккаунтности | Аккаунт, с которого пришло событие, взят из события `self.user_id` |
| `ts` | `float` | Да | Unix-время (в секундах) прихода события, база для TTL |

Правила согласованности записей:

- **Однозначное соответствие**: один `request_id` соответствует максимум одной записи; повторные события с одним `request_id` перезаписывают запись (идемпотентность)
- **Очистка после обработки**: запись удаляется после успешной операции
- **TTL**: на основе `ts`, рекомендуется 1 час (перекрывает срок действия запроса на платформе); просроченные записи считаются не сохраненными, используются эндпоинт по умолчанию с WARNING
- **Ключ (при хранении в KV)**: `{ключ конфигурации адаптера}:request_ctx:{request_id}`, чтобы избежать конфликтов между адаптерами

#### 5.3.4 Пример реализации (внутренний кэш)

```python
import time

from ErisPulse.Core import BaseAdapter, RequestDSL


class MyAdapter(BaseAdapter):
    """Адаптер платформы с гетерогенными эндпоинтами (отдельные эндпоинты для запросов в друзья и группы)"""

    _REQ_CTX_TTL = 3600    # Время жизни контекста в секундах, покрывает срок действия запроса на платформе
    _REQ_CTX_MAX = 512     # Максимальный объем кэша

    def __init__(self, sdk=None):
        super().__init__(sdk)
        self._request_ctx: dict[str, dict] = {}   # request_id → контекст запроса

    def remember_request(self, request_id: str, *, request_type: str,
                         sub_type: str | None = None, group_id: str | None = None,
                         account: str | None = None) -> None:
        """Сохранение контекста запроса (вызывается в точке входа адаптера при получении события запроса)"""
        now = time.time()
        expired = [k for k, c in self._request_ctx.items() if now - c["ts"] > self._REQ_CTX_TTL]
        for k in expired:
            self._request_ctx.pop(k)
        while len(self._request_ctx) >= self._REQ_CTX_MAX:
            self._request_ctx.pop(min(self._request_ctx, key=lambda k: self._request_ctx[k]["ts"]))
        self._request_ctx[request_id] = {
            "request_type": request_type,   # "friend" / "group"
            "sub_type": sub_type,           # Подтип группы: "add" / "invite"
            "group_id": group_id,
            "account": account,             # Аккаунт, с которого пришло событие (self.user_id)
            "ts": now,
        }

    class Request(RequestDSL):
        """Маршрутизация эндпоинтов: kwargs явного указания > кэш > эндпоинт по умолчанию + WARNING"""

        def _route(self, **kwargs) -> dict:
            ctx = {k: kwargs[k] for k in ("request_type", "sub_type", "group_id") if kwargs.get(k)}
            cached = self._adapter._request_ctx.get(self._request_id, {})
            if not ctx.get("request_type"):
                ctx.update({k: v for k, v in cached.items()
                            if k in ("request_type", "sub_type", "group_id") and v})
                ctx.setdefault("account", cached.get("account"))
            if not ctx.get("request_type"):
                self._adapter.logger.warning(f"Тип запроса {self._request_id} неизвестен, используется эндпоинт для друзей")
                ctx["request_type"] = "friend"
            return ctx

        async def _do_accept(self, **kwargs) -> dict:
            """Согласие с запросом; kwargs для маршрутизации типа можно переопределить request_type / sub_type / group_id"""
            return await self._do_action(approve=True, **kwargs)

        async def _do_reject(self, **kwargs) -> dict:
            """Отказ в запросе (аналогично _do_accept: approve=False)"""
            return await self._do_action(approve=False, **kwargs)

        async def _do_action(self, approve: bool, **kwargs) -> dict:
            ctx = self._route(**kwargs)
            account = self.request_context.get("account_id") or ctx.get("account")
            try:
                if ctx["request_type"] == "group":
                    result = await self._adapter.call_api(
                        endpoint="/set_group_add_request",
                        flag=self._request_id,
                        sub_type=ctx.get("sub_type") or "add",
                        approve=approve,
                        account_id=account,
                    )
                else:
                    result = await self._adapter.call_api(
                        endpoint="/set_friend_add_request",
                        flag=self._request_id,
                        approve=approve,
                        account_id=account,
                    )
                response = {
                    "status": "ok" if result.get("code") == 0 else "failed",
                    "retcode": result.get("code", 0),
                    "data": None,
                    "message_id": "",
                    "message": result.get("message", ""),
                }
            except Exception as e:
                response = {
                    "status": "failed",
                    "retcode": 34001,
                    "data": None,
                    "message_id": "",
                    "message": f"Операция запроса не удалась: {e}",
                }
            if response["status"] == "ok":
                self._adapter._request_ctx.pop(self._request_id, None)   # Очистка после обработки
            return response
```

#### 5.3.5 Персистентное сохранение (опционально)

Использование процессного кэша с TTL покрывает большинство сценариев: от получения запроса до его обработки обычно занимает несколько секунд или минут, платформа сама имеет срок действия, окно потери кэша при перезапуске очень мало (использование эндпоинта по умолчанию с WARNING гарантирует наблюдаемость). Только если адаптер обеспокоен "моментом перезапуска", когда обработка только началась, можно сохранить контекст в персистентном хранилище, выбрав один из следующих вариантов, все сохраняются в формате, описанном в §5.3.3:

- **Хранилище KV**: `self.sdk.storage` (единое хранилище KV фреймворка, переключение бэкендов см. [Хранилище бэкендов](../advanced/storage-backends.md)):

  ```python
  # В точке входа: запись (см. правила ключей в §5.3.3)
  key = f"{self._get_config_key()}:request_ctx:{request_id}"
  self.sdk.storage.set(key, {"request_type": "group", "sub_type": "invite",
                             "group_id": group_id, "account": self_id, "ts": time.time()})

  # В точке операции: чтение + очистка
  ctx = self.sdk.storage.get(key)
  self.sdk.storage.delete(key)
  ```

  Слой хранения не отвечает за удаление устаревших записей: записи содержат `ts`, проверка на устаревание выполняется на стороне чтения (считается не сохраненной, используется эндпоинт по умолчанию + WARNING); после обработки обязательно `delete`.

- **Встроенный ORM**: объявленные модели `Model` / `Field` (встроенные с 2.9, см. [Слой данных ORM](../developer-guide/orm.md)) могут использоваться как эквивалентный носитель, таблица создается по единому набору полей (столбцы по таблице `request_id` в качестве первичного ключа). Важно помнить: `create_table` идемпотентна с `IF NOT EXISTS`, дальнейшие изменения схемы таблиц адаптер должен обновлять самостоятельно; таблица относится к данным адаптера, а не является общей для всех адаптеров.

Независимо от выбранного носителя: **не должно блокировать поток событий при неудачной записи в персистентное хранилище** — если бэкенд хранения недоступен (период быстрой неудачи), используется только внутренний кэш, события по-прежнему распределяются; оба варианта персистентного хранения являются опциональными, по умолчанию используется только внутренний кэш, не добавляются дополнительные зависимости.

### 5.4 Платформа не поддерживает операции запроса

Если платформа сама по себе не поддерживает операции с запросами (например, некоторые платформы автоматически обрабатывают запросы), адаптер может:

1. **Не переопределять внутренний класс `Request`**: использовать базовую реализацию, при вызове `accept()`/`reject()` возвращать `retcode=10002`
2. **В конвертере не генерировать `request_id`**: не создавать `request_id`, чтобы `event.approve()` выбросил `ValueError`
3. **Запись логов**: в `_do_accept` / `_do_reject` записывать предупреждения и возвращать соответствующие коды ошибок

### 5.5 Обобщение: Send и Request параллельно

У адаптера есть два параллельных внутренних класса DSL, каждый отвечает за свою задачу:

```
BaseAdapter
├── Send(SendDSL)     ← Отправка сообщений
│   ├── Raw_ob12()    ← Обязательно реализовать
│   ├── Text()        ← Рекомендуется реализовать
│   └── Image()       ← Реализовать по необходимости
│
└── Request(RequestDSL) ← Операции запроса
    ├── accept()        ← Публичный вход (механизм авторизации scope + упаковка задачи, не переопределять)
    ├── reject()        ← Публичный вход (аналогично)
    ├── _do_accept()    ← Реализовать по необходимости
    └── _do_reject()    ← Реализовать по необходимости
```

### 5.6 Важные замечания при инициализации адаптера

При переопределении `Request` внутреннего класса `__init__`, необходимо передать параметры и вызвать `super().__init__()`, подробнее см. [Введение в разработку адаптеров - Замечания при __init__](../developer-guide/adapters/getting-started.md#init-注意事项) (аналогично для `Request`, параметры: `adapter, request_id, account_id`).

## 6. Проверочный список реализации адаптера

### Основные требования
- [ ] Если переопределяется `__init__`, вызван `super().__init__()` (успешно инициализированы Send / Request фабрики)

### Преобразование запроса
- [ ] Событие запроса содержит поле `request_id` (рекомендуется)
- [ ] `detail_type` корректно отображается в `"friend"` или `"group"`
- [ ] Сохранены исходные данные платформы в поле `{platform}_raw`
- [ ] Правила генерации `request_id` описаны в документации

### Операции запроса
- [ ] Внутренний класс `Request` реализован (если платформа поддерживает операции запроса)
- [ ] Переопределены `_do_accept()` / `_do_reject()` (публичные входные точки `accept()` / `reject()` не переопределять — обход механизма авторизации)
- [ ] Операции возвращают стандартный формат ответа API
- [ ] Не поддерживаемые операции возвращают `retcode=10002`
- [ ] Ошибки сети возвращают `retcode=33xxx` (соответствие стандарту ответов API)

### Сохранение контекста типа запроса (платформы с гетерогенными эндпоинтами, см. §5.3)
- [ ] В точке входа события запроса сохранен контекст `request_id → {тип запроса, sub_type, group_id, аккаунт}`
- [ ] Поля записи соответствуют таблице унифицированных полей в §5.3.3 (включая `ts` метку времени; `request_id` однозначно соответствует, запись удаляется после обработки)
- [ ] Маршрутизация эндпоинтов в `accept` / `reject` происходит в порядке: явные параметры kwargs > кэш > эндпоинт по умолчанию + WARNING
- [ ] Параметры для перезаписи типа имеют зарезервированные имена `request_type` / `sub_type` / `group_id` (без подчеркивания, одинаковые имена для всех адаптеров); не используются `_request_type` и подобные частные имена
- [ ] Кэш имеет TTL и ограничение по объему, запись удаляется после успешной операции
- [ ] Аккаунт для операции получается через базовое свойство `self.request_context.get("account_id")` (явное указание через `Using()` > автоматическая привязка через цепочку событий, аналогично `send_context` в Send); аккаунт события используется как резервный при отсутствии в цепочке событий (например, синтезированные события от опроса, восстановление после перезапуска)
- [ ] При использовании персистентного хранилища: при неудачной записи используется только внутренний кэш, не блокируется поток событий

## 7. Расширение кодов ошибок

Рекомендуемые коды ошибок на уровне реализации адаптера, связанные с операциями запроса (соответствуют [Стандарту ответов API](api-response.md) §3.2, попадают в сегмент `34xxx` низших трех цифр платформенных ошибок):

| Код ошибки | Название ошибки | Описание |
|-------|-------|------|
| 34001 | Request Not Found | Запрос не существует или просрочен |
| 34002 | Request Already Handled | Запрос уже обработан |
| 34003 | Request Not Supported | Платформа не поддерживает данную операцию запроса |
| 34004 | Permission Denied | Бот не имеет прав на обработку этого запроса (возвращается платформой) |

> **Граница с кодами фреймворка**: вышеупомянутые `340xx` — это ошибки, возвращаемые **платформой/адаптером** при обработке запроса; ErisPulse фреймворк перед вызовом адаптера, если `scope.actions` запрещает действие `request` для модуля, **напрямую возвращает `34601`** (Action Denied, см. [Стандарт ответов API §5.3](api-response.md#53-框架扩展返回码34xxx-平台错误段的低三位自定义)), оба не взаимозаменяемы: сначала проходит фреймворк `34601`, затем платформа `340xx`.
