# Руководство по стандартизации адаптеров (общее руководство)

> [!TIP]
> **Когда нужно читать это руководство**: когда вы разрабатываете новый адаптер, или хотите добавить новую функциональность для какой-либо платформы, и не знаете, "включать в стандарт или использовать расширение `{platform}_", как называть, как обрабатывать различия между платформами, сначала читайте это руководство. Если вы просто хотите посмотреть конкретные стандарты для определенной области, вы можете перейти прямо к §2 соответствующему стандарту.

Данное руководство является **общим руководством** по стандартизации адаптеров ErisPulse: оно устанавливает принципы стандартизации для кроссплатформенной совместимости, стандартные карты, модели обработки различий, процессы включения новых возможностей в стандарт, а также дает **стандартные определения интерактивных компонентов** (кнопки/клавиатура, выпадающий список и т. д.) и **стандартные обратные вызовы событий взаимодействия**. Любые разработчики адаптеров при реализации новых функций должны **в первую очередь использовать стандартные определения**, чтобы разработчики модулей могли использовать один и тот же код на любой платформе и получать согласованное поведение — одинаковые имена, параметры и возвращаемые значения.

---

## 1. Принципы стандартизации

1. **Единообразие имен**: одно и то же понятие на всех платформах должно использовать одно и то же имя (например, удаление сообщения — `delete_message`, сегмент кнопок — `keyboard`), не завися от платформы.
2. **Единообразие параметров**: структура параметров стандартных действий/сегментов/методов должна быть одинаковой на всех платформах; платформенные специфичные параметры предоставляются в виде **необязательных расширенных параметров** или **расширенных полей**, не загрязняя стандартный сигнатуру.
3. **Единообразие возвращаемых значений**: все API/вызовы отправки должны возвращать стандартную структуру ответа (`status/retcode/data/message_id/message`), стандартные поля в `data` (например, `user_id/user_name`) должны иметь одинаковую семантику; платформенные оригинальные данные помещаются в `{platform}_raw`.
4. **Обоснованность расширений**: платформенные специфичные возможности должны называться с префиксом `{platform}_` (сегмент: `yunhu_form`; действие: `yunhu.board`; поля событий: `qqbot_button_id`), четко указывая, что они не являются кроссплатформенными.
5. **Абсорбция различий на уровне адаптера**: код модуля должен программироваться с учетом стандарта, платформенные различия должны обрабатываться адаптером (отображение параметров, стандартизация полей, понижение возможностей), модулю не нужно писать платформенные ветки.
6. **Понижение возможностей без ошибок**: если платформа не поддерживает какую-либо стандартную возможность, она должна быть элегантно понижена (возвращается `retcode=10002`, компоненты преобразуются в текст и помещаются в `alt_message`), без выбрасывания исключений и прерывания логики модуля.

## 3. Процесс стандартизации (как новая возможность попадает в стандарт)

```
Платформенные специфичные возможности (префикс {platform}_)
        │  ≥2 платформы демонстрируют подобную возможность
        ▼
Выявление общих черт (извлечение общих понятий и подмножества параметров)
        │
        ▼
Стандартный проект (имя + параметры + возвращаемые значения + таблица отображения на платформах)
        │  Обзор
        ▼
Включение в это общее руководство/документы стандартов по областям + реализация базового класса и совместимого слоя адаптера
        │
        ▼
Стандартный сегмент/действие (без префикса) — модуль может использовать кроссплатформенно
```

**Пример**: кнопки сначала реализовывались независимо на каждой платформе (`telegram_inline_keyboard` / кнопки Yunhu / клавиатура QQBot) → появляются на ≥3 платформах → извлекается общая структура (`label/type/data` + rows) → публикуется стандартный сегмент `keyboard` → реализуется совместимый слой адаптера (модификаторы принимают общую структуру + преобразование стандартного сегмента + прозрачная передача оригинальных сегментов).

### 3.1 Правила именования

| Объект | Правило | Пример |
|------|------|------|
| Стандартный сегмент сообщения | Маленькие буквы, общее понятие без префикса | `keyboard`, `select`, `mention` |
| Платформенный расширенный сегмент | Префикс `{platform}_` | `telegram_sticker`, `yunhu_form` |
| Стандартное API-действие | Стандартное имя OB12 (snake_case) | `get_group_info`, `delete_message` |
| Платформенное расширенное действие | Префикс `{platform}.` или общее имя протокола | `yunhu.board`, `send_poke` (расширение OB11) |
| Модификатор | PascalCase, общая возможность в базовом классе фреймворка | `.Keyboard(rows)`, `.At(uid)` |
| Стандартное поле события | Общее понятие без префикса | `interaction_id`, `button_data`, `request_id` |
| Платформенное поле события | Префикс `{platform}_` | `qqbot_event_id`, `telegram_chat_id` |

### 3.2 Правила параметров и возвращаемых значений

- Стандартные параметры на всех платформах **одинаковые по имени и значению**; единицы измерения/форматы четко определены в стандарте (например, временные метки в секундах, строковые идентификаторы)
- Обязательные параметры — это **общее подмножество** возможностей всех платформ; платформенные расширения — необязательные параметры
- Сильные ограничения платформы (например, в QQBot нельзя одновременно отправлять богатую медиа и event_id) должны обрабатываться адаптером автоматически/понижаться, не выставляясь модулю
- Стандартные поля `data` возвращаемых значений должны быть одинаковыми на всех платформах; дополнительная платформенная информация помещается в `data` в платформенные поля или в `{platform}_raw`

## 4. Модели обработки различий (на уровне адаптера)

| Модель | Описание | Пример |
|------|------|------|
| **Отображение параметров** | Стандартный параметр → платформенный оригинальный параметр | `delete_message(message_id)` → TG `deleteMessage(chat_id, message_id)` (заполняется chat_id из регистра) |
| **Преобразование структуры** | Стандартный сегмент → платформенная оригинальная структура | Сегмент `keyboard` → `inline_keyboard` / buttons / клавиатура QQBot |
| **Отображение действий** | Стандартное имя действия → платформенное имя действия | `get_self_info` → `get_login_info` (OB11) |
| **Стандартизация полей** | Платформенный ответ → стандартные поля | `getMe()` → `{user_id, user_name, user_displayname}` |
| **Генерация идентификатора** | При отсутствии оригинального идентификатора на платформе генерируется определенный ID | TG join request без ID → `tjr_{chat}_{user}_{date}` |
| **Понижение возможностей** | При отсутствии поддержки возвращается текст/10002 | Kook без клавиатуры → alt_message в текстовом виде; `get_friend_list` → 10002 |
| **Нормализация** | Платформенные "грязные" данные → стандартный формат | QQBot @-отметка openid → bot_id (имя нормализуется) |
| **Двухрежимная совместимость** | Стандартная структура и платформенная оригинальная структура одновременно поддерживаются | `.Keyboard()` принимает общие rows или оригинальную структуру |

## 5. Стандарт интерактивных компонентов

### 5.1 Список компонентов и состояние

| Компонент | Стандартный сегмент type | Состояние | Поддерживаемые платформы |
|------|------------|------|-----------|
| Кнопки/клавиатура (keyboard) | `keyboard` | ✅ Стандартизирован | Telegram / Yunhu / QQBot |
| Выпадающий список (select) | `select` | 📋 Зарезервирован (структура см. §5.4) | Discord / Telegram(bot) |
| Карточки (card) | `card` | 📋 Зарезервирован (см. §5.5) | Kook / Yunhu(html) |
| Модальное окно (modal) | `modal` | 📋 Зарезервирован | Discord |

> Соглашение о иерархии модификаторов: модификаторы отправки общих интерактивных компонентов реализуются в **классе Send адаптера** (базовый класс фреймворка не содержит их), именование следует соглашениям §5.2, параметры соответствуют стандартной структуре настоящего руководства.

### 5.2 Кнопки/внутренняя клавиатура (keyboard)

#### Структура сегмента сообщения (направление отправки)

Стандартный сегмент `keyboard` = двумерный массив `rows`, каждый элемент кнопки —
`{"label": "отображаемый текст", "type": "callback" | "link", "data": "данные для обратного вызова или адрес перехода"}`, дополнительно допускаются необязательные платформенные поля (адаптер отображает или игнорирует в зависимости от возможностей).

> **Официальное определение структуры**: полная JSON-структура сегмента сообщения, таблица полей и семантика полей см.
> [Стандарт преобразования событий §4.1.1 Сегмент кнопки/внутренней клавиатуры](event-conversion.md#411-keyboard-кнопки-внутренняя-клавиатура-сегмент-кроссплатформенный-общий),
> в настоящем разделе повторять не будем.

#### Сопоставление на платформах

| Платформа | Стандартный сегмент → оригинальная структура | Оригинальная структура |
|------|------------------|-------------|
| Telegram | `reply_markup.inline_keyboard`: `[{text, callback_data \| url}]` | callback→`callback_data` (≤64 байта), link→`url` |
| Yunhu | `content.buttons`: `[{label, action_type}]` | callback→`action_type:2` + `action` + `value`, link→`action_type:1` + `url` |
| QQBot | `keyboard.content.rows`: `[{label, type, data}]` | callback→`type:2` + `data`, link→`type:0` + `data` (сообщение должно быть типа markdown) |
| Kook | Модуль `action-group` карточки: `[{type, text, value, click}]` | callback→`click:return` + `value`, link→`click:link` + `url` |
| Discord | `components[].components`: `[{label, style, custom_id \| url}]` | callback→`style:1` + `custom_id`, link→`style:5` + `url` |

#### Модификаторы отправки (реализуются в классе Send каждого адаптера)

Общие модификаторы реализуются **в классе Send каждого адаптера** (базовый класс фреймворка не изменяется):

- `.Keyboard(rows)`: общее имя, принимает структуру rows из §5.2, внутри генерирует стандартный сегмент `keyboard`
  (или напрямую преобразует в оригинальную структуру платформы), обрабатывается `Raw_ob12`
- `.Buttons(rows)`: необязательное синонимичное имя, поведение такое же
- **Обратная совместимость**: при обнаружении оригинальной структуры платформы — прозрачная передача (без ошибок, без преобразования)
- Платформенные оригинальные расширенные сегменты (например `telegram_inline_keyboard`) продолжают передаваться без изменений

```python
# Один и тот же код, любая платформа (адаптеры предоставляют модификаторы и преобразования)
rows = [[{"label": "Лайк", "type": "callback", "data": "like:1"},
         {"label": "Главная", "type": "link", "data": "https://example.com"}]]
await adapter.Send.To("group", gid).Keyboard(rows).Text("Выберите")
```

> Список совместимых адаптеров: QQBot / Telegram / Yunhu реализованы (модификаторы + преобразование стандартного сегмента);
> Новые адаптеры реализуются по настоящему руководству (см. §7 Checklist).

### 5.3 Обратные вызовы событий взаимодействия (после нажатия кнопки)

Событие, отправленное платформой после нажатия кнопки, **должно** содержать следующие стандартные поля (detail_type может сохранять платформенное имя):

| Стандартное поле | Тип | Обязательно | Описание |
|---------|------|------|------|
| `interaction_id` | str | Да | Идентификатор взаимодействия (может использоваться для ответа, например, индикатор загрузки/уведомление) |
| `button_data` | str | Да | Данные, возвращаемые кнопкой (см. §5.2 `data`) |
| `button_label` | str | Нет | Отображаемый текст кнопки |
| `user_id` | str | Да | ID пользователя, нажавшего |
| `message_id` | str | Нет | ID сообщения, в котором находится кнопка |
| `group_id` / `channel_id` | str | Нет | Идентификатор источника сессии |

**Соглашение о detail_type**: сохраняйте существующие платформенные имена (`qqbot_interaction` / `telegram_callback_query` /
`yunhu_a2ui_button` и т.д.), но **стандартные поля должны быть полными** — модули могут использовать `event.get("button_data")` для получения значений кроссплатформенно.

**Рекомендуемые расширенные методы Event (предоставляются EventMixin адаптера):**

```python
def get_button_data(self) -> str: ...     # button_data
def get_interaction_id(self) -> str: ...  # interaction_id
```

**Ответ на взаимодействие** (в зависимости от возможностей платформы): `adapter.reply_interaction(interaction_id, code=0)` (QQBot) /
`answerCallbackQuery` (Telegram) и т.д., именование следует семейству методов платформы, не обязательно унифицировать.

#### Сопоставление обратных вызовов событий на платформах

| Платформа | Оригинальное событие | detail_type | Источник interaction_id | Источник button_data |
|------|---------|-------------|--------------------|-----------------|
| Telegram | `callback_query` | `telegram_callback_query` (notice) | `callback_query.id` | `callback_query.data` |
| Yunhu | Событие нажатия кнопки | `yunhu_button_click` / `yunhu_a2ui_button` | `buttonId` / `sourceComponentId` | `value` / `actionName` |
| QQBot | `INTERACTION_CREATE` | `qqbot_interaction` | `interaction.id` | `data.resolved.button_data` |
| Kook | Событие нажатия кнопки | `kook_button_click` | `msg_id`+`value` | `value` |
| Discord | `INTERACTION_CREATE` | `discord_interaction` | `interaction.id` | `data.custom_id` |

### 5.4 select выпадающий список (резервный)

```json
{
  "type": "select",
  "data": {
    "placeholder": "Выберите",
    "options": [
      {"label": "Вариант A", "data": "opt:A"},
      {"label": "Вариант B", "data": "opt:B"}
    ],
    "min_values": 1,
    "max_values": 1
  }
}
```

Обратные вызовы событий используют поля из §5.3 (`button_data` = выбранный `data`, для множественного выбора — JSON-массив). Первые реализующие платформы: Discord (select menu), Telegram (переключение клавиатуры). Платформы, не реализующие, должны в `alt_message` преобразовывать сегмент в текстовый список.

### 5.5 card карточки (резервный, отложенный стандартизации)

Структура карточек сильно различается (модуль полнофункциональной карточки Kook vs html Yunhu vs markdown + клавиатура QQ), стандартизация отложена. Рекомендуется:

- Использовать комбинацию `text` + `keyboard` для выражения богатых текстовых карточек (для большинства сценариев достаточно)
- Полнофункциональные карточки платформы продолжают использовать расширенный сегмент `{platform}_card` (например, `kook_card`)
- Стандартизация будет рассмотрена, когда появится похожая карточная возможность на ≥2 платформах

## 6. Будущие кандидаты (Roadmap)

Следующие возможности уже появляются на ≥2 платформах или предполагаются, и стандартизация будет продвигаться в порядке приоритета:

| Кандидат | Платформы | Приоритет | Примечание |
|------|---------|--------|------|
| select выпадающий список | Discord / Telegram | Высокий | Структурный проект см. §5.4 |
| Реакции/эмоции (reactions) | QQBot / Telegram / Discord / Kook | Высокий | Стандартизация действий и событий с обеих сторон |
| Действия по управлению группой (запрет/выгон/одобрение) | QQBot / Yunhu / OB11 | Высокий | Большинство уже реализовано как платформенные действия, ожидается извлечение стандартного сигнатура |
| Анонсы/доски | Yunhu / Telegram / Discord | Средний | Действия типа `set_announcement` |
| Модель ресурсов файлов (двухчастный file_id) | Все платформы | Низкий (отложено) | Прямая отправка `SendDSL.File(file, filename)` уже стандартный путь (URL/путь/bytes напрямую, см. [Стандарт методов отправки §2.1](send-method-spec.md)); model file_id только при наличии на бэкенде, см. [Стандарт API-действий §3.5](api-action-spec.md) |
| Карточки card | Kook / Yunhu | Низкий | Структура сильно различается, см. §5.5 |
| Формы form | Yunhu | Низкий | Платформенный специфичный, сохраняется префикс `{platform}_` |
| Транскодирование медиа/определение размера | Все платформы | Низкий | Реализуется внутри адаптера, не стандартизируется |

## 7. Список проверки для разработчиков новых адаптеров

При разработке нового адаптера следуйте этому списку проверки (★ — обязательный, остальное рекомендуется):

- [ ] ★ Преобразование событий в стандартную структуру OneBot12, наследование `BaseConverter`
- [ ] ★ Поддержка стандартных сегментов сообщений (text/image/mention/reply/keyboard и т.д.; медиа-сегменты по [Стандарту методов отправки §2.1](send-method-spec.md) с обработкой иерархии и понижения)
- [ ] ★ Реализация `Raw_ob12` (включая преобразование стандартного сегмента → платформенную структуру; обязательна реализация стандартного сегмента `keyboard`)
- [ ] ★ Возвращение стандартной структуры ответа (`make_response`/`make_error`)
- [ ] ★ Поддержка нескольких аккаунтов: `AccountConfigClass(BotAccountConfig)` + парсинг аккаунта (сопоставление имени / `bot_id`)
- [ ] ★ Класс Send наследует `BaseAdapter.Send`, использует `_apply_modifiers`/`send_context`
- [ ] ☆ Api DSL: стандартные действия отображаются в API платформы (см. Стандарт API-действий)
- [ ] ☆ Request DSL: событие запроса содержит `request_id` + `accept/reject`
- [ ] ☆ Интерактивные компоненты: преобразование сегмента `keyboard` + стандартные поля обратных вызовов + модификаторы `.Keyboard()`/.Buttons() (реализуются в классе Send адаптера)
- [ ] ☆ EventMixin: `get_raw_event()` / `get_button_data()` и другие расширенные методы платформы
- [ ] ☆ Задачи жизненного цикла используют `runtime.spawn_background`
- [ ] ☆ Чтение конфигурации с помощью `self.cfg`
- [ ] ☆ Фреймворк: не объявлять жесткую зависимость от ErisPulse + проверка версии во время выполнения
- [ ] ☆ i18n: многоязычная конфигурация и логи
- [ ] ☆ platform-guide платформенная документация + файл platform-features.md в репозитории адаптера
