# Хранилище

> [!TIP]
> **Когда нужно читать эту статью**: при смене sqlite / mysql / postgres или при настройке пользовательского хранилища. Если не нужно, пропустите — это не повлияет на использование других функций.

ErisPulse включает три асинхронных хранилища, которые можно переключать с помощью конфигурации — **API полностью идентичны, переключение происходит без изменения кода**:

| Хранилище | Драйвер | Установка | Особенности |
|------|------|------|------|
| SQLite (по умолчанию) | aiosqlite | Готово к использованию | Нулевая конфигурация, одиночный файл, WAL-параллелизм |
| MySQL / MariaDB | aiomysql | `pip install ErisPulse[mysql]` | Подходит для уже существующей инфраструктуры MySQL, общие ресурсы между несколькими экземплярами |
| PostgreSQL | asyncpg | `pip install ErisPulse[postgres]` | Сильная поддержка транзакций, экосистема JSONB, высокая параллельность |

{!--< tips >!--}
1. Асинхронность реализована в основном интерфейсе (`aget/aset/atransaction/aExecute`), синхронные API — это слой совместимости
2. Все внутренние данные, такие как конфигурация, почтовый ящик сессий и контрольные точки диалога, хранятся в одном хранилище — переключение хранилища означает полную миграцию
3. `[mysql]` extra включает `cryptography` — необходим для аутентификации `caching_sha2_password` в MySQL 8, отсутствие приведет к ошибке инициализации пула соединений
{!--< /tips >!--}

## Выбор хранилища

Настройка в `config/config.toml`:

```toml
[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использование глобальной базы данных в пакете data/config.db
```

Также поддерживаются переменные окружения (Docker / 12-factor):

```bash
ERISPULSE_STORAGE_BACKEND=postgres
ERISPULSE_STORAGE_POSTGRES_HOST=db.example.com
ERISPULSE_STORAGE_POSTGRES_PASSWORD=secret
```

Правила именования переменных окружения: путь конфигурации в верхнем регистре, точки заменяются нижним подчеркиванием  
(`ErisPulse.storage.postgres.host` → `ERISPULSE_STORAGE_POSTGRES_HOST`).

## Параметры подключения

### MySQL (`ErisPulse.storage.mysql`)

```toml
[ErisPulse.storage.mysql]
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
charset = "utf8mb4"
pool_min = 1
pool_max = 10
```

### PostgreSQL (`ErisPulse.storage.postgres`)

```toml
[ErisPulse.storage.postgres]
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
pool_min = 1
pool_max = 10
```

> [!NOTE]
> После изменения параметров подключения необходимо перезапустить фреймворк (при горячем обновлении конфигурации будет выведено предупреждение о необходимости перезапуска).  
> Пул соединений создается лениво по циклу событий, при временных сбоях (например, сетевые колебания / окно перезапуска базы данных) автоматически повторяется с экспоненциальной задержкой.

## Поведение при сбое подключения

Фреймворк запускается и работает **без зависимости от доступности базы данных** — сбой подключения к MySQL / PostgreSQL не приведет к краху или невозможности запуска:

1. При временных сбоях создания пула соединений автоматически повторяется с экспоненциальной задержкой (по умолчанию 3 раза)
2. При исчерпании попыток — записывается предупреждение (с указанием причины и времени охлаждения), фреймворк запускается и продолжает работу, но операции с хранилищем временно недоступны
3. В течение периода охлаждения (по умолчанию 30 секунд) последующие операции с хранилищем **быстро завершаются ошибкой** (не блокируют, не замедляют остальные функции)
4. По окончании периода охлаждения автоматически пробуется повторное подключение — при восстановлении базы данных хранилище также восстанавливается, перезапуск не требуется

Пример лога: `mysql 连接池创建最终失败（已重试 3 次），30 秒后自动重连；期间存储操作将快速失败，框架其余功能不受影响`

## Семантика ошибок (начиная с 2.12)

| Сценарий | Поведение |
|------|------|
| Ошибка выполнения операции (превышение времени ожидания блокировки / SQL-ошибка / нарушение ограничений) | **Вызывается `StorageOperationError`** (запись: `aset` / `adelete` / `aclear` / `set_multi` и синхронные аналоги) — больше не возвращается `False` в тихом режиме, важные ошибки записи должны быть видны |
| Недоступность на уровне подключения (быстрое завершение в период охлаждения) | Возвращается `False` / `None` (быстрый отказ при недоступности на уровне подключения, сопровождается событиями `storage.unreachable` / `storage.recovered`) |
| Превышение времени ожидания начала транзакции (>30s) | Вызывается `StorageOperationError` (`STORAGE_TXN_BEGIN_TIMEOUT_SECS`) |

Важные операции записи следует обернуть в `try/except` и предусмотреть компенсацию; в блоке транзакции размещайте только чистые операции с базой данных.

## Асинхронный оригинальный API

```python
# Операции с ключ-значением
await sdk.storage.aset("app.name", "MyApp")
value = await sdk.storage.aget("app.name")
keys = await sdk.storage.aget_all_keys()

# Операции с таблицами
await sdk.storage.aCreateTable("users", {
    "id": "INTEGER PRIMARY KEY AUTOINCREMENT",
    "name": "TEXT NOT NULL",
})
rows = await sdk.storage.Table("users").Select("name").ToDict().aExecute()

# Асинхронная транзакция
async with sdk.storage.atransaction():
    await sdk.storage.aset("key1", "value1")
    await sdk.storage.Table("users").Insert({"name": "Alice"}).aExecute()
```

Синхронные API (`get/set/transaction/Table(...).Execute()`) продолжают работать, внутри они выполняются в фоновом цикле событий через `AsyncBridge` — **рекомендуется использовать методы с префиксом `a`** (`aget` / `aset` / `adelete` / `atransaction` / `aExecute`): синхронные интерфейсы при вызове в асинхронном обработчике блокируют цикл событий до завершения операции с хранилищем (при частом вызове это приводит к таймаутам обработчика и остановке обработки событий), фреймворк будет выводить предупреждения с частотой ограничения (с указанием места вызова — `файл:строка (имя функции)`, с охлаждением по месту вызова для предотвращения спама) — получив предупреждение, следует перенести соответствующий вызов на метод с префиксом `a`. Две важные границы необходимо знать:

- **Внутри моста запрещено вызывать синхронные интерфейсы**: синхронные интерфейсы выполняются в мостовом потоке, повторный вызов синхронных интерфейсов приведет к исключению `RuntimeError` (защита от повторного вызова, предотвращение самозаморозки)
- **После закрытия цикла событий вызовы будут завершаться ошибкой**: после `uninit()` не следует вызывать интерфейсы хранилища

Полный список методов см. в [SQL-построителе запросов](sql-builder.md).

## Различия в поведении диалектов

Все различия в диалектах скрыты внутри фреймворка, код вызывающей стороны не должен их знать:

| Различие | SQLite | MySQL | PostgreSQL |
|------|------|------|------|
| Заполнители | `?` | `%s` (автоматически переводится) | `$1..$n` (автоматически переводится) |
| UPSERT для KV | `INSERT OR REPLACE` | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT DO UPDATE` |
| Тип колонки для значения KV | `TEXT` | `LONGTEXT` | `TEXT` |
| Автоинкрементный первичный ключ | Нативная поддержка | `AUTO_INCREMENT` (автоматически переводится) | `SERIAL` (автоматически переводится) |

Определение типов колонок при создании таблиц следует использовать в стиле SQLite (например, `"INTEGER PRIMARY KEY AUTOINCREMENT"`, `"TEXT NOT NULL"`, `"DOUBLE DEFAULT 0.0"`), диалект автоматически переводит их в эквивалентный формат целевой базы данных.

## Устранение ошибки "database is locked" в SQLite

Встроенная поддержка SQLite в фреймворке включает: **режим журналирования WAL** (чтение и запись не блокируют друг друга) + **busy_timeout** (автоматическое ожидание при конкуренции за блокировку записи, по умолчанию 5000 мс, параметр см. ниже) + автокоммит-соединения + несколько циклов событий, каждый с общим соединением + **транзакция `BEGIN IMMEDIATE`** (начиная с 2.12 — транзакция получает блокировку записи при старте, устраняя `SQLITE_BUSY_SNAPSHOT` при повышении уровня в deferred-транзакциях, эти ошибки busy не повторяются, `busy_timeout` не помогает, это внутренняя причина периодических locked при частом смешанном чтении и записи).

При использовании чистого фреймворка (2.12+) с хранилищем / ORM / смешанным двойным путем перестанет возникать locked; если все еще возникает, проверьте в следующем порядке:

| Сценарий | Причина | Решение |
|------|------|------|
| Долгая операция в транзакции | `atransaction` блок содержит медленную активность (внешний HTTP, большие вычисления), удержание блокировки превышает busy_timeout — фреймворк выводит предупреждение при удержании блокировки более 1 секунды (`STORAGE_TXN_SLOW_WARN_SECS`) и указывает место начала, что позволяет напрямую локализовать | Перенести медленные операции за пределы транзакции |
| Синхронный API блокирует цикл событий | Многочисленные таймауты обработчиков событий + предупреждения о вызове синхронного API в асинхронном контексте | Перенести вызовы, указанные в предупреждениях, на методы с префиксом `a` (`set` → `aset` и т.д.) |
| Смешанное использование второго ORM | В одном процессе sqlmodel / SQLAlchemy / обычный sqlite3 открывают соединения и записывают в один файл базы данных | **Использовать только один ORM** (встроенный уже асинхронный), не смешивать |
| Множественные процессы с одним файлом | Несколько экземпляров / Dashboard / инструменты базы данных открыли один файл sqlite | Использовать отдельные каталоги `config/` для каждого экземпляра; инструменты управления открывать в режиме только для чтения; при частой записи переключиться на mysql / postgres (переключение происходит без изменения кода) |
| Старая версия фреймворка | Проблема повышения уровня deferred-транзакций в версиях <2.12 | Обновить фреймворк |

Матрица блокировок (режим WAL): **чтение с чтением, чтение с записью не блокируют друг друга**; блокировка существует только между **записью с записью** — транзакционное соединение (удерживает блокировку до коммита) и общие соединения циклов событий конкурируют за одну и ту же блокировку записи, длинные транзакции — главный подозреваемый в таймаутах ожидания.

> `busy_timeout` настраивается через `ErisPulse.storage.sqlite.busy_timeout` (миллисекунды, по умолчанию 5000); увеличение может продлить время ожидания при очереди блокировок, изменения требуют перезапуска (PRAGMA применяется при установлении соединения).

## Пользовательское SQL-хранилище

Для чисто SQL-хранилищ можно наследовать общий базовый класс, предоставив только управление соединениями и диалект выполнения:

```python
from ErisPulse.Core.Bases.sql_base import SQLDialect, SQLStorageBase

class MyDialect(SQLDialect):
    name = "mydb"
    # Переопределить: перевод заполнителей / кавычки / UPSERT / сопоставление типов ...

class MyStorage(SQLStorageBase):
    dialect = MyDialect()

    async def _create_loop_resource(self): ...   # Пул соединений
    async def _destroy_loop_resource(self, r): ...
    async def _acquire_resource_conn(self, r): ...
    async def _release_resource_conn(self, r, c): ...
    async def _open_txn_conn(self): ...
    async def _close_txn_conn(self, c): ...
    async def _exec_query_on(self, kind, sql, params, conn): ...  # Выполнение запроса
```

Для не-SQL хранилищ (например, Redis), наследуя `BaseStorage` и реализуя асинхронные интерфейсы KV, можно получить цепочечные возможности запросов к таблицам через `KVQueryBuilder` (фильтрация в памяти, подходит для небольших объемов данных).
