# Хранилище

> [!TIP]
> **Когда нужно читать эту статью**: при переключении на sqlite / mysql / postgres или при использовании пользовательского хранилища. Если не нужно — пропустите, это не повлияет на использование других функций.

ErisPulse включает три асинхронных хранилища, которые можно переключать с помощью конфигурации, **API полностью идентичны, переключение не требует изменений кода**:

| Хранилище | Драйвер | Установка | Особенности |
|------|------|------|------|
| SQLite (по умолчанию) | aiosqlite | Готово к использованию | Нулевая конфигурация, одиночный файл, WAL-параллелизм |
| MySQL / MariaDB | aiomysql | `pip install ErisPulse[mysql]` | Подходит для существующей инфраструктуры MySQL, совместное использование несколькими экземплярами |
| PostgreSQL | asyncpg | `pip install ErisPulse[postgres]` | Сильная поддержка транзакций, экосистема JSONB, высокая параллельность |

{!--< tips >!--}
1. Асинхронность является основным интерфейсом (агет/асет/атранзакция/аэкзекьют), синхронный API — это слой совместимости
2. Постоянная конфигурация фреймворка, почтовый ящик сессий, контрольные точки диалога — все данные хранятся в одном хранилище. Переключение хранилища означает полную миграцию
3. Дополнительный пакет `[mysql]` уже включает `cryptography` — необходим для аутентификации `caching_sha2_password`, используемой по умолчанию в MySQL 8. При отсутствии пакета инициализация пула соединений завершится ошибкой
{!--< /tips >!--}

## Выбор хранилища

Настройка в файле `config/config.toml`:

```toml
[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использование глобальной базы данных data/config.db из пакета
```

Поддерживается также перекрытие через переменные окружения (Docker / 12-factor):

```bash
ERISPULSE_STORAGE_BACKEND=postgres
ERISPULSE_STORAGE_POSTGRES_HOST=db.example.com
ERISPULSE_STORAGE_POSTGRES_PASSWORD=secret
```

Правило именования переменных окружения: путь конфигурации в верхнем регистре, точки заменяются на нижние подчеркивания
(`ErisPulse.storage.postgres.host` → `ERISPULSE_STORAGE_POSTGRES_HOST`).

## Параметры подключения

### MySQL (`ErisPulse.storage.mysql`)

```toml
[ErisPulse.storage.mysql]
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
charset = "utf8mb4"
pool_min = 1
pool_max = 10
```

### PostgreSQL (`ErisPulse.storage.postgres`)

```toml
[ErisPulse.storage.postgres]
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
pool_min = 1
pool_max = 10
```

> [!NOTE]
> После изменения параметров подключения необходимо перезапустить фреймворк (при горячем обновлении конфигурации будет выведено предупреждение о необходимости перезапуска).
> Пул соединений создается лениво по циклу событий. При временных ошибках (колебания сети / окно перезапуска базы данных) автоматически происходит экспоненциальная повторная попытка.

## Поведение при сбое подключения

Запуск и работа фреймворка **не зависят от доступности базы данных** — сбой подключения к MySQL / PostgreSQL не приведет к аварийному завершению или невозможности запуска:

1. При временной ошибке создания пула соединений происходит автоматическая повторная попытка с экспоненциальной задержкой (по умолчанию 3 раза)
2. При исчерпании попыток — запись предупреждения (с указанием причины и времени охлаждения), фреймворк запускается и продолжает работу, операции с хранилищем временно недоступны
3. В течение периода охлаждения (по умолчанию 30 секунд) последующие операции с хранилищем **быстро завершаются с ошибкой** (не блокируют, не замедляют другие функции)
4. По окончании периода охлаждения автоматически происходит попытка повторного подключения — при восстановлении базы данных хранилище также восстанавливается, перезапуск не требуется

Пример лога: `mysql 连接池创建最终失败（已重试 3 次），30 秒后自动重连；期间存储操作将快速失败，框架其余功能不受影响`

## Семантика сбоев (начиная с 2.12)

| Сценарий | Поведение |
|------|------|
| Ошибка выполнения операции (превышение времени ожидания блокировки / SQL-ошибка / нарушение ограничений) | **Вызывается `StorageOperationError`** (запись: асет / адеlete / акlear / сет_мульти и синхронные методы) — больше не возвращается `False`, важные ошибки записи должны быть видны |
| Недоступность на уровне подключения (быстрая ошибка в периоде охлаждения) | Возвращается `False` / `None` (быстрая ошибка при недоступности на уровне подключения, сопровождается событиями `storage.unreachable` / `storage.recovered`) |
| Превышение времени ожидания начала транзакции (>30s) | Вызывается `StorageOperationError` (`STORAGE_TXN_BEGIN_TIMEOUT_SECS`) |

Важные операции записи следует обернуть в try/except и выполнить компенсацию; в блоке транзакции размещайте только чистые операции БД.

## Асинхронный оригинальный API

```python
# Операции KV
await sdk.storage.aset("app.name", "MyApp")
value = await sdk.storage.aget("app.name")
keys = await sdk.storage.aget_all_keys()

# Операции таблиц
await sdk.storage.aCreateTable("users", {
    "id": "INTEGER PRIMARY KEY AUTOINCREMENT",
    "name": "TEXT NOT NULL",
})
rows = await sdk.storage.Table("users").Select("name").ToDict().aExecute()

# Асинхронная транзакция
async with sdk.storage.atransaction():
    await sdk.storage.aset("key1", "value1")
    await sdk.storage.Table("users").Insert({"name": "Alice"}).aExecute()
```

## Синхронные методы (осторожно)

У каждого асинхронного метода с префиксом `a` есть соответствующий синхронный вариант (`aget`→`get`, `aset`→`set`, `atransaction`→`transaction`, `aExecute`→`Execute`), который выполняется через мост на фоновом цикле событий — **они блокируют вызывающий поток**:

- **Вызов в асинхронном обработчике приведет к блокировке всего цикла событий** до завершения операции с хранилищем: при частом вызове это приведет к таймауту обработчика, остановке обработки событий, веб-качеству, и может цепочкой вызвать `database is locked` (ожидание блокировки записи истекло). Фреймворк выводит предупреждение о лимитировании частоты вызовов (с указанием `файл:строка (имя функции)`), получив такое предупреждение, следует перенести соответствующий вызов в асинхронный метод с префиксом `a`
- В режиме разработки можно включить `ErisPulse.framework.strict.sync_in_async = true`: синхронные вызовы больше не разрешаются, сразу выбрасывается `StrictModeError` (с указанием места вызова и инструкциями по миграции), что позволяет обнаружить проблему сразу, а не на этапе продакшена
- В режиме работы для срочного решения: ожидание моста в асинхронном контексте по умолчанию ограничено 10 секундами (`ErisPulse.framework.sync_in_async_bridge_wait`), при превышении таймаута отменяется и возвращается по fail-soft семантике — это запасной вариант, а не разрешение

**Убедитесь, что вы понимаете, что делаете, иначе не используйте синхронные формы.** В чисто синхронных потоках (без цикла событий) вызовы не ограничены, это допустимый сценарий (например, синхронный скрипт, ожидание завершения транзакции).

`asyncio.to_thread` / пулы потоков для выполнения синхронных драйверов аналогично, и в определенных сценариях может быть эффективным: **если хранилище поддерживает настоящую параллельность подключений** (PostgreSQL / MySQL — каждому потоку отдельное подключение, серверная MVCC-параллельность), перемещение синхронного драйвера за пределы цикла событий — разумный подход. Но в случае SQLite **не делайте этого** — потоковые подключения будут конкурировать с подключениями aiosqlite фреймворка за один и тот же блокировочный замок, увеличивая область гонки и, возможно, вызывая сбои записи или даже потерю данных.

Полный список методов см. в [SQL-построителе запросов](sql-builder.md).

## Различия в поведении диалектов

Все различия в диалектах скрыты внутри фреймворка, код вызова не должен их осознавать:

| Различие | SQLite | MySQL | PostgreSQL |
|------|------|------|------|
| Заполнитель | `?` | `%s` (автоматически переводится) | `$1..$n` (автоматически переводится) |
| KV UPSERT | `INSERT OR REPLACE` | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT DO UPDATE` |
| Тип значения колонки KV | `TEXT` | `LONGTEXT` | `TEXT` |
| Автоинкрементный первичный ключ | Встроенная поддержка | `AUTO_INCREMENT` (автоматически переводится) | `SERIAL` (автоматически переводится) |

Определения типов столбцов при создании таблиц используют стиль SQLite (например, `"INTEGER PRIMARY KEY AUTOINCREMENT"`, `"TEXT NOT NULL"`, `"DOUBLE DEFAULT 0.0"`), которые автоматически переводятся в эквивалентные записи для целевой СУБД.

## Отладка "database is locked" в SQLite

Встроенный SQLite-хранилище фреймворка уже включает: **режим журналов WAL** (чтение и запись не взаимоисключаются) + **busy_timeout** (автоматическое ожидание при конкуренции за блокировку записи, по умолчанию 5000 мс, параметр конфигурации см. ниже) + автокоммит соединений + несколько циклов событий с общим подключением + **транзакция `BEGIN IMMEDIATE`** (начиная с 2.12 — транзакция получает блокировку записи при старте, устраняя `SQLITE_BUSY_SNAPSHOT`, возникающий при обновлении `deferred`-транзакций "сначала читаем, потом записываем", этот `busy` не повторяется, `busy_timeout` не помогает, это внутренняя причина периодических `locked` в сценариях с интенсивным чтением и записью).

В чистом использовании фреймворка 2.12+ (хранилище / ORM / смешанные двойные пути) `locked` больше не должно возникать; если все еще возникает, проверьте следующие сценарии:

| Сценарий | Признак | Действие |
|------|------|------|
| Медленные операции в транзакции | В блоке `atransaction` есть медленные операции (внешний HTTP, большие вычисления), удерживающие блокировку более чем `busy_timeout` — фреймворк выводит предупреждение о транзакциях, удерживающих блокировку более чем 1 секунду (`STORAGE_TXN_SLOW_WARN_SECS`), с указанием места начала, что позволяет напрямую локализовать | Переместите медленные операции за пределы блока транзакции |
| Синхронный API блокирует цикл событий | Многочисленные таймауты обработчиков событий + предупреждения о "использовании синхронного API хранилища в асинхронном контексте" | Переместите вызовы, указанные в предупреждениях, в асинхронные методы с префиксом `a` (`set` → `aset` и т.д.) |
| Использование второй ORM | В одном процессе одновременно используются sqlmodel / SQLAlchemy / голый sqlite3 с открытым подключением к одному файлу базы данных | **Используйте только одну ORM** (встроенный фреймворк уже асинхронный), не смешивайте |
| Множественные процессы с одним файлом | Несколько экземпляров / Dashboard / инструменты базы данных открыли один и тот же файл SQLite | Используйте отдельные каталоги `config/` для каждого экземпляра; инструменты базы данных открывайте в режиме только для чтения; при частых записях переключитесь на mysql / postgres (переключение с помощью конфигурации без изменения кода) |
| Старая версия фреймворка | `deferred`-транзакции в версиях `<2.12` | Обновите фреймворк |

Матрица взаимных блокировок (режим WAL): **чтение с чтением, чтение с записью не взаимоисключаются**; взаимное исключение происходит только между **записью с записью** — транзакционное соединение (удерживает блокировку до коммита) и общие соединения для циклов событий конкурируют за один и тот же блокировочный замок, длительные транзакции — основной подозреваемый в таймаутах ожидания записи.

> `busy_timeout` настраивается параметром `ErisPulse.storage.sqlite.busy_timeout` (миллисекунды, по умолчанию 5000); увеличение может продлить терпение при очереди блокировок записи, изменение требует перезапуска (PRAGMA применяется при установлении соединения).

## Пользовательское SQL-хранилище

Для чистого SQL-хранилища можно унаследоваться от общего базового класса, достаточно предоставить управление подключениями и диалект выполнения:

```python
from ErisPulse.Core.Bases.sql_base import SQLDialect, SQLStorageBase

class MyDialect(SQLDialect):
    name = "mydb"
    # Переопределение: перевод заполнителей / кавычек для идентификаторов / UPSERT / сопоставление типов ...

class MyStorage(SQLStorageBase):
    dialect = MyDialect()

    async def _create_loop_resource(self): ...   # Пул соединений
    async def _destroy_loop_resource(self, r): ...
    async def _acquire_resource_conn(self, r): ...
    async def _release_resource_conn(self, r, c): ...
    async def _open_txn_conn(self): ...
    async def _close_txn_conn(self, c): ...
    async def _exec_query_on(self, kind, sql, params, conn): ...  # Выполнение запроса
```

Для не-SQL хранилищ (например, Redis) унаследуйтесь от `BaseStorage` и реализуйте асинхронный интерфейс KV, затем используйте `KVQueryBuilder` для получения цепочечной возможности запроса таблиц (фильтрация в памяти, подходит для небольших данных).
