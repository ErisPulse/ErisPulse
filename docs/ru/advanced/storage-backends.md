# Хранилище

> [!TIP]
> **Когда читать эту статью:** при смене sqlite / mysql / postgres или при использовании пользовательского хранилища. Не нужно — пропустите, это не повлияет на использование других функций.

ErisPulse включает три асинхронных хранилища, которые можно переключать по настройке одним кликом — **API полностью совместимы, переключение без изменений кода**:

| Хранилище | Драйвер | Установка | Особенности |
|------|------|------|------|
| SQLite (по умолчанию) | aiosqlite | Готово к использованию | Нулевая конфигурация, одиночный файл, WAL-параллелизм |
| MySQL / MariaDB | aiomysql | `pip install ErisPulse[mysql]` | Подходит для существующей инфраструктуры MySQL, совместное использование между несколькими экземплярами |
| PostgreSQL | asyncpg | `pip install ErisPulse[postgres]` | Сильная поддержка транзакций, экосистема JSONB, высокая параллельность |

{!--< tips >!--}
1. Асинхронный интерфейс является основным (`aget/aset/atransaction/aExecute`), синхронные API — это слой совместимости
2. Конфигурация фреймворка, почтовый ящик сессий, контрольные точки диалогов — все используют одно хранилище. Смена хранилища означает полную миграцию
3. `[mysql]` extra включает `cryptography` — обязательный для MySQL 8 по умолчанию `caching_sha2_password` аутентификации, отсутствие приведет к сбою инициализации пула подключений
{!--< /tips >!--}

## Выбор хранилища

Настройка в `config/config.toml`:

```toml
[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использование глобальной базы данных data/config.db из пакета
```

Также поддерживается переопределение через переменные окружения (Docker / 12-factor):

```bash
ERISPULSE_STORAGE_BACKEND=postgres
ERISPULSE_STORAGE_POSTGRES_HOST=db.example.com
ERISPULSE_STORAGE_POSTGRES_PASSWORD=secret
```

Правило именования переменных окружения: путь конфигурации в верхнем регистре, точки заменяются на подчеркивания  
(`ErisPulse.storage.postgres.host` → `ERISPULSE_STORAGE_POSTGRES_HOST`).

## Параметры подключения

### MySQL (`ErisPulse.storage.mysql`)

```toml
[ErisPulse.storage.mysql]
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
charset = "utf8mb4"
pool_min = 1
pool_max = 10
```

### PostgreSQL (`ErisPulse.storage.postgres`)

```toml
[ErisPulse.storage.postgres]
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
pool_min = 1
pool_max = 10
```

> [!NOTE]
> После изменения параметров подключения необходимо перезапустить фреймворк (при горячем обновлении конфигурации будет выведено напоминание о перезапуске).  
> Пул подключений создается лениво по циклу событий, при мгновенном сбое создания (дребезг сети / окно перезапуска базы данных) автоматически происходит экспоненциальная повторная попытка.

## Поведение при сбое подключения

Запуск и работа фреймворка **не зависят от доступности базы данных** — сбой подключения к MySQL / PostgreSQL не приведет к краху или невозможности запуска:

1. При мгновенном сбое создания пула происходит автоматическая экспоненциальная повторная попытка (по умолчанию 3 раза)
2. После исчерпания попыток — запись предупреждения (с указанием причины и времени охлаждения), фреймворк запускается и продолжает работу, только операции с хранилищем временно недоступны
3. В течение периода охлаждения (по умолчанию 30 секунд) последующие операции с хранилищем **быстро завершаются с ошибкой** (не блокируют, не замедляют остальные функции)
4. По окончании периода охлаждения автоматически происходит попытка повторного подключения — при восстановлении базы данных хранилище восстанавливается без перезапуска

Пример лога: `mysql 连接池创建最终失败（已重试 3 次），30 秒后自动重连；期间存储操作将快速失败，框架其余功能不受影响`

## Семантика сбоев (начиная с 2.12)

| Сценарий | Поведение |
|------|------|
| Ошибка выполнения операции (время ожидания блокировки / SQL-ошибка / нарушение ограничений) | **Вызывается `StorageOperationError`** (запись: `aset` / `adelete` / `aclear` / `set_multi` и аналогичные синхронные методы) — вместо тихого `False`, важные ошибки записи теперь видны |
| Недоступность на уровне подключения (быстрая ошибка в периоде охлаждения) | Возвращается `False` / `None` (правило 26 — устойчивость фреймворка, также есть события `storage.unreachable` / `storage.recovered`) |
| Таймаут начала транзакции (>30 с) | Вызывается `StorageOperationError` (`STORAGE_TXN_BEGIN_TIMEOUT_SECS`) |

Для важных операций записи используйте try/except и делайте компенсацию; в блоке транзакции размещайте только чистые операции с БД.

## Асинхронный оригинальный API

```python
# Операции с ключ-значением
await sdk.storage.aset("app.name", "MyApp")
value = await sdk.storage.aget("app.name")
keys = await sdk.storage.aget_all_keys()

# Операции с таблицами
await sdk.storage.aCreateTable("users", {
    "id": "INTEGER PRIMARY KEY AUTOINCREMENT",
    "name": "TEXT NOT NULL",
})
rows = await sdk.storage.Table("users").Select("name").ToDict().aExecute()

# Асинхронная транзакция
async with sdk.storage.atransaction():
    await sdk.storage.aset("key1", "value1")
    await sdk.storage.Table("users").Insert({"name": "Alice"}).aExecute()
```

Синхронный API (`get/set/transaction/Table(...).Execute()`) продолжает быть доступен, внутри он выполняется через `AsyncBridge` в фоновом цикле событий — **рекомендуется использовать методы с префиксом `a`** (`aget` / `aset` / `adelete` / `atransaction` / `aExecute`): синхронные интерфейсы в асинхронном обработчике вызывают блокировку этого цикла событий до завершения операции с хранилищем (при частом вызове это приводит к таймауту обработчика, остановке обработки событий), фреймворк выводит предупреждение о лимитировании частоты вызова (с указанием `файл:строка (имя функции)`), при получении предупреждения следует перенести соответствующий вызов на метод с префиксом `a`. Две важные границы:

- **Внутри мостового потока запрещено вызывать синхронные интерфейсы** — синхронные интерфейсы выполняются в мостовом потоке, повторный вызов синхронных интерфейсов приведет к `RuntimeError` (защита от повторного вызова, предотвращение самоблокировки)
- **После закрытия цикла событий вызов будет неудачным** — после `uninit()` не вызывайте интерфейсы хранилища

Полный список методов см. в [SQL-построителе запросов](sql-builder.md).

## Различия в поведении диалектов

Все различия в диалектах скрыты внутри фреймворка, код вызова не должен их знать:

| Различие | SQLite | MySQL | PostgreSQL |
|------|------|------|------|
| Заполнители | `?` | `%s` (автоматически переводится) | `$1..$n` (автоматически переводится) |
| UPSERT для KV | `INSERT OR REPLACE` | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT DO UPDATE` |
| Тип столбца значений KV | `TEXT` | `LONGTEXT` | `TEXT` |
| Автоинкрементный первичный ключ | Встроенная поддержка | `AUTO_INCREMENT` (автоматически переводится) | `SERIAL` (автоматически переводится) |

Определение типов столбцов таблицы должно использоваться в стиле SQLite (например, `"INTEGER PRIMARY KEY AUTOINCREMENT"`, `"TEXT NOT NULL"`, `"DOUBLE DEFAULT 0.0"`), а диалект автоматически переводит их в эквивалентную запись для целевого хранилища.

## Устранение "database is locked" в SQLite

Фреймворк SQLite включает: **режим WAL-журнала** (чтение и запись не блокируют друг друга) + **busy_timeout** (автоматическое ожидание при конфликте блокировки, по умолчанию 5000 мс, параметр см. ниже) + автокоммит подключения + несколько циклов событий с общим подключением + **транзакция `BEGIN IMMEDIATE`** (начиная с 2.12 — транзакция получает блокировку при старте, устраняя `SQLITE_BUSY_SNAPSHOT` при обновлении deferred-транзакций, этот `busy` не повторяется, `busy_timeout` не помогает, это корень проблемы `locked` в условиях частого смешанного чтения и записи).

Начиная с 2.12, при чистом использовании фреймворка (хранилище / ORM / смешанная двойная запись) не должно возникать `locked`; если всё ещё возникает, проверьте в следующем порядке:

| Сценарий | Причина | Решение |
|------|------|------|
| Медленные операции в транзакции | `atransaction` блок содержит медленные операции (внешний HTTP, большие вычисления), удержание блокировки превышает busy_timeout — фреймворк выводит предупреждение о транзакции, удерживающей блокировку более 1 с (`STORAGE_TXN_SLOW_WARN_SECS`), с указанием места запуска, можно сразу найти | Перенести медленные операции за пределы транзакции |
| Синхронный API блокирует цикл событий | Много таймаутов в обработчике событий + предупреждение о "использовании синхронного API хранилища в асинхронном контексте" | Перенести вызовы, указанные предупреждением, на методы с префиксом `a` (`set` → `aset` и т.д.) |
| Использование второй ORM | В одном процессе sqlmodel / SQLAlchemy / нативный sqlite3 открывают подключение и записывают в один файл базы данных | **Использовать только одну ORM** (встроенная уже асинхронная), не смешивать |
| Множественные процессы с одним файлом | Множественные экземпляры / Dashboard / инструменты базы данных открыли один и тот же sqlite | Использовать отдельные каталоги `config/` для каждого экземпляра; инструменты управления открывать в режиме только для чтения; при частом письме перейти на mysql / postgres (один клик переключения без изменения кода) |
| Старая версия фреймворка | Проблема с deferred-транзакциями в версиях `<2.12` | Обновить фреймворк |

Матрица взаимоблокировок (режим WAL): **чтение с чтением, чтение с записью не блокируются**; блокировка возникает только между **записями** — транзакционное подключение (устанавливает блокировку при `BEGIN IMMEDIATE` до завершения) и общие подключения циклов событий конкурируют за одну и ту же блокировку записи, длительные транзакции — главный подозреваемый в таймауте ожидания записи.

> `busy_timeout` настраивается через `ErisPulse.storage.sqlite.busy_timeout` (миллисекунды, по умолчанию 5000); увеличение может продлить терпение очереди блокировки, изменение требует перезапуска (PRAGMA применяется при установлении подключения).

## Пользовательское SQL-хранилище

Для чисто SQL-хранилища можно унаследовать общий базовый класс, нужно только предоставить управление подключениями и исполнительный пул диалекта:

```python
from ErisPulse.Core.Bases.sql_base import SQLDialect, SQLStorageBase

class MyDialect(SQLDialect):
    name = "mydb"
    # Переопределить: перевод заполнителей / ссылки на идентификаторы / UPSERT / сопоставление типов ...

class MyStorage(SQLStorageBase):
    dialect = MyDialect()

    async def _create_loop_resource(self): ...   # Пул подключений
    async def _destroy_loop_resource(self, r): ...
    async def _acquire_resource_conn(self, r): ...
    async def _release_resource_conn(self, r, c): ...
    async def _open_txn_conn(self): ...
    async def _close_txn_conn(self, c): ...
    async def _exec_query_on(self, kind, sql, params, conn): ...  # Исполнительный пул
```

Для не-SQL хранилищ (например, Redis) унаследуйте `BaseStorage`, реализуйте асинхронные интерфейсы KV, затем используйте `KVQueryBuilder` для получения цепочечных возможностей запросов к таблицам (фильтрация в памяти, подходит для небольших объемов данных).
