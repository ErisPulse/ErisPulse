# Система интерактивных сессий

> [!TIP]
> **Когда нужно читать эту статью**: при необходимости использования `wait_reply`, многократных диалогов,定时овых напоминаний, взаимоисключающих сессий или трассировки цепочки событий. Если не требуется, пропустите, это не повлияет на использование других функций.

> [!NOTE]
> В этой главе требуется ErisPulse **2.8.0+**.

ErisPulse реализует "непрерывное взаимодействие с пользователем" на уровне фреймворка: от одной `wait_reply`, до定时овых напоминаний, многоканального ожидания, взаимоисключающих сессий и восстановления после перезапуска, всё это управляется единым **менеджером интерактивных сессий** (`Core/Event/interaction.py`, `sdk.interaction`).

{!--< tips >!--}
Каждая из описанных в этой статье возможностей имеет **владельца (owner)**: ожидание интеракции, аренды,定时овые таймеры все регистрируются с указанием имени модуля, при отключении модуля или адаптера фреймворк автоматически очищает эти данные, и ожидание немедленно получает уведомление, а не просто ждёт таймаута — это расширение системы владения на уровень интеракции (см. [Систему владения](ownership.md)).
{!--< /tips >!--}

## Ожидание ответа: wait_reply

`wait_reply` — основа интерактивных сессий: приостанавливает текущую корутину и ожидает ответа от целевого пользователя в следующем сообщении.

```python
from ErisPulse.Core.Event import command

@command("ask")
async def ask_command(event):
    reply = await event.wait_reply(prompt="Пожалуйста, введите ваше имя:", timeout=30)
    if reply is None:
        await event.reply("Таймаут")
        return
    await event.reply(f"Привет, {reply.get_text()}!")
```

### Полный список параметров

| Параметр | Описание | Значение по умолчанию |
|------|------|------|
| `prompt` | Сообщение, отправляемое перед приостановкой | None |
| `timeout` | Таймаут ожидания (секунды) | 60 |
| `pattern` | Фильтр в формате glob (`*` / `?` / `[seq]`), если не совпадает — продолжает ожидание | None |
| `regex` | Регулярное выражение (должно совпадать с pattern, если задано), если не совпадает — продолжает ожидание | None |
| `validator` | Функция проверки (принимает Event, возвращает bool), если провал — продолжает ожидание | None |
| `callback` | Колбэк при получении ответа (альтернатива возвращаемому значению) | None |
| `method` | Метод отправки подсказки | "Text" |
| `session` | **Сессионное ожидание**: ответ любого участника в той же сессии (группа / канал) будет считаться ответом | False |

```python
# Принимает только сумму в виде числа и "元", иначе продолжает ожидание
reply = await event.wait_reply("Введите сумму:", regex=r"\d+\s*元", timeout=30)

# Сессионное ожидание: в сценарии групповой работы любой участник может ответить
reply = await event.wait_reply(session=True, prompt="Кто-нибудь может помочь ответить?")
```

### Граница между ожиданием и командой (пропуск команд)

Во время ожидания, если приходит сообщение с **зарегистрированной командой** (например, `/cancel`), по умолчанию оно передаётся диспетчеру команд и не считается ответом (параметр `ErisPulse.event.wait_reply.cmdpass`, если `True` — поведение меняется: сообщение всегда считается ответом). Текст сообщения сравнивается по тому же правилу, что и при диспетчеризации команд: `alt_message` имеет приоритет, если отсутствует, используется объединение текстовых сегментов (начиная с версии 2.10.1, это правило также применяется к адаптерам, использующим только чистый `message` сегмент).

### Когда ожидание будет отменено

Ожидание больше не ограничено только таймаутом — следующие события немедленно прервут его (возврат `None` от `wait_reply`), а не заставляют вызывающий код ждать до истечения таймаута:

| Событие | Причина отмены (InteractionCancelled.reason) | Описание |
|------|------|------|
| Модуль-владелец был отключен / отключен | `owner_unload` | Очистка владельца: кто зарегистрировал ожидание, тот и удаляет его |
| Адаптер был остановлен / перезапущен | `platform_stop` | Все ожидания на этой платформе отменяются |
| В той же сессии зарегистрировано новое ожидание / аренда | `conflict` | См. раздел "Арбитраж сессий" |
| Ответивший пользователь был заблокирован / модуль-владелец был откреплён | `revoked` | Проверка прав: проверка по идентификатору участника + по модулю |
| Ответ был получен | — | Нормальный путь, возвращается событие ответа |

Все исключения внизу иерархии наследуются от `InteractionCancelled` (входит в `InteractionError`), `wait_reply` уже преобразует их в возврат `None`; если нужно знать причину, можно использовать низкоуровневый API `sdk.interaction.register()`.

### Полная цепочка проверки ответа

Когда приходит сообщение с ответом, менеджер интеракции проверяет его по следующей последовательности (выполняется **до** командной диспетчеризации, приоритет сохраняется — даже если сообщение уже было признано другим высокоприоритетным обработчиком, приостановленный диалог может быть завершён):

```
Соответствие ключу сессии (точный по пользователю → возврат к сессионному ожиданию)
  → Фильтрация текста по pattern / regex (если не совпадает — продолжает ожидание)
  → Проверка по validator (если провал — продолжает ожидание)
  → Проверка прав (по идентификатору участника + по владельцу модуля, если провал — завершает ожидание)
  → Пробуждение ожидающего и признание события (mark_processed)
```

##定时овые таймеры сессии: remind / escalate

Превращает "таймаут" из возвращаемого значения в управляемый примитив.定时овые таймеры привязаны к интерактивной сессии и автоматически отменяются при отключении модуля или адаптера, максимальное количество активных remind на сессию — 5.

### remind: напоминание при отсутствии ответа

```python
@command("ticket")
async def ticket_command(event):
    await event.reply("Заявка создана, результат будет уведомлен здесь")
    # Если в течение 5 минут нет ответа, мягко напомнить один раз; любой ответ пользователя автоматически отменяет таймер
    event.remind(300, "Есть ли кто-нибудь? Результат будет уведомлен в ближайшее время")
    reply = await event.wait_reply(timeout=3600)
    ...
```

- `event.remind(delay, text=None, *, callback=None)`: при истечении срока отправляет в текущую сессию `text` (или выполняет `callback(event)`, поддерживает синхронные и асинхронные функции). **Обязательная проверка**: `text` и `callback` должны быть выбраны (если не заданы — выбрасывается `ValueError`)
- Возвращает `Reminder` дескриптор: `reminder.cancel()` для ручной отмены, `reminder.expired` для проверки состояния
- Автоматически отменяется при ответе пользователя — это и есть смысл "напоминания": напоминание появляется только если пользователь молчит
- В `Conversation` также доступно: `conv.remind(120, "Ещё думаете?")`

### escalate: обязательное уведомление по истечении срока

```python
event.escalate(1800, lambda e: notify_master(f"Заявка не обработана 30 минут: {event.get_command_args()}"))
```

Единственное отличие от `remind`: **не отменяется ответом пользователя** — действие "эскалации" (уведомление владельца, передача в ручную обработку) — это обязательное уведомление по истечении срока, отменяется только ручной `cancel()` / отключение модуля / остановка адаптера.

| | `remind` | `escalate` |
|---|---|---|
| Действие по истечению | Отправка текста / выполнение callback | Выполнение callback |
| Ответ пользователя | **Автоматически отменяется** | Не влияет |
| Очистка при отключении / остановке платформы | Отменяется | Отменяется |
| Максимальное количество на сессию | 5 | Не ограничено (очистка по владельцу в качестве резерва) |

## Многоканальное ожидание: expect + select

Ожидание нескольких условий одновременно, **первое поступившее событие** — победитель — типичный сценарий: ожидание одобрения администратором и одновременно ожидание отмены пользователем, голосование с участием нескольких участников.

```python
which, reply = await event.select(
    event.expect(pattern="同意*", user="10001"),
    event.expect(pattern="拒绝*", user="10002"),
    event.expect(validator=lambda e: e.get_text() == "搁置", session=True),
    timeout=60,
)
if which is None:
    await event.reply("В течение 60 секунд не получено ни одного результата одобрения")
elif which == 0:
    await event.reply("Одобрено")
elif which == 1:
    await event.reply("Отклонено")
```

- `event.expect(...)` создаёт **описание ожидания** (не регистрирует ожидание): поддерживает `pattern` / `regex` / `validator` / `user` (ограничение ответившего пользователя) / `session` (любой может ответить)
- `event.select(*expectations, timeout=60)`: объединяет ожидания → при первом совпадении возвращает `(индекс, событие ответа)` → несовпавшие ожидания автоматически отменяются; при истечении таймаута возвращается `(None, None)`. **Обязательная проверка**: нужно передать хотя бы одно ожидание, иначе выбрасывается `ValueError`
- Событие, которое совпало, уже признано фреймворком (mark_processed), и не будет повторно обработано другими обработчиками

{!--< tips >!--}
`select` против ручной организации с `asyncio.wait` в многопоточном режиме: несовпавшие ожидания автоматически очищаются, событие, которое совпало, автоматически признано, проверка прав и очистка владельца полностью реализованы — не нужно самостоятельно управлять Future.
{!--< /tips >!--}

> [!NOTE]
> Начиная с версии 2.10.1, `select` стал **агрегирующим ожиданием**: все ожидания объединяются в один элемент + пользовательская логика определения совпадения, одновременно несколько ожиданий (например, два разных pattern для одного пользователя) больше не отменяют друг друга, первое совпадение возвращает результат. Критерий определения текста совпадения — `alt_message` имеет приоритет + возврат текста из сегментов (согласуется с диспетчеризацией команд).
>
> Ограничение: `event.wait_for(...)` привязан к событию адаптера и **не проходит** через промежуточные обработчики и фильтры `detail_type` (вход по идентификатору участника обеспечивается на уровне входа в диспетчер). Для полной цепочки ожидания используйте `wait_reply` / `select`.

## Взаимоисключающие сессии: acquire / hold / get_owner_of

Владение ресурсами перешло на уровень сессии — "кто сейчас занят этим пользователем" стал первостепенным вопросом.

```python
# Запрос: кто сейчас взаимодействует с этой сессией? (если свободна, возвращает None)
owner = sdk.interaction.get_owner_of(event)
if owner and owner != "MyModule":
    return  # Другой модуль уже взаимодействует, избегаем мешать

# Взаимоисключающая аренда: эксклюзивное владение сессией (политика deny, если занята — возвращает None)
lease = sdk.interaction.acquire(event)          # По умолчанию TTL 1 час, можно передать ttl=
if lease is None:
    return  # Уже занята
try:
    ...  # Эксклюзивное взаимодействие
finally:
    lease.release()
```

Форма контекстного менеджера (при неудаче выбрасывает `SessionOccupiedError`):

```python
with sdk.interaction.hold(event) as lease:
    ...  # Автоматически освобождается при выходе
```

Аренда поддерживает `renew(ttl)` для продления; TTL отключается по истечении — просроченные аренды автоматически очищаются при следующем обращении.

При восстановлении сессии (`Conversation.resume()`) фреймворк автоматически приобретает аренду (см. [Многоходовой диалог Conversation](conversation.md) "Восстановление — это захват") — восстановленный диалог автоматически владеет сессией, другие модули не смогут вмешаться.

## Почтовый ящик сессии: event.history

> Стратегия хранения (7 дней / лимит по количеству) и API для управления в режиме выполнения, риски и аудит см. в специальной статье [Почтовый ящик сессии](transcript.md).

Единая запись недавних сообщений для каждой сессии (со стороны пользователя и бота), служит в качестве общего фактического фундамента для модулей, использующих контекст AI, предотвращения повторений, анализа поведения — каждый модуль больше не должен хранить историю отдельно.

```python
messages = await event.history(20)   # Последние 20 сообщений в текущей сессии, в порядке возрастания времени
for m in messages:
    print(m["role"], ":", m["text"])  # role: "user" / "bot"
```

- Автоматическая запись: входящие сообщения (role=user) + исходящие текстовые сообщения бота (role=bot)
- Хранение: отдельная таблица SQLite, стратегия хранения = лимит на сессию (по умолчанию 50) + глобальный TTL (по умолчанию 7 дней)
- Запись: буферизация в памяти + асинхронная постепенная запись на диск (задержка до 1 сек), интерфейс запроса автоматически объединяет несохранённые буферные строки — чтение из буфера в том же процессе не влияет; при нормальном завершении (sdk.uninit / выход из процесса) данные автоматически записываются на диск. **При сильном сбое / принудительном завершении процесса последние около 1 сек записи могут быть потеряны**: эта база данных предназначена для кэширования недавнего контекста, не подходит для аудита или долгосрочного хранения
- Конфигурация: `ErisPulse.transcript = {enabled = true, max_per_session = 50, ttl_hours = 168}`
- API менеджера: `sdk.transcript.append() / get() / clear()`, `aflush()` / `flush()` для ручной записи на диск

## Транзакции сообщений: message_tx

Все исходящие отправки в транзакции автоматически записываются в журнал; **при аномальном завершении транзакции автоматически отменяются отправленные сообщения** (если адаптер не реализует `delete_message`, отмена пропускается, журнал записывается нормально).

```python
async with event.message_tx():
    await event.reply("Обработка в процессе, подождите")
    result = await do_something()          # Здесь выбрасывается исключение →
    await event.reply(f"Готово: {result}")   # Сообщение "Обработка в процессе" автоматически отменяется
```

Отправки вне транзакции не записываются (нулевой накладной расход); `get_send_receipts()` позволяет просмотреть уже отправленные в текущей транзакции сообщения.

## Трассировка цепочки: trace-id

Каждому входящему событию автоматически присваивается идентификатор трассировки (используется `event["id"], если отсутствует — генерируется), он проходит через:

- контекст обработчика (`get_current_trace_id()` для чтения)
- исходящие отправки (строки лога `[Send]` с дополнением `[trace:...]`, поле `trace_id` в хуках `message.sending/sent`)
- данные цикла жизни (словарь автоматически дополняется `_trace_id`)
- направленные события (`lifecycle.emit(..., to=...)`) и транзакционные подтверждения сообщений

При обработке одного сообщения несколькими модулями, по одному ID можно проследить всю цепочку (в логах / медленных запросах / аудите).

## Связь с другими системами

- **Владение**: ожидание / аренда /定时овые таймеры все регистрируются с указанием владельца, при отключении модуля — очищаются (см. [Систему владения](ownership.md))
- **Область действия**: проверка прав и модульного владения при совпадении ответа; аудит межмодульных вызовов выходит за пределы исходящего (см. [Область действия (scope)](scope.md))
- **Conversation**: многоходовой диалог — это конечный автомат на основе интерактивной сессии (см. [Conversation](conversation.md)), его ожидания также имеют все отмены / проверки прав / владение, описанные на этой странице
