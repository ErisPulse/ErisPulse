# Система интерактивных сессий

> [!TIP]
> **Когда нужно читать эту статью**: если нужны `wait_reply`, многоконтактные диалоги,定时овые напоминания, сессионная изоляция или трассировка цепочки. Если не нужно, пропустите, это не повлияет на использование других функций.

> [!NOTE]
> В этой главе требуется ErisPulse **2.8.0+**.

ErisPulse реализует "постоянное взаимодействие с пользователями" на уровне фреймворка: от одной `wait_reply`, до定时овых напоминаний, многоканального ожидания, сессионной изоляции и восстановления после перезапуска — всё это управляется единым **менеджером интерактивных сессий** (`Core/Event/interaction.py`, `sdk.interaction`).

{!--< tips >!--}
Каждая из описанных в этой статье возможностей имеет **владельца (owner)**: ожидание, аренда, таймеры — всё это записывается с именем модуля при регистрации, и при выгрузке модуля / отключении адаптера фреймворк автоматически очищает ожидания, и ожидаемый получатель немедленно получает уведомление, а не ждёт таймаута. Это расширение системы владения на интерактивную ось (см. [систему владения](ownership.md)).
{!--< /tips >!--}

## Ожидание ответа: wait_reply

`wait_reply` — основа интерактивных сессий: приостанавливает текущий корутин, ожидая, что целевой пользователь ответит следующим сообщением.

```python
from ErisPulse.Core.Event import command

@command("ask")
async def ask_command(event):
    reply = await event.wait_reply(prompt="Пожалуйста, введите ваше имя:", timeout=30)
    if reply is None:
        await event.reply("Таймаут")
        return
    await event.reply(f"Привет, {reply.get_text()}!")
```

### Полный список параметров

| Параметр | Описание | По умолчанию |
|------|------|------|
| `prompt` | Сообщение, отправленное перед приостановкой | None |
| `timeout` | Время ожидания (секунды) | 60 |
| `pattern` | Фильтрация с помощью шаблона (glob, `*` / `?` / `[seq]`), если не совпадает — продолжить ожидание | None |
| `regex` | Фильтрация с помощью регулярного выражения (должно совпадать, если заданы и pattern и regex), если не совпадает — продолжить ожидание | None |
| `validator` | Функция проверки (принимает Event, возвращает bool), если провал — продолжить ожидание | None |
| `callback` | Колбэк при получении ответа (альтернативный способ вместо возвращения значения) | None |
| `method` | Метод отправки prompt | "Text" |
| `session` | **Сессионное ожидание**: ответ любого участника в той же сессии (группа / канал) может быть принят | False |

```python
# Принимает только числовую сумму, иначе продолжает ожидание
reply = await event.wait_reply("Введите сумму:", regex=r"\d+\s*元", timeout=30)

# Сессионное ожидание: сценарий сотрудничества в группе, любой участник может ответить
reply = await event.wait_reply(session=True, prompt="Кто-нибудь может помочь ответить?")
```

### Граница между ожиданием и командами (проникновение команд)

Во время ожидания, если приходит сообщение с **зарегистрированной командой** (например, `/cancel`), по умолчанию оно передаётся диспетчеру команд и не считается ответом (параметр `ErisPulse.event.wait_reply.cmdpass`, при `True` — наоборот — сообщение всегда считается ответом). Текст сообщения сравнивается с командой так же, как и в диспетчере команд: `alt_message` имеет приоритет, если отсутствует — используется строка из сообщения (с 2.10.1 работает и для адаптеров, где сообщение состоит только из `message`).

### Когда ожидание будет отменено

Ожидание больше не "только ждать таймаута" — следующие ситуации немедленно **прекращают** ожидание (`wait_reply` возвращает `None`), а не заставляют вызывающий код ждать таймаута:

| Причина | Причина отмены (reason типа `InteractionCancelled`) | Описание |
|------|------|------|
| Модуль-владелец был выгружен / отключен | `owner_unload` | Очистка владения: тот, кто зарегистрировал ожидание, при исчезновении модуля ожидание также удаляется |
| Адаптер был остановлен / перезапущен | `platform_stop` | Все ожидания в рамках этой платформы отменяются |
| В той же сессии появилось новое ожидание / аренда | `conflict` | См. ниже "арбитраж сессий" |
| Ответивший пользователь был заблокирован / владелец модуля был отвязан | `revoked` | Проверка прав доступа: проверка по идентификатору участника + модуля |
| Ответ был принят | — | Нормальный путь, возвращает событие ответа |

Внутреннее исключение — `InteractionCancelled` (входит в систему исключений `InteractionError`), `wait_reply` уже преобразует его в возвращение `None`; если нужно получить причину, вызывающий код может использовать низкоуровневый API `sdk.interaction.register()`.

### Полная цепочка проверки принятия ответа

При получении сообщения ответа менеджер интерактивных сессий проверяет его в следующем порядке (выполняется **до** командного распознавания, приоритет сохранения диалога — даже если сообщение было распознано другим обработчиком с высоким приоритетом, приостановленный диалог может быть завершён):

```
Соответствие сессионного ключа (точный user-уровень → возврат к сессионному ожиданию)
  → фильтрация текста с помощью pattern / regex (если не совпадает — продолжить ожидание)
  → проверка validator (если провал — продолжить ожидание)
  → проверка прав доступа (по идентификатору участника + модуля, если провал — завершить ожидание)
  → пробуждение ожидаемого получателя + подтверждение события (mark_processed)
```

## Декларативные многоконтактные диалоги: `.got()` цепочка (2.11+)

`@command` возвращает **прокси для многоконтактного управления**, с помощью `.got()` можно последовательно объявлять этапы сбора данных — функции этапов получают уже собранные значения (включая параметры входной команды) по именам параметров, типы автоматически определяются по `type=` или аннотациям. Всё это компилируется в `Conversation`: каждый этап — это ветвь, переходы автоматически сохраняют контрольные точки, **после перезапуска пользовательский ответ продолжится с сохранённого этапа** (фабрика восстановления автоматически регистрируется при декорировании и автоматически удаляется при выгрузке модуля).

```python
@command("weather")
async def weather(event):
    pass  # Вход: первый .got автоматически отправит prompt, не нужно спрашивать вручную

@weather.got("city", prompt="Пожалуйста, введите название города")
async def weather_city(event, city: str):
    await event.reply(f"{city}: ясно, 25℃")

@weather.got("days", prompt="На сколько дней прогнозировать?", type=int, retry_prompt="Введите число")
async def weather_days(event, city: str, days: int):
    await event.reply(f"{city} прогноз на {days} дней...")
```

### Параметры

| Параметр | Описание |
|------|------|
| `name` | Имя значения (имя параметра в последующих функциях этапов; уникально в рамках процесса, повторное объявление вызовет ошибку при регистрации) |
| `prompt` | Автоматически отправляемый вопрос при переходе на этот этап |
| `timeout` | Время ожидания на этапе (секунды или строка длительности, например, "90s" / "1h30m", по умолчанию 60s) |
| `type` | Тип значения (`int` / `float` / `str`…; если парсинг провалится, автоматически повторно отправляется `retry_prompt`, максимум `max_retries` раз) |
| `validator` / `pattern` / `regex` | Фильтрация и проверка ответа (семантика и [`wait_reply`](#ожидание-ответа-wait_reply)) |
| `session` | Сессионное ожидание (ответ любого участника в той же сессии может быть принят) |
| `cmdpass` | Трёхзначный режим пропуска команд (по умолчанию команды, такие как `/cancel`, выполняются в ожидании) |

### Семантика и границы

- **Любой этап завершается таймаутом / прерыванием → вся цепочка завершается** и контрольные точки удаляются (семантика совпадает с `wait_reply`); в функциях этапов можно в любое время использовать `event.reply(...)` для вывода промежуточных результатов
- **У одного пользователя может быть только одна приостановленная интеракция** — вторая цепочка ожидания отменяет предыдущую (`InteractionCancelled("conflict")`); для уведомления о конфликте используйте [сессионную аренду](#сессионная-изоляцияacquire--hold--get_owner_of)
- Собранные значения существуют только в рамках процесса; для сложных состояний, требующих сохранения между перезапусками, используйте [Conversation](conversation.md) (с `context` + `branch/goto` + ручные контрольные точки)
- `@command` возвращает прокси-объект: поведение, `__name__`, docstring и пользовательские атрибуты полностью идентичны оригинальному объекту; `command.unregister(прокси)` автоматически распаковывает

## Сессионные таймеры: remind / escalate

Превращает "таймаут" из возвращаемого значения в компилируемую примитивную конструкцию. Таймеры привязаны к интерактивной сессии и автоматически отменяются при выгрузке модуля / остановке адаптера, лимит активных remind на сессию — 5 штук.

### remind: напоминание при отсутствии ответа

```python
@command("ticket")
async def ticket_command(event):
    await event.reply("Заявка принята, результаты будут здесь")
    # Если нет ответа за 5 минут, мягко напомнить; любой ответ пользователя автоматически отменит напоминание
    event.remind(300, "Есть ли ещё что-то? Результат будет сообщён сразу")
    reply = await event.wait_reply(timeout=3600)
    ...
```

- `event.remind(delay, text=None, *, callback=None)`: при истечении срока отправляет `text` (или выполняет `callback(event)`, поддерживает синхронные / асинхронные функции) в текущую сессию. **Обязательная проверка**: `text` и `callback` должны быть выбраны (не заданы — выброс `ValueError`)
- Возвращает `Reminder` дескриптор: `reminder.cancel()` для ручной отмены, `reminder.expired` для проверки состояния
- Ответ пользователя в этой сессии **автоматически отменяет напоминание** — это и есть смысл "напоминания": напоминание появляется только, когда пользователь молчит
- В `Conversation` также можно использовать: `conv.remind(120, "Ещё думаете?")`

### escalate: гарантированное уведомление по истечении срока

```python
event.escalate(1800, lambda e: notify_master(f"Заявка не обработана 30 минут: {event.get_command_args()}"))
```

Единственное отличие от `remind`: **не отменяется ответом пользователя** — уведомление (уведомление владельца, передача в ручную поддержку) — это "гарантированное уведомление по истечении срока", отменяется только ручной `cancel()` / выгрузкой модуля / остановкой адаптера.

| | `remind` | `escalate` |
|---|---|---|
| Действие по истечении срока | Отправка текста / выполнение callback | Выполнение callback |
| Ответ пользователя | **Автоматически отменяет** | Не влияет |
| Очистка владения (выгрузка / остановка платформы) | Отменяет | Отменяет |
| Лимит на сессию | 5 | Не ограничен (очистка по владению) |

## Многоканальное ожидание: expect + select

Приостанавливает несколько ожиданий одновременно, **первое поступившее событие — первое обслуживается** — типичный сценарий: ожидание одобрения администратором и одновременно ожидание отмены пользователем, голосование с участием нескольких человек.

```python
which, reply = await event.select(
    event.expect(pattern="同意*", user="10001"),
    event.expect(pattern="拒绝*", user="10002"),
    event.expect(validator=lambda e: e.get_text() == "搁置", session=True),
    timeout=60,
)
if which is None:
    await event.reply("В течение 60 секунд не получено ни одного результата")
elif which == 0:
    await event.reply("Утверждено")
elif which == 1:
    await event.reply("Отклонено")
```

- `event.expect(...)` создаёт **описание ожидания** (не регистрирует никаких ожиданий): поддерживает `pattern` / `regex` / `validator` / `user` (ограничение ответившего) / `session` (ответ может быть принят любым)
- `event.select(*expectations, timeout=60)`: регистрирует все ожидания → при первом совпадении возвращает `(индекс, событие ответа)` → несовпавшие ожидания автоматически отменяются; при таймауте возвращается `(None, None)`. **Обязательная проверка**: нужно передать хотя бы одно ожидание, иначе выброс `ValueError`
- Полученное событие уже подтверждено фреймворком (mark_processed), не будет повторно обработано другими обработчиками

{!--< tips >!--}
`select` по сравнению с ручной компиляцией с помощью `asyncio.wait` в многопоточном режиме: автоматическая очистка несовпавших ожиданий, автоматическое подтверждение полученных событий, автоматическая проверка прав доступа и очистка владения — всё это работает без необходимости вручную управлять Future.
{!--< /tips >!--}

> [!NOTE]
> С 2.10.1 `select` стал **агрегирующим ожиданием**: все ожидания объединяются в одно с пользовательским правилом совпадения, одновременные ожидания (например, два разных pattern для одного user) больше не отменяют друг друга, первое совпадение возвращает результат. Текст ответа сравнивается по `alt_message` с приоритетом + возврат к сообщению (семантика совпадает с диспетчером команд).
>
> Ограничения: `event.wait_for(...)` привязан к событию адаптера, **не проходит** через промежуточные обработчики и фильтры `detail_type` (вход по идентификатору участника обеспечивается входом в диспетчер); для полной цепочки ожидания используйте `wait_reply` / `select`.

## Сессионная изоляция: acquire / hold / get_owner_of

Владение расширяется от "ресурсов" до "сессий" — "кто сейчас занят этим пользователем" становится первостепенным вопросом.

```python
# Запрос: кто сейчас взаимодействует с этой сессией? (если свободна, возвращает None)
owner = sdk.interaction.get_owner_of(event)
if owner and owner != "MyModule":
    return  # Другой модуль уже взаимодействует, избегать мешать

# Исключительная аренда: эксклюзивная сессия (политика deny, если занята возвращает None)
lease = sdk.interaction.acquire(event)          # По умолчанию TTL 1 час, можно передать ttl=
if lease is None:
    return  # Уже занято
try:
    ...  # Эксклюзивное взаимодействие
finally:
    lease.release()
```

Форма контекстного менеджера (при неудаче выбрасывает `SessionOccupiedError`):

```python
with sdk.interaction.hold(event) as lease:
    ...  # Автоматически освобождается при выходе
```

Аренда поддерживает `renew(ttl)` для продления; TTL惰性过期 — истёкшие аренды автоматически очищаются при следующем обращении.

`Conversation.resume()` при восстановлении диалога автоматически приобретает аренду (см. [многоконтактные диалоги в Conversation](conversation.md) "восстановление — это захват") — восстановленный диалог автоматически владеет сессией, другие модули не смогут вмешаться.

## Сессионный ящик: event.history

> Стратегия хранения (7 дней / лимит на сообщения) и API для управления во время выполнения, риски и аудит см. в специальной статье [Сессионный ящик](transcript.md).

Единая запись недавних сообщений для каждой сессии (со стороны пользователя и бота), служит в качестве **общей базы фактов** для модулей, работающих с ИИ, предотвращения повторного ввода, анализа поведения — каждый модуль больше не хранит историю отдельно.

```python
messages = await event.history(20)   # Последние 20 сообщений текущей сессии, в порядке возрастания времени
for m in messages:
    print(m["role"], ":", m["text"])  # role: "user" / "bot"
```

- Автоматически записывается: входящие сообщения (role=user) + текстовые ответы бота (role=bot)
- Хранение: отдельная таблица SQLite, стратегия хранения = лимит на сессию (по умолчанию 50) + глобальный TTL (по умолчанию 7 дней)
- Запись: буфер в памяти + фоновая пакетная запись на диск (задержка до 1 секунды), интерфейс запроса автоматически объединяет не записанные строки — чтение из буфера в том же процессе не влияет; при нормальном завершении (`sdk.uninit` / выход из процесса) буфер автоматически записывается. **В случае жёсткого завершения / принудительного убийства процесса последние ~1 секунды записи могут быть потеряны**: эта база данных предназначена для кэширования недавних контекстов, не подходит для аудита или долгосрочного хранения
- Конфигурация: `ErisPulse.transcript = {enabled = true, max_per_session = 50, ttl_hours = 168}`
- API менеджера: `sdk.transcript.append() / get() / clear()`, `aflush()` / `flush()` для ручной записи

## Транзакции сообщений: message_tx

Все отправленные сообщения в рамках транзакции автоматически записываются в журнал; **при выходе с ошибкой автоматически отменяются отправленные сообщения в обратном порядке** (если адаптер не реализует `delete_message`, отмена пропускается, журнал всё равно записывается).

```python
async with event.message_tx():
    await event.reply("Обработка, пожалуйста, подождите")
    result = await do_something()          # Здесь выбрасывается исключение →
    await event.reply(f"Готово: {result}") # Предыдущее "Обработка" автоматически отменяется
```

Отправка вне транзакции не записывается (нулевая накладная); `get_send_receipts()` позволяет просмотреть уже отправленные в текущей транзакции сообщения.

## Трассировка цепочки: trace-id

Каждому входящему событию автоматически присваивается идентификатор трассировки (используется `event["id"]`, если отсутствует — генерируется), который проходит через:

- контекст обработчика (`get_current_trace_id()` для чтения)
- отправку сообщений (строки лога `[Send]` с `[trace:...]`), поле `trace_id` в хуках `message.sending/sent`
- данные жизненного цикла (dict автоматически дополняется `_trace_id`)
- направленные события (`lifecycle.emit(..., to=...)`) и транзакционные чеки сообщений

При обработке одного сообщения несколькими модулями, вся цепочка может быть связана одним и тем же ID (для логов / медленных запросов / аудита).

## Связь с другими системами

- **Владение**: ожидание / аренда / таймеры записывают владельца, при выгрузке — очищение (см. [систему владения](ownership.md))
- **Область видимости**: проверка прав доступа при ответе по идентификатору участника + модуля; аудит вызовов между модулями по направлению выхода (см. [область видимости](scope.md))
- **Conversation**: многоконтактный диалог — это конечный автомат на основе интерактивной сессии (см. [Conversation](conversation.md)), его ожидания также имеют все отмены / проверки / владения, описанные на этой странице
