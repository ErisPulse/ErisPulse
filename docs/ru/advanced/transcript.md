# Входящие диалога (Transcript)

> [!TIP]
> **Когда стоит читать этот документ**: когда нужны история сообщений, восстановление диалога или настройка политики хранения входящих. Если в этом нет необходимости — пропустите; на использование остальных функций это не влияет.


Входящие диалога автоматически записывают сообщения, которые бот отправляет и получает (организованные по ключу диалога `platform:detail_type:target_id`),
и предоставляют исторические данные для восстановления диалога (`event.history`), diff теневых модулей, воспроизведения при холодном старте и т.д.
Этот документ описывает **модель хранения и что именно защищает каждый регулятор политики хранения**, а также API переопределения во время выполнения и реальную цену снятия ограничений.

> Прежде чем менять ограничения, дочитайте до конца раздел «Риски и аудит» — у каждого регулятора есть причина своего существования.

## Принцип работы

```
Сообщение ──append()──▶ буфер записи (deque в памяти, жёсткий предел 4096 строк)
                        │  пакетная запись на диск каждую 1 секунду (одна партия ≤64 строк, одна транзакция)
                        ▼
              таблица transcript бэкенда storage (по умолчанию sqlite)
                        │  каждые ~32 добавления лениво запускают одну очистку по политике хранения
                        ▼
              ┌─ FIFO-обрезка по диалогу (max_per_session, по умолчанию 50 записей)
              └─ глобальное удаление по TTL (ttl_hours, по умолчанию 168 = 7 дней)
```

Три уровня защиты, и каждый защищает от своего риска:

| Регулятор | По умолчанию | Что защищает | Последствия отключения (=0) |
|-----------|--------------|--------------|------------------------------|
| Предел буфера записи | 4096 строк (константа, не настраивается) | **Память**: бэклог за время недоступности хранилища не переполняет RAM | Отключить нельзя — это линия обороны памяти |
| Обрезка отдельного текста | 2000 символов (константа, не настраивается) | Затраты памяти/диска одного сообщения | Отключить нельзя |
| `max_per_session` | 50 записей на диалог | **Рост на диске**: бесконечное накопление истории одного диалога | История этого диалога растёт бесконечно |
| `ttl_hours` | 168 (7 дней) | **Рост на диске**: долгосрочное накопление по всем диалогам | Таблица `transcript` растёт бесконечно |

Ключевое понимание: **у буфера записи есть жёсткий предел, поэтому ослабление политики хранения не переполнит память напрямую**;
настоящий риск находится на уровне хранилища и в потребителях ниже по потоку (см. следующий раздел).

> [!TIP]
> **Приложениям, которым не нужна память диалогов, можно отключить её целиком**: `ErisPulse.transcript.enabled = false`
> останавливает автоматическую запись входящих/исходящих сообщений — не пишется ни буфер в памяти, ни хранилище, что экономит резидентную память и постоянный
> IO уровня хранилища. Входящие диалога в основном обслуживают два класса потребностей — инъекцию AI-контекста и защиту от повторов; развёртываниям, где не нужны ни те, ни другие
> (например, чисто командным ботам), рекомендуется отключение.

## Конфигурация

```toml
[ErisPulse.transcript]
enabled = true          # вести ли автоматическую запись
max_per_session = 50    # сколько записей хранить на один диалог (0 = отключить обрезку диалога)
ttl_hours = 168.0       # глобальная длительность хранения (часы, 0 = никогда не очищать)
self_echo = "bot"       # обработка входящего эха бота: bot / skip / user
```

Переопределение переменными окружения тоже действует: `ERISPULSE_TRANSCRIPT_MAX_PER_SESSION`, `ERISPULSE_TRANSCRIPT_TTL_HOURS`,
`ERISPULSE_TRANSCRIPT_SELF_ECHO`.
Изменения конфигурации применяются «на горячую» (в пределах ритма записи буфера на диск, задержка не более ~1 секунды).

> [!TIP]
> **Если память диалогов не нужна — отключите её**: единственные потребители входящих — восстановление диалога / diff теней / воспроизведение при холодном старте.
> Если ваш бот (или развёрнутые модули) вообще не использует эти возможности, установка `enabled = false`
> сэкономит буфер памяти входящих и фоновый пакетный IO записи на диск — приём/передача сообщений и обработка команд остаются совершенно незатронутыми.

## Атрибуция сообщений (sender и meta)

Каждая запись во всех интерфейсах запросов (`get` / `recent` / `get_by_trace` / `event.history`)
единообразно несёт поля атрибуции, служащие для различения «кто сказал / какой модуль отправил»:

| Поле | Смысл |
|------|-------|
| `sender` | Идентификатор отправителя: для входящих — `user_id`, для исходящих — аккаунт бота / `self.user_id` в случае эха |
| `meta` | Метаданные на момент записи (контракт белого списка, не полный raw event) |

Белый список `meta`:

- **Входящие**: `nickname` (никнейм на момент события; при обратном запросе позже будет получен «текущий никнейм»),
  `self_id` (аккаунт бота), `sub_type`, `message_id`; эхо-сообщения дополнительно несут `self_echo: true`;
- **Исходящие**: контекст отправки (`platform` / `method` / `detail_type` / `target_id` /
  `bot_id` / `trace_id` / `preview`) и `module` (модуль, которому принадлежит отправка, см. ниже).

У записей старых версий (эпохи без колонки meta) `meta` равно `{}`, и обращение `meta.get("nickname", "")`
естественно деградирует; когда бэкенд хранилища не поддерживает ALTER, likewise происходит тихий откат к `{}`.

### Принадлежность исходящих (meta.module)

На одном экземпляре сообщения отправляют несколько модулей (чат, управление, запланированные напоминания). `meta.module`
исходящих записей идентифицирует принадлежность отправки; приоритет значений: `current_owner > current_caller > ""`:

| Сценарий отправки | Значение module |
|-------------------|-----------------|
| Код модуля выполняется в рамках вызова `module.call` | Имя целевого модуля |
| Отправка внутри обработчика событий модуля | Имя модуля, зарегистрировавшего этот обработчик (автоматически внедряется в период диспетчеризации) |
| Сам фреймворк / без контекста модуля | `""` |

Полезная нагрузка хуков `message.sent` / `message.sending` (send_ctx) также несёт поле `module`.

### Входящее эхо бота (self_echo)

Некоторые платформы/реализации протоколов сообщают о сообщениях, отправленных самим ботом, как о событиях message (например,
`report-self-message` в OneBot v11, outgoing message в Telegram). Фреймворк перед записью входящего распознаёт эхо по
условию `self.user_id == user_id` и обрабатывает его согласно конфигурации `self_echo`:

| Значение | Поведение |
|----------|-----------|
| `"bot"` (по умолчанию) | Запись всё равно выполняется, но с `role="bot"`, `sender=self_id`, `meta.self_echo=true` |
| `"skip"` | Запись не выполняется (если адаптер при этом вызывает `message.sent`, исходящая запись образуется естественным образом) |
| `"user"` | Записывается с `role="user"` (старое поведение, аварийный запасной выход для совместимости) |

На платформах без эха (где `self.user_id != user_id` выполняется всегда) поведение полностью совпадает с отключением этой функции.

### recent с фильтрацией по диалогу

```python
from ErisPulse import transcript

# Глобальное временное окно по всем диалогам (семантика воспроизведения при холодном старте, по умолчанию)
transcript.recent(3600)

# Ограничение одним диалогом: фильтрация на стороне сервера, чтобы избежать глобальной выборки с последующим сравнением session_key на клиенте запись за записью
transcript.recent(3600, session_key="onebot11:group:123")
```

`session_key=None` сохраняет сквозную семантику по всем диалогам; пустая строка `""` эквивалентна отсутствию фильтра (для устойчивости к ошибкам).

## API переопределения во время выполнения

Когда нужно динамически подстроить параметры во время работы (например, временно продлить хранение для отдельного сценария):

```python
from ErisPulse import transcript

# Переопределение (приоритетнее конфигурации; хранится только в памяти, после перезапуска восстанавливаются значения конфигурации)
transcript.set_retention(max_per_session=500, ttl_hours=24 * 30)

# Запрос действующих значений и их источника
transcript.get_retention()
# {'max_per_session': 500, 'ttl_hours': 720.0, 'overridden': ['max_per_session', 'ttl_hours']}

# Вернуть действие по конфигурации
transcript.reset_retention()
```

- Передача `0` = отключение соответствующей политики (в лог пишется warning, оставляющий след в аудите); отрицательные числа вызывают `ValueError`;
- Переопределение вступает в силу при следующей очистке по политике хранения (лениво, с задержкой в пределах ритма ~32 добавлений);
- Синглтон `transcript` можно импортировать из корневого пакета, а также доступен как `sdk.transcript`.

### Ручная архивация и запись на диск (append / flush)

Записи сообщений автоматически пишутся конвейером фреймворка; взаимодействия, не являющиеся сообщениями (клики по кнопкам, платёжные колбэки, внешние
webhook), тоже можно архивировать в ту же временную линию диалога, и в сочетании с `get_by_trace` пользовательские события
также становятся доступными для диагностики цепочки через `explain_trace`:

```python
from ErisPulse import transcript

transcript.append(
    "onebot11:12345",                 # подойдёт объект события / dict / строка ключа диалога
    role="bot",
    text="Пользователь нажал кнопку: pay_ok",
    event_id="evt_click_1024",
    meta={"order_id": "A-1024"},      # метаданные атрибуции (контракт белого списка)
)

await transcript.aflush()             # асинхронная принудительная запись на диск (вызывать перед assert в скриптах/тестах)
```

- `append` помещает запись только в буфер памяти и сразу возвращается (порядка микросекунд); очистка выполняется унифицированно по политике хранения; `flush` /
  `aflush` немедленно пишет в хранилище, а интерфейсы запросов автоматически объединяют ещё не записанные на диск строки буфера
- `session` должен совпадать с целевым диалогом (переиспользуйте ключ диалога события сообщения), иначе архивация попадёт в отдельную
  временную линию диалога

## Риски и аудит: обязательно прочитать перед снятием ограничений

После отключения `max_per_session` / `ttl_hours` (или значительного увеличения) таблица `transcript` **растёт бесконечно** вслед за объёмом сообщений. Цепочка последствий:

1. **Диск заполняется** — единственный файл sqlite непрерывно разрастается, и после исчерпания диска уровень хранилища фреймворка становится неработоспособным;
2. **Деградация запросов** — стоимость сканирования `get()` / `recent()` / `get_by_trace()` растёт вместе с таблицей;
3. **Давление на память вниз по потоку (реальный источник OOM)** — потребители,
   загружающие историю в память целыми фрагментами
   (восстановление диалога с историей, полная выгрузка панелью, ваш бизнес-код с `get(session, n)` при большом n)
   съедают память по мере роста таблицы; в крайних случаях срабатывает OOM kill.

**Перед снятием ограничений задайте себе три вопроса**: какая глубина истории нужна? какого объёма? кто будет её чистить?
Если ответ опирается на «никогда не удалять», правильное решение обычно — внешняя архивация (регулярно переносить старые данные в отдельную специализированную базу),
а не бесконечное хранение во входящих.

Средства аудита (регулярная проверка размера таблицы):

```python
# Число строк и объём через ORM/SQL-конструктор (пример для sqlite)
from ErisPulse import storage

row = storage.Table("transcript").raw_sql("SELECT COUNT(*) AS n FROM transcript")
```

```sql
-- Прямой запрос к файлу sqlite (объём таблицы)
SELECT COUNT(*) FROM transcript;
```

Появление в логе warning `политика хранения отключена` = кто-то отключил политику значением 0; убедитесь, что это была ваша собственная операция.

## Границы с другими механизмами

- **Таймеры интерактивных диалогов / wait_reply**: см. [Систему интерактивных диалогов](interaction.md), к входящим отношения не имеет;
- **Возврат истории при восстановлении диалога**: `resume(with_history=N)` берёт последние N записей из входящих —
  после обрезки входящих объём истории, который можно вернуть, уменьшается (увеличение `max_per_session` продлевает окно восстановления);
- **Diff теневых модулей**: зависит от цепочечных запросов `get_by_trace`; входящие со слишком коротким TTL сокращают окно, доступное для diff.
