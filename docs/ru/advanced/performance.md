## Тестирование производительности (2026-10-05, Python 3.13.14)

Один и тот же компьютер, два последовательных теста (предварительная прогревка + несколько циклов выборки с определением процентиля), NoneBot2 2.5.0 — контрольная среда в отдельном окружении.  
Все числовые значения можно воспроизвести с помощью встроенного в репозиторий бенчмарка: `python tests/performance/benchmark.py`.

## Самостоятельная проверка и сравнение с базовым тестом

```bash
# Быстрый режим (примерно 1/4 выборки, для быстрой проверки)
python tests/performance/benchmark.py --quick

# Полный базовый тест с сохранением результатов (8 компонентов: config/event/storage/send/router/module/overall/startup)
python tests/performance/benchmark.py --json baseline.json

# Сравнение с предыдущим базовым тестом (разница в пределах ±5% считается шумом)
python tests/performance/benchmark.py --compare baseline.json

# HTML-отчёт / указание бэкенда для хранения компонентов
python tests/performance/benchmark.py --html report.html
python tests/performance/benchmark.py --backend mysql
```

> Примечание для CI: цифры в базовом тесте могут меняться в зависимости от машины. Порог ±5% в `--compare` подходит только для **сравнения на одной и той же машине** (для проверки обновлений), но не подходит для сравнения между разными машинами.

## Оптимизация

1. **Узкое место по всей цепочке сообщений — это запись сессий**: по умолчанию включена запись transcript (с 2.9 версии — буферизация в памяти + фоновая пакетная запись на диск); при отсутствии потребностей в аудите можно отключить, пропускная способность по всей цепочке возрастёт примерно с 2,804 → 3,774 операций/с.
2. **Управление сборкой мусора (GC)**: группа настроек `proactive_gc` в `ErisPulse.framework` (`interval` / `full_every` / `memory_growth_mb` / `idle_only`) — при пике событий автоматически пропускает GC; на этапе инициализации уже встроена `gc.freeze()`.
3. **Хранилище**: для локального одиночного экземпляра sqlite (WAL) достаточно; при необходимости совместного использования данных между несколькими экземплярами используйте mysql / postgres (см. [Хранилище](storage-backends.md)).
4. **Встроенные оптимизации критических участков кода** (начиная с 2.9, не требует настройки): пакетная запись transcript, кэширование i18n, защита уровней логирования, предварительная компиляция матчера, объединённая синхронизация задержанных записей конфигурации.
5. **Максимальное количество состояний команд**: таблица состояний охлаждения/ограничения/квоты ограничена 4096 записями (при превышении удаляются самые старые); при развертывании в больших группах настройка не требуется.

## Диагностика памяти

При поиске проблемы «чем дольше работает, тем больше ест памяти» поставьте по одному снимку с меткой label до и после подозрительного участка кода — для одинаковых label дельта рассчитывается автоматически (по двум метрикам: RSS + tracemalloc):

```python
from ErisPulse.runtime import log_snapshot, snapshot

class MyModule(BaseModule):
    async def on_load(self, event):
        snapshot("MyModule.load")            # Собирает и возвращает dict (включая дельту RSS по label)

    async def on_unload(self, event):
        log_snapshot("MyModule.unload")      # Сбор тем же методом и запись в лог уровня TRACE
```

- `snapshot(label)` возвращает машиночитаемый dict, подходит для ассертов и отчётов; `log_snapshot(label)`
  сразу пишет в лог (уровень TRACE), подходит для временной диагностики
- Кэш label ограничен по размеру и не «утекает» с ростом числа вызовов; в сочетании с метриками процесса
  эндпоинта `/metrics` можно вести долгосрочное наблюдение за трендами
- Остаточный рост памяти после выгрузки модуля обычно указывает на отсутствие привязки владельца (см. записи
  фоновых задач `bind_owner` в разделе [система владения](ownership.md))
