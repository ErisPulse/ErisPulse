# Процесс запуска и ручное управление

> [!TIP]
> **Когда стоит читать этот документ**: когда нужно вручную управлять цепочкой запуска, настраивать порядок запуска или разбираться со сбоями запуска. Если нет — пропустите, на использование остальных функций это не влияет.

`await sdk.run()` / `await sdk.init()` в ErisPulse инкапсулируют всю цепочку запуска в «одну строку кода». Но если вам нужно полностью кастомизировать процесс запуска (например, частичная загрузка, динамическая регистрация, горячая замена, внедрение собственной стратегии загрузки), потребуется понять, что именно происходит внутри этой цепочки и как вручную управлять каждым шагом.

В этой статье цепочка запуска разбита на отдельные этапы, описаны их обязанности и порядок вызова, а также приведён пример полного ручного запуска.

> Предполагается, что вы уже прошли руководство [Первый бот](../getting-started/first-bot.md) и знакомы с двумя режимами `sdk.run(keep_running=True/False)`. Статья сосредоточена на разборе цепочки **внутри** `init()`, а также на более низкоуровневых точках входа вроде `init()`/`init_task()`/`init_sync()`.

## Обзор точек входа SDK верхнего уровня

Помимо двух режимов `keep_running` у `run()`, SDK предоставляет несколько более низкоуровневых точек входа для инициализации. Различия — в **асинхронности, возвращаемом значении и том, перехватываются ли исключения**:

| Точка входа | Асинхронность | Возвращаемое значение | Обработка исключений | Сценарий применения |
|------|--------|--------|----------|----------|
| `await sdk.run(True)` | async, блокируется и поддерживает работу | `None` (при закрытии автоматически вызывает `uninit`) | Ошибки модулей/адаптеров перехватываются, не роняя процесс | Чисто бот-приложения |
| `await sdk.run(False)` | async, не блокируется | `None` (не выгружает автоматически) | Аналогично | Выполнение собственной логики после инициализации |
| `await sdk.init()` | async, требует await | `bool` | Перехватывает исключения компонентов внутри, при неудаче возвращает `False` | Ручное управление жизненным циклом (в паре с `uninit()`) |
| `sdk.init_task()` | async, возвращает Task, не блокирует | `asyncio.Task` | Как у `init()` | Параллельное выполнение другой инициализации или когда event loop ещё не запущен |
| `sdk.init_sync()` | **синхронный**, блокирует текущий поток | `bool` | Как у `init()` | CLI-скрипты, синхронные точки входа без event loop |

> **Частое заблуждение**: `await sdk.init()` **не эквивалентен** `await sdk.run(keep_running=False)`. Два отличия: ① `init()` возвращает `bool` (при неудаче — `False`), тогда как `run()` возвращает `None`; ② `init()` только выполняет инициализацию и **не выгружает автоматически**, тогда как `run()` при завершении event loop автоматически вызывает `uninit()`. Поэтому, когда требуется ручная пара с выгрузкой или собственный жизненный цикл, используйте `init()` + `uninit()`.

## Общая схема цепочки запуска

`sdk.init()` (точнее — его внутренний `Initializer.init()`) поднимает весь фреймворк в следующем порядке:

```mermaid
flowchart TD
    A[0. Подготовка окружения<br/>загрузка конфигурации / обработка исключений] --> B
    B[1. Параллельное обнаружение и загрузка<br/>AdapterLoader.load / ModuleLoader.load<br/>внутри вызывается Finder.find_all] --> C
    C[2. Регистрация адаптеров<br/>AdapterLoader.register_to_manager] --> D
    D[3. Запуск адаптеров<br/>adapter.startup] --> E
    E[4. Регистрация модулей<br/>ModuleLoader.register_to_manager] --> F
    F[5. Инициализация модулей<br/>ModuleLoader.initialize_modules<br/>создание экземпляров и монтирование в sdk] --> G
    G[6. Запуск сервера маршрутов<br/>router.start]
```

Соответствующие ключевые компоненты:

| Уровень | Компонент | Обязанности |
|----|------|------|
| Обнаружение | `AdapterFinder` / `ModuleFinder` | **Обнаружение** адаптеров/модулей среди entry-points установленных пакетов |
| Загрузка | `AdapterLoader` / `ModuleLoader` | Обнаружение + импорт + чтение метаданных + определение включён/выключен, возвращает список объектов |
| Регистрация | `*Loader.register_to_manager` | Регистрирует объекты в соответствующих менеджерах |
| Управление | `sdk.adapter` / `sdk.module` | Поддерживает экземпляры адаптеров/модулей, предоставляет интерфейсы запуска/остановки |
| Инициализация | `ModuleLoader.initialize_modules` | Создаёт экземпляры модулей и монтирует их в `sdk` (обрабатывает топологическую сортировку зависимостей) |
| Маршрутизация | `sdk.router` | HTTP / WebSocket сервер |

> **Важно**: `Finder` и `Loader` — это два уровня. `Loader` **уже содержит** внутри себя `Finder` (`AdapterLoader` имеет встроенный `AdapterFinder`, `ModuleLoader` — `ModuleFinder`). В подавляющем большинстве случаев вам достаточно `Loader`; отдельный `Finder` нужен только когда требуется «перечислить без импорта».

## Подробный разбор каждого этапа

### 1. Уровень обнаружения: Finder

Finder отвечает только за «поиск пакетов, предоставляющих адаптеры/модули», без импорта и без создания экземпляров.

```python
from ErisPulse.finders import AdapterFinder, ModuleFinder

adapter_finder = AdapterFinder()
module_finder = ModuleFinder()

# Поиск всех установленных entry-points адаптеров/модулей
adapter_entries = adapter_finder.find_all()    # list[EntryPoint]
module_entries = module_finder.find_all()      # list[EntryPoint]

# Поиск одного по имени
entry = module_finder.find_by_name("MyModule")  # EntryPoint | None
```

У каждого `EntryPoint` можно вызвать `.load()` и получить соответствующий класс, но обычно вручную это делать не нужно — Loader сделает это сам.

### 2. Уровень загрузки: Loader

Поверх Finder Loader выполняет «импорт + чтение метаданных + определение включён/выключен».

```python
from ErisPulse.loaders import AdapterLoader, ModuleLoader
from ErisPulse import sdk

adapter_loader = AdapterLoader()
module_loader = ModuleLoader()

# Внутри load(): вызов finder.find_all() → поочерёдная обработка entry-points → возврат кортежа из трёх элементов
adapter_objs, enabled_adapters, disabled_adapters = await adapter_loader.load(sdk.adapter)
module_objs, enabled_modules, disabled_modules = await module_loader.load(sdk.module)
```

Кортеж из трёх элементов, возвращаемый `load()`:

| Возвращаемое значение | Значение |
|--------|------|
| `objs` (`dict`) | имя → объект (класс адаптера / объект-обёртка модуля) |
| `enabled` (`list[str]`) | включённые имена (не отключённые в конфигурации) |
| `disabled` (`list[str]`) | отключённые имена |

#### Диагностическая информация при сбое загрузки

Когда модуль/адаптер выбрасывает исключение на этапе загрузки или инициализации, фреймворк пропускает этот компонент и продолжает загрузку остальных, одновременно выводя **сводку кадров пользовательского кода**, чтобы вы могли локализовать место ошибки даже на уровне INFO по умолчанию, без ручного включения DEBUG:

```
[ERROR] [ModuleLoader] Не удалось загрузить модуль MyModule из entry-point, пропущен: 'NoneType' object has no attribute 'platform'
  → MyModule/Core.py:42 in on_load
      adapter = sdk.platform
  → AttributeError: 'NoneType' object has no attribute 'platform'
  → Подсказка: повысьте уровень логов до DEBUG, чтобы увидеть полный стек; проверьте код реализации модуля MyModule
```

Диагностическая информация генерируется модулем `ErisPulse.runtime.diagnostics`, который автоматически отфильтровывает внутренние кадры фреймворка, оставляя только кадры вашего кода. Для повторного использования в собственной логике загрузки:

```python
from ErisPulse.runtime import log_diagnostic

try:
    risky_init()
except Exception as e:
    log_diagnostic(e)  # автоматически извлекает кадры пользовательского кода и пишет в лог уровня ERROR
```

Модуль также предоставляет две низкоуровневые функции: `extract_user_frame()` (возвращает структурированную информацию о кадре) и `format_diagnostic_block()` (возвращает многострочный текст).

### 3. Уровень регистрации: register_to_manager

Регистрирует объекты, полученные от Loader, в менеджерах, чтобы `sdk.adapter` / `sdk.module` могли их распознавать.

```python
# Регистрация адаптеров (возвращает bool — признак того, что всё прошло успешно)
await adapter_loader.register_to_manager(enabled_adapters, adapter_objs, sdk.adapter)

# Регистрация модулей
await module_loader.register_to_manager(enabled_modules, module_objs, sdk.module)
```

После регистрации адаптеры внесены в менеджер адаптеров, модули — в менеджер модулей, но **ни те, ни другие ещё не запущены/не инстанцированы**.

### 4. Запуск адаптеров

```python
# Запуск всех зарегистрированных адаптеров
await sdk.adapter.startup()
# Или указать платформы
await sdk.adapter.startup("yunhu")
await sdk.adapter.startup(["yunhu", "telegram"])
```

> Регистрация ≠ запуск. `register_to_manager` лишь вносит в реестр; только `startup` вызывает `start()` адаптера и устанавливает соединение с платформой.

### 5. Инициализация модулей

У модулей на один шаг больше, чем у адаптеров — нужно **создать экземпляры** и смонтировать их в `sdk` (чтобы вы могли обращаться через `sdk.MyModule.xxx`). На этом шаге также обрабатываются объявления зависимостей между модулями и топологическая сортировка.

```python
success = await module_loader.initialize_modules(
    enabled_modules, module_objs, sdk.module, sdk
)
```

После успешного создания экземпляров модули будут доступны как `sdk.<ModuleName>`.

### 6. Запуск сервера маршрутов

```python
await sdk.router.start(
    host="0.0.0.0",
    port=8000,
    ssl_certfile=None,
    ssl_keyfile=None,
)
```

Сервер маршрутов отвечает за приём Webhook / WebSocket callback'ов адаптеров. Если его не запустить, адаптеры в режиме server не смогут получать сообщения.

## Полный пример ручного запуска

Следующий код **эквивалентен** основному процессу `await sdk.init()`, но каждый шаг открыт в ваших руках: в любой этап можно вставить собственную логику:

```python
import asyncio
from ErisPulse import sdk
from ErisPulse.loaders import AdapterLoader, ModuleLoader

async def manual_startup():
    # 0. Подготовка окружения (загрузка конфигурации, регистрация глобальной обработки исключений)
    #    _prepare_environment — предварительный шаг внутри init(); при ручном процессе его тоже нужно вызвать сначала,
    #    иначе Loader не сможет прочитать конфигурацию и ошибочно сочтёт все адаптеры/модули отключёнными.
    if not await sdk._prepare_environment():
        print("Не удалось подготовить окружение")
        return False

    # 1. Создание загрузчиков (каждый внутри держит свой Finder)
    adapter_loader = AdapterLoader()
    module_loader = ModuleLoader()

    # 2. Параллельное обнаружение и загрузка (как внутри init(), используется gather)
    (adapter_objs, enabled_adapters, disabled_adapters), \
    (module_objs, enabled_modules, disabled_modules) = await asyncio.gather(
        adapter_loader.load(sdk.adapter),
        module_loader.load(sdk.module),
    )

    # 3. Регистрация адаптеров
    await adapter_loader.register_to_manager(
        enabled_adapters, adapter_objs, sdk.adapter
    )

    # 4. Запуск адаптеров
    if enabled_adapters:
        await sdk.adapter.startup()

    # 5. Регистрация модулей
    await module_loader.register_to_manager(
        enabled_modules, module_objs, sdk.module
    )

    # 6. Инициализация модулей (создание экземпляров + монтирование в sdk)
    if enabled_modules:
        await module_loader.initialize_modules(
            enabled_modules, module_objs, sdk.module, sdk
        )

    # 7. Запуск сервера маршрутов
    await sdk.router.start(host="0.0.0.0", port=8000)

    print("Ручной запуск завершён")
    return True

async def main():
    ok = await manual_startup()
    if ok:
        # Блокировка для поддержания работы (ручной процесс не блокируется автоматически)
        await asyncio.Event().wait()

if __name__ == "__main__":
    asyncio.run(main())
```

### Когда нужен ручной запуск?

В подавляющем большинстве случаев ручной запуск **не нужен** — `await sdk.run()` уже делает всё вышеперечисленное. Ручной запуск имеет смысл только в следующих сценариях:

- **Частичная загрузка**: загрузить только указанные адаптеры/модули, пропустив остальные
- **Динамическая регистрация**: регистрация новых адаптеров/модулей во время выполнения по условию
- **Собственный порядок**: если нужно изменить порядок загрузки по умолчанию (например, сначала запустить модуль, потом адаптеры)
- **Внедрение стратегий**: передать Loader собственный менеджер строгого режима, стратегии загрузки и т.д.
- **Отладка/диагностика**: если какой-то этап падает, вручную управлять процессом для локализации проблемы

## Детализированное управление во время выполнения

Даже если запуск выполнен через `sdk.run()`, вы всё равно можете управлять отдельными подсистемами во время выполнения, не перезапуская весь SDK:

### Горячий запуск и остановка адаптеров

```python
# Горячий перезапуск адаптера (починить соединение, не затрагивая другие платформы)
await sdk.adapter.shutdown("yunhu")
await sdk.adapter.startup("yunhu")

# Поднять новую платформу на ходу
await sdk.adapter.startup("telegram")

# Временно отключить платформу
await sdk.adapter.shutdown("telegram")
```

> `adapter.startup()` требует, чтобы адаптер был **уже зарегистрирован** в менеджере. Регистрация происходит внутри `init()`/`run()`, поэтому это детализированное управление **после** запуска.

### Сервер маршрутов

```python
# Временно остановить webhook-сервер
await sdk.router.stop()

# Перезапуск (например, на другом порту)
await sdk.router.start(host="0.0.0.0", port=9000)
```

### Загрузка модулей по требованию

```python
# Ручная загрузка (возможно, ленивого) модуля
await sdk.load_module("MyModule")
```

## Корректное завершение работы

Начиная с 2.7.0, `sdk.shutdown()` предоставляет **программное корректное завершение**: устанавливается событие завершения, благодаря чему главный цикл, ожидающий в `await sdk.run(keep_running=True)`, возвращается, что в свою очередь запускает `uninit()` для очистки ресурсов.

```python
# Вызов из любой сопрограммы запускает корректный выход (run() возвращается из ожидания и автоматически делает uninit)
sdk.shutdown()
```

Типичный сценарий использования:

```python
async def shutdown_after_idle():
    await asyncio.sleep(3600)
    sdk.shutdown()  # корректный выход после 1 часа простоя
```

**Обработка сигналов**: внутри `run()` регистрируются обработчики `SIGTERM` / `SIGHUP`, превращающие системные сигналы в корректное завершение — при остановке оркестратором контейнеров (Docker `docker stop`) или через `systemd` процесс завершит очистку `uninit()`, а не будет убит принудительно.

- Windows не поддерживает `loop.add_signal_handler`, поэтому обработчики сигналов автоматически пропускаются (закрытие по-прежнему можно вызвать через `sdk.shutdown()` или Ctrl+C)
- Повторные вызовы `sdk.shutdown()` безопасны (если событие уже установлено, повторный вызов — no-op)

## Процесс выгрузки

Обратная запуску операция — `await sdk.uninit()`; она выполняет очистку в обратном порядке:

1. Закрывает все адаптеры (`adapter.shutdown()`)
2. Выгружает все модули
3. Очищает все обработчики событий
4. Очищает менеджеры и атрибуты модулей на объекте SDK

В сценарии ручного запуска не забудьте вызвать `uninit()` перед выходом, чтобы гарантировать корректное завершение:

```python
try:
    await asyncio.Event().wait()   # поддержание работы
finally:
    await sdk.uninit()
```

## Перезапуск

SDK предоставляет два способа перезапуска; ни в одном из них не нужно предварительно выгружать самому — фреймворк сделает это сам:

| Способ | Вызов | Поведение | Сценарий применения |
|------|------|------|----------|
| Горячий перезапуск | `await sdk.restart()` | **Горячая перезагрузка кода на уровне компонентов в рамках одного процесса**: все модули проходят единую линию перезагрузки (общая предварительная проверка синтаксиса / откат по снапшоту / сверка идентичности); адаптеры сначала **заново обнаруживают entry-points** (установленные/удалённые на ходу адаптеры вступают в силу мгновенно), а затем перезагружаются по одному на уровне кода | чтобы код вступил в силу после pip-обновления или установки компонентов, горячее обновление модулей |
| Жёсткий перезапуск | `await sdk.hard_restart()` | После `uninit()` процесс завершается с **кодом выхода 42**, внешний супервизор поднимает совершенно новый процесс | обновление самого фреймворка (обновлённый код фреймворка действует только в новом процессе), побочные эффекты C-расширений, подозрение на утечку ресурсов |

```python
# Горячий перезапуск: горячая перезагрузка кода на уровне компонентов (самый частый случай; недавно установленные через pip адаптеры тоже будут подняты)
await sdk.restart()

# Жёсткий перезапуск: выход из процесса, перезапуск выполняет внешний супервизор (см. «Руководство по супервизорам» ниже)
await sdk.hard_restart("sdk self-update")  # необязательный reason для показа супервизором
```

> **Два замечания**:
> 1. Оба метода выполняют перезапуск фоновым заданием, **немедленно возвращая `True`, что означает «задача перезапуска запланирована»**, а не «перезапуск завершён». Фактический перезапуск происходит в фоне, чтобы не прерывать текущую цепочку событий.
> 2. Принцип работы `hard_restart()`: после выгрузки и записи конфигурации на диск процесс завершается с **кодом выхода 42** (`HARD_RESTART_EXIT_CODE`) — **сам он новый процесс не поднимает**; внешний супервизор должен обнаружить код выхода 42 и запустить процесс заново. Если запускать напрямую `python main.py` без какого-либо супервизора, процесс завершится с кодом 42 и на этом закончится, **автоматического перезапуска не будет** (фреймворк выведет предупреждение).

> **Взаимоисключение и слияние горячих перезапусков** (начиная с 2.11.1): все операции горячей перезагрузки (перезагрузка одиночного модуля / полная перезагрузка / перезагрузка адаптера / гибернация / горячая загрузка нового плагина) полностью взаимоисключающие — при «шторме сохранений» последовательные срабатывания не пересекаются конкурентно; выполняющийся restart при получении нового запроса автоматически сливает их (запрос, пришедший во время удержания блокировки обычной перезагрузки, также сливается и ставится в очередь), после завершения выполняется не более одного дополнительного прогона. При сохранении файла с синтаксической ошибкой весь цикл перезагрузки отклоняется **агрегированной предварительной проверкой синтаксиса** ещё до выгрузки (все ошибочные файлы и номера строк перечисляются за один раз), уровень адаптеров пропускает этот цикл перезагрузки, `restart` фиксирует неудачу, а все старые экземпляры продолжают обслуживать; после исправления достаточно снова выполнить `restart`.

### Когда использовать жёсткий перезапуск?

Горячий перезапуск уже покрывает подавляющее большинство сценариев (pip-обновление/установка компонентов, горячее обновление кода модулей, **включая адаптеры, установленные во время работы**). Жёсткий перезапуск нужен только в следующих случаях:

- **Обновление самого фреймворка**: после обновления ErisPulse новый код фреймворка вступает в силу только в совершенно новом процессе (Python не переимпортирует уже загруженный код фреймворка).
- **Побочные эффекты бинарных библиотек (C-расширений)**: горячий перезапуск происходит в том же процессе и не может освободить процессные ресурсы вроде C-расширений, открытых файловых дескрипторов, потоков; жёсткий перезапуск меняет процесс на совершенно новый, и эти побочные эффекты полностью обнуляются.
- **Поиск утечек ресурсов**: при подозрении на утечку памяти или дескрипторов жёсткий перезапуск даёт чистое окружение.

> Функция «Перезапуск фреймворка» на панели управления Dashboard в своей основе вызывает именно `hard_restart()`.

### Контракт кода выхода 42

Жёсткий перезапуск — это межпроцессное взаимодействие: **SDK отвечает за выход (код 42), супервизор — за поднятие**.

| Роль | Поведение |
|------|------|
| SDK (при жёстком перезапуске) | `uninit()` → запись конфигурации на диск → запись маркера жёсткого перезапуска (причина / PID, для показа супервизором) → `os._exit(42)` |
| Супервизор | Обнаруживает у дочернего процесса код выхода 42 → показывает причину жёсткого перезапуска → заново запускает ту же команду |

> `sdk.is_supervised()` позволяет узнать, запущен ли текущий процесс супервизором (проверяет переменную окружения `ERISPULSE_SUPERVISED`). Команда CLI `run` автоматически внедряет этот маркер при запуске дочернего процесса; внешние супервизоры вроде systemd / Docker его не внедряют, `is_supervised()` возвращает `False`, и после жёсткого перезапуска фреймворк выведет предупреждение «супервизор не обнаружен».

### Руководство по супервизорам

Выберите подходящий вам супервизор, чтобы жёсткий перезапуск действительно работал:

#### 1. Команда CLI run (разработка/простое развёртывание, рекомендуется)

`epsdk run main.py` имеет встроенный цикл супервизии: обнаруживает код выхода дочернего процесса, при 42 немедленно перезапускает (и показывает причину жёсткого перезапуска); другие аварийные коды выхода автоматически повторяет с экспоненциальной задержкой; `Ctrl+C` сначала корректно завершает дочерний процесс (код 0 считается нормальным выходом, повторно не поднимается).

```bash
epsdk run main.py
```

`epsdk run --reload` (режим горячей перезагрузки для разработки, начиная с 2.11.1) также использует структуру «процесс-супервизор + дочерний worker для перезагрузки»: сохранение `.py`-файла внутри worker запускает **горячую перезагрузку уровня компонентов** (без перезапуска всего фреймворка); жёсткий перезапуск выполняется процессом-супервизором, который заново поднимает совершенно новый worker — после обновления фреймворка новый код вступает в силу немедленно.

#### Детализированное определение единицы перезагрузки (2.12+)

После сохранения `.py` минимальная единица перезагрузки выбирается по принадлежности исходного кода во время выполнения, а не угадывается по строке пути:

| Изменённый файл | Обработка |
|----------|------|
| Внутри каталога плагинов (`ErisPulse.framework.plugins_dir`) | Обрабатывается hot-reload watcher'ом плагинов, dev-watcher повторно не срабатывает |
| Исходный код загруженного модуля (включая `pip install -e` и site-packages) | `sdk.reload_module(имя_модуля)` |
| Исходный код зарегистрированного адаптера | `sdk.reload_adapter(имя_платформы)` |
| Входной скрипт | Перезапуск уровня процесса (код выхода 42, повторно поднимается супервизором) |
| Исходный код самого фреймворка (внутри пакета `ErisPulse`) | Перезапуск уровня процесса |
| Одновременное совпадение с несколькими owner / невозможно отнести | Консервативно — перезапуск уровня процесса |

Скриптовый режим (`epsdk run main.py --reload`) не превращает скрипт в worker:
dev-watcher монтируется внутри дочернего процесса скрипта, а `component_reload_pid`
записывается в `.erispulse/runtime.json`; когда родительский процесс видит этот маркер,
изменения модулей/адаптеров/плагинов передаются дочернему процессу, и только
изменение входного скрипта или исходного кода фреймворка перезапускает процесс скрипта.

#### 2. systemd (Linux-серверы)

`RestartForceExitStatus=42` заставляет код выхода 42 тоже триггерить перезапуск (по умолчанию `on-failure` срабатывает только для ненулевых кодов):

```ini
[Service]
ExecStart=/usr/bin/python3 /opt/mybot/main.py
Restart=on-failure
RestartForceExitStatus=42
RestartSec=2
User=mybot
```

#### 3. Docker / docker-compose

Внутри контейнера PID 1 — это процесс приложения; после кода выхода 42 контейнер завершается — используйте стратегию `restart`, чтобы он автоматически перезапускался:

```yaml
services:
  bot:
    build: .
    restart: unless-stopped   # перезапуск при любом завершении (включая 42)
```

#### 4. PM2 (эксплуатация в экосистеме Node)

```bash
pm2 start main.py --name mybot --interpreter python3
# 42 рассматривается как код выхода, PM2 перезапускает по умолчанию; задайте restart_delay для антидребезга
pm2 set mybot.restart_delay 2000
```

#### 5. supervisord

```ini
[program:mybot]
command=python3 /opt/mybot/main.py
autorestart=true
exitcodes=0,2,42    # 42 также считается «нормальным завершением, требующим перезапуска»
```

#### 6. Собственный супервизор на чистом Python

```python
import subprocess, sys, time

while True:
    p = subprocess.Popen([sys.executable, "main.py"])
    code = p.wait()
    if code == 42:          # запрос жёсткого перезапуска
        time.sleep(0.5)
        continue
    if code == 0:           # нормальный выход
        break
    time.sleep(3)           # аварийный выход, повтор с задержкой
```

> **Поведение без супервизора**: при прямом запуске `python main.py` после вызова `hard_restart()` процесс завершится с кодом 42 и не перезапустится. В этом случае следует подключить любой из перечисленных выше супервизоров.
