# Процесс запуска и ручное управление

> [!TIP]
> **Когда стоит читать этот документ**: если вам нужно вручную управлять цепочкой запуска, настраивать порядок запуска или разбираться со сбоями при запуске. Если нет — пропустите, на использование остальных функций это не влияет.


`await sdk.run()` / `await sdk.init()` в ErisPulse упаковывают всю цепочку запуска в «одну строку кода». Но когда требуется полностью кастомизировать процесс запуска (например, частичная загрузка, динамическая регистрация, горячее подключение, внедрение собственной стратегии загрузки), нужно понимать, что именно происходит внутри этой цепочки и как вручную управлять каждым шагом.

В этой статье цепочка запуска разбита на отдельные этапы, описаны их назначение и порядок вызова, а также приведён пример полного ручного запуска.

> Предполагается, что вы уже прошли [Первого бота](../getting-started/first-bot.md) и знакомы с двумя режимами `sdk.run(keep_running=True/False)`. Статья сосредоточена на разборе цепочки **внутри** `init()`, а также на более низкоуровневых точках входа — `init()`/`init_task()`/`init_sync()`.

## Обзор точек входа верхнего уровня SDK

Помимо двух режимов `keep_running` у `run()`, SDK предоставляет несколько более низкоуровневых точек входа для инициализации, различающихся **асинхронностью, возвращаемым значением и обработкой исключений**:

| Точка входа | Асинхронность | Возвращаемое значение | Обработка исключений | Сценарии применения |
|------|--------|--------|----------|----------|
| `await sdk.run(True)` | async, блокирует и поддерживает работу | `None` (при завершении автоматически вызывает `uninit`) | Ошибки модулей/адаптеров перехватываются и не роняют процесс | Чисто бот-приложения |
| `await sdk.run(False)` | async, не блокирует | `None` (без автоматической выгрузки) | То же | Выполнение собственной логики после инициализации |
| `await sdk.init()` | async, требует await | `bool` | Перехватывает исключения компонентов внутри, при неудаче возвращает `False` | Ручное управление жизненным циклом (в паре с `uninit()`) |
| `sdk.init_task()` | async, возвращает Task, не блокирует | `asyncio.Task` | Как у `init()` | Параллельное выполнение другой инициализации либо когда цикл событий ещё не запущен |
| `sdk.init_sync()` | **синхронный**, блокирует текущий поток | `bool` | Как у `init()` | Скрипты командной строки, синхронные точки входа без цикла событий |

> **Типичное заблуждение**: `await sdk.init()` **не эквивалентен** `await sdk.run(keep_running=False)`. Два отличия: ① `init()` возвращает `bool` (при неудаче — `False`), `run()` возвращает `None`; ② `init()` только выполняет инициализацию и **не выгружает автоматически**, тогда как `run()` автоматически вызывает `uninit()` при завершении цикла событий. Поэтому для ручного парного управления выгрузкой или кастомного жизненного цикла используйте `init()` + `uninit()`.

## Обзор цепочки запуска

`sdk.init()` (точнее — его внутренний `Initializer.init()`) поднимает весь фреймворк в следующем порядке:

```mermaid
flowchart TD
    A[0. Подготовка окружения<br/>загрузка конфигурации / обработка исключений] --> B
    B[1. Параллельное обнаружение и загрузка<br/>AdapterLoader.load / ModuleLoader.load<br/>внутри вызывается Finder.find_all] --> C
    C[2. Регистрация адаптеров<br/>AdapterLoader.register_to_manager] --> D
    D[3. Запуск адаптеров<br/>adapter.startup] --> E
    E[4. Регистрация модулей<br/>ModuleLoader.register_to_manager] --> F
    F[5. Инициализация модулей<br/>ModuleLoader.initialize_modules<br/>инстанцирование и монтирование в sdk] --> G
    G[6. Запуск сервера маршрутизации<br/>router.start]
```

Соответствующие ключевые компоненты:

| Слой | Компонент | Назначение |
|----|------|------|
| Обнаружение | `AdapterFinder` / `ModuleFinder` | **Обнаружение** адаптеров/модулей среди entry-points установленных пакетов |
| Загрузка | `AdapterLoader` / `ModuleLoader` | Обнаружение + импорт + чтение метаданных + определение включён/выключен, возвращает список объектов |
| Регистрация | `*Loader.register_to_manager` | Регистрация объектов в соответствующих менеджерах |
| Управление | `sdk.adapter` / `sdk.module` | Обслуживание экземпляров адаптеров/модулей, предоставление интерфейсов запуска/остановки |
| Инициализация | `ModuleLoader.initialize_modules` | Создание экземпляров модулей и их монтирование в `sdk` (с топологической сортировкой зависимостей) |
| Маршрутизация | `sdk.router` | HTTP / WebSocket сервер |

> **Важно**: `Finder` и `Loader` — это два уровня. Внутри `Loader` **уже содержится** `Finder` (`AdapterLoader` имеет встроенный `AdapterFinder`, `ModuleLoader` — `ModuleFinder`). В подавляющем большинстве случаев достаточно использовать `Loader`; отдельно `Finder` нужен только когда требуется «только перечислить, не импортируя».

## Подробный разбор каждого этапа

### 1. Уровень обнаружения: Finder

Finder отвечает только за «поиск пакетов, предоставляющих адаптеры/модули», без импорта и без инстанцирования.

```python
from ErisPulse.finders import AdapterFinder, ModuleFinder

adapter_finder = AdapterFinder()
module_finder = ModuleFinder()

# Поиск всех установленных entry-points адаптеров/модулей
adapter_entries = adapter_finder.find_all()    # list[EntryPoint]
module_entries = module_finder.find_all()      # list[EntryPoint]

# Поиск одного по имени
entry = module_finder.find_by_name("MyModule")  # EntryPoint | None
```

У каждого `EntryPoint` можно вызвать `.load()` для получения соответствующего класса, но обычно делать это вручную не нужно — это делает Loader.

### 2. Уровень загрузки: Loader

Loader поверх Finder выполняет «импорт + чтение метаданных + определение включён/выключен».

```python
from ErisPulse.loaders import AdapterLoader, ModuleLoader
from ErisPulse import sdk

adapter_loader = AdapterLoader()
module_loader = ModuleLoader()

# Внутри load(): вызов finder.find_all() → поочерёдная обработка entry-point → возврат триады
adapter_objs, enabled_adapters, disabled_adapters = await adapter_loader.load(sdk.adapter)
module_objs, enabled_modules, disabled_modules = await module_loader.load(sdk.module)
```

Триада, возвращаемая `load()`:

| Возвращаемое значение | Значение |
|--------|------|
| `objs` (`dict`) | имя → объект (класс адаптера / объект-обёртка модуля) |
| `enabled` (`list[str]`) | включённые имена (не отключённые в конфигурации) |
| `disabled` (`list[str]`) | отключённые имена |

#### Диагностическая информация при сбое загрузки

Когда какой-либо модуль/адаптер выбрасывает исключение на этапе загрузки или инициализации, фреймворк пропускает этот компонент и продолжает загрузку остальных, при этом выводя **сводку кадров пользовательского кода**, что позволяет локализовать место ошибки уже на уровне INFO по умолчанию, без необходимости вручную включать DEBUG:

```
[ERROR] [ModuleLoader] Не удалось загрузить модуль MyModule из entry-point, пропущен: 'NoneType' object has no attribute 'platform'
  → MyModule/Core.py:42 in on_load
      adapter = sdk.platform
  → AttributeError: 'NoneType' object has no attribute 'platform'
  → Подсказка: повысьте уровень логирования до DEBUG, чтобы увидеть полный стек; проверьте реализацию модуля MyModule
```

Диагностическая информация генерируется модулем `ErisPulse.runtime.diagnostics`, который автоматически отфильтровывает внутренние кадры фреймворка, оставляя только кадры вашего кода. Для повторного использования в собственной логике загрузки:

```python
from ErisPulse.runtime import log_diagnostic

try:
    risky_init()
except Exception as e:
    log_diagnostic(e)  # автоматически извлекает кадры пользовательского кода и пишет в лог ERROR
```

Модуль также предоставляет два низкоуровневых метода: `extract_user_frame()` (возвращает структурированную информацию о кадре) и `format_diagnostic_block()` (возвращает многострочный текст).

### 3. Уровень регистрации: register_to_manager

Регистрирует объекты, созданные Loader, в менеджерах, чтобы `sdk.adapter` / `sdk.module` могли их распознавать.

```python
# Регистрация адаптеров (возвращает bool — признак полного успеха)
await adapter_loader.register_to_manager(enabled_adapters, adapter_objs, sdk.adapter)

# Регистрация модулей
await module_loader.register_to_manager(enabled_modules, module_objs, sdk.module)
```

После регистрации адаптеры занесены в менеджер адаптеров, модули — в менеджер модулей, но **все они ещё не запущены/не инстанцированы**.

### 4. Запуск адаптеров

```python
# Запуск всех зарегистрированных адаптеров
await sdk.adapter.startup()
# Или указать платформы
await sdk.adapter.startup("yunhu")
await sdk.adapter.startup(["yunhu", "telegram"])
```

> Регистрация ≠ запуск. `register_to_manager` лишь регистрирует; только `startup` вызывает `start()` адаптера, устанавливая соединение с платформой.

### 5. Инициализация модулей

У модулей на один шаг больше, чем у адаптеров — требуется **инстанцирование** и монтирование в `sdk` (чтобы можно было вызывать `sdk.MyModule.xxx`). На этом шаге также обрабатываются декларации зависимостей между модулями и топологическая сортировка.

```python
success = await module_loader.initialize_modules(
    enabled_modules, module_objs, sdk.module, sdk
)
```

После успешного инстанцирования модули становятся доступны через `sdk.<ModuleName>`.

### 6. Запуск сервера маршрутизации

```python
await sdk.router.start(
    host="0.0.0.0",
    port=8000,
    ssl_certfile=None,
    ssl_keyfile=None,
)
```

Сервер маршрутизации отвечает за приём Webhook / WebSocket колбэков адаптеров. Без него адаптеры в режиме server не смогут получать сообщения.

## Пример полного ручного запуска

Следующий код **эквивалентен** основному процессу `await sdk.init()`, но каждый шаг находится в ваших руках — на любом этапе можно вставить собственную логику:

```python
import asyncio
from ErisPulse import sdk
from ErisPulse.loaders import AdapterLoader, ModuleLoader

async def manual_startup():
    # 0. Подготовка окружения (загрузка конфигурации, регистрация глобальной обработки исключений)
    #    _prepare_environment — предшествующий шаг внутри init(); в ручном процессе его тоже
    #    нужно вызвать первым, иначе Loader не сможет прочитать конфигурацию и ошибочно
    #    сочтёт все адаптеры/модули отключёнными.
    if not await sdk._prepare_environment():
        print("Не удалось подготовить окружение")
        return False

    # 1. Создание загрузчиков (каждый внутри содержит свой Finder)
    adapter_loader = AdapterLoader()
    module_loader = ModuleLoader()

    # 2. Параллельное обнаружение и загрузка (как внутри init() — через gather)
    (adapter_objs, enabled_adapters, disabled_adapters), \
    (module_objs, enabled_modules, disabled_modules) = await asyncio.gather(
        adapter_loader.load(sdk.adapter),
        module_loader.load(sdk.module),
    )

    # 3. Регистрация адаптеров
    await adapter_loader.register_to_manager(
        enabled_adapters, adapter_objs, sdk.adapter
    )

    # 4. Запуск адаптеров
    if enabled_adapters:
        await sdk.adapter.startup()

    # 5. Регистрация модулей
    await module_loader.register_to_manager(
        enabled_modules, module_objs, sdk.module
    )

    # 6. Инициализация модулей (инстанцирование + монтирование в sdk)
    if enabled_modules:
        await module_loader.initialize_modules(
            enabled_modules, module_objs, sdk.module, sdk
        )

    # 7. Запуск сервера маршрутизации
    await sdk.router.start(host="0.0.0.0", port=8000)

    print("Ручной запуск завершён")
    return True

async def main():
    ok = await manual_startup()
    if ok:
        # Блокируем и поддерживаем работу (ручной процесс не блокирует автоматически)
        await asyncio.Event().wait()

if __name__ == "__main__":
    asyncio.run(main())
```

### Когда следует запускать вручную?

В подавляющем большинстве случаев ручной запуск **не нужен** — `await sdk.run()` уже выполняет всё вышеперечисленное. Ручной запуск ценен только в следующих сценариях:

- **Частичная загрузка**: загрузить только указанные адаптеры/модули, пропустив остальные
- **Динамическая регистрация**: регистрация новых адаптеров/модулей во время выполнения по условиям
- **Кастомный порядок**: необходимость изменить порядок загрузки по умолчанию (например, сначала запустить модуль, потом адаптер)
- **Внедрение стратегий**: передать Loader собственный менеджер строгого режима, стратегии загрузки и т.п.
- **Отладка/диагностика**: при сбое на каком-то этапе вручную проуправлять шагами, чтобы локализовать проблему

## Тонкое управление во время выполнения

### Горячая перезагрузка локальных плагинов

`sdk.enable_plugin_hot_reload()` отслеживает изменения исходного кода в каталоге локальных плагинов (`plugins/`) и перезагружает их автоматически.
В `epsdk run` это включено автоматически, вызывать вручную не требуется; при запуске **«голым» `sdk.run()`**, если нужна горячая перезагрузка плагинов,
вызовите метод один раз перед `run()` (действует только на каталог локальных плагинов и не затрагивает установленные через pip модули/адаптеры):

```python
sdk.enable_plugin_hot_reload()
sdk.run()
```


Даже если запуск выполнен через `sdk.run()`, вы всё равно можете отдельно управлять подсистемами во время выполнения, не перезапуская весь SDK:

### Горячий запуск и остановка адаптеров

```python
# Горячий перезапуск адаптера (восстановление соединения, другие платформы не затрагиваются)
await sdk.adapter.shutdown("yunhu")
await sdk.adapter.startup("yunhu")

# Подъём новой платформы во время работы
await sdk.adapter.startup("telegram")

# Временное отключение платформы
await sdk.adapter.shutdown("telegram")
```

> `adapter.startup()` требует, чтобы адаптер был **уже зарегистрирован** в менеджере. Регистрация происходит внутри `init()`/`run()`, поэтому это тонкое управление **после** запуска.

### Сервер маршрутизации

```python
# Временное отключение webhook-сервера
await sdk.router.stop()

# Перезапуск (например, на другом порту)
await sdk.router.start(host="0.0.0.0", port=9000)
```

### Загрузка модулей по требованию

```python
# Ручная загрузка (возможно, лениво загружаемого) модуля
await sdk.load_module("MyModule")
```

## Корректное завершение работы

Начиная с 2.7.0, `sdk.shutdown()` предоставляет **программное корректное завершение**: устанавливается событие завершения, благодаря чему главный цикл, приостановленный в `await sdk.run(keep_running=True)`, возвращается и тем самым запускает `uninit()` для очистки ресурсов.

```python
# Вызов из любой корутины запускает корректный выход (приостановленный run() возвращается и автоматически вызывает uninit)
sdk.shutdown()
```

Типичное применение:

```python
async def shutdown_after_idle():
    await asyncio.sleep(3600)
    sdk.shutdown()  # корректный выход после 1 часа простоя
```

**Обработка сигналов**: внутри `run()` регистрируются обработчики `SIGTERM` / `SIGHUP`, превращающие системные сигналы в корректное завершение — при остановке сервиса оркестратором контейнеров (Docker `docker stop`) или `systemd` процесс успевает выполнить очистку `uninit()`, а не уничтожается принудительно. Также регистрируется обработчик `SIGUSR1`, превращающий сигнал во внутрипроцессный мягкий перезапуск (`sdk.restart()`) — `epsdk restart` для экземпляров с PID 1 внутри контейнера (завершение означает выход контейнера, внешний перезапуск невозможен) вместо завершения посылает этот сигнал, запуская горячую перезагрузку компонентов. Канал горячей перезагрузки по SIGUSR1 требует ErisPulse **2.12+**.

- Windows не поддерживает `loop.add_signal_handler`, обработчики сигналов автоматически пропускаются (для завершения по-прежнему можно использовать `sdk.shutdown()` или Ctrl+C)
- Повторные вызовы `sdk.shutdown()` безопасны (после установки события повторный вызов — no-op)

## Процесс выгрузки

Обратной к запуску операцией является `await sdk.uninit()`, которая выполняет очистку в обратном порядке:

1. Остановка всех адаптеров (`adapter.shutdown()`)
2. Выгрузка всех модулей
3. Очистка всех обработчиков событий
4. Очистка менеджеров и атрибутов модулей на SDK

При ручном запуске не забудьте вызвать `uninit()` перед выходом, чтобы обеспечить корректное завершение:

```python
try:
    await asyncio.Event().wait()   # Поддержание работы
finally:
    await sdk.uninit()
```

## Перезапуск

SDK предоставляет два способа перезапуска, и ни один из них не требует предварительной выгрузки вручную — фреймворк сделает это сам:

| Способ | Вызов | Поведение | Сценарии применения |
|------|------|------|----------|
| Горячий перезапуск | `await sdk.restart()` | **Горячая перезагрузка на уровне кода компонентов в том же процессе**: все модули проходят единый конвейер перезагрузки (общая предпроверка синтаксиса / откат по снапшоту / сверка идентичности); адаптеры сначала **заново обнаруживают entry-points** (установленные/удалённые во время работы адаптеры вступают в силу немедленно), затем перезагружаются по одному на уровне кода | Вступление кода в силу после pip-обновления или установки компонентов, горячее обновление модулей |
| Жёсткий перезапуск | `await sdk.hard_restart()` | После `uninit()` процесс завершается с **кодом выхода 42**, а новый процесс поднимает внешний супервизор | Обновление самого фреймворка (обновлённый код фреймворка действует только в новом процессе), побочные эффекты C-расширений, подозрение на утечку ресурсов |

```python
# Горячий перезапуск: горячая перезагрузка на уровне кода компонентов (самый частый случай; поднимаются и адаптеры, только что установленные через pip)
await sdk.restart()

# Жёсткий перезапуск: выход из процесса, перезапуск внешним супервизором (см. «Руководство по супервизорам» ниже)
await sdk.hard_restart("sdk self-update")  # необязательная reason для отображения супервизором
```

> **Два замечания**:
> 1. Оба метода выполняют перезапуск через фоновую задачу и **сразу возвращают `True`, означающее «задача перезапуска запланирована»**, а не «перезапуск завершён». Фактический перезапуск идёт в фоне, чтобы не прерывать текущую цепочку событий.
> 2. Принцип `hard_restart()`: после выгрузки и записи конфигурации на диск процесс завершается с **кодом выхода 42** (`HARD_RESTART_EXIT_CODE`) — **сам он новый процесс не поднимает**, это обязан сделать внешний супервизор, обнаружив код выхода 42. Если запускать напрямую `python main.py` без какого-либо супервизора, процесс просто завершится с кодом 42 и **не перезапустится автоматически** (фреймворк выдаст предупреждение).

> **Взаимное исключение и объединение горячих перезапусков** (начиная с 2.11.1): все операции горячего перезагруза (перезагрузка одного модуля / полная перезагрузка / перезагрузка адаптера / гибернация / горячая установка новых плагинов) полностью взаимоисключающи — при «шторме сохранений» подряд идущие срабатывания не пересекаются параллельно; выполняющийся restart при получении нового запроса автоматически объединяет его (запрос, пришедший во время удержания блокировки обычной перезагрузки, также объединяется в очередь), после завершения выполняется не более одного дополнительного прохода. При сохранении файла с синтаксической ошибкой весь цикл перезагрузки отклоняется до выгрузки **сводной предпроверкой синтаксиса** (за один раз перечисляются все ошибочные файлы и номера строк): слой адаптеров пропускает этот цикл перезагрузки, `restart` фиксирует неудачу, все старые экземпляры продолжают работу; после исправления достаточно выполнить `restart` повторно.

### Когда нужен жёсткий перезапуск?

Горячий перезапуск покрывает подавляющее большинство сценариев (pip-обновление/установка компонентов, горячее обновление кода модулей, **включая адаптеры, установленные во время работы**). Жёсткий перезапуск нужен лишь в следующих случаях:

- **Обновление самого фреймворка**: после обновления ErisPulse новый код фреймворка вступает в силу только в совершенно новом процессе (Python не выполняет повторный import уже загруженного кода фреймворка).
- **Побочные эффекты бинарных библиотек (C-расширений)**: горячий перезапуск идёт в рамках того же процесса и не может освободить C-расширения, открытые файловые дескрипторы, потоки и другие ресурсы уровня процесса; жёсткий перезапуск поднимает новый процесс, и эти эффекты полностью обнуляются.
- **Поиск утечек ресурсов**: при подозрении на утечку памяти или дескрипторов жёсткий перезапуск даёт чистую среду.

> Функция «Перезапуск фреймворка» в панели управления Dashboard в своей основе вызывает именно `hard_restart()`.

### Контракт кода выхода 42

Жёсткий перезапуск — это межпроцессное взаимодействие: **SDK отвечает за выход (код 42), супервизор — за запуск**.

| Роль | Поведение |
|------|------|
| SDK (при жёстком перезапуске) | `uninit()` → запись конфигурации на диск → запись маркера жёсткого перезапуска (причина / PID, для отображения супервизором) → `os._exit(42)` |
| Супервизор | Обнаружив код выхода дочернего процесса 42 → отображает причину жёсткого перезапуска → перезапускает ту же команду |

> `sdk.is_supervised()` позволяет узнать, запущен ли текущий процесс супервизором (проверяется переменная окружения `ERISPULSE_SUPERVISED`). CLI-команда `run` при запуске дочернего процесса автоматически внедряет этот маркер; внешние супервизоры вроде systemd / Docker его не внедряют, `is_supervised()` возвращает `False`, и после жёсткого перезапуска фреймворк выдаст предупреждение «супервизор не обнаружен».

### Руководство по супервизорам

Выберите подходящий супервизор, чтобы жёсткий перезапуск реально работал:

#### 1. CLI-команда run (разработка/простое развёртывание, рекомендуется)

`epsdk run main.py` имеет встроенный цикл супервизии: отслеживает код выхода дочернего процесса, при 42 немедленно перезапускает (и отображает причину жёсткого перезапуска); другие аномальные коды выхода автоматически повторяются с экспоненциальной задержкой; `Ctrl+C` сначала корректно завершает дочерний процесс (код 0 считается нормальным выходом, без повторного запуска).

```bash
epsdk run main.py
```

`epsdk run --reload` (режим разработки с горячей перезагрузкой, с 2.11.1) также использует структуру «процесс-супервизор + дочерний worker-процесс перезагрузки»: сохранение `.py`-файла внутри worker запускает **горячую перезагрузку на уровне компонентов** (без перезапуска всего фреймворка); жёсткий перезапуск выполняется процессом-супервизором через подъём совершенно нового worker — после обновления фреймворка новый код вступает в силу сразу.

#### Тонкое определение перезагрузки (2.12+)

После сохранения `.py` минимальная единица перезагрузки выбирается по принадлежности исходников во время выполнения, а не по эвристике строк пути:

| Изменённый файл | Обработка |
|----------|------|
| Файлы внутри каталога плагинов (`ErisPulse.framework.plugins_dir`) | Обрабатываются watcher'ом горячей перезагрузки плагинов, dev watcher не срабатывает повторно |
| Исходники загруженных модулей (включая `pip install -e` и site-packages) | `sdk.reload_module(имя_модуля)` |
| Исходники зарегистрированных адаптеров | `sdk.reload_adapter(имя_платформы)` |
| Входной скрипт | Перезапуск уровня процесса (код выхода 42, повторный подъём супервизором) |
| Исходники самого фреймворка (внутри пакета `ErisPulse`) | Перезапуск уровня процесса |
| Одновременное совпадение с несколькими owner / принадлежность не определена | Консервативно — перезапуск уровня процесса |

В режиме скрипта (`epsdk run main.py --reload`) скрипт не превращается в worker: внутри дочернего процесса скрипта монтируется
dev watcher, а `component_reload_pid` записывается в `.erispulse/runtime.json`; увидев этот маркер, родительский процесс
передаёт изменения модулей/адаптеров/плагинов дочернему процессу, и лишь изменения входного скрипта или исходников фреймворка
приводят к перезапуску процесса скрипта.

#### 2. systemd (серверы Linux)

`RestartForceExitStatus=42` позволяет коду выхода 42 тоже запускать перезапуск (по умолчанию `on-failure` срабатывает только на ненулевых кодах):

```ini
[Service]
ExecStart=/usr/bin/python3 /opt/mybot/main.py
Restart=on-failure
RestartForceExitStatus=42
RestartSec=2
User=mybot
```

#### 3. Docker / docker-compose

Внутри контейнера PID 1 — это процесс приложения; после кода выхода 42 контейнер завершается — используйте стратегию `restart` для автоматического перезапуска:

```yaml
services:
  bot:
    build: .
    restart: unless-stopped   # перезапуск при любом завершении (включая 42)
```

> Внутри контейнера `epsdk restart` для экземпляров с PID 1 использует внутрипроцессный горячий перезапуск по SIGUSR1 и не завершает контейнер;
> перезапуск всего процесса обеспечивает стратегия `restart`. Подробнее: [Развёртывание → Перезапуск внутри контейнера](../user-guide/deployment.md#перезапуск-внутри-контейнера-экземпляры-pid-1).

#### 4. PM2 (эксплуатация в экосистеме Node)

```bash
pm2 start main.py --name mybot --interpreter python3
# 42 считается кодом выхода, PM2 по умолчанию перезапускает; задайте restart_delay для антидребезга
pm2 set mybot.restart_delay 2000
```

#### 5. supervisord

```ini
[program:mybot]
command=python3 /opt/mybot/main.py
autorestart=true
exitcodes=0,2,42    # 42 тоже считается «нормальным выходом, требующим перезапуска»
```

#### 6. Собственный супервизор на чистом Python

```python
import subprocess, sys, time

while True:
    p = subprocess.Popen([sys.executable, "main.py"])
    code = p.wait()
    if code == 42:          # запрос жёсткого перезапуска
        time.sleep(0.5)
        continue
    if code == 0:           # нормальный выход
        break
    time.sleep(3)           # аномальный выход, повтор с задержкой
```

> **Поведение без супервизора**: при прямом запуске `python main.py` после вызова `hard_restart()` процесс завершится с кодом 42 без перезапуска. В этом случае следует подключить любой из перечисленных выше супервизоров.
