# Теневые модули и постепенный переход

> [!TIP]
> **Когда читать эту статью**: при необходимости постепенного развертывания — одновременная пробная работа новой версии, сравнение поведения и принятие решения о переходе или откате. Если вам это не нужно, можете пропустить эту статью — это не повлияет на использование других функций.

> **Что вы узнаете**: пять уровней изоляции теневых модулей, способ сопоставления поведения (`diff`), процесс одобренного перехода (`promote`) и автоматического отката при сбое, а также границы, которые не могут быть пересечены фреймворком.
>
> **В этой статье не рассматриваются**: общие механизмы горячей перезагрузки и управления принадлежностью модулей (см. [систему владельцев (owner)](ownership.md)).

Теневой модуль = **новая версия** того же модуля, которая параллельно работает с текущей версией под отдельным владельцем (например, `roll_shadow`), получая **копии** реальных событий и **перехватывая** исходящие действия для учета, а не отправляя их наружу. Сравнение поведения двух версий происходит в `shadow_diff`. После подтверждения, что новая версия безопасна, можно выполнить `promote`, чтобы сразу принять её как основную, или `dismiss`, чтобы отказаться от неё в любой момент. **Код модуля не изменяется**, вся работа осуществляется с помощью API во время выполнения: такие же операции, как `load / unload / reload`, можно вызывать через Dashboard или пользовательские модули управления, без необходимости писать какие-либо конфигурационные параметры.

{!--< tips >!--}
1. Запуск: ``await sdk.module.shadow_start("roll", source="путь/к/v2")``
   — новая версия кода работает параллельно со старой под отдельным владельцем (по умолчанию имя владельца берется из пути)
2. Теневой модуль не участвует в реальной маршрутизации и графе зависимостей: команды с одинаковыми именами выполняются в директории теневого модуля, маршрутизация регистрируется, но не привязывается, тихая трансляция жизненного цикла, `module.call` и разрешение зависимостей по-прежнему указывают на v1
3. Принятие решения о переходе всегда осуществляется человеком: ``await sdk.module.promote_shadow("roll")``, при сбое происходит автоматический откат к старой версии; ``dismiss_shadow`` позволяет в любой момент отказаться от теневого модуля
{!--< /tips >!--}

## Быстрый старт

```python
# Код v2: обычный модуль, без теневого режима (любой каталог, например downloads/roll_v2/)
```

```python
# В онлайн-боте (через Dashboard / модуль управления), запуск грейд-теста одной строкой:
await sdk.module.shadow_start("roll", source="downloads/roll_v2")
# → Теневой модуль с отдельным owner "roll_v2" параллельно работает с v1, исходящие сообщения перехватываются и записываются

# Сравнение поведения во время тестирования:
report = sdk.module.shadow_diff("roll")
# {"shadow_owner": "roll_v2", "count": 3, "aligned": [...]}
```

- **v1 фактическая отправка**: из бот-таймлайна в инбоксе (transcript)
- **v2 предполагаемая отправка**: теневой отчёт (запись в исходящем трафике о "что хотели отправить")
- Оба сопоставляются по `trace_id` — для одного и того же сообщения, почему один и другой вариант сработали/не сработали, что хотели отправить/что отправили — всё видно

После проверки без ошибок:

```python
await sdk.module.promote_shadow("roll")   # Промоутить, при ошибке автоматически откатить к v1
await sdk.module.dismiss_shadow("roll")   # Или отменить теневой режим
```

## Пять изолирующих барьеров

| Барьер | Механизм |
|----|------|
| Копия события | Теневой обработчик получает **независимую копию** события (с меткой `shadow`) — изменения / признание / остановка распространения теневого события влияют только на копию, не затрагивая оригинальную цепочку событий |
| Выходная дверь | Все вызовы DSL `Send` и `Api` теневого события перехватываются и регистрируются (возвращается фиктивный ответ), событие не отправляется наружу — теневой обработчик не будет повторно отвечать |
| Слой перекрытия хранилища | Запись KV теневого события происходит в слое перекрытия в памяти и не сохраняется в базу данных; чтение сначала проверяет слой перекрытия, при неудаче — обращается к реальной базе данных (灰度 процесс работает с реальными данными); удаление помечается как "могильный камень" |
| Блокировка маршрутизации | HTTP/WS/SSE маршруты теневого события регистрируются, но не подключаются; команды с тем же именем записываются в каталог теневых команд, методы платформенных событий запрещены к вставке |
| Тихий жизненный цикл | Теневой обработчик не транслирует собственные события жизненного цикла и не участвует в экосистемной зависимости (вызовы `module.call` и разрешение зависимостей по-прежнему указывают на v1, чтобы избежать зависимости от незавершённого продукта) |

Наследование конфигурации: теневой обработчик по умолчанию **наследует конфигурационные разделы оригинального модуля** (иначе серая версия будет отличаться от оригинала), после перевода в основной режим конфигурация применяется на месте.

## Честные границы (не остановить)

- Отправка / API / хранилище KV / единый HTTP-клиент через фреймворк **всё можно остановить**;
  модули, обходящие фреймворк, запускают `aiohttp` напрямую, создают потоки и пишут во внешние системы — фреймворк не может остановить
- **Чтение и запись ORM не входят в область покрытия** (по строкам overlay невозможно реализовать чисто на уровне SQL) —
  в период теневого режима рекомендуется избегать зависимости от ORM для обеспечения изоляции
- **Источник теневого режима — локальный путь**: новая версия кода импортируется по пути, загружается отдельным владельцем; один и тот же пакет PyPI
  в одном и том же интерпретаторе ограничен ключом `sys.modules`, не позволяя одновременно использовать две версии
- Аудитор утечек (`sdk.module.audit`) видит принадлежность теневых ресурсов; побочные эффекты от обхода фреймворка
  по крайней мере не будут бесшумными

## Промотирование и откат

Процесс `promote`: создание снимка текущей версии (включая все зависимые модули) → полное удаление → регистрация теневого экземпляра с настоящим именем → загрузка → при сбое на любом этапе автоматический откат, старый экземпляр продолжает обслуживать запросы (семантика "по возможности": эффекты, вызванные уже выполненным `on_unload`, не могут быть отменены, после отката старый экземпляр находится в состоянии завершения). После успешного промотирования теневые ресурсы утилизируются, и связь снимается; конфигурация оригинального модуля применяется на месте.

**Примечание о сохранении изменений**: промотирование происходит в режиме выполнения — после перезапуска будет продолжать работать версия v2. Необходимо **сохранить новую версию** (установить новую версию с помощью `pip install -U` или заменить файлы плагина). Переключение в режиме выполнения не заменяет пакетный менеджер.

# Транскрипт (Transcript)

> [!TIP]
> **Когда нужно прочитать эту статью**: при необходимости истории сообщений, восстановления диалога или настройки политик хранения транскриптов. Если не требуется, можно пропустить, это не повлияет на использование других функций.

Транскрипт автоматически записывает отправленные и полученные роботом сообщения (организованные по ключу сессии `platform:detail_type:target_id`), обеспечивая исторические данные для восстановления диалога (`event.history`), сравнения изменений в теневых модулях, воспроизведения при холодном запуске и т.д. В настоящем документе описаны **модель хранения, политики хранения и то, что защищает каждый параметр**, а также API перекрытия в процессе выполнения и реальная стоимость снятия ограничений.

> Прочитайте раздел «Риски и аудит» перед изменением ограничений — каждый параметр имеет свою причину существования.

## Работа

```
Сообщение ──append()──▶ Буфер записи (в памяти deque, жёсткий лимит 4096 строк)
                        │  Батчевая запись на диск каждые 1 секунду (не более 64 строк в батче, одна транзакция)
                        ▼
              Таблица transcript в backend storage (по умолчанию sqlite)
                        │  Примерно каждые 32 строки запускается ленивая очистка по сохранению
                        ▼
              ┌─ Обрезка FIFO по сессиям (max_per_session, по умолчанию 50 строк)
              └─ Глобальное удаление по TTL (ttl_hours, по умолчанию 168 = 7 дней)
```

Три уровня защиты, каждый защищает от разных рисков:

| Параметр | Значение по умолчанию | Что защищает | Последствия при отключении (=0) |
|------|--------|----------|------------------|
| Верхний лимит буфера записи | 4096 строк (константа, не настраиваемая) | **Память**: накопление сообщений при недоступности хранилища не переполняет RAM | Нельзя отключить — это защита памяти |
| Обрезка текста одной строки | 2000 символов (константа, не настраиваемая) | Память и использование диска на одну строку | Нельзя отключить |
| `max_per_session` | 50 строк/сессия | **Рост диска**: бесконечное накопление истории в одной сессии | История сессии будет бесконечно расти |
| `ttl_hours` | 168 (7 дней) | **Рост диска**: долгосрочное накопление истории по всем сессиям | Таблица `transcript` будет бесконечно расти |

Важное понимание: **буфер записи имеет жёсткий лимит, поэтому отключение стратегии сохранения не приведёт к переполнению памяти**;
Реальный риск находится на уровне хранения и потребителей данных (см. следующий раздел).

> [!TIP]
> **Приложениям, не нуждающимся в памяти сессий, можно полностью отключить**: `ErisPulse.transcript.enabled = false`
> Это остановит автоматическую запись входящих/исходящих сообщений — не будет записи ни в буфер памяти, ни в хранилище, что экономит постоянную память и постоянные операции ввода-вывода на уровне хранения. Сессионная корзина в основном служит для инъекции контекста для ИИ и предотвращения повторов, и если эти функции не нужны (например, для чисто командных роботов), отключение рекомендуется.

## Конфигурация

```toml
[ErisPulse.transcript]
enabled = true          # Автоматически ли записывать транскрипты
max_per_session = 50    # Количество записей, сохраняемых в одной сессии (0 = отключить обрезку сессии)
ttl_hours = 168.0       # Общая продолжительность хранения (часы, 0 = никогда не удалять)
self_echo = "bot"       # Обработка эха сообщений от бота: bot / skip / user
```

Переменные окружения также действуют: `ERISPULSE_TRANSCRIPT_MAX_PER_SESSION`, `ERISPULSE_TRANSCRIPT_TTL_HOURS`,
`ERISPULSE_TRANSCRIPT_SELF_ECHO`. Изменения конфигурации применяются динамически (с задержкой до ~1 секунды в зависимости от частоты записи в буфер).

> [!TIP]
> **Отключите сессии, если они вам не нужны**: единый получатель транскриптов — это восстановление диалога / сравнение теней / воспроизведение при холодном запуске.
> Если ваш бот (или модуль) не использует эти функции, установите `enabled = false`
> для экономии памяти буфера входящих сообщений и фоновой массовой записи на диск — обработка сообщений и команд не пострадает.

## Атрибуция сообщений (отправитель и meta)

Все интерфейсы запросов (`get` / `recent` / `get_by_trace` / `event.history`) возвращают записи с атрибутивными полями, которые используются для различения "кто отправил / какой модуль отправил":

| Поле | Значение |
|------|------|
| `sender` | Идентификатор отправителя: для входящих сообщений это `user_id`, для исходящих — учетная запись бота / `self.user_id` при эхо-сообщениях |
| `meta` | Метаданные в момент записи (белый список контракта, не полный raw event) |

Белый список `meta`:

- **Входящие**: `nickname` (никнейм в момент события, при последующем запросе получается "текущий никнейм"), `self_id` (учетная запись бота), `sub_type`, `message_id`; для эхо-сообщений дополнительно присутствует `self_echo: true`;
- **Исходящие**: контекст отправки (`platform` / `method` / `detail_type` / `target_id` / `bot_id` / `trace_id` / `preview`) и `module` (модуль отправителя, см. ниже).

В старых записях (до появления поля `meta`) значение `meta` — `{}`; при обращении `meta.get("nickname", "")` происходит естественное понижение уровня; при отсутствии поддержки ALTER в хранилище тихо возвращается `{}`.

### Отправка из модуля (meta.module)

В одном экземпляре могут отправлять сообщения несколько модулей (чат, управление, напоминания). В исходящих записях `meta.module` указывает отправителя, приоритет значений: `current_owner > current_caller > ""`:

| Сценарий отправки | Значение `module` |
|----------|-----------|
| При вызове модульного кода через `module.call` | Имя целевого модуля |
| При отправке из обработчика событий модуля | Имя модуля, зарегистрировавшего обработчик (автоматически вставляется в фазе маршрутизации) |
| Изнутри фреймворка / без модульного контекста | `""` |

В payload хуков `message.sent` / `message.sending` (send_ctx) также присутствует поле `module`.

### Эхо-сообщения бота (self_echo)

Некоторые платформы/протоколы могут отправлять события сообщений, которые были отправлены самим ботом (например, `report-self-message` в OneBot v11, outgoing message в Telegram). Фреймворк идентифицирует эхо-сообщения до записи входящих сообщений по условию `self.user_id == user_id` и обрабатывает их в соответствии с настройкой `self_echo`:

| Значение | Поведение |
|------|------|
| `"bot"` (по умолчанию) | Сохраняется, но `role="bot"`, `sender=self_id`, `meta.self_echo=true` |
| `"skip"` | Не сохраняется (адаптер при этом автоматически запускает `message.sent`, создавая запись исходящего сообщения) |
| `"user"` | Сохраняется как `role="user"` (устаревшее поведение, служит для обратной совместимости) |

На платформах, где эхо-сообщения не отправляются (`self.user_id != user_id` всегда), поведение идентично с отключенной данной функцией.

### Фильтрация по сессии (recent)

```python
from ErisPulse import transcript

# Глобальное окно времени, охватывающее все сессии (по умолчанию, для воспроизведения при запуске)
transcript.recent(3600)

# Ограничение одной сессией: фильтрация на стороне сервера, избегая глобального получения и последующей клиентской фильтрации по session_key
transcript.recent(3600, session_key="onebot11:group:123")
```

Если `session_key=None`, используется глобальное поведение; пустая строка `""` эквивалентна отсутствию фильтрации (для обработки ошибок).

## API для переопределения во время выполнения

Для динамического изменения (например, временного увеличения срока хранения для определённой сессии):

```python
from ErisPulse import transcript

# Переопределение (приоритет над конфигурацией; только в памяти, после перезапуска восстанавливается значение из конфигурации)
transcript.set_retention(max_per_session=500, ttl_hours=24 * 30)

# Получение текущих значений и источника
transcript.get_retention()
# {'max_per_session': 500, 'ttl_hours': 720.0, 'overridden': ['max_per_session', 'ttl_hours']}

# Восстановление значений из конфигурации
transcript.reset_retention()
```

- Передача `0` отключает соответствующую стратегию (в журнале будет записано предупреждение); отрицательные числа вызывают исключение `ValueError`;
- Переопределение вступает в силу при следующей очистке (ленивая, задержка максимум до добавления ~32 записей);
- Единственный экземпляр `transcript` можно импортировать из корневого пакета, а также через `sdk.transcript`.

## Риски и аудит: что нужно знать перед отключением ограничений

После отключения `max_per_session` / `ttl_hours` (или при значительном увеличении их значений) таблица `transcript` будет расти бесконечно вместе с количеством сообщений. Это приведёт к следующим последствиям:

1. **Заполнение диска** — SQLite-файл будет постоянно увеличиваться, и при заполнении диска слой хранения фреймворка станет недоступен;
2. **Ухудшение производительности запросов** — стоимость сканирования в `get()` / `recent()` / `get_by_trace()` будет расти вместе с ростом таблицы;
3. **Давление на память (истинный источник OOM)** — потребители, загружающие историю целиком в память (восстановление диалога с историей, панель с полной выгрузкой, ваш бизнес-код `get(session, n)` с большим n), будут потреблять всё больше памяти, что в экстремальных случаях приведёт к OOM kill.

**Перед отключением задайте себе три вопроса**: как долго вам нужна история? Какого размера? Кто будет её очищать?  
Если ответ зависит от "никогда не удалять", правильным решением обычно является внешняя архивация (периодическая отправка старых данных в специальную базу), а не бесконечное хранение в почтовом ящике.

Средства аудита (регулярная проверка размера таблицы):

```python
# С помощью ORM/SQL-конструктора проверьте количество строк и объём (пример для sqlite)
from ErisPulse import storage

row = storage.Table("transcript").raw_sql("SELECT COUNT(*) AS n FROM transcript")
```

```sql
-- Прямой запрос к файлу sqlite (объём таблицы)
SELECT COUNT(*) FROM transcript;
```

В логах появится предупреждение `стратегия хранения была отключена` — это означает, что кто-то отключил стратегию, установив значение 0. Убедитесь, что это ваше действие.

## Границы с другими механизмами

- **Таймеры интерактивных сеансов / wait_reply**: см. [Система интерактивных сеансов](interaction.md), не связано с ящиком входящих;
- **Восстановление диалога с историей**: `resume(with_history=N)` берёт последние N элементов из ящика входящих — после обрезки ящика количество восстанавливаемой истории уменьшается (увеличение `max_per_session` продлевает окно восстановления);
- **Дифф теневых модулей**: зависит от цепочки запросов `get_by_trace`, слишком короткий TTL ящика входящих сокращает окно для дифф-операций.
