# Стандарт оформления комментариев ErisPulse

При создании основных методов EP необходимо добавлять комментарии к методам в следующем формате:

## Документирующие комментарии уровня модуля

В начале каждого файла модуля должна содержаться документация модуля:
```python
"""
[Название модуля]
[Описание функциональности модуля]

{!--< tips >!--}
Важные инструкции по использованию или примечания
{!--< /tips >!--}
"""
```

## Комментарии методов

### Базовый формат
```python
def func(param1: type1, param2: type2) -> return_type:
    """
    [Описание функциональности]
    
    :param param1: [Тип1] [Описание параметра 1]
    :param param2: [Тип2] [Описание параметра 2]
    :return: [Тип возвращаемого значения] [Описание возвращаемого значения]
    """
    pass
```

### Полный формат (для сложных методов)
```python
def complex_func(param1: type1, param2: type2 = None) -> Tuple[type1, type2]:
    """
    [Подробное описание функциональности]
    [Может содержать несколько строк описания]
    
    :param param1: [Тип1] [Описание параметра 1]
    :param param2: [Тип2] [Описание необязательного параметра 2] (по умолчанию: None)
    
    :return: 
        type1: [Описание возвращаемого параметра 1]
        type2: [Описание возвращаемого параметра 2]
    
    :raises ErrorType: [Описание ошибки]
    """
    pass
```

## Специальные теги (для генерации документации API)

Когда комментарий метода содержит перечисленное ниже, при сборке документации API будет произведён соответствующий эффект:

| Формат тега | Назначение | Пример |
|---------|------|------|
| `{!--< internal-use >!--}` | Помечает как внутреннее использование, документация не генерируется | `{!--< internal-use >!--}` |
| `{!--< ignore >!--}` | Игнорирует этот метод, документация не генерируется | `{!--< ignore >!--}` |
| `{!--< deprecated >!--}` | Помечает метод как устаревший | `{!--< deprecated >!--} Используйте вместо этого new_func()` |
| `{!--< experimental >!--}` | Помечает как экспериментальную функциональность | `{!--< experimental >!--} Может быть нестабильной` |
| `{!--< tips >!--}...{!--< /tips >!--}` | Многострочное содержимое подсказки | `{!--< tips >!--}\nВажное содержимое подсказки\n{!--< /tips >!--}` |
| `{!--< tips >!--}` | Однострочное содержимое подсказки | `{!--< tips >!--} Примечание: этот метод требует предварительной инициализации` |

> **Примечание о границах применения**: в основном тексте документации (Markdown в `docs/`) для обозначения важной информации используются блоки подсказок GitHub (`> [!TIP]` и т. д.); внутри docstring используются теги `{!--< ... >!--}` из этого раздела — **это две независимые системы, смешивать их не следует** (`> [!TIP]` внутри docstring не будет распознан генератором документации API как блок подсказки, а теги `{!--< >!--}` в Markdown-тексте обрабатываться не будут).

## Контракт разбора тегов

Ниже описано **фактическое поведение разбора** функции `process_docstring_for_markdown()` в `scripts/tools/generate-api-docs.py` (основное преобразование выполняется построчно в `_process_doc_lines()`). При написании тегов ожидаемый результат генерации следует оценивать в соответствии с этим контрактом:

1. **`{!--< ignore >!--}` действует глобально**: перед началом преобразования выполняется проверка на подстроку по всему исходному тексту docstring; при совпадении модуль / класс / метод **полностью исключается из генерации документации**. Положение не имеет значения — тег срабатывает даже внутри кодового блока
2. **Кодовый блок имеет приоритет**: как только в строке встречается маркер блока ` ``` `, все строки внутри блока передаются как есть, а остальные теги внутри блока **не разбираются**
3. **`tips` собираются построчно**: текст «после тега» в строке с открывающим тегом + последующие строки, вплоть до строки, содержащей `{!--< /tips >!--}` (берётся текст до закрывающего тега), целиком рендерится как цитата `> **Подсказка**`; примеры и кодовые блоки внутри блока преобразуются как обычно. Текст «до тега» в строке с открывающим тегом и текст «после закрывающего тега» в строке с закрывающим тегом будет **отброшен**
4. **Незакрытые tips не вызывают ошибку**: при отсутствии закрывающего тега сбор продолжается молча до конца docstring, и весь фрагмент рендерится как блок подсказки — без ошибок и предупреждений; обнаружить это можно только при проверке результата генерации
5. **Однострочные теги сопоставляются по подстроке**: `internal-use` / `deprecated` / `experimental` выводятся как **внутренний метод** / **устаревший** / **экспериментальная функциональность** + текст после «последнего вхождения тега» в этой строке; текст до тега отбрасывается
6. **Неизвестные и неправильно написанные теги**: если строка одновременно содержит `{!--<` и `>!--}`, но тег не входит в число перечисленных известных, строка **молча пропускается**; если формат тега написан с ошибкой (например, `{!--< tip >--}` без `!`), условие пропуска не выполняется, и тег **попадёт в сгенерированный текст документации API как есть** — после генерации обязательно визуально проверяйте вывод

## Лучшие рекомендации

1. **Аннотации типов**: используйте синтаксис аннотаций типов Python
   ```python
   def func(param: int) -> str:
   ```

2. **Описание параметров**: указывайте значения по умолчанию для необязательных параметров
   ```python
   :param timeout: [int] Время ожидания (в секундах) (по умолчанию: 30)
   ```

3. **Возвращаемые значения**: для нескольких возвращаемых значений используйте `Tuple` или явно указывайте их
   ```python
   :return: 
       str: Информация о состоянии
       int: Код состояния
   ```

4. **Описание исключений**: используйте `:raises` для указания возможных исключений
   ```python
   :raises ValueError: Выбрасывается при недопустимом аргументе
   ```

5. **Внутренние методы**: непубличные API должны быть помечены тегом `{!--< internal-use >!--}`

6. **Устаревшие методы**: помечайте устаревшие методы и предоставляйте альтернативы
   ```python
   {!--< deprecated >!--} Используйте вместо этого new_method() | 2025-07-09
   ```
