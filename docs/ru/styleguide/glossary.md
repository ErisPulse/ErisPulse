# Глоссарий (единственный источник истины)

> [!TIP]
> **Когда читать этот документ**: когда при написании или редактировании документации вы не уверены, как назвать тот или иной концепт, или обнаружили, что в двух документах одно и то же понятие описано по-разному. Если это не ваш случай — пропустите.

В этой таблице сведены ключевые концепты документации ErisPulse, которые ранее в разных местах назывались непоследовательно. Для каждого термина приводится только одно **официальное название**, одна пара **русско-английского соответствия** и абзац с **пояснением исторических псевдонимов**; при расхождении основного текста с другими документами приоритет имеет эта таблица, и, пожалуйста, заодно исправляйте конфликтующие документы.

Принципы отбора:

- Включаются только концепты, «названия которых исторически дрейфовали или которые при смешанном употреблении русского и английского легко порождают неоднозначность»; чистые идентификаторы кода (например, `BaseModule`) не включаются
- Каждое определение предварительно проверено через grep по всей базе `docs/zh-CN` и по исходному коду на предмет фактического употребления; определения согласуются с доминирующим употреблением
- При первом появлении в документе указывается полное название (по-русски + английский термин в скобках), далее используется сокращение

## 1. Client и HttpClient

| Параметр | Содержание |
|------|------|
| Официальное название | `Client` (базовый класс `BaseClient`) |
| Рус.-англ. соответствие | Client (единый HTTP/WS-клиент) |
| Исторические псевдонимы | `HttpClient` (имя класса до 2.8.0, сохранено как совместимый псевдоним); `BaseHttpClient` (имя базового класса до 2.8.0, сохранено как совместимый псевдоним) |

**Единственное определение**: единый HTTP/WS-клиент, который через уровень абстракции инкапсулирует базовую библиотеку запросов (сейчас это aiohttp) и предоставляет статистику запросов, повторные попытки, журналирование, WebSocket-клиент и систему исключений ErisPulse. Начиная с 2.8.0 имя класса изменено с `HttpClient` на `Client`, **имя атрибута `sdk.client` не изменилось**.

**Как писать в документации**: всегда пишите `Client`; `HttpClient` упоминайте только в контексте «миграции старого кода / совместимости» с пометкой «совместимый псевдоним». Источник определения см. в [http-client](../advanced/http-client.md) и [Обзоре архитектуры](../architecture.md).

## 2. storage, env и StorageManager

| Параметр | Содержание |
|------|------|
| Официальное название | Экземпляр: `storage` (тип `BaseStorage`); базовый класс: `BaseStorage` |
| Рус.-англ. соответствие | storage (хранилище); StorageManager (менеджер хранилища, старое имя класса) |
| Исторические псевдонимы | `env` (унаследованный псевдоним v1, = тот же экземпляр); `StorageManager` (первоначальное имя класса SQLite-реализации до рефакторинга на несколько бэкендов, теперь совместимый псевдоним `SQLiteStorage`) |

**Единственное определение**: хранилище во время выполнения доступно через экземпляр `storage` (`sdk.storage` или `from ErisPulse import storage`); конкретный бэкенд выбирается конфигурацией `ErisPulse.storage.backend` (по умолчанию sqlite, можно переключить на mysql / postgres), API всех трёх бэкендов идентичен.

**Как писать в документации**: для описания «системы хранения / возможностей хранения» используйте «хранилище (storage)»; для обозначения типа пишите `BaseStorage`; для конкретных бэкендов — `SQLiteStorage` / `MySQLStorage` / `PostgresStorage`. `StorageManager` — **это лишь совместимое старое имя класса SQLite-реализации**, оно не представляет систему хранения в целом и в новых документах не используется; `env` — унаследованный псевдоним v1 (тот же экземпляр), поддерживаемый только для совместимости со старым кодом, в документации и примерах всегда используйте `sdk.storage`. Источник определения см. в [Бэкендах хранилища](../advanced/storage-backends.md) и [SQL-конструкторе](../advanced/sql-builder.md).

## 3. BaseConfig и AdapterConfig (включая ключи метаданных ui / webui)

| Параметр | Содержание |
|------|------|
| Официальное название | Базовый класс конфигурации: `BaseConfig`; ключ конфигурации элементов управления полей: `"ui"` |
| Рус.-англ. соответствие | BaseConfig (декларативный базовый класс конфигурации); AdapterConfig (старое имя, совместимый псевдоним) |
| Исторические псевдонимы | `AdapterConfig` (= обратно совместимый псевдоним `BaseConfig`); `"webui"` — ключ метаданных полей (старое имя, всё ещё поддерживается) |

**Единственное определение**: `BaseConfig` — универсальный декларативный базовый класс конфигурации, применимый в любых сценариях: адаптеры, модули, внешние проекты и т.д. (класс конфигурации объявляется вложенным классом `ConfigClass` и привязывается к модулю / адаптеру). Официальное имя ключа конфигурации элементов управления WebUI в поле `metadata` — `"ui"`; приоритет чтения: `"ui"` > `"webui"`, `"webui"` поддерживается только для совместимости со старым кодом.

**Как писать в документации**: всегда пишите `BaseConfig` и `"ui"`. Важно различать: имена вида `MyAdapterConfig` в примерах кода — это **просто соглашение об именовании собственных подклассов конфигурации у разработчиков** и не связаны с псевдонимом `AdapterConfig`. Источник определения см. в [Базовых концепциях адаптеров](../developer-guide/adapters/core-concepts.md) и [Базовых концепциях модулей](../developer-guide/modules/core-concepts.md).

## 4. Три измерения области действия (scope)

| Параметр | Содержание |
|------|------|
| Официальное название | Система в целом: область действия (scope); три измерения: **модульное измерение / измерение идентичности / исходящее измерение** |
| Рус.-англ. соответствие | module dimension (модульное измерение), identity dimension (измерение идентичности), outbound dimension (исходящее измерение) |
| Исторические псевдонимы | Старого имени нет, но исторически встречались неточные обобщающие названия вроде «система прав / система чёрно-белых списков» |

**Единственное определение** (соответствует трём точкам проверки в исходном коде `Core/scope.py`):

- **Модульное измерение**: какие модули доступны в данном контексте — `scope.is_allowed`; привязка на трёх уровнях: платформа / Bot / сессия (приоритет: сессия > Bot > платформа)
- **Измерение идентичности**: чьи события принимаются, а какие нет (допуск событий) — `scope.is_identity_allowed`; политики на четырёх уровнях: пользователь / сессия / Bot / адаптер (берётся наиболее конкретный)
- **Исходящее измерение**: что модуль может делать наружу (ограничения исходящих действий) — `scope.is_action_allowed`; по умолчанию всё разрешено, запрет появляется только при явном ужесточении, поддерживается гранулярность до уровня метода

**Как писать в документации**: названия трёх измерений фиксированы — «модульное измерение / измерение идентичности / исходящее измерение»; не используйте в качестве официальных названий варианты вроде «фильтрация модулей / проверка идентичности / ограничение действий»; нумерация ①②③ в документах — лишь маркеры изложения, не часть названия. Чёрно-белые списки — лишь одна из форм конфигурации модульного измерения, не используйте их для обозначения всей системы области действия. Источник определения см. в [Области действия (scope)](../advanced/scope.md).

## 5. owner / владение / контекст owner

| Параметр | Содержание |
|------|------|
| Официальное название | Название системы: **система владения (owner)**; название механизма: **контекст owner** |
| Рус.-англ. соответствие | ownership (владение), owner context (контекст owner), `current_owner` (текущий владелец) |
| Исторические псевдонимы | Смешанное употребление русского и английского: в документации «владение» и «owner» ранее чередовались, обозначая одну и ту же систему |

**Единственное определение**: владение — краеугольный камень «plug-and-play» для модулей: все ресурсы фреймворка (задачи, соединения, таймеры, домены перевода и т.д.), регистрируемые модулем в контексте owner, автоматически записываются на его имя и централизованно освобождаются при выгрузке модуля. **Контекст owner** — это текущий владелец, фиксируемый фреймворком на время выполнения кода модуля (переменная контекста `current_owner`); ресурсы, созданные внутри этого контекста, принадлежат текущему модулю. Если контекст недоступен (например, в колбэках tool-потоков), параметр `owner` следует передавать явно. Фасадом централизованного освобождения ресурсов служит `ErisPulse.Core.ownership`.

**Как писать в документации**: в русском тексте используйте «владение», при первом упоминании системы пишите полное название «система владения (owner)»; в кодовых идентификаторах и названии механизма контекста сохраняйте английский (контекст owner, `current_owner`, `owner_scope`). Не используйте варианты перевода вроде «собственность», «хозяин». Источник определения см. в [Системе владения (owner)](../advanced/ownership.md).

## 6. Границы трёх терминов module.call: сервисный контракт / каталог сервисов / белый список сервисов

| Параметр | Содержание |
|------|------|
| Название механизма | **Сервисный контракт** (сторона объявления, `meta.services`) |
| Название интерфейса | **Каталог сервисов** (сторона запросов, `sdk.module.services()`) |
| Описательное слово | **Белый список сервисов** (описывает лишь семантику ужесточения после объявления, не используется как название механизма) |

**Единственное определение**:

- **Сервисный контракт (meta.services)**: автор модуля в поле `services` метода `get_meta()` объявляет методы, доступные для внешнего вызова, — это **сторона объявления** контракта. Если ничего не объявлено, вызывать можно любой публичный метод (обратная совместимость); после объявления поверхность вызовов сужается, а выход за её пределы вызывает `ServiceNotProvidedError`
- **Каталог сервисов (services())**: интерфейс запросов во время выполнения `sdk.module.services()`, перечисляющий модули, явно объявившие контракт, а также сигнатуры их методов и описания, — это представление контракта со **стороны потребителя**; служит основой данных для MCP-изации (предоставления точек вызова ИИ)
- **Белый список сервисов**: текстовый термин, используемый только для **описания** семантики «после объявления вызывать можно лишь методы из белого списка»; не должен фигурировать в заголовках как название механизма или интерфейса

Граница одним предложением: **то, что объявляет автор, называется контрактом; запрос во время выполнения — каталогом; «белый список» лишь описывает семантику ужесточения**. Источник определения см. в [Межмодульном взаимодействии](../advanced/module-communication.md) и [API основных модулей](../api-reference/core-modules.md).
