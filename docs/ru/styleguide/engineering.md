# Правила надежности проекта

В этом документе описаны правила надежности исходного кода ErisPulse. Каждое правило содержит пояснение "почему" и реальные примеры из данного репозитория; перед внесением кода на вкладку, пожалуйста, пройдитесь по этой странице, поскольку часть проверок, помимо CI, выполняется на этапе ревью.

## 1. Классификация обработки исключений

`except` не является мусорным ведром. Что делать с исключением после его перехвата, зависит от того, что именно вы "поглотили":

| Категория | Критерии | Действие |
|------|------|------|
| Обнаружение | При сбое есть безопасное значение по умолчанию, и направление сбоя безвредно (например, обнаружение имени атрибута экземпляра с возвратом имени класса) | `pass` допустимо |
| Снижение | При сбое используется альтернативный путь, но все равно важно знать об этом (например, отсутствие необязательной зависимости) | `logger.debug` для логирования |
| Освобождение ресурсов | Закрытие соединений, файловых дескрипторов, потоков, задач | Минимум `logger.debug`, при повторении — `warning` |
| Запись данных | Запись конфигурации, логов сообщений, сохранение состояния | Начинать с `warning` — тихая потеря данных не позволит отслеживать их впоследствии |

**Запрещено двойное снижение**: не оборачивайте "вызов логирования" в `try/except: pass` — оповещение исчезнет при исключительных условиях, что равносильно отсутствию оповещения.

Примеры ошибок (все исправлены, приведены как шаблоны):

- В `close()` менеджера конфигурации последняя попытка записи была поглощена без логирования — пользователь изменил конфигурацию и закрыл процесс, изменения были потеряны без следа
- При замене сессии в HTTP-клиенте неудачное закрытие старой сессии было поглощено без логирования — утечка ресурсов соединения
- Повторное вызывание инициализации `warning` само было обернуто в `try/except: pass` — оповещение исчезло, когда i18n не был готов

## 2. Дисциплина уровней логирования

- **События сбоев — минимум `warning`**: исчерпание попыток повтора, срабатывание отката, неудача обратного вызова подписчика, неудача повторного воспроизведения состояния — это означает "состояние системы не соответствует ожиданиям", уровень `debug` равнозначен невидимости для пользователя
- **Повторяющиеся сбои в циклах должны быть ограничены**: в циклах очистки, наблюдателях, фоновых сборщиках мусора повторяющиеся исключения нужно ограничивать — использовать "первое предупреждение + последующий счетчик/охлаждение" или понижать до `debug` с периодическим суммированием, чтобы предотвратить переполнение логов
- `trace` используется только для обычных потоков в высокочастотных критических участках; `error` оставляется для сбоев, которые уже повлияли на результат запроса

## 3. 参数行为的集中化

Время ожидания, количество повторных попыток, период охлаждения, интервал опроса — все эти параметры должны быть определены в файле `Core/constants.py` (параметры поведения, доступные через CLI, также должны быть в этом файле), с именами `*_TIMEOUT_SECS` / `*_RETRY_*` / `*_COOLDOWN_SECS`, и в комментариях должно быть указано, где они используются. В реализационных файлах запрещено использовать "голые" числовые значения для тайм-аутов (`timeout=30`, `sleep(5)`), — разброс одинаковых значений по разным местам — это начало дрейфа.

**Ограничение**: это правило распространяется на основной репозиторий; рекомендуется, чтобы сторонние модули / адаптеры определяли параметры поведения в пределах своих собственных модулей, без обязательного размещения в `Core/constants.py`.

## 4. Общие API контракты

Классы и методы без префикса нижнего подчеркивания должны иметь: полные docstring (см. [Стиль комментариев](docstring.md)), полную аннотацию параметров и возвращаемых значений. Внутренние реализации (с `_` префиксом) могут быть менее строгими, но как только они появляются в документации или примерах, они должны соответствовать общим стандартам.

**Граница существующих элементов**: эти требования применяются к **новым / затронутым файлам**, не обязательно применять их к существующему коду; проблемы с существующим кодом отображаются в виде базового уровня, и когда файл затрагивается, проблемы с существующим кодом в этом файле становятся блокирующими.

## 5. Запрет на обратные ссылки на синглтоны

Компоненты фреймворка (менеджеры, загрузчики, базовые классы) не должны содержать полей с обратными ссылками на "корневой синглтон SDK":

- Обратные ссылки означают, что жизненный цикл компонента зависит от порядка сборки, и если сборщик забудет подключить, функциональность **тихо отключится**, а не выдаст ошибку — в этом проекте из-за удаления вызова `set_sdk_ref` в шести версиях библиотеки тихая перезагрузка/уведомления о зависимости тихо отключались
- При необходимости корневой ссылки: внедрение через конструктор (передача корня) или ленивое разрешение (первое использование при импорте), один из двух вариантов; ленивое разрешение никогда не должно "забыть вызвать"
- При необходимости доступа к состоянию других компонентов предпочтительно использовать подписку на события или фасад, а не лезть в чужие реестры; состояние менеджеров должно очищаться самостоятельно, а не через глобальный фасад (внутри фасада есть обратные ссылки на синглтоны, которые не покрывают отдельные экземпляры)

## 6. Дисциплина очистки и отката

- Пути очистки/удаления должны быть идемпотентными: при неудаче на полпути повторная попытка или повторная очистка не должны повторно освобождать или вызывать ошибку
- Перед необратимыми операциями (удаление, перезагрузка, удаление конфигурации) сначала делайте снимок состояния; снимок для отката имеет семантику "стараться изо всех сил", при неудаче отката должно быть `warning`
- Порядок очистки: отмена задач → закрытие соединений → внешние хуки → освобождение регистраций, каждый шаг независим, при сбое одного шага последующие не блокируются

## 7. Дисциплина тестирования

- При изменении поведения обязательно изменяются тесты; при исправлении бага сначала должен быть красный тест, который воспроизводит этот баг
- Пути с исключениями и граничные случаи (пустой ввод, тайм-аут, повторные вызовы, частично инициализированные объекты) рассматриваются наравне с обычными путями — защитная сеть регрессии является основой для рефакторинга
- Тесты могут обращаться к внутренним структурам, но точки доступа должны быть сконцентрированы: при изменении внутреннего расположения тесты изменяются путём модификации import и путей, а не семантики утверждений

**Существующие границы**: Дисциплина применяется к **новым / затронутым файлам**, не требуя обязательного добавления тестов для существующего кода; пробелы в покрытии существующего кода отображаются в проверках как базовый уровень, а проблемы в файлах, которые были затронуты, повышаются до уровня блокировки.
