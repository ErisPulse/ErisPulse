## 標準の概要

ErisPulse は、OneBot12 をコアイベント標準として採用し、その上に拡張および細分化を行っています。

### コア原則

1. **互換性**：すべての標準は OneBot12 標準と互換性を保つ必要があります。
2. **拡張性**：プラットフォーム固有の機能はプレフィックス方式で拡張し、衝突を避ける。
3. **一貫性**：タイムスタンプ、ID 形式などの重要なフィールドは統一的に処理する必要があります。
4. **トレーサビリティ**：デバッグや問題のトラブルシューティングのために、元のデータを保持する。

## なぜ標準が必要なのか？

### 1. クロスプラットフォーム互換性の確保

異なるプラットフォームではイベントのフォーマットが異なります。標準化された変換により、次のようなメリットがあります：
- モジュールのコードを一度だけ記述すれば、すべてのプラットフォームで動作します
- イベント処理ロジックが一貫性を保ちます
- 開発および保守コストを削減できます

### 2. API インターフェースの規範化

統一された API 応答フォーマットにより、次のようなメリットがあります：
- モジュールは一貫して API エラーを処理できます
- エラーメッセージが統一されており、理解しやすくなります
- 戻り値のデータ構造が一貫しています

### 3. コード品質の向上

標準規格により、次のようなメリットがあります：
- コードスタイルの一貫性を保ちます
- 名前衝突を減らします
- コードの可読性を向上させます

## 標準に従う利点

### アダプター開発者にとって

- 明確な変換ルール
- 統一されたレスポンス形式
- デバッグやテストが容易

### モジュール開発者にとって

- 一貫したイベントインターフェース
- 予測可能な API 挙動
- クロスプラットフォーム開発が簡素化

### 最終ユーザーにとって

- 穏やかなシステム挙動
- 統一されたメッセージ形式
- 良好な互換性

## 標準遵守チェックリスト

### イベント変換

- [ ] すべての標準フィールドが正しくマッピングされている
- [ ] プラットフォーム固有のフィールドにプレフィックスが追加されている
- [ ] タイムスタンプが10桁の秒単位に変換されている
- [ ] 元のデータが {platform}_raw に保存されている
- [ ] 元のイベントタイプが {platform}_raw_type に保存されている
- [ ] メッセージセグメントの alt_message が生成されている
- [ ] 要求イベントに request_id フィールドが含まれている

### API 応答

- [ ] status フィールドが含まれている
- [ ] retcode フィールドが含まれている
- [ ] data フィールドが含まれている
- [ ] message_id フィールドが含まれている
- [ ] message フィールドが含まれている
- [ ] 返却コードは OneBot12 規格に従っている

### 送信メソッドの命名

- [ ] パスカルケース（PascalCase）を使用している
- [ ] Task オブジェクトを返す
- [ ] 修飾メソッドは self を返す
- [ ] パラメータの命名が規則に従っている

### 要求操作

- [ ] HandleRequest クラスが _do_accept / _do_reject を実装している
- [ ] 操作の返り値は標準的な API 応答形式である
- [ ] 対応していない操作は retcode=10002 を返す
