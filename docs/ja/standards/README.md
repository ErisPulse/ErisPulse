## 標準の概要

ErisPulse は、コアイベント標準として OneBot12 を採用し、その上に拡張および細分化を行っています。

### コア原則

1. **互換性**：すべての標準は、OneBot12 標準と互換性を保つ必要があります。
2. **拡張性**：プラットフォーム固有の機能は、前接辞（プレフィックス）方式で拡張し、競合を避ける必要があります。
3. **一貫性**：タイムスタンプ、ID 形式などの重要なフィールドは、統一された処理を行う必要があります。
4. **追跡可能性**：デバッグや問題のトラブルシューティングのために、元のデータを保持する必要があります。

## なぜ標準が必要なのか？

### 1. プラットフォーム間の互換性を確保する

異なるプラットフォームのイベント形式はそれぞれ異なります。標準化された変換により、以下のことが保証されます：
- モジュールコードを一度書けば、すべてのプラットフォームで動作します
- イベント処理ロジックが一貫性を保ちます
- 開発と保守のコストを削減します

### 2. API インターフェースを規範化する

統一された API 応答形式により、以下のことが保証されます：
- モジュールは一貫して API エラーを処理できます
- エラーメッセージは統一されており、理解しやすいです
- 返されるデータ構造が一貫しています

### 3. コード品質の向上

標準的な規範により、以下のことが可能になります：
- コードスタイルの一貫性を保ちます
- 名前衝突を減らします
- コードの可読性を高めます

## 標準に従う利点

### アダプター開発者にとって

- 明確な変換ルール
- 統一されたレスポンス形式
- デバッグやテストが容易

### モジュール開発者にとって

- 一貫したイベントインターフェース
- 予測可能な API 挙動
- プラットフォーム間の開発が簡素化

### 最終ユーザーにとって

- 穏やかなシステム動作
- 統一されたメッセージ形式
- 良好な互換性

## 標準遵守チェックリスト

### イベント変換

- [ ] すべての標準フィールドが正しくマッピングされている
- [ ] プラットフォーム固有のフィールドにプレフィックスが追加されている
- [ ] タイムスタンプが10桁の秒単位に変換されている
- [ ] 保持された元のデータは {platform}_raw に格納されている
- [ ] 保持された元のイベントタイプは {platform}_raw_type に格納されている
- [ ] メッセージセグメントの alt_message が生成されている
- [ ] 要求イベントには request_id フィールドが含まれている

### API 応答

- [ ] status フィールドが含まれている
- [ ] retcode フィールドが含まれている
- [ ] data フィールドが含まれている
- [ ] message_id フィールドが含まれている
- [ ] message フィールドが含まれている
- [ ] 返却コードは OneBot12 規格に従っている

### 送信メソッドの命名

- [ ] パスカルケース（PascalCase）を使用している
- [ ] Task オブジェクトを返している
- [ ] 修飾メソッドは self を返している
- [ ] パラメータの命名は規則に従っている

### 要求操作

- [ ] HandleRequest クラスに _do_accept / _do_reject が実装されている
- [ ] 操作は標準の API 応答形式を返している
- [ ] 対応していない操作は retcode=10002 を返している
