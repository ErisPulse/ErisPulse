## 標準の概要

ErisPulse は OneBot12 をコアイベント標準として採用し、その上に拡張および細分化を行っています。

### コア原則

1. **互換性**：すべての標準は OneBot12 標準と互換性を保つ必要があります
2. **拡張性**：プラットフォーム特有の機能はプレフィックス方式で拡張し、衝突を避ける
3. **一貫性**：タイムスタンプ、ID形式などの重要なフィールドは統一して処理する
4. **追跡可能性**：デバッグや問題のトラブルシューティングのために元のデータを保持する

## 標準の必要性

### 1. クロスプラットフォーム互換性の確保

異なるプラットフォームのイベント形式はそれぞれ異なり、標準化された変換により以下が保証されます：
- モジュールコードは一度書けば、すべてのプラットフォームで実行可能
- イベント処理ロジックは一貫性を保つ
- 開発および保守コストを削減

### 2. API インターフェースの規範化

統一された API レスポンス形式により以下が保証されます：
- モジュールは一貫して API エラーを処理できる
- エラーメッセージは統一され、理解しやすい
- 戻り値のデータ構造は一貫している

### 3. コード品質の向上

標準規格により以下が助けられます：
- コードスタイルの一貫性を保つ
- 名前衝突を減らす
- コードの可読性を高める

## 標準を遵守することのメリット

### アダプター開発者にとって

- 明確な変換ルール
- 統一されたレスポンス形式
- 調整およびテストが容易

### モジュール開発者にとって

- 一貫したイベントインターフェース
- 予測可能な API 挙動
- クロスプラットフォーム開発が簡素化

### 最終ユーザーにとって

- 穏やかなシステム動作
- 統一されたメッセージ形式
- 良好な互換性

## 標準準拠チェックリスト


### イベント変換


- [ ] すべての標準フィールドが正しくマッピングされている
- [ ] プラットフォーム固有のフィールドにプレフィックスが付与されている
- [ ] タイムスタンプが10桁の秒単位に変換されている
- [ ] 生データが {platform}_raw に保存されている
- [ ] 元のイベントタイプが {platform}_raw_type に保存されている
- [ ] メッセージセグメントの alt_message が生成されている
- [ ] リクエストイベントに request_id フィールドが含まれている

### API レスポンス


- [ ] status フィールドが含まれている
- [ ] retcode フィールドが含まれている
- [ ] data フィールドが含まれている
- [ ] message_id フィールドが含まれている
- [ ] message フィールドが含まれている
- [ ] リターンコードが OneBot12 仕様に準拠している

### 送信メソッドの命名


- [ ] パスカルケース（PascalCase）を使用している
- [ ] Task オブジェクトを返す
- [ ] 修飾メソッドは self を返す
- [ ] パラメータの命名が規範に準拠している

### メディア送信（Image / Voice / Video / File）


- [ ] `file` パラメータはすべての形式を必須サポート：HTTP(S) URL / ローカルパス / `bytes`
- [ ] `file` パラメータは可能な限りの形式をサポートすることが望ましい：`file://` URI / Base64 / Data URI（サポート不可の場合はフォールバック階層に従い `retcode=10002` を返す）
- [ ] 形式判定の順序が規範に準拠している（bytes → URL → `file://` → パス）
- [ ] `File` のファイル名は導出順序に従って生成されている（明示的な `filename` > URL の basename > パスの basename > プラットフォームのデフォルト）
- [ ] プラットフォームのメディア制限がアダプタードキュメントで宣言されている
- [ ] サポート対象外のメディアタイプはフォールバック階層に従って処理されている（近縁タイプへのフォールバックまたは `retcode=10002` を返す。例外をスローせず、サイレントに破棄しない）

> プロトコルの詳細は [送信メソッド規範 §2.1](send-method-spec.md#21-メディアメッセージ送信プロトコルimage--voice--video--file) を参照

### リクエスト操作


- [ ] Request 内部クラスで _do_accept / _do_reject がオーバーライドされている（公開エントリの accept()/reject() はオーバーライドしないこと）
- [ ] 操作は標準の API レスポンス形式を返す
- [ ] サポート対象外の操作は retcode=10002 を返す
