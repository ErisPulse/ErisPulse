## 標準の概要

ErisPulse は、OneBot12 をコアイベント標準として採用し、その上で拡張および細分化を行っています。

### 核心原則

1. **互換性**：すべての標準は OneBot12 標準と互換性を保つ必要があります。
2. **拡張性**：プラットフォーム固有の機能はプレフィックス方式で拡張し、競合を避けるようにします。
3. **一貫性**：タイムスタンプ、ID 形式などの重要なフィールドは統一的に処理する必要があります。
4. **追跡可能性**：デバッグや問題のトラブルシューティングのために、元のデータを保持する必要があります。

## なぜ標準が必要なのか？


### 1. プラットフォーム間の互換性を確保する


各プラットフォームのイベント形式は異なりますが、標準化された変換により以下が保証されます：
- モジュールのコードは一度書けば、すべてのプラットフォームで動作します
- イベント処理のロジックが一貫性を持ちます
- 開発および保守コストを削減できます

### 2. API インターフェースを規格化する


統一された API 応答形式により以下が保証されます：
- モジュールが一貫して API エラーを処理できます
- エラーメッセージが統一され、理解しやすくなります
- 戻り値のデータ構造も一貫しています

### 3. コード品質の向上


標準規格により以下が可能になります：
- コードスタイルの一貫性を保ちます
- 名前衝突を減らします
- コードの可読性を高めます

## 標準に従うメリット


### アダプタ開発者にとって


- 明確な変換ルール
- 統一されたレスポンス形式
- デバッグやテストが容易

### モジュール開発者にとって


- 一貫したイベントインターフェース
- 予測可能な API 振る舞い
- 跨プラットフォーム開発が簡素化

### 最終ユーザーにとって


- 穏やかなシステム動作
- 統一されたメッセージ形式
- 良好な互換性

## 標準遵守チェックリスト

### イベント変換

- [ ] すべての標準フィールドが正しくマッピングされている
- [ ] プラットフォーム固有のフィールドにプレフィックスが追加されている
- [ ] タイムスタンプが10桁の秒単位に変換されている
- [ ] 元のデータが {platform}_raw に保存されている
- [ ] 元のイベントタイプが {platform}_raw_type に保存されている
- [ ] メッセージセグメントの alt_message が生成されている
- [ ] 要求イベントに request_id フィールドが含まれている

### API レスポンス

- [ ] status フィールドが含まれている
- [ ] retcode フィールドが含まれている
- [ ] data フィールドが含まれている
- [ ] message_id フィールドが含まれている
- [ ] message フィールドが含まれている
- [ ] 返却コードは OneBot12 規格に従っている

### 送信メソッドの命名

- [ ] パスカルケース（PascalCase）を使用している
- [ ] Task オブジェクトを返す
- [ ] 修飾メソッドは self を返す
- [ ] パラメータの命名が規則に従っている

### 要求操作

- [ ] HandleRequest クラスに _do_accept / _do_reject が実装されている
- [ ] 操作は標準的な API レスポンス形式を返す
- [ ] 対応していない操作は retcode=10002 を返す
