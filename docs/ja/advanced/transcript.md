# セッション受信トレイ（Transcript）

> [!TIP]
> **このドキュメントを読むべきケース**：メッセージ履歴や会話の復元が必要なとき、または受信トレイの保持ポリシーを調整したいとき。不要であれば読み飛ばしても、他の機能の利用には影響しません。


セッション受信トレイは、ボットが送受信したメッセージを自動的に記録し（セッションキー `platform:detail_type:target_id` 単位で整理）、
会話の復元（`event.history`）、シャドウモジュールの diff、コールドスタートのリプレイなどに履歴データを提供します。
このドキュメントでは、その**ストレージモデルと、保持ポリシーの各調整ノブがそれぞれ何を保護しているのか**、実行時オーバーライド API、そして制限を緩和することの実際のコストについて説明します。

> 制限を変更する前に、必ず「リスクと監査」のセクションを最後までお読みください——各調整ノブには、それが存在する理由があります。

## 仕組み

```
メッセージ ──append()──▶ 書き込みバッファ（メモリ上の deque、ハード上限 4096 行）
                        │  1 秒ごとにバッチで永続化（1 バッチ ≤64 行、単一トランザクション）
                        ▼
              storage バックエンドの transcript テーブル（デフォルトは sqlite）
                        │  約 32 件の追記ごとに遅延発火で保持クリーンアップを 1 回実行
                        ▼
              ┌─ セッション単位の FIFO 切り詰め（max_per_session、デフォルト 50 件）
              └─ グローバル TTL による削除（ttl_hours、デフォルト 168 = 7 日）
```

3 つの階層の保護は、それぞれ異なるリスクを防ぐためのものです：

| 調整ノブ | デフォルト値 | 保護する内容 | 無効化（=0）した場合の影響 |
|------|--------|----------|------------------|
| 書き込みバッファ上限 | 4096 行（定数、設定不可） | **メモリ**：ストレージが利用できない間のバックログで RAM が溢れないこと | 無効化不可——これはメモリの防衛線です |
| 単一テキストの切り詰め | 2000 文字（定数、設定不可） | 単一メッセージが占有するメモリ/ディスク量 | 無効化不可 |
| `max_per_session` | 50 件/セッション | **ディスク増加**：単一セッションの履歴が無限に蓄積すること | 該当セッションの履歴が無限に増え続けます |
| `ttl_hours` | 168（7 日） | **ディスク増加**：全セッションにわたる長期的な蓄積 | `transcript` テーブルが無限に増加します |

重要なポイント：**書き込みバッファにはハード上限があるため、保持ポリシーを緩和してもメモリが直接圧迫されることはありません**。
本当に注意すべきリスクは、ストレージ層と下流のコンシューマー側にあります（次のセクションを参照）。

## 設定

```toml
[ErisPulse.transcript]
enabled = true          # 自動記録を行うかどうか
max_per_session = 50    # セッションごとの保持件数（0 = セッション切り詰めを無効化）
ttl_hours = 168.0       # グローバルな保持期間（時間単位、0 = 永久にクリーンアップしない）
```

環境変数によるオーバーライドも同様に機能します：`ERISPULSE_TRANSCRIPT_MAX_PER_SESSION`、`ERISPULSE_TRANSCRIPT_TTL_HOURS`。
設定の変更はホットリロードで反映されます（書き込みバッファの永続化サイクル内、最大約 1 秒の遅延）。

## 実行時オーバーライド API

実行中に動的に調整したい場合（例：特定のシナリオ向けに一時的に保持期間を延長する）：

```python
from ErisPulse import transcript

# オーバーライド（設定より優先；メモリ上のみ有効、再起動後は設定値に戻る）
transcript.set_retention(max_per_session=500, ttl_hours=24 * 30)

# 有効な値とその出所を照会
transcript.get_retention()
# {'max_per_session': 500, 'ttl_hours': 720.0, 'overridden': ['max_per_session', 'ttl_hours']}

# 設定値に基づく動作に戻す
transcript.reset_retention()
```

- `0` を渡す = 対応するポリシーの無効化（warning ログに記録が残ります）。負の値は `ValueError` を送出します；
- オーバーライドは次回の保持クリーンアップ時に反映されます（遅延実行のため、最大で約 32 件分の追記サイクル遅延します）；
- `transcript` シングルトンはルートパッケージからインポートできるほか、`sdk.transcript` からもアクセスできます。

## リスクと監査：制限を緩和する前に必読

`max_per_session` / `ttl_hours` を無効化（または大幅に引き上げ）すると、`transcript` テーブルはメッセージ量に応じて
**無限に増加**します。その影響の連鎖：

1. **ディスク容量の枯渇**——sqlite の単一ファイルが膨張し続け、ディスクを使い果たすとフレームワークのストレージ層が使用不能になります；
2. **クエリの劣化**——`get()` / `recent()` / `get_by_trace()` のスキャンコストがテーブルの増加とともに上昇します；
3. **下流のメモリ圧迫（OOM の実際の原因）**——履歴を丸ごとメモリへ読み込むコンシューマー
   （履歴を伴う会話復元、パネルによる全件取得、ビジネスコードでの `get(session, n)` による大きな n の取得）は
   テーブルの増加とともにメモリを消費し、最悪の場合 OOM kill が発生します。

**緩和する前に自問すべき 3 つのこと**：どのくらいの期間の履歴が必要か？どれくらいの量が必要か？誰がクリーンアップするのか？
答えが「永遠に削除しない」に依存するなら、正しいアプローチは通常、外部アーカイブ（古いデータを定期的に専用データベースへ移動する）であり、
受信トレイに無限の保持をさせることではありません。

監査手段（テーブル規模の定期チェック）：

```python
# ORM/SQL ビルダー経由で行数とサイズを照会（sqlite の例）
from ErisPulse import storage

row = storage.Table("transcript").raw_sql("SELECT COUNT(*) AS n FROM transcript")
```

```sql
-- sqlite ファイルへ直接クエリ（テーブルサイズ）
SELECT COUNT(*) FROM transcript;
```

`保持ポリシーが無効化されました` という warning ログを受け取った場合 = 誰かが `0` を渡してポリシーを無効化したことを意味するため、ご自身の操作であることを確認してください。

## 他のメカニズムとの境界

- **対話セッションタイマー / wait_reply**：[対話セッションシステム](interaction.md) を参照してください。受信トレイとは無関係です；
- **会話復元による履歴の持ち帰り**：`resume(with_history=N)` は受信トレイから直近の N 件を取得します——
  受信トレイが切り詰められると、持ち帰れる履歴もそれに応じて減少します（`max_per_session` を引き上げれば復元可能な期間を延長できます）；
- **シャドウモジュールの diff**：`get_by_trace` によるトレース照会に依存するため、TTL が短すぎる受信トレイは diff 可能な期間を短縮します。
