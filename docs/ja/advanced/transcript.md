# セッション受信トレイ（Transcript）

> [!TIP]
> **このドキュメントを読むべきケース**：メッセージ履歴や会話の復元が必要なとき、または受信トレイの保持ポリシーを調整したいとき。不要であれば読み飛ばしても、他の機能の利用には影響しません。


セッション受信トレイは、ボットが送受信したメッセージを自動的に記録し（セッションキー `platform:detail_type:target_id` 単位で整理）、
会話の復元（`event.history`）、シャドウモジュールの diff、コールドスタートのリプレイなどに履歴データを提供します。
このドキュメントでは、その**ストレージモデルと、保持ポリシーの各調整ノブがそれぞれ何を保護しているのか**、実行時オーバーライド API、そして制限を緩和することの実際のコストについて説明します。

> 制限を変更する前に、必ず「リスクと監査」のセクションを最後までお読みください——各調整ノブには、それが存在する理由があります。

## 動作原理

```
メッセージ ──append()──▶ 書き込みバッファ（メモリ上の deque、ハード上限 4096 行）
                        │  1 秒ごとにバッチでディスクへ書き出し（1 バッチ ≤64 行、単一トランザクション）
                        ▼
              storage バックエンドの transcript テーブル（デフォルトは sqlite）
                        │  約 32 件の追加ごとに 1 回、遅延的に保持クリーンアップをトリガー
                        ▼
              ┌─ セッションごとの FIFO トリミング（max_per_session、デフォルト 50 件）
              └─ グローバル TTL 削除（ttl_hours、デフォルト 168 = 7 日）
```

三つの階層の保護は、それぞれ異なるリスクに対応しています：

| 調整項目 | デフォルト値 | 保護対象 | 無効化（=0）した場合の影響 |
|------|--------|----------|------------------|
| 書き込みバッファ上限 | 4096 行（定数、設定不可） | **メモリ**：ストレージが利用できない間のバックログで RAM が溢れないようにする | 無効化不可——これがメモリの防衛線です |
| 単一テキストの切り詰め | 2000 文字（定数、設定不可） | 単一メッセージのメモリ/ディスク占有量 | 無効化不可 |
| `max_per_session` | 50 件/セッション | **ディスク増加**：単一セッションの履歴が無限に蓄積する | そのセッションの履歴が無限に増加します |
| `ttl_hours` | 168（7 日） | **ディスク増加**：全セッションの長期的な蓄積 | `transcript` テーブルが無限に増加します |

重要なポイント：**書き込みバッファにはハード上限があるため、保持ポリシーを緩めてもメモリが直接圧迫されることはありません**。
真のリスクはストレージ層と下流のコンシューマー側にあります（次のセクションを参照）。

> [!TIP]
> **セッション記憶が不要なアプリケーションは全体を無効化できます**：`ErisPulse.transcript.enabled = false`
> と設定すれば、インバウンド/アウトバウンドメッセージの自動記録が停止します——メモリバッファにもストレージにも
> 書き込まなくなるため、常駐メモリと継続的なストレージ層の IO を節約できます。セッション受信トレイは主に
> AI コンテキスト注入と繰り返し防止という 2 つのニーズに対応しており、どちらも必要としないデプロイメント
> （純粋なコマンド型ボットなど）では無効化を推奨します。

## 設定

```toml
[ErisPulse.transcript]
enabled = true          # 自動記録するかどうか
max_per_session = 50    # 1セッションあたりの保持件数（0 = このセッションのトリミングを無効化）
ttl_hours = 168.0       # グローバル保持期間（時間、0 = 自動クリーンアップなし）
self_echo = "bot"       # 着信 bot エコーの処理方法：bot / skip / user
```

環境変数による上書きも同様に有効です：`ERISPULSE_TRANSCRIPT_MAX_PER_SESSION`、`ERISPULSE_TRANSCRIPT_TTL_HOURS`、
`ERISPULSE_TRANSCRIPT_SELF_ECHO`。
設定の変更はホットリロードで反映されます（書き込みバッファのディスク書き込みサイクル内で、最大約1秒の遅延）。

> [!TIP]
> **セッションメモリが不要ならオフにしましょう**：インボックスの唯一の利用者は会話復元 / シャドウ diff / コールドスタート再生です。
> お使いのボット（またはデプロイ済みのモジュール）がこれらの機能を一切使用しない場合は、`enabled = false`
> を設定するだけで、インボックスのメモリバッファとバックグラウンドのバッチディスク書き込み IO を節約できます——メッセージの送受信とコマンド処理には一切影響しません。

## メッセージの帰属（sender と meta）

すべてのクエリインターフェース（`get` / `recent` / `get_by_trace` / `event.history`）の各レコードには、帰属フィールドが統一して含まれており、「誰が発言したか / どのモジュールが送信したか」を区別するために使用されます：

| フィールド | 意味 |
|------|------|
| `sender` | 送信者識別子：インバウンドは `user_id`、アウトバウンドは bot アカウント / エコー時の `self.user_id` |
| `meta` | 記録時点のメタデータ（ホワイトリスト契約、完全な raw event ではない） |

`meta` のホワイトリスト：

- **インバウンド**：`nickname`（イベント発生時点のニックネーム。後から逆引きで取得できるのは「現在のニックネーム」）、`self_id`（bot アカウント）、`sub_type`、`message_id`。エコーメッセージにはさらに `self_echo: true` が付与されます；
- **アウトバウンド**：送信コンテキスト（`platform` / `method` / `detail_type` / `target_id` / `bot_id` / `trace_id` / `preview`）と `module`（送信の帰属モジュール、下記参照）。

旧バージョンのレコード（meta 列が存在しなかった時期のもの）の `meta` は `{}` となり、呼び出し側の `meta.get("nickname", "")` は自然にフォールバックします。ストレージバックエンドが ALTER をサポートしていない場合も、同様にサイレントで `{}` にフォールバックします。

### アウトバウンドの帰属（meta.module）

同一インスタンス上では複数のモジュールがメッセージを送信します（チャット、管理、定期リマインダーなど）。アウトバウンドレコードの `meta.module` は送信の帰属を示し、値の優先順位は `current_owner > current_caller > ""` です：

| 送信シナリオ | module の値 |
|----------|-----------|
| モジュールコードが `module.call` 経由で呼び出されている期間 | 対象モジュール名 |
| モジュールのイベントハンドラ内での送信 | そのハンドラを登録したモジュール名（ディスパッチ時に自動注入） |
| フレームワーク自身 / モジュールコンテキストなし | `""` |

`message.sent` / `message.sending` フックのペイロード（send_ctx）にも同様に `module` フィールドが含まれます。

### インバウンド bot エコー（self_echo）

一部のプラットフォーム/プロトコル実装では、bot 自身が送信したメッセージが message イベントとしてエコー返却されます（例：OneBot v11 の `report-self-message`、Telegram の outgoing message）。フレームワークはインバウンド記録の前に `self.user_id == user_id` によってエコーを識別し、`self_echo` の設定に従って処理します：

| 値 | 動作 |
|------|------|
| `"bot"`（デフォルト） | 記録は行うが、`role="bot"`、`sender=self_id`、`meta.self_echo=true` となる |
| `"skip"` | 記録しない（アダプタが同時に `message.sent` を発火させる場合は、アウトバウンド記録が自然に存在する） |
| `"user"` | `role="user"` として記録（旧動作、互換性のためのエスケープハッチ） |

エコーを返さないプラットフォーム（`self.user_id != user_id` が常に成立）では、この機能を無効にした場合と動作が完全に同一です。

### セッションでフィルタリングする recent

```python
from ErisPulse import transcript

# セッションを跨ぐグローバル時間窓（コールドスタート再生セマンティクス、デフォルト）
transcript.recent(3600)

# 単一セッションに限定：サーバー側でフィルタリングし、グローバル取得後にクライアントが session_key を一件ずつ比較することを回避
transcript.recent(3600, session_key="onebot11:group:123")
```

`session_key=None` はセッションを跨ぐセマンティクスを維持します。空文字列 `""` はフィルタなしと同等です（フォールトトレラント動作）。

## 実行時オーバーライド API

実行中に動的に調整したい場合（例：特定のシナリオ向けに一時的に保持期間を延長する）：

```python
from ErisPulse import transcript

# オーバーライド（設定より優先；メモリ上のみ有効、再起動後は設定値に戻る）
transcript.set_retention(max_per_session=500, ttl_hours=24 * 30)

# 有効な値とその出所を照会
transcript.get_retention()
# {'max_per_session': 500, 'ttl_hours': 720.0, 'overridden': ['max_per_session', 'ttl_hours']}

# 設定値に基づく動作に戻す
transcript.reset_retention()
```

- `0` を渡す = 対応するポリシーの無効化（warning ログに記録が残ります）。負の値は `ValueError` を送出します；
- オーバーライドは次回の保持クリーンアップ時に反映されます（遅延実行のため、最大で約 32 件分の追記サイクル遅延します）；
- `transcript` シングルトンはルートパッケージからインポートできるほか、`sdk.transcript` からもアクセスできます。

## リスクと監査：制限を緩和する前に必読

`max_per_session` / `ttl_hours` を無効化（または大幅に引き上げ）すると、`transcript` テーブルはメッセージ量に応じて
**無限に増加**します。その影響の連鎖：

1. **ディスク容量の枯渇**——sqlite の単一ファイルが膨張し続け、ディスクを使い果たすとフレームワークのストレージ層が使用不能になります；
2. **クエリの劣化**——`get()` / `recent()` / `get_by_trace()` のスキャンコストがテーブルの増加とともに上昇します；
3. **下流のメモリ圧迫（OOM の実際の原因）**——履歴を丸ごとメモリへ読み込むコンシューマー
   （履歴を伴う会話復元、パネルによる全件取得、ビジネスコードでの `get(session, n)` による大きな n の取得）は
   テーブルの増加とともにメモリを消費し、最悪の場合 OOM kill が発生します。

**緩和する前に自問すべき 3 つのこと**：どのくらいの期間の履歴が必要か？どれくらいの量が必要か？誰がクリーンアップするのか？
答えが「永遠に削除しない」に依存するなら、正しいアプローチは通常、外部アーカイブ（古いデータを定期的に専用データベースへ移動する）であり、
受信トレイに無限の保持をさせることではありません。

監査手段（テーブル規模の定期チェック）：

```python
# ORM/SQL ビルダー経由で行数とサイズを照会（sqlite の例）
from ErisPulse import storage

row = storage.Table("transcript").raw_sql("SELECT COUNT(*) AS n FROM transcript")
```

```sql
-- sqlite ファイルへ直接クエリ（テーブルサイズ）
SELECT COUNT(*) FROM transcript;
```

`保持ポリシーが無効化されました` という warning ログを受け取った場合 = 誰かが `0` を渡してポリシーを無効化したことを意味するため、ご自身の操作であることを確認してください。

## 他のメカニズムとの境界

- **対話セッションタイマー / wait_reply**：[対話セッションシステム](interaction.md) を参照してください。受信トレイとは無関係です；
- **会話復元による履歴の持ち帰り**：`resume(with_history=N)` は受信トレイから直近の N 件を取得します——
  受信トレイが切り詰められると、持ち帰れる履歴もそれに応じて減少します（`max_per_session` を引き上げれば復元可能な期間を延長できます）；
- **シャドウモジュールの diff**：`get_by_trace` によるトレース照会に依存するため、TTL が短すぎる受信トレイは diff 可能な期間を短縮します。
