# ドキュメントと外部向け執筆ルール

このページは、ErisPulse のドキュメントの執筆スタイルと外部向け（README/リリースページ）の執筆を規定しています。対象読者は、ドキュメントへの貢献者および README の維持管理者です。

## 一、ドキュメントの書き方

### 1. 価値を先に示す

すべてのドキュメントの第一画面では、一つの問いに答えます:「この記事を読むことで何が得られるのか」。必要に応じて参照するタイプのドキュメントは、統一された `> [!TIP]` のトリガー記述で始めます——**「いつこの記事を読む必要があるか: ……不要であれば読み飛ばしてください」**。必読のコアドキュメントは `> [!NOTE]` でリーディングパスにおける位置を示します。

### 2. 説明よりも実例を優先

実行可能なコードブロックで説明できる内容は、説明的な段落を書きません。コード例は import と最小限のコンテキストを含めてそのままコピーして実行できるものとし、`...` で重要なステップを省略しません。

### 3. トリガー記述は検索の入り口

ドキュメント冒頭の「いつ読むか」という一文は、AI アシスタントや検索とのマッチングテキストです——具体的なシナリオ（「アダプターで……が必要なとき」）を書き、抽象的な分類（「本書では……を紹介します」）は書きません。

### 4. 末尾のリンクは意図別にグループ化

文末の「次のステップ」リンクは、読者の意図ごとにグループ化します（X を深く学びたい → リンク A、問題 Y に直面した → リンク B）。無差別に目次を並べるだけの構成にはしません。

### 5. 変更履歴の書き方

更新ログにはリリース状態間の正味の差分を記録し、開発プロセスは記録しません: 同一テーマを複数回修正した場合は、既存のエントリを最終形態に更新します。同一リリース内で導入され、かつ同一リリース内で修正されたものは独立したエントリとしません。ユーザーからは感知できない内部調整は記録しません。完全な規範は `CHANGELOG.md` 冒頭の「執筆規範」を参照してください。

### 6. バージョン表記の規範

ドキュメント本文のバージョン表記には**動作の差分**のみを記載し、利用条件（必須バージョン）は記載しません:

- **本文には動作の差分を表記**: 動作がバージョンによって変化する場合にのみ表記し、「差分が何か」を必ず明記します——たとえば「X.Y.Z から `reload()` はデフォルトで全量リロード（それ以前は変更のあったモジュールのみリロード）」。読者はこれをもとに、自分のコードが新旧バージョンで挙動が異なるかどうかを判断できます
- **「本機能には X+ が必要」といった利用条件の表記はバージョン早見表に集約**: 各ドキュメント本文に散在させず、`docs/ja/README.md` のバージョン早見表に統一してまとめます。本文から必要に応じてリンクするだけで十分です
- **例の中のバージョン番号はプレースホルダーを使用**: ドキュメントのサンプルコードに登場するバージョン番号は `x.y.z` などのプレースホルダー形式で記述し、リリースのたびに陳腐化するのを避けます（本文で実際のバージョン番号を用いた動作差分の表記を除く）

## 二、外部向けページ（README / リリースページ）

### 1. 三段構成の骨格

1. **価値提案**：「これを使えば何ができるのか」を一言で明確にし、直後に30秒で検証できる効果（最小サンプル / デモ動画 / スクリーンショット）を続ける
2. **証明**：機能カード、実際の実行スクリーンショット、エコシステムの規模——証拠は説得力の順に並べ、詰め込みすぎない
3. **行動の入り口**：インストールコマンドは1行でコピー可能に。主要な各パス（クイックスタート / 深掘り開発 / エコシステム閲覧）ごとに、明確な次のステップへのリンクを示す

### 2. 羅列ではなくユースケースで語る

機能リストの各項目は「我々には何があるか」ではなく「どんな問題を解決するのか」に答える。エコシステムの紹介では、各項目に適用シーンを一言と最小サンプルを添え、ロゴを貼るだけで済ませない。

### 3. 言語とメッセージの統一

- **メイン言語**：現状——中国語（zh-CN）をドキュメントの主ソースとし、英語などのその他の言語は CI の翻訳プロセスによって zh-CN から自動生成する（`docs/zh-CN` だけを変更すれば、その他の言語は CI 経由で同期される）；目標——長期的には英語主版へと移行する。目標達成までの間、外部向けページは「中国語主ソース・多言語翻訳成果物」として保守し、その他の言語には「同期待ち」の表記を付けない（CI が自動同期を保証するため）
- 外部向けページでは内部用語（モジュールのコードネーム、マイルストーン名、内部プロセス用語）を使わない——読者はプロジェクトを初めて目にする人である
- 数字と約束（バージョン、性能、サポート範囲）はドキュメント本文と一致していなければならず、古くなった内容は残すよりも削除する

### 4. クイックスタートページのコンバージョン構造

`quick-start` 系のページ：まず「60秒で確認できる効果」（インストール → 3行のコード → 実行結果）を示してから解説を展開する。ユーザーはまず成功を体験してはじめて、読み進める気になるものだ。
