# プロジェクトの堅牢性に関するルール

このページは、ErisPulse ソースコードにおける堅牢性に関する規律です。各ルールには「なぜ」が記述されており、本リポジトリの実際の例も示されています。コードを貢献する前に、このページを確認してください。CI 以外の部分はレビューによって実行されます。

## 1. 例外の記録と分類

`except` はゴミ箱ではありません。例外をキャッチした後、何をするかは、あなたがどの例外を「飲み込む」かによって決まります：

| カテゴリ | 判定基準 | 処理方法 |
|------|------|------|
| 探測型 | 失敗しても安全なデフォルト値があり、失敗の方向が無害（例：インスタンスの属性名を検証し、クラス名にフォールバック） | `pass` で問題ありません |
| 降格型 | 失敗しても代替パスをたどり、それでも通知が必要（例：オプションの依存が欠落） | `logger.debug` で記録 |
| リソース解放型 | 接続、ファイルハンドル、スレッド、タスクの閉じる処理 | 低くても `logger.debug`、繰り返し発生する場合は `warning` に昇格 |
| データ書き込み型 | 設定の保存、メッセージの記録、ステータスの永続化を含む書き込み処理 | `warning` から始めるべき——データの静かなる破棄は事後調査が不可能になります |

**二重降格は禁止**：「ログの呼び出し自体」を `try/except: pass` で囲むことはしないでください。例外の条件でアラートが消えてしまうことは、アラートが存在しないのと同じです。

反面例（すべて修正済み、参考例として残します）：

- 設定マネージャーの `close()` 内で、最後のフラッシュ書き込みが失敗しても無視されてしまった——ユーザーが設定を変更してプロセスを終了したが、変更が記録されず失われた
- HTTPクライアントがセッションを置き換える際、古いセッションの `close()` が失敗しても無視されてしまった——接続リソースがリークした
- 初期化の繰り返し呼び出しで `warning` が発生するが、その `warning` 自体が `try/except: pass` に囲まれていた——i18nが準備できていないときにアラートが消えた

## 2. ログの分類ルール

- **失敗イベントは最低でも `warning` 以上**：リトライが尽きたり、ロールバックがトリガーされたり、サブスクライバのコールバックが失敗したり、ステートのリプレイが失敗した場合——これらは「システムの状態が期待と一致していない」ことを意味し、`debug` レベルのログはユーザーには見えないものとする
- **ループ内の失敗は節流する**：クリーンアップループ、watcher、バックグラウンド GC における繰り返しのエラーは、「最初の warning + 以降のカウント/クールダウン」または `debug` に降格して周期的にまとめることで、ログの大量出力を防止する
- `trace` は頻繁に実行されるホットパスの正常なフローにのみ使用する；`error` はリクエストの結果に影響を与える失敗にのみ使用する

## 3. 振る舞いパラメータの一元管理

タイムアウト、リトライ回数、クールダウン期間、ポーリング間隔はすべて `Core/constants.py` に定義する（CLI 側の振る舞いパラメータも同様にこのファイルへ集約する）。命名は `*_TIMEOUT_SECS` / `*_RETRY_*` / `*_COOLDOWN_SECS` とし、コメントに使用箇所を明記する。実装ファイルにベタ書きの数値によるタイムアウト（`timeout=30`、`sleep(5)`）を記述することは禁止とする —— 同じ意味のベタ書き値が複数箇所に散在するのは、ドリフトの起点となる。

**境界**：このルールはコアリポジトリに対する制約である。サードパーティモジュール / アダプタは、自身のモジュール内で振る舞いパラメータを一元定義することが推奨され、`Core/constants.py` への配置は必須としない。

## 4. パブリック API 契約

先頭にアンダースコアを持たないクラスおよびメソッドは、完全な docstring（[コメントスタイル規約](docstring.md) を参照）と、すべての引数および戻り値の型アノテーションを同時に備える必要があります。内部実装（`_` 接頭辞）については緩和されますが、ドキュメントやサンプルに一度でも登場した場合は、パブリック基準に従って扱われます。

**既存コードに関する境界**：上記の要件は**新規追加または変更されたファイル**が対象であり、既存コード全体への遡及適用（バックフィル）は強制されません。既存の問題はチェック時にベースラインとして表示され、該当ファイルが変更された時点で、その既存の問題はブロッキング（Blocker）に昇格します。

## 5. シングルトンの循環参照禁止

フレームワークコンポーネント（マネージャー、ローダー、基底クラス）は「ルート SDK シングルトン」への循環参照フィールドを保持してはいけません。

- 循環参照フィールドは、コンポーネントのライフサイクルとアセンブリの順序が結合することを意味し、アセンブリ側が接続を忘れると、機能は**静かに失効**します。エラーではなく、このプロジェクトでは `set_sdk_ref` の呼び出し元が削除されたことで、6つのリリースバージョンでホットリロード/依存性通知が静かに失効しました。
- ルートへの参照が必要な場合は、コンストラクタインジェクション（コンポジションルートから渡す）または遅延解決（最初に使用するときにインポートする）のいずれかを使用します。遅延解決は「呼び出しを忘れることはありません」。
- 他人の状態が必要な場合は、イベントのサブスクライブやファサードを優先し、他人のレジストリに手を伸ばしてはいけません。マネージャーインスタンスの独自の状態は、インスタンス内で自ら管理する必要があります。グローバルなファサードを介してはいけません（ファサード内部はシングルトンの循環参照であり、独立したインスタンスを上書きできません）。

## 6. クリーンアップとロールバックの規律

- アンインストール/クリーンアップパスは冪等性を保証する必要があります。途中で失敗した場合や、再試行、再アンインストールを行っても、2回目のリリースやエラーを投げてはいけません。
- 不可逆操作（アンインストール、再ロード、設定の削除）の前に必ずスナップショットを撮ります。スナップショットのロールバックは「最善を尽くす」意味合いで、ロールバックに失敗した場合は `warning` を残す必要があります。
- クリーンアップの順序は、タスクのキャンセル → 接続の閉じ → 外部フック → レジストリの回収です。各ステップは独立して耐障害性を持ち、1ステップの失敗が次のステップをブロックしてはいけません。

## 7. テスト規律

- 振る舞いを変更したら必ずテストも変更する。バグを修正する際は、そのバグを再現できるレッドテストを必ず先に用意する
- 異常パスと境界条件（空入力、タイムアウト、重複呼び出し、半初期化）は正常パスと同等に扱う。回帰を防ぐセーフティネットこそがリファクタリングの自信となる
- テストが内部構造にアクセスすることは許容されるが、アクセスポイントは集約すべきである。内部レイアウト変更時にテストを移行する際に修正するのは import とパスであって、アサーションのセマンティクスではない

**既存コードに関する境界**：上記の規律は**新規追加 / 変更が加えられたファイル**を対象とし、既存コード全体に対するテストの一括遡及追加を強制するものではない。既存コードのカバレッジ欠落はチェック時にベースラインとして表示され、該当ファイルに変更が加えられた時点でその既存の問題はブロッキングに昇格する。
