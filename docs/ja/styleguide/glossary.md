# 用語集（唯一の真実源）

> [!TIP]
> **このドキュメントを読むタイミング**：ドキュメントを作成・修正する際に、ある概念を何と呼ぶべきか迷ったとき、または2つのドキュメントで同一の概念について異なる表現が使われていることに気づいたとき。必要でなければ読み飛ばしてください。

この表は、ErisPulse ドキュメント内に存在していた一貫性のない概念を統一するためのものです。各用語には、**正式名称**、**中英対訳**、および**歴史的な別名の説明**が1つずつ記載されています。本文や他のドキュメントと矛盾する場合は、本表を優先とし、その都度矛盾しているドキュメントを修正してください。

収録基準：

- 「歴史的に呼び方が変化した」、または「中英混在で誤解を招きやすい」概念のみを収録します。純粋なコード識別子（例：`BaseModule`）は収録しません。
- 各定義は、`docs/zh-CN` フォルダ全体とソースコードで grep を実行し、実際の用法を検証した上で、主流の用法と一致するように定義しています。
- ドキュメント内で初めて登場する際には、全称（中国語 + 英語の括弧表記）を使用し、以降は略称を使用します。

## 1. Client と HttpClient

| 項 | 内容 |
|------|------|
| 正式名 | `Client`（基底クラス `BaseClient`） |
| 中英対照 | Client（統一 HTTP/WS クライアント） |
| 歴史的別名 | `HttpClient`（2.8.0 以前のクラス名、互換性のための別名として保持）；`BaseHttpClient`（2.8.0 以前の基底クラス名、互換性のための別名として保持） |

**唯一の定義**：統一された HTTP/WS クライアント。抽象層を介して下位のリクエストライブラリ（現在は aiohttp）をラップし、リクエスト統計、リトライ、ログ、WebSocket クライアント、および ErisPulse の例外体系を提供します。2.8.0 以降、クラス名は `HttpClient` から `Client` に変更されましたが、**`sdk.client` の属性名は変更されません**。

**ドキュメントでの表記**：一律 `Client` と記述します。ただし「旧コードの移行 / 互換性」の文脈では `HttpClient` と記述し、括弧内に「互換性のための別名」と明記します。定義の出典は [http-client](../advanced/http-client.md) および [アーキテクチャ概要](../architecture.md) を参照してください。

## 2. storage、env と StorageManager

| 項 | 内容 |
|------|------|
| 正式名 | インスタンス：`storage`（型 `BaseStorage`）；基底クラス：`BaseStorage` |
| 中英対照 | storage（ストレージ）；StorageManager（ストレージマネージャー、旧クラス名） |
| 歴史的別名 | `env`（v1 残存の別名、同一インスタンス）；`StorageManager`（マルチバックエンドリファクタリング前の SQLite 実装の旧クラス名、現在は `SQLiteStorage` の互換別名） |

**唯一の定義**：実行時のストレージはインスタンス `storage` を通じてアクセスします（`sdk.storage` または `from ErisPulse import storage`）。具体的なバックエンドは `ErisPulse.storage.backend` で設定され、スケジュールされます（デフォルトは sqlite、mysql / postgres に切り替え可能）。3つのバックエンドの API は同一です。

**ドキュメントの記法**：ストレージシステムやストレージ能力を説明する際は「ストレージ（storage）」と記述します。型を指す場合は `BaseStorage`、具体的なバックエンドを指す場合は `SQLiteStorage` / `MySQLStorage` / `PostgresStorage` と記述します。`StorageManager` は **SQLite 実装クラスの互換旧名** であり、ストレージシステム全体を表すものではありません。新規ドキュメントでは使用せず、`env` は v1 残存の別名（同一インスタンス）であり、既存の旧コード互換用のみ使用します。ドキュメントやサンプルでは一律 `sdk.storage` を使用します。定義の出典は [ストレージバックエンド](../advanced/storage-backends.md) および [SQLビルダ](../advanced/sql-builder.md) を参照してください。

## 3. BaseConfig と AdapterConfig（ui / webui メタデータキーを含む）

| 項 | 内容 |
|------|------|
| 正式名 | 設定基底クラス：`BaseConfig`；フィールドコントロール設定キー：`"ui"` |
| 中英対照 | BaseConfig（宣言的設定基底クラス）；AdapterConfig（旧名、互換性別名） |
| 歴史的別名 | `AdapterConfig`（= `BaseConfig` の互換性別名）；`"webui"` フィールドメタデータキー（旧名、引き続き互換性あり） |

**唯一定義**：`BaseConfig` は、アダプタ、モジュール、外部プロジェクトなど、あらゆる場面に適用可能な汎用的な宣言的設定基底クラスです（設定クラスは、モジュール / アダプタに宣言的にアタッチされるネストされたクラス `ConfigClass` として定義されます）。フィールド `metadata` 内の WebUI コントロール設定キーの正式名は `"ui"` です。読み取り優先度は `"ui"` > `"webui"` であり、`"webui"` は旧コードの互換性のためのみ使用されます。

**ドキュメントの書き方**：一律 `BaseConfig` と `"ui"` を使用してください。注意点として、例示コード内の `MyAdapterConfig` といった名前は、**開発者が独自に設定サブクラスにつけた命名習慣**であり、`AdapterConfig` 別名とは関係ありません。定義の出所は [アダプタの基本概念](../developer-guide/adapters/core-concepts.md) および [モジュールの基本概念](../developer-guide/modules/core-concepts.md) を参照してください。

## 4. スコープ（scope）の3次元

| 項目 | 内容 |
|------|------|
| 正式名称 | 全体：スコープ（scope）；3次元：**モジュール次元 / ID次元 / 出力次元** |
| 中英対照 | module dimension（モジュール次元）、identity dimension（ID次元）、outbound dimension（出力次元） |
| 歴史的旧称 | 旧名は存在しないが、「権限システム / ホワイトリスト・ブラックリストシステム」などの不正確な一般的な呼称が過去に使われていた |

**唯一の定義**（ソースコード `Core/scope.py` の3つの判定エントリポイントに対応）：

- **モジュール次元**：あるコンテキスト内でどのモジュールが使用可能か — `scope.is_allowed`、バインド対象は3段階：プラットフォーム / Bot / セッション（優先度は セッション > Bot > プラットフォーム）
- **ID次元**：誰のイベントを受け入れるか（イベントの入力制限） — `scope.is_identity_allowed`、戦略は4段階：ユーザー / セッション / Bot / アダプタ（最も具体的なものを選択）
- **出力次元**：モジュールが外部に対して何ができるか（出力アクションの制限） — `scope.is_action_allowed`、デフォルトではすべて許可、明示的に制限する場合のみ禁止、メソッドレベルでの細かい粒度もサポート

**ドキュメントの書き方**：3つの次元名は「モジュール次元 / ID次元 / 出力次元」として固定して使用し、「モジュールフィルタリング / ID検証 / アクション制限」などのバリエーションは正式名として使用しないこと。ドキュメント内の ①②③ 番号は文脈のためのマーキングであり、名前には含まれない。ホワイトリスト・ブラックリストはモジュール次元の構成の1つの形態に過ぎず、作用域システム全体を指すために使用しないこと。定義の出典は [作用域（scope）](../advanced/scope.md) を参照。

## 5. owner / 所有権 / owner コンテキスト

| 項 | 内容 |
|------|------|
| 正式名 | システム名：**所有権（owner）システム**；メカニズム名：**owner コンテキスト** |
| 中英対照 | ownership（所有権）、owner context（owner コンテキスト）、`current_owner`（現在の所有者） |
| 歴史的別名 | 中英混在：ドキュメント内で「所有権」「owner」が同一システムを指して交互に使用されていた |

**唯一の定義**：所有権はモジュールの「即插即用」の基盤です。モジュールが owner コンテキスト内で登録するフレームワークリソース（タスク、接続、タイマー、翻訳ドメインなど）はすべて自動的に名前が付けられ、モジュールがアンロードされた際に一括して回収されます。**owner コンテキスト**とは、モジュールコードの実行中にフレームワークが記録する現在の所有者（`current_owner` 上下文変数）を指します。リソースはこのコンテキスト内で作成された場合、現在のモジュールに所有されます。コンテキストが利用できない場合（たとえばツールスレッドのコールバック時）は、明示的に `owner` パラメータを渡す必要があります。一括回収のインターフェースは `ErisPulse.Core.ownership` です。

**ドキュメントの書き方**：中国語の文章では「所有権」を使用し、システム名が初めて登場する場合は「所有権（owner）システム」と記述します。コードの識別子やコンテキストメカニズム名は英語のまま（owner コンテキスト、`current_owner`、`owner_scope`）です。「所有権」「属主」などの訳語は使用しないでください。定義の出典は [所有権（owner）システム](../advanced/ownership.md) を参照してください。

## 6. module.call 三つの境界：サービス契約 / サービスディレクトリ / サービスホワイトリスト

| 項目 | 内容 |
|------|------|
| 機制名 | **サービス契約**（`meta.services` 声明端） |
| インターフェース名 | **サービスディレクトリ**（`sdk.module.services()` クエリ端） |
| 説明用語 | **サービスホワイトリスト**（宣言後の制限を説明するための語彙、メカニズムのタイトルには使わない） |

**唯一の定義**：

- **サービス契約（meta.services）**：モジュール作者が `get_meta()` の `services` フィールドで外部から呼び出せるメソッドを宣言するもの——契約の**宣言端**。宣言がなければ任意の公開メソッドを呼び出せる（後方互換性あり）、宣言後は呼び出し範囲が狭まり、範囲外の呼び出しは `ServiceNotProvidedError` をスローする。
- **サービスディレクトリ（services()）**：`sdk.module.services()` は実行時に呼び出せるモジュールとそのメソッドの署名、説明をリストアップするクエリインターフェース——契約の**消費端**の視点であり、MCP化（呼び出しポイントをAIに公開）のためのデータ基盤を提供する。
- **サービスホワイトリスト**：宣言後の「ホワイトリスト内のみのメソッド呼び出しが可能」という意味を説明するための用語であり、メカニズムやインターフェースの名称としてタイトルに使われることはない。

一言で境界を示す：**作者が宣言する部分を「契約」と呼び、実行時にクエリする部分を「ディレクトリ」と呼び、「ホワイトリスト」は制限された呼び出しを説明する語彙にすぎない**。定義の出典は [モジュール間通信](../advanced/module-communication.md) と [コアモジュール API](../api-reference/core-modules.md) を参照。
