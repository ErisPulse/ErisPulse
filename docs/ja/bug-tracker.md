# バグ追跡器

このドキュメントは、ErisPulse SDK の既知のバグとその修正状況を、修正バージョンの日付順に記録しています。

> **読者の皆様へ**
> どのようなソフトウェアにも完璧さは存在せず、どんなに注意深く開発者であっても小さなミスを残してしまうことがあります。本追跡リストに記載されているのは、実行に実際の影響を与える問題のみです。あまりにも些細で「軽微」の等級にも達しないような欠点は、ここには含まれません。リストに「重大」の項目が多めに見えるかもしれませんが、公開する目的は、問題の調査と遡及をスムーズにすることであり、不安を煽ることではありません。見える化され、記録され、修正された問題こそが、プロジェクトが進化している証拠です。このリストを見て不安になる必要はありません。これは問題解決のためのツールであり、不安の原因ではありません。

> **読み方と保守の規約**
> - 各バグ記録には、問題の説明、根本原因分析、影響を受けたバージョン範囲、修正方法などの構造化されたフィールドが含まれており、アップグレードする前に「影響バージョン」が現在使用しているバージョンをカバーしているかを確認することをお勧めします。
> - 新しいバグ項目を追加する場合は、対応する位置に内容を追加し、以下のフィールド規格と重大度/タイプ分類に従ってください。

## フィールド説明

### 必須フィールド

| フィールド | 説明 |
|------|------|
| **問題** | バグの外的表現、ユーザーが観察できる異常現象。エラーメッセージや典型的なシナリオをできるだけ含めてください |
| **原因** | 具体的なコードの欠陥を指す根本原因分析（「根本原因の経路」の図は複雑な場合に使用） |
| **影響バージョン** | 影響を受けたバージョンの範囲、形式 `導入バージョン - 修正バージョン`（両端の dev バージョンを含む） |
| **修正バージョン** | そのバグを修正した具体的なバージョン番号 |
| **修正内容** | 修正方法の簡潔な説明、重要なコード変更点を含む |
| **修正日** | 対応する修正バージョンのリリース日、`YYYY/MM/DD` 形式 |
| **重大度** | 下記「重大度の分類」に従って記載 |
| **タイプ** | 下記「タイプ分類」に従って記載、複合も可（例: `アダプタ / ルーティング`） |

### 省略可能なフィールド

| フィールド | 説明 | 適用場面 |
|------|------|---------|
| **再現手順** | そのバグを引き起こす最小限の再現手順 | 複雑なバグ、偶発的なバグは推奨 |
| **関連** | 関連する Issue / PR / Commit リンク | 外部の議論記録がある場合に追加 |
| **リグレッションテスト** | 修正の検証、再発防止のためのテストケースの位置 | pytest 用のテストケースが作成されている場合に追加 |

## 重大度の分類

| 記号 | 等級 | 判定基準 | 典型的な現象 |
|------|------|---------|---------|
| 🔴 | 重大 | プロセスのクラッシュ、データの損失/破損、コア機能の完全不可用、セキュリティの脆弱性 | OOM Kill、メッセージの送信失敗、モジュールのロード失敗、ホットリロードの失敗 |
| 🟡 | 中等 | 機能の異常だが回避方法あり、非コア機能の失敗、偶発的な問題 | 状態の判断ミス、繰り返し発動、キャッシュの期限切れ、エラーメッセージの不正確 |
| 🟢 | 軽微 | コア機能に影響せず、コード品質や体験の問題、潜在的なリスクが発生していない | 非推奨の API、死んだコード、警告ログの欠落 |

## 修正済みのバグ

### [BUG-001] イベントハンドラの重複登録によりイベントが複数回処理される

**問題**: 複数の `@message` / `@notice` などのデコレーターを使ってハンドラを登録した場合、同じイベントが複数回トリガーされ、コマンドが複数回実行されたり、ログが複数回出力されたりする。

**原因**: `BaseEventHandler` がアダプタのイベントバスにハンドラを登録する際に重複チェックがなく、各デコレーターがバスに1回ずつ登録され、イベント配信時に複数回呼び出される。

**影響バージョン**: 2.2.0-dev.0 - 2.2.1-dev.0

**修正バージョン**: 2.2.1-dev.0

**修正内容**: `BaseEventHandler` を最適化し、各イベントタイプがアダプタに1回だけハンドラを登録するようにし、重複トリガーを回避する。

**修正日**: 2025/08/18

**重大度**: 🔴 重大

**タイプ**: イベントシステム

---

### [BUG-002] Init コマンドのアダプタ設定パスの型エラー

**問題**: `ep init` コマンドを使ってインタラクティブに初期化を行うと、アダプタの設定を選択した際に型エラーが発生する：

```
インタラクティブ初期化が失敗しました: 'str' と 'str' の '//' 演算子がサポートされていません
```

**原因**: 2.3.7 バージョンで設定ファイルのパスを調整した際に、メソッドの引数の型が不一致。`_configure_adapters_interactive_sync` は `str` 型の引数を受け取りますが、内部で `Path` の `/` 演算子を使ってパスを結合しています。

**影響バージョン**: 2.3.7 - 2.3.9-dev.1

**修正バージョン**: 2.3.9-dev.1

**修正内容**: `_configure_adapters_interactive_sync` メソッドの引数の型を `str` から `Path` に変更し、呼び出し時に `Path` オブジェクトを直接渡す。

**修正日**: 2026/03/23

**重大度**: 🟡 中等

**タイプ**: CLI

### [BUG-003] 再起動後にコマンドイベントが無効になる

**問題**: `sdk.restart()` を呼び出した後、`@command` で登録したコマンドがトリガーされなくなり、コマンドを送信してもロボットが反応しない。

**原因**: `adapter.shutdown()` がイベントバスをクリアした後、`BaseEventHandler` の `_linked_to_adapter_bus` 状態が `False` にリセットされていないため、`_process_event` メソッドがアダプタのバスにすでにマウントされていると判断し、再マウント処理をスキップする。

**影響バージョン**: 2.2.x - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `_linked_to_adapter_bus` 状態を追跡する仕組みを導入し、`_clear_handlers()` でバスの接続を切断した後、次回の `register()` で自動的に再マウントするようにし、`shutdown`/`restart` のシナリオに対応する。

**修正日**: 2026/04/09

**重大度**: 🔴 重大

**タイプ**: イベントシステム

### [BUG-004] ライフサイクルイベントハンドラがクリアされない

**問題**: `sdk.restart()` の後、古いライフサイクルイベントハンドラが存在し、重複してトリガーされ、同じイベントが複数回処理される。

**原因**: `lifecycle._handlers` 辞書が `uninit()` 時にクリアされておらず、`restart` 後に古いハンドラと新しいハンドラが同時に存在する。

**影響バージョン**: 2.3.0 - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `Uninitializer` のクリーンアップフローの末尾（すべてのイベントが送信された後）、`lifecycle._handlers` をクリアする。

**修正日**: 2026/04/09

**重大度**: 🟡 中等

**タイプ**: ランタイム

### [BUG-005] Event.is_friend_add/is_friend_delete の detail_type が OB12 標準と一致しない

**問題**: `Event.is_friend_add()` は `detail_type == "friend_add"` をチェックし、`Event.is_friend_delete()` は `detail_type == "friend_delete"` をチェックしていますが、OneBot12 標準では `detail_type` の値は `"friend_increase"` と `"friend_decrease"` です。`notice.py` の `on_friend_add`/`on_friend_remove` デコレーターが使用する値と一致しないため、デコレーターで登録したハンドラがトリガーされた際に、対応する `is_friend_add()`/`is_friend_delete()` 判定メソッドは `False` を返します。

**原因**: `wrapper.py` では非標準の命名が使われており、`notice.py` では正しい OB12 標準の命名が使われています。

**影響バージョン**: 実装以降

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `is_friend_add()` のマッチング値を `"friend_add"` から `"friend_increase"` に、`is_friend_delete()` を `"friend_delete"` から `"friend_decrease"` に変更します。

**修正日**: 2026/04/13

**重大度**: 🟡 中等

**タイプ**: イベントシステム

### [BUG-008] Bot オンラインイベントが shutdown プロセス中に重複送信される

**問題**: `adapter.shutdown()` を使ってすべてのアダプタを閉じる際、`_update_bot_status()` が閉じるプロセス中に Bot オンラインイベントを繰り返し送信し、同一批の Bot が複数回オフラインとマークされ、`adapter.bot.offline` ライフサイクルイベントが複数回トリガーされます。

**原因**: 2.4.0-dev.1 で導入された Bot 状態の追跡システムは、`shutdown()` 中に「閉じ中」のフラグを設定しておらず、`_update_bot_status()` は通常のオフラインと閉じるプロセス中の連鎖的なオフラインを区別できません。

**影響バージョン**: 2.4.0-dev.1 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `AdapterManager` に `_is_being_shutdown` フラグを追加し、`shutdown()` 開始時に True に、終了時にクリアします。`_update_bot_status()` はこのフラグをチェックして、閉じるプロセス中の重複送信をスキップします。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: アダプタ

### [BUG-009] LazyModule が同期アクセスで BaseModule を初期化していない

**問題**: ユーザーが同期コンテキストで LazyModule の BaseModule 属性にアクセスする場合、`loop.create_task()` を使って非同期的に初期化しますが、待機せずに返すため、初期化が完了していない可能性があり、競合状態が発生します。

**原因**: `_ensure_initialized()` は `loop.create_task(self._initialize())` を使って初期化を開始した後、初期化が完了するのを保証していません。

**影響バージョン**: 2.4.0-dev.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**: 同期コンテキストでは、BaseModule の初期化を `asyncio.run(self._initialize())` に変更し、初期化が完了してから返すようにします。透明なプロキシの特性を維持し、ユーザーは同期/非同期の違いを意識する必要がありません。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: ローディングシステム

### [BUG-010] 複数スレッドでの設定書き込みでデータが失われる

**問題**: 複数スレッドで `config.setConfig()` を呼び出す場合、`_flush_config()` の読み取り-変更-書き込み操作は原子的ではなく、一部の書き込みが失われる可能性があります。

**原因**: `_flush_config()` は `RLock` を使用していますが、ファイルの読み取りと書き込みの間にはファイルロックが保護されておらず、`_schedule_write` の Timer が複数回トリガーされて上書きされる可能性があります。

**影響バージョン**: 2.3.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**:
1. ファイルロックメカニズム（`_file_lock`）を追加してファイル操作の原子性を保証
2. ファイルの書き込み後に一時ファイルを原子的にリネーム（`os.replace`/`os.rename`）
3. `_schedule_write` の Timer のキャンセルと再スケジュールのロジックを改善

**修正日**: 2026/04/21

**重大度**: 🔴 重大

**タイプ**: 設定システム

### [BUG-011] Windows で CTRL+C でプログラムを停止できない

**問題**: Windows で `python main.py` を直接実行すると、CTRL+C でプログラムを停止できません。プログラムは正常に起動し、ルーティングサーバーの情報を出力した後、CTRL+C は全く反応せず、タスクマネージャーで強制終了するしかありません。一方、`epsdk run` で起動した場合は正常に停止できますが、`epsdk run` はサブプロセスモデルで実行されています。

**原因**: Hypercorn ASGI サーバーの `serve()` 関数内部で `signal.signal(SIGINT, handler)` を使って独自の SIGINT ハンドラーを登録しており、Python のデフォルトの `KeyboardInterrupt` 処理メカニズムを上書きしています。`asyncio.create_task()` でバックグラウンドタスクとして Hypercorn を起動した場合、Hypercorn の内部のシャットダウンフローが正しくトリガーされない（`worker_serve` モードを期待しているため）、CTRL+C シグナルが Hypercorn に飲み込まれても、クリーンアップ動作が発生しません。

**影響バージョン**: 2.3.6 - 2.4.2

**修正バージョン**: 2.4.3-dev.0

**修正内容**:
1. ASGI サーバーを Hypercorn から Uvicorn に切り替えます（`pyproject.toml` の依存関係を変更）
2. `uvicorn.Server._serve()` を直接使ってサーバーを起動し、**`capture_signals()`** シグナル処理コンテキストマネージャーを回避します
3. `server.should_exit = True` を使って優雅な停止を実現し、タイムアウトしたらバックグラウンドタスクをキャンセルします
4. 同期的にサブプロセス実行モデルと `runtime/cleanup.py` クリーンアップモジュールを削除します（サブプロセスのクリーンアップメカニズムは不要になります）

**修正日**: 2026/04/28

**重大度**: 🔴 重大

**タイプ**: CLI / ランタイム

### [BUG-012] ホットリスタート後に更新されたモジュールのコードが有効にならない

**問題**: `sdk.restart()` を使ってソフトリスタートした後、`epsdk install` でアップグレードされたモジュール/アダプタの新しいコード（追加された API ルートなど）が有効にならず、以前のバージョンのロジックが実行されます。プロセスを完全に再起動するまで最新のコードをロードできません。

**原因**: `_do_restart()` が再初期化する際に `entry_point.load()` を呼び出しますが、この関数は `sys.modules` からキャッシュされた古いモジュールオブジェクトを返すため、ディスクから最新のコードを再読み込みしません。

**影響バージョン**: 早期のバージョン - 2.4.3-dev.1

**修正バージョン**: 2.4.3-dev.1

**修正内容**: `uninit()` の後、`init()` の前に `sys.modules` にロードされたモジュール/アダプタパッケージのキャッシュをクリアし、`entry_point.load()` がディスクから最新のコードをロードできるようにします。`_collect_top_level_modules()` と `_invalidate_module_cache()` を追加し、`top_level.txt` または entry-point value からトップレベルモジュール名を推定します。

**修正日**: 2026/05/03

**重大度**: 🔴 重大

**タイプ**: ローディングシステム / ランタイム

### [BUG-013] モジュールのロード戦略のソートロジックが誤っている
