# バグ追跡ツール

このドキュメントでは、ErisPulse SDK の既知のバグと修正状況を記録しています。

---

## 修正済みのバグ

### [BUG-001] Init コマンドアダプタ構成パスの型エラー

**問題**: `ep init` コマンドを使用して対話型で初期化する場合、構成アダプタを選択すると型エラーが発生します。

```
インタラクティブな初期化に失敗しました: unsupported operand type(s) for /: 'str' and 'str'
```

**原因**: バージョン 2.3.7 で設定ファイルのパスを調整した際、メソッドパラメータの型が不一致でした。`_configure_adapters_interactive_sync` は `str` 型のパラメータを受け取りますが、内部では `Path` の `/` 演算子を使用してパスを連結しています。

**影響バージョン**: 2.3.7 - 2.3.9-dev.1

**修正バージョン**: 2.3.9-dev.1

**修正内容**: `_configure_adapters_interactive_sync` メソッドのパラメータ型を `str` から `Path` に変更し、呼び出し時に直接 `Path` オブジェクトを渡します。

**修正日**: 2026/03/23

### [BUG-002] 再起動後にコマンドイベントが無効になる

**問題**: `sdk.restart()` を呼び出した後、`@command` で登録されたコマンドが発火しなくなります。コマンドを送信してもロボットが反応しないという状態になります。

**原因**: `adapter.shutdown()` でイベントバスをクリアした後、`BaseEventHandler` の `_linked_to_adapter_bus` 状態が `False` にリセットされず、`_process_event` メソッドがアダプタバスにマウント済みであると判断し、再マウント処理をスキップしてしまいます。

**影響バージョン**: 2.2.x - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `_linked_to_adapter_bus` 状態の追跡を導入し、`_clear_handlers()` でバス接続を切断した後、次回の `register()` で自動的に再マウントするようにし、shutdown/restart のシナリオに対応しました。

**修正日**: 2026/04/09

### [BUG-003] ライフサイクルイベントハンドラがクリアされていない

**問題**: `sdk.restart()` 後も、古いライフサイクルイベントハンドラが存在し、重複して発火するため、同じイベントが複数回処理されます。

**原因**: `lifecycle._handlers` 辞書は `uninit()` 時に一度もクリアされておらず、再起動後は古いハンドラと新しいハンドラが同時に存在します。

**影響バージョン**: 2.3.0 - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `Uninitializer` のクリア処理の末尾（すべてのイベントのコミット後）で `lifecycle._handlers` をクリアします。

**修正日**: 2026/04/09

### [BUG-006] Event.is_friend_add/is_friend_delete の detail_type と OB12 標準が不一致

**問題**: `Event.is_friend_add()` は `detail_type == "friend_add"` をチェックし、`Event.is_friend_delete()` は `detail_type == "friend_delete"` をチェックします。しかし OneBot12 標準で定義されている `detail_type` の値は `"friend_increase"` および `"friend_decrease"` です。`notice.py` 内の `on_friend_add`/`on_friend_remove` デコレータで使用される値と不一致であり、デコレータ経由で登録されたハンドラが発火した際、対応する `is_friend_add()`/`is_friend_delete()` 判定メソッドが `False` を返してしまいます。

**原因**: `wrapper.py` で非標準の命名を使用し、一方 `notice.py` では正しい OB12 標準の命名を使用しています。

**影響バージョン**: rq実装以来

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `is_friend_add()` のマッチ値を `"friend_add"` から `"friend_increase"` に変更し、`is_friend_delete()` を `"friend_delete"` から `"friend_decrease"` に変更します。

**修正日**: 2026/04/13

**修正内容**: `command.py` 内の2箇所の `asyncio.get_event_loop()` を `asyncio.get_running_loop()` に置き換えます。

**修正日**: 2026/04/13

**修正内容**: スキップする前に、`key` が欠落しているフィールド情報を記録する `logger.warning()` を追加します。

**修正日**: 2026/04/13

### [BUG-010] LazyModule 同期アクセスによる未初期化完了の状態

**問題**: ユーザーが同期コンテキスト内で遅延ロードされた BaseModule プロパティにアクセスした際、モジュールは `loop.create_task()` を使用して非同期で初期化されますが待機されず、プロパティアクセス時にまだ初期化が完了していない可能性があり、競合状態を引き起こします。

**原因**: `_ensure_initialized()` は BaseModule に `loop.create_task(self._initialize())` を使用した後すぐにリターンし、初期化完了を保証していません。

**影響バージョン**: 2.4.0-dev.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**: 同期コンテキスト内では、BaseModule の初期化を `asyncio.run(self._initialize())` に変更し、初期化完了後にリターンするようにします。透過プロキシの特性を維持し、ユーザーは同期/非同期の違いを感知する必要はありません。

**修正日**: 2026/04/21

### [BUG-011] 設定システムのマルチスレッド書き込みによるデータ損失

**問題**: マルチスレッド環境下で、複数のスレッドが同時に `config.setConfig()` を呼び出すと、`_flush_config()` の読み取り-修正-書き込み操作がアトミックではなく、部分的な書き込みが失われる可能性があります。

**原因**: `_flush_config()` は `RLock` を使用していますが、ファイルの読み取りと書き込みの間にファイルロックによる保護がなく、`_schedule_write` の Timer が複数回トリガーされ上書きされる可能性があります。

**影響バージョン**: 2.3.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**:
1. ファイルロックメカニズム（`_file_lock`）を追加してファイル操作のアトミック性を確保
2. 一時ファイルに書き込んだ後、アトミックにリネーム（`os.replace`/`os.rename`）
3. `_schedule_write` の Timer のキャンセルと再スケジューリングロジックを改善

**修正日**: 2026/04/21

### [BUG-014] Windows での CTRL+C でプログラムが停止しない

**問題**: Windows 上で直接 `python main.py` を実行すると、CTRL+C を押してもプログラムを終了できません。プログラムは正常に起動してルーティングサーバー情報を出力した後、CTRL+C は完全に反応せず、タスクマネージャーでプロセスを強制終了するしかありません。一方、`epsdk run` から起動した場合は正常に停止します――しかし `epsdk run` はサブプロセスモデルで実行されます。

**原因**: Hypercorn ASGI サーバーの `serve()` 関数内部で `signal.signal(SIGINT, handler)` を使用して独自の SIGINT ハンドラを登録し、Python のデフォルトの `KeyboardInterrupt` 処理メカニズムを上書きしています。`asyncio.create_task()` を使用して Hypercorn をバックグラウンドタスクとして起動すると、Hypercorn の内部シャットダウンフローは正常にトリガーされません（`worker_serve` モードを期待しているため）、CTRL+C シグナルは Hypercorn によって吸い取られますが、何らかのクリーンアップアクションも起こりません。

**影響バージョン**: [2.3.6 - 2.4.2]

**修正バージョン**: 2.4.3-dev.0

**修正内容**:
1. ASGI サーバーを Hypercorn から Uvicorn に変更（`pyproject.toml` の依存関係変更）
2. `uvicorn.Server._serve()` を直接使用してサーバーを起動し、`capture_signals()` 信号処理コンテキストマネージャーを**バイパス**
3. `server.should_exit = True` で優雅な停止を実現し、タイムアウト時はバックグラウンドタスクをキャンセル
4. 同時にサブプロセス実行モデルと `runtime/cleanup.py` クリアモジュールを削除（サブプロセスクリアメカニズムはもはや必要ありません）

**修正日**: 2026/04/28

### [BUG-018] サブプロセスモード `ep run <script>` でスクリプトがあるディレクトリのサブパッケージが見つからない

**問題**: `ep r .\main.py` を使用してスクリプトを非ホットリロードモードで実行する場合、スクリプトに相対インポート（例えば `from qg import ...`）があると、`No module named 'qg'` エラーが発生します。一方、`--reload` モードは正常に動作します。

**原因**: 非ホットリロードモードでは `runpy.run_path()` を直接使用してスクリプトを実行しますが、この関数はスクリプトがあるディレクトリを自動的に `sys.path` に追加しません。一方、`--reload` モードは `subprocess.Popen` を使用してサブプロセスとして実行し、サブプロセスは自動的に現在の作業ディレクトリを継承するため、`sys.path[0]` がスクリプトがあるディレクトリとなり、正常に動作します。

**影響バージョン**: 2.5.0 - 2.5.2-dev.0

**修正バージョン**: 2.5.2-dev.0

**修正内容**: `runpy.run_path()` を呼び出す前に、スクリプトがあるディレクトリを `sys.path[0]` に手動で挿入します。

**修正日**: 2026/06/27

### [BUG-019] SQL クエリビルダが合法なワイルドカードと列式を拒否する

**問題**: `SQLiteQueryBuilder` の `_build_select_sql()` はすべての SELECT 列に対して `_validate_identifier()` を呼び出します。この関数は厳格なホワイトリスト正規表現 `^[a-zA-Z_][a-zA-Z0-9_]*$` を使用しており、合法な SQL 構文が安全ではない列名として誤判定されます：

- `SELECT *` — `*` は SQL 標準のワイルドカード
- `SELECT COUNT(*)` — 集計関数
- `SELECT users.name` — 限定された列名
- `SELECT col AS alias` — 列の別名

その中でも `Select("*")` は Cron などのモジュールで使用されており、モジュールの `on_load` 実行に失敗し、モジュールが読み込めない状態になります。

**原因**: バージョン 2.4.6 で SQL インジェクション対策を強化し、`_validate_identifier()` のホワイトリスト検証を導入しました。この検証はすべての列名に適用されましたが、読み取り側（SELECT/ORDER BY）と書き込み側（INSERT/UPDATE）を区別していません。SELECT 列には複雑な SQL 式を許可すべきであり、単純な識別子のホワイトリスト制限を受けるべきではありません。

**影響バージョン**: 2.4.6 - 2.5.2-dev.1

**修正バージョン**: 2.5.2-dev.2

**修正内容**: SELECT/ORDER BY の列検証をホワイトリストモードからブラックリストモードに変更します：
1. 新しい `_validate_select_column()` 関数を追加し、SQL インジェクションの危険文字（`;` `'` `"` `--` `/*` `*/` `\x00` 改行コード）のみをブロック
2. 任意の合法な SQL 列式を許可（`*`、`table.*`、`table.column`、`COUNT(*)`、`col AS alias` など）
3. INSERT/UPDATE の列名は引き続き厳格なホワイトリスト検証（単純な識別子のみ許可）

**修正日**: 2026/06/29

### [BUG-020] _resolve_account() アカウント解釈の回帰（_accounts_data が未填充）

**問題**: バージョン 2.5.2 の設定システムのリファクタリング後、`AccountConfigClass` を宣言したマルチアカウントアダプタで `wait_reply`、`reply` などメッセージを送信する必要があるメソッドを呼び出すと、エラー `ValueError("未声明 AccountConfigClass，无法解析账户")` が発生します。アダプタが正しくマルチアカウント情報を設定していても、アカウント解釈は失敗したままです。

**原因**: バージョン 2.5.2-dev.5 で `_load_accounts()`（設定の読み取り + 検証 + `_accounts_data` の填充を担当）を `_ensure_accounts_exist()`（設定テンプレートの生成のみ）にリファクタリングしましたが、`_resolve_account()` はまだ `self._accounts_data is None` をチェックします。`_ensure_accounts_exist()` が `_accounts_data` を填充しなくなったため、このプロパティは常に `None` となり、`_resolve_account()` が事前に `(None, None)` を返してしまい、アカウント解釈が完全に失効します。

**根因の連鎖**:
```
_load_accounts() が削除された
  → __init__ で _accounts_data が填充されなくなった
    → _accounts_data が常に None になる
      → _resolve_account() で _accounts_data is None をチェック → return (None, None)
        → _resolve_account を呼ぶ下流（例: call_api）で None が渡される
          → エラーが発生する
```

**影響バージョン**: 2.5.2-dev.5 - 2.5.2

**修正バージョン**: 2.5.3

**修正内容**: `BaseAdapter.__init__` 内で、`_ensure_accounts_exist()` の後に `_accounts_data` の填充を復元します：
```python
if self.AccountConfigClass is not None:
    self._ensure_accounts_exist()
    self._accounts_data = self.accounts  # 填充を復元、データソースはリアルタイムで読み取られる accounts プロパティ
```
`_resolve_account()` のロジックは変更せず、完全に後方互換を維持します：
- `AccountConfigClass` を宣言しないアダプタ：`_accounts_data` は `None` のまま → `(None, None)` を返す
- `AccountConfigClass` を宣言しているアダプタ：`_accounts_data` が填充される → 正常に解釈
- `_load_accounts` を上書きしているか、`_accounts_data` を手動で設定しているアダプタ：`super().__init__()` の後に上書き、優先度が最も高い
