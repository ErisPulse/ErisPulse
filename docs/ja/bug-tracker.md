# バグ追跡器

このドキュメントは、ErisPulse SDK の既知のバグとその修正状況を、修正されたバージョンの日時順に記録しています。

> **読者の皆様へ**
> 完全に完璧なソフトウェアは存在せず、どんなに注意深い開発者でも小さなミスを残してしまうものです。本追跡リストに含まれるバグは、実際の動作に影響を与えるもののみを対象としています。あまりにも細かく、「軽微」のレベルにも達しないような欠点は、ここには含まれません。リストに「重大」の項目が多めに見えるかもしれませんが、これらのバグを公開して記録する目的は、トラブルの調査や遡及をスムーズにするためであり、不安を煽るためではありません。バグが見える化され、記録され、修正されることこそ、プロジェクトが着実に改善している証拠です。このリストを見て不安になる必要はありません。これはトラブル調査のためのツールであり、不安の原因ではありません。

> **リストの読み方 & 維持管理のルール**
> - 各バグの記録には、問題の説明、根本原因の分析、影響を受けるバージョン範囲、修正方法などの構造化されたフィールドが含まれており、アップグレード前に「影響バージョン」が現在使用しているバージョンをカバーしているかを検索することを推奨します。
> - バグの新規登録が必要な場合は、対応する位置に内容を追加し、下記のフィールド規格と重大度/タイプの分類に従ってください。

---

## フィールドの説明

### 必須フィールド

| フィールド | 説明 |
|------|------|
| **問題** | バグの外的現象、ユーザーが観察可能な異常現象。エラーメッセージや典型的なシナリオをできるだけ含めてください |
| **原因** | 根本原因の分析、具体的なコード欠陥を指す（複雑なシナリオには「根本原因の経路」図を含む） |
| **影響バージョン** | 影響を受けたバージョンの範囲、形式は `導入バージョン - 修正バージョン`（両端の dev バージョンを含む） |
| **修正バージョン** | このバグを修正した具体的なバージョン番号 |
| **修正内容** | 修正案の簡潔な説明、重要なコード変更点を含む |
| **修正日** | 修正バージョンに対応するリリース日、`YYYY/MM/DD` 形式を採用 |
| **重大性** | 下記「重大性の分類」に従って記載 |
| **タイプ** | 下記「タイプの分類」に従って記載、組み合わせ可能（例：`アダプター / ルーティング`） |

### 省略可能なフィールド

| フィールド | 説明 | 適用場面 |
|------|------|---------|
| **再現手順** | このバグを引き起こす最小限の再現手順 | 複雑なバグ、偶発的なバグには補足することを推奨 |
| **関連** | 関連する Issue / PR / Commit のリンク | 外部での議論記録がある場合に補足 |
| **リグレッションテスト** | 修正の検証、再発防止のためのテストケースの位置 | 対応する pytest テストケースを既に作成している場合に補足 |

## 严重性分级

| 標識 | 級別 | 判定基準 | 典型な現象 |
|------|------|---------|---------|
| 🔴 | 重大 | プロセスのクラッシュ、データの喪失/破損、コア機能が完全に使用不能、セキュリティの脆弱性 | OOM Kill、メッセージの送信失敗、モジュールのロード失敗、ホットリロードの失敗 |
| 🟡 | 中等 | 機能が異常だが回避方法がある、コア機能以外が失敗、偶発的な問題 | 状態の誤った判断、重複したトリガー、キャッシュの期限切れ、エラーメッセージの不正確 |
| 🟢 | 軽微 | コア機能に影響しない、コードの品質や体験の問題、潜在的なリスクが発生していない | 非推奨のAPI、無用のコード、警告ログの欠如 |

## 修正したバグ

### [BUG-001] イベントハンドラの重複登録によるイベントの多重処理

**問題**: `@message` / `@notice` などのデコレータを複数使用してハンドラを登録すると、同一イベントが複数回トリガーされ、コマンドが複数回実行されたり、ログが重複出力されたりする。

**原因**: `BaseEventHandler` がアダプターイベントバスにハンドラを登録する際に重複除去ロジックがなく、各デコレータがバスに1回ずつマウントされるため、イベント配信時に複数回呼び出される。

**影響バージョン**: 2.2.0-dev.0 - 2.2.1-dev.0

**修正バージョン**: 2.2.1-dev.0

**修正内容**: `BaseEventHandler` を最適化し、各イベントタイプがアダプターに1回だけハンドラを登録されるようにし、重複トリガーを回避。

**修正日**: 2025/08/18

**重大度**: 🔴 重大

**タイプ**: イベントシステム

---

### [BUG-002] Init コマンドのアダプター設定パスの型エラー

**問題**: `ep init` コマンドを使ってインタラクティブに初期化を行うと、アダプターの設定を選択した際に型エラーが発生する：

```
インタラクティブ初期化失敗: 'str' と 'str' の型に対してサポートされていない演算子
```

**原因**: 2.3.7 バージョンで設定ファイルパスを調整した際、メソッドのパラメータ型が一貫していない。`_configure_adapters_interactive_sync` は `str` 型のパラメータを受け取るが、内部で `Path` の `/` 操作でパスを結合している。

**影響バージョン**: 2.3.7 - 2.3.9-dev.1

**修正バージョン**: 2.3.9-dev.1

**修正内容**: `_configure_adapters_interactive_sync` メソッドのパラメータ型を `str` から `Path` に変更し、呼び出し時に `Path` オブジェクトを直接渡す。

**修正日**: 2026/03/23

**重大度**: 🟡 中等

**タイプ**: CLI

### [BUG-003] 再起動後にコマンドイベントが無効になる

**問題**: `sdk.restart()` を呼び出した後、`@command` で登録したコマンドがトリガーされなくなり、送信したコマンドに対してロボットが応答しなくなる。

**原因**: `adapter.shutdown()` がイベントバスをクリアした後、`BaseEventHandler` の `_linked_to_adapter_bus` 状態が `False` にリセットされていないため、`_process_event` メソッドが既にアダプターのバスにマウントされていると認識し、再マウント処理をスキップしてしまう。

**影響バージョン**: 2.2.x - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `_linked_to_adapter_bus` 状態を追跡する仕組みを導入し、`_clear_handlers()` でバス接続を切断した後、次の `register()` で自動的に再マウントされるようにし、shutdown/restart のシナリオに対応。

**修正日**: 2026/04/09

**重大度**: 🔴 重大

**タイプ**: イベントシステム

### [BUG-004] ライフサイクルイベントハンドラの未クリア

**問題**: `sdk.restart()` 後、古いライフサイクルイベントハンドラが依然として存在し、同じイベントが複数回処理される。

**原因**: `uninit()` 時に `lifecycle._handlers` 辞書がクリアされていないため、restart 後に古いハンドラと新しいハンドラが共存する。

**影響バージョン**: 2.3.0 - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `Uninitializer` のクリーンアップ処理の末尾（すべてのイベントが送信された後）、`lifecycle._handlers` をクリアする。

**修正日**: 2026/04/09

**重大度**: 🟡 中等

**タイプ**: ランタイム

### [BUG-005] Event.is_friend_add/is_friend_delete の detail_type が OB12 標準と不一致

**問題**: `Event.is_friend_add()` は `detail_type == "friend_add"` をチェックし、`Event.is_friend_delete()` は `detail_type == "friend_delete"` をチェックするが、OneBot12 標準では `detail_type` の値は `"friend_increase"` と `"friend_decrease"` である。`notice.py` の `on_friend_add`/`on_friend_remove` デコレータで使用されている値と不一致のため、デコレータで登録したハンドラがトリガーされた際に、対応する `is_friend_add()`/`is_friend_delete()` 判定メソッドは `False` を返す。

**原因**: `wrapper.py` で非標準の命名が使用され、`notice.py` では正しい OB12 標準の命名が使用されている。

**影響バージョン**: 実装以降

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `is_friend_add()` のマッチング値を `"friend_add"` から `"friend_increase"`、`is_friend_delete()` を `"friend_delete"` から `"friend_decrease"` に変更。

**修正日**: 2026/04/13

**重大度**: 🟡 中等

**タイプ**: イベントシステム

### [BUG-006] adapter.clear() が _started_instances をクリアしないことで再起動後の状態が不正になる

**影響バージョン**: 2.4.0-dev.1 - 2.4.2-dev.0

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `clear()` メソッドに `self._started_instances.clear()` を追加する。

**修正日**: 2026/04/13

**重大度**: 🟡 中等

**タイプ**: アダプター

### [BUG-007] command.wait_reply() で廃止された asyncio.get_event_loop() を使用

**問題**: `CommandHandler.wait_reply()` メソッドは `asyncio.get_event_loop()` を使って future を作成し、タイムスタンプを取得しているが、このメソッドは Python 3.10+ で廃止されている。非同期コンテキストでは `asyncio.get_running_loop()` を使用すべきである。同ファイルの `wrapper.py` の `wait_for()` メソッドで使用されている `get_running_loop()` と不一致である。

**原因**: 開発時に古い API を使用しており、後で追加された `wait_for()` は正しい API を使用しているが、古いコードを修正していない。

**影響バージョン**: 2.3.0-dev.0

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `command.py` の 2 か所の `asyncio.get_event_loop()` を `asyncio.get_running_loop()` に置き換える。

**修正日**: 2026/04/13

**重大度**: 🟢 軽微

**タイプ**: イベントシステム

### [BUG-008] Bot のオフラインイベントが shutdown 過程で繰り返し送信される

**問題**: `adapter.shutdown()` ですべてのアダプターを閉じる際に、`_update_bot_status()` が閉じるプロセスの中で繰り返し Bot オフラインイベントを送信し、同じ一連の Bot が複数回オフラインとマークされ、`adapter.bot.offline` ライフサイクルイベントが複数回トリガーされる。

**原因**: 2.4.0-dev.1 で導入された Bot 状態追跡システムが、`shutdown()` 間に「閉じ中」フラグを設定していないため、`_update_bot_status()` は通常のオフラインと閉じるプロセス中の連鎖オフラインを区別できない。

**影響バージョン**: 2.4.0-dev.1 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `AdapterManager` に `_is_being_shutdown` フラグを追加し、`shutdown()` 開始時に True に設定、終了時にクリアする。`_update_bot_status()` はこのフラグをチェックして、閉じるプロセス中の繰り返し送信をスキップする。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: アダプター

### [BUG-009] LazyModule の同期アクセスで BaseModule の初期化が完了していない

**問題**: ユーザーが同期コンテキストで LazyModule の属性にアクセスするとき、モジュールは `loop.create_task()` を使って非同期に初期化するが、待機しないため、属性アクセス時に初期化が完了していない可能性があり、競合状態が発生する。

**原因**: `_ensure_initialized()` は BaseModule に対して `loop.create_task(self._initialize())` を使用して初期化を開始した後、即座に返すため、初期化が完了していることを保証していない。

**影響バージョン**: 2.4.0-dev.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**: 同期コンテキストでは、BaseModule の初期化を `asyncio.run(self._initialize())` に変更し、初期化が完了してから返すようにする。透明プロキシの特性を維持し、ユーザーは同期/非同期の差異を意識する必要がない。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: ロードシステム

### [BUG-010] 複数スレッドでの設定システムの書き込みでデータが失われる

**問題**: 複数スレッド環境で、複数のスレッドが同時に `config.setConfig()` を呼び出すと、`_flush_config()` は読み取り-変更-書き込み操作が原子的ではないため、一部の書き込みが失われる可能性がある。

**原因**: `_flush_config()` は `RLock` を使用しているが、ファイルの読み取りと書き込みの間にはファイルロックの保護がなく、`_schedule_write` の Timer が複数回トリガーされて上書きされる可能性がある。

**影響バージョン**: 2.3.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**:
1. ファイルロック機構（`_file_lock`）を追加してファイル操作の原子性を保証
2. 一時ファイルに書き込んだ後、`os.replace`/`os.rename` で原子的にリネームする
3. `_schedule_write` の Timer のキャンセルと再スケジュールのロジックを改善

**修正日**: 2026/04/21

**重大度**: 🔴 重大

**タイプ**: 設定システム

### [BUG-011] Windows で CTRL+C でプログラムを停止できない

**問題**: Windows 上で `python main.py` を直接実行すると、CTRL+C でプログラムを終了できない。プログラムは正常に起動し、ルーティングサーバー情報を出力した後、CTRL+C は完全に反応せず、タスクマネージャーでプロセスを強制終了する必要がある。一方、`epsdk run` で起動した場合は正常に停止できるが、`epsdk run` はサブプロセスモデルで実行される。

**原因**: Hypercorn ASGI サーバーの `serve()` 関数内部で `signal.signal(SIGINT, handler)` を使って独自の SIGINT ハンドラを登録しており、Python のデフォルトの `KeyboardInterrupt` ハンドラの処理メカニズムを上書きしている。`asyncio.create_task()` で Hypercorn をバックグラウンドタスクとして起動すると、Hypercorn の内部のシャットダウンフローが正常にトリガーされない（`worker_serve` モードを想定しているため）、CTRL+C シグナルが Hypercorn に飲み込まれるが、クリーンアップ動作は発生しない。

**影響バージョン**: 2.3.6 - 2.4.2

**修正バージョン**: 2.4.3-dev.0

**修正内容**:
1. ASGI サーバーを Hypercorn から Uvicorn に切り替える（`pyproject.toml` 依存関係の変更）
2. `uvicorn.Server._serve()` を直接使ってサーバーを起動し、**`capture_signals()`** シグナル処理コンテキストマネージャーを**回避**する
3. `server.should_exit = True` を使って優雅な停止を実現し、タイムアウト後はバックグラウンドタスクをキャンセルする
4. 同期的に子プロセス実行モデルと `runtime/cleanup.py` クリーンアップモジュールを削除する（子プロセスのクリーンアップ機構は不要）

**修正日**: 2026/04/28

**重大度**: 🔴 重大

**タイプ**: CLI / ランタイム

### [BUG-012] ホットリスタート後に更新されたモジュールの Python コードが有効にならない

**問題**: `sdk.restart()` でソフトリスタートを実行した後、`epsdk install` でアップグレードされたモジュール/アダプターの新しいコード（追加された API ルートなど）が有効にならず、以前のバージョンのロジックが実行されたまま。完全にプロセスを再起動するまで最新のコードをロードできない。

**原因**: `_do_restart()` が再初期化時に `entry_point.load()` を呼び出すが、この関数は `sys.modules` からキャッシュされた古いモジュールオブジェクトを返すため、磁盤から最新のコードをロードしない。

**影響バージョン**: 早期バージョン - 2.4.3-dev.1

**修正バージョン**: 2.4.3-dev.1

**修正内容**: `uninit()` 後、`init()` 前に `sys.modules` にロードされたモジュール/アダプターのパッケージのキャッシュをクリアし、`entry_point.load()` が最新のコードをロードできるようにする。`_collect_top_level_modules()` と `_invalidate_module_cache()` ヘルパー関数を追加し、`top_level.txt` または entry-point value からトップレベルモジュール名を推定する。

**修正日**: 2026/05/03

**重大度**: 🔴 重大

**タイプ**: ロードシステム / ランタイム

### [BUG-030] 設定のウォッチャーの競合により setConfig の遅延書き込みが静かにデータを失う

**問題**: 複数のユーザーが `config.setConfig(key, value)`（デフォルト `immediate=False`）を使用した後、自分のモジュールの設定が `config.toml` に書き込まれず、他のモジュールの設定は正常に動作する。`immediate=True`（強制的に書き込み）を設定すると回避できる。動作時、書き込まれた設定は再起動後に失われ、起動時にテンプレート生成された設定は保持される。

**原因**: 2つの重なった欠陥：
1. **論理的欠陥**: `_watch_loop` が `_check_file_change()` が `True` を返した場合に無条件に `_dirty_keys.clear()` で全ての待機キーを破棄する。しかし、`_check_file_change()` は `!=` で mtime を比較するだけであり、フレームワーク自身の `_flush_config` が書き込み後に mtime を更新するが、ウォッチャーのスレッドはファイルの書き込みと mtime 代入の間（および粗いファイルシステム上）で mtime の差異を観測する可能性があり、外部の変更と誤って判断し、全ての待機キーを破棄する。
2. **スレッドの欠陥**: `_watch_loop` は `_write_timer`/`_dirty_keys` を操作する際に `_lock` を保持していないため、`setConfig`（`_dirty_keys` に書き込む際にロックを保持）、`_schedule_write`（`_write_timer` に書き込む際にロックを保持）とデータ競合がある。

**根本的な連鎖**:
```
モジュールA setConfig(immediate=True) → flush で書き込み、mtime が変わる
  → ユーザーモジュール setConfig(immediate=False) → _dirty_keys に入り、5秒後に書き込み
    → ワッチャーのルーニング、_check_file_change が先ほどの自身の書き込みの mtime 差異を観測
      → _dirty_keys.clear() → ユーザーモジュールの待機キーが静かに破棄される
        → 再起動後に設定が失われる
```

**影響バージョン**: 2.6.0 - 2.7.0

**修正バージョン**: 2.7.1

**修正内容**:
1. 新たに `_last_self_write_mtime` フィールドを追加。`_flush_config` が書き込み後にこの値を記録する。`_check_file_change` は mtime が変化した場合にこの値と比較し、一致すれば自身の書き込みと判断して `False` を返す
2. `_watch_loop` の全体を `_lock` で保持する。実際の外部変更の場合は _dirty_keys を保持（マージの意味）、次回の flush で外部内容とマージ（汚染されたキーが優先）、`_dirty_keys` をクリアしない
3. `getConfig`/`_check_cache_validity` パスは影響を受けない（reload は本来 dirty_keys をクリアしない）

**修正日**: 2026/08/06

**回帰テスト**: `tests/unit/test_unit_config.py` → `test_self_write_not_detected_as_external`、`test_external_change_preserves_dirty_keys`、`test_flush_merges_dirty_with_external`

### [BUG-032] 設定の遅延書き込み中に「書き込み後すぐに読み取り」で古い値が読み取られる

**問題**: `config.setConfig()`（デフォルト `immediate=False` で約5秒遅延書き込み）でピリオド区切りのキーを書き込んだ後、直ちにその**親/祖先ノード**（例：`set_erispulse_section("scope.actions.MyModule", {...})` の後で `get_erispulse_config()` を呼び出す）を読み取ると、以前の値が返り、書き込んだ子キーは「消えてしまい」、書き込み後にのみ表示される。スコープ設定のホット更新などの「書き込み-読み取り-書き込み」シナリオに影響される（2.8.0 テストプラグイン `/t_section` の用例が暴露）。

**原因**: `setConfig` はピリオド区切りのキーを**フラット形式**で待機キュー `_dirty_keys` に保存するが、`getConfig` の**正確なキー照合**のみが待機キューにヒットする。ツリー形式のパス照合（`getConfig("ErisPulse.scope")`）はキャッシュツリーのみを走り、待機値をマージしない—遅延書き込み（`_flush_config` が待機キューをキャッシュにマージし、キューをクリアするまで）の間、読み取り-書き込み-読み取りの断層が発生する。

**影響バージョン**: 2.6.0 - 2.8.0-dev.1

**修正バージョン**: 2.8.0-dev.1

**修正内容**: `getConfig` に待機マージの意味を導入する—① 精確に待機キーにヒットした場合は既存の動作を維持する；② 待機キーが照合キーの祖先である場合、最も長い待機祖先を取得し、残りのパスをその値のサブツリーに解析する；③ 待機キーが照合キーの子孫である場合、`_dirty_overlay` でサブツリーを構築し、キャッシュのサブツリーと深くマージする（`_deep_merge`、override が優先、元のキャッシュオブジェクトを変更しない）。待機キーがない場合は元の高速パスを走る、追加のオーバーヘッドなし。

**回帰テスト**: `tests/unit/test_unit_config.py` → `test_get_config_overlays_dirty_descendant`、`test_get_config_overlay_merges_with_cache_siblings`、`test_get_config_overlay_new_branch`、`test_get_config_dirty_ancestor_query`、`test_get_config_dirty_exact_key_still_wins`
