# バグ追跡ツール

本ドキュメントでは、ErisPulse SDK の既知のバグと修正状況を記録しています。

---

## 修正済みバグ

### [BUG-001] Init コマンドアダプター設定パスの型エラー

**問題**: `ep init` コマンドを使用したインタラクティブな初期化時、設定アダプターを選択すると型エラーが発生します：

```
Interactive init failed: unsupported operand type(s) for /: 'str' and 'str'
```

**原因**: 2.3.7 バージョンで設定ファイルパスを調整した際、メソッド引数の型が不一致でした。`_configure_adapters_interactive_sync` は `str` 型の引数を受け取りますが、内部では `Path` の `/` 演算子を使用してパスを連結しています。

**影響バージョン**: 2.3.7 - 2.3.9-dev.1

**修正バージョン**: 2.3.9-dev.1

**修正内容**: `_configure_adapters_interactive_sync` メソッドの引数型を `str` から `Path` に変更し、呼び出し時に直接 `Path` オブジェクトを渡すようにしました。

**修正日**: 2026/03/23

### [BUG-002] 再起動後にコマンドイベントが無効になる

**問題**: `sdk.restart()` を呼び出した後、`@command` で登録されたコマンドがトリガーできなくなります。コマンドを送信してもボットからの応答がないという症状が現れます。

**原因**: `adapter.shutdown()` でイベントバスがクリアされた後も、`BaseEventHandler` の `_linked_to_adapter_bus` 状態が `False` にリセットされず、`_process_event` メソッドは既にアダプターバスにアタッチされていると判断して再アタッチ処理をスキップしてしまいます。

**影響バージョン**: 2.2.x - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `_linked_to_adapter_bus` 状態の追跡を導入し、`_clear_handlers()` でバス接続を切断した後、次回の `register()` で自動的に再アタッチするようにしました。これにより shutdown/restart のシナリオに対応します。

**修正日**: 2026/04/09

### [BUG-003] ライフサイクルイベントハンドラのクリア漏れ

**問題**: `sdk.restart()` 後、旧のライフサイクルイベントハンドラが残存し、多重にトリガーされます。これにより同じイベントが複数回処理されることになります。

**原因**: `lifecycle._handlers` 辞書は `uninit()` 時に一度もクリアされておらず、restart 後に古いハンドラと新しいハンドラが同時に存在してしまいます。

**影響バージョン**: 2.3.0 - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `Uninitializer` のクリア処理の末尾（すべてのイベントが送信された後）、`lifecycle._handlers` をクリアするようにしました。

**修正日**: 2026/04/09

### [BUG-006] Event.is_friend_add/is_friend_delete の detail_type と OB12 標準の不一致

**問題**: `Event.is_friend_add()` は `detail_type == "friend_add"` をチェックしますが、OneBot12 標準では `detail_type` の値は `"friend_increase"` と `"friend_decrease"` と定義されています。`notice.py` 内の `on_friend_add`/`on_friend_remove` デコレータで使用される値と不一致であり、デコレータ経由で登録されたハンドラがトリガーされた際、対応する `is_friend_add()`/`is_friend_delete()` の判定メソッドが `False` を返してしまいます。

**原因**: `wrapper.py` で非標準の命名が使用されていましたが、`notice.py` は正しい OB12 標準の命名を使用していました。

**影響バージョン**: rq実装以来

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `is_friend_add()` のマッチ値を `"friend_increase"` に変更し、`is_friend_delete()` は `"friend_decrease"` に変更しました。

**修正日**: 2026/04/13

**修正バージョン**: 2.4.2-dev.1

### [BUG-008] command.wait_reply() が非推奨の asyncio.get_event_loop() を使用している

**問題**: `CommandHandler.wait_reply()` メソッドは `asyncio.get_event_loop()` を使用して future を作成し、タイムスタンプを取得します。このメソッドは Python 3.10+ で非推奨となり、非同期コンテキストでは `asyncio.get_running_loop()` を使用するべきです。同ファイル内の `wrapper.py` の `wait_for()` メソッドで使用されている `get_running_loop()` と不一致です。

**原因**: 開発時に旧版 API を使用しており、その後追加された `wait_for()` は正しい API を使用していましたが、旧コードへの修正が行われませんでした。

**影響バージョン**: 2.3.0-dev.0

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `command.py` 内の2箇所の `asyncio.get_event_loop()` を `asyncio.get_running_loop()` に置換しました。

**修正日**: 2026/04/13

### [BUG-009] Event.collect() で key が欠落している場合に黙ってスキップされる

**問題**: `Event.collect()` メソッドはフィールドリストを走査する際、特定のフィールド辞書に `key` が欠落していると、何もログや警告も出力せずにそのフィールドを黙ってスキップします。開発者がスペルミス（例: `"Key"` ではなく `"key"`）をした場合、フィールド全体が無言で無視され、処理フロー追跡が困難になります。

**原因**: 入力検証とエラーフィードバックが不足しています。

**影響バージョン**: 2.4.0-dev.4

**修正バージョン**: 2.4.2-dev.1

**修正内容**: スキップする前に、`key` が欠落しているフィールドの情報を `logger.warning()` で記録するようにしました。

**修正日**: 2026/04/13

### [BUG-010] LazyModule 同期アクセス BaseModule 导致未初始化完成

**問題**: ユーザーが同期コンテキストで遅延読み込みの BaseModule プロパティにアクセスした際、モジュールは `loop.create_task()` で非同期に初期化されますが待機されず、プロパティアクセス時に初期化が完了していない可能性があり、競合条件（race condition）を引き起こします。

**原因**: `_ensure_initialized()` は BaseModule に対して `loop.create_task(self._initialize())` を使用した後にすぐに戻るため、初期化の完了が保証されていません。

**影響バージョン**: 2.4.0-dev.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**: 同期コンテキスト内では、BaseModule の初期化を `asyncio.run(self._initialize())` に変更し、初期化が完了してから返すようにしました。透過プロキシ特性を維持し、ユーザーは同期/非同期の違いを意識する必要はありません。

**修正日**: 2026/04/21

### [BUG-011] 設定システムのマルチスレッド書き込みによりデータが失われる

**問題**: マルチスレッド環境では、複数のスレッドが同時に `config.setConfig()` を呼び出すと、`_flush_config()` の読み取り-変更-書き込み操作はアトミックではありません。一部の書き込みが失われる可能性があります。

**原因**: `_flush_config()` は `RLock` を使用していますが、ファイルの読み取りと書き込みの間にファイルロックによる保護がなく、`_schedule_write` の Timer が複数回トリガーされて上書きされる可能性があります。

**影響バージョン**: 2.3.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**:
1. ファイルロック機構（`_file_lock`）を追加し、ファイル操作のアトミック性を確保
2. 一時ファイルに書き込み、その後アトミックにリネーム（`os.replace`/`os.rename`）を使用
3. `_schedule_write` の Timer のキャンセルと再スケジューリングロジックを改善

**修正日**: 2026/04/21

### [BUG-012] SDK プロパティアクセスエラーのメッセージが不正確

1. 登録済みだが有効になっていない：モジュール/アダプターが有効になっていないことを通知
2. 完全に存在しない：名前のスペルミスを確認することを通知
同時に、元の AttributeError を再スローして、上位層でキャッチできるようにします。

**修正日**: 2026/04/21

### [BUG-014] Windows で CTRL+C がプログラムの停止に失敗する

**問題**: Windows で直接 `python main.py` を実行すると、CTRL+C を押してもプログラムが終了しません。プログラムは正常に起動してルーターサーバー情報を出力した後、CTRL+C に完全に反応しません。タスクマネージャーで強制終了するしかありません。一方、`epsdk run` で起動した場合は正常に停止します——ただし、`epsdk run` はサブプロセスモデルで実行されています。

**原因**: Hypercorn ASGI サーバーの `serve()` 関数内部で `signal.signal(SIGINT, handler)` を使用して独自の SIGINT ハンドラーを登録しており、Python のデフォルトの `KeyboardInterrupt` 処理機構を上書きしています。`asyncio.create_task()` を使用して Hypercorn をバックグラウンドタスクとして起動した場合、Hypercorn の内部シャットダウンフローは正常にトリガーされません（`worker_serve` モードを想定しているため）、CTRL+C 信号は Hypercorn によって処理されますが、何もクリーンアップアクションが起こりません。

**影響バージョン**: [2.3.6 - 2.4.2]

**修正バージョン**: 2.4.3-dev.0

**修正内容**:
1. ASGI サーバーを Hypercorn から Uvicorn に変更（`pyproject.toml` 依存関係の変更）
2. `uvicorn.Server._serve()` を直接使用してサーバーを起動し、`capture_signals()` 信号処理コンテキストマネージャーを**迂回**します
3. `server.should_exit = True` で優雅に停止し、タイムアウトの場合はバックグラウンドタスクをキャンセルします
4. サブプロセス実行モデルと `runtime/cleanup.py` クリアモジュールを同期的に削除（サブプロセスクリアメカニズムはもう必要ありません）

**修正日**: 2026/04/28

### [BUG-015] モジュール読み込み戦略の並べ替えロジックエラー

**問題**: `ModuleLoadStrategy` はモジュールの初期化優先順位を宣言するために `priority` フィールドを提供しますが、読み込み戦略の実装にミスがあり、モジュールが期待される優先順序順に初期化されず、実際には `entry_points()` のデフォルト順序で読み込まれます。モジュール間に読み込み依存がある場合、`priority` を使用して正しい初期化順序を確保できません。

**原因**: 読み込み戦略の実装において並べ替えロジックが間違っており、`initialize_modules()` が `priority` を使用してモジュールリストをソートしていません。

**影響バージョン**: 2.3.4 - 2.4.5-dev.2

**修正バージョン**: 2.4.5-dev.3

**修正内容**: `initialize_modules()` でループする前に、`priority` で降順にソートされたモジュールリストを使用します。同 `priority` のモジュールは元の相対順序を維持します（安定ソート）。

**修正日**: 2026/05/15

**修正日**: 2026/05/15

### [BUG-017] 設定ファイルパスが作業ディレクトリに依存する

**影響バージョン**: 2.3.7 - 2.4.5-dev.3

**修正日**: 2026/05/15

### [BUG-018] サブプロセスモード `ep run <script>` でスクリプトのサブパッケージが見つからない

**問題**: `ep r .\main.py` を使用して非ホットリロードモードでスクリプトを実行する場合、スクリプトに相対インポート（例: `from qg import ...`）があると、`No module named 'qg'` エラーが発生します。一方、`--reload` モードは正常に動作します。

**原因**: 非ホットリロードモードは `runpy.run_path()` を直接呼び出してスクリプトを実行しますが、この関数はスクリプトがあるディレクトリを `sys.path` に自動的に追加しません。一方、`--reload` モードは `subprocess.Popen` サブプロセスを使用して実行され、サブプロセスは現在の作業ディレクトリを継承するため `sys.path[0]` がスクリプトがあるディレクトリになり、正常に動作します。

**影響バージョン**: 2.5.0 - 2.5.2-dev.0

**修正バージョン**: 2.5.2-dev.0

**修正内容**: `runpy.run_path()` を呼び出す前に、手動でスクリプトがあるディレクトリを `sys.path[0]` に挿入するようにしました。

**修正日**: 2026/06/27

### [BUG-019] SQL クエリビルダーが有効なワイルドカードと列式を拒否する

**問題**: `SQLiteQueryBuilder` の `_build_select_sql()` はすべての SELECT 列に対して `_validate_identifier()` を呼び出します。この関数は厳格なホワイトリスト正規表現 `^[a-zA-Z_][a-zA-Z0-9_]*$` を使用するため、正当な SQL 構文が安全でない列名と誤判別されます：

- `SELECT *` — `*` は SQL 標準のワイルドカード
- `SELECT COUNT(*)` — 集合関数
- `SELECT users.name` — 限定された列名
- `SELECT col AS alias` — 列のエイリアス

特に `Select("*")` は Cron などのモジュールで使用されているため、モジュールの `on_load` 実行に失敗し、モジュールの読み込みができなくなります。

**原因**: 2.4.6 バージョンで SQL インジェクション対策を強化し、`_validate_identifier()` というホワイトリスト検証を導入しました。この検証はすべての列名に適用されましたが、読み取り側（SELECT/ORDER BY）と書き込み側（INSERT/UPDATE）を区別していません。SELECT 列では複雑な SQL 式が許可されるべきであり、単純な識別子のホワイトリスト制限を受けてはなりません。

**影響バージョン**: 2.4.6 - 2.5.2-dev.1

**修正バージョン**: 2.5.2-dev.2

**修正内容**: SELECT/ORDER BY の列検証をホワイトリストモードからブラックリストモードに変更しました：
1. 新しい `_validate_select_column()` 関数を作成し、SQL インジェクションの危険文字（`;` `'` `"` `--` `/*` `*/` `\x00` 改行）のみを遮断します
2. 任意の正当な SQL 列式（`*`、`table.*`、`table.column`、`COUNT(*)`、`col AS alias` など）を許可します
3. INSERT/UPDATE の列名は引き続き厳格なホワイトリスト検証を維持します（単純な識別子のみ許可）

**修正日**: 2026/06/29
