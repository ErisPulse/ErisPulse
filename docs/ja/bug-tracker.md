# バグ追跡器

このドキュメントは、ErisPulse SDK の既知のバグとその修正状況を、修正されたバージョンの日付順に記録しています。

> **読者の皆様へ**
> どんなソフトウェアにも完璧さは存在せず、どんなに注意深い開発者でも小さなミスを残してしまうものです。本追跡リストに収録されているのは、実行に実際の影響を与える問題だけです。あまりにも細かくて「軽微」の等級にも達しないような些細な欠陥はここには含まれません。リストに「重大」の項目が多めに見えるかもしれませんが、これらのバグを公開記録にすることは、トラブルの調査と再現をスムーズにするためであり、不安を煽るためではありません。見える化され、記録され、修正された問題こそが、プロジェクトが常に改善されている証拠です。このリストを見ても心配する必要はありません。これはトラブル調査のためのツールであり、恐怖の原因ではありません。

> **読み方と維持の規約**
> - 各バグの記録には、問題の説明、根本原因分析、影響を受けたバージョン範囲、修正方法などの構造化されたフィールドが含まれています。アップグレードする前に、影響を受けたバージョンが現在使用しているバージョンをカバーしているかどうかを確認することを推奨します。
> - バグの新規追加が必要な場合は、対応する位置に内容を追加し、以下のフィールド規格と重大度/タイプ分類に従ってください。

## フィールドの説明

### 必須フィールド

| フィールド | 説明 |
|------|------|
| **問題** | バグの外観、ユーザーが観察できる異常現象。エラーメッセージや典型的なシナリオをできるだけ詳しく記述してください |
| **原因** | 具体的なコードの欠陥に至る根本原因分析（複雑なシナリオには「根本原因の経路」の図示も含む） |
| **影響バージョン** | 影響を受けたバージョンの範囲、形式 `導入バージョン - 修正バージョン`（両端の dev バージョンを含む） |
| **修正バージョン** | そのバグを修正した具体的なバージョン番号 |
| **修正内容** | 修正方法の簡潔な説明、重要なコード変更点を含む |
| **修正日** | 対応する修正バージョンのリリース日、`YYYY/MM/DD` 形式で |
| **重大度** | 下記の「重大度分類」に従って記載 |
| **タイプ** | 下記の「タイプ分類」に従って記載、複数選択可能（例: `アダプタ / ルーティング`） |

### 省略可能なフィールド

| フィールド | 説明 | 適用場面 |
|------|------|---------|
| **再現手順** | そのバグを引き起こす最小限の再現手順 | 複雑なバグ、偶発的なバグには推奨 |
| **関連** | 関連する Issue / PR / Commit リンク | 外部の議論記録がある場合に追加 |
| **リグレッションテスト** | 修正の検証、再発防止のためのテストケースの位置 | 対応する pytest 用例を書いた場合に追加 |

## 重大度分類

| 標識 | 等級 | 判定基準 | 典型的な現象 |
|------|------|---------|---------|
| 🔴 | 重大 | プロセスのクラッシュ、データの損失/破損、コア機能の完全な不可用、セキュリティの脆弱性 | OOM Kill、メッセージの送信不可、モジュールのロード不可、ホットリロード失敗 |
| 🟡 | 中等 | 機能の異常だが回避方法がある、コア機能以外の機能が失敗、偶発的な問題 | 状態の判断ミス、繰り返し発動、キャッシュの期限切れ、エラーメッセージの不正確 |
| 🟢 | 軽微 | コア機能に影響しない、コード品質や体験の問題、潜在的なリスクが発生していない | 非推奨API、デッドコード、警告ログの欠落 |

## 修正済みのバグ

### [BUG-001] イベントハンドラの重複登録によりイベントが複数回処理される

**問題**: `@message` / `@notice` などのデコレータを複数使用してハンドラを登録すると、同じイベントが複数回トリガーされ、コマンドが複数回実行されたり、ログが重複して出力されたりします。

**原因**: `BaseEventHandler` がアダプタのイベントバスにハンドラを登録する際に重複除去のロジックがなく、各デコレータがバスに1回ずつ登録され、イベント配信時に複数回呼び出されます。

**影響バージョン**: 2.2.0-dev.0 - 2.2.1-dev.0

**修正バージョン**: 2.2.1-dev.0

**修正内容**: `BaseEventHandler` を最適化し、各イベントタイプがアダプタに1回だけハンドラを登録されるようにし、重複トリガーを防ぎます。

**修正日**: 2025/08/18

**重大度**: 🔴 重大

**タイプ**: イベントシステム

---

### [BUG-002] Init コマンドのアダプタ設定パスの型エラー

**問題**: `ep init` コマンドを使用してインタラクティブに初期化を行うと、アダプタの設定を選択すると型エラーが発生します：

```
インタラクティブな初期化が失敗しました: 'str' と 'str' の演算子 '/' はサポートされていません
```

**原因**: 2.3.7 バージョンで設定ファイルのパスを調整した際に、メソッドの引数の型が一貫していません。`_configure_adapters_interactive_sync` は `str` 型の引数を受け取りますが、内部で `Path` の `/` 演算子を使ってパスを結合しています。

**影響バージョン**: 2.3.7 - 2.3.9-dev.1

**修正バージョン**: 2.3.9-dev.1

**修正内容**: `_configure_adapters_interactive_sync` メソッドの引数の型を `str` から `Path` に変更し、呼び出し時に `Path` オブジェクトを直接渡すようにします。

**修正日**: 2026/03/23

**重大度**: 🟡 中等

**タイプ**: CLI

### [BUG-003] 再起動後にコマンドイベントが無効になる

**問題**: `sdk.restart()` を呼び出した後、`@command` で登録したコマンドがトリガーされなくなり、コマンドを送信してもロボットが応答しない状態になります。

**原因**: `adapter.shutdown()` がイベントバスをクリアした後、`BaseEventHandler` の `_linked_to_adapter_bus` 状態が `False` にリセットされていないため、`_process_event` メソッドはすでにアダプタのバスに接続されていると判断し、再接続処理をスキップします。

**影響バージョン**: 2.2.x - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `_linked_to_adapter_bus` 状態を追跡する仕組みを導入し、`_clear_handlers()` でバス接続を切断した後、次回の `register()` で自動的に再接続するようにし、shutdown/restart のシナリオに対応します。

**修正日**: 2026/04/09

**重大度**: 🔴 重大

**タイプ**: イベントシステム

### [BUG-004] ライフサイクルイベントハンドラがクリアされない

**問題**: `sdk.restart()` の後、古いライフサイクルイベントハンドラがまだ存在し、同じイベントが複数回処理されるようになります。

**原因**: `uninit()` 時に `lifecycle._handlers` 辞書がクリアされておらず、restart 後に古いハンドラと新しいハンドラが同時に存在します。

**影響バージョン**: 2.3.0 - 2.4.0-dev.2

**修正バージョン**: 2.4.0-dev.3

**修正内容**: `Uninitializer` のクリーンアップ処理の末尾（すべてのイベントが送信された後）、`lifecycle._handlers` をクリアします。

**修正日**: 2026/04/09

**重大度**: 🟡 中等

**タイプ**: 実行時

### [BUG-005] Event.is_friend_add/is_friend_delete の detail_type が OB12 標準と一致しない

**問題**: `Event.is_friend_add()` は `detail_type == "friend_add"` をチェックし、`Event.is_friend_delete()` は `detail_type == "friend_delete"` をチェックしますが、OneBot12 標準で定義されている `detail_type` の値は `"friend_increase"` と `"friend_decrease"` です。`notice.py` で使用されている `on_friend_add`/`on_friend_remove` デコレータの値と一致しないため、デコレータで登録したハンドラがトリガーされた際に、対応する `is_friend_add()`/`is_friend_delete()` 判定メソッドは `False` を返します。

**原因**: `wrapper.py` では非標準の命名が使用されており、`notice.py` では正しい OB12 標準の命名が使用されています。

**影響バージョン**: 実装以降

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `is_friend_add()` のマッチング値を `"friend_add"` から `"friend_increase"` に、`is_friend_delete()` のマッチング値を `"friend_delete"` から `"friend_decrease"` に変更します。

**修正日**: 2026/04/13

**重大度**: 🟡 中等

**タイプ**: イベントシステム

**修正バージョン**: 2.4.2-dev.1

### [BUG-007] command.wait_reply() が非推奨の asyncio.get_event_loop() を使用している

**問題**: `CommandHandler.wait_reply()` メソッドは `asyncio.get_event_loop()` を使用して future を作成し、タイムスタンプを取得していますが、このメソッドは Python 3.10+ で非推奨であり、非同期コンテキストでは `asyncio.get_running_loop()` を使用する必要があります。同ファイルの `wrapper.py` の `wait_for()` メソッドでは `get_running_loop()` が使用されていますが、古いコードは更新されていません。

**原因**: 開発時に古い API を使用しており、後で追加された `wait_for()` は正しい API を使用していますが、古いコードをリバースエンジニアリングして修正していません。

**影響バージョン**: 2.3.0-dev.0

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `command.py` の 2 か所の `asyncio.get_event_loop()` を `asyncio.get_running_loop()` に置き換えます。

**修正日**: 2026/04/13

**重大度**: 🟢 軽微

**タイプ**: イベントシステム

### [BUG-008] Bot のオフラインイベントが shutdown 過程で繰り返し送信される

**問題**: `adapter.shutdown()` を呼び出してすべてのアダプタを閉じる際、`_update_bot_status()` が閉じるプロセス中に Bot のオフラインイベントを繰り返し送信し、同じ一連の Bot が複数回オフラインとしてマークされ、`adapter.bot.offline` ライフサイクルイベントが複数回トリガーされます。

**原因**: 2.4.0-dev.1 で導入された Bot 状態の追跡システムは、`shutdown()` の間の「閉じ中」フラグを設定しておらず、`_update_bot_status()` は通常のオフラインと閉じるプロセス中の連鎖的なオフラインを区別できません。

**影響バージョン**: 2.4.0-dev.1 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.1

**修正内容**: `AdapterManager` に `_is_being_shutdown` フラグを追加し、`shutdown()` の開始時に True に設定し、終了時にクリアします。`_update_bot_status()` はこのフラグをチェックして、閉じるプロセス中の繰り返し送信をスキップします。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: アダプタ

### [BUG-009] LazyModule の同期アクセスで BaseModule が初期化が完了していない

**問題**: ユーザーが同期コンテキストで LazyModule の BaseModule 属性にアクセスする場合、モジュールは `loop.create_task()` を使用して非同期に初期化しますが、待機せずに返すため、属性アクセス時に初期化が完了していない可能性があり、競合状態が発生します。

**原因**: `_ensure_initialized()` は BaseModule に対して `loop.create_task(self._initialize())` を使用して初期化を開始した後、即座に返り、初期化が完了したことを保証していません。

**影響バージョン**: 2.4.0-dev.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**: 同期コンテキストでは、BaseModule の初期化を `asyncio.run(self._initialize())` に変更し、初期化が完了してから返すようにします。透明なプロキシ特性を維持し、ユーザーは同期/非同期の違いを意識する必要はありません。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: ローディングシステム

### [BUG-010] 複数スレッドでの設定書き込みによりデータが失われる

**問題**: 多スレッド環境で複数のスレッドが同時に `config.setConfig()` を呼び出す場合、`_flush_config()` の読み取り-変更-書き込み操作は原子的ではないため、一部の書き込みが失われる可能性があります。

**原因**: `_flush_config()` は `RLock` を使用していますが、ファイルの読み取りと書き込みの間にファイルロックの保護がなく、`_schedule_write` の Timer が複数回トリガーされて上書きされる可能性があります。

**影響バージョン**: 2.3.0 - 2.4.2-dev.1

**修正バージョン**: 2.4.2-dev.2

**修正内容**:
1. ファイルロックメカニズム（`_file_lock`）を追加してファイル操作の原子性を確保します
2. 一時ファイルに書き込んだ後、原子的なリネーム（`os.replace`/`os.rename`）を行います
3. `_schedule_write` の Timer のキャンセルと再スケジュールのロジックを改善します

**修正日**: 2026/04/21

**重大度**: 🔴 重大

**タイプ**: 設定システム

### [BUG-011] Windows で CTRL+C でプログラムを停止できない

**問題**: Windows で `python main.py` を直接実行すると、CTRL+C を押してもプログラムを終了できません。プログラムは正常に起動し、ルーティングサーバーの情報を出力した後、CTRL+C は完全に反応せず、タスクマネージャーで強制的にプロセスを終了する必要があります。一方、`epsdk run` で起動した場合は正常に停止できます。ただし、`epsdk run` はサブプロセスモデルで実行されます。

**原因**: Hypercorn ASGI サーバーの `serve()` 関数は内部で `signal.signal(SIGINT, handler)` を使用して独自の SIGINT ハンドラを登録しており、Python のデフォルトの `KeyboardInterrupt` ハンドラを上書きしています。`asyncio.create_task()` を使用して Hypercorn をバックグラウンドタスクとして起動すると、Hypercorn の内部のシャットダウンフローが正常にトリガーされません（`worker_serve` モードを期待しているため）、CTRL+C シグナルは Hypercorn に飲み込まれますが、クリーンアップ処理は実行されません。

**影響バージョン**: 2.3.6 - 2.4.2

**修正バージョン**: 2.4.3-dev.0

**修正内容**:
1. ASGI サーバーを Hypercorn から Uvicorn に切り替えます（`pyproject.toml` の依存関係を変更）
2. `uvicorn.Server._serve()` を直接使用してサーバーを起動し、**`capture_signals()` シグナル処理コンテキストマネージャーを回避**します
3. `server.should_exit = True` を使用して優雅な停止を実現し、タイムアウト後はバックグラウンドタスクをキャンセルします
4. サブプロセス実行モデルと `runtime/cleanup.py` クリーンアップモジュールを同期的に削除します（サブプロセスのクリーンアップメカニズムは不要になります）

**修正日**: 2026/04/28

**重大度**: 🔴 重大

**タイプ**: CLI / 実行時

### [BUG-012] ホットリスタート後に更新されたモジュールの Python コードが有効にならない

**問題**: `sdk.restart()` を使用してソフトリスタートした後、`epsdk install` でアップグレードされたモジュール/アダプタの新しいコード（追加された API ルートなど）が有効にならず、古いバージョンのロジックが実行されます。最新のコードを読み込むには、プロセスを完全に再起動する必要があります。

**原因**: `_do_restart()` が再初期化時に `entry_point.load()` を呼び出しますが、この関数は `sys.modules` からキャッシュされた古いモジュールオブジェクトを返し、ディスクから再読み込みしません。

**影響バージョン**: 初期バージョン - 2.4.3-dev.1

**修正バージョン**: 2.4.3-dev.1

**修正内容**: `uninit()` 後、`init()` 前に `sys.modules` にロードされたモジュール/アダプタパッケージのキャッシュをクリアし、`entry_point.load()` が最新のコードをディスクから読み込むようにします。`_collect_top_level_modules()` と `_invalidate_module_cache()` の補助メソッドを追加し、`top_level.txt` または entry-point value からトップレベルモジュール名を推定します。

**修正日**: 2026/05/03

**重大度**: 🔴 重大

**タイプ**: ローディングシステム / 実行時

### [BUG-026] notice/request イベントの reply の送信先が誤って推定される

**問題**: グループ通知イベント（例：メンバーのグループ加入 `group_member_increase`）で `event.reply()` を呼び出すと、メッセージはイベントをトリガーしたユーザーのプライベートチャットに送信され、イベントが発生したグループには送信されません。友達通知イベントも同様で、返信先が間違える可能性があります。

**原因**: `infer_receive_type()` はイベントの `detail_type` をそのまま会話タイプとして返しています。message イベントでは正しいです（`detail_type` の値 `private`/`group` が会話タイプです）、しかし notice/request イベントの `detail_type` は語義のサブタイプ（例：`group_member_increase`、`friend_increase`）であり、会話タイプではありません。その後の `convert_to_send_type()` と `get_id_field()` はマッピング表にその値が見つからないため、デフォルトの `"user"` / `"user_id"` に戻り、返信先が間違えられます。

**根本原因の経路**:
```
notice イベント detail_type="group_member_increase"
  → infer_receive_type() は "group_member_increase" をそのまま返す
    → convert_to_send_type("group_member_increase") はマッピング表にないため "user" に戻る
    → get_id_field("group_member_increase") はマッピング表にないため "user_id" に戻る
      → target_id = event["user_id"]  ← 新メンバーのプライベートチャット（グループではなく）
```

**影響バージョン**: 全バージョン

**修正バージョン**: 2.7.0-dev.3

**修正内容**: `infer_receive_type()` に判断を追加します。`detail_type` が既知の会話タイプ（標準タイプまたはカスタムタイプ）である場合にのみ、そのまま返します。それ以外は、ID フィールド（`group_id` / `channel_id` / `user_id` など）に基づいて正しい会話タイプを推定します。

**リグレッションテスト**: `tests/unit/test_unit_session_type.py` → `TestNoticeRequestTypeInference`（10 テストケース）

**修正日**: 2026/07/29

**重大度**: 🟢 軽微

**タイプ**: イベントシステム

### [BUG-027] ルーティングのリクエスト制限のクリーンアップタスクが固定ウィンドウを使用して長時間のリクエスト制限ルールが無効になる

**問題**: ルーティングのリクエスト制限を長時間のルール（例：`100/hour`、`{"requests": 100, "window": 3600}`）に設定すると、リクエスト制限は無効になり、実際の動作は `100/minute` に近い（1時間で約 6000 回のリクエストが許可される）ため、予想される時間単位の保護機能はまったく機能しません。

**原因**: `_apply_rate_limit` は各ルーティングの実際の `window`（最大 3600 秒）を解析します。各リクエストのチェックも確かにそのウィンドウを使用します。しかし、バックグラウンドのクリーンアップタスク `_cleanup_expired_rate_limits` は、すべてのルーティングの統一クリーンアップ閾値として固定定数 `DEFAULT_RATE_LIMIT_WINDOW_SECS`（60 秒）を使用しています。したがって、`100/hour` ルーティングでは 60 秒前のタイムスタンプがクリーンアップタスクによって早めにクリアされ、1 時間のウィンドウ内では常に 1 分間の記録しか蓄積されず、リクエスト制限が大幅に弱まります。

**根本原因の経路**:
```
_apply_rate_limit は window=3600（100/hour）を解析する
  → per-request 検査は 3600s でタイムスタンプを保持する（正しい）
  → しかし _cleanup_expired_rate_limits は固定 max_window=60s を使用してクリーンアップする
    → 60 秒前のタイムスタンプがすべてクリアされる
      → 1 時間のウィンドウ内では常に最近 1 分間の記録しか残らない
        → 100/hour は実際には ~100/minute に退化（約 60 倍緩和）
```

**影響バージョン**: 2.6.0-dev.0 - 2.7.0-dev.4

**修正バージョン**: 2.7.0-dev.5

**修正内容**: 新たに `_rate_limit_windows: dict[str, int]` を追加し、store キーごとに各ルーティングの実際のウィンドウを記録します。`_apply_rate_limit` が最初にエントリを作成する際にウィンドウを書き込みます。`_cleanup_expired_rate_limits` は各キーの自身のウィンドウでクリーンアップするように変更します（存在しない場合はデフォルト値に回帰）。クリーンアップでエントリの削除と `stop()` の際の同期維持は2つの辞書で行います。

**修正日**: 2026/07/31

**リグレッションテスト**: `tests/unit/test_unit_router.py` → `TestRateLimit::test_cleanup_respects_per_route_window`

**重大度**: 🔴 重大

**タイプ**: ルーティング

### [BUG-029] 設定監視タスクが半完成の TOML をブロードキャストし、例外を静かに飲み込む

**問題**: ユーザーが `config.toml` を保存中に（一時的な構文エラーを生じる）作業を中断すると、設定監視バックグラウンドスレッドは mtime の変化を検出し、設定を再読み込みしますが、読み込みに失敗しても空の設定 `{}` で `config.updated` イベントを発行し、アダプタ/モジュールの `on_config_update` は空の設定を受け取り、すべての設定項目がリセットされたと誤って判断してデフォルト値に復帰します。さらに、監視ループは `except Exception: pass` を使用してすべての例外を静かに飲み込み、watcher の障害を調査できません。

**原因**: 2 つの欠陥が重なっています：
1. `_load_config` は TOML 構文エラー/権限エラー/その他のエラー時に `self._cache` を `{}` に上書きしますが、バックグラウンド監視スレッドの `_watch_loop` とキャッシュの有効期限チェックの `_check_cache_validity` は `_load_config()` の呼び出し後に**無条件**で `_emit_config_updated()` を実行し、"読み込みに失敗した空のキャッシュ"を真の変更としてブロードキャストします。
2. `_watch_loop` の `except Exception` はログを一切記録しません。

**根本原因の経路**:
```
ユーザーが保存中に中断 → TOML 構文エラー
  → _load_config() は _cache = {} に上書きする
    → _watch_loop は無条件で _emit_config_updated(new_config={})
      → アダプタ/モジュール on_config_update は空の設定を受け取る
        → 設定がリセットされたと誤って判断し、デフォルト値に復帰する
```

**影響バージョン**: 2.6.2-dev.1 - 2.7.0-dev.4

**修正バージョン**: 2.7.0-dev.5

**修正内容**:
1. `_load_config` は `bool` を返すように変更します。TOML 構文エラー/権限エラー/その他のエラーの場合は**前回の有効なキャッシュを保持**します（`{}` に上書きしない）、診断ログを記録するだけで `False` を返します
2. `_watch_loop` と `_check_cache_validity` は `_load_config()` が `True` を返した場合にのみ `config.updated` を発行します
3. `_watch_loop` の `except Exception` は `warning` レベルで記録するように変更します（新しい i18n キー `core.config.watcher_error` を追加し、5 言語で同期）

**修正日**: 2026/07/31

**リグレッションテスト**: `tests/unit/test_unit_config.py` → `test_malformed_toml_preserves_last_valid_cache`、`test_permission_denied_logs_clear_message`（更新してキャッシュの保持と `False` の返り値を検証する）
