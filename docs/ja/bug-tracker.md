# バグ追跡器

本ドキュメントでは、ErisPulse SDK の既知のバグとその修正状況を、修正されたバージョンの日付順に記録しています。

> **読者の皆様へ**
> どんなソフトウェアにも完璧さは存在せず、どんなに注意深く開発者でも小さなミスを残す可能性があります。本追跡リストに記載されているのは、実際の動作に影響を与える問題のみです。「軽微」レベルにも満たない、些細な欠点はここには含まれません。リストに「重大」が多めに記載されているように見えるかもしれませんが、バグを公開記録に残す目的は、トラブルの調査と再現をスムーズにするためであり、不安を煽るためではありません。バグが見える化され、記録され、修正されるということは、プロジェクトが継続的に改善されている証拠です。このリストを見て不安になる必要はありません。これはトラブル解決のためのツールであり、不安の原因ではありません。

> **読む方法と維持のルール**
> - 各バグの記録には、問題の説明、根本原因の分析、影響を受けたバージョン範囲、修正方法などの構造化されたフィールドが含まれています。アップグレードする前に、「影響を受けたバージョン」が現在使用しているバージョンをカバーしているかを確認することをお勧めします。
> - 新しいバグの項目を追加する場合は、対応する位置に内容を追加し、以下のフィールド規格と重大度/タイプの分類に従ってください。

---

## フィールドの説明

### 必須フィールド

| フィールド | 説明 |
|------|------|
| **問題** | バグの外観、ユーザーが観察できる異常現象。エラーメッセージや典型的なシナリオをできるだけ具体的に記述してください。|
| **原因** | 根本原因の分析、具体的なコードの欠陥を指します（「根本原因の経路」図は複雑なシナリオ用）。|
| **影響を受けたバージョン** | 影響を受けたバージョンの範囲、形式は「導入されたバージョン - 修正されたバージョン」（両端の dev バージョンを含む）。|
| **修正されたバージョン** | このバグを修正した具体的なバージョン番号。|
| **修正内容** | 修正方法の簡潔な説明、重要なコード変更点を含む。|
| **修正日** | 対応する修正バージョンのリリース日、形式は `YYYY/MM/DD`。|
| **重大度** | 下記「重大度の分類」に従って記載。|
| **タイプ** | 下記「タイプの分類」に従って記載、複数指定可（例：`アダプタ / ルーティング`）。|

### 任意フィールド

| フィールド | 説明 | 適用場面 |
|------|------|---------|
| **再現手順** | このバグを引き起こす最小限の再現手順 | 複雑なバグ、偶発性バグには推奨。|
| **関連** | 関連する Issue / PR / Commit リンク | 外部の議論記録がある場合に追加。|
| **回帰テスト** | 修正の検証、再発防止のためのテストケースの位置 | pytest 用のテストケースが作成されている場合に追加。|

## 重大度の分類

| 記号 | 級別 | 判定基準 | 典型的な現象 |
|------|------|---------|---------|
| 🔴 | 重大 | プロセスのクラッシュ、データの失われや破損、コア機能が完全に使用不能、セキュリティの脆弱性 | OOM Kill、メッセージの送信不可、モジュールのロード不可、ホットリロードの失敗 |
| 🟡 | 中等 | 機能の異常だが回避経路あり、コア機能が失効、偶発的な問題 | 状態の判断ミス、繰り返しの発動、キャッシュの期限切れ、エラーメッセージの不正確 |
| 🟢 | 軽微 | コア機能に影響しない、コード品質や体験の問題、潜在的なリスクが発生していない | 非推奨の API、デッドコード、警告ログの欠如 |

## 修正済みのバグ

### [BUG-001] イベントハンドラの重複登録によりイベントが複数回処理される

**問題**: 複数の `@message` / `@notice` などのデコレータを使ってハンドラを登録すると、同じイベントが複数回トリガーされ、コマンドが複数回実行されたり、ログが重複出力される。

**原因**: `BaseEventHandler` がアダプタのイベントバスにハンドラを登録する際に重複チェックがなく、各デコレータが一度ずつバスにハンドラを登録し、イベント配信時に複数回呼び出される。

**影響を受けたバージョン**: 2.2.0-dev.0 - 2.2.1-dev.0

**修正されたバージョン**: 2.2.1-dev.0

**修正内容**: `BaseEventHandler` を最適化し、各イベントタイプがアダプタに一度だけハンドラを登録できるようにし、重複トリガーを回避。

**修正日**: 2025/08/18

**重大度**: 🔴 重大

**タイプ**: イベントシステム

---

### [BUG-002] Init コマンドでアダプタの設定パスの型が間違っている

**問題**: `ep init` コマンドを使ってインタラクティブに初期化を行うと、アダプタの設定を選択した際に型エラーが発生する：

```
インタラクティブな初期化に失敗しました: 'str' と 'str' の型に対してサポートされていない演算子です
```

**原因**: 2.3.7 バージョンで設定ファイルのパスを調整する際に、メソッドのパラメータの型が一致していない。`_configure_adapters_interactive_sync` は `str` 型のパラメータを受け取るが、内部では `Path` の `/` 演算子を使ってパスを結合している。

**影響を受けたバージョン**: 2.3.7 - 2.3.9-dev.1

**修正されたバージョン**: 2.3.9-dev.1

**修正内容**: `_configure_adapters_interactive_sync` メソッドのパラメータの型を `str` から `Path` に変更し、呼び出し時に `Path` オブジェクトを直接渡す。

**修正日**: 2026/03/23

**重大度**: 🟡 中等

**タイプ**: CLI

### [BUG-003] 再起動後にコマンドイベントが無効になる

**問題**: `sdk.restart()` を呼び出した後、`@command` で登録したコマンドがトリガーされなくなり、メッセージを送信してもロボットが反応しない。

**原因**: `adapter.shutdown()` がイベントバスをクリアした後、`BaseEventHandler` の `_linked_to_adapter_bus` 状態が `False` にリセットされていないため、`_process_event` メソッドはバスに接続されたと認識し、再接続処理をスキップする。

**影響を受けたバージョン**: 2.2.x - 2.4.0-dev.2

**修正されたバージョン**: 2.4.0-dev.3

**修正内容**: `_linked_to_adapter_bus` 状態を追跡する仕組みを導入し、`_clear_handlers()` でバス接続を切断した後、次の `register()` で自動的に再接続するようにし、`shutdown`/`restart` のシナリオに対応。

**修正日**: 2026/04/09

**重大度**: 🔴 重大

**タイプ**: イベントシステム

### [BUG-004] ライフサイクルイベントハンドラがクリーンアップされない

**問題**: `sdk.restart()` の後、古いライフサイクルイベントハンドラが残存して重複発動し、同じイベントが複数回処理される。

**原因**: `lifecycle._handlers` 辞書は `uninit()` 時にクリーンアップされず、`restart` 後には古いハンドラと新しいハンドラが両方存在する。

**影響を受けたバージョン**: 2.3.0 - 2.4.0-dev.2

**修正されたバージョン**: 2.4.0-dev.3

**修正内容**: `Uninitializer` のクリーンアップ処理の末尾（すべてのイベントが送信された後）、`lifecycle._handlers` をクリアする。

**修正日**: 2026/04/09

**重大度**: 🟡 中等

**タイプ**: 実行時

### [BUG-005] Event.is_friend_add/is_friend_delete の detail_type が OB12 標準と一致しない

**問題**: `Event.is_friend_add()` は `detail_type == "friend_add"` をチェックし、`Event.is_friend_delete()` は `detail_type == "friend_delete"` をチェックしますが、OneBot12 標準では `detail_type` の値は `"friend_increase"` と `"friend_decrease"` です。`notice.py` の `on_friend_add`/`on_friend_remove` デコレータで使われている値と一致しないため、デコレータで登録したハンドラがトリガーされた際に、対応する `is_friend_add()`/`is_friend_delete()` 判定メソッドは `False` を返します。

**原因**: `wrapper.py` では非標準の命名が使われており、`notice.py` では正しい OB12 標準の命名が使われています。

**影響を受けたバージョン**: 実装以来

**修正されたバージョン**: 2.4.2-dev.1

**修正内容**: `is_friend_add()` のマッチング値を `"friend_add"` から `"friend_increase"` に、`is_friend_delete()` のマッチング値を `"friend_delete"` から `"friend_decrease"` に変更。

**修正日**: 2026/04/13

**重大度**: 🟡 中等

**タイプ**: イベントシステム

### [BUG-007] command.wait_reply() で非推奨の asyncio.get_event_loop() を使用

**影響を受けたバージョン**: 2.3.0-dev.0

**修正されたバージョン**: 2.4.2-dev.1

**修正内容**: `command.py` の 2 か所の `asyncio.get_event_loop()` を `asyncio.get_running_loop()` に置き換えました。

**修正日**: 2026/04/13

**重大度**: 🟢 軽微

### [BUG-008] Bot オフラインイベントが shutdown プロセス中に繰り返し送信される

**問題**: `adapter.shutdown()` を使ってすべてのアダプタを閉じる際に、`_update_bot_status()` が閉じるプロセス中に Bot オフラインイベントを繰り返し送信し、同じ一連の Bot が複数回オフラインとマークされ、`adapter.bot.offline` ライフサイクルイベントが複数回トリガーされます。

**原因**: 2.4.0-dev.1 で導入された Bot 状態の追跡システムは、`shutdown()` 中に「閉じ中」フラグを設定しておらず、`_update_bot_status()` は通常のオフラインと閉じるプロセス中の連鎖的なオフラインを区別できません。

**影響を受けたバージョン**: 2.4.0-dev.1 - 2.4.2-dev.1

**修正されたバージョン**: 2.4.2-dev.1

**修正内容**: `AdapterManager` に `_is_being_shutdown` フラグを追加し、`shutdown()` 開始時に True に、終了時にクリアします。`_update_bot_status()` はこのフラグをチェックして、閉じるプロセス中の重複送信をスキップします。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: アダプタ

### [BUG-009] LazyModule が同期的に BaseModule をアクセスして初期化が完了していない

**問題**: ユーザーが同期コンテキストで LazyModule の BaseModule 属性にアクセスする際に、`loop.create_task()` を使って非同期に初期化するが待機せず、初期化が完了していない状態で属性にアクセスされ、競合状態が発生します。

**原因**: `_ensure_initialized()` は BaseModule に対して `loop.create_task(self._initialize())` を使って初期化を開始した後、即座に返却しており、初期化が完了していることを保証していません。

**影響を受けたバージョン**: 2.4.0-dev.0 - 2.4.2-dev.1

**修正されたバージョン**: 2.4.2-dev.2

**修正内容**: 同期コンテキストでは、BaseModule の初期化を `asyncio.run(self._initialize())` に変更し、初期化が完了してから返すようにします。透明なプロキシの特性を保持し、ユーザーは同期/非同期の違いを意識する必要がありません。

**修正日**: 2026/04/21

**重大度**: 🟡 中等

**タイプ**: 加載システム

### [BUG-010] 複数スレッドでの設定書き込みがデータの失われを引き起こす

**問題**: 複数スレッドで `config.setConfig()` を呼び出す際に、`_flush_config()` は読み取り-変更-書き込みの操作がアトミックでなく、一部の書き込みが失われる可能性があります。

**原因**: `_flush_config()` は `RLock` を使用していますが、ファイルの読み取りと書き込みの間にはファイルロックの保護がなく、`_schedule_write` の Timer が複数回トリガーされて上書きされる可能性があります。

**影響を受けたバージョン**: 2.3.0 - 2.4.2-dev.1

**修正されたバージョン**: 2.4.2-dev.2

**修正内容**:
1. ファイルロック機構（`_file_lock`）を追加してファイル操作のアトミック性を保証
2. 一時ファイルに書き込んだ後、アトミックなリネーム（`os.replace`/`os.rename`）を行う
3. `_schedule_write` の Timer のキャンセルと再スケジュールのロジックを改善

**修正日**: 2026/04/21

**重大度**: 🔴 重大

**タイプ**: 設定システム

### [BUG-011] Windows で CTRL+C でプログラムを停止できない

**問題**: Windows で `python main.py` を直接実行した後、CTRL+C を押してもプログラムを終了できません。プログラムは正常に起動し、ルーティングサーバーの情報を出力した後、CTRL+C は全く反応せず、タスクマネージャーで強制的にプロセスを終了するしかありません。一方、`epsdk run` で起動した場合は正常に停止できますが、`epsdk run` はサブプロセスモデルで実行されます。

**原因**: Hypercorn ASGI サーバーの `serve()` 関数内部で `signal.signal(SIGINT, handler)` を使って独自の SIGINT ハンドラを登録しており、Python のデフォルトの `KeyboardInterrupt` ハンドラを上書きしています。`asyncio.create_task()` でバックグラウンドタスクとして Hypercorn を起動した場合、Hypercorn の内部のシャットダウンフローは `worker_serve` モードを想定しており、`CTRL+C` シグナルをキャッチしても何のクリーンアップ動作も起こりません。

**影響を受けたバージョン**: 2.3.6 - 2.4.2

**修正されたバージョン**: 2.4.3-dev.0

**修正内容**:
1. ASGI サーバーを Hypercorn から Uvicorn に切り替えます（`pyproject.toml` の依存関係を変更）
2. `uvicorn.Server._serve()` を直接使ってサーバーを起動し、**`capture_signals()`** シグナル処理コンテキストマネージャーを回避します
3. `server.should_exit = True` を使って優雅な停止を実現し、タイムアウトしたらバックグラウンドタスクをキャンセルします
4. 同期的にサブプロセスの実行モデルと `runtime/cleanup.py` のクリーンアップモジュールを削除します（サブプロセスのクリーンアップ機構は不要になります）

**修正日**: 2026/04/28

**重大度**: 🔴 重大

**タイプ**: CLI / 実行時

### [BUG-012] ホットリスタート後に更新されたモジュールの Python コードが有効にならない

**問題**: `sdk.restart()` を使ってソフトリスタートした後、`epsdk install` でアップグレードしたモジュール/アダプタの新しいコード（追加された API ルートなど）が有効にならず、古いロジックが実行され続けます。完全にプロセスを再起動しなければ最新のコードをロードできません。

**原因**: `_do_restart()` が再初期化の際に `entry_point.load()` を呼び出しますが、この関数は `sys.modules` からキャッシュされた古いモジュールオブジェクトを返すだけで、ディスクから再読み込みしません。

**影響を受けたバージョン**: 早期のバージョン - 2.4.3-dev.1

**修正されたバージョン**: 2.4.3-dev.1

**修正内容**: `uninit()` 後、`init()` 前に `sys.modules` にロードされたモジュール/アダプタパッケージのキャッシュをクリアし、`entry_point.load()` が最新のコードをディスクからロードできるようにします。`_collect_top_level_modules()` と `_invalidate_module_cache()` の補助メソッドを追加し、`top_level.txt` または entry-point value からトップレベルモジュール名を推定します。

**修正日**: 2026/05/03

**重大度**: 🔴 重大

**タイプ**: 加載システム / 実行時

### [BUG-027] ルーティングのリクエスト制限のクリーンアップタスクが固定ウィンドウを使用して長時間のリクエスト制限ルールが機能しない

**根本原因の経路**:

### [BUG-030] 設定の watcher 競合により setConfig 延期書き込みが静かにデータを失う

**問題**: 複数のユーザーが `config.setConfig(key, value)`（デフォルト `immediate=False`）を呼び出した後、自分のモジュールの設定が `config.toml` に書き込まれず、他のモジュールの設定は正常です。`immediate=True`（強制的に書き込み）に設定すると回避できます。実行時に書き込まれた設定は再起動後に失われ、起動時にテンプレート生成された設定は保持されます。

**原因**: 2 つの重複する欠陥：
1. **論理的な欠陥**: `_watch_loop` が `_check_file_change()` が `True` を返したときに無条件に `_dirty_keys.clear()` してすべての待機キーをクリーンアップします。しかし、`_check_file_change()` は `!=` で mtime を比較するだけです。フレームワーク自身の `_flush_config` が書き込みを行うと mtime が変化しますが、`_flush_config` は書き込み後に `_config_mtime` を更新しますが、watcher スレッドはファイルの書き込みと mtime への代入の間（および粗いファイルシステム上）で mtime の差異を観測する可能性があり、外部の変更と誤認してすべての待機キーをクリーンアップします。
2. **スレッドの欠陥**: `_watch_loop` は `_write_timer`/`_dirty_keys` を操作する際に `_lock` を取得していません。`setConfig`（`_dirty_keys` に書き込む際にロックを取得）、`_schedule_write`（`_write_timer` に書き込む際にロックを取得）とデータ競合があります。

**根本原因の経路**:
```
モジュール A setConfig(immediate=True) → flush で書き込み、mtime が変化
  → ユーザーモジュール setConfig(immediate=False) → _dirty_keys に追加、5 秒後に書き込み
    → watcher ルーポン、_check_file_change が自身の書き込みによる mtime 差異を観測
      → _dirty_keys.clear() → ユーザーモジュールの待機キーが静かにクリーンアップ
        → 再起動後に設定が欠落
```

**影響を受けたバージョン**: 2.6.0 - 2.7.0

**修正されたバージョン**: 2.7.1

**修正内容**:
1. `_last_self_write_mtime` フィールドを追加し、`_flush_config` が書き込んだ後に更新します。`_check_file_change` は mtime が変化した際にこの値と比較し、一致すれば自身の書き込みと判断して `False` を返します
2. `_watch_loop` の全体を `_lock` でロックします。実際の外部変更の際は `_dirty_keys` を保持します（マージの意味）、次回の flush は外部内容とマージされます（待機キーが優先）
3. `getConfig`/`_check_cache_validity` の経路は影響を受けません（リロードはクリーンアップをしない）

### [BUG-032] 設定の遅延書き込み中に「書き込み後直ちに読み取り」で古い値を読み取る

**問題**: `config.setConfig()`（デフォルト `immediate=False` で約 5 秒遅延）でピリオド区切りのキーを書き込んだ後、その親/祖先ノード（例：`set_erispulse_section("scope.actions.MyModule", {...})` の後で `get_erispulse_config()` を呼び出す）を直ちに読み取ると、古い値が返されます。書き込んだ子キーは「消え」、書き込みが完了するまで見えません。スコープ設定のホット更新など「書き込み-読み取り-書き込み」のシナリオに影響を受けます（2.8.0 テストプラグイン `/t_section` のケースで明らかになりました）。

**原因**: `setConfig` はピリオド区切りのキーを**フラット形式**で待機キュー `_dirty_keys` に保存し、`getConfig` の**正確なキークエリ**が待機キューにヒットするだけです。ツリー形式のパスクエリ（`getConfig("ErisPulse.scope")`）はキャッシュのみを走り、待機値を追加しません。遅延書き込み（`_flush_config` が待機キューをキャッシュにマージし、キューをクリアするまで）の間、読み-あなた-書き込みの断層が生じます。

**修正内容**: `getConfig` に待機値のマージロジックを導入します：
1. 正確にヒットする待機キーはそのまま返します（既存の動作は変更なし）
2. 待機キーがクエリキーの祖先である場合、最も長い待機祖先を取得し、残りのパスをその値のサブツリー内で解析します
3. 待機キーがクエリキーの子孫である場合、`_dirty_overlay` にマージされたサブツリーを構築し、キャッシュのサブツリーと深くマージします（`_deep_merge`、上書き優先、元のキャッシュオブジェクトを変更しない）。待機キーがない場合は元の高速パスを走り、追加のオーバーヘッドはゼロです。
