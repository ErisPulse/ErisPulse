# 常見問題（FAQ）

> [!TIP]
> **いつ読む必要があるか**：実行中に「ロボットが反応しない / メッセージが失われる / database is locked / メモリが継続的に上昇する」などの現象が発生した場合、まずはここに症状を照らし合わせて原因とトラブルシューティングの手順を確認してください。該当しない場合は、対応するトピックドキュメントをご覧ください。

## メッセージとイベント

### 群内でロボットに @ されたが、ロボットが反応しない？

順番に確認してください：

1. **複数アカウントのデプロイ + `cross_account_policy = "drop"`**：@されたアカウントのコピーには @ でのメンション優遇（必ず通す）がありますが、対象アカウントの身元口径を確認してください。バインドテーブル/所属判定には `self.user_id` と `self.account_id` の二つの口径が使用されます（[跨アカウントの重複受付](../developer-guide/adapters/core-concepts.md)を参照）
2. **`ignore_self`**：送信者が受信アカウント自身の場合、イベントはフィルタリングされます（デフォルトで有効）。自分のエコーではないか確認してください。
3. **プロセッサの条件**：`on()` で登録した `detail_type` / テキスト条件が、イベントの実際のフィールドと一致しているか確認してください。イベントに `detail_type` が欠如している場合、条件を宣言したプロセッサはマッチしなくなります。
4. **モジュールの休眠/ラジオロード**：`activate_on` がトリガーされないモジュールはロードされません（[ラジオロードと休眠](../advanced/lazy-loading.md)を参照）

### 同じメッセージに対してロボットが2回返信した？

- 複数アカウントが同じグループにいる場合：両方のアカウントがそれぞれ1つのコピーを受け取ります。`cross_account_policy` を有効にするか、`session_accounts` を設定して会話の正確な所属を指定してください（[構成](configuration.md)を参照）
- 同じ優先度の複数プロセッサが同一のイベントをマッチする場合：それぞれが独立したコピーとして並行実行され、プロセッサの `mark_processed` が後続をブロックします。あなたのプロセッサの登録条件を確認してください。

## ストレージとデータベース

### `database is locked` が繰り返し発生しますか？

SQLite のロック相互排他は**書き込みと書き込み**の間でのみ発生します（WAL では読み込みと書き込みは排他しません）。頻繁に発生する場合は順番に確認してください：

1. **長時間トランザクション**：フレームワークは、ロック保持時間が 1 秒を超えるトランザクションに対して警告を出力し、開始位置も表示します（`トランザクションは x.xx s ロックを保持しています ...`）——警告に従い、遅い処理をトランザクションブロックから移動してください。
2. **同期 API のブロッキング**：`ストレージ同期 API を非同期コンテキストで呼び出す` 警告で指摘された呼び出し箇所を a 前置きの非同期メソッド（`set` → `aset`）に移動してください——handler のタイムアウトも同じ原因で同じ方法で対処できます。上記の 1、2 番目の手順を参照してください。
3. **書き込みロックの待機**：`ErisPulse.storage.sqlite.busy_timeout` を大きくしてください（再起動で有効になります）。
4. それでも解決しない場合は → 完全なトラブルシューティングマトリクスは [ストレージバックエンド](../advanced/storage-backends.md) を参照してください。

### アップグレード後に書き込みで `StorageOperationError` が発生しますか？

2.12.0 以降、書き込み失敗は**静かに `False` を返すのではなく、例外を投げます**——アップグレード移行ガイド ([migration.md](migration.md)) に従い、try/except に変更してください。

## 実行時

### イベントハンドラが大量にタイムアウト / ロボットが断続的に反応しない？

典型的な原因：**ハンドラ内で同期ストレージAPIを呼び出している**（各呼び出しはイベントループを完了するまでブロックする）。特徴：`ストレージ同期APIを非同期コンテキストで呼び出す`の制限超過アラート + ハンドラのタイムアウトが集中して発生。対処：アラートの呼び出し箇所に従い、`aset` / `aget` / `aExecute` に移行する（[アップグレード移行ガイド](migration.md)を参照）。

### メモリが継続的に増加する場合の対応？

1. `ErisPulse.framework.memory_tracing = true` を有効にする（トラブルシューティング時に有効にし、通常は無効にする）——`/metrics` とメモリスナップショットはトレースされたメモリと最もメモリを消費しているアロケーションポイントを出力する
2. GC周期ログ内のスナップショットの傾向を観察する（`log_snapshot`）；フレームワークの自動GCタスクはメモリの増加に応じて自動的に全量回収を行う
3. ホットリロード後にメモリが大幅に増加する場合：2.12.1以降では、アンロード経路が解凍され回収される（旧バージョンの `gc.freeze` の盲点は修正済み）——フレームワークをアップグレードする
4. モジュール自身のコンテナが無制限に増加するのはモジュールの責任である——所有者コンテキストに登録してリソースを割り当てる（[所有権システム](../advanced/ownership.md)を参照）

### ホットリロード後にモジュールが「消えた」ように見える？

ホットリロードのアンロード時に所有タスクがキャンセルされ、所有リソースが回収される。モジュールが `on_unload` 以外で独自にタスクやスレッドを作成し、所有を登録していない場合、フレームワークはその対応ができない——すべて `self.spawn()` / `spawn_background(owner=...)` を使用して作成する（[所有権システム](../advanced/ownership.md)を参照）。

## 設定とデプロイ

### 設定を変えたのに効果がありませんか？

- **ホットアップデートがサポートされている**キー（例: `cross_account_policy`、`event_dedupe`、`memory_tracing`、GC パラメータ）は、変更後すぐに有効になります。
- **再起動が必要な**キー（`storage.use_global_db`、`storage.sqlite.busy_timeout`、router cors/security）は、変更時にフレームワークが「プロセスを再起動後に有効になります」というアラートを出力します。アラートが表示された場合は、必ず再起動してください。`storage.backend` の変更も同様に再起動が必要です（現在はアラートが表示されませんが、変更後は再起動をお忘れなく）。
- 編集中に構文エラーが発生した場合：フレームワークは前回有効な設定を保持し、診断情報を出力します（空の設定をブロードキャストすることはありません）。

### コンテナ内で `epsdk restart` を実行するとコンテナが終了しますか？

コンテナ内（PID 1）での `restart` は、プロセス内のソフトリスタートをトリガーする `SIGUSR1` 信号の送信に変更されました。この動作が必要な場合は、2.12.0 以上にアップグレードしてください。プロセス全体の再起動は、コンテナの再起動ポリシーに任せてください。
