# モジュールトラブルシューティングガイド

> [!TIP]
> **いつこのガイドを読むべきか**：ボットが「反応しない」とき——モジュールをインストールしたのにロードされない、コマンドを送っても応答がない、イベントハンドラーが実行されない、コードを変更して reload しても古い挙動のまま、モジュールが有効になっているのにイベントを受け取れない——症状に応じて該当するシナリオに当てはめて確認してください。不要であれば読み飛ばしても他の機能の利用には影響しません。


モジュールが「反応しない」場合は、症状に応じて該当するシナリオで切り分けます。最初の3種類のシナリオでは、フレームワークの診断ツールが直接結論を提示します：

| 症状 | 診断ツール | 切り分け対象 |
|------|---------|---------|
| モジュールがロードされない | `ErisPulse.runtime.explain_module(name)` | 登録とロードのチェーン |
| イベントに応答しない | `ErisPulse.runtime.explain_event(event)` | ディスパッチエントリーのチェック |
| コマンドが発火しない | ディスパッチ決定チェーン（テスト側 `DispatchTrace` / フレームワーク組み込み `trace`） | コマンド判定チェーン |

いずれの診断関数も**読み取り専用**の操作であり、状態を一切変更せず、いつでも呼び出せます。機械可読な dict を返し、`format_report()` を併用して人間が読めるテキストへレンダリングできます。

## シナリオ1：モジュールがロードされない

```python
from ErisPulse.runtime import explain_module, format_report

report = explain_module("MyModule")
print(format_report(report))
```

`explain_module()` は項目ごとにチェックして結論を出力し、以下の原因をカバーします：

| チェック項目 | 説明 |
|-------|------|
| 未登録 | パッケージが未インストール、entry-point グループ名の誤り、または登録名と照会名の不一致 |
| 遅延ロードにより未インスタンス化 | **正常な状態であり故障ではない**：遅延ロードモジュールは最初に呼び出されたとき（`module.call` / コマンド発火など）にのみインスタンス化される |
| 設定により無効化 | `ErisPulse.modules.status.<モジュール名> = false`（未設定ならデフォルトで有効） |
| 依存関係が未ロード | モジュールが宣言した `depends` リスト内のモジュールが未準備 |
| SDK バージョン要件未達 | モジュールのメタデータが宣言する `min_sdk_version` が現在のフレームワークバージョンより高い |
| on_load 例外 | 登録は正常だがロードされておらず、上記の原因もない場合——起動ログでモジュール名に対応する ERROR 記録を確認 |

返される dict の構造化フィールド：`registered` / `loaded` / `lazy` / `enabled`（`None` は未設定＝デフォルト有効を意味する）/ `missing_dependencies` / `sdk_version_ok` / `conclusion`（一文の結論）/ `reasons`（原因のリスト）。

## シナリオ2：イベントに応答しない

```python
from ErisPulse.runtime import explain_event, format_report

report = explain_event(event)   # ハンドラー内で受け取った Event または生のイベント dict
print(format_report(report))
```

`explain_event()` はディスパッチエントリーの実際のチェック順序に従って結論を出力します：

1. **プラットフォームアダプター未登録**：`platform` に対応するアダプターインスタンスが存在しない——イベントがそもそもフレームワークに入っていない。
2. **ID ディメンションがスコープによって拒否された**：ユーザー / セッション / Bot / アダプターがブラックリストに入っている——イベントはディスパッチエントリーで完全に破棄されます。スコープの設定については[モジュール設定](../user-guide/configuration.md)を参照してください。
3. **モジュールがセッションによってブロックされている**：現在のセッションの `available_modules`（利用可能）と `blocked_modules`（スコープによってブロック）を区別します。
4. **テキストがコマンド形式だが未ヒット**：コマンドプレフィックスは付いているが、登録済みのどのコマンドとも一致しない——プレフィックス設定とコマンド名を確認してください。

エントリーでのチェックをすべて通過しても応答がない場合は、結論として次の2点を引き続き確認するよう案内されます：

- **ハンドラーのフィルター条件**：`detail_type` / `pattern=` / `regex=` などの条件が満たされていない。
- **ミドルウェアによる拒否**：ミドルウェアが明示的に `False` を返すとイベントレベルで破棄され、`adapter.event.blocked` ライフサイクルフック（ミドルウェア名と完全なイベントを含む）が発火します——このフックを登録すれば「誰がイベントを破棄したのか」を監査できます。

## シナリオ3：コマンドが発火しない（ディスパッチ決定チェーン）

プレフィックス付きのメッセージが実際にコマンドを実行するには、以下を順に通過する必要があります：コマンドテキスト判定 → コマンドヒット判定（未ヒット時はスペル候補を提示）→ スコープ → ユーザー ACL → オーナーチェック → 権限関数 → クールダウン / レート制限 / 使用量によるサイレント破棄 → 非推奨コマンドの拒否と通知 → 引数解析 → 実行。フレームワークは各判定ポイントを因果チェーンとして記録し、「なぜ発火しなかったのか」という結論を提示します。

### テスト中：TestBot.dispatch が返す DispatchTrace

テストで問題を再現したうえで、因果チェーンを直接読むことを推奨します（ツールの使い方は[モジュールテスト](testing.md)を参照）：

```python
trace = await bot.dispatch(create_command_event("dailyx", user_id="123"))

trace.verdict          # executed / rejected / dropped / failed / no_match / passed
print(trace.explain()) # 行ごとの因果説明（現在の言語）
trace.assert_no_match()
```

### フレームワーク組み込みの trace モジュール

決定チェーンは `ErisPulse.Core.Event.trace` によって提供され、デフォルトで**ゼロオーバーヘッド**です——収集コンテキストにいない間は判定ポイントをそのままスキップするため、本番パスでは感知されません：

```python
from ErisPulse.Core.Event import (
    start_dispatch_trace,
    format_dispatch_trace,
    final_verdict,
)

with start_dispatch_trace() as records:
    ...  # 収集コンテキスト内で発生したディスパッチ（そこから派生したハンドラータスクを含む）

print(format_dispatch_trace(records))   # 人間が読める因果チェーン（現在の言語）
print(final_verdict(records))           # 総合結論
```

`final_verdict()` の戻り値：

| 結論 | 意味 |
|------|------|
| `executed` | コマンドが実行された |
| `rejected` | 権限系の判定で拒否された（スコープ / ACL / オーナー / 権限関数） |
| `dropped` | サイレントに破棄された（クールダウン / レート制限 / 使用量 / ミドルウェア拒否） |
| `failed` | 実行時にエラーが発生 |
| `no_match` | プレフィックス付きだがどのコマンドにも一致しない |
| `passed` | コマンドではないテキストとしてメッセージハンドラーに通過 |

記録は機械可読な dict（`stage` / `verdict` / `message_key` / `params`）として保存され、独自に表示する場合は `stage` でフィルターできます（例：`cooldown` のみ表示）。

### ガバナンス系サイレントヒットの見分け方

`cooldown=` / `rate_limit=` / `usage_limit=` にヒットした場合は**デフォルトでサイレント破棄**されます（コマンドは引き続き占有され、低優先度ハンドラーには漏れません）。これは「コマンドが壊れた」と誤認しやすい点です：症状としては一部のユーザーには動作し、一部のユーザーからは無応答に見え、決定チェーンには該当する `stage` の `dropped` 記録が現れます。`deprecated=` コマンドの場合は、呼び出し時に非推奨メッセージが自動返信されるという挙動を示します（`deprecated_reject=True` の場合は実行を拒否）。

## シナリオ4：コードを変更して reload しても古い挙動のまま（2.11+）

以下の順に確認してください：

1. **戻り値と失敗の現場を確認**：`reload` / `load` が `False` を返した場合は、
   直接 `sdk.module.last_error("モジュール名")` を呼び出します——例外と完全な
   traceback（エラー発生行番号を含む）が返され、ログファイルを漁る必要はありません。
   `module.get_info(モジュール名)["last_error"]` も同じ情報源です。
2. **構文エラーではアンロードされない**：reload はアンロード前に構文の事前チェックを行い、
   失敗時は拒否します（旧インスタンスが引き続き動作）。
   ログにはファイル + 行番号が表示されます。構文を修正してから再度 reload してください。
3. **同一性未変化の警告**：ログに「再ロード後にコードの同一性が変化していません」や
   イベント `identity_changed: false` が現れた場合は、プロセス内でまだ古いコードが
   動作していることを示します（C 拡張など消去できないキャッシュでよく発生します）——
   この種のモジュールはフレームワークの再起動が必要です。
4. **モジュールのソースが再インポート可能か確認**：ランタイムで登録
   （`sdk.module.register()`）されたモジュールのクラス定義が `__main__` /
   エントリースクリプト内にある場合、再インポートを拒否します（ガード警告）。
   クラスをインポート可能なモジュールファイルへ移動してください。
5. **遅延ロードモジュールが強制的にアクティブ化される**：再ロードでは、もともと
   遅延ロードだったモジュールがアクティブ化されます（明示的なログが出力されます）。
   休眠中のモジュールは休眠を維持します。

## シナリオ5：モジュールが「有効になっているのにイベントを受け取れない」（遅延ロード休眠、2.11+）

`dormant_after` を宣言している遅延ロードモジュールは、アイドル時間がしきい値を超えると
**自動的に休眠**します：ランタイムリソースが解放され、イベントハンドラーが登録解除されるため、
イベントを受け取らなくなります（`activate_on` で宣言されたイベントを除く——イベントは
まずモジュールを復帰させてから転送されます）。

- 休眠しているかどうか確認：ログで「休眠しました」を検索するか、`module.sleep` イベントを
  観察するか、`sdk.module.get_status_summary()` で該当モジュールが `loaded` で
  なくなっていることを確認
- 即時復帰：任意の属性アクセス（`sdk.モジュール名.任意属性`）または
  `await sdk.module.call(...)`
- 自動休眠を望まない場合：`get_load_strategy()` 内の `dormant_after` 宣言を削除
- 状態が失われるかどうか：休眠前には `on_before_unload(reason="dormant")` が発火します。
  モジュールがこのフックで状態保存を実装していない場合、休眠時にメモリ上の状態は
  失われます（アンロードと同様）——状態を引き継ぎたい場合は
  [遅延ロード休眠](../advanced/lazy-loading.md#遅延ロード休眠dormant_after)を参照してください

## 共通のアドバイス

- 切り分けの前に、まずログレベルを `DEBUG` / `TRACE` に上げてください（設定は[開発者ガイド](README.md#デバッグのコツ)を参照）。モジュールのロード、ルート登録、イベントディスパッチなど、フレームワーク内部の流れが確認できます。
- `explain_module` / `explain_event` はいつでも呼び出せ、読み取り専用で副作用がないため、運用コマンドや管理パネルに直接組み込むのに適しています。
- 「コマンドが発火しない」系の問題は、まず `DispatchTrace` のアサーションテストを書いて再現するのがおすすめです——`assert_executed` / `assert_rejected` などのアサーションが失敗すると、完全な因果チェーンが自動的に添付されます。

## それでも問題が解決しない場合

- **まず既知の問題を確認**：[バグトラッカー](../bug-tracker.md)と照合し、記録済みの問題かどうか、およびその回避方法を確認します。
- **フィードバックの提出**：[GitHub Issues](https://github.com/ErisPulse/ErisPulse/issues) で問題を報告する際は、`explain_module` / `explain_event` の出力、`DispatchTrace` の因果チェーン、フレームワークのバージョン番号を添付すると、問題特定の時間を大幅に短縮できます。
- **議論と質問**：バグかどうか判断できない場合は、まず [Discussions](https://github.com/ErisPulse/ErisPulse/discussions) で症状と再現手順を説明してください。
